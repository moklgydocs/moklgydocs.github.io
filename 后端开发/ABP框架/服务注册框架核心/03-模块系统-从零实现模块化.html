模块系统 - 从零实现模块化

03 - 模块系统：从零实现模块化

模块系统是整个框架的骨架。本章从零开始，一步步实现一个完整的模块化系统。

第一步：定义模块接口

模块的生命周期分为两个大阶段：

  1. 服务配置阶段（在 DI 容器构建之前） — 注册服务到 IServiceCollection
  2. 应用运行阶段（在 DI 容器构建之后） — 从 IServiceProvider 解析服务

每个阶段又细分为 Pre / Main / Post 三个子阶段：

服务配置阶段（容器构建前）：
  PreConfigureServices     → 预处理，如注册选项验证器
  ConfigureServices        → 核心，注册服务
  PostConfigureServices    → 后处理，如修改已注册的服务

应用运行阶段（容器构建后）：
  OnApplicationInitialization  → 应用启动时执行
  OnApplicationShutdown        → 应用关闭时执行

IMokFrameworkModule 接口

// 文件：MokFramework.Core/Modularity/IMokFrameworkModule.cs

public interface IMokFrameworkModule
{
    // === 服务配置阶段（同步） ===
    void PreConfigureServices(ServiceConfigurationContext context);
    void ConfigureServices(ServiceConfigurationContext context);
    void PostConfigureServices(ServiceConfigurationContext context);

    // === 应用运行阶段（同步） ===
    void OnApplicationInitialization(ApplicationInitializationContext context);
    void OnApplicationShutdown(ApplicationShutdownContext context);

    // === 异步版本（与同步一一对应） ===
    Task PreConfigureServicesAsync(ServiceConfigurationContext context);
    Task ConfigureServicesAsync(ServiceConfigurationContext context);
    Task PostConfigureServicesAsync(ServiceConfigurationContext context);
    Task OnApplicationInitializationAsync(ApplicationInitializationContext context);
    Task OnApplicationShutdownAsync(ApplicationShutdownContext context);
}

为什么同时有同步和异步？

  • 大部分模块只需要同步方法（注册服务本身是同步的）
  • 少数场景需要异步（如初始化时从远程读取配置）
  • 基类提供默认实现：异步方法调用同步方法 + 返回 Task.CompletedTask
  • 这样既保持向后兼容，又支持异步场景

上下文对象

// 服务配置阶段的上下文
public class ServiceConfigurationContext
{
    public IServiceCollection Services { get; }
    public IDictionary<string, object?> Items { get; }  // 模块间共享数据

    public object? this[string key]
    {
        get => Items.GetValueOrDefault(key);
        set => Items[key] = value;
    }
}

// 应用初始化阶段的上下文
public class ApplicationInitializationContext
{
    public IServiceProvider ServiceProvider { get; }
}

// 应用关闭阶段的上下文
public class ApplicationShutdownContext
{
    public IServiceProvider ServiceProvider { get; }
}

为什么用上下文对象而不是直接传参？

  • 可扩展：未来增加新参数不需要改接口
  • Items 字典允许模块间传递数据（如 Module A 计算出的结果，Module B 需要使用）

第二步：实现模块基类

// 文件：MokFramework.Core/Modularity/MokFrameworkModule.cs

public abstract class MokFrameworkModule : IMokFrameworkModule
{
    // 由框架在 ConfigureModuleServices 时设置，完成后清除
    internal ServiceConfigurationContext? ServiceConfigurationContext { get; set; }

    // === 同步方法：空实现，子类按需覆盖 ===
    public virtual void PreConfigureServices(ServiceConfigurationContext context) { }
    public virtual void ConfigureServices(ServiceConfigurationContext context) { }
    public virtual void PostConfigureServices(ServiceConfigurationContext context) { }
    public virtual void OnApplicationInitialization(ApplicationInitializationContext context) { }
    public virtual void OnApplicationShutdown(ApplicationShutdownContext context) { }

    // === 异步方法：默认调用同步版本（向后兼容） ===
    public virtual Task PreConfigureServicesAsync(ServiceConfigurationContext context)
    {
        PreConfigureServices(context);
        return Task.CompletedTask;
    }
    // ... 其他异步方法同理

    // === 辅助方法 ===

    /// <summary>
    /// 验证一个类型是否是有效的模块
    /// </summary>
    public static bool IsModule(Type type)
    {
        return type.IsClass
            && !type.IsAbstract
            && !type.IsGenericType
            && typeof(MokFrameworkModule).IsAssignableFrom(type);
    }

    /// <summary>
    /// Options 模式的便捷方法
    /// </summary>
    protected void Configure<TOptions>(Action<TOptions> configureOptions)
        where TOptions : class
    {
        ServiceConfigurationContext?.Services.Configure(configureOptions);
    }
}

关键设计点：

  1. ServiceConfigurationContext 属性用 internal set — 只有框架内部能设置
  2. 异步方法默认调用同步方法 — 用户只需覆盖一种
  3. IsModule() 排除抽象类和泛型类 — 防止注册基类或泛型定义

第三步：声明模块依赖

// 文件：MokFramework.Core/Modularity/DependsOnAttribute.cs

[AttributeUsage(AttributeTargets.Class, AllowMultiple = true)]
public class DependsOnAttribute : Attribute
{
    public Type[] DependedModuleTypes { get; }

    public DependsOnAttribute(params Type[] dependedModuleTypes)
    {
        DependedModuleTypes = dependedModuleTypes;
    }
}

使用方式：

[DependsOn(typeof(InfrastructureModule))]
[DependsOn(typeof(MokFrameworkAspNetCoreModule))]
public class AppModule : MokFrameworkModule { }

// 或者合并写
[DependsOn(typeof(InfrastructureModule), typeof(MokFrameworkAspNetCoreModule))]
public class AppModule : MokFrameworkModule { }

为什么用 AllowMultiple = true？

因为写多个 [DependsOn] 比写一个长长的列表更清晰，特别是依赖多个模块时。

第四步：模块描述符

// 文件：MokFramework.Core/Modularity/ModuleDescriptor.cs

public class ModuleDescriptor
{
    public Type ModuleType { get; }
    public MokFrameworkModule Instance { get; }
    public List<ModuleDescriptor> Dependencies { get; } = new();

    public ModuleDescriptor(Type moduleType, MokFrameworkModule instance)
    {
        ModuleType = moduleType;
        Instance = instance;
    }
}

ModuleDescriptor 是模块依赖图中的节点，包含：

  • 模块的类型信息
  • 模块的实例（通过 Activator.CreateInstance 创建）
  • 依赖的其他模块（有向边）

第五步：模块加载器 — 核心算法

模块加载器是模块系统的核心，它要完成：

  1. 递归发现：从启动模块出发，沿 [DependsOn] 链递归发现所有模块
  2. 去重：同一个模块类型只创建一个实例
  3. 拓扑排序：确保被依赖的模块排在前面

递归发现

// 文件：MokFramework.Core/Modularity/ModuleLoader.cs

public List<ModuleDescriptor> LoadModules(IServiceCollection services, Type startupModuleType)
{
    // 1. 递归发现所有模块
    var descriptors = GetModuleDescriptors(startupModuleType);
    // 2. 建立描述符之间的依赖引用
    SetDependencies(descriptors);
    // 3. 拓扑排序
    return TopologicalSort(descriptors);
}

private Dictionary<Type, ModuleDescriptor> GetModuleDescriptors(Type startupModuleType)
{
    var descriptors = new Dictionary<Type, ModuleDescriptor>();
    FillModuleDescriptors(descriptors, startupModuleType);
    return descriptors;
}

private void FillModuleDescriptors(Dictionary<Type, ModuleDescriptor> descriptors, Type moduleType)
{
    // 去重：已发现的模块不再处理
    if (descriptors.ContainsKey(moduleType))
        return;

    // 验证是有效的模块类型
    if (!MokFrameworkModule.IsModule(moduleType))
        throw new ArgumentException($"Type {moduleType.FullName} is not a valid module.");

    // 创建模块实例
    var instance = (MokFrameworkModule)Activator.CreateInstance(moduleType)!;
    descriptors[moduleType] = new ModuleDescriptor(moduleType, instance);

    // 递归处理所有依赖
    foreach (var dependedType in GetDependedModuleTypes(moduleType))
    {
        FillModuleDescriptors(descriptors, dependedType);
    }
}

private static IEnumerable<Type> GetDependedModuleTypes(Type moduleType)
{
    return moduleType
        .GetCustomAttributes<DependsOnAttribute>(true)
        .SelectMany(attr => attr.DependedModuleTypes);
}

算法说明：

假设模块依赖关系为：AppModule → InfrastructureModule

FillModuleDescriptors(AppModule)
  ├── 创建 AppModule 实例
  ├── 发现 [DependsOn(InfrastructureModule)]
  └── FillModuleDescriptors(InfrastructureModule)
       └── 创建 InfrastructureModule 实例（无更多依赖）

拓扑排序（DFS）

private static List<ModuleDescriptor> TopologicalSort(Dictionary<Type, ModuleDescriptor> descriptors)
{
    var sorted = new List<ModuleDescriptor>();
    var visited = new HashSet<Type>();     // 已完成的节点
    var visiting = new HashSet<Type>();    // 正在访问的节点（用于检测环）

    foreach (var descriptor in descriptors.Values)
    {
        TopologicalSortVisit(descriptor, descriptors, sorted, visited, visiting);
    }

    return sorted;
}

private static void TopologicalSortVisit(
    ModuleDescriptor descriptor,
    Dictionary<Type, ModuleDescriptor> all,
    List<ModuleDescriptor> sorted,
    HashSet<Type> visited,
    HashSet<Type> visiting)
{
    var type = descriptor.ModuleType;

    // 已处理完毕
    if (visited.Contains(type)) return;

    // 检测循环依赖：正在处理中又遇到了 → 有环！
    if (visiting.Contains(type))
        throw new InvalidOperationException(
            $"Circular dependency detected for module: {type.FullName}");

    visiting.Add(type);

    // 先递归处理所有依赖（DFS）
    foreach (var dependency in descriptor.Dependencies)
    {
        TopologicalSortVisit(dependency, all, sorted, visited, visiting);
    }

    visiting.Remove(type);
    visited.Add(type);
    sorted.Add(descriptor);  // 所有依赖都已入队，自己才入队
}

拓扑排序原理：

DFS 后序遍历天然产生拓扑序。当一个节点的所有依赖都已加入结果列表后，它才被加入。

输入：AppModule → InfrastructureModule

DFS 过程：
  Visit(AppModule)
    Visit(InfrastructureModule)
      无依赖 → sorted = [InfrastructureModule]
    sorted = [InfrastructureModule, AppModule]

结果：[InfrastructureModule, AppModule]  ✅ 被依赖的在前

循环依赖检测：

使用 visiting 集合（灰色标记）。如果 DFS 过程中遇到一个正在访问中的节点，说明存在环。

A → B → C → A  ❌ 循环！

Visit(A)          visiting = {A}
  Visit(B)        visiting = {A, B}
    Visit(C)      visiting = {A, B, C}
      Visit(A)    A 在 visiting 中！→ throw CircularDependency

第六步：模块管理器

// 文件：MokFramework.Core/Modularity/ModuleManager.cs

public class ModuleManager : IModuleManager
{
    private readonly List<ModuleDescriptor> _modules;
    private readonly ILogger<ModuleManager> _logger;

    public ModuleManager(List<ModuleDescriptor> modules, ILogger<ModuleManager> logger)
    {
        _modules = modules;
        _logger = logger;
    }

    /// <summary>
    /// 初始化：按拓扑序（正序）
    /// </summary>
    public async Task InitializeModulesAsync(ApplicationInitializationContext context)
    {
        foreach (var module in _modules)  // 正序：依赖在前
        {
            _logger.LogDebug("Initializing module: {Module}", module.ModuleType.Name);
            await module.Instance.OnApplicationInitializationAsync(context);
        }
    }

    /// <summary>
    /// 关闭：按拓扑序的逆序
    /// </summary>
    public async Task ShutdownModulesAsync(ApplicationShutdownContext context)
    {
        var reversedModules = _modules.AsEnumerable().Reverse();

        foreach (var module in reversedModules)  // 逆序：依赖者先关闭
        {
            try
            {
                await module.Instance.OnApplicationShutdownAsync(context);
            }
            catch (Exception ex)
            {
                // 关闭时不抛异常，确保所有模块都有机会清理
                _logger.LogError(ex, "Error shutting down module: {Module}",
                    module.ModuleType.Name);
            }
        }
    }
}

为什么初始化和关闭的顺序相反？

  • 初始化：被依赖的先初始化（Infrastructure 先于 App），确保上游服务就绪
  • 关闭：依赖者先关闭（App 先于 Infrastructure），确保不会在关闭过程中访问已释放的服务

为什么关闭时吞异常？

一个模块关闭失败不应该阻止其他模块的清理。所有模块都应该有机会释放资源。

完整生命周期流程

CreateAsync<AppModule>()
│
├── 1. ModuleLoader.LoadModules(AppModule)
│   ├── 递归发现: AppModule → InfrastructureModule
│   ├── 拓扑排序: [InfrastructureModule, AppModule]
│   └── 返回有序的 ModuleDescriptor 列表
│
├── 2. RegisterCoreServices()
│   ├── 注册 IMokFrameworkApplication (self)
│   ├── 注册 List<ModuleDescriptor>
│   ├── 注册 IModuleManager / ModuleManager
│   ├── 注册 IModuleLoader / ModuleLoader
│   └── 注册每个模块实例为 Singleton
│
├── 3. ConfigureModuleServicesAsync()
│   │
│   ├── Phase 1: PreConfigureServices
│   │   ├── InfrastructureModule.PreConfigureServicesAsync()
│   │   └── AppModule.PreConfigureServicesAsync()
│   │
│   ├── Phase 2: ConfigureServices
│   │   ├── ConventionalRegistrar.RegisterAssembly(InfrastructureModule 的程序集)
│   │   ├── InfrastructureModule.ConfigureServicesAsync()
│   │   ├── ConventionalRegistrar.RegisterAssembly(AppModule 的程序集)
│   │   └── AppModule.ConfigureServicesAsync()
│   │
│   └── Phase 3: PostConfigureServices
│       ├── InfrastructureModule.PostConfigureServicesAsync()
│       └── AppModule.PostConfigureServicesAsync()
│
├── 4. InitializeAsync()
│   ├── BuildServiceProvider()（仅 InternalServiceProvider 模式）
│   └── ModuleManager.InitializeModulesAsync()
│       ├── InfrastructureModule.OnApplicationInitializationAsync()
│       └── AppModule.OnApplicationInitializationAsync()
│
└── 5. ShutdownAsync()（逆序）
    └── ModuleManager.ShutdownModulesAsync()
        ├── AppModule.OnApplicationShutdownAsync()
        └── InfrastructureModule.OnApplicationShutdownAsync()

注意 Phase 2 中 ConventionalRegistrar 在每个模块的 ConfigureServices 之前执行。
这意味着模块可以在 ConfigureServices 中覆盖约定注册器的默认行为。
