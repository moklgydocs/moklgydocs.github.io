一、编译错误记录

E1：#[embassy_executor::task] 不允许泛型参数

错误代码：

// 尝试用泛型 I2C trait 抽象，方便单元测试注入 mock
#[embassy_executor::task]
async fn sensor_loop<I>(i2c: I)
where
    I: embedded_hal_async::i2c::I2c + 'static,
{
    // ...
}

编译错误：

error: task functions must not be generic
  --> src/main.rs:15:1
   |
15 | async fn sensor_loop<I>(i2c: I)
   | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
   |
   = note: this error originates in the attribute macro `embassy_executor::task`

原因分析：

Embassy executor 在编译期为每个 task 分配一个 TaskStorage<F> 结构体，其大小必须在编译期确定。泛型参数 I 导致 Future 大小随类型变化，破坏静态分配的前提。

修复方案：使用 HAL 提供的具体类型替代 trait bound：

// ✅ 使用具体的 embassy-rp 类型
#[embassy_executor::task]
async fn sensor_loop(
    i2c: embassy_rp::i2c::I2c<'static, I2C0, embassy_rp::i2c::Async>,
    uart_tx: embassy_rp::uart::UartTx<'static, UART0, embassy_rp::uart::Blocking>,
) -> ! {
    // ...
}

对 C# 开发者的类比：

这相当于 C# IL2CPP AOT 编译时，泛型方法必须在发布前被具体类型实例化。Embassy task 宏是编译期 AOT，不支持运行时泛型分发。

E2：no_std 中不能使用 format! 宏

错误代码：

// 想用 format! 生成 JSON 字符串
let json = format!(
    r#"{{"ts":{},"temp":{:.1},"hum":{:.1}}}"#,
    ts_ms, temp, hum
);

编译错误：

error[E0433]: failed to resolve: use of undeclared crate or module `alloc`
  --> src/reporter/uart.rs:12:15
   |
12 |     let json = format!(...);
   |                ^^^^^^ use of undeclared crate or module `alloc`

error[E0463]: can't find crate for `std`

两个子问题：

  1. format! 需要 alloc::string::String，而 #![no_std] 禁用了 alloc
  2. 即使加 extern crate alloc，RP2040 也没有默认的 global allocator（违反 AC4）

修复方案：使用 heapless::String<N> + core::fmt::Write + write!：

use core::fmt::Write;
use heapless::String;

fn format_json(ts_ms: u64, reading: &SensorReading) -> String<128> {
    let mut buf: String<128> = String::new();

    // 整数 × 10 格式化，避免浮点（Cortex-M0+ 无 FPU）
    let t = reading.temperature_decidegrees;
    let sign = if t < 0 { "-" } else { "" };
    let t_abs = t.unsigned_abs();
    let h = reading.humidity_decipercent;

    // write! 宏对 no_std heapless::String 有效
    write!(
        buf,
        "{{\"ts\":{},\"temp\":{}{}.{},\"hum\":{}.{}}}",
        ts_ms,
        sign, t_abs / 10, t_abs % 10,
        h / 10, h % 10
    )
    .ok(); // heapless::String 满了返回 Err，此处 ignore（128 字节足够）

    buf
}

关键认知：

  • write! 宏来自 core::fmt，在 no_std 中可用
  • heapless::String<N> 实现了 core::fmt::Write，因此 write! 能写入
  • .ok() 处理容量溢出（String<128> 容纳 JSON 绰绰有余）

E3：embassy-rp 的 time-driver feature 缺失

错误代码（Cargo.toml 漏了关键 feature）：

[dependencies]
embassy-rp = { version = "0.9.0", features = ["defmt"] }  # 缺少 time-driver

编译错误：

error[E0433]: failed to resolve: use of undeclared crate or module `embassy_time`
  --> src/main.rs:5:5
   |
5  |     embassy_time::Timer::after_millis(80).await;
   |                   ^^^^^ use of undeclared crate or module `embassy_time`

note: `embassy-time` requires a time driver, enable one of:
      - `embassy-rp/time-driver`
      - `embassy-stm32/time-driver-*`
      - `embassy-nrf/time-driver-*`

原因：embassy-time 是抽象层，需要平台的 time-driver feature 提供底层计时支持（RP2040 使用 Timer peripheral）。

修复：

embassy-rp = { version = "0.9.0", features = [
    "defmt",
    "time-driver",          ← 必须！
    "critical-section-impl",
] }

E4：task 参数需要 'static 生命周期

错误代码：

#[embassy_executor::main]
async fn main(spawner: Spawner) {
    let p = embassy_rp::init(Default::default());

    // 局部变量 —— 生命周期 < 'static
    let i2c = i2c::I2c::new_async(p.I2C0, p.PIN_5, p.PIN_4, Irqs, I2cConfig::default());

    // 试图传递局部变量给 task
    spawner.spawn(sensor_loop(i2c)).unwrap();
    // 'main 函数返回后 i2c 被释放，但 task 还在运行 → 悬空引用！
}

编译错误：

error[E0597]: `i2c` does not live long enough
   |
   | spawner.spawn(sensor_loop(i2c)).unwrap();
   |                            ^^^ borrowed value does not live long enough
   |
   = note: task requires `'static` lifetime

修复：RP2040 的 embassy_rp::init() 返回的外设 handle 具有 'static 生命周期（外设寄存器地址永不失效），直接移动到 task，不通过引用：

// ✅ Peripherals 移动（不是借用）给 task，类型自动推断为 'static
let i2c: I2c<'static, I2C0, Async> = I2c::new_async(
    p.I2C0, p.PIN_5, p.PIN_4, Irqs, I2cConfig::default()
);
// i2c 的生命周期绑定到 I2C0 peripheral，后者是 RP2040 静态地址 → 'static ✓
spawner.spawn(sensor_loop(i2c, uart_tx)).unwrap();
// main() 此后可以 loop {}，其生命周期不影响已移入 task 的外设

对 C# 开发者的类比：

这相当于将 IDisposable 对象的所有权转给一个后台 Task。Rust 的借用检查器在编译期保证没有悬空引用——C# 靠 GC，Rust 靠所有权规则。

E5：I²C 错误类型不匹配，? 不能直接用

错误代码：

pub async fn init(&mut self, i2c: &mut I2c<'_, I2C0, Async>) -> Result<(), SensorError> {
    i2c.write(AHT20_ADDR, &CMD_INIT).await?;  // ❌ 类型不匹配
    // ...
}

编译错误：

error[E0277]: `?` couldn't convert the error to `SensorError`
  --> src/sensor/aht20.rs:42:47
   |
42 |     i2c.write(AHT20_ADDR, &CMD_INIT).await?;
   |                                            ^ the trait `From<embassy_rp::i2c::Error>`
   |                                              is not implemented for `SensorError`

原因：? 运算符自动调用 From::from(e) 转换错误类型，而 SensorError 没有为 embassy_rp::i2c::Error 实现 From。

修复方案：使用 .map_err(|_| SensorError::I2c)?：

// ✅ 显式映射错误类型
i2c.write(AHT20_ADDR, &CMD_INIT).await
    .map_err(|_| SensorError::I2c)?;

为什么不实现 From<i2c::Error>？

在 no_std 环境中，i2c::Error 是泛型类型 ErrorKind（不同 HAL 实现各自的 I²C 错误）。在嵌入式驱动中，通常只关心"成功 / I²C 失败"的粗粒度结果，详细 I²C 错误通过 defmt::error! 记录，不需要在错误链中传播。

E6：bind_interrupts! 宏放置位置错误

错误代码（放在 sensor/aht20.rs 中）：

// ❌ bind_interrupts! 必须在使用外设的 crate 根或 main.rs 中
bind_interrupts!(struct Irqs {
    I2C0_IRQ => i2c::InterruptHandler<I2C0>;
});

错误：

error[E0412]: cannot find type `Irqs` in this scope
  --> src/main.rs:25:43

修复：bind_interrupts! 必须在 main.rs 或 lib.rs 中定义，因为它会生成一个实现 Handler trait 的结构体，需要在整个 crate 可见；在子模块中定义不会自动导出：

// main.rs（crate 根）
use embassy_rp::{bind_interrupts, i2c, peripherals::I2C0};

bind_interrupts!(struct Irqs {
    I2C0_IRQ => i2c::InterruptHandler<I2C0>;
});

// sensor/aht20.rs 中传入 Irqs 时通过 crate::Irqs 引用

二、架构决策记录（ADR）

ADR-1：Embassy vs RTIC vs bare-metal

背景：实现 RP2040 上的周期性采集 + UART 上报，有 Embassy、RTIC、bare-metal 三个主流选择。

Embassy ✅ 选用：

  • async/await 语法与已掌握的 tokio 完全一致，认知迁移成本最低
  • #[embassy_executor::task] 内置定时器集成，Timer::after_millis 无需手动配置
  • 官方对 RP2040 有一级支持（embassy-rp crate）

RTIC (Real-Time Interrupt-driven Concurrency)：

  • 基于中断优先级的并发模型，没有 async/await
  • 对有 C# async 背景的开发者心智负担较高
  • 更适合硬实时场景（优先级调度有严格延迟保证）

bare-metal（main loop + 轮询）：

  • 最简单，但"忙等"80ms 期间 CPU 空转，无法并发其他任务
  • Flash 最小，但无法扩展多任务

结论：本项目只有一个采集任务，bare-metal 也够用，但选 Embassy 是为了掌握工程能力，为后续更复杂的多任务嵌入式系统打基础。

ADR-2：AHT20 驱动设计——借用 I²C vs 拥有 I²C

方案 A（拥有 I²C）：

pub struct Aht20 {
    i2c: I2c<'static, I2C0, Async>,  // Aht20 拥有 I²C 总线
}

问题：I²C 总线被 Aht20 独占，无法再挂载其他 I²C 设备（如 OLED 显示屏）。

方案 B（借用 I²C） ✅ 选用：

pub struct Aht20 {
    initialized: bool,               // 只存轻量状态
}

impl Aht20 {
    pub async fn read(&mut self, i2c: &mut I2c<'_, I2C0, Async>) -> Result<SensorReading, SensorError>;
}

优点：

  • I²C 总线在 task 中持有，驱动每次调用时借用
  • 可以在同一个任务里同时驱动 AHT20 + 其他 I²C 设备
  • 符合 embedded-hal 社区惯例

结论：方案 B，驱动只存必要状态（initialized flag），I²C handle 由调用方持有。

ADR-3：时间戳方案——ms since boot vs UTC

方案 A（UTC 时间）：需要 RTC 模块或 GPS，RP2040 无内置 RTC；通过 UART 从上位机同步时间，增加协议复杂度。

方案 B（ms since boot） ✅ 选用：

let ts_ms = embassy_time::Instant::now().as_millis();
  • 零硬件依赖，embassy-time 提供
  • 上位机收到后根据首条数据对齐绝对时间（加一个固定偏移量）
  • RP2040 Timer 精度 ±1μs，误差 < 0.01%

结论：使用 Instant::now().as_millis() 作为相对时间戳，上位机负责换算 UTC。

ADR-4：panic 处理——panic-probe vs panic-halt

panic-probepanic-halt
Flash 开销+8KB（包含文件/行号字符串）~200 字节
行为RTT 输出 panic 位置，然后断点立即停止执行（loop {}）
适用开发/调试阶段生产部署

决策：Cargo feature 分开处理：

# 开发模式：cargo build（默认 dev profile）
panic-probe = { version = "0.3.2", features = ["print-defmt"] }

生产刷机时通过 Cargo.toml 注释替换：panic-halt = "0.2" 节省 ~8KB Flash。

本文档的 Flash 验收（AC1）使用 panic-probe 测量，实际部署可切换到 panic-halt 进一步缩小。

ADR-5：浮点运算策略

AHT20 原始值到温度/湿度的转换公式涉及除法（/ 2^20）和乘法：

T(°C) = raw_temp / 1,048,576 × 200 - 50
H(%RH) = raw_hum  / 1,048,576 × 100

方案 A（浮点）：f32 计算直观，但 Cortex-M0+ 无 FPU，软件浮点库 libgcc_s 增加 ~8-12KB Flash。

方案 B（整数 × 10，移位运算） ✅ 选用：

// 2^20 = 1,048,576，用移位替代除法
// humidity_decipercent = (raw_hum * 1000) >> 20
let raw_hum: u32 = ((buf[1] as u32) << 12) | ((buf[2] as u32) << 4) | ((buf[3] as u32) >> 4);
let humidity_decipercent = ((raw_hum as u64 * 1_000) >> 20) as u16;

// temperature_decidegrees = ((raw_temp * 2000) >> 20) - 500
let raw_temp: u32 = (((buf[3] & 0x0F) as u32) << 16) | ((buf[4] as u32) << 8) | (buf[5] as u32);
let temperature_decidegrees = (((raw_temp as u64 * 2_000) >> 20) as i32 - 500) as i16;

注意 raw_hum * 1000 可能超过 u32 上限（最大 ~20 亿，乘 1000 超 u32），用 u64 中间算再右移。

Flash 节省：无浮点运算，不链接 soft-float 库，节省约 10KB Flash。

3.2 AHT20 初始化调试

初版代码在 init() 后立刻调用 read()，发现 AHT20 返回 status = 0x1C（Busy 位 = 0，但没有等待足够初始化时间）：

// AHT20 上电后需要 40ms 初始化时间，随后发 0xBE 初始化命令
// 实测：0xBE 命令发出后需要额外 10ms 校准才可读取
Timer::after_millis(40).await;   // 上电等待
i2c.write(AHT20_ADDR, &CMD_INIT).await.map_err(|_| SensorError::I2c)?;
Timer::after_millis(10).await;   // 初始化命令执行等待

通过逻辑分析仪确认时序后 defmt 日志正常。

3.3 JSON 格式化时负温度处理

测试时发现 temperature_decidegrees = -23（-2.3°C）格式化错误：

// Bug：输出 {"temp":-0.3} 而非 {"temp":-2.3}
write!(buf, "{}{}.{}", sign, t_abs / 10, t_abs % 10)
// t = -23, t_abs = 23 (u16), t_abs/10 = 2, t_abs%10 = 3 → 正确
// t = -3,  t_abs = 3  (u16), t_abs/10 = 0, t_abs%10 = 3 → "-0.3" ✓

实际上 -23 / 10 = 2, -23 % 10 = 3 在 Rust i16 中：(-23i16).unsigned_abs() = 23u16，23 / 10 = 2, 23 % 10 = 3，格式化正确。验证了所有负数分支后，逻辑无误。
