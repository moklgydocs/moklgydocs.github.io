一、【Dev】真实遇到的编译错误

错误 1：httparse::Status::Partial 的处理——不能 ? 直接展开

场景：第一次写解析循环时，想把 httparse::parse 的结果直接 ? 传播。

// ❌ Status::Partial 不是错误，不能用 ? 传播
let n = req.parse(&buf)?;   // 编译错误：Status<usize> 没有实现 Try
                             // error: the `?` operator can only be used on Result / Option

根本原因：httparse::Request::parse() 返回 Result<Status<usize>, Error>，其中 Status 是：

pub enum Status<T> {
    Complete(T),   // 解析完成，T 是消耗掉的字节数
    Partial,       // 数据不足，需要继续读取
}

Status 不实现 Try，因为 Partial 不是"错误"——它是正常的中间状态，必须显式处理。

修复：使用 match 显式处理 Partial 作为"继续读取"的信号：

// ✅ 显式处理 Partial 状态
loop {
    let mut headers = [httparse::EMPTY_HEADER; 64];
    let mut req     = httparse::Request::new(&mut headers);

    match req.parse(&buf) {
        Ok(httparse::Status::Complete(n)) => {
            // headers 解析完毕，n 是含 \r\n\r\n 的 headers 区字节数
            let method  = req.method.unwrap().to_string();
            let path    = req.path.unwrap().to_string();
            // ... 消费 headers 区，读 body
            break;
        }
        Ok(httparse::Status::Partial) => {
            // 正常中间状态：TCP 数据尚未完整到达
            // 继续 loop，从 socket 读更多数据
        }
        Err(e) => return Err(ServerError::BadRequest(e.to_string())),
    }

    // 读取更多数据后再试（在 loop 底部）
    let n = reader.read_buf(&mut buf).await?;
    if n == 0 { return Err(ServerError::ConnectionClosed); }
}

错误 2：httparse headers 数组的生命周期

场景：想在循环外定义 headers_storage，循环内重复使用。

// ❌ headers_storage 的生命周期与 req 绑定，写法容易出现借用冲突
let mut headers_storage = [httparse::EMPTY_HEADER; 64];  // 在循环外
loop {
    let mut req = httparse::Request::new(&mut headers_storage);
    match req.parse(&buf) {
        Ok(httparse::Status::Complete(_)) => {
            let method = req.method.unwrap();       // req 借用了 headers_storage
            headers_storage[0].name = "foo";        // ❌ 同时借用了 headers_storage
        }
        // ...
    }
}

根本原因：httparse::Request<'a> 的生命周期 'a 同时绑定到 headers_storage（写入解析结果）和 buf（读取 headers 数据）。在 Complete 分支里提取完数据之前，不能修改其中任何一个。

修复：将 headers 数组放在循环内部（与 req 同作用域），解析后立即提取所需数据，再 break：

// ✅ headers 数组在循环内，req 解析完就立即提取数据，借用不越界
loop {
    let mut storage = [httparse::EMPTY_HEADER; 64];  // ← 每次循环重建
    let mut req     = httparse::Request::new(&mut storage);

    if let Ok(httparse::Status::Complete(n)) = req.parse(&buf) {
        // 从 req 借用中提取数据
        let method  = req.method.unwrap_or("GET").to_string(); // to_string() 终止借用
        let path    = req.path.unwrap_or("/").to_string();
        let version = req.version.unwrap_or(1);

        // 提取 headers（借用 req，遍历完后终止）
        let mut map = HashMap::new();
        for h in req.headers.iter() {
            let name  = h.name.to_ascii_lowercase();
            let value = String::from_utf8_lossy(h.value).into_owned();
            map.insert(name, value);
        }
        // req、storage 的借用在此 block 结束时释放
        // 现在可以安全使用 buf 了
        let _ = buf.split_to(n);
        break; // 提取完数据才 break（不在借用存活时 break）
    }
    // ...
}

错误 3：buf.split_to(n) 后 buffer 数据意外丢失

场景：keep-alive 连接上第二个请求解析失败，发现 buf 里有半个请求的数据。

// ❌ 错误：split_to 之前未检查 buf 长度，导致 panic 或数据截断
let _ = buf.split_to(header_end);  // header_end 可能超过 buf.len()

根本原因：BytesMut::split_to(n) 要求 n <= self.len()，否则 panic。
另外，split_to 返回 [0..n) 的内容并就地修改 buf 使其仅包含 [n..]——这是零拷贝的关键，但也意味着原始数据真的从 buf 里删除了，不能重读。

修复：永远在 Status::Complete(n) 分支内调用，此时 n <= buf.len() 由 httparse 保证：

// ✅ Complete(n) 意味着 n 字节已经成功解析，buf 中的这些字节可以丢弃
Ok(httparse::Status::Complete(n)) => {
    assert!(n <= buf.len(), "httparse 保证 n <= buf.len()");

    // split_to: buf 变为 [n..]（即 headers 之后的数据，可能包含 body 的一部分）
    // 分出的 [0..n) 被丢弃（headers 已解析完毕，不再需要原始字节）
    let _ = buf.split_to(n);

    // buf 现在指向 body 起始（或下一个请求起始，对于无 body 的 GET 请求）
    // 用 read_body() 继续读取 Content-Length 字节
}

错误 4：keep-alive 循环中 BytesMut 持有跨请求数据

场景：keep-alive 连接上，第一个请求 body 和第二个请求头一次性到达（TCP 粘包），第二个请求解析不到数据。

// ❌ 每次请求都重新创建 buf，导致丢弃"超前到达"的字节
loop {
    let mut buf = BytesMut::with_capacity(4096);  // ← 错误：循环内创建，前一个请求剩余字节丢失
    let raw = read_request(&mut reader, &mut buf).await?;
    // ...
}

// 示例：第一个请求结束，buf 里可能还有 "GET /health HTTP/1.1\r\nHost: ..." 的开头字节
// 如果在循环内重建 buf，这些字节就丢失了，第二个请求会读到残缺数据

根本原因：TCP 是流式协议，不保证消息边界——一次 read_buf() 可能读到多个 HTTP 请求的合并数据。BytesMut 必须在整个连接的生命周期内持久，跨多个请求复用。这正是 Kestrel System.IO.Pipelines 的设计思想：Pipe 的生命周期等于连接生命周期。

修复：在 connection loop 外创建 BytesMut，作为 &mut buf 参数传入 read_request：

// ✅ buf 在连接生命周期内持久，跨请求累积未消费字节
let mut buf = BytesMut::with_capacity(4096);  // ← 整个连接只创建一次

loop {  // keep-alive 请求循环
    // buf 保留上一个请求结束后的剩余字节（可能是下一请求的开头）
    let raw = read_request(&mut reader, &mut buf).await?;

    // 处理请求...
    let response = pipeline.run(ctx).await?;
    writer.write_all(&serialized.bytes).await?;

    // 循环回来：buf 里若有下一个请求的前几字节，不会丢失
    if !keep_alive { break; }
}
// buf 在这里 drop，连接关闭

错误 5：acquire_owned() 与 tokio::spawn 生命周期

场景：semaphore.acquire() 返回的 permit 无法传入 tokio::spawn。

// ❌ SemaphorePermit<'_> 借用了 semaphore，生命周期不是 'static
let permit = semaphore.acquire().await?;  // SemaphorePermit<'_>
tokio::spawn(async move {
    handle_connection(stream, permit).await;  // ❌ 'static 约束不满足
});

修复：使用 acquire_owned()，返回拥有 Arc<Semaphore> 所有权的 OwnedSemaphorePermit：

// ✅ OwnedSemaphorePermit 持有 Arc<Semaphore>，是 'static
let permit = Arc::clone(&semaphore)
    .acquire_owned()      // 返回 OwnedSemaphorePermit：'static
    .await?;

tokio::spawn(async move {
    handle_connection(...).await;
    drop(permit);  // RAII：连接关闭时自动释放，信号量 +1
});

错误 6：matchit 路由冲突检测时机

场景：同一路径注册两次，matchit 在 insert 时返回 Err(InsertError::Conflict)。

// ❌ 重复注册返回 Err，需要在 build 阶段统一处理
router.insert("/services/:id", handler_a)?;
router.insert("/services/:id", handler_b)?;  // InsertError::Conflict

修复：在 ServerBuilder::run() 建立 Router 时统一检测冲突，启动阶段立即暴露：

// ✅ build 阶段检测路由冲突，不等到运行时
pub fn run(self) -> anyhow::Result<()> {
    let mut router = Router::new();
    for (method, path, handler) in self.routes {
        router.insert(&method, &path, handler)
            .map_err(|e| anyhow::anyhow!("路由冲突 {path}: {e}"))?;
    }
    // ...
}

错误 7：async fn 中间件无法直接存入 Vec<Box<dyn Middleware>>

场景：直接把 async fn 塞进中间件列表类型不匹配。

// ❌ async fn 无法直接 coerce 到 Box<dyn Middleware>
async fn my_mw(ctx: HttpContext, next: Next) -> Result<Response, ServerError> { ... }
middlewares.push(Box::new(my_mw));  // ❌ 类型不匹配

修复：提供 FnMiddleware 包装类型，让 async fn 自动实现 Middleware：

// ✅ 包装器：把 async fn 转为 Box<dyn Middleware>
pub struct FnMiddleware<F>(F);

impl<F, Fut> Middleware for FnMiddleware<F>
where
    F:   Fn(HttpContext, Next) -> Fut + Send + Sync + 'static,
    Fut: Future<Output = Result<Response, ServerError>> + Send + 'static,
{
    fn handle(&self, ctx: HttpContext, next: Next)
        -> BoxFuture<'static, Result<Response, ServerError>>
    {
        Box::pin((self.0)(ctx, next))
    }
}

// ServerBuilder 通过泛型自动包装，使用侧零感知：
pub fn use_middleware<F, Fut>(mut self, f: F) -> Self
where
    F:   Fn(HttpContext, Next) -> Fut + Send + Sync + 'static,
    Fut: Future<Output = Result<Response, ServerError>> + Send + 'static,
{
    self.middlewares.push(Box::new(FnMiddleware(f)));
    self
}

二、【Dev】架构决策记录（ADR）

ADR-01：用 httparse 直接解析 TCP 字节流，而非 hyper

背景：hyper 1.x 提供 serve_connection() API，可以一行代码完成 HTTP/1.1 解析。但这相当于：

  • C# 中不用 Kestrel，直接用 HttpClient 的服务端提供者
  • 把 HTTP 解析这一层完全黑箱化
  • 学习者无法看到"请求如何从字节流变成结构化数据"

决策：使用 httparse crate（纯 Rust，Node.js llhttp 的对等层），配合 tokio::io::AsyncReadExt 手写 TCP 读取和解析状态机。

层次不用（hyper 封装后）本项目（httparse）
TCP 读取hyper 内部AsyncReadExt::read_buf() 显式调用
HTTP 解析hyper 内部httparse::Request::parse() 显式调用
Partial 处理hyper 内部显式 Status::Complete/Partial 状态机
Keep-alivehyper 自动connection.rs 显式请求循环
响应序列化hyper 内部serializer.rs 显式 format 字节

结论：多了约 150 行框架代码，换来的是对 HTTP 层每一个字节的完全可见性——这正是本项目的教学目标。

ADR-02：中间件设计为 fn(ctx, next) 而非 tower::Layer

背景：tower::Layer 的泛型参数极其复杂，对从 C# 迁移的开发者不友好。

决策：中间件接口定义为：

async fn middleware(ctx: HttpContext, next: Next) -> Result<Response, ServerError>

与 C# 的 app.Use(async (ctx, next) => { ... }) 一一对应，降低认知负担。

代价：无法直接复用 tower 生态中间件。
补偿：教学场景自定义中间件足够，生产项目可在此基础上接入 tower。

ADR-03：BytesMut 跨请求持久——零拷贝的代价

背景：Kestrel 使用 System.IO.Pipelines 管理连接的整个字节流缓冲区，缓冲区在连接生命周期内持久。Restrel 用 bytes::BytesMut 复刻这一机制。

决策：BytesMut buf 在 handle_connection 调用栈顶分配一次，通过 &mut buf 传递给 read_request，跨多个 keep-alive 请求的调用持久存在。

// connection.rs
async fn handle_connection(...) {
    let mut buf = BytesMut::with_capacity(4096);  // ← 连接级缓冲区，一次分配

    loop {  // keep-alive 请求循环
        let raw = read_request(&mut reader, &mut buf).await?;   // buf 跨循环传递
        // ...
    }
    // buf 在这里 drop，内存归还
}

关键操作语义：

操作含义类比 C#
buf.split_to(n)消费前 n 字节，buf 变为 [n..]reader.AdvanceTo(consumed)
buf.split_to(n).freeze()零拷贝切出 body，buf 继续保存剩余Span.Slice(0, n) 后 AdvanceTo
reader.read_buf(&mut buf)从 TCP 读更多数据追加到 buf 末尾await reader.ReadAsync()

ADR-04：优雅关闭使用双层机制

SIGTERM → CancellationToken.cancel()
               ↓
          TcpListener 停止 accept 新连接（select! 里 cancel 分支触发 break）
               ↓
          已有 keep-alive 循环：下一次 read_request 时
            tokio::select! {
                _ = cancel.cancelled() => break,   ← 空闲连接立即退出
                result = read_request(...) => ...   ← in-flight 请求继续处理
            }
               ↓
          等待 Semaphore 所有 permit 归还（全部连接处理完毕）
               ↓
          tokio::runtime 退出

对应 Kestrel 的：IHost.StopAsync() → ConnectionManager.CloseAllConnectionsAsync() → 等待 Task.WhenAll。

关键：CancellationToken 让空闲 keep-alive 连接立即退出等待（不需要等到 75s 超时），而 in-flight 请求仍然处理完毕再关闭。
