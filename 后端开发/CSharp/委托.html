彻底理解 C# 委托

一、委托到底是什么（编译器视角）

你写一行：

delegate int Calculate(int a, int b);

编译器把它翻译成一个完整的类，等价于：

// 编译器自动生成的代码（简化版）
public sealed class Calculate : System.MulticastDelegate
{
    // 构造函数：绑定"目标对象"和"方法指针"
    public Calculate(object target, IntPtr methodPtr) { }

    // 同步调用
    public virtual int Invoke(int a, int b) { }

    // 异步调用（老式异步，现在少用）
    public virtual IAsyncResult BeginInvoke(int a, int b, ...) { }
    public virtual int EndInvoke(IAsyncResult result) { }
}

所以你写的 Calculate add = (a, b) => a + b; 实际上是在 new Calculate(...)。

二、内部的四个字段（MulticastDelegate 核心）

MulticastDelegate 继承自 Delegate，底层有四个关键字段：

┌─────────────────────────────────────────────────────────────┐
│                    Delegate 对象内存布局                     │
├──────────────────┬──────────────────────────────────────────┤
│  _target         │  方法所在的对象实例（静态方法为 null）     │
│  _methodPtr      │  方法的内存地址（函数指针）               │
│  _invocationList │  方法列表（单个时为 null，多播时为数组）  │
│  _invocationCount│  方法数量（正数=多播，负数=特殊情况）     │
└──────────────────┴──────────────────────────────────────────┘

三种状态：

// 状态1：绑定单个实例方法
var obj = new Calculator();
Calculate d1 = obj.Add;
// _target    = obj（对象本身）
// _methodPtr = Add 方法的地址

// 状态2：绑定静态方法
Calculate d2 = Calculator.StaticAdd;
// _target    = null
// _methodPtr = StaticAdd 地址

// 状态3：多播（绑定多个方法）
Calculate d3 = d1 + d2;
// _target          = null
// _methodPtr       = 指向执行调度逻辑
// _invocationList  = [ d1, d2 ]  ← 存方法的数组
// _invocationCount = 2

三、读懂 Func / Action 源码

完整定义：

// ────── Action 系列（无返回值）──────
public delegate void Action();
public delegate void Action<T>(T arg);
public delegate void Action<T1, T2>(T1 arg1, T2 arg2);
// ... 一直到 Action<T1,...,T16>

// ────── Func 系列（有返回值）──────
public delegate TResult Func<TResult>();
public delegate TResult Func<T, TResult>(T arg);
public delegate TResult Func<T1, T2, TResult>(T1 arg1, T2 arg2);
// ... 一直到 Func<T1,...,T16,TResult>

// ────── Predicate（特殊的 Func<T, bool>）──────
public delegate bool Predicate<T>(T obj);

核心规律：

Func<输入1, 输入2, ..., 输入N, 返回值>
         ↑ 前 N 个都是输入         ↑ 最后一个永远是返回值

Action<输入1, 输入2, ..., 输入N>
       ↑ 全部都是输入，无返回值

选择时机：

场景用哪个
无参无返回Action
有参无返回Action<T>
无参有返回Func<TResult>
有参有返回Func<T, TResult>
返回 bool 的判断Predicate<T>
需要特殊语义（事件）自定义 delegate

四、Lambda 背后发生了什么（闭包真相）

情况1：简单 Lambda（无闭包）→ 编译为静态方法

Func<int, int> square = x => x * x;

编译器生成：

// 你看不见的代码，编译器悄悄加的
private static int <Main>b__0(int x)
{
    return x * x;
}

// 你的代码变成了：
Func<int, int> square = new Func<int, int>(null, <Main>b__0);
//                                          ↑ null = 静态方法，无目标对象

情况2：捕获外部变量（闭包）→ 编译为隐藏类

int multiplier = 3;
Func<int, int> triple = x => x * multiplier;
multiplier = 10; // 改了！
Console.WriteLine(triple(5)); // 输出 50，不是 15！

编译器生成了一个隐藏类来"装住"被捕获的变量：

// 编译器生成的隐藏类（你看不见）
private sealed class <>c__DisplayClass
{
    public int multiplier; // 注意：是字段，不是局部变量副本！

    public int <Main>b__0(int x)
    {
        return x * this.multiplier; // 直接引用字段
    }
}

// 你的代码等价于：
var closure = new <>c__DisplayClass();
closure.multiplier = 3;                      // int multiplier = 3
Func<int, int> triple = closure.<Main>b__0; // Lambda 绑定到这个对象的方法

closure.multiplier = 10;                     // multiplier = 10 → 改的是同一个字段！
Console.WriteLine(triple(5));               // 读的是 closure.multiplier = 10，所以是 50

经典闭包陷阱：for 循环

// 陷阱：三个 Lambda 共享同一个 closure.i
var actions = new List<Action>();
for (int i = 0; i < 3; i++)
{
    actions.Add(() => Console.WriteLine(i));
}
actions[0](); // 输出 3，不是 0！
actions[1](); // 输出 3，不是 1！
actions[2](); // 输出 3，不是 2！

// 修复：用局部变量复制一份，每次循环产生新的 DisplayClass
for (int i = 0; i < 3; i++)
{
    int copy = i; // 每次循环都是独立的 DisplayClass.copy
    actions.Add(() => Console.WriteLine(copy));
}

五、多播委托的细节

Action<string> log = null;

log += msg => Console.WriteLine($"[文件] {msg}");
log += msg => Console.WriteLine($"[邮件] {msg}");
log += msg => Console.WriteLine($"[数据库] {msg}");

log("用户登录");
// 依次输出：
// [文件] 用户登录
// [邮件] 用户登录
// [数据库] 用户登录

// 获取调用列表（_invocationList 数组）
Delegate[] list = log.GetInvocationList();
Console.WriteLine(list.Length); // 3

多播委托的两个关键坑：

// 坑1：多播委托的返回值只保留最后一个
Func<int> f = null;
f += () => 1;
f += () => 2;
f += () => 3;
Console.WriteLine(f()); // 输出 3，前两个返回值丢弃了！

// 如果需要收集所有返回值，用 GetInvocationList 手动调用
var results = f.GetInvocationList()
               .Cast<Func<int>>()
               .Select(fn => fn())
               .ToList(); // [1, 2, 3]

// 坑2：多播中某个方法抛异常，后续方法不会执行
Action a = null;
a += () => Console.WriteLine("方法1");
a += () => throw new Exception("炸了");
a += () => Console.WriteLine("方法3"); // 不会执行！

// 安全调用方式：逐个 try-catch
foreach (Action item in a.GetInvocationList())
{
    try { item(); }
    catch (Exception ex) { Console.WriteLine($"跳过异常：{ex.Message}"); }
}

六、事件（event）= 委托 + 访问限制

// 不加 event 关键字的问题：外部可以直接 = 赋值（清除所有订阅者）
public Action<string> OnMessage; // 危险！外部可以 OnMessage = null

// 加 event 之后：外部只能 += 和 -=，不能 = 赋值
public event Action<string> OnMessage; // 安全

// event 的本质是编译器生成了 add/remove 访问器，等价于：
private Action<string> _onMessage;
public event Action<string> OnMessage
{
    add    { _onMessage += value; } // 只允许 +=
    remove { _onMessage -= value; } // 只允许 -=
}
// 外部不能写：obj.OnMessage = null;  ← 编译报错
// 外部也不能写：obj.OnMessage("hi"); ← 编译报错（只有声明类内部能 Invoke）

七、思路闭环 —— 委托解决的是什么问题

问题：我想把"行为"当成参数传递，或者延迟执行
        ↓
解决：委托 = 把方法包装成对象
        ↓
┌──────────────────────────────────────────────────────┐
│                   委托的三种用途                      │
├────────────────┬────────────────┬────────────────────┤
│  回调（Callback）│ 策略（Strategy）│  事件（Event）   │
│                │                │                    │
│  你做完叫我    │  你决定怎么做  │  发生了通知我      │
│                │                │                    │
│  await Task    │  LINQ、Sort    │  button.Click      │
│  HttpClient    │  工厂模式      │  INotifyPropertyChanged│
└────────────────┴────────────────┴────────────────────┘

用"排序策略"理解委托存在的意义：

// 没有委托的世界：为每种排序规则写一个方法
void SortByName(List<User> users) { ... }
void SortByAge(List<User> users) { ... }
// 每加一种规则就要改代码 → 不可扩展

// 有了委托的世界：把"比较规则"当参数传进来
void Sort(List<User> users, Comparison<User> compare)
//                          ↑ 这个参数就是委托，"比较方式"可以随意替换
{
    for (int i = 0; i < users.Count; i++)
        for (int j = i + 1; j < users.Count; j++)
            if (compare(users[i], users[j]) > 0)
                Swap(users, i, j);
}

// 调用方决定排序规则，完全解耦
Sort(users, (a, b) => a.Name.CompareTo(b.Name)); // 按名字
Sort(users, (a, b) => a.Age - b.Age);            // 按年龄
Sort(users, (a, b) => b.Score - a.Score);        // 按分数倒序

八、完整示例 —— 串联所有概念

using System;
using System.Collections.Generic;

// ============ 模拟一个订单处理流水线 ============

public class Order
{
    public int Id { get; set; }
    public decimal Amount { get; set; }
    public bool IsPaid { get; set; }
}

public class OrderPipeline
{
    // 1. 自定义委托（有语义名称）
    public delegate bool Validator(Order order);

    // 2. event：订单处理完成后通知外部
    //    外部只能 +=/-=，不能主动触发
    public event Action<Order> OnOrderProcessed;

    // 3. Func 作为策略参数（计算折扣的规则由外部决定）
    public void Process(Order order, Validator validate, Func<decimal, decimal> discount)
    {
        // 调用委托：执行验证
        if (!validate(order))
        {
            Console.WriteLine($"订单 {order.Id} 验证失败");
            return;
        }

        // 调用委托：执行折扣计算
        order.Amount = discount(order.Amount);
        order.IsPaid = true;

        Console.WriteLine($"订单 {order.Id} 处理完成，金额：{order.Amount}");

        // 触发事件（?.Invoke 是空安全调用，防止无订阅者时崩溃）
        OnOrderProcessed?.Invoke(order);
    }
}

// ============ 使用方 ============
var pipeline = new OrderPipeline();

// 订阅事件（多播）
pipeline.OnOrderProcessed += order => Console.WriteLine($"[日志] 记录订单 {order.Id}");
pipeline.OnOrderProcessed += order => Console.WriteLine($"[邮件] 通知用户，金额 {order.Amount}");

var order = new Order { Id = 1001, Amount = 200m };

// 把验证规则和折扣策略作为委托传入（策略模式）
pipeline.Process(
    order,
    validate: o => o.Amount > 0,       // 验证：金额 > 0
    discount: amount => amount * 0.9m  // 折扣：九折
);

// 输出：
// 订单 1001 处理完成，金额：180
// [日志] 记录订单 1001
// [邮件] 通知用户，金额 180

十、破局总结

你已知补充的连接
委托有数组存方法那个数组叫 _invocationList，+= 就是往数组里加，调用时依次执行
Func 最后一个是返回值因为它就是 delegate TResult Func<T1,...,TResult>，泛型定义就这样写的
Lambda 是委托的语法糖编译器把它变成方法（无闭包）或隐藏类的方法（有闭包），本质还是 new Delegate(...)
看源码理解慢凡是看到 Func<A,B,C> 就读成"吃A和B，吐C"；看到 Action<A> 就读成"吃A，不吐"
整体思路委托 = 把方法包成对象 → 方法可以当参数传 → 行为可以解耦 → 这就是策略/回调/事件的本质
