C# 垃圾回收机制（GC）

Moklgy2026/4/20大约 21 分钟CSharpGC垃圾回收内存管理CLR

一、托管堆

每个程序都需要操作各种类型的资源，例如文件、内存缓冲区、屏幕空间、网络连接、数据库资源等。面向对象编程里面，每个类型代表可供程序调用的一种资源，要使用这些资源，就必须要分配内存，而内存的管理由托管堆（Managed Heap） 处理。

1.1 托管堆结构

CLR 要求所有对象都从托管堆分配。进程初始化时，CLR 划定一个地址空间区域作为托管堆，并维护一个NextObjPtr 指针，指向下一个对象在堆中的分配地址。初始时，NextObjPtr 指向地址空间区域的起始位置。

托管堆（Managed Heap）

  ┌──────────────────────────────────────────────────────────┐
  │   已分配对象区域                         │ 空闲区域      │
  │  [对象A][对象B][对象C][对象D]            │               │
  └──────────────────────────────────────────────────────────┘
                                             ↑
                                         NextObjPtr
                                    （下个对象放这里）

CLR 通过"指针碰撞（Bump the Pointer）"的方式分配内存：只需移动 NextObjPtr，就完成了内存分配，比 C/C++ 的 malloc（需要遍历空闲链表）快得多。

二、分配内存步骤

2.1 C# new 操作符触发的完整流程

C# 的 new 操作符触发 CLR 执行以下步骤：

第1步：计算所需字节数

  • 计算类型所有字段所需的字节数（含从基类继承的字段）

第2步：加上对象开销字节数

每个对象都有两个开销字段：

开销字段32位应用64位应用作用
类型对象指针（Type Object Pointer）4 字节8 字节指向该对象的类型对象（方法表）
同步块索引（Sync Block Index）4 字节8 字节用于线程同步（lock 语句）
  • 32位应用：每个对象额外增加 8 字节
  • 64位应用：每个对象额外增加 16 字节

第3步：检查托管堆空间，完成分配

CLR 检查 NextObjPtr 处是否有足够字节：

  • 有足够空间 → 在 NextObjPtr 处放入对象，字节清零，调用构造器
  • 空间不足 → 触发垃圾回收，回收后重试
// 这一行 C# 代码
var obj = new MyClass();

// CLR 内部等效操作（伪代码）：
// 1. bytes = sizeof(MyClass fields) + sizeof(TypeObjPtr) + sizeof(SyncBlockIndex)
// 2. if (NextObjPtr + bytes > heapEnd) GC.Collect();
// 3. obj = NextObjPtr;          // 对象放在当前指针位置
// 4. ZeroMemory(obj, bytes);    // 内存清零
// 5. obj.ctor();                // 调用构造器
// 6. NextObjPtr += bytes;       // 指针后移，指向下一空闲位置
// 7. return obj;                // 返回对象引用

2.2 使用资源的完整生命周期

a. 调用 IL 指令 newobj（C# new）向系统申请内存
b. 初始化内存，类型构造器设置初始状态
c. 访问类型成员使用资源（可重复）
d. 摧毁资源状态，进行清理（Dispose / Finalize）
e. 释放内存 ← 垃圾回收器独自负责这一步

三、垃圾回收（GC）

3.1 为何需要垃圾回收

  1. 内存不可能无限大
  2. 手动管理内存极易出错：
    • 访问已释放的内存 → 程序异常
    • 忘记释放内存 → 内存泄漏
    • 重复释放 → 堆损坏
    • 内存破坏是程序开发中最严重的问题，CLR 通过 GC 从根本上解决了这一问题

3.2 GC 根（Roots）

根（Root） 是所有引用类型的变量。GC 从根出发，遍历所有可达对象，决定哪些对象存活。

CLR 认定以下变量为根：

根的类型说明
局部变量方法栈帧中的引用类型局部变量
方法参数传入方法的引用类型参数
静态字段类型的静态引用字段（生命周期贯穿整个 AppDomain）
CPU 寄存器当前线程寄存器中保存的对象引用
GC 句柄GCHandle 显式创建的引用
终结队列等待执行 Finalize 的对象引用

重要提示

静态字段引用的对象会一直存活，直到加载该类型的 AppDomain 卸载为止。

如果静态字段引用了集合，并且持续往集合中添加数据，就会导致内存泄漏，因此尽量避免使用静态字段持有大量数据。

3.3 触发垃圾回收的时机

触发条件说明
托管堆空间不足最常见的触发原因
系统物理内存不足操作系统通知进程低内存
显式调用GC.Collect()（通常不建议）
AppDomain 卸载CLR 自动触发
CLR 关闭进程退出时

3.4 垃圾回收的四个阶段

阶段1：挂起（Suspend）
  → 所有托管线程被强行暂停（GC 需要一致的堆视图）

阶段2：标记（Mark）
  → 从所有根出发，按引用关系遍历对象图
  → 可达对象标记为 1（存活），不可达标记为 0（垃圾）

阶段3：碎片整理（Compact）
  → 将标记为 1 的对象移动到连续内存
  → 更新所有根，使其指向对象新地址

阶段4：恢复（Resume）
  → 所有托管线程恢复运行
  → 线程继续访问对象，如同 GC 没发生过

3.5 两种垃圾回收算法

引用计数算法（C# 不使用）

每个对象维护一个计数器，被引用+1，引用断开-1，计数为0时回收。

  • 致命缺点：无法解决循环引用，例如：对象A引用对象B，对象B引用对象A，两者计数永远不为0，永远无法回收。

引用跟踪算法（C# 使用）

只关心引用类型变量（根），从根出发遍历引用关系：

CLR 开始 GC 时：
1. 所有对象标记为 0
2. 从每个根出发，遍历引用的对象，标记为 1
   （已标记过就跳过，避免循环引用导致的死循环）
3. 遍历完毕，标记为 1 的是存活对象（可达），0 是垃圾
4. 压缩阶段：移动存活对象到连续内存，更新所有根的指向
5. 恢复所有线程

天然解决循环引用：循环引用的对象如果无根指向，标记阶段
不会被访问到，直接标记为 0，被回收。

四、代（Generations）

4.1 分代假设

.NET GC 采用分代回收策略，基于两个经过验证的工程经验：

  1. 新创建的对象生命周期短，很快会变成垃圾
  2. 存活越久的对象，未来存活时间也越长

因此，GC 将对象分为 3 代（0、1、2 代），对不同代采用不同回收频率。

4.2 对象创建与 0 代

所有新对象默认分配在 0 代（Generation 0）

┌─────────────────────────────────────────────────────┐
│                  托管堆（初始状态）                  │
│                                                     │
│  ┌───────────────┐  ┌───────────┐  ┌─────────────┐ │
│  │    0 代区域   │  │  1 代区域 │  │   2 代区域  │ │
│  │  [A][B][C][D] │  │  （空）   │  │   （空）    │ │
│  └───────────────┘  └───────────┘  └─────────────┘ │
└─────────────────────────────────────────────────────┘

4.3 0 代回收：存活对象晋升到 1 代

当新对象分配时 0 代空间不足，触发 0 代回收：

回收前：0 代 = [A*][B][C*][D]（* 表示可达，将存活）

  标记阶段：遍历根，A 和 C 被标记为可达
  压缩阶段：B 和 D 被回收，A 和 C 被移动
  晋升：    A 和 C 移入 1 代区域

┌─────────────────────────────────────────────────────┐
│                   回收后                            │
│  ┌──────────┐  ┌──────────────┐  ┌──────────────┐  │
│  │  0 代    │  │    1 代      │  │    2 代      │  │
│  │ [新对象] │  │  [A]  [C]   │  │   （空）     │  │
│  └──────────┘  └──────────────┘  └──────────────┘  │
└─────────────────────────────────────────────────────┘

4.4 1 代回收：存活对象晋升到 2 代

1 代回收频率远低于 0 代，通常在多次 0 代回收后才触发：

┌─────────────────────────────────────────────────────┐
│               1 代回收后（晋升至 2 代）              │
│  ┌──────────┐  ┌──────────────┐  ┌──────────────┐  │
│  │  0 代    │  │    1 代      │  │    2 代      │  │
│  │ [E][F]   │  │  （空）      │  │  [A]  [C]   │  │
│  └──────────┘  └──────────────┘  └──────────────┘  │
└─────────────────────────────────────────────────────┘

4.5 2 代回收（全量回收）

2 代是最高代，回收频率最低：

  • 2 代回收会同时回收 0、1、2 代，所以也称全量回收
  • 存活的 2 代对象仍留在 2 代（无更高代）
┌─────────────────────────────────────────────────────┐
│               2 代回收后（全量回收）                 │
│  ┌──────────┐  ┌──────────────┐  ┌──────────────┐  │
│  │  0 代    │  │    1 代      │  │    2 代      │  │
│  │ （空）   │  │  （空）      │  │    [A]       │  │
│  └──────────┘  └──────────────┘  └──────────────┘  │
│                                  （C 不可达，被回收）│
└─────────────────────────────────────────────────────┘

4.6 三代对比

代别回收频率空间大小晋升规则典型对象
0 代最高最小（~256KB）存活 → 晋升 1 代临时变量、短命对象
1 代中等中等（~2MB）存活 → 晋升 2 代中等周期对象
2 代最低最大（无上限）始终留在 2 代单例、长期缓存

4.7 代回收验证代码

using System;

class Program
{
    static void Main()
    {
        object obj = new object();
        Console.WriteLine($"新对象所在代：{GC.GetGeneration(obj)}"); // 0

        GC.Collect(0); // 触发 0 代回收，obj 存活 → 晋升 1 代
        Console.WriteLine($"0 代回收后：{GC.GetGeneration(obj)}");   // 1

        GC.Collect(1); // 触发 1 代回收，obj 存活 → 晋升 2 代
        Console.WriteLine($"1 代回收后：{GC.GetGeneration(obj)}");   // 2

        GC.Collect(2); // 触发 2 代全量回收，obj 存活 → 留在 2 代
        Console.WriteLine($"2 代回收后：{GC.GetGeneration(obj)}");   // 2
    }
}

五、终结（Finalization）

这是 CLR via C# 中最重要也最容易被误解的机制之一。

5.1 什么是终结

当一个对象持有非托管资源（文件句柄、数据库连接、网络 Socket 等），GC 无法自动清理这些资源。C# 提供 终结器（Finalizer） 让对象在被回收前执行清理代码：

public class ResourceHolder
{
    private IntPtr _handle; // 非托管句柄

    // 终结器：语法是 ~类名()，编译器将其转为 Finalize() 方法
    ~ResourceHolder()
    {
        // GC 回收此对象前，CLR 会调用这里
        // 用于释放非托管资源
        CloseHandle(_handle);
    }
}

5.2 终结器如何工作（关键！）

终结机制涉及两个特殊队列，这是理解终结的核心：

                  GC 发现 ResourceHolder 不可达

                        ↓

         ① 不会立即回收！改为放入「终结队列（Finalization Queue）」

             终结队列 = [ResourceHolder 的引用]
             （放入队列后，对象再次变为「可达」，不会被回收）

                        ↓

         ② 一个专用的 CLR 终结线程 从队列取出对象
            调用 Finalize() 方法执行清理

                        ↓

         ③ 对象移入「可终结可达队列（freachable queue）」
            → 这个队列的对象会在下一次 GC 时被真正回收

                        ↓

         ④ 下一次 GC 运行时，发现 freachable queue 中的对象
            → 此时才真正回收内存

结论：有终结器的对象至少要经历两次 GC 才能被真正回收，因此：

  • 带终结器的对象生命周期更长
  • 很可能被晋升到 1 代甚至 2 代（使本应短命的对象变成长命对象）
  • 应该尽量避免使用终结器
// 演示终结器的生命周期延长问题
class WithFinalizer
{
    ~WithFinalizer() { } // 仅有一个空终结器
}

class WithoutFinalizer { }

// WithFinalizer 的对象：
//   第1次 GC：进入终结队列，晋升到更高代（没被回收）
//   第2次 GC：才真正被回收

// WithoutFinalizer 的对象：
//   第1次 GC：如果不可达，直接回收

5.3 对象复活（Resurrection）

终结器代码中，如果把 this 赋值给一个根（如静态字段），对象会"复活"：

class Zombie
{
    public static Zombie Instance;

    ~Zombie()
    {
        // 警告：这会使对象复活！
        Zombie.Instance = this;
        // 下次 GC 时，Instance 是根，对象再次可达
        // 如需再次终结，需调用 GC.ReRegisterForFinalize(this)
    }
}

六、IDisposable 与 Dispose 模式

终结器无法控制执行时机，因此 CLR 设计了 IDisposable 接口，让对象的使用者能够主动、确定性地释放资源。

6.1 仅有非托管资源（简单版）

public class SimpleResource : IDisposable
{
    private bool _disposed = false;
    private IntPtr _handle; // 非托管资源

    public void Dispose()
    {
        Dispose(true);
        // 告诉 GC：终结器不需要执行了，移除出终结队列
        // 这样对象下次 GC 就能被立即回收，不需要等两次
        GC.SuppressFinalize(this);
    }

    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;

        if (disposing)
        {
            // 释放托管资源（其他 IDisposable 对象）
        }

        // 释放非托管资源（无论托管还是终结器调用都要执行）
        CloseHandle(_handle);
        _handle = IntPtr.Zero;

        _disposed = true;
    }

    ~SimpleResource()
    {
        // 用户忘记调用 Dispose 的保底机制
        Dispose(false); // false 表示是终结器调用，不能再访问托管对象
    }

    private void CloseHandle(IntPtr h) { /* 释放句柄 */ }
}

6.2 标准 Dispose 模式（含子类继承）

// 可以被继承的类
public class BaseResource : IDisposable
{
    private bool _disposed = false;

    // 公共入口：用户主动调用
    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this); // 取消终结器，下次 GC 直接回收
    }

    // 核心清理方法：disposing=true 表示用户调用，false 表示终结器调用
    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;

        if (disposing)
        {
            // 只有用户主动调用时才清理托管资源
            // 因为终结器调用时，托管对象可能已经被 GC 处理过了
            _managedResource?.Dispose();
        }

        // 非托管资源：两种情况都要清理
        ReleaseUnmanagedResource();

        _disposed = true;
    }

    ~BaseResource() => Dispose(false);

    private IDisposable _managedResource;
    private void ReleaseUnmanagedResource() { }
}

// 子类：重写 Dispose(bool)
public class DerivedResource : BaseResource
{
    private bool _disposed = false;

    protected override void Dispose(bool disposing)
    {
        if (_disposed) return;

        if (disposing)
        {
            // 清理子类自己的托管资源
        }
        // 清理子类自己的非托管资源

        _disposed = true;
        base.Dispose(disposing); // 调用父类清理
    }
}

6.3 using 语句 = 自动 Dispose

// using 语句保证 Dispose 一定被调用（即使抛异常）
using (var conn = new SqlConnection(connectionString))
{
    conn.Open();
    // ... 使用连接
} // 此处自动调用 conn.Dispose()

// 等价于：
var conn = new SqlConnection(connectionString);
try
{
    conn.Open();
    // ... 使用连接
}
finally
{
    conn?.Dispose(); // finally 保证一定执行
}

// C# 8.0+ 简化写法（不需要括号和缩进）
using var conn = new SqlConnection(connectionString);
// 方法/作用域结束时自动 Dispose

6.4 SafeHandle（推荐替代原始终结器）

SafeHandle 是微软提供的封装非托管句柄的基类，内部已实现了完整的 Dispose 模式和终结逻辑，应优先使用而非自己写终结器：

using Microsoft.Win32.SafeHandles;

public class MyResource : IDisposable
{
    // 用 SafeFileHandle 封装文件句柄，无需自己写 Finalize
    private SafeFileHandle _fileHandle;

    public MyResource(string path)
    {
        _fileHandle = new SafeFileHandle(
            CreateFile(path, ...), ownsHandle: true);
    }

    public void Dispose()
    {
        _fileHandle?.Dispose(); // SafeHandle 内部处理所有终结逻辑
        GC.SuppressFinalize(this);
    }
}

七、弱引用（WeakReference）

7.1 什么是弱引用

普通引用（强引用）会阻止 GC 回收对象。弱引用不阻止 GC 回收对象，但在对象仍存活时可以访问它。

典型用途：缓存——缓存的对象在内存不足时可被 GC 回收，避免缓存撑爆内存。

// 创建弱引用
var data = new BigData();              // data 是强引用
var weak = new WeakReference<BigData>(data); // weak 是弱引用

data = null; // 断开强引用，此后 GC 可以回收 BigData 对象

// 尝试从弱引用获取对象
if (weak.TryGetTarget(out BigData target))
{
    // 对象还没被 GC 回收，可以使用
    target.Process();
}
else
{
    // 对象已被 GC 回收，需要重建
    var newData = new BigData();
    weak.SetTarget(newData);
    newData.Process();
}

7.2 短弱引用 vs 长弱引用

类型说明何时失效
短弱引用（默认）new WeakReference<T>(obj)对象终结器执行后失效
长弱引用new WeakReference<T>(obj, trackResurrection: true)对象内存真正释放后才失效
// 短弱引用：对象进入终结队列即失效（推荐）
var shortWeak = new WeakReference<MyObj>(obj);

// 长弱引用：可以感知"复活"后的对象（谨慎使用）
var longWeak = new WeakReference<MyObj>(obj, trackResurrection: true);

7.3 弱引用缓存实践

public class WeakCache<TKey, TValue> where TValue : class
{
    private readonly Dictionary<TKey, WeakReference<TValue>> _cache = new();

    public TValue GetOrAdd(TKey key, Func<TKey, TValue> factory)
    {
        if (_cache.TryGetValue(key, out var weakRef) &&
            weakRef.TryGetTarget(out var cached))
        {
            return cached; // 缓存命中，且对象未被 GC 回收
        }

        // 缓存未命中或已被回收，重建
        var value = factory(key);
        _cache[key] = new WeakReference<TValue>(value);
        return value;
    }
}

八、大对象堆（LOH）

8.1 什么是大对象

在 .NET 中，大小超过 85,000 字节 的对象被视为"大对象"，存放在独立的大对象堆（Large Object Heap，LOH）。

常见大对象：

  • 大型数组：byte[] 超过 85,000 个元素
  • 长字符串：超过约 42,500 个字符（每个 char 占 2 字节）

8.2 LOH 的特性

特性说明
直接归 2 代大对象分配后直接属于第 2 代，不经过 0、1 代晋升
只在 2 代回收时被回收0/1 代回收不影响 LOH
默认不压缩移动大对象成本太高，默认只清理不移动（可能产生碎片）
.NET Core 3.0+ 支持手动压缩通过配置触发一次 LOH 压缩
托管堆（完整结构）

  ┌──────────────────────────────────────────────────────────────┐
  │  小对象堆（SOH）                    │  大对象堆（LOH）        │
  │  ┌────────┬────────┬────────┐       │  ┌──────────────────┐  │
  │  │ 0 代   │ 1 代   │ 2 代   │       │  │  大对象（≥85KB）  │  │

  └─────────────────────────────────────────────────────────────-┘

8.3 LOH 碎片问题及解决

// LOH 碎片：对象A（200KB）、对象B（300KB）、对象C（200KB）
// 回收 B 后，留下 300KB 空洞
// 如果新对象是 350KB，虽然总空闲 > 350KB，但连续空间不够 → 触发 GC

// 解决方案1：手动触发一次 LOH 压缩（.NET Core 3.0+）
GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce;
GC.Collect(); // 触发后自动重置为 Default

// 解决方案2：对象池（ArrayPool）复用大数组，避免反复分配
byte[] buffer = ArrayPool<byte>.Shared.Rent(100_000); // 从池中借用
try
{
    // 使用 buffer
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer); // 归还到池，不触发 LOH 分配
}

8.4 LOH 最佳实践

  1. 拆分大数组：将 byte[100000] 拆分为多个 byte[10000]，避免进入 LOH
  2. 使用 ArrayPool：复用大数组，减少 LOH 分配压力
  3. 避免大字符串拼接：使用 StringBuilder 并设合理初始容量
  4. 监控 LOH：GC.GetGCMemoryInfo().GenerationInfo[3] 查看 LOH 大小

九、垃圾回收模式

CLR 启动时选择 GC 模式，进程终止前不可更改。

9.1 工作站 GC（Workstation GC）

  • 应用程序的默认模式
  • 单个后台 GC 线程处理所有代的回收
  • 对延迟敏感，适合桌面/交互式应用

9.2 服务器 GC（Server GC）

  • 为每个逻辑处理器分配一个专用 GC 线程和独立堆（小对象堆 + LOH）
  • 优点：多处理器并行回收，吞吐量大，内存分配速度快，段更大
  • 适合 ASP.NET Core 等高吞吐服务端应用
<!-- 在 .csproj 或 runtimeconfig.json 中配置 -->
<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>
  <!-- 并发 GC（减少停顿时间） -->
  <ConcurrentGarbageCollection>true</ConcurrentGarbageCollection>
</PropertyGroup>

堆结构单套堆每 CPU 一套堆
并行回收否（单线程）是（多线程并行）
段大小较小较大
内存分配速度一般快（减少竞争）

十、后台垃圾回收（Background GC）

10.1 前台 GC 的问题

前台 GC（非并发）在回收期间会暂停所有托管线程（Stop The World），对延迟敏感的应用会产生明显卡顿。

10.2 后台 GC 机制

后台 GC 只影响 第 2 代 的回收，允许应用线程在 2 代回收期间继续运行：

后台 GC 执行 2 代回收时：

  应用线程：    运行...运行...运行...运行...运行...运行
  后台 GC 线程：---------  执行 2 代回收  ---------

  （0 代和 1 代回收仍然是前台回收，会短暂暂停应用线程）
  • .NET 4.0+ 工作站 GC 支持后台 GC
  • .NET 4.5+ 服务器 GC 也支持后台 GC
  • 默认开启，无需手动配置

十一、强制垃圾回收

通常不建议显式调用 GC，这会打乱 GC 的分代优化节奏。

11.1 GC.Collect 重载

// 全量回收所有代（等价于 GC.Collect(2)）
GC.Collect();

// 指定代：回收 0 代及以下（只回收 0 代）
GC.Collect(0);

// 完整签名
GC.Collect(
    generation: 2,
    mode: GCCollectionMode.Forced,    // Forced / Optimized / Aggressive (NET6+)
    blocking: true,                    // true = 前台阻塞完成；false = 尽量后台
    compacting: true                   // true = 强制压缩托管堆
);

11.2 合理使用场景

// 场景1：已知将要分配大量内存，提前清理一次（如导入大文件前）
GC.Collect();
GC.WaitForPendingFinalizers(); // 等待所有终结器执行完毕
GC.Collect();                  // 再次回收（终结器执行后对象进入 freachable queue，需二次 GC）

// 场景2：单元测试验证内存回收行为
// 场景3：关闭某个大型功能模块后主动释放内存

// GC.KeepAlive：防止对象被 GC 提前回收
void UseResource()
{
    var res = new NativeResource();
    // ... 使用 res，但编译器可能优化掉对 res 的引用
    DoSomethingWithHandle(res.Handle);
    GC.KeepAlive(res); // 确保 res 在这行之前不会被 GC
}

11.3 GC 内存压力通知

当使用非托管内存（如 Marshal.AllocHGlobal）时，GC 不知道实际内存压力，需要手动通知：

// 分配了 100MB 非托管内存，告知 GC 增加回收压力
int unmanagedBytes = 100 * 1024 * 1024;
GC.AddMemoryPressure(unmanagedBytes);

// 释放非托管内存后，告知 GC 减少压力
Marshal.FreeHGlobal(ptr);
GC.RemoveMemoryPressure(unmanagedBytes);

十二、对象固定（Pinning）

12.1 为什么需要固定

GC 的压缩阶段会移动对象，但非托管代码（如 P/Invoke 调用 C 函数）持有对象的内存指针，如果对象被移动，指针就失效了。固定（Pinning）让 GC 在回收期间不移动某个对象。

12.2 fixed 语句（栈上固定）

// fixed 语句：在 unsafe 代码块中固定托管对象
unsafe void PassArrayToNativeCode(byte[] data)
{
    fixed (byte* ptr = data) // 固定 data 数组，GC 回收时不会移动它
    {
        NativeMethod(ptr, data.Length); // 安全地把指针传给非托管代码
    }
    // fixed 块结束，对象解除固定，GC 可以自由移动
}

12.3 GCHandle（显式固定句柄）

// GCHandle：更灵活的固定方式，可以跨越方法边界
byte[] buffer = new byte[1024];

// 创建固定句柄
GCHandle handle = GCHandle.Alloc(buffer, GCHandleType.Pinned);
try
{
    IntPtr ptr = handle.AddrOfPinnedObject(); // 获取固定后的指针
    NativeMethod(ptr);
}
finally
{
    handle.Free(); // 必须释放！否则对象永远不会被 GC 移动（内存泄漏）
}

注意

固定对象会阻碍 GC 的内存整理，导致内存碎片。应尽量缩短固定时间，用完立即解除固定。

十三、提升 GC 性能

以下是 CLR via C# 中的核心建议，按重要程度排列。

13.1 减少对象分配量

// 不好：每次调用都分配新对象
string result = "";
for (int i = 0; i < 1000; i++)
    result += i.ToString(); // 每次 += 都创建新的 string 对象

// 好：复用 StringBuilder
var sb = new StringBuilder(4096); // 预分配容量，避免内部扩容
for (int i = 0; i < 1000; i++)
    sb.Append(i);
string result2 = sb.ToString();

13.2 只对 0 代对象进行 GC（让对象短命）

// 不好：方法内部对象持有对外部长命对象的引用，导致短命对象晋升
public void Process()
{
    var temp = new TempObject();
    temp.LongLivedRef = _longLivedCache; // temp 被晋升，因为它引用了长命对象
}

// 好：让临时对象只持有临时引用，生命周期短，在 0 代就被回收
public void Process()
{
    var temp = new TempObject();
    var result = temp.Process(_longLivedCache.GetData()); // 只传数据，不持有引用
}

13.3 减小对象树的深度，减少对象间引用

// 不好：深度嵌套的对象图，GC 标记阶段需要遍历更多节点
class A { B b; }
class B { C c; }
class C { D d; }
class D { /* ... */ }

// 好：扁平化结构
class Container
{
    // 直接持有数据，减少引用层级
    string name;
    int age;
    DateTime created;
}

13.4 对长期存活对象和大型对象进行池化

// ArrayPool：复用大数组，避免 LOH 分配
byte[] buffer = ArrayPool<byte>.Shared.Rent(minimumLength: 81920);
try
{
    // 使用 buffer
    int bytesRead = stream.Read(buffer, 0, buffer.Length);
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: false);
}

// ObjectPool：复用昂贵对象（如 StringBuilder）
var pool = new ObjectPool<StringBuilder>(() => new StringBuilder());
var sb = pool.Get();
try { sb.Append("..."); return sb.ToString(); }
finally { sb.Clear(); pool.Return(sb); }

13.5 用弱引用作为缓存

// 弱引用缓存：内存充足时命中缓存，GC 时自动清理，不会 OOM
private static readonly Dictionary<string, WeakReference<Report>> _cache = new();

public static Report GetReport(string key)
{
    if (_cache.TryGetValue(key, out var weakRef) &&
        weakRef.TryGetTarget(out var report))
        return report; // 缓存命中

    var newReport = BuildReport(key); // 缓存未命中，重建
    _cache[key] = new WeakReference<Report>(newReport);
    return newReport;
}

13.6 避免使用终结器

// 不好：自己写终结器（导致对象至少多活一个 GC 周期）
class BadResource
{
    ~BadResource() { CloseHandle(_handle); } // 触发二次 GC 才能回收
}

// 好：用 SafeHandle 封装，内部有完善的终结逻辑
class GoodResource : IDisposable
{
    private SafeFileHandle _handle;
    public void Dispose() { _handle?.Dispose(); }
    // 不需要写 ~GoodResource()
}

13.7 避免对象固定

// 不好：长时间固定对象阻碍 GC 压缩，产生碎片
GCHandle handle = GCHandle.Alloc(buffer, GCHandleType.Pinned);
DoSlowOperation(); // 长时间操作期间对象固定，GC 无法移动
handle.Free();

// 好：缩短固定时间，或使用 Memory<T> 等现代 API
// Memory<T> 结合 MemoryPool<T> 可以避免固定操作

  │  小对象堆（SOH）                           大对象堆（LOH）  │
  │  ┌──────────┬──────────┬──────────┐       ┌──────────────┐ │
  │  │   0 代   │   1 代   │   2 代   │       │  ≥ 85KB 对象 │ │

  └─────────────────────────────────────────────────────────────┘

    高频回收     中频回收     低频回收（全量）

  GC 触发 → 挂起线程 → 标记（从根遍历）→ 压缩 → 恢复线程

  特殊机制：
  ┌─────────────────────────────────────────────────────────────┐
  │ 终结器   │ 对象不可达 → 终结队列 → 终结线程执行 → 再次 GC  │
  │ 弱引用   │ 不阻止 GC 回收，TryGetTarget 检查对象是否存活   │
  │ 固定对象 │ GC 压缩时不移动，用于 P/Invoke，需尽快解除固定  │

    · 用 IDisposable + using 确定性释放资源
    · 用 SafeHandle 代替自定义终结器
    · 用 ArrayPool / ObjectPool 减少大对象分配
    · 用 WeakReference 做内存安全的缓存
    · 让对象尽量在 0 代死亡
