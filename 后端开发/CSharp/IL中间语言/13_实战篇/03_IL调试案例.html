IL 调试案例

当 C# 源码看起来没问题，但运行时行为异常——问题往往藏在 IL 层。通过真实的调试案例，学会从 IL 视角定位和修复 Bug。

一、案例 1：callvirt 导致的 NullReferenceException

1.1 症状

// C# 源码
string name = GetName();
int length = name.Length;  // NullReferenceException 这里

报错指向 name.Length，但源码看起来是属性访问，不像方法调用。

1.2 IL 调查

; IL
ldloc.0                                 ; 加载 name
callvirt    instance int32 [System.Runtime]System.String::get_Length()
;           ^^^^^^^^ callvirt 在 null 引用上抛 NullReferenceException

1.3 根因

Length 是非虚属性，但 C# 编译器用 callvirt 调用。callvirt 执行前会检查对象引用是否为 null，如果是则抛出 NullReferenceException。

如果用 call 调用非虚方法，null 引用不会触发异常（除非方法体内部访问了 this）：

; 假设使用 call（实际上 C# 编译器不会这样做）
ldloc.0
call        instance int32 [System.Runtime]System.String::get_Length()
; call 不检查 null，如果 Length 内部不访问 this 字段，不会异常
; 但 String.Length 需要访问字段，所以仍然会异常

1.4 修复

// 修复1：null 检查
int length = name?.Length ?? 0;

// 修复2：确保方法不返回 null
string name = GetName() ?? string.Empty;

callvirt 的 null 检查是特性

C# 编译器选择 callvirt 正是为了提供免费的 null 检查。如果用 call 调用 null 对象的方法，方法体中如果没访问 this，会静默执行——这是更危险的 Bug。

二、案例 2：属性 getter 无限递归

2.1 症状

// C# 源码
public class Config
{
    public string Name { get; set; }  // 自动属性
}

开发者不小心将自动属性改为了：

public class Config
{
    public string Name
    {
        get { return Name; }    // Bug：应该是 name 字段
        set { Name = value; }   // Bug：应该是 name = value
    }
}

运行时 StackOverflowException。

2.2 IL 调查

; get_Name IL
ldarg.0                             ; this
call    instance string Config::get_Name()   ; 递归调用自身！
ret

; set_Name IL
ldarg.0                             ; this
ldarg.1                             ; value
call    instance void Config::set_Name(string) ; 递归调用自身！
ret

2.3 根因

属性 getter/setter 中引用了属性名本身而非后备字段，导致无限递归。在 IL 中可以清楚看到 call instance string Config::get_Name() 调用了自身。

2.4 正确的 IL

; 正确的 get_Name（使用后备字段）
ldarg.0
ldfld       string Config::<Name>k__BackingField
ret

; 正确的 set_Name
ldarg.0
ldarg.1
stfld       string Config::<Name>k__BackingField
ret

2.5 修复

// 修复：使用后备字段
private string _name;
public string Name
{
    get => _name;
    set => _name = value;
}

// 或直接使用自动属性
public string Name { get; set; }

三、案例 3：Reflection.Emit 生成的无效 IL

3.1 症状

// 使用 DynamicMethod 生成代码时
var method = new DynamicMethod("Bad", typeof(int), new[] { typeof(int) });
ILGenerator il = method.GetILGenerator();

il.Emit(OpCodes.Ldarg_0);
il.Emit(OpCodes.Ldc_I4, 1);
il.Emit(OpCodes.Add);
// 忘记 Emit Ret！

int result = (int)method.Invoke(null, new object[] { 5 });
// InvalidProgramException: Common Language Runtime detected an invalid program.

3.2 IL 调查

; 缺少 ret 的 IL
ldarg.0
ldc.i4.1
add
; 没有返回指令！栈上有值但方法未正确返回

3.3 常见 Reflection.Emit 错误

错误症状原因
缺少 RetInvalidProgramException方法没有返回指令
栈不平衡InvalidProgramException方法结束时栈上有多余值
类型不匹配VerificationException操作数类型与指令不匹配
分支到无效偏移InvalidProgramException标签未 MarkLabel
缺少 Nop 对齐微妙的执行差异异常处理边界不正确

3.4 修复

il.Emit(OpCodes.Ldarg_0);
il.Emit(OpCodes.Ldc_I4, 1);
il.Emit(OpCodes.Add);
il.Emit(OpCodes.Ret);    // 添加返回指令！

始终验证 Emit 的 IL

建议在 DynamicMethod 开发过程中：

  1. 先写等效 C#，用 ildasm 或 SharpLab 查看目标 IL
  2. 逐条对照 Emit
  3. 用 peverify 验证生成的程序集

四、案例 4：泛型方法中的隐式装箱

4.1 症状

// 性能回归：泛型方法比非泛型方法慢
public T Process<T>(T value)
{
    // 某些分支下 value 被装箱
    return value;
}

4.2 IL 调查

// 实际代码
public T Process<T>(T value)
{
    if (typeof(T) == typeof(int))
    {
        object boxed = value;       // T → object：装箱！
        int unboxed = (int)boxed;   // object → int：拆箱！
        return (T)(object)(unboxed + 1);
    }
    return value;
}
; typeof(T) == typeof(int) 分支的 IL
ldarg.1
box         !!T                  ; 装箱 T
stloc.1                          ; 存为 object
ldloc.1
unbox.any    [System.Runtime]System.Int32   ; 拆箱为 int
ldc.i4.1
add
box         [System.Runtime]System.Int32    ; 再次装箱为 object
unbox.any   !!T                  ; 拆箱为 T
ret
; 4 次装箱/拆箱操作！

4.3 根因

泛型中通过 object 中转值类型会产生多次装箱。T → object → int → object → T 的转换链在 IL 中清晰可见。

4.4 修复

// 避免通过 object 中转
public T Process<T>(T value) => value;  // 如果可能，直接使用 T

// 如果需要特殊处理值类型，使用模式匹配
if (value is int intValue)
{
    return (T)(object)(intValue + 1);  // 仍有一次装箱，但减少到 1 次
}

五、案例 5：Async 状态机异常被吞

5.1 症状

// 异步方法中的异常没有传播到调用者
public async Task<string> GetDataAsync()
{
    try
    {
        await SomeOperationAsync();
    }
    catch
    {
        // 吞掉异常，没有 rethrow 或记录
    }
    return "default";
}

更隐蔽的情况：fault 块（C# 不直接支持，但 IL 中存在）吞掉异常：

; 编译器生成的异步状态机 MoveNext 方法（简化）
.try
{
    ; await SomeOperationAsync()
    call       instance class [System.Runtime]System.Threading.Tasks.Task::GetAwaiter()
    call       instance void TaskAwaiter::GetResult()
    leave.s    IL_0050
}
.fault
{
    ; fault 块：异常时执行但不捕获异常
    ldarg.0
    ldc.i4.m1
    stfld      int32 StateMachine::<>1__state
    endfault
}
; 如果 fault 块后没有重新抛出，异常就被吞了

5.2 IL 调查

在 dnSpy 中查看异步状态机的 MoveNext 方法：

  1. 找到 <>c__DisplayClass 或 AsyncTaskMethodBuilder 相关类型
  2. 查看 MoveNext() 方法的异常处理表（EH Table）
  3. 确认 catch 块是否正确 rethrow，fault 块后是否继续传播异常

5.3 修复

// 修复1：不要吞异常
catch (Exception ex)
{
    _logger.LogError(ex, "Operation failed");
    throw;  // 重新抛出
}

// 修复2：使用 ExceptionDispatchInfo 保持调用栈
catch (Exception ex)
{
    _logger.LogError(ex, "Operation failed");
    ExceptionDispatchInfo.Capture(ex).Throw();
}

六、案例 6：迭代器未 Dispose

6.1 症状

// 迭代器方法中的 try/finally 未执行
public IEnumerable<int> GetNumbers()
{
    try
    {
        yield return 1;
        yield return 2;
        yield return 3;
    }
    finally
    {
        Console.WriteLine("Cleanup");  // 可能不会执行
    }
}

// 调用方提前退出
foreach (var n in GetNumbers())
{
    Console.WriteLine(n);
    break;  // 提前退出，finally 不执行？
}

6.2 IL 调查

迭代器被编译为状态机，finally 块在 Dispose() 中执行：

; 迭代器状态机的 MoveNext 方法（简化）
; state = 0 → yield return 1
ldarg.0
ldc.i4.1
stfld      int32 Iterator::<>2__current
ldarg.0
ldc.i4.1
stfld      int32 Iterator::<>1__state
ldc.i4.1
ret

; Dispose 方法
; state > 0 时执行 finally 块
ldarg.0
ldfld      int32 Iterator::<>1__state
ldc.i4.0
ble.s      IL_0010
; ... 执行 finally 块 ...

6.3 根因

foreach 编译为 try/finally，正常退出时调用 Dispose()。但如果调用方没有使用 foreach，而是手动获取枚举器：

var enumerator = GetNumbers().GetEnumerator();
enumerator.MoveNext();
// 没有调用 enumerator.Dispose() → finally 不执行

6.4 修复

// 修复1：确保使用 foreach（编译器生成 Dispose 调用）
foreach (var n in GetNumbers())
{
    break;  // foreach 的 finally 会调用 Dispose
}

// 修复2：手动确保 Dispose
var enumerator = GetNumbers().GetEnumerator();
try
{
    enumerator.MoveNext();
}
finally
{
    enumerator.Dispose();
}

迭代器的 finally 依赖 Dispose

迭代器方法中的 finally 块被编译到 Dispose() 方法中。只有调用 Dispose()（或 foreach 正常/异常退出）才会触发 finally 逻辑。提前退出迭代时务必确保 Dispose 被调用。

七、dnSpy IL 级调试

7.1 设置 IL 断点

  1. 打开 dnSpy，加载程序集
  2. 在方法视图中切换到 IL 视图（右键 → View → IL）
  3. 在 IL 指令行设置断点
  4. 附加到进程，开始调试

7.2 查看 EH 表

在 dnSpy 中查看方法的异常处理表：

.try IL_0000 to IL_0010 catch Exception handler IL_0010 to IL_0025
.try IL_0000 to IL_0010 finally handler IL_0025 to IL_0030

7.3 读取 EH 表的技巧

EH 子句类型含义
Catch捕获指定类型的异常
Filter条件捕获（VB 的 When、C# 的 when）
Finally无论如何都执行的清理块
Fault异常时执行但不捕获（C# 不直接使用）

八、SOS/DumpIL 生产调试

8.1 使用 SOS 扩展

# 加载 SOS 扩展
.loadby sos clr

# 查看方法的 IL
!DumpIL <MethodDesc>

# 查看方法描述符
!DumpMD <MethodDesc>

# 查看栈上的方法
!CLRStack

# 查看异常对象
!PrintException <address>

8.2 使用 dotnet-dump

# 创建进程转储
dotnet-dump collect -p <pid>

# 分析转储
dotnet-dump analyze <dump>

# 在分析器中
> clrstack          # 查看托管栈
> dumpil <MethodDesc>  # 查看方法 IL
> pe                 # 查看当前异常

面试要点

  1. callvirt 为什么会抛 NullReferenceException？ callvirt 执行前会检查目标对象引用是否为 null。即使是调用非虚方法，C# 编译器也默认使用 callvirt，所以属性访问 null 对象会抛异常。

  2. 属性 getter 无限递归在 IL 中如何表现？ getter 的 IL 中 call instance Type::get_Property() 调用自身，没有 ldfld 访问后备字段。这是在 IL 层最直接的诊断方式。

  3. Reflection.Emit 生成无效 IL 的常见原因？ 缺少 Ret、栈不平衡（方法结束时栈上有多余值）、类型不匹配、分支标签未标记。建议先用 ildasm 查看目标 IL，再逐条 Emit。

  4. 迭代器的 finally 为什么可能不执行？ 迭代器的 finally 块被编译到 Dispose() 方法中。如果调用方没有通过 foreach（会自动调用 Dispose）遍历，而是手动获取枚举器后提前退出，finally 不会执行。

  5. 如何调试生产环境的 IL 级问题？ 使用 dotnet-dump collect 收集进程转储，用 dotnet-dump analyze 或 SOS 扩展查看托管栈和方法 IL。关键命令：clrstack、dumpil、pe。
