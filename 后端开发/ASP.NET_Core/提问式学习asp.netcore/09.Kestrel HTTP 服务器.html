Kestrel HTTP 服务器

ASP.NET Core Kestrel HTTP 服务器：源码级深入

一、核心认知

Kestrel 的本质就是一个"TCP 连接管理器 + HTTP 协议解析器"：它监听 TCP 端口，接收原始字节流，将其解析为 HTTP 请求对象，然后把请求交给中间件管道处理，最后把响应序列化为字节流写回网络。

四、KestrelServer 启动流程

// 📁 源码位置: src/Servers/Kestrel/Core/src/KestrelServerImpl.cs

internal sealed class KestrelServerImpl : IServer
{
    private readonly ServerAddressesFeature _serverAddresses;
    private readonly IConnectionListenerFactory _transportFactory;

    public async Task StartAsync<TContext>(
        IHttpApplication<TContext> application,
        CancellationToken cancellationToken)
        where TContext : notnull
    {
        // 🔥 第1步：解析监听地址
        var addresses = _serverAddresses.Addresses;
        // 例如: ["http://localhost:5000", "https://localhost:5001"]
        // 或来自配置: builder.WebHost.UseUrls("http://*:8080")

        // 🔥 第2步：对每个地址创建监听器
        foreach (var address in _bindAddresses)
        {
            var endpoint = ParseAddress(address);
            // "http://localhost:5000" → IPEndPoint(127.0.0.1, 5000)
            // "https://*:443" → IPEndPoint(0.0.0.0, 443)
            
            await BindAsync(endpoint, application, cancellationToken);
        }
    }

    private async Task BindAsync<TContext>(
        EndpointConfig endpointConfig,
        IHttpApplication<TContext> application,
        CancellationToken cancellationToken)
    {
        // 🔥 第3步：创建传输层监听器
        var transport = await _transportFactory.BindAsync(
            endpointConfig.EndPoint, 
            cancellationToken);
        // SocketTransportFactory 
        //   → 创建 Socket
        //   → Socket.Bind(endpoint) 
        //   → Socket.Listen(backlog)

        // 🔥 第4步：构建连接中间件管道
        var connectionDelegate = BuildConnectionPipeline(endpointConfig);
        // 连接中间件管道（和请求中间件管道类似，但是连接级别的）：
        //   TLS Middleware → HTTP Protocol Middleware

        // 🔥 第5步：开始接受连接
        StartAcceptLoop(transport, connectionDelegate, application);
    }

    private void StartAcceptLoop<TContext>(
        IConnectionListener transport,
        ConnectionDelegate connectionDelegate,
        IHttpApplication<TContext> application)
    {
        // 🔥 在后台线程中循环接受新连接
        _ = AcceptConnectionsAsync();
        
        async Task AcceptConnectionsAsync()
        {
            while (true)
            {
                // 等待新的 TCP 连接
                var connection = await transport.AcceptAsync();
                
                if (connection == null)
                    break; // 服务器正在关闭
                
                // 🔥 为每个连接启动处理任务
                // 不 await，允许同时处理多个连接
                _ = ProcessConnectionAsync(connection, connectionDelegate);
            }
        }
    }

    private async Task ProcessConnectionAsync(
        ConnectionContext connection,
        ConnectionDelegate connectionDelegate)
    {
        try
        {
            _connectionManager.AddConnection(connection);
            
            // 🔥 执行连接中间件管道
            await connectionDelegate(connection);
            // TLS → HTTP 协议处理
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Connection {id} error", connection.ConnectionId);
        }
        finally
        {
            _connectionManager.RemoveConnection(connection);
            await connection.DisposeAsync();
        }
    }
}

五、连接处理 —— 从 TCP 到 HTTP

5.1 连接中间件管道

// Kestrel 有两层管道：
// 1. 连接级别管道（Connection Middleware）—— 处理TCP连接
// 2. 请求级别管道（Request Middleware）—— 处理HTTP请求（就是我们学过的中间件管道）

// 连接级别管道：
//
// TCP 连接到达
//     │
//     ▼
// [连接中间件1] TLS Handshake (HTTPS)
//     │  如果是HTTPS连接，在这里进行TLS握手
//     │  协商加密算法，验证证书
//     │  之后的数据都是加密传输
//     ▼
// [连接中间件2] HTTP Version Detection
//     │  检测HTTP协议版本
//     │  HTTP/1.1 → Http1Connection
//     │  HTTP/2   → Http2Connection（通过ALPN协商）
//     │  HTTP/3   → Http3Connection（基于QUIC）
//     ▼
// [HTTP处理] 根据协议版本解析请求
//     │  解析请求行、请求头、请求体
//     │  创建 HttpContext
//     │  执行请求中间件管道
//     │  写回响应

{
    public async Task ProcessRequestsAsync<TContext>(IHttpApplication<TContext> application)
    {

        if (_context.Protocols.HasFlag(HttpProtocols.Http2) && 
            IsHttp2Connection())
        {

            await http2Connection.ProcessRequestsAsync(application);
        }
        else

            await http1Connection.ProcessRequestsAsync();
        }
    }
}

六、Http1Connection —— HTTP/1.1 请求处理核心

// 📁 源码位置: src/Servers/Kestrel/Core/src/Internal/Http/Http1Connection.cs

internal sealed partial class Http1Connection : HttpProtocol, IRequestProcessor
{
    // 🔥 循环处理同一TCP连接上的多个请求（Keep-Alive）
    public async Task ProcessRequestsAsync()
    {
        while (true)
        {
            // ====================================
            // 🔥 第1阶段：解析请求行
            // "GET /api/users/123 HTTP/1.1\r\n"
            // ====================================
            var readResult = await Input.ReadAsync();
            var buffer = readResult.Buffer;
            
            if (!TryParseRequestLine(buffer, out var consumed, out var examined))
            {
                if (readResult.IsCompleted)
                    return; // 连接关闭
                continue;   // 数据不完整，继续读取
            }
            
            // 解析结果：
            // Method = "GET"
            // Path = "/api/users/123"
            // HttpVersion = Http11
            
            Input.AdvanceTo(consumed, examined);

            // ====================================
            // 🔥 第2阶段：解析请求头
            // "Host: sso.example.com\r\n"
            // "Authorization: Bearer eyJhbG...\r\n"
            // "Accept: application/json\r\n"
            // "\r\n"  ← 空行表示头结束
            // ====================================
            while (true)
            {
                readResult = await Input.ReadAsync();
                buffer = readResult.Buffer;
                
                if (TryParseHeaders(buffer, out consumed, out examined))
                    break; // 所有请求头解析完毕
                    
                Input.AdvanceTo(consumed, examined);
            }

            // ====================================
            // 🔥 第3阶段：处理请求
            // ====================================
            var messageBody = CreateMessageBody();
            // 根据 Content-Length 或 Transfer-Encoding
            // 创建请求体读取器
            
            // 🔥🔥🔥 调用应用层处理请求
            await _application.ProcessRequestAsync(_context);
            // HostingApplication.ProcessRequestAsync()
            //   → 创建 HttpContext
            //   → 创建 DI Scope
            //   → 执行中间件管道
            //   → 释放 DI Scope
            
            // ====================================
            // 🔥 第4阶段：完成响应
            // ====================================
            await FlushResponseAsync();
            
            // ====================================
            // 🔥 第5阶段：检查是否 Keep-Alive
            // ====================================
            if (!_keepAlive)
            {
                return; // 关闭连接
            }
            
            // Keep-Alive → 重置状态，准备处理下一个请求
            Reset();
            
            // 回到循环开头，等待下一个请求
        }
    }
}

6.1 请求行解析

// 📁 源码位置: src/Servers/Kestrel/Core/src/Internal/Http/HttpParser.cs

internal sealed class HttpParser<TRequestHandler> : IHttpParser<TRequestHandler>
    where TRequestHandler : IHttpHeadersHandler, IHttpRequestLineHandler
{
    public bool ParseRequestLine(
        TRequestHandler handler, 
        ref SequenceReader<byte> reader)
    {
        // 原始字节：
        // 47 45 54 20 2F 61 70 69 2F 75 73 65 72 73 2F 31 32 33 20 48 54 54 50 2F 31 2E 31 0D 0A
        // G  E  T     /  a  p  i  /  u  s  e  r  s  /  1  2  3     H  T  T  P  /  1  .  1  \r \n

        // 🔥 优化：不使用字符串分割，直接在字节级别解析
        
        // 找到第一个空格 → Method结束
        var methodEnd = reader.UnreadSpan.IndexOf((byte)' ');
        var method = reader.UnreadSpan.Slice(0, methodEnd);
        // method = "GET" (字节)
        
        // 🔥 已知HTTP方法的快速匹配
        // 不是逐字比较，而是把前几个字节作为整数比较
        if (method.Length == 3)
        {
            var methodInt = (method[0] << 16) | (method[1] << 8) | method[2];
            if (methodInt == (('G' << 16) | ('E' << 8) | 'T'))
            {
                knownMethod = HttpMethod.Get;
                // 直接识别为GET，避免字符串创建和比较
            }
        }
        
        reader.Advance(methodEnd + 1); // 跳过空格
        
        // 找到第二个空格 → Path结束
        var pathEnd = reader.UnreadSpan.IndexOf((byte)' ');
        var path = reader.UnreadSpan.Slice(0, pathEnd);
        // path = "/api/users/123" (字节)
        
        reader.Advance(pathEnd + 1);
        
        // 剩下的是 HTTP版本 + \r\n
        // "HTTP/1.1\r\n"
        var version = ParseHttpVersion(reader);

        // 通知Handler
        handler.OnStartLine(knownMethod, version, targetPath, ...);
        
        return true;
    }
}

6.2 请求头解析

// 📁 源码位置: src/Servers/Kestrel/Core/src/Internal/Http/HttpParser.cs

public bool ParseHeaders(
    TRequestHandler handler,
    ref SequenceReader<byte> reader)
{
    while (true)
    {
        var span = reader.UnreadSpan;
        
        // 🔥 检查是否到达空行（\r\n）→ 头部结束
        if (span.Length >= 2 && span[0] == '\r' && span[1] == '\n')
        {
            reader.Advance(2);
            return true; // 所有头部解析完毕
        }
        
        // 找到冒号 → 分隔 Header Name 和 Value
        var colonIndex = span.IndexOf((byte)':');
        var headerName = span.Slice(0, colonIndex);
        
        // 跳过冒号后的空格
        var valueStart = colonIndex + 1;
        while (span[valueStart] == ' ') valueStart++;
        
        // 找到 \r\n → Value结束
        var lineEnd = span.IndexOf((byte)'\r');
        var headerValue = span.Slice(valueStart, lineEnd - valueStart);
        
        // 🔥 已知头部的快速匹配
        // ASP.NET Core 维护了一个已知头部名称的查找表
        // "Host"、"Content-Type"、"Authorization" 等
        // 使用长度+前几个字符的组合快速识别
        
        var knownHeader = TryMatchKnownHeader(headerName);
        
        if (knownHeader != null)
        {
            // 已知头部 → 使用预分配的字符串，避免内存分配
            handler.OnHeader(knownHeader, headerValue);
            // 例如：OnHeader(KnownHeaders.Authorization, "Bearer eyJhbG...")
        }
        else
        {
            // 未知头部 → 创建字符串
            handler.OnHeader(
                Encoding.ASCII.GetString(headerName),
                Encoding.ASCII.GetString(headerValue));
        }
        
        reader.Advance(lineEnd + 2); // 跳过 \r\n
    }
}

七、System.IO.Pipelines —— Kestrel 的高性能 I/O 基础

7.1 为什么需要 Pipelines？

传统的 Stream I/O 问题：

byte[] buffer = new byte[4096];
int bytesRead = await stream.ReadAsync(buffer, 0, buffer.Length);

问题1：缓冲区大小固定
  → 如果请求头超过4096字节，需要多次读取
  → 需要自己管理缓冲区拼接

问题2：每次Read都可能分配新的byte[]
  → GC压力大

问题3：Read和Parse耦合
  → 必须先Read完才能Parse
  → 无法并行读取和解析

Pipelines 的解决方案：

PipeReader reader = connection.Transport.Input;

ReadResult result = await reader.ReadAsync();
ReadOnlySequence<byte> buffer = result.Buffer;
// buffer 可能跨越多个内存段（链表），零拷贝
// 不需要自己管理缓冲区大小
// 底层使用内存池（ArrayPool），减少GC

// 解析后告诉Pipeline消费了多少
reader.AdvanceTo(consumed, examined);
// Pipeline会自动回收已消费的内存

│  │                 │             │                 │             │
│  │  网络层写入      │    Pipe     │  Kestrel解析    │             │
│  │  TCP数据到这里   │ ─────────► │  从这里读取      │             │
│  │                 │   环形     │  HTTP请求数据    │             │
│  │                 │   缓冲区   │                 │             │
│  └─────────────────┘             └─────────────────┘             │
│                                                                   │
│  写入流程：                                                       │
│  1. Memory<byte> mem = writer.GetMemory(sizeHint);               │
│     → 从内存池获取一块内存                                         │
│  2. 将网络数据复制到 mem                                           │
│  3. writer.Advance(bytesWritten);                                 │
│     → 告诉Pipe写了多少字节                                        │
│  4. await writer.FlushAsync();                                    │
│     → 通知Reader有新数据可读                                      │
│                                                                   │
│  读取流程：                                                       │
│  1. ReadResult result = await reader.ReadAsync();                 │
│     → 等待有数据可读（如果没有数据会异步等待）                      │
│  2. ReadOnlySequence<byte> buffer = result.Buffer;                │
│     → 获取可读的字节序列（可能跨越多个内存段）                      │
│  3. 解析数据...                                                   │
│  4. reader.AdvanceTo(consumed, examined);                         │
│     → consumed: 已消费的位置（这些内存可以回收）                    │
│     → examined: 已检查的位置（下次从这里之后开始提供新数据）         │
│                                                                   │
│  ┌──────────────────────────────────────────────────────────┐     │
│  │  内存布局 (ReadOnlySequence<byte>)                       │     │
│  │                                                          │     │
│  │  Segment1[4096]  → Segment2[4096]  → Segment3[2048]     │     │
│  │  ├──已消费──┤├──可读────────────────────────────┤        │     │
│  │             consumed                      examined       │     │
│  │                                                          │     │
│  │  和 Stream 的区别：                                       │     │
│  │  - Stream: 连续的byte[]，大小固定                         │     │
│  │  - Sequence: 链表结构，可以无限增长                        │     │
│  │  - 不需要复制数据到单个连续缓冲区                          │     │
│  └──────────────────────────────────────────────────────────┘     │
│                                                                   │
└───────────────────────────────────────────────────────────────────┘

// 📁 源码位置: src/Servers/Kestrel/Transport.Sockets/src/Internal/SocketConnection.cs

internal sealed class SocketConnection : TransportConnection
{
    private readonly Socket _socket;
    private readonly Pipe _inputPipe;   // 网络 → 应用
    private readonly Pipe _outputPipe;  // 应用 → 网络

    // 🔥 接收循环：从Socket读取数据写入Pipe
    private async Task DoReceive()
    {
        while (true)
        {
            // 从Pipe获取写入缓冲区
            var buffer = _inputPipe.Writer.GetMemory(MinAllocBufferSize);
            // 使用内存池，几乎零GC
            
            try
            {
                // 🔥 从Socket读取数据
                var bytesReceived = await _socket.ReceiveAsync(buffer, SocketFlags.None);
                
                if (bytesReceived == 0)
                {
                    // 连接关闭
                    break;
                }
                
                // 告诉Pipe写入了多少字节
                _inputPipe.Writer.Advance(bytesReceived);
            }
            catch (Exception ex)
            {
                _logger.ConnectionError(_connectionId, ex);
                break;
            }
            
            // 🔥 刷新 → 通知读取端有新数据
            var result = await _inputPipe.Writer.FlushAsync();
            
            if (result.IsCompleted || result.IsCanceled)
            {
                break; // 读取端已关闭
            }
        }
        
        // 标记写入完成
        _inputPipe.Writer.Complete();
    }

    // 🔥 发送循环：从Pipe读取数据发送到Socket
    private async Task DoSend()
    {
        while (true)
        {
            // 等待应用层写入的响应数据
            var result = await _outputPipe.Reader.ReadAsync();
            var buffer = result.Buffer;
            
            if (buffer.IsEmpty && result.IsCompleted)
            {
                break;
            }
            
            // 🔥 将数据发送到Socket
            if (!buffer.IsEmpty)
            {
                if (buffer.IsSingleSegment)
                {
                    // 单段 → 直接发送
                    await _socket.SendAsync(buffer.First, SocketFlags.None);
                }
                else
                {
                    // 多段 → 使用 Scatter/Gather I/O
                    foreach (var segment in buffer)
                    {
                        await _socket.SendAsync(segment, SocketFlags.None);
                    }
                }
            }
            
            // 标记已消费
            _outputPipe.Reader.AdvanceTo(buffer.End);
        }
    }
}

        //   IHttpRequestFeature    → 请求信息（Method, Path, Headers等）
        //   IHttpResponseFeature   → 响应信息（StatusCode, Headers等）
        //   IHttpResponseBodyFeature → 响应体写入
        //   IHttpConnectionFeature → 连接信息（RemoteIP等）

        var scope = _serviceScopeFactory.CreateScope();
        httpContext.RequestServices = scope.ServiceProvider;
        // 从这里开始，Scoped服务生效
        // 如 DbContext, IOpenIddictApplicationManager 等
        
        context.Scope = scope;

        if (_diagnosticSource.IsEnabled("Microsoft.AspNetCore.Hosting.HttpRequestIn"))
        {
            _diagnosticSource.StartActivity(context.Activity, ...);
        }

        _logger.RequestStarting(
            httpContext.Request.Protocol,
            httpContext.Request.Method,
            httpContext.Request.Scheme,
            httpContext.Request.Host.ToString(),
            httpContext.Request.Path);

        return context;
    }

    // =====================================================
    // 🔥 处理请求
    // =====================================================
    public Task ProcessRequestAsync(Context context)
    {
        // 🔥🔥🔥 执行中间件管道！
        return _application(context.HttpContext!);
        // _application 就是 ApplicationBuilder.Build() 生成的 RequestDelegate
        //
        // 等价于：
        // AuthenticationMiddleware
        //   → AuthorizationMiddleware
        //     → RoutingMiddleware
        //       → EndpointMiddleware
        //         → Controller/Minimal API
    }

    // =====================================================
    // 🔥 清理上下文
    // =====================================================
    public void DisposeContext(Context context, Exception? exception)
    {
        // 🔥 记录请求结束
        _logger.RequestFinished(
            context.HttpContext!.Response.StatusCode,
            context.HttpContext.Request.ContentLength,
            context.HttpContext.Response.ContentLength,
            context.ElapsedTime);

        if (context.Activity != null)
        {
            _diagnosticSource.StopActivity(context.Activity, ...);
        }

        // 🔥🔥🔥 释放 DI Scope
        context.Scope?.Dispose();
        // 所有 Scoped 服务在这里被释放
        // DbContext.Dispose()
        // OpenIddict 的 Scoped 服务释放
        
        // 回收 HttpContext 到对象池
        _httpContextFactory.Dispose(context.HttpContext!);
        // DefaultHttpContext 不是每次都new
        // 使用对象池复用，减少GC压力
    }

    internal struct Context

        public Activity? Activity;

Feature 集合的设计：Kestrel 和 HttpContext 的解耦

为什么用 Feature 而不是直接设置属性？

因为不同的服务器（Kestrel, IIS, TestServer）提供不同的功能。
Feature 集合是服务器和应用之间的契约。

Kestrel 提供的 Features：
├── IHttpRequestFeature      → Method, Path, Headers, Body
├── IHttpResponseFeature     → StatusCode, Headers
├── IHttpResponseBodyFeature → 响应体写入（PipeWriter）
├── IHttpConnectionFeature   → RemoteIpAddress, RemotePort
├── IHttpRequestLifetimeFeature → Abort()
├── IHttp2StreamIdFeature    → HTTP/2 流ID
├── ITlsConnectionFeature    → ClientCertificate
└── ...

IIS 提供的 Features（不同的子集）：
├── IHttpRequestFeature
├── IHttpResponseFeature
├── IServerVariablesFeature  → IIS特有
└── ...

TestServer 提供的 Features：
├── IHttpRequestFeature      → 从内存中创建
├── IHttpResponseFeature     → 写入内存
└── ...

通过 Feature 集合，HttpContext 不需要知道底层是什么服务器
只要 Feature 存在就能使用对应功能

Http2Connection 的多路复用

// 📁 源码位置: src/Servers/Kestrel/Core/src/Internal/Http2/Http2Connection.cs

// HTTP/2 连接处理（简化版）
internal sealed class Http2Connection
{
    // 活跃的流（每个流 = 一个独立的请求）
    private readonly ConcurrentDictionary<int, Http2Stream> _streams = new();
    
    public async Task ProcessRequestsAsync<TContext>(IHttpApplication<TContext> application)
    {
        while (true)
        {
            // 🔥 读取 HTTP/2 帧
            var frame = await ReadFrameAsync();
            
            switch (frame.Type)
            {
                case Http2FrameType.HEADERS:
                    // 🔥 新的请求流
                    var stream = new Http2Stream(frame.StreamId, this);
                    _streams[frame.StreamId] = stream;
                    
                    // 🔥 解析HPACK压缩的请求头
                    DecodeHeaders(frame, stream);
                    
                    // 🔥 在独立的Task中处理此流的请求
                    // 不阻塞其他流！
                    _ = stream.ProcessRequestAsync(application);
                    break;
                    
                case Http2FrameType.DATA:
                    // 🔥 请求体数据
                    if (_streams.TryGetValue(frame.StreamId, out var dataStream))
                    {
                        dataStream.OnDataReceived(frame.Payload);
                    }
                    break;
                    
                case Http2FrameType.WINDOW_UPDATE:
                    // 流量控制
                    HandleWindowUpdate(frame);
                    break;
                    
                case Http2FrameType.RST_STREAM:
                    // 取消某个流
                    if (_streams.TryRemove(frame.StreamId, out var cancelledStream))
                    {
                        cancelledStream.Abort();
                    }
                    break;
                    
                case Http2FrameType.GOAWAY:
                    // 关闭连接
                    return;
            }
        }
    }
}

internal class Http2Stream
{

        // 创建 HttpContext → 执行中间件管道 → 写回响应

12.2 已知请求头的零分配优化

// Kestrel 对常见的HTTP头部进行了特殊优化

// 📁 源码位置: src/Servers/Kestrel/Core/src/Internal/Http/HttpHeaders.Generated.cs

// 例如 Content-Type 头：
// 不是存为 Dictionary<string, StringValues>
// 而是直接在类中定义字段

internal partial class HttpRequestHeaders
{
    // 🔥 常见头部有专门的字段，避免字典查找
    private StringValues _Host;
    private StringValues _ContentType;
    private StringValues _ContentLength;
    private StringValues _Authorization;
    private StringValues _Accept;
    private StringValues _Connection;
    private StringValues _UserAgent;
    private StringValues _Cookie;
    // ... 更多已知头部

    // 🔥 已知头部名称使用预分配的字符串常量
    // 不需要每次从字节解析成新的字符串
    
    private static readonly byte[] _headerHost = Encoding.ASCII.GetBytes("Host");
    private static readonly byte[] _headerContentType = Encoding.ASCII.GetBytes("Content-Type");
    // ...
    
    // 🔥 设置头部时，通过长度和首字节快速判断
    public void Append(ReadOnlySpan<byte> name, ReadOnlySpan<byte> value)
    {
        switch (name.Length)
        {
            case 4:
                // "Host" (长度4)
                if (name[0] == 'H' && name.SequenceEqual(_headerHost))
                {
                    _Host = new StringValues(value.ToString());
                    _bits |= 0x1; // 标记位
                    return;
                }
                break;
                
            case 12:
                // "Content-Type" (长度12)
                if (name[0] == 'C' && name.SequenceEqual(_headerContentType))
                {
                    _ContentType = new StringValues(value.ToString());
                    _bits |= 0x2;
                    return;
                }
                break;
                
            case 13:
                // "Authorization" (长度13)
                if (name[0] == 'A' && name.SequenceEqual(_headerAuthorization))
                {
                    _Authorization = new StringValues(value.ToString());
                    _bits |= 0x4;
                    return;
                }
                // "Content-Length" (也是长度13)
                if (name[0] == 'C' && name.SequenceEqual(_headerContentLength))
                {
                    _ContentLength = new StringValues(value.ToString());
                    _bits |= 0x8;
                    return;
                }
                break;
        }
        
        // 🔥 未知头部才存入字典
        _unknownHeaders ??= new Dictionary<string, StringValues>();
        _unknownHeaders[name.ToString()] = value.ToString();
    }
}

1. OpenIddict 签发 Token 时需要知道正确的 Issuer
   Token.Issuer = https://sso.example.com

十四、优雅关闭（Graceful Shutdown）

// 📁 源码位置: src/Servers/Kestrel/Core/src/KestrelServerImpl.cs

public async Task StopAsync(CancellationToken cancellationToken)
{
    // 🔥 第1步：停止接受新连接
    foreach (var listener in _listeners)
    {
        await listener.UnbindAsync(cancellationToken);
    }
    // 此时新的TCP连接会被操作系统拒绝（Connection Refused）

    // 🔥 第2步：等待正在处理的请求完成
    // 或者等到 cancellationToken 超时
    var tasks = new List<Task>();
    foreach (var connection in _connectionManager.GetConnections())
    {
        // 通知连接应该关闭
        connection.RequestClose();
        // HTTP/1.1: 设置 Connection: close 头
        // HTTP/2: 发送 GOAWAY 帧
        
        tasks.Add(connection.CompletionTask);
    }
    
    // 等待所有连接完成（有超时）
    await Task.WhenAll(tasks).WaitAsync(cancellationToken);
    
    // 🔥 第3步：如果超时，强制关闭
    if (cancellationToken.IsCancellationRequested)
    {
        foreach (var connection in _connectionManager.GetConnections())
        {
            connection.Abort(new ConnectionAbortedException("Server shutting down"));
        }
    }
}

十九、检验你的理解

  1. Kestrel 监听 TCP 端口后，一个完整的请求处理经过哪些层？每层的职责是什么？
    （答案：① Transport层（SocketConnection）：管理TCP Socket的读写，使用Pipe进行高效I/O。② 连接中间件层：TLS握手（HTTPS）、HTTP协议版本检测。③ HTTP协议层（Http1Connection/Http2Connection）：解析HTTP请求行、请求头、管理请求体和响应写入。④ 应用层（HostingApplication）：创建HttpContext和DI Scope，执行中间件管道（RequestDelegate），释放Scope。）

  2. System.IO.Pipelines 比传统 Stream 好在哪里？为什么 Kestrel 选择用 Pipe？
    （答案：① 内存管理：Pipe使用MemoryPool/ArrayPool，减少GC。Stream每次Read可能分配新byte[]。② 缓冲区管理：Pipe自动管理可变大小的缓冲区（链表结构），不需要预估大小。Stream需要固定大小的缓冲区。③ 反压（Backpressure）：Pipe天然支持写入端和读取端的速度协调。④ 读写分离：Pipe的Writer和Reader可以在不同线程并行工作。⑤ 零拷贝：ReadOnlySequence可以跨多个内存段，不需要拷贝到连续缓冲区。）

  3. 为什么 HttpContext 的属性（Method, Path, Headers等）要通过 Feature 集合获取，而不是直接存储？
    （答案：为了解耦服务器实现和应用层。不同的服务器（Kestrel、IIS、TestServer）提供不同的Feature实现。HttpContext只依赖Feature接口，不依赖具体服务器。这样Kestrel可以提供高性能的Feature实现（如直接操作Pipe），IIS可以提供IIS特有的Feature（如ServerVariables），而应用代码不需要修改。这是策略模式的应用。）

  4. 在反向代理后面运行 Kestrel 时，为什么必须配置 ForwardedHeaders？对 SSO 项目有什么影响？
    （答案：反向代理接收HTTPS请求后，以HTTP转发给Kestrel。Kestrel看到的是HTTP请求，RemoteIP是代理的IP。不配置ForwardedHeaders会导致：① OpenIddict 的 Issuer 是 "http://localhost:5000" 而不是 "https://sso.example.com"——Token验证会失败。② Cookie 的 Secure 标志不会设置——SameSite=None失效，跨域SSO不工作。③ 审计日志记录的是代理IP而不是客户端真实IP。④ redirect_uri 的 scheme 不匹配——OAuth流程中断。）

  5. HTTP/2 多路复用是怎么实现的？和 HTTP/1.1 Keep-Alive 有什么本质区别？
    （答案：HTTP/1.1 Keep-Alive 是连接级别的串行复用——同一时间同一连接只能处理一个请求/响应对，必须等上一个完成才能发下一个（队头阻塞）。HTTP/2 多路复用是流级别的并行复用——同一个TCP连接上可以同时有多个Stream（逻辑通道），每个Stream独立传输一个请求/响应对，它们的数据帧可以交错发送。在Kestrel中，Http2Connection为每个Stream创建独立的Http2Stream实例，每个Stream在独立的Task中执行中间件管道，互不阻塞。）

  6. Kestrel 优雅关闭时正在处理的 SSO Token 请求会怎样？
    （答案：① 首先停止接受新TCP连接——新的请求会被操作系统拒绝（Connection Refused）。② 对已有连接，HTTP/1.1设置Connection: close，HTTP/2发送GOAWAY帧——通知客户端不要发新请求。③ 正在处理的Token请求会继续执行直到完成——授权码验证、Token签发、数据库写入都会正常完成。④ 在配置的ShutdownTimeout内等待所有请求完成。⑤ 超时后强制中断剩余连接。所以只要ShutdownTimeout足够长，正在进行的Token交换不会丢失。）
