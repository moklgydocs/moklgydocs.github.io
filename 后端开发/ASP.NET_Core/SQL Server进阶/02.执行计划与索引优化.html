执行计划与索引优化

第二章：执行计划与索引优化

不会看执行计划的 DBA，就像不会看 X 光片的医生。 执行计划是 SQL 性能优化的"第一工具"。

一、执行计划基础

1.1 如何查看执行计划

-- 方式1：SSMS 图形化（推荐）
-- Ctrl + L = 预估执行计划
-- Ctrl + M = 包含实际执行计划，然后执行查询

-- 方式2：文本执行计划
SET SHOWPLAN_TEXT ON;
GO
SELECT * FROM Orders WHERE OrderDate > '2024-01-01';
GO
SET SHOWPLAN_TEXT OFF;

-- 方式3：XML执行计划（最详细）
SET STATISTICS XML ON;
GO
SELECT * FROM Orders WHERE OrderDate > '2024-01-01';
GO
SET STATISTICS XML OFF;

-- 方式4：查看IO和时间统计
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
GO
SELECT * FROM Orders WHERE OrderDate > '2024-01-01';
GO

1.2 执行计划核心操作符

┌────────────────────┬──────────────────────────────────────────┬────────┐
│ 操作符              │ 含义                                      │ 好/坏  │
├────────────────────┼──────────────────────────────────────────┼────────┤
│ Table Scan         │ 全表扫描（堆表）                           │ ❌ 差  │
│ Clustered Index Scan│ 聚集索引扫描（全表扫描的等价）               │ ⚠️ 一般│
│ Index Scan         │ 非聚集索引扫描                              │ ⚠️ 一般│
│ Index Seek         │ 索引查找（精确定位）                         │ ✅ 好  │
│ Clustered Index Seek│ 聚集索引查找                               │ ✅ 好  │
│ Key Lookup         │ 回表查找（非聚集索引→聚集索引）              │ ⚠️ 代价│
│ RID Lookup         │ 回堆查找（非聚集索引→堆表）                 │ ⚠️ 代价│
│ Nested Loops       │ 嵌套循环JOIN                                │ 小表好 │
│ Hash Match         │ 哈希匹配JOIN                                │ 大表好 │
│ Merge Join         │ 合并JOIN（都已排序）                        │ ✅ 最佳│
│ Sort               │ 排序                                       │ ⚠️ 开销│
│ Hash Aggregate     │ 哈希聚合（GROUP BY）                        │ 大表好 │
│ Stream Aggregate   │ 流聚合（数据已排序时）                      │ ✅ 好  │
│ Parallelism        │ 并行操作                                    │ 视情况 │
│ Bookmark Lookup    │ 书签查找（同Key Lookup）                    │ ⚠️ 代价│
└────────────────────┴──────────────────────────────────────────┴────────┘

1.3 执行计划阅读方法

阅读顺序：从右到左，从上到下

                    ┌──────────────┐
                    │ SELECT       │ ← 最后执行
                    │ Cost: 0%     │
                    └──────┬───────┘
                           │
                    ┌──────┴───────┐
                    │ Nested Loops │ ← JOIN操作
                    │ Cost: 5%     │
                    └──┬────────┬──┘
                       │        │
              ┌────────┴──┐  ┌──┴──────────┐
              │Index Seek │  │Key Lookup   │ ← 先执行这两个
              │Cost: 30%  │  │Cost: 65%    │ ← 这个代价最高！
              └───────────┘  └─────────────┘

关注点：
1. 线条粗细 → 数据流量大小
2. Cost 百分比 → 哪步最贵
3. 黄色感叹号 → 有警告
4. Actual vs Estimated 行数差异 → 统计信息是否准确

二、索引类型深入

2.1 聚集索引（Clustered Index）

聚集索引 = 数据本身的物理排序方式
每张表只能有一个聚集索引（因为数据只能有一种物理排列方式）

类比：字典按拼音排序 → 拼音就是聚集索引
     你翻到 "H" 部分，就能找到所有 H 开头的字

B+Tree 结构：
                    ┌──────┐
                    │ Root │
                    │ M    │
                    └──┬───┘
                   /       \
          ┌──────┐         ┌──────┐
          │ D  H │         │ P  T │
          └──┬───┘         └──┬───┘
         /   |   \        /   |   \
     ┌───┐┌───┐┌───┐ ┌───┐┌───┐┌───┐
     │A-C││D-G││H-L│ │M-O││P-S││T-Z│  ← 叶子节点=实际数据行
     └───┘└───┘└───┘ └───┘└───┘└───┘     （数据按索引键排序存储）

默认：主键 = 聚集索引
但可以分开设计（高级技巧）
-- 创建聚集索引
CREATE CLUSTERED INDEX IX_Orders_OrderDate ON Orders(OrderDate);

-- 注意：如果已有主键聚集索引，需要先删除
-- 或者创建主键时指定NONCLUSTERED
ALTER TABLE Orders ADD CONSTRAINT PK_Orders PRIMARY KEY NONCLUSTERED (Id);
CREATE CLUSTERED INDEX IX_Orders_OrderDate ON Orders(OrderDate);

2.2 非聚集索引（Nonclustered Index）

非聚集索引 = 单独的索引结构，叶子节点存储索引键 + 指向数据的指针

类比：书后面的索引页
     "认证 → 第106页"
     你需要先查索引页，再翻到对应页码

B+Tree 结构：
                    ┌──────┐
                    │ Root │
                    └──┬───┘
                   /       \
          ┌──────┐         ┌──────┐
          │      │         │      │
          └──┬───┘         └──┬───┘
         /       \        /       \
     ┌──────┐┌──────┐┌──────┐┌──────┐
     │Key=A ││Key=D ││Key=M ││Key=T │  ← 叶子节点
     │Ptr→行││Ptr→行││Ptr→行││Ptr→行│     存索引键 + 行指针
     └──────┘└──────┘└──────┘└──────┘

⚠️ 如果查询需要索引中没有的列 → Key Lookup（回表）
-- 创建非聚集索引
CREATE NONCLUSTERED INDEX IX_Orders_CustomerId 
ON Orders(CustomerId);

-- 复合索引（多列）
CREATE NONCLUSTERED INDEX IX_Orders_Status_Date 
ON Orders(Status, OrderDate DESC);
-- 最左前缀原则：Status必须在前面才能用到这个索引

2.3 覆盖索引（Covering Index）—— 性能利器

覆盖索引：索引包含了查询需要的所有列，不需要回表（Key Lookup）

回表的代价：
  1. 用非聚集索引找到行指针
  2. 再用行指针去聚集索引/堆中找完整行
  → 两次 IO 操作！
  → 如果返回很多行，Key Lookup 成本极高

覆盖索引消除回表：
  索引中直接包含需要的列 → 一次 IO 搞定
-- 场景：经常执行这个查询
SELECT OrderId, OrderDate, TotalAmount
FROM Orders
WHERE CustomerId = 123 AND Status = 'Completed';

-- 创建覆盖索引
CREATE NONCLUSTERED INDEX IX_Orders_Covering
ON Orders(CustomerId, Status)         -- 索引键（用于查找）
INCLUDE (OrderId, OrderDate, TotalAmount);  -- 包含列（覆盖查询）

-- 执行计划：Index Seek（不再有 Key Lookup）✅
何时用 INCLUDE vs 放入索引键？

索引键（INDEX ON 后面的列）：
  → 用于 WHERE、JOIN ON、ORDER BY 的列
  → 参与 B+Tree 排序
  → 影响索引大小和维护成本

INCLUDE 列：
  → 只用于 SELECT 的列
  → 不参与排序，只存在叶子节点
  → 存储开销小，维护成本低

原则：
  查找条件的列 → 放索引键
  只读取不查找的列 → 放 INCLUDE

2.4 筛选索引（Filtered Index）

-- 只为特定数据建索引（减少索引大小）
CREATE NONCLUSTERED INDEX IX_Orders_Active
ON Orders(OrderDate, CustomerId)
INCLUDE (TotalAmount)
WHERE Status = 'Active';  -- 只索引活跃订单

-- 适用场景：
-- 1. 状态字段（只索引"未处理"的）
-- 2. 非NULL值（WHERE ColumnName IS NOT NULL）
-- 3. 最近的数据（WHERE Year >= 2024）

三、索引失效场景 —— 必须牢记

3.1 隐式类型转换

-- ❌ 索引失效！VarcharColumn 是 varchar，但参数是 nvarchar
SELECT * FROM Users WHERE PhoneNumber = N'13800138000';
-- SQL Server 会把整列转成 nvarchar 来比较 → Index Scan

-- ✅ 类型匹配
SELECT * FROM Users WHERE PhoneNumber = '13800138000';
-- → Index Seek ✅

3.2 函数包裹列

-- ❌ 索引失效
SELECT * FROM Orders WHERE YEAR(OrderDate) = 2024;
SELECT * FROM Orders WHERE CONVERT(VARCHAR, OrderDate, 112) = '20240101';
SELECT * FROM Users WHERE UPPER(Name) = 'ZHANGSAN';

-- ✅ 改写为范围查询
SELECT * FROM Orders 
WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01';

-- ✅ SQL Server 2017+ 可以用计算列+索引
ALTER TABLE Users ADD UpperName AS UPPER(Name) PERSISTED;
CREATE INDEX IX_Users_UpperName ON Users(UpperName);

3.3 LIKE 以通配符开头

-- ❌ 索引失效
SELECT * FROM Products WHERE Name LIKE '%手机%';

-- ✅ 前缀匹配可以用索引
SELECT * FROM Products WHERE Name LIKE '华为%';

-- 解决方案：全文索引
CREATE FULLTEXT INDEX ON Products(Name) KEY INDEX PK_Products;
SELECT * FROM Products WHERE CONTAINS(Name, '手机');

3.4 OR 条件

-- ❌ 可能导致索引失效
SELECT * FROM Orders WHERE CustomerId = 1 OR OrderDate = '2024-01-01';

-- ✅ 用 UNION ALL 改写
SELECT * FROM Orders WHERE CustomerId = 1
UNION ALL
SELECT * FROM Orders WHERE OrderDate = '2024-01-01' AND CustomerId <> 1;

3.5 不等于操作

-- ❌ 索引效率低
SELECT * FROM Orders WHERE Status <> 'Completed';
-- 如果 90% 的订单都是 Completed，这个查询返回 10% 的数据
-- SQL Server 可能选择 Index Scan 而不是 Seek

-- ✅ 正面思维：查你要的，而不是排除不要的
SELECT * FROM Orders WHERE Status IN ('Pending', 'Processing', 'Shipped');

索引失效速查表

场景                           原因                    解决方案
──────────────────────────────────────────────────────────────────
函数包裹列                     无法利用B+Tree          改写为范围查询
LIKE '%xxx'                   无法定位起点            全文索引
隐式类型转换                   整列转换                类型匹配
OR 条件                       两个条件无法同时Seek    UNION ALL
NOT IN / <>                   需要扫描排除            IN/正向条件
IS NULL (某些情况)             索引不存NULL(默认)      筛选索引
列参与计算 (col+1=10)          等同于函数              移到右边(col=9)
小表/低选择性                   优化器认为Scan更快      正常，不用管
参数嗅探                       首次缓存的计划不适合     OPTION(RECOMPILE)

四、索引设计原则

4.1 复合索引的列顺序

最左前缀原则：
  索引 (A, B, C) 可以满足：
    ✅ WHERE A = ?
    ✅ WHERE A = ? AND B = ?
    ✅ WHERE A = ? AND B = ? AND C = ?
    ❌ WHERE B = ?            （跳过了A）
    ❌ WHERE B = ? AND C = ?  （跳过了A）
    ⚠️ WHERE A = ? AND C = ?  （只能用A，C无法Seek）

列顺序设计原则：
  1. 等值条件的列放前面
  2. 范围条件的列放后面（范围后面的列无法Seek）
  3. 选择性高的列放前面
  
  例：WHERE Status = 'Active' AND OrderDate > '2024-01-01'
  → INDEX (Status, OrderDate)  ✅ Status等值+OrderDate范围
  → INDEX (OrderDate, Status)  ❌ OrderDate范围后Status无法Seek

4.2 索引数量平衡

过多索引的代价：
  1. INSERT/UPDATE/DELETE 变慢（每个索引都要维护）
  2. 占用磁盘空间
  3. 统计信息维护开销

经验法则：
  OLTP 系统（增删改多）：每张表 5-10 个索引
  OLAP 系统（查询多）：可以更多
  
  监控未使用的索引：
  SELECT * FROM sys.dm_db_index_usage_stats
  WHERE user_seeks = 0 AND user_scans = 0 AND user_lookups = 0;

4.3 查找缺失索引

-- SQL Server 自动记录"建议的索引"
SELECT 
    d.statement AS TableName,
    d.equality_columns,          -- 等值条件列
    d.inequality_columns,        -- 范围条件列
    d.included_columns,          -- 建议 INCLUDE 的列
    s.avg_user_impact,           -- 预估性能提升百分比
    s.user_seeks,                -- 如果有索引，预计会用多少次
    s.last_user_seek
FROM sys.dm_db_missing_index_details d
INNER JOIN sys.dm_db_missing_index_groups g ON d.index_handle = g.index_handle
INNER JOIN sys.dm_db_missing_index_group_stats s ON g.index_group_handle = s.group_handle
WHERE d.database_id = DB_ID()
ORDER BY s.avg_user_impact * s.user_seeks DESC;

五、统计信息 —— 执行计划的"参谋"

统计信息 = SQL Server 对数据分布的"估计"
优化器根据统计信息选择执行计划

如果统计信息过期 → 优化器做出错误选择 → 性能差

查看统计信息：
  DBCC SHOW_STATISTICS ('Orders', 'IX_Orders_OrderDate');

更新统计信息：
  UPDATE STATISTICS Orders;                    -- 更新表的所有统计信息
  UPDATE STATISTICS Orders IX_Orders_OrderDate; -- 更新特定索引

自动更新：
  SQL Server 默认在数据变化达到阈值时自动更新
  但大表可能不及时 → 手动更新或启用 Trace Flag 2371

六、参数嗅探（Parameter Sniffing）

参数嗅探 = SQL Server 首次编译存储过程时，
          用第一次传入的参数值来生成执行计划，
          后续调用都复用这个计划。

问题场景：
  第一次调用：查Status='Pending'（1%的数据）→ 生成 Index Seek 计划
  第二次调用：查Status='Completed'（90%的数据）→ 复用 Index Seek 计划
  → 对90%的数据做 Index Seek + Key Lookup = 灾难性慢！

解决方案：
-- 方案1：OPTION(RECOMPILE)（最简单）
SELECT * FROM Orders WHERE Status = @Status
OPTION (RECOMPILE);
-- 每次都重新编译，100%准确但有编译开销

-- 方案2：OPTIMIZE FOR UNKNOWN
SELECT * FROM Orders WHERE Status = @Status
OPTION (OPTIMIZE FOR (@Status UNKNOWN));
-- 使用平均分布来估计，折中方案

-- 方案3：OPTIMIZE FOR 特定值
SELECT * FROM Orders WHERE Status = @Status
OPTION (OPTIMIZE FOR (@Status = 'Pending'));
-- 总是按 Pending 的分布来优化

-- 方案4：查询存储（Query Store）
-- SQL Server 2016+ 推荐方案
ALTER DATABASE YourDB SET QUERY_STORE = ON;
-- 自动检测计划回归，强制使用好的计划

七、大数据分页优化

-- ❌ 传统分页（深页慢）
SELECT * FROM Orders
ORDER BY OrderDate DESC
OFFSET 1000000 ROWS FETCH NEXT 20 ROWS ONLY;
-- 需要扫描 1000020 行，只返回 20 行

-- ✅ 键集分页（Keyset Pagination）
SELECT TOP 20 * FROM Orders
WHERE OrderDate < @LastOrderDate  -- 上一页最后一条的日期
   OR (OrderDate = @LastOrderDate AND Id < @LastId)  -- 同日期用ID排
ORDER BY OrderDate DESC, Id DESC;
-- 只扫描 20 行 ✅

-- ✅ 分页覆盖索引
CREATE INDEX IX_Orders_Paging 
ON Orders(OrderDate DESC, Id DESC)
INCLUDE (CustomerId, TotalAmount, Status);

八、实战：慢查询优化案例

案例：订单报表查询优化

-- 原始查询（慢，5秒）
SELECT 
    o.OrderId, o.OrderDate, o.TotalAmount,
    c.CustomerName, c.City,
    COUNT(oi.OrderItemId) AS ItemCount,
    SUM(oi.Quantity) AS TotalQuantity
FROM Orders o
INNER JOIN Customers c ON o.CustomerId = c.CustomerId
INNER JOIN OrderItems oi ON o.OrderId = oi.OrderId
WHERE o.OrderDate >= '2024-01-01' 
  AND o.OrderDate < '2024-04-01'
  AND o.Status = 'Completed'
GROUP BY o.OrderId, o.OrderDate, o.TotalAmount, c.CustomerName, c.City
ORDER BY o.OrderDate DESC;
优化步骤：

Step 1: 看执行计划
  → Clustered Index Scan on Orders（全表扫描）
  → Key Lookup on OrderItems
  → Sort（ORDER BY）

Step 2: 分析问题
  1. Orders 表没有合适的索引 → 全表扫描
  2. OrderItems 的非聚集索引不覆盖 → Key Lookup
  3. 最后还需要 Sort

Step 3: 创建索引
-- 为 Orders 创建覆盖索引
CREATE NONCLUSTERED INDEX IX_Orders_Report
ON Orders(Status, OrderDate DESC)
INCLUDE (OrderId, CustomerId, TotalAmount)
WHERE Status = 'Completed';  -- 筛选索引

-- 为 OrderItems 创建覆盖索引
CREATE NONCLUSTERED INDEX IX_OrderItems_ByOrder
ON OrderItems(OrderId)
INCLUDE (OrderItemId, Quantity);

-- 优化后：0.2秒 ✅
-- Index Seek on Orders（筛选索引）
-- Index Seek on OrderItems（覆盖索引）
-- 无 Key Lookup，无额外 Sort

九、索引维护

-- 查看索引碎片
SELECT 
    OBJECT_NAME(ips.object_id) AS TableName,
    i.name AS IndexName,
    ips.avg_fragmentation_in_percent AS Fragmentation,
    ips.page_count AS Pages
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') ips
INNER JOIN sys.indexes i ON ips.object_id = i.object_id AND ips.index_id = i.index_id
WHERE ips.avg_fragmentation_in_percent > 10
ORDER BY ips.avg_fragmentation_in_percent DESC;
碎片处理策略：

碎片率 < 10%:  不处理
碎片率 10-30%: REORGANIZE（在线操作，轻量级）
碎片率 > 30%:  REBUILD（更彻底，但会锁表）

ALTER INDEX IX_Orders_OrderDate ON Orders REORGANIZE;
ALTER INDEX IX_Orders_OrderDate ON Orders REBUILD;
ALTER INDEX ALL ON Orders REBUILD;  -- 重建所有索引

十、DMV 性能监控常用查询

-- TOP 10 最耗资源的查询
SELECT TOP 10
    qs.total_elapsed_time / qs.execution_count AS AvgTime,
    qs.execution_count,
    qs.total_logical_reads / qs.execution_count AS AvgReads,
    SUBSTRING(qt.text, qs.statement_start_offset/2 + 1,
        (CASE WHEN qs.statement_end_offset = -1 
              THEN LEN(CONVERT(NVARCHAR(MAX), qt.text)) * 2
              ELSE qs.statement_end_offset 
         END - qs.statement_start_offset) / 2 + 1) AS QueryText
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) qt
ORDER BY qs.total_elapsed_time / qs.execution_count DESC;
