索引失效的 20 种场景

索引失效的 20 种场景

明明建了索引，查询还是全表扫描。这种情况十有八九是你写的 SQL 把索引搞失效了。下面列出最常见的 20 种情况，都是实际踩过的坑。

1. 对索引列用函数

-- ❌ 索引失效
SELECT * FROM Orders WHERE YEAR(OrderDate) = 2024;
SELECT * FROM Employees WHERE LEFT(Name, 1) = '张';
SELECT * FROM Logs WHERE CONVERT(DATE, CreateTime) = '2024-01-01';

-- ✅ 改成范围查询
SELECT * FROM Orders WHERE OrderDate >= '2024-01-01' AND OrderDate < '2025-01-01';
SELECT * FROM Employees WHERE Name LIKE '张%';
SELECT * FROM Logs WHERE CreateTime >= '2024-01-01' AND CreateTime < '2024-01-02';

索引里存的是 OrderDate 的原始值，你用 YEAR() 包了一层，SQL Server 没法直接在 B+ 树里查找。

2. 对索引列做运算

-- ❌
SELECT * FROM Products WHERE Price * 1.1 > 100;
SELECT * FROM Orders WHERE OrderId + 1 = 1001;

-- ✅ 把运算移到另一边
SELECT * FROM Products WHERE Price > 100 / 1.1;
SELECT * FROM Orders WHERE OrderId = 1000;

3. 隐式类型转换

这个最隐蔽，执行计划里会出现 CONVERT_IMPLICIT 警告。

-- 表定义：Phone VARCHAR(20), 有索引
-- ❌ 传入参数是 NVARCHAR
SELECT * FROM Customers WHERE Phone = N'13800138000';
-- SQL Server 会把 VARCHAR 列转成 NVARCHAR 来比较 → 索引失效

-- ✅ 类型一致
SELECT * FROM Customers WHERE Phone = '13800138000';  -- 不带 N 前缀

规则：SQL Server 按数据类型优先级做隐式转换，VARCHAR → NVARCHAR，INT → BIGINT。如果是索引列被转换（而不是参数被转换），索引就废了。

常见的坑：

  • C# 默认传 string 到 Dapper/ADO.NET 时是 NVARCHAR，但表字段是 VARCHAR
  • 解决：参数显式指定 DbType = DbType.AnsiString

4. LIKE 左侧通配符

-- ❌ 走不了索引
SELECT * FROM Products WHERE ProductName LIKE '%手机%';

-- ✅ 前缀匹配可以走索引
SELECT * FROM Products WHERE ProductName LIKE '华为%';

%xxx% 这种模糊查询在 B+ 树里没法定位起点，只能全扫。如果业务必须支持中间匹配，考虑全文索引。

5. OR 条件

-- ❌ 如果 Status 没有索引，整个查询放弃走 CustomerId 的索引
SELECT * FROM Orders WHERE CustomerId = 100 OR Status = 1;

-- ✅ 改成 UNION ALL
SELECT * FROM Orders WHERE CustomerId = 100
UNION ALL
SELECT * FROM Orders WHERE Status = 1 AND CustomerId <> 100;

OR 的两边如果都有索引，SQL Server 可能用 Index Union 合并。但只要有一边没索引，整个 WHERE 就走全扫。

6. NOT IN / NOT LIKE / <>

-- ⚠️ 否定条件通常不走索引 Seek，而是走 Scan
SELECT * FROM Orders WHERE Status <> 3;
SELECT * FROM Orders WHERE CustomerId NOT IN (1, 2, 3);

因为"不等于"要排除一些值，B+ 树很难直接定位（要跳过某些区间），通常退化为扫描。

7. IS NULL / IS NOT NULL

-- ⚠️ 看情况
SELECT * FROM Orders WHERE Remark IS NULL;

SQL Server 的索引可以包含 NULL 值。IS NULL 能不能走索引取决于 NULL 值的比例——如果大部分行 Remark 都是 NULL，走索引反而不如扫描快，优化器可能选择不走。

8. 联合索引没遵循最左前缀

-- 索引: (DeptId, CreateDate)

-- ✅ 走索引
SELECT * FROM Employees WHERE DeptId = 1;
SELECT * FROM Employees WHERE DeptId = 1 AND CreateDate > '2024-01-01';

-- ❌ 跳过了 DeptId，索引用不上
SELECT * FROM Employees WHERE CreateDate > '2024-01-01';

9. SELECT * 导致回表成本过高

-- 索引: (CustomerId) INCLUDE (OrderDate)

-- ✅ 覆盖索引，不回表
SELECT OrderDate FROM Orders WHERE CustomerId = 100;

-- ❌ SELECT * 需要回表取其他列。如果结果集太大，优化器干脆放弃索引走全扫
SELECT * FROM Orders WHERE CustomerId = 100;

这不是"索引失效"，而是优化器算了一下：走索引 + 回表 10000 次，还不如直接全表扫一遍。所以别动不动 SELECT *。

10. 数据量太少

-- 表里就 100 行，建了索引也不走
SELECT * FROM Settings WHERE Category = 'System';

SQL Server 很聪明——100 行全放在几个数据页里，全扫也就读 2-3 个页。走索引还要先读索引页再读数据页，反而更多 IO。优化器会直接选全扫。

11. 统计信息过期

优化器根据统计信息估算行数来决定用不用索引。统计信息过期 → 估算不准 → 可能做出错误的决定。

-- 手动更新统计信息
UPDATE STATISTICS Orders WITH FULLSCAN;

12. 参数嗅探（后面有专门的文章）

第一次执行存储过程时传了个"特殊值"（比如查 VIP 客户只有 10 条），SQL Server 缓存了这个执行计划。后面传普通值（几万条）还是用这个计划，索引选择就错了。

13. IN 列表太长

-- ❌ 上千个值
SELECT * FROM Products WHERE ProductId IN (1, 2, 3, ..., 5000);

IN 列表太长会增加编译时间，也可能让优化器放弃索引。建议超过几百个值就改用临时表 JOIN。

14. 低选择性索引

-- Status 只有 0, 1, 2 三个值。索引选择性太低
CREATE INDEX IX_Orders_Status ON Orders(Status);

SELECT * FROM Orders WHERE Status = 1;
-- 如果 Status=1 的行有 40 万条（总共 100 万），走索引要 Key Lookup 40 万次
-- 优化器会选全表扫描

15. 更新导致索引碎片

索引碎片率超过 30% 后，扫描效率下降。虽然 Seek 不太受影响，但 Scan 会明显变慢。定期重建。

16. 表变量没有统计信息

DECLARE @t TABLE (Id INT PRIMARY KEY, Name NVARCHAR(50));
-- 表变量的统计信息永远估算 1 行
-- 即使你插了 10 万行，优化器还是以为只有 1 行 → 选错计划

数据量大的时候用临时表 #temp，不要用表变量 @t。

17. 跨列比较

-- ❌ 两个列比较，没法用单列索引
SELECT * FROM Orders WHERE CreateDate > UpdateDate;

这种条件没法用 B+ 树定位。可以加一个计算列然后建索引：

ALTER TABLE Orders ADD DateDiff AS DATEDIFF(DAY, UpdateDate, CreateDate) PERSISTED;
CREATE INDEX IX ON Orders(DateDiff);

18. 字符集/排序规则不一致

-- 两个表的 Name 列排序规则不一样（一个 Latin1，一个 Chinese_PRC）
-- JOIN 的时候需要运行时转换 → 索引不匹配
SELECT * FROM TableA a JOIN TableB b ON a.Name = b.Name COLLATE Chinese_PRC_CI_AS;

19. 链接服务器查询

-- 链接服务器的表没法直接用本地索引
SELECT * FROM LinkedServer.DB.dbo.Orders WHERE CustomerId = 100;
-- 可能会把整张远程表拉过来

20. 查询提示 NOLOCK 不影响索引，但 INDEX 提示可能帮倒忙

-- 强制用某个索引，结果这个索引不是最优的
SELECT * FROM Orders WITH (INDEX(IX_Orders_Status)) WHERE ...;

除非你确定优化器选错了，否则别用 INDEX 提示。

快速排查清单

遇到查询不走索引，按这个顺序排查：

  1. WHERE 条件的列上有没有索引？
  2. 有没有对索引列用函数/运算？
  3. 有没有隐式类型转换？（看执行计划的 Warning）
  4. 联合索引有没有跳过最左列？
  5. 统计信息是不是过期了？
  6. SELECT * 导致回表成本太高？
  7. 数据选择性低（查出来的行占全表比例太大）？

终极手段：SET STATISTICS IO ON 对比加索引前后的 logical reads。
