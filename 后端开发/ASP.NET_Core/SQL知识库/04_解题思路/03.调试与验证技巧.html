调试与验证技巧

SQL 写完了怎么确认结果是对的？出了 Bug 怎么快速定位？这篇整理日常调试 SQL 的实用技巧。

最基本的：PRINT + SELECT 中间结果

-- 调试存储过程时，在关键位置输出中间值
PRINT '---- Step 1: 过滤后行数 ----';
SELECT COUNT(*) AS Step1Count FROM #temp;

PRINT '---- Step 2: JOIN 后 ----';
SELECT TOP 10 * FROM #result;

SET STATISTICS IO / TIME

SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT * FROM Orders WHERE CustomerId = 100;

-- 输出：
-- Table 'Orders'. Scan count 1, logical reads 45
-- CPU time = 0 ms, elapsed time = 2 ms

logical reads 是核心指标——代表读了多少个 8KB 的数据页。优化前后对比这个数字。

执行计划调试

预估执行计划 vs 实际执行计划

-- 预估计划（不实际执行，快速查看计划）
-- SSMS: Ctrl+L

-- 实际执行计划（执行后看真实数据）
-- SSMS: Ctrl+M 然后 F5

实际执行计划里能看到真实行数 vs 预估行数，偏差大说明统计信息有问题。

执行计划里的关键警告

警告含义怎么办
Missing Index缺索引右键查看建议
Implicit Conversion隐式类型转换修改参数类型或列类型
No Join Predicate缺 JOIN 条件（笛卡尔积）检查 ON 条件
Sort Warning排序溢出到磁盘加内存或优化查询减少排序
Residual Predicate额外的过滤条件可能索引不够好

快速验证查询结果

对比行数

-- 改查询前后总行数应该一致（如果逻辑没变）
SELECT COUNT(*) FROM (原来的查询) t1;
SELECT COUNT(*) FROM (优化后的查询) t2;

EXCEPT 找差异

-- 两个查询的结果应该完全一样
-- 用 EXCEPT 找出不同的行
(SELECT * FROM (原查询) t1)
EXCEPT
(SELECT * FROM (新查询) t2);
-- 返回 0 行 = 完全一致

-- 反向也要检查
(SELECT * FROM (新查询) t2)
EXCEPT
(SELECT * FROM (原查询) t1);

用已知数据验证

-- 知道客户 100 有 5 笔订单，手动验证
SELECT COUNT(*) FROM Orders WHERE CustomerId = 100;
-- 应该 = 5

SELECT * FROM (你的复杂查询) t WHERE CustomerId = 100;
-- 结果合理吗？

存储过程调试

用 PRINT 跟踪流程

CREATE PROCEDURE usp_Process
AS
BEGIN
    PRINT 'Step 1: 开始处理';
    -- ...
    PRINT 'Step 1 完成，影响行数: ' + CAST(@@ROWCOUNT AS VARCHAR);

    PRINT 'Step 2: 开始计算';
    -- ...
    PRINT 'Step 2 完成';
END;

TRY-CATCH 捕获详细错误

BEGIN CATCH
    SELECT
        ERROR_NUMBER() AS ErrNum,
        ERROR_SEVERITY() AS Severity,
        ERROR_STATE() AS State,
        ERROR_PROCEDURE() AS ErrProc,
        ERROR_LINE() AS ErrLine,
        ERROR_MESSAGE() AS ErrMsg;
END CATCH;

ERROR_LINE() 告诉你具体哪一行出错了。

常见调试场景

结果比预期多

大概率是 JOIN 导致的行膨胀——一对多关系 JOIN 会产生多行。

-- 检查：是不是一对多
SELECT CustomerId, COUNT(*) FROM Orders GROUP BY CustomerId HAVING COUNT(*) > 1;
-- 如果有多行，JOIN 后就会膨胀

结果比预期少

可能是 INNER JOIN 过滤掉了不匹配的行，或者 WHERE 条件过滤了 NULL。

-- 改成 LEFT JOIN 看看是不是多了
-- 检查 NULL 值
SELECT COUNT(*) FROM 表 WHERE 某列 IS NULL;

聚合结果不对

先不聚合，看明细数据是不是对的：

-- 不要直接 SUM，先看明细
SELECT * FROM Orders WHERE CustomerId = 100;
-- 手动加一下，和 SUM 的结果对不对

时区/日期问题

-- 看一下实际存的时间值
SELECT OrderDate, CONVERT(VARCHAR(23), OrderDate, 121) 
FROM Orders WHERE OrderId = 12345;

性能调试工具箱

-- 1. 查当前正在跑的查询
SELECT session_id, status, command, wait_type, 
    total_elapsed_time/1000 AS sec
FROM sys.dm_exec_requests WHERE session_id > 50;

-- 2. 查 TempDB 使用情况
SELECT SUM(user_object_reserved_page_count) * 8 / 1024 AS UserObj_MB,
    SUM(internal_object_reserved_page_count) * 8 / 1024 AS InternalObj_MB
FROM sys.dm_db_file_space_usage;

-- 3. 查缓存命中率
SELECT
    (a.cntr_value * 1.0 / b.cntr_value) * 100.0 AS BufferCacheHitRatio
FROM sys.dm_os_performance_counters a
JOIN sys.dm_os_performance_counters b ON a.object_name = b.object_name
WHERE a.counter_name = 'Buffer cache hit ratio'
    AND b.counter_name = 'Buffer cache hit ratio base';

调试习惯清单

  1. 改 SQL 前先保存原版
  2. 每改一步跑一次对比
  3. 用 SET STATISTICS IO ON 量化改进
  4. 复杂查询先 SELECT TOP 10 看采样
  5. 多用 COUNT(*) 和 EXCEPT 验证一致性
  6. 遇到诡异结果先检查 NULL 和数据类型
