依赖注入与作用域

依赖注入与作用域

中间件在 ASP.NET Core 中以单例形式存在，这一特性使得依赖注入的使用变得微妙。如果忽略了中间件的生命周期，就会遇到 Captive Dependency、Scoped 服务泄漏等难以排查的问题。本章将系统讲解中间件中正确使用依赖注入的方式与常见陷阱。

一、中间件的生命周期

1.1 中间件是单例

ASP.NET Core 在应用启动时构建请求管道，每个中间件实例只会被创建一次，随后在每次请求中复用同一个实例：

public class MyMiddleware
{
    private readonly RequestDelegate _next;

    public MyMiddleware(RequestDelegate next)
    {
        _next = next;
        // 这个构造函数只会在应用启动时调用一次
        Console.WriteLine($"MyMiddleware 创建于: {DateTime.UtcNow}");
    }

    public async Task InvokeAsync(HttpContext context)
    {
        // 每个请求都会进入这里
        Console.WriteLine($"请求处理: {context.Request.Path}");
        await _next(context);
    }
}

输出结果：

MyMiddleware 创建于: 2026/1/15 08:30:00   ← 只出现一次
请求处理: /api/users                        ← 每次请求
请求处理: /api/products                     ← 每次请求
请求处理: /api/orders                        ← 每次请求

1.2 构造函数注入的服务也是单例捕获

因为中间件只构造一次，所以在构造函数中注入的服务也被"冻结"为同一实例：

public class RequestLoggingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestLoggingMiddleware> _logger;

    public RequestLoggingMiddleware(
        RequestDelegate next,
        ILogger<RequestLoggingMiddleware> logger)  // 单例捕获
    {
        _next = next;
        _logger = logger;  // _logger 在所有请求中指向同一个实例
    }

    public async Task InvokeAsync(HttpContext context)
    {
        _logger.LogInformation("请求: {Path}", context.Request.Path);
        await _next(context);
    }
}

ILogger<T> 本身是单例安全的，所以没有问题。但如果注入的是 Scoped 服务，就会产生严重问题。

1.3 常见陷阱：在构造函数中注入 Scoped 服务

// ❌ 危险！Scoped 服务被单例中间件捕获
public class BadMiddleware
{
    private readonly RequestDelegate _next;
    private readonly AppDbContext _dbContext;  // Scoped!

    public BadMiddleware(RequestDelegate next, AppDbContext dbContext)
    {
        _next = next;
        _dbContext = dbContext;  // 同一个 DbContext 实例被所有请求共享!
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var user = await _dbContext.Users.FindAsync(1);
        // 多个请求并发访问同一个 DbContext → 异常或数据污染
        await _next(context);
    }
}

运行时可能出现的错误：

InvalidOperationException: A second operation started on this context before a
previous operation completed. This is usually caused by different threads using
the same instance of DbContext.

根因：AppDbContext 注册为 Scoped，本应每个请求一个实例，却被单例中间件长期持有，变成了"事实上的单例"——而且是不安全的单例。

二、正确的依赖注入方式

2.1 方式一：InvokeAsync 参数注入（推荐）

在 InvokeAsync 方法签名中直接声明需要的服务，框架会从当前请求的作用域中解析：

public class RequestLoggingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestLoggingMiddleware> _logger;

    // 构造函数只注入单例服务
    public RequestLoggingMiddleware(
        RequestDelegate next,
        ILogger<RequestLoggingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    // Scoped 服务通过方法参数注入
    public async Task InvokeAsync(
        HttpContext context,
        AppDbContext dbContext,          // 从请求作用域解析
        IUserService userService)        // 从请求作用域解析
    {
        var user = await userService.GetCurrentUserAsync(context);
        var log = new RequestLog
        {
            Path = context.Request.Path,
            UserId = user.Id,
            Timestamp = DateTime.UtcNow
        };
        dbContext.RequestLogs.Add(log);
        await dbContext.SaveChangesAsync();

        _logger.LogInformation("请求已记录: {Path}", context.Request.Path);
        await _next(context);
    }
}

工作原理：

  1. 应用启动时，框架创建中间件实例（单例）
  2. 每次请求到达时，框架调用 InvokeAsync
  3. 框架检测到方法参数中的服务类型，从当前请求的 ServiceProvider 中解析
  4. 解析得到的服务与请求生命周期一致（Scoped 服务就是每个请求新实例）

2.2 方式二：IMiddleware + AddTransient（工厂激活）

实现 IMiddleware 接口并将中间件注册为 Transient，让每个请求都创建新的中间件实例：

public class FactoryActivatedMiddleware : IMiddleware
{
    private readonly AppDbContext _dbContext;
    private readonly IUserService _userService;

    // 构造函数中可以安全注入 Scoped 服务
    public FactoryActivatedMiddleware(
        AppDbContext dbContext,
        IUserService userService)
    {
        _dbContext = dbContext;
        _userService = userService;
    }

    public async Task InvokeAsync(HttpContext context, RequestDelegate next)
    {
        var user = await _userService.GetCurrentUserAsync(context);
        var log = new RequestLog
        {
            Path = context.Request.Path,
            UserId = user.Id,
            Timestamp = DateTime.UtcNow
        };
        _dbContext.RequestLogs.Add(log);
        await _dbContext.SaveChangesAsync();

        await next(context);
    }
}

// 注册
builder.Services.AddTransient<FactoryActivatedMiddleware>();

// 使用
app.UseMiddleware<FactoryActivatedMiddleware>();

2.3 两种方式对比

特性InvokeAsync 参数注入IMiddleware 工厂模式

三、IMiddleware 工厂模式详解

3.1 实现步骤

第一步：实现 IMiddleware 接口

public class TenantResolutionMiddleware : IMiddleware
{
    private readonly ITenantService _tenantService;
    private readonly ILogger<TenantResolutionMiddleware> _logger;

    public TenantResolutionMiddleware(
        ITenantService tenantService,
        ILogger<TenantResolutionMiddleware> logger)
    {
        _tenantService = tenantService;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context, RequestDelegate next)
    {
        var host = context.Request.Host.Host;
        var tenant = await _tenantService.ResolveTenantAsync(host);

        if (tenant == null)
        {
            _logger.LogWarning("未识别的租户: {Host}", host);
            context.Response.StatusCode = 404;
            return;
        }

        // 将租户信息存入 HttpContext.Items
        context.Items["Tenant"] = tenant;
        context.Items["TenantId"] = tenant.Id;

        await next(context);
    }
}

第二步：注册到 DI 容器

// 必须注册为 Transient 或 Scoped
builder.Services.AddScoped<ITenantService, TenantService>();
builder.Services.AddTransient<TenantResolutionMiddleware>();
// 或者
// builder.Services.AddScoped<TenantResolutionMiddleware>();

第三步：添加到管道

app.UseMiddleware<TenantResolutionMiddleware>();

3.2 UseMiddleware 的自动注册

调用 UseMiddleware<T>() 时，框架会检测 T 是否实现了 IMiddleware：

// 框架内部的简化逻辑
public static IApplicationBuilder UseMiddleware<TMiddleware>(
    this IApplicationBuilder app, params object[] args)
{
    if (typeof(IMiddleware).IsAssignableFrom(typeof(TMiddleware)))
    {
        // 工厂激活模式
        // 检查 TMiddleware 是否已注册到 DI
        // 如果未注册，抛出 InvalidOperationException
        return app.Use(next =>
        {
            return async context =>
            {
                // 从请求的 ServiceProvider 解析中间件实例
                var middleware = context.RequestServices
                    .GetRequiredService<TMiddleware>();
                await middleware.InvokeAsync(context, next);
            };
        });
    }
    else
    {
        // 约定式激活模式（单例）
        // 使用反射创建实例，调用 InvokeAsync
    }
}

如果忘记注册 IMiddleware 实现类，会得到如下错误：

InvalidOperationException: No service for type
'TenantResolutionMiddleware' has been registered.

3.3 工厂激活的内部工作流程

请求到达
  │
  ▼
UseMiddleware 委托执行
  │
  ▼
从 HttpContext.RequestServices 解析 TMiddleware
  │  ← 每次请求都会创建新实例（Transient）
  │  ← Scoped 服务也在此处正确解析
  ▼
调用 middleware.InvokeAsync(context, next)
  │
  ▼
请求结束，中间件实例可被 GC 回收

四、Scoped 服务的正确使用

4.1 DbContext 在中间件中的使用

DbContext 是最典型的 Scoped 服务。在中间件中使用时，必须通过参数注入或工厂模式：

// ✅ 方式1：参数注入
public class AuditMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<AuditMiddleware> _logger;

    public AuditMiddleware(RequestDelegate next, ILogger<AuditMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context, AppDbContext dbContext)
    {
        var audit = new AuditLog
        {
            Path = context.Request.Path,
            Method = context.Request.Method,
            Timestamp = DateTime.UtcNow,
            UserAgent = context.Request.Headers.UserAgent.ToString()
        };

        // 请求前记录
        dbContext.AuditLogs.Add(audit);
        await dbContext.SaveChangesAsync();

        var sw = Stopwatch.StartNew();
        await _next(context);
        sw.Stop();

        // 请求后更新
        audit.StatusCode = context.Response.StatusCode;
        audit.DurationMs = sw.ElapsedMilliseconds;
        await dbContext.SaveChangesAsync();
    }
}

4.2 在中间件中创建 Scope（IServiceScopeFactory）

当需要在中间件的私有方法中使用 Scoped 服务，或者需要更细粒度的控制时，可以使用 IServiceScopeFactory：

public class BackgroundTaskMiddleware
{
    private readonly RequestDelegate _next;
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<BackgroundTaskMiddleware> _logger;

    public BackgroundTaskMiddleware(
        RequestDelegate next,
        IServiceScopeFactory scopeFactory,
        ILogger<BackgroundTaskMiddleware> logger)
    {
        _next = next;
        _scopeFactory = scopeFactory;  // IServiceScopeFactory 是单例，安全
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        // 先让管道继续执行
        await _next(context);

        // 响应完成后，在后台任务中使用 Scoped 服务
        if (context.Response.StatusCode == 200)
        {
            _ = Task.Run(async () =>
            {
                try
                {
                    // 创建新的 Scope
                    using var scope = _scopeFactory.CreateScope();
                    var dbContext = scope.ServiceProvider
                        .GetRequiredService<AppDbContext>();
                    var emailService = scope.ServiceProvider
                        .GetRequiredService<IEmailService>();

                    // 执行后台任务
                    var userId = context.Items["UserId"]?.ToString();
                    if (userId != null)
                    {
                        var user = await dbContext.Users.FindAsync(int.Parse(userId));
                        if (user != null)
                        {
                            await emailService.SendActivityNotificationAsync(user.Email);
                        }
                    }
                }
                catch (Exception ex)
                {
                    _logger.LogError(ex, "后台任务执行失败");
                }
            });
        }
    }
}

4.3 手动创建 Scope 的完整代码示例

以下是一个审计中间件，使用 IServiceScopeFactory 实现请求前后的数据库操作：

public class ComprehensiveAuditMiddleware
{
    private readonly RequestDelegate _next;
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<ComprehensiveAuditMiddleware> _logger;

    public ComprehensiveAuditMiddleware(
        RequestDelegate next,
        IServiceScopeFactory scopeFactory,
        ILogger<ComprehensiveAuditMiddleware> logger)
    {
        _next = next;
        _scopeFactory = scopeFactory;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        // 不用参数注入也能获取 Scoped 服务
        using var scope = _scopeFactory.CreateScope();
        var dbContext = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        var identityService = scope.ServiceProvider
            .GetRequiredService<IIdentityService>();

        var audit = new AuditLog
        {
            Path = context.Request.Path,
            Method = context.Request.Method,
            Timestamp = DateTime.UtcNow,
            UserId = identityService.GetCurrentUserId()
        };

        dbContext.AuditLogs.Add(audit);
        await dbContext.SaveChangesAsync();

        var sw = Stopwatch.StartNew();
        try
        {
            await _next(context);
        }
        catch (Exception ex)
        {
            audit.Exception = ex.Message;
            throw;
        }
        finally
        {
            sw.Stop();
            audit.StatusCode = context.Response.StatusCode;
            audit.DurationMs = sw.ElapsedMilliseconds;
            await dbContext.SaveChangesAsync();
        }
    }
}

[!WARNING]
使用 IServiceScopeFactory 创建的 Scope 必须妥善释放。推荐使用 using var 声明，确保在方法结束时调用 Dispose()。

五、常见 DI 陷阱

5.1 陷阱一：构造函数注入 Scoped → Captive Dependency

// ❌ 错误示例
public class CaptiveDependencyMiddleware
{
    private readonly RequestDelegate _next;
    private readonly IUserService _userService;  // IUserService 是 Scoped!

    public CaptiveDependencyMiddleware(
        RequestDelegate next,
        IUserService userService)  // 被单例捕获!
    {
        _next = next;
        _userService = userService;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        // _userService 永远是第一次请求时创建的那个实例
        // 后续请求使用的都是同一个"过期"实例
        var user = await _userService.GetUserAsync(1);
        await _next(context);
    }
}

现象：

  • 第一次请求正常
  • 后续请求可能使用到已释放的资源
  • 可能抛出 ObjectDisposedException
  • 数据可能不一致（永远读到旧数据）

开发环境下的检测：

builder.Services.Configure<ServiceProviderOptions>(options =>
{
    options.ValidateScopes = true;  // 开发环境下默认开启
});

// 或者在 CreateBuilder 时
var builder = WebApplication.CreateBuilder(args);
builder.Host.UseDefaultServiceProvider(options =>
{
    options.ValidateScopes = true;
});

开启后，在构造函数中注入 Scoped 服务会直接抛出异常：

InvalidOperationException: Cannot consume scoped service 'IUserService'
from singleton 'CaptiveDependencyMiddleware'.

5.2 陷阱二：在单例中间件中缓存 Scoped 服务的引用

// ❌ 错误示例
public class CachingMiddleware
{
    private readonly RequestDelegate _next;
    private IUser? _cachedUser;  // 从 Scoped 服务获取的引用被缓存!

    public CachingMiddleware(RequestDelegate next)
    {
        _next = next;
    }

    public async Task InvokeAsync(HttpContext context, IUserService userService)
    {
        if (_cachedUser == null)
        {
            // 第一次请求：从 Scoped 服务获取并缓存
            _cachedUser = await userService.GetCurrentUserAsync(context);
        }

        // 后续请求使用缓存的引用 → 可能已释放
        context.Items["User"] = _cachedUser;
        await _next(context);
    }
}

问题分析：

  • _cachedUser 是从某个请求的 Scoped 服务获取的
  • 该请求结束后，Scoped 服务及其关联的资源（如 DbContext）被释放
  • _cachedUser 可能持有对已释放资源的引用
  • 后续请求使用 _cachedUser 可能导致 ObjectDisposedException

正确做法：只缓存不可变数据

// ✅ 正确示例
public class CachingMiddleware
{
    private readonly RequestDelegate _next;
    private string? _cachedUserName;  // 缓存的是值类型或不可变数据

    public CachingMiddleware(RequestDelegate next)
    {
        _next = next;
    }

    public async Task InvokeAsync(HttpContext context, IUserService userService)
    {
        // 每个请求都从当前 Scoped 服务获取
        var user = await userService.GetCurrentUserAsync(context);
        context.Items["User"] = user;

        // 可以缓存独立于 Scoped 服务的不可变数据
        if (_cachedUserName == null)
        {
            _cachedUserName = user.Name;  // 值类型拷贝，不持有引用
        }

        await _next(context);
    }
}

5.3 陷阱三：使用 IServiceProvider 直接 GetService

// ❌ 错误示例
public class ServiceProviderMiddleware
{
    private readonly RequestDelegate _next;
    private readonly IServiceProvider _serviceProvider;

    public ServiceProviderMiddleware(
        RequestDelegate next,
        IServiceProvider serviceProvider)
    {
        _next = next;
        _serviceProvider = serviceProvider;  // 根容器，不是请求作用域!
    }

    public async Task InvokeAsync(HttpContext context)
    {
        // 从根容器解析 → Scoped 服务变成单例行为!
        var dbContext = _serviceProvider.GetService<AppDbContext>();
        var user = await dbContext.Users.FindAsync(1);

        await _next(context);
    }
}

问题：IServiceProvider 注入的是根容器，从中解析 Scoped 服务会导致：

  • Scoped 服务不会随请求结束而释放
  • 可能造成内存泄漏
  • 多个请求可能共享同一个 Scoped 实例

正确做法：

// ✅ 方式1：使用 HttpContext.RequestServices
public async Task InvokeAsync(HttpContext context)
{
    var dbContext = context.RequestServices.GetService<AppDbContext>();
    await _next(context);
}

// ✅ 方式2：使用参数注入
public async Task InvokeAsync(HttpContext context, AppDbContext dbContext)
{
    await _next(context);
}

// ✅ 方式3：使用 IServiceScopeFactory 创建 Scope
public async Task InvokeAsync(HttpContext context)
{
    using var scope = _scopeFactory.CreateScope();
    var dbContext = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    await _next(context);
}

5.4 解决方案汇总表

陷阱现象根因解决方案
构造函数注入 ScopedObjectDisposedException 或数据不一致单例持有 Scoped 引用，请求结束后 Scoped 被释放使用 InvokeAsync 参数注入
缓存 Scoped 引用随机 ObjectDisposedException缓存的对象可能引用已释放的资源只缓存值类型或不可变数据
根容器 GetService内存泄漏、并发异常根容器解析的 Scoped 不会随请求释放使用 context.RequestServices 或 IServiceScopeFactory
构造函数注入 TransientTransient 变成单例行为单例中间件持有 Transient 引用，GC 无法回收使用 InvokeAsync 参数注入
多个参数注入方法签名过长业务逻辑过度耦合在中间件中考虑使用 IMiddleware 工厂模式

小结

  • 中间件是单例，构造函数中只能安全注入 Singleton 服务
  • Scoped 服务必须通过 InvokeAsync 参数注入、IMiddleware 工厂模式或 IServiceScopeFactory 获取
  • 开发环境下务必开启 ValidateScopes = true 以尽早发现 Captive Dependency
  • 绝对不要在中间件中缓存从 Scoped 服务获取的可变对象引用
  • 不要使用根 IServiceProvider 解析 Scoped 服务，应使用 HttpContext.RequestServices
