性能调优

性能调优

数据库性能问题 80% 来自糟糕的 SQL 和缺失的索引，20% 来自参数配置不当。系统化的调优方法论比"盲猜参数"更有效：先定位瓶颈，再对症下药。

参考资料：小林coding - MySQL 调优 | MySQL 官方文档 - Optimization

1. 慢查询日志

慢查询日志是 MySQL 调优的起点，记录执行时间超过阈值的 SQL。

1.1 开启与配置

-- 开启慢查询日志
SET GLOBAL slow_query_log = ON;

-- 设置阈值（秒）
SET GLOBAL long_query_time = 1;  -- 超过1秒的查询记录

-- 慢查询日志文件路径
SHOW VARIABLES LIKE 'slow_query_log_file';

-- 是否记录未使用索引的查询
SET GLOBAL log_queries_not_using_indexes = ON;

-- 每分钟记录未使用索引查询的最大数量（防止日志暴增）
SET GLOBAL log_throttle_queries_not_using_indexes = 60;

-- 记录管理语句（ALTER、ANALYZE 等）
SET GLOBAL log_slow_admin_statements = ON;

1.2 分析慢查询

# 使用 mysqldumpslow 快速分析
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log
# -s t: 按查询时间排序
# -t 10: 显示前10条

# 使用 pt-query-digest（更强大）
pt-query-digest /var/log/mysql/slow.log > slow_report.txt
# pt-query-digest 输出示例
# Rank Query ID           Response time  Calls
# ==== ================== ============== =====
#    1 0x5A1C6B2D3E4F...  120.4567 62.1%  3421
#    2 0x7B8C9D0E1F2A...   45.1234 23.3%  1523
#    3 0x9C0D1E2F3A4B...   15.6789  8.1%   892

慢查询日志大小控制

  • 生产环境 long_query_time 建议 0.1~1 秒
  • 日志文件定期轮转，避免磁盘占满
  • 使用 pt-query-digest --review 将分析结果持久化到数据库

2. Performance Schema

Performance Schema 是 MySQL 内置的性能监控引擎，低开销地收集服务器运行数据。

2.1 核心监控表

表监控内容
events_waits_current当前等待事件
events_waits_history最近等待事件
events_statements_current当前执行的语句
events_statements_history最近执行的语句
file_summary_by_instance文件 IO 统计
memory_summary_by_thread线程内存使用

2.2 常用查询

-- 查看当前正在等待的事件
SELECT
    EVENT_NAME,
    TIMER_WAIT / 1000000000 AS '等待时间(ms)',
    SOURCE
FROM performance_schema.events_waits_current
WHERE TIMER_WAIT > 1000000000;  -- 超过1秒

-- 查看 IO 瓶颈
SELECT
    FILE_NAME,
    COUNT_READ,
    COUNT_WRITE,
    SUM_TIMER_READ / 1000000000 AS '读耗时(ms)',
    SUM_TIMER_WRITE / 1000000000 AS '写耗时(ms)'
FROM performance_schema.file_summary_by_instance
ORDER BY SUM_TIMER_READ + SUM_TIMER_WRITE DESC
LIMIT 10;

-- 查看最耗时的 SQL
SELECT
    DIGEST_TEXT AS 'SQL',
    COUNT_STAR AS '执行次数',
    SUM_TIMER_WAIT / 1000000000 AS '总耗时(ms)',
    AVG_TIMER_WAIT / 1000000000 AS '平均耗时(ms)',
    MAX_TIMER_WAIT / 1000000000 AS '最大耗时(ms)'
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;

2.3 内存监控

-- 查看各线程的内存使用
SELECT
    THREAD_ID,
    EVENT_NAME,
    CURRENT_NUMBER_OF_BYTES_USED / 1024 / 1024 AS '当前使用(MB)',
    HIGH_NUMBER_OF_BYTES_USED / 1024 / 1024 AS '峰值(MB)'
FROM performance_schema.memory_summary_by_thread_by_event_name
WHERE CURRENT_NUMBER_OF_BYTES_USED > 1048576  -- > 1MB
ORDER BY CURRENT_NUMBER_OF_BYTES_USED DESC
LIMIT 10;

3. Sys Schema

Sys Schema 是 Performance Schema 的友好视图，开箱即用：

-- Top 10 最耗时的 SQL
SELECT * FROM sys.statements_with_runtimes_in_95th_percentile;

-- 未使用索引的查询
SELECT * FROM sys.statements_with_full_table_scans;

-- 冗余索引
SELECT * FROM sys.schema_unused_indexes;

-- 冗余索引（更详细）
SELECT * FROM sys.schema_redundant_indexes;

-- 表 IO 统计
SELECT
    table_schema,
    table_name,
    rows_fetched,
    rows_inserted,
    rows_updated,
    rows_deleted,
    io_read / 1024 / 1024 AS '读MB',
    io_write / 1024 / 1024 AS '写MB'
FROM sys.schema_table_statistics_with_buffer
ORDER BY io_read + io_write DESC
LIMIT 10;

-- 会话连接统计
SELECT * FROM sys.session
WHERE command = 'Query'
ORDER BY timer_wait DESC;

定期清理冗余索引

  • 冗余索引浪费存储，增加写入开销
  • 优化器可能选错索引
  • 用 sys.schema_unused_indexes 识别，确认安全后删除

4. 核心参数优化

4.1 关键参数一览

参数推荐值说明
innodb_buffer_pool_size物理内存 60%~80%最重要的参数
innodb_buffer_pool_instances4~8（>1GB时）减少锁竞争
innodb_io_capacitySSD:10000~20000, HDD:200~400刷脏速度
innodb_io_capacity_maxinnodb_io_capacity × 2刷脏上限
innodb_flush_log_at_trx_commit1（主库）事务持久性
sync_binlog1（主库）Binlog 持久性
max_connections500~2000最大连接数
innodb_lock_wait_timeout10~30锁等待超时（秒）
innodb_deadlock_detectON死锁检测
innodb_print_all_deadlocksON记录死锁日志
innodb_sort_buffer_size2M~8M排序缓冲区
join_buffer_size4M~16MJOIN 缓冲区
sort_buffer_size2M~8MORDER BY 缓冲区
innodb_thread_concurrency0（默认，不限）并发线程数

4.2 Buffer Pool 配置

-- 32GB 内存服务器的推荐配置
SET GLOBAL innodb_buffer_pool_size = 25769803776;     -- 24GB
SET GLOBAL innodb_buffer_pool_instances = 8;           -- 8个实例
SET GLOBAL innodb_old_blocks_pct = 37;                 -- Old区3/8
SET GLOBAL innodb_old_blocks_time = 1000;              -- 1秒晋升窗口

4.3 IO 相关配置

-- SSD 磁盘推荐
SET GLOBAL innodb_io_capacity = 10000;
SET GLOBAL innodb_io_capacity_max = 20000;
SET GLOBAL innodb_flush_method = O_DIRECT;  -- 绕过OS缓存

-- HDD 磁盘推荐
SET GLOBAL innodb_io_capacity = 200;
SET GLOBAL innodb_io_capacity_max = 400;

innodb_flush_method = O_DIRECT

  • O_DIRECT 绕过操作系统文件缓存，避免 Doublewrite
  • 适用于 Buffer Pool 较大（>4GB）的场景
  • 如果 Buffer Pool 较小，O_DIRECT 反而降低性能

5. 连接池调优

-- 查看当前连接数
SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Max_used_connections';

-- 查看连接配置
SHOW VARIABLES LIKE 'max_connections';
SHOW VARIABLES LIKE 'wait_timeout';
SHOW VARIABLES LIKE 'interactive_timeout';

-- 推荐配置
SET GLOBAL max_connections = 1000;
SET GLOBAL wait_timeout = 28800;        -- 8小时
SET GLOBAL interactive_timeout = 28800;
SET GLOBAL max_connect_errors = 100;    -- 防止暴力破解
# HikariCP 连接池配置（Java 应用推荐）
spring:
  datasource:
    hikari:
      maximum-pool-size: 20          # 连接池大小 = CPU核心数 × 2 + 磁盘数
      minimum-idle: 5                # 最小空闲连接
      connection-timeout: 30000      # 获取连接超时30秒
      idle-timeout: 600000           # 空闲连接超时10分钟
      max-lifetime: 1800000          # 连接最大存活30分钟
      connection-test-query: SELECT 1

连接数不是越多越好

  • 每个连接消耗约 2~5MB 内存（sort_buffer + join_buffer 等）
  • 1000 个连接可能消耗 2~5GB 内存
  • 连接池大小建议：CPU 核心数 × 2 + 有效磁盘数

6. Query Cache（已移除）

MySQL 8.0 正式移除了 Query Cache，原因：

问题说明
全局锁查询缓存使用全局互斥锁，高并发下成为瓶颈
失效频繁任何表的数据变化都导致该表所有缓存失效
命中率低生产环境命中率通常 < 20%
内存浪费缓存占用 Buffer Pool 空间

8.0 不再有 Query Cache

  • 5.7 可设置 query_cache_type = OFF 禁用
  • 8.0 已完全移除相关参数
  • 替代方案：应用层缓存（Redis/Memcached）

# 分析慢查询日志
pt-query-digest /var/log/mysql/slow.log

# 分析 Processlist

pt-index-usage slow.log --host=127.0.0.1 --drop-all

8. 真实案例：从 10s 到 50ms

场景

一个订单系统的查询，按日期范围 + 状态筛选，执行时间 10 秒：

-- 原始查询
SELECT * FROM orders
WHERE created_at BETWEEN '2025-01-01' AND '2025-06-30'
    AND status IN ('PAID', 'SHIPPED')
    AND region = 'EAST'
ORDER BY created_at DESC
LIMIT 20;

优化过程

-- Step 1: EXPLAIN 分析
EXPLAIN SELECT * FROM orders
WHERE created_at BETWEEN '2025-01-01' AND '2025-06-30'
    AND status IN ('PAID', 'SHIPPED')
    AND region = 'EAST'
ORDER BY created_at DESC
LIMIT 20;

-- 结果：type=ALL，rows=5000000，Using where; Using filesort
-- 问题：全表扫描 + 文件排序
-- Step 2: 添加复合索引
ALTER TABLE orders
ADD INDEX idx_region_status_created (region, status, created_at);

-- Step 3: 再次 EXPLAIN
-- 结果：type=range，rows=50000，Using index condition
-- 执行时间：2秒（有改善但不够）
-- Step 4: 覆盖索引优化（避免回表）
SELECT id, order_no, created_at, status, amount
FROM orders
WHERE region = 'EAST'
    AND status IN ('PAID', 'SHIPPED')
    AND created_at BETWEEN '2025-01-01' AND '2025-06-30'
ORDER BY created_at DESC
LIMIT 20;

-- 结果：Using index，执行时间 50ms
-- Step 5: 进一步优化 - 调整 Buffer Pool
-- 确保热数据在内存中
SET GLOBAL innodb_buffer_pool_size = 17179869184;  -- 16GB

-- Step 6: 验证 Buffer Pool 命中率
SELECT
    (1 - (SELECT VARIABLE_VALUE FROM performance_schema.global_status
           WHERE VARIABLE_NAME = 'Innodb_buffer_pool_reads')
         / (SELECT VARIABLE_VALUE FROM performance_schema.global_status
            WHERE VARIABLE_NAME = 'Innodb_buffer_pool_read_requests')
    ) * 100 AS '命中率%';
-- 结果：99.97%

优化总结

阶段优化手段耗时提升倍数
原始无索引10s-
加索引复合索引2s5x
覆盖索引避免回表50ms200x
Buffer Pool内存命中率30ms333x

9. 使用 dbeaver 辅助调优

在 dbeaver 中可以方便地进行性能调优：

  1. 执行计划分析：SQL 编辑器中点击 Explain Plan 查看执行计划
  2. 慢查询定位：使用 SQL 编辑器执行 sys.statements_with_runtimes_in_95th_percentile
  3. 索引管理：右键表 → Edit Table → Indexes 选项卡
  4. Schema 对比：使用 dbeaver 的 Compare 功能对比不同环境的表结构
-- 在 dbeaver 中一键查看数据库健康状态
SELECT
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status
     WHERE VARIABLE_NAME = 'Innodb_buffer_pool_read_requests') AS '逻辑读',
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status
     WHERE VARIABLE_NAME = 'Innodb_buffer_pool_reads') AS '磁盘读',
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status
     WHERE VARIABLE_NAME = 'Threads_connected') AS '当前连接',
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status
     WHERE VARIABLE_NAME = 'Slow_queries') AS '慢查询数',
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status
     WHERE VARIABLE_NAME = 'Innodb_row_lock_waits') AS '锁等待次数';

10. 面试技巧

面试高频问题

  1. 如何定位慢查询？

    • 开启慢查询日志，用 pt-query-digest 分析
    • 结合 Performance Schema 和 Sys Schema 定位瓶颈

  2. innodb_buffer_pool_size 设多大？

    • 物理内存的 60%~80%
    • 专用数据库服务器可以设到 80%
    • 留足内存给 OS 和其他进程

  3. 如何优化一条慢 SQL？

    • EXPLAIN 分析执行计划
    • 添加合适的索引（复合索引、覆盖索引）
    • 避免回表、文件排序、临时表
    • 优化 SQL 写法（避免 SELECT *、子查询改 JOIN）

  4. sync_binlog 和 innodb_flush_log_at_trx_commit 怎么设？

    • 主库必须双1（sync_binlog=1, flush_log_at_trx_commit=1）
    • 从库可以放松（sync_binlog=0, flush_log_at_trx_commit=2）

  5. Query Cache 为什么被移除？

    • 全局互斥锁成为并发瓶颈
    • 缓存命中率低、失效频繁
    • 8.0 已完全移除，用应用层缓存替代
