自治智能体的权限模式

自治智能体的权限模式

权限阶梯——从"每个动作都审"到"全部批准"的分级自治——是 harness 治理"自治智能体不问就能做什么"的方式。本课的实例 Claude Code 暴露了六种模式:"plan" 每个动作前都要问;"default"(UI 里标为 "Manual")只对危险动作发问;"acceptEdits" 自动批准文件写入,但 shell 执行仍要确认;"bypassPermissions" 全部批准。Auto 模式——auto 权限模式——把逐动作审批换成一个独立的分类器模型:它在每个动作运行前审查,拦下任何超出请求范围的升级动作。动作预算通过 max_turns 和 max_budget_usd 强制。auto 的可用性取决于套餐、组织开关、模型和提供方——而且 Anthropic 明说:单靠分类器是不够的。

类型: 学习
编程语言: Python(标准库,两阶段分类器模拟器)
前置要求: 第 15 阶段 · 01(长程智能体),第 15 阶段 · 09(编程智能体版图)
预计耗时: 约 45 分钟

问题

你机器上的自治编程智能体,是一个独立的安全品类。攻击面是智能体能够到的一切——文件系统、网络、凭证、剪贴板、任何浏览器标签页、任何开着的终端。Bruce Schneier 等人公开警告过:操作电脑的智能体不是聊天机器人的"功能更新",而是一种新型工具,带着新型的风险画像。

Claude Code 的权限系统是 Anthropic 的答案。不是一个"自治/不自治"的开关,而是六种模式组成的能力阶梯:plan → default → acceptEdits → … → bypassPermissions。每种模式都是"速度"与"逐动作审查"之间不同的取舍。Auto 模式(2026 年 3 月)再加一个独立的分类器模型,把审批从用户的关键路径上挪开:它在每个动作运行前审查,拦下任何超出请求的升级动作。

工程问题:这套系统抓得住什么、漏掉什么,以及一个给定任务到底该用哪一档?

概念

六种权限模式

模式行为何时用
plan智能体提计划;用户批准整个计划;每个动作执行前都审不熟悉的任务;临近生产的代码;第一次在该仓库上用智能体
defaultUI 里标为 "Manual"。智能体执行动作;任何"危险"动作(shell 执行、破坏性操作、网络调用)都要问用户大多数交互式编程会话
acceptEdits文件写入自动批准;shell 执行和网络调用仍要问跨多文件的重构
auto独立的分类器模型在每个动作运行前审查;拦下超出请求的升级受限工作区里的长程无人值守运行
dontAsk从不发问;未被权限规则预批准的动作一律拒绝一次性沙箱、CI 任务、研究脚本
bypassPermissions全部批准文档写明:"只在你舍得扔掉的一次性容器里用"

(名称与公开的 Claude Code 文档一致;UI 把 default 标为 "Manual"。)

一页纸讲清 Auto 模式

Auto 模式(2026 年 3 月 24 日发布)是第一个把逐动作审批委托给模型的权限模式。结构:

  1. 独立的分类器模型。 审查每个提议的动作,依据声明的任务和会话当前状态做判断,拦下任何超出请求范围的升级。被拦的动作回落给用户。
  2. 门控可用。 auto 是否提供,取决于套餐、组织开关、模型和提供方。

预算控制与分类器并列:

  • max_turns ——会话总迭代数。
  • max_budget_usd ——中止会话的美元上限。
  • 按工具的动作数上限(如 WebFetch 调用不超过 N 次)。

系统抓得住什么

  • 注入到工具输入里的直白 prompt 注入——只要注入的指令对应已知危险动作的形状。
  • 重复的工具循环——分类器看得到动作 N+1 与动作 N 几乎一样,连着五次。
  • 在纯文件编辑会话里明显越界的 shell 命令。

系统可能漏掉什么

  • 微妙的 prompt 注入:只调制行为,不产出任何单个会被标记的动作。间接 prompt 注入不是一个能完全打补丁的漏洞(OpenAI 防备部门负责人,2025,谈浏览器智能体——见第 11 课)。
  • 语义级坏行为。 每个单独动作看起来都安全,组合起来的轨迹却有害。分类器审的是动作,它不重新推导用户的意图。
  • 通过合法通道外泄。 把数据写进你自己的文件,再 git push 到公开仓库——一连串都被允许的动作,问题出在组合上。

研究预览的定位

Anthropic 以研究预览的形式发布 Auto 模式。文档写得很清楚:分类器是一层,不是解决方案。用户应当把 Auto 模式与预算、白名单、隔离工作区和轨迹审计(第 12–16 课)组合使用。预览的定位也反映了第 1 课讲过的"评估-部署差距"——离线评估合格的分类器,在用户上下文含糊的真实会话里,行为可能不同。

这架梯子在你的工作流里怎么摆

  • 不熟悉的任务:从 plan 开始。读计划比回滚一次坏运行便宜。
  • 熟悉的重构:acceptEdits 省一大堆确认点击。
  • 无人值守的后台运行:只用 auto,且必须在你量过爆炸半径的工作区里(无凭证、无生产挂载、没有你主动开通的出站)。
  • 一次性容器:dontAsk / bypassPermissions 可以接受,当且仅当容器及其凭证都是可丢弃的。

投入使用

code/main.py 把动作审查分类器模拟成两阶段流水线——这是教学简化;真实的 auto 模式背后是一个独立的分类器模型,没有公开的两阶段契约。第 1 阶段是对提议动作的廉价关键词规则;第 2 阶段是更慢的多规则审查器。驱动程序喂进一段短的合成轨迹(安全动作、一次 prompt 注入尝试、一个重复循环),展示分类器在哪里抓住、在哪里漏掉。

交付

outputs/skill-permission-mode-picker.md 把一段任务描述匹配到合适的权限模式、预算上限和所需的隔离级别。

练习

  1. 运行 code/main.py。哪一类合成动作第 1 阶段从不标记、第 2 阶段总能抓住?哪一类两个都抓不住?

  2. 扩展第 1 阶段的规则集,抓住一种已知坏形状(如 curl $ATTACKER/exfil)。在良性动作样本上测误报率。

  3. 读 Anthropic 的"How the agent loop works"文档。列出 default 模式下智能体默认触及的所有外部状态。无人值守跑 auto 之前,哪些需要单独设闸?

  4. 设计一个 24 小时无人值守运行的预算:max_turns、max_budget_usd、按工具的上限、白名单。为每个数字给出理由。

  5. 描述一条轨迹:每个单独动作都被分类器批准,组合行为却是失配的。(第 14 课讲急停开关和金丝雀 token 如何应对这类情况。)
