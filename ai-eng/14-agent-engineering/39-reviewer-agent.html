评审智能体:建造与打分分离

评审智能体:建造与打分分离

写代码的智能体不能给自己的代码打分。评审者是第二条循环:不同的系统提示、不同的目标、对建造者产出的一切只读。建造者与评审者之间的这道缝,正是可靠性大半居住的地方。

类型: 动手构建
编程语言: Python(标准库)
前置要求: 第 14 阶段 · 38(验证闸门)
预计耗时: 约 55 分钟

学习目标

  • 说明为什么同一个智能体无法可靠地评审自己的工作
  • 构建一个消费建造者工件、产出结构化评审报告的评审智能体循环
  • 编写按具体维度打分、而非凭感觉的评审评分细则
  • 把评审者接进工作台,让人工评审从一份真实工件开始

问题

你让智能体修一个 bug。它改了四个文件,跑了测试,报告完成。验证闸门(第 14 阶段 · 38)确认验收命令跑过、范围守住,裁决 passed: true。你合并了。两天后,你发现那个修复解决的是这个 bug 的错的一半。

验收是必要的,不是充分的。评审者问的是验收问不了的问题:它解决的是对的问题吗?它扩大了范围却没有标记吗?它记下的假设里,有没有本该被质疑的?它留下的工作台状态,下个会话接得起来吗?

概念

评审评分细则

五个维度,每个 0 到 2 分。

维度问题
问题契合改动解决的是陈述的那个任务,而不是隔壁的任务?
范围纪律编辑被限制在契约内,还是契约被刻意扩大了?
假设所有隐藏的假设都写在了可评审的地方吗?
验证质量验收命令真的证明了目标,还是只证明了一个更弱的版本?
交接就绪下个会话能从当前状态干净地接手吗?

总分 10 分。低于 7 是软失败;低于 5 是硬失败。

评审者是一个独立的角色,不一定是独立的模型

你可以用和建造者同一个模型跑评审者。纪律在角色分离:不同的系统提示、不同的输入、对 diff 没有写权限。姿态的改变,就是信号的改变。

评审者不能改 diff

评审者读 diff、状态、反馈、裁决,写报告。它不打补丁。报告说"修这个",就由建造者的下一轮去修,评审者回去继续评审。角色一混,这道缝就白留了。

评审细则 vs 验证闸门

闸门(第 14 阶段 · 38)检查确定性事实:验收跑了吗、规则过了吗、范围守住了吗。评审者做的是定性判断:这是不是对的工作、文档写了吗、交接能用吗。两者缺一不可。

wb-builder-marker

动手构建

code/main.py 实现:

  • 一个 ReviewerInputs dataclass,打包评审者要读的工件。
  • 一个按维度打分的评分器,每维度一个函数。本课中是确定性的教学桩;真实实现会调 LLM。
  • 一个 review_report.json 写入器:五个分数、总分和裁决(pass、soft_fail、hard_fail)。
  • 两个演示案例:一个干净的改动,一个"测试对了、问题错了"的改动。

运行:

python3 code/main.py

输出:写入磁盘的两份评审报告,以及一张打印到控制台的维度分数表。

野外的生产模式

收据:Cloudflare 2026 年 4 月的 AI Code Review 系统,30 天内在 5,169 个仓库的 48,095 个合并请求上跑了 131,246 次评审,中位评审耗时 3 分 39 秒。最多七个专家评审者(安全、性能、代码质量、文档、发布管理、合规、Engineering Codex)在一个 Review Coordinator 下并行——由它去重发现、判定严重级。顶级模型专给协调员用,专家们跑在更便宜的层级上。

四个模式让它在规模下成立。

专家池,不是一个大评审者。 一个带五维细则的评审者,对单人仓库够用;一旦代码库有了安全关键、性能关键和文档表面,就拆成提示更小的专家。协调员负责去重,专家们永远不跑完整细则。模型层级分离随之而来:便宜的专家,昂贵的协调员。

偏见缓解是设计要求,不是优化项。 LLM 裁判呈现四种可靠偏见(Adnan Masood,2026 年 4 月):位置偏置(GPT-4 在 (A,B) 与 (B,A) 两种顺序上约 40% 不一致)、啰嗦偏置(对更长输出约 15% 的分数膨胀)、自我偏爱(裁判偏好同族模型的输出)、权威偏置(裁判高估引用知名作者的内容)。缓解:两种顺序都评,只计一致胜出;用明确奖励简洁的 1–4 分制;跨模型家族轮换裁判;打分前剥掉作者名。

校准集,不是凭感觉。 一份 10–20 个历史任务、带已知正确裁决的集合。每次改提示词都在上面跑评审者:与历史记录的吻合度低于 80%,评审者上线前就得修订细则。这是每个团队最终都会重新发现的东西——不如一开始就有。

与闸门的 Hybrid Norm 分工。 验证闸门(第 14 阶段 · 38)管确定性检查(验收跑了吗、测试过了吗、范围守住了吗);评审者管语义检查(这是对的工作吗、假设写了吗、交接能用吗)。Anthropic 2026 年的指南对这个分工说得很明确:别让评审者重做闸门已经证明过的事。

投入使用

生产模式:

  • Claude Code 子智能体。 建造者关闭任务后,评审子智能体运行,把细则分数作为评论发到 PR 上。
  • OpenAI Agents SDK handoffs。 任务完成时建造者 handoff 给评审者;评审者可以带着发现清单 handoff 回来,或上交人类。
  • 双模型搭配。 建造者跑更快更便宜的模型;评审者跑更强的模型、上下文更小,专注判断。

评审者就是当人类无法亲自做完所有评审时,工作台长出来的第二双眼睛。

交付

outputs/skill-reviewer-agent.md 生成项目专属的评审细则、一个接好建造者工件的评审智能体桩,以及与验证闸门的集成——让人工评审从一份成文报告开始,而不是一张白纸。

练习

  1. 加一个你产品领域专属的第六维度。论证为什么它不能被现有五个吸收。
  2. 用两份不同的系统提示(简洁、啰嗦)跑评审者。哪份产出的报告人类更可能读?
  3. 给每个维度加 confidence 字段:最低维度的置信度低于 0.6 时,拒绝交付报告。
  4. 构建校准集:10 个带已知正确裁决的历史任务收尾。在上面跑评审者,它在哪些地方与历史记录不一致?
  5. 加"请求更多证据"的通道:评审者可以在打分前要求建造者补跑某个特定测试。正确的退让机制是什么,才不会形成循环?

关键术语

术语别人的说法实际含义
评审细则(Reviewer rubric)"检查单"五维 0–2 打分,每维度配一个成文问题
软失败(Soft fail)"需要返工"总分低于 7;建造者拿到要处理的发现
硬失败(Hard fail)"拒收"总分低于 5 或任一维度为 0;停下并报给人类
角色分离(Role separation)"换个提示词"同一模型可以身兼两角;纪律在输入与姿态
置信度下限(Confidence floor)"低信号报告别发"细则不确定时,拒绝发出裁决
