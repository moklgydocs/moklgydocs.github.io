监督者 / 编排者-工人模式

监督者 / 编排者-工人模式

一个领头智能体规划并委派,专业工人在各自独立的上下文中并行执行并回报。这就是 Anthropic Research 系统背后的模式(Claude Opus 4 当领头,Sonnet 4 当子智能体),内部研究评测上比单智能体 Opus 4 高出 +90.2%。Anthropic 的工程博文报告:BrowseComp 上 80% 的方差仅由 token 用量解释——多智能体之所以赢,主要因为每个子智能体都拿到一个崭新的上下文窗口。本课从原语出发构建监督者模式,并讲讲 2026 年生产部署的工程经验。

类型: 学习 + 动手构建
编程语言: Python(标准库,threading)
前置要求: 第 16 阶段 · 04(原语模型)
预计耗时: 约 75 分钟

问题

研究是单智能体系统注定失败的原型任务。你问"2023 到 2026 年间,多智能体系统发生了什么变化?"一个单智能体按序读五篇论文,半个上下文被论文原文塞满,然后还得把它们放在一起推理。读到第五篇时,它已经忘了第一篇。它没法并行。

监督者模式解决了这个问题:一个领头智能体规划搜索,把每个子问题委派给一个工人,然后综合。每个工人为一个狭窄问题拿到自己独立的 20 万 token 窗口。领头永远看不到论文原文——只看到工人的摘要。

Anthropic 的生产 Research 系统报告:内部研究评测比单个 Opus 4 高 +90.2%。同一篇博文指出,BrowseComp 方差的 80% 仅由 token 用量解释。每个子智能体一个崭新上下文,是主要机制。

概念

模式

                 │   Lead       │  plans, decomposes,
                 │  (Opus 4)    │  synthesizes

                    │    │   │

      └─────────┘  └─────────┘  └─────────┘
         fresh       fresh        fresh
         context     context      context

领头从不读原始材料。工人在领头综合之前,互看不到对方的工作。每个箭头都是一次移交,载荷是一份狭窄的工件。

为什么它赢

三个机制:

  1. 每个子智能体一个崭新上下文。 探索"FIPA-ACL 传承"的工人,不背着领头规划花掉的 4 万 token。它为一个问题独享 20 万 token 窗口。
  2. 经提示词的专门化。 领头的提示词是"分解与综合",不是"做研究"。每个工人的提示词是狭窄的:"找出 X 里发生了什么变化"。聚焦的提示词产出聚焦的输出。
  3. 并行。 工人并发运行。墙钟时间约为 max(worker_times) + plan + synthesis,而不是 sum(worker_times)。

工程经验(Anthropic 2025)

Anthropic 的博文列了几条到 2026 年仍然适用的生产经验:

  • 按查询复杂度伸缩投入。 简单查询:一个智能体,3-10 次工具调用。复杂查询:10+ 个智能体。这个判断要由领头做,不是调用方。
  • 先宽后窄。 先分解成宽泛的子问题;如果答案值得深挖,再为每个子问题派生更多工人。
  • 彩虹部署(Rainbow deployments)。 智能体是长时运行且有状态的。传统的蓝绿部署行不通。Anthropic 用彩虹式:新版本逐步推出,旧版本逐步排空。
  • token 用量主导。 多智能体的 token 消耗约为单智能体的 15 倍。只有任务价值配得上成本时才跑。

图原生的转向

LangGraph 最初交付了一个 langgraph-supervisor 库,带高层 create_supervisor 辅助函数。2025 年,LangChain 把推荐改为直接用工具调用实现监督者模式,因为工具调用让你更能控制监督者看到什么(上下文工程)。那个库仍然能用,但文档现在推荐工具调用形式。

失败模式

  • 领头幻觉计划。 如果领头生成的子问题并没有真正分解原问题,工人就会在错误的目标上做精确的研究。
  • 工人过度探索。 没有明确的范围边界,工人会漂出被指派的子问题,污染综合步骤。
  • 综合冲突。 两个工人返回矛盾的事实。领头必须要么追问(加一轮),要么显式记下分歧。 silently 选边站是最糟的失败:用户永远不知道发生过分歧。

监督者何时是错的

  • 串行任务。 如果第 2 步确实需要第 1 步的输出,并行什么也买不到。用流水线(CrewAI Sequential、LangGraph 线性图)。
  • 简单查询。 单智能体处理得更快更便宜。派生工人之前,先过一遍领头的"伸缩投入"检查。
  • 严格确定性。 监督者用 LLM 选择的委派。当审计/回放比适应性更重要时,静态图更好。

动手构建

code/main.py 用 threading 实现一个带三个并行工人的监督者。领头把查询分解成子问题,工人在每个子问题上并发运行,领头综合。没有真实 LLM——工人是脚本化的,模拟抓取-摘要。

关键结构:

  • Lead.plan(query) 把查询拆成 3 个子问题。
  • Worker.run(sub_q) 返回一份假摘要(生产中可以是任何使用工具的智能体)。
  • Lead.run(query) 在线程里启动工人,join,综合。

运行:

python3 code/main.py

输出展示计划、带起止时间戳的并行工人轨迹,以及最终综合。你能看到墙钟收益:三个 0.3 秒的工人约在 0.35 秒跑完,而不是 0.9 秒。

投入使用

outputs/skill-supervisor-designer.md 接收一个用户查询,产出一份监督者模式设计:领头系统提示词、工人角色、子问题分解规则和综合模板。构建新的研究型智能体系统之前,先用它。

交付

部署监督者模式之前的检查清单:

  • 模型配对。 领头用推理级模型(Opus 级、o3 级)。工人用更快更便宜的模型(Sonnet、o4-mini)。
  • 工人超时。 任何超过 2 倍中位运行时间的工人都被杀掉;领头要么缩小范围重派,要么不带它继续。
  • 每工人 token 上限。 硬性上限(比如预期综合输入的 10 倍),防止失控工人烧爆预算。
  • 可观测性。 追踪领头的计划、每个工人的工具调用和综合过程。这是一切事后调试的基础。
  • 彩虹发布。 有状态的长时运行智能体需要渐进的版本更替,不是热切换。

练习

  1. 运行 code/main.py,然后把领头改成派生 5 个工人而不是 3 个。观察墙钟效果。在这个 demo 里,工人数量到多少时,派生开销会超过并行收益?
  2. 实现工人超时:杀掉任何运行超过 0.5 秒的工人,让领头用剩下的结果综合。你需要什么可观测性,才能知道一个工人被砍了?
  3. 给领头的综合加冲突检测:如果两个工人返回矛盾答案,领头记下分歧而不是选一个。不调 LLM,怎么检测矛盾?
  4. 读 Anthropic 的 Research 系统工程博文。列出这个玩具 demo 要上生产必须采纳的三条实践。
  5. 对比 LangGraph 的 create_supervisor(legacy)与新的工具调用推荐。哪个让你更能控制监督者看到什么?为什么 Anthropic 显式地只把子答案、而不是工人的原始上下文,传进综合?

关键术语

术语大家口头的说法实际含义
监督者(Supervisor)"领头智能体"规划、委派、综合的编排智能体。不亲自干活。
工人(Worker)"子智能体"被监督者以狭窄范围和独立上下文窗口调用的聚焦智能体。
编排者-工人"监督者模式"同一个东西,不同名字。2026 年文献两个都用。
崭新上下文"干净窗口"工人的上下文从它的系统提示词和指派问题开始,不继承领头的历史。
彩虹部署"渐进发布"长时运行的有状态智能体需要按版本排空替换,不是蓝绿。
token 主导"上下文才是变量"按 Anthropic 数据,研究评测方差的 80% 来自总 token 用量,而非模型选择。
伸缩投入"智能体数匹配复杂度"领头估计查询难度,据此派生 1 个还是 10+ 个工人。
综合冲突"工人有分歧"两个工人返回矛盾事实;领头必须亮出分歧,不能 silently 选一个。
