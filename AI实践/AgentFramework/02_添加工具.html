添加工具

添加工具（Function Tools）

上一篇的 Agent 只会聊天，这一篇给它装上工具——查天气、查数据库、调 API。

工具是 Agent 区别于聊天机器人的关键。没有工具，Agent 只能基于模型自身的知识回答；有了工具，Agent 才能调用外部能力完成实际任务。

2.1 什么是工具

工具就是 Agent 在对话过程中可以调用的外部代码（函数）。

LLM 本身只会"说话"：它不能查实时天气（训练数据是过时的）、不能查你公司的数据库、不能发邮件、不能执行计算。工具就是给 LLM 装上"手和眼"，让它能干这些事。

2.1.1 工具调用的本质（function calling 机制）

这是整个 Agent 体系最核心的机制，搞懂这个，后面所有内容都好理解。

用户提问："阿姆斯特丹天气怎么样？"
      ↓
1. 你的代码把【用户问题 + 工具清单（含描述）】一起发给 LLM
      ↓
2. LLM 思考：这个问题我需要调 get_weather 工具
   → LLM 返回："请调用 get_weather(location='Amsterdam')"
   （注意：LLM 自己不执行代码，它只是告诉你"应该调这个函数"）
      ↓
3. 框架（Agent Framework）自动执行你定义的 GetWeather 函数
      ↓
4. 框架把函数返回值（"天气15度多云"）再发给 LLM
      ↓
5. LLM 基于这个结果，生成自然语言回答给用户：
   "阿姆斯特丹现在是多云，最高15度。"

这里有个反直觉的点：LLM 不直接执行你的代码，它只是输出一个"调用指令"。真正执行你的函数的是框架，执行完把结果回传给 LLM，LLM 再把结果"翻译"成用户能懂的话。

这就是所谓的 function calling。所有 Agent 框架的核心机制都是这个，Agent Framework 只是把流程封装好了，你只需要：定义工具 → 注册给 Agent → 框架自动跑。

2.2 框架支持的工具类型

官方把工具分成很多类，新手容易懵。按使用频率排个序：

常用工具（先掌握这些）：

  • 函数工具 Function Tool：你自己写的 C# 方法，在你的进程里跑
  • 本地 MCP 工具：连接本地/自托管 MCP 服务器，工具在 MCP 服务器进程里跑
  • 托管 MCP 工具：连接云端托管的 MCP 服务器，工具在云端跑

内置工具（特定 Provider 才有）：

  • 代码解释器（Code Interpreter）：在沙盒里跑 Python 代码
  • 文件搜索（File Search）：搜索上传的文件
  • Web 搜索（Web Search）：联网搜索
  • 图像生成（Image Generation）：生成图片

Foundry 专属工具（预览/实验，先别碰）：Bing Grounding、Azure AI Search、SharePoint、Microsoft Fabric、Computer Use、Browser Automation 等。

新手策略：先吃透函数工具（90% 场景够用），其他用到再查表。

不同 Provider 支持的工具不一样，简单看个矩阵：

工具类型OpenAI/Azure OpenAIFoundryAnthropicOllama
函数工具✅✅✅⚠️（看模型）
代码解释器✅✅❌❌
文件搜索✅✅❌❌
本地 MCP✅✅✅✅

结论：函数工具和本地 MCP 几乎全平台支持，是跨 Provider 的通用能力。

2.3 给 Agent 加一个天气工具

2.3.1 第一步：定义工具函数

用普通 C# 方法 + [Description] 特性：

using System.ComponentModel;

[Description("Get the weather for a given location.")]
static string GetWeather([Description("The location to get the weather for.")] string location)
    => $"The weather in {location} is cloudy with a high of 15°C.";

方法本身是个普通静态方法，参数和返回值都是普通 C# 类型。[Description] 贴在方法上，告诉 LLM 这个工具是干什么的；贴在参数上，告诉 LLM 这个参数要填什么。LLM 就是靠这段描述决定要不要调它，会从用户问题里提取"阿姆斯特丹"填进参数。

[Description] 是 LLM 理解工具的唯一线索。描述写得越清楚，LLM 调用越准确；描述含糊，LLM 会乱调或漏调。

2.3.2 第二步：注册工具给 Agent

using Microsoft.Extensions.AI;  // 注意这个 using，AIFunctionFactory 在这

AIAgent agent = new AIProjectClient(
        new Uri(endpoint),
        new DefaultAzureCredential())
    .AsAIAgent(
        model: deploymentName,
        instructions: "You are a helpful assistant.",
        tools: [AIFunctionFactory.Create(GetWeather)]);  // ← 关键

AIFunctionFactory.Create(方法名) 把一个 C# 方法包装成 AIFunction 对象。tools: [...] 是 AsAIAgent 的参数，传一个工具数组。

为什么要 AIFunctionFactory.Create？C# 方法本身只是 IL 代码，LLM 不认识。这个工厂方法通过反射读取方法的元数据（名字、参数类型、[Description] 特性），生成一个 LLM 能理解的 JSON Schema。这个 Schema 会被发给 LLM，LLM 据此决定怎么调用。

2.3.3 第三步：像之前一样运行

Console.WriteLine(await agent.RunAsync("What is the weather like in Amsterdam?"));

和第 1 篇的代码完全一样。区别只在创建 Agent 时多传了 tools。

框架自动完成的事：把工具描述发给 LLM → LLM 决定调 GetWeather(location="Amsterdam") → 框架执行你的 GetWeather 方法 → 把结果回传 LLM → LLM 生成最终回答。你完全不用写"如果用户问天气就调 GetWeather"这种 if/else，LLM 自己判断。

2.4 一个完整示例（多工具版本）

为了让全貌清楚，写一个 Agent 同时有多个工具的版本：

using System;
using System.ComponentModel;
using Azure.AI.Projects;
using Azure.Identity;
using Microsoft.Agents.AI;
using Microsoft.Extensions.AI;

var endpoint = Environment.GetEnvironmentVariable("AZURE_OPENAI_ENDPOINT")
    ?? throw new InvalidOperationException("Set AZURE_OPENAI_ENDPOINT");
var deploymentName = Environment.GetEnvironmentVariable("AZURE_OPENAI_DEPLOYMENT_NAME")
    ?? "gpt-4o-mini";

// ============ 工具定义 ============

[Description("Get the weather for a given location.")]
static string GetWeather([Description("The location to get the weather for.")] string location)
    => $"The weather in {location} is cloudy with a high of 15°C.";

[Description("Get the current time in a timezone.")]
static string GetCurrentTime([Description("The timezone, e.g. 'UTC', 'China Standard Time'")] string timezone)
    => $"Current time in {timezone} is {DateTime.UtcNow.AddHours(8):HH:mm}.";

[Description("Calculate the sum of two numbers.")]
static string AddNumbers(
    [Description("First number")] int a,
    [Description("Second number")] int b)
    => $"The sum of {a} and {b} is {a + b}.";

// ============ 创建 Agent ============

AIAgent agent = new AIProjectClient(new Uri(endpoint), new DefaultAzureCredential())
    .AsAIAgent(
        model: deploymentName,
        instructions: "You are a helpful assistant. Use tools when needed.",
        tools: [
            AIFunctionFactory.Create(GetWeather),
            AIFunctionFactory.Create(GetCurrentTime),
            AIFunctionFactory.Create(AddNumbers)
        ]);

// ============ 测试 ============

Console.WriteLine(await agent.RunAsync("What's the weather in Tokyo?"));
Console.WriteLine(await agent.RunAsync("What time is it in China?"));
Console.WriteLine(await agent.RunAsync("Add 123 and 456."));

LLM 会自动选择：问天气就调 GetWeather，问时间就调 GetCurrentTime，问加法就调 AddNumbers，问"你好"就什么工具都不调直接回话。这就是 Agent 的"智能"所在——LLM 根据工具描述自主决策。

2.5 把一个 Agent 当成另一个 Agent 的工具

这是 Agent Framework 一个很强大的模式——Agent 组合。

假设你有一个"天气专家 Agent"，它有专业的天气工具和指令。现在你想做一个"综合助手 Agent"，让它能调用天气专家来回答天气问题。

// 1. 先创建内部专家 Agent
AIAgent weatherAgent = new AIProjectClient(
        new Uri(endpoint),
        new DefaultAzureCredential())
    .AsAIAgent(
        model: "gpt-4o-mini",
        instructions: "You answer questions about the weather.",
        name: "WeatherAgent",
        description: "An agent that answers questions about the weather.",  // ← 注意这个 description
        tools: [AIFunctionFactory.Create(GetWeather)]);

// 2. 再创建主 Agent，把专家 Agent 当工具
AIAgent mainAgent = new AIProjectClient(
        new Uri(endpoint),
        new DefaultAzureCredential())
    .AsAIAgent(
        model: "gpt-4o-mini",
        instructions: "You are a helpful assistant.",
        tools: [weatherAgent.AsAIFunction()]);  // ← 关键：AsAIFunction()

// 3. 主 Agent 遇到天气问题，会自动调天气专家
Console.WriteLine(await mainAgent.RunAsync("What's the weather in Amsterdam?"));

agent.AsAIFunction() 把一个 AIAgent 转成 AIFunction，这样它就能被当成工具传给另一个 Agent。内部 Agent 的 description 很重要——主 Agent 就是靠它判断"这个问题该不该交给天气专家"。

这是多 Agent 协作的最简单形式。后面学 Workflows 时会看到更复杂的多 Agent 编排，但本质上都是这个模式的扩展：一个 Agent 当"调度员"，多个专家 Agent 当"工具"，调度员根据用户问题决定调哪个专家。

2.6 高级模式速览

官方文档还提到这些高级特性，先知道有这回事，用到再深入。

工具审批（Tool Approval）。场景是工具会执行敏感操作（比如删数据、发邮件、转账），你不想让 LLM 自动调用，要人工确认。框架提供 tool_approval 配置，每次工具调用前可以弹出来让人确认再执行。生产环境必备——生产里的 Agent 不能全自动跑危险操作。

运行时控制工具可用性。FunctionInvocationContext.AddTools() / RemoveTools() 可以在运行中动态加减工具；用 tool_choice 强制首次调用特定工具；用函数中间件拦截工具调用。

仅声明工具（Declaration-only Tool）。工具的 schema 发给 LLM，但框架不执行——结果由调用方提供。场景是工具实际在客户端 UI 执行（比如"获取用户位置"只能在浏览器里跑），框架只负责让 LLM 知道有这个工具。

类封装多个工具。多个工具共享状态时，把它们包装在一个类里，传绑定方法：

class MyTools
{
    private readonly SomeService _service;
    public MyTools(SomeService service) => _service = service;

    [Description("...")]
    public string ToolA(...) => _service.DoA(...);

    [Description("...")]
    public string ToolB(...) => _service.DoB(...);
}

var tools = new MyTools(service);
agent = ...AsAIAgent(tools: [
    AIFunctionFactory.Create(tools.ToolA),
    AIFunctionFactory.Create(tools.ToolB)
]);

2.7 常见坑 & 最佳实践

[Description] 一定要写清楚。这是最容易出问题的地方。

不好的写法：

[Description("Get data.")]  // LLM 不知道是什么 data
static string GetData(string input) => ...;  // 参数也没描述

好的写法：

[Description("Get the current weather for a city. Returns temperature and condition.")]
static string GetWeather([Description("City name, e.g. 'Amsterdam' or 'Tokyo'")] string city)
    => ...;

返回值最好是字符串或简单类型。LLM 看 JSON 比看复杂对象更准。如果工具返回复杂对象，建议 JsonSerializer.Serialize 成字符串。

工具命名用动词开头。GetWeather、SearchOrders、SendEmail 这种命名 LLM 更容易理解。别用 WeatherService、OrderManager 这种名词。

不是所有 Agent 类型都支持函数工具。官方明确警告：并非所有代理类型都支持函数工具，有些可能仅支持自定义内置工具。本教程用的 ChatClientAgent（通过 AsAIAgent 创建）支持，后面遇到 FoundryAgent 等类型时要查文档。

生产环境一定要加工具审批。开发时图省事可以全自动，生产环境对敏感工具必须加 tool_approval，否则 LLM 误调可能造成事故。

2.8 自测题

试着回答这几个问题，答不上来就回头翻：

  1. 如果用户问"巴黎天气"，LLM 自己能回答吗？为什么还要调工具？
  2. [Description] 特性是给谁看的？程序运行时它会改变方法行为吗？
  3. AIFunctionFactory.Create 到底做了什么事？
  4. 一个 Agent 同时注册 5 个工具，LLM 怎么决定调哪个？
  5. 把 Agent A 当成 Agent B 的工具，A 的哪个属性最重要？为什么？
  6. 生产环境为什么不建议工具全自动调用？
