服务托管

服务托管（Hosting）

前 5 篇的所有代码都是本地跑的——控制台程序里 await agent.RunAsync(...) 拿结果。这一篇解决怎么把 Agent 和 Workflow 部署成服务，让用户和其他 Agent 能通过网络调用它。

6.1 为什么需要托管

本地跑的 Agent 只能你自己用。真实业务里，Agent 至少要面对这几种调用方：

  • 前端 Web 应用，用户在网页里和 Agent 对话
  • 移动 App
  • 其他 Agent（多代理系统里互相调用）
  • 业务系统通过 HTTP API 触发 Agent

把这些场景统一抽象成"把 Agent 暴露成网络服务"，就是托管。框架给了几种托管方式，对应不同场景。

6.2 四种托管选项

官方列了四种，先了解各自适合什么：

A2A 协议（Agent-to-Agent）——通过标准化的 A2A 协议暴露 Agent。适合多代理系统，尤其是跨框架、跨技术栈的代理互相通信。

OpenAI-Compatible 端点——把 Agent 暴露成兼容 OpenAI Chat Completion 或 Responses API 的接口。适合已经有 OpenAI 兼容客户端、想无缝替换的场景。

Durable Extension——让 Agent 和 Workflow 跑在 Azure Functions 或自托管计算上，支持持久化和长任务。适合需要长期稳定运行的工作负载。

AG-UI 协议——专门给 Web 前端用的协议，方便构建基于浏览器的 AI Agent 应用。

这四种不是互斥的，同一个 Agent 可以同时通过多个协议暴露。下面重点讲 A2A 和 ASP.NET Core 托管，因为这是 .NET 开发者最常用的路径。

6.3 ASP.NET Core 托管的核心库

Microsoft.Agents.AI.Hosting 是基础托管库，提供把 AI Agent 集成到 ASP.NET Core 应用的扩展方法。它的核心思路是把 Agent 注册到依赖注入容器里，让 Agent 能用应用的基础设施（配置、日志、数据库连接等），同时让外部协议适配器能从容器里取出 Agent 来调用。

整个过程可以这样理解：托管库是个"协议适配器"——外部请求通过协议特定的中间件进来，被翻译成对 AIAgent 的调用，响应再被翻译回协议格式。Agent 实现本身和协议无关，换协议不用改 Agent 代码。

6.3.1 注册 IChatClient

在配置 Agent 之前，先把 IChatClient 注册到 DI 容器。IChatClient 是和底层 LLM 服务通信的客户端，Agent 通过它调模型。

// endpoint 是你的 Microsoft Foundry 项目端点
// deploymentName 比如 "gpt-4o-mini"
IChatClient chatClient = new AIProjectClient(
        new Uri(endpoint),
        new DefaultAzureCredential())
    .GetProjectOpenAIClient()
    .GetProjectResponsesClient()
    .AsIChatClient(deploymentName);

builder.Services.AddSingleton(chatClient);

DefaultAzureCredential 还是那句话——开发方便，生产环境换 ManagedIdentityCredential。

6.3.2 用 AddAIAgent 注册 Agent

var pirateAgent = builder.AddAIAgent(
    "pirate",
    instructions: "You are a pirate. Speak like a pirate",
    description: "An agent that speaks like a pirate.",
    chatClientServiceKey: "chat-model");

AddAIAgent 返回一个 IHostedAgentBuilder，可以链式配置 Agent。比如加工具：

var pirateAgent = builder.AddAIAgent("pirate", instructions: "You are a pirate. Speak like a pirate")
    .WithAITool(new MyTool()); // MyTool 是自定义 AITool 派生类

或者配会话存储：

var pirateAgent = builder.AddAIAgent("pirate", instructions: "You are a pirate. Speak like a pirate")
    .WithInMemorySessionStore();

WithInMemorySessionStore 是开发用的，生产环境要换成持久化存储——这块和第 4 篇讲的 ChatHistoryProvider 是一回事，只是这里通过托管库的扩展方法配置。

6.3.3 用 AddWorkflow 注册工作流

工作流也能托管。下面这个例子把两个 Agent 串成顺序工作流——用户输入先进 agent-1，响应再进 agent-2，最终输出：

builder.AddAIAgent("agent-1", instructions: "you are agent 1!");
builder.AddAIAgent("agent-2", instructions: "you are agent 2!");

var workflow = builder.AddWorkflow("my-workflow", (sp, key) =>
{
    var agent1 = sp.GetRequiredKeyedService<AIAgent>("agent-1");
    var agent2 = sp.GetRequiredKeyedService<AIAgent>("agent-2");
    return AgentWorkflowBuilder.BuildSequential(key, [agent1, agent2]);
});

注意这里 lambda 的两个参数：sp 是 IServiceProvider，用来从 DI 容器取依赖；key 是工作流的名字，会传给 AgentWorkflowBuilder。AgentWorkflowBuilder.BuildSequential 是个便捷方法，把多个 Agent 按顺序串起来。还有个 BuildConcurrent 创建并发执行的工作流。

6.3.4 把工作流转成 Agent 暴露

工作流本身不能直接通过 A2A 或 OpenAI 协议暴露——这些协议期望的是 AIAgent 接口。所以要先转换：

var workflowAsAgent = builder
    .AddWorkflow("science-workflow", (sp, key) => { ... })
    .AddAsAIAgent();  // 现在工作流可以当 Agent 用了

AddAsAIAgent() 把工作流包装成 AIAgent，之后所有对 Agent 适用的协议集成都能用上。这是工作流接入协议层的标准姿势。

6.4 通过 A2A 协议暴露 Agent

A2A 是个标准化协议，支持四件事：通过 AgentCard 发现代理、基于消息的代理间通信、通过任务支持长时间运行的代理进程、跨框架互操作。说白了就是让不同技术栈写的代理能互相说话。

A2A 协议规范在 https://a2a-protocol.org/latest/，想深入可以看。日常用不需要读规范，框架封装好了。

6.4.1 装 NuGet 包

# A2A 协议的 ASP.NET Core 集成
dotnet add package Microsoft.Agents.AI.Hosting.A2A.AspNetCore --prerelease

# 连接 Microsoft Foundry 需要的
dotnet add package Azure.AI.Projects --prerelease
dotnet add package Azure.Identity
dotnet add package Microsoft.Agents.AI.Foundry --prerelease

6.4.2 完整的最小 A2A 服务端

using A2A.AspNetCore;
using Azure.AI.Projects;
using Azure.Identity;
using Microsoft.Agents.AI;
using Microsoft.Agents.AI.Hosting;
using Microsoft.Extensions.AI;

var builder = WebApplication.CreateBuilder(args);

string endpoint = builder.Configuration["AZURE_OPENAI_ENDPOINT"]
    ?? throw new InvalidOperationException("AZURE_OPENAI_ENDPOINT is not set.");
string deploymentName = builder.Configuration["AZURE_OPENAI_DEPLOYMENT_NAME"]
    ?? throw new InvalidOperationException("AZURE_OPENAI_DEPLOYMENT_NAME is not set.");

// 注册 IChatClient
IChatClient chatClient = new AIProjectClient(
        new Uri(endpoint),
        new DefaultAzureCredential())
    .GetProjectOpenAIClient()
    .GetProjectResponsesClient()
    .AsIChatClient(deploymentName);
builder.Services.AddSingleton(chatClient);

// 注册 Agent
var pirateAgent = builder.AddAIAgent("pirate", instructions: "You are a pirate. Speak like a pirate.");

var app = builder.Build();

// 通过 A2A 协议暴露 Agent
app.MapA2A(pirateAgent, path: "/a2a/pirate", agentCard: new()
{
    Name = "Pirate Agent",
    Description = "An agent that speaks like a pirate.",
    Version = "1.0"
});

app.Run();

跑起来之后，/a2a/pirate 就是这个 Agent 的 A2A 端点。MapA2A 把 Agent 挂到指定路径，附带的 agentCard 是这个 Agent 的"名片"。

6.3.3 测试这个端点

启动服务后，发个 HTTP 请求就能调：

POST {{baseAddress}}/a2a/pirate/v1/message:stream
Content-Type: application/json
{
  "message": {
    "kind": "message",
    "role": "user",
    "parts": [
      {
        "kind": "text",
        "text": "Hey pirate! Tell me where have you been",
        "metadata": {}
      }
    ],
    "messageId": null,
    "contextId": "foo"
  }
}

响应长这样：

{
  "kind": "message",
  "role": "agent",
  "parts": [
    {
      "kind": "text",
      "text": "Arrr, ye scallywag! ..."
    }
  ],
  "messageId": "chatcmpl-CXtJbis...",
  "contextId": "foo"
}

请求里的两个字段值得注意：

  • messageId——这条消息的唯一标识，自己生成 GUID 也行，传 null 让 Agent 自动生成
  • contextId——会话标识。自己传一个 ID 就是开新对话，复用之前的 contextId 就是续上之前的对话。Agent 会保留同一个 contextId 的会话历史。不传就自动生成。

这个 contextId 和第 3、4 章讲的 Session 是一回事——A2A 协议层叫 contextId，框架内部叫 service_session_id，两者自动映射。

6.4.4 AgentCard 是什么

AgentCard 是 A2A 协议的"代理名片"，用来让其他 Agent 发现你、了解你的能力。属性有：

  • Name——显示名
  • Description——简短说明
  • Version——版本号
  • URL——端点 URL，不指定会自动分配
  • Capabilities——可选元数据，说明是否支持流式、推送通知等

通过 GET /a2a/pirate/v1/card 能拿到这张名片。其他 Agent 调你之前，先 GET 这张卡了解你是什么 Agent、支持什么能力。

6.4.5 一个服务暴露多个 Agent

只要端点路径不冲突，一个 ASP.NET Core 应用可以挂多个 Agent：

var mathAgent = builder.AddAIAgent("math", instructions: "You are a math expert.");
var scienceAgent = builder.AddAIAgent("science", instructions: "You are a science expert.");

app.MapA2A(mathAgent, "/a2a/math");
app.MapA2A(scienceAgent, "/a2a/science");

这种结构适合把一组相关的 Agent 部署在一起，共用底层 IChatClient 和基础设施。

6.5 作为客户端调用远程 A2A Agent

托管不光是"暴露 Agent"，反过来——调用远程 A2A Agent 也是托管的一部分。A2AAgent 类把任何远程 A2A 端点包装成本地 Agent，调用方式和你自己创建的 Agent 一模一样。

// 用 A2AAgent 包装远程 A2A 端点
async Task Main()
{
    string a2aHost = "https://your-a2a-agent.example.com";

    // 1. 先发现远程 Agent 的能力（拿 AgentCard）
    using var httpClient = new HttpClient();
    var cardResolver = new A2ACardResolver(httpClient, a2aHost);
    AgentCard card = await cardResolver.GetAgentCardAsync();
    Console.WriteLine($"Found agent: {card.Name}");

    // 2. 创建 A2AAgent 并发消息
    using var agent = new A2AAgent(
        name: card.Name,
        agentCard: card,
        url: a2aHost);

    var response = await agent.RunAsync("What are your capabilities?");
    foreach (var message in response.Messages)
    {
        Console.WriteLine(message.Text);
    }
}

A2AAgent 帮你处理了所有协议细节——拿 AgentCard、序列化请求、解析响应、管理会话。你写的代码和调本地 Agent 没区别。

6.5.1 长任务的 background 模式

默认 RunAsync 会等远程 Agent 跑完才返回。长任务可能跑几分钟几小时，不能傻等。这时用 background 模式：

// 启动长任务，立即返回 continuation token
var response = await agent.RunAsync("Process this large dataset", background: true);

if (response.ContinuationToken is not null)
{
    // 之后用 token 轮询结果
    var result = await agent.PollTaskAsync(response.ContinuationToken);
    Console.WriteLine(result);
}

这种"启动—拿 token—之后轮询"的模式是处理长任务的标准做法。配合 Durable Extension 能做更优雅的回调通知，不用傻轮询。

6.5.2 会话连续性

A2AAgent 调用时如果传了 AgentSession，会自动从 session.ServiceSessionId 派生出 A2A 的 context_id。这样跨多次 A2A 调用保持会话连续，不用每次手动设 context_id：

var session = new AgentSession(serviceSessionId: "my-conversation-1");

// context_id 自动设成 "my-conversation-1"
var response = await agent.RunAsync("Hello!", session);

// 同一个 session 继续聊
response = await agent.RunAsync("Follow-up question", session);

如果消息里显式带了 context_id，那个值优先。这个优先级要记住——显式 > 自动派生。

6.6 持久化托管：Durable Extension

ASP.NET Core 托管适合短交互——请求来、Agent 响应、连接关。但有些场景需要 Agent 长时间运行、跨多次调用保持状态、出故障能恢复，这时用 Durable Extension。

Durable Extension 让 Agent 和 Workflow 跑在 Azure Functions 或自托管计算上，提供：

  • 持久化状态——进程重启不丢
  • 长任务支持——可以跑几小时几天
  • 故障恢复——失败的任务能从检查点续上
  • 自动伸缩——按负载扩缩容

Durable Extension 和第 5 篇讲的超级步骤检查点是配套的——工作流在超级步骤边界保存检查点，崩了能从最近的检查点恢复，不用从头跑。

具体配置涉及 Azure Functions 的细节比较多，入门阶段知道有这个选项就行，需要时查官方的 Durable Agents 示例。

6.7 协议、Agent、Workflow 三者的关系

到这里你可能有疑问：协议（A2A/OpenAI）、Agent、Workflow 到底怎么组合？理清楚：

                        ┌─────────────────┐
外部请求 ──→ 协议适配器 ──→│  AIAgent 实例   │
（A2A/HTTP）              │  (或 Workflow   │
                        │   包装成 Agent) │
                        └─────────────────┘
                                │
                                ↓
                          IChatClient
                                │
                                ↓
                            LLM 服务

要点：

  1. 协议层只认 AIAgent——不管你后面是单 Agent 还是 Workflow，对外都得是 AIAgent。Workflow 要用 AddAsAIAgent() 转换。
  2. Agent 实例从 DI 容器拿——AddAIAgent 注册的 Agent 在容器里，协议适配器从容器取出来用。
  3. 同一个 Agent 能挂多个协议——同时通过 A2A 和 OpenAI-Compatible 端点暴露，Agent 代码不动。
  4. IChatClient 是底层依赖——所有 Agent 共用一个，通过 DI 注入。

理解了这个分层，后面碰到的所有托管场景都能套进去。

6.8 几个注意事项

生产环境必须换 DefaultAzureCredential。前面几章反复说过，这里再说一次。生产环境用 ManagedIdentityCredential 或其他特定凭证，否则有安全风险和性能问题——DefaultAzureCredential 会按顺序尝试多种凭证，每个失败的尝试都增加延迟。

WithInMemorySessionStore 只能开发用。生产环境必须换成持久化存储，否则服务重启所有会话历史丢失，用户回来发现 Agent "失忆"了。第 4 篇讲的自定义 ChatHistoryProvider 在这里通过 WithSessionStorage（或类似扩展方法）接入。

长任务别让 HTTP 请求一直挂着。HTTP 请求默认超时几十秒到几分钟，长任务必须用 background 模式启动 + 轮询/回调拿结果。直接 await agent.RunAsync(...) 等几小时，网关和浏览器都会先断开。

一个端点路径只能挂一个 Agent。MapA2A 的 path 参数必须唯一，否则启动报错。多 Agent 用不同路径区分。

AgentCard 要写清楚。其他 Agent 是靠 AgentCard 决定要不要调你的——Description 含糊，可能被误调或漏调。这和工具的 [Description] 一个道理。

Workflow 不能直接暴露。必须 AddAsAIAgent() 转换成 Agent。忘了这步会发现在 MapA2A 那里编译不过，因为参数类型不对。

C# 侧 A2AAgent 客户端要 dispose。它持有 HTTP 连接，用完不释放会泄漏连接。用 using 或 await using 包起来。
