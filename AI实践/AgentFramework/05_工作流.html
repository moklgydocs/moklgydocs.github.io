工作流基础

工作流（Workflow）

前 4 篇都是单 Agent，从这一篇开始进入"多代理编排"。前面看到的 Agent 都是让 LLM 自己决定调什么工具、怎么回答——好处是灵活，坏处是流程不可控。当你有一个明确的业务流程要执行时，就需要 Workflow。

5.1 工作流和 Agent 的区别

这是整篇的核心认知，先讲清楚。

Agent 是 LLM 驱动的，它执行的步骤是动态变化的，由 LLM 根据对话上下文和可用工具决定。适合开放式、对话式、需要 LLM 自主决策的场景。

Workflow 是一系列预定义的操作，可以把 AI Agent 作为组件包含在内。流程是显式定义的，开发者写死执行路径，LLM 只在节点里被调用。适合复杂业务流程、人工干预、与外部系统集成。

打个比方，Agent 像请了个顾问，你给目标他自己决定怎么干；Workflow 像写了张 SOP 流程图，每一步干什么是定死的，但某些步骤可以让 LLM 帮忙。

这里有个判断标准很重要：如果流程能用普通代码写清楚，就用 Workflow；如果需要 LLM 自己判断下一步干啥，才用 Agent。 Workflow 里可以嵌 Agent，反过来不行。

5.2 工作流的核心概念

框架的 Workflow 模型是个有向图，由四个核心概念组成：

执行器（Executor）——工作流里的处理单元，接收输入消息、执行任务、生成输出消息。可以是 AI Agent，也可以是纯逻辑代码。

边缘（Edge）——执行器之间的连接，决定消息怎么流。可以带条件，根据消息内容路由。

事件（Event）——工作流执行过程的可观测性。生命周期事件、执行器事件、自定义事件都能拿到。

WorkflowBuilder——把执行器和边缘组装成有向图的工具，支持流式和非流式两种运行模式。

理解这四个就够入门了。后面所有的 API 都是围绕它们展开。

5.3 一个最小工作流

先看最简单的例子——两个执行器串起来，第一个把字符串转大写，第二个把字符串反转：

using Microsoft.Agents.AI.Workflows;

// Step 1: 用函数快速创建执行器
Func<string, string> uppercaseFunc = s => s.ToUpperInvariant();
var uppercase = uppercaseFunc.BindAsExecutor("UppercaseExecutor");

// Step 2: 用类定义执行器
class ReverseTextExecutor() : Executor<string, string>("ReverseTextExecutor")
{
    public override ValueTask<string> HandleAsync(string message, IWorkflowContext context, CancellationToken cancellationToken = default)
    {
        return ValueTask.FromResult(string.Concat(message.Reverse()));
    }
}
ReverseTextExecutor reverse = new();

// 组装工作流
WorkflowBuilder builder = new(uppercase);
builder.AddEdge(uppercase, reverse).WithOutputFrom(reverse);
var workflow = builder.Build();

// 运行
await using Run run = await InProcessExecution.RunAsync(workflow, "Hello, World!");
foreach (WorkflowEvent evt in run.NewEvents)
{
    if (evt is ExecutorCompletedEvent executorComplete)
    {
        Console.WriteLine($"{executorComplete.ExecutorId}: {executorComplete.Data}");
    }
}

输入 "Hello, World!"，第一个执行器输出 "HELLO, WORLD!"，第二个输出 "!DLROW ,OLLEH"。

这段代码把 Workflow 的基本骨架全展示了：定义执行器 → WorkflowBuilder 加边 → Build() → InProcessExecution.RunAsync() 跑。后面只是在这个骨架上加东西。

5.4 执行器怎么定义

执行器有三种定义方式，从简单到复杂。

方式一：函数式执行器。适合无状态的简单转换。

Func<string, string> uppercaseFunc = s => s.ToUpperInvariant();
var uppercase = uppercaseFunc.BindAsExecutor("UppercaseExecutor");

方式二：继承 Executor 基类，用 [MessageHandler]。这是 C# 推荐做法，用源生成器在编译时注册处理程序，性能好、支持 AOT：

internal sealed partial class UppercaseExecutor() : Executor("UppercaseExecutor")
{
    [MessageHandler]
    private ValueTask<string> HandleAsync(string message, IWorkflowContext context)
    {
        string result = message.ToUpperInvariant();
        return ValueTask.FromResult(result); // 返回值自动发给下游
    }
}

注意类必须标 partial，否则源生成器不工作。返回值会自动发给所有连接的下游执行器。

如果你不想自动发送，可以手动控制：

[MessageHandler]
private async ValueTask HandleAsync(string message, IWorkflowContext context)
{
    string result = message.ToUpperInvariant();
    await context.SendMessageAsync(result); // 手动发给下游
}

方式三：一个执行器处理多种输入类型。在一个类里写多个 [MessageHandler]：

internal sealed partial class SampleExecutor() : Executor("SampleExecutor")
{
    [MessageHandler]
    private ValueTask<string> HandleStringAsync(string message, IWorkflowContext context)
        => ValueTask.FromResult(message.ToUpperInvariant());

    [MessageHandler]
    private ValueTask<int> HandleIntAsync(int message, IWorkflowContext context)
        => ValueTask.FromResult(message * 2);
}

框架根据消息类型自动路由到对应的 handler。这是强类型的好处——编译期就检查类型匹配，不用运行时试错。

IWorkflowContext

handler 第二个参数 IWorkflowContext context 是和整个工作流交互的入口，主要方法两个：

  • SendMessageAsync——把消息发给连接的下游执行器
  • YieldOutputAsync——产出工作流的最终输出（或中间输出）

区别很重要：SendMessageAsync 是发给下游继续处理，YieldOutputAsync 是直接产出给调用方。如果 handler 既不发送也不产出，那它只是执行副作用，比如写日志、调外部 API。

5.5 边缘怎么连

边缘是工作流的"血管"。最简单的直接连接：

builder.AddEdge(sourceExecutor, targetExecutor);

但工作流的威力在条件边缘。

条件边缘

给 AddEdge 传一个 condition 谓词，消息满足条件才走这条边：

private static Func<object?, bool> GetCondition(bool expectedResult) =>
    detectionResult => detectionResult is DetectionResult result && result.IsSpam == expectedResult;

var workflow = new WorkflowBuilder(spamDetectionExecutor)
    .AddEdge(spamDetectionExecutor, emailAssistantExecutor, condition: GetCondition(expectedResult: false))
    .AddEdge(emailAssistantExecutor, sendEmailExecutor)
    .AddEdge(spamDetectionExecutor, handleSpamExecutor, condition: GetCondition(expectedResult: true))
    .WithOutputFrom(handleSpamExecutor, sendEmailExecutor)
    .Build();

这就是个垃圾邮件分流流程：检测器判断是不是垃圾邮件，是垃圾走 handleSpamExecutor，不是垃圾走 emailAssistantExecutor → sendEmailExecutor。两条路径都可能是工作流输出，用 WithOutputFrom 标出来。

条件函数的写法注意下：参数是 object?，因为消息类型在路由时不一定确定。函数里要做类型检查（is DetectionResult result），匹配不上要安全降级。官方建议"fail closed"——解析失败时返回 false，避免误路由到错误路径。

Switch-Case 边缘

条件多于两个分支时，用 AddSwitch 更清晰：

builder.AddSwitch(spamDetectionExecutor, switchBuilder =>
    switchBuilder
    .AddCase(GetCondition(SpamDecision.NotSpam), emailAssistantExecutor)
    .AddCase(GetCondition(SpamDecision.Spam), handleSpamExecutor)
    .WithDefault(handleUncertainExecutor)
)

比堆一堆 AddEdge(condition) 清楚多了，还能加 WithDefault 兜底。

扇出和扇入

扇出——一个执行器同时给多个下游发消息，并行处理。用 AddFanOutEdge 加一个 targetSelector：

builder.AddFanOutEdge(
    emailAnalysisExecutor,
    targets: [handleSpamExecutor, emailAssistantExecutor, emailSummaryExecutor, handleUncertainExecutor],
    targetSelector: GetTargetAssigner()
);

private static Func<AnalysisResult?, int, IEnumerable<int>> GetTargetAssigner()
{
    return (analysisResult, targetCount) =>
    {
        if (analysisResult.SpamDecision == SpamDecision.Spam)
            return [0]; // 只发给 spam handler
        else if (analysisResult.SpamDecision == SpamDecision.NotSpam)
        {
            var targets = new List<int> { 1 }; // 总是发给 email assistant
            if (analysisResult.EmailLength > LongEmailThreshold)
                targets.Add(2); // 长邮件额外发给 summarizer
            return targets;
        }
        else
            return [3]; // 不确定走 uncertain handler
    };
}

targetSelector 返回的是目标索引列表，可以返回多个——这就是扇出的本质，一条消息可以同时进入多条处理路径。

扇入——多个执行器的输出汇聚到一个执行器。用 AddFanInBarrierEdge：

builder.AddFanInBarrierEdge(sources: [worker1, worker2, worker3], target: aggregatorExecutor);

Barrier 这个词很关键——汇聚是"屏障式"的，要等所有 sources 都完成才往下走。适合"三个 worker 并行处理，结果汇总"这种场景。

扇出和 Switch-Case 容易混，区别就一句话：Switch-Case 只选一个分支走，扇出可以同时走多条。

5.6 工作流怎么跑

WorkflowBuilder.Build() 出来的是 Workflow 对象，本身不执行。要执行用 InProcessExecution：

// 非流式：等执行完一次性拿结果
Run result = await InProcessExecution.RunAsync(workflow, inputMessage);
foreach (WorkflowEvent evt in result.NewEvents)
{
    if (evt is WorkflowOutputEvent outputEvt)
        Console.WriteLine($"Final result: {outputEvt.Data}");
}

// 流式：边执行边收事件
StreamingRun run = await InProcessExecution.RunStreamingAsync(workflow, inputMessage);
await foreach (WorkflowEvent evt in run.WatchStreamAsync())
{
    if (evt is ExecutorCompletedEvent executorComplete)
        Console.WriteLine($"{executorComplete.ExecutorId}: {executorComplete.Data}");
    if (evt is WorkflowOutputEvent outputEvt)
        Console.WriteLine($"Workflow completed: {outputEvt.Data}");
}

InProcessExecution 是进程内执行器，也是目前最常用的。后面托管章节会讲怎么把工作流部署到服务端跑。

WorkflowEvent 是所有事件的基类，常见的子类：

  • ExecutorCompletedEvent——某个执行器完成了，带 ID 和数据
  • WorkflowOutputEvent——工作流产出最终输出
  • 还有一些生命周期事件、自定义事件

流式模式让你能实时看到"哪个执行器在跑、产出了什么"，调试和监控都靠它。

5.7 超级步骤（Superstep）— 执行模型

这是工作流执行最底层的机制，理解了它才能解释一些"奇怪"的行为。

框架用的是修改过的 Pregel 模型，本质是批量同步并行（BSP）。执行被组织成离散的"超级步骤"，每个超级步骤干这些事：

  1. 收集上一个超级步骤产生的所有挂起消息
  2. 按边缘定义把消息路由到目标执行器
  3. 在这个超级步骤里，所有目标执行器并发运行
  4. 等所有执行器都完成才进入下一个超级步骤（同步屏障）
  5. 执行器发出的新消息排队等下一个超级步骤处理
Superstep N:
  收集挂起消息 → 路由 → 并发执行所有目标 → 屏障等待 → 进入下一超级步骤

最关键的是同步屏障。一个超级步骤里所有触发的执行器并行跑，但必须全部完成才能进下一个超级步骤。

这会带来一个反直觉的现象：如果你扇出到两条路径，一条是 step1 → step2 → step3 的链，另一条是单个 longRunningExecutor，那么链式路径的 step2 必须等 longRunningExecutor 跑完才能开始——因为它在下一个超级步骤里，而超级步骤要等上一轮全部完成。

如果你真有两条互不阻塞的并行路径，解决方法是把 step1 → step2 → step3 合并成一个执行器。这样两条路径在同一个超级步骤里执行，互不干扰。

为什么要这么设计？BSP 模型给三个保证：

  • 确定性执行——相同输入永远按相同顺序执行
  • 可靠检查点——状态可以在超级步骤边界保存，用于容错
  • 更简单的推理——超级步骤之间没有竞争条件，每个超级步骤看到的消息是一致的

简单说就是用同步换可预测性。在分布式和长任务场景下，可预测性比绝对的并行度重要。

5.8 输出执行器：final 和 intermediate

执行器调 YieldOutputAsync 产出的东西，到底是"最终输出"还是"中间进度信息"，是构建时决定的，配置在 WorkflowBuilder 上，不是每次调用单独设标志：

  • final_output_from——这些执行器的 YieldOutput 调用会产生 "output" 事件，被 WorkflowRunResult.GetOutputs() 返回
  • intermediate_output_from——这些执行器的 YieldOutput 调用会产生 "intermediate" 事件，被 GetIntermediateOutputs() 返回
var workflow = new WorkflowBuilder(
    startExecutor: analysisExecutor,
    finalOutputFrom: [summaryExecutor],
    intermediateOutputFrom: [analysisExecutor]
).Build();

注意：YieldOutputAsync 本身没有单次标志。同一个调用到底是 output 还是 intermediate，完全看构建器怎么命名。没有 YieldIntermediateAsync 这种 API。

如果某个执行器既不在 final_output_from 也不在 intermediate_output_from 里，它的 YieldOutput 调用会被丢弃——但它仍然可以通过 SendMessageAsync 给下游发消息。

这个设计有点反直觉，但想清楚就明白：把"产出语义"和"产出动作"解耦，执行器代码不用关心自己是不是终点，由组装工作流的人决定。

5.9 工作流验证

Build() 不是简单装个图，框架会在构建时做全面验证：

  • 类型兼容性——连接的执行器之间消息类型必须兼容
  • 图连接性——所有执行器必须能从起始执行器到达
  • 执行器绑定——所有执行器必须正确绑定和实例化
  • 边缘验证——检查重复边缘和无效连接

这是强类型工作流的好处。很多问题编译期或构建时就暴露了，不会留到运行时炸。

5.10 一个完整业务示例：邮件处理流程

把前面的东西拼起来，看个真实场景。流程是：邮件进来 → 垃圾邮件检测 → 是垃圾就标记归档；不是垃圾就让 AI 助手起草回复 → 发送回复。

先定义数据模型：

public sealed class DetectionResult
{
    [JsonPropertyName("is_spam")] public bool IsSpam { get; set; }
    [JsonPropertyName("reason")] public string Reason { get; set; } = "";
}

public sealed class EmailResponse
{
    [JsonPropertyName("response")] public string Response { get; set; } = "";
}

定义执行器（这里展示关键部分，省略 Agent 创建细节）：

internal sealed partial class SpamDetectionExecutor(AIAgent agent) : Executor("SpamDetectionExecutor")
{
    [MessageHandler]
    private async ValueTask<DetectionResult> HandleAsync(ChatMessage message, IWorkflowContext context, CancellationToken ct = default)
    {
        var response = await agent.RunAsync(message, cancellationToken: ct);
        return JsonSerializer.Deserialize<DetectionResult>(response.Text)!;
    }
}

internal sealed partial class EmailAssistantExecutor(AIAgent agent) : Executor("EmailAssistantExecutor")
{
    [MessageHandler]
    private async ValueTask<EmailResponse> HandleAsync(DetectionResult message, IWorkflowContext context, CancellationToken ct = default)
    {
        if (message.IsSpam)
            throw new ArgumentException("This executor should only handle non-spam messages.");
        // 起草回复...
        var response = await agent.RunAsync("...", cancellationToken: ct);
        return JsonSerializer.Deserialize<EmailResponse>(response.Text)!;
    }
}

internal sealed partial class SendEmailExecutor() : Executor("SendEmailExecutor")
{
    [MessageHandler]
    private async ValueTask HandleAsync(EmailResponse message, IWorkflowContext context, CancellationToken ct = default)
        => await context.YieldOutputAsync($"Email sent: {message.Response}");
}

internal sealed partial class HandleSpamExecutor() : Executor("HandleSpamExecutor")
{
    [MessageHandler]
    private async ValueTask HandleAsync(DetectionResult message, IWorkflowContext context, CancellationToken ct = default)
        => await context.YieldOutputAsync($"Email marked as spam: {message.Reason}");
}

组装工作流：

var workflow = new WorkflowBuilder(spamDetectionExecutor)
    .AddEdge(spamDetectionExecutor, emailAssistantExecutor, condition: GetCondition(expectedResult: false))
    .AddEdge(emailAssistantExecutor, sendEmailExecutor)
    .AddEdge(spamDetectionExecutor, handleSpamExecutor, condition: GetCondition(expectedResult: true))
    .WithOutputFrom(handleSpamExecutor, sendEmailExecutor)
    .Build();

// 跑
string emailContent = "Congratulations! You've won $1,000,000! Click here to claim!";
StreamingRun run = await InProcessExecution.RunStreamingAsync(workflow, new ChatMessage(ChatRole.User, emailContent));

await foreach (WorkflowEvent evt in run.WatchStreamAsync())
{
    if (evt is WorkflowOutputEvent outputEvent)
        Console.WriteLine(outputEvent);
}

这个例子把前面所有概念都用上了：执行器（含 Agent 包装）、条件边缘、多输出、流式执行。垃圾邮件会走 handleSpamExecutor 路径，正常邮件走 emailAssistantExecutor → sendEmailExecutor 路径。两条路径都可能产出最终输出。

5.11 几个注意事项

有状态执行器跨运行会串数据。执行器可以持有可变状态，但如果同一个执行器实例被多个工作流运行共享，必须在执行器上实现 IResettableExecutor，在运行之间清理状态。否则上一轮的状态会污染下一轮。

超级步骤的同步屏障容易被忽略。扇出后两条路径速度差异大时，快的路径会被慢的拖住。真要互不阻塞，把链式步骤合并进单个执行器。

条件函数要 fail closed。消息类型不匹配或解析失败时返回 false，不要返回 true 让消息误入歧途。错误路由比直接报错难调试多了。

YieldOutputAsync 不等于发下游。它产出的是工作流输出，不是发给下一个执行器。要把消息传给下游，用 SendMessageAsync。

Agent 当执行器要包一层。不能直接把 AIAgent 传给 WorkflowBuilder，要写个 Executor 类把 Agent 包起来，在 handler 里调 agent.RunAsync。前面邮件例子里的 SpamDetectionExecutor 就是这么做的。

partial 关键字不能漏。用 [MessageHandler] 的执行器类必须标 partial，源生成器才能工作。漏了的话编译能过，但运行时找不到 handler。
