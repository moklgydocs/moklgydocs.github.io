Fiber 架构

Fiber 架构

为什么需要 Fiber？

React 15 的「栈调和」（Stack Reconciler）有一个致命问题：渲染是同步且不可中断的。一旦开始渲染，必须一口气完成整棵组件树，期间浏览器无法响应用户输入。

当组件树很大时，用户会感到明显卡顿。

Fiber 的核心思想：可中断的渲染

Fiber 把渲染工作拆分成小单元（Fiber 节点），每完成一个单元就检查是否有更高优先级的任务：

旧方式（栈）：                  新方式（Fiber）：
开始 → A → B → C → D → 完成     开始 → A → 暂停（有用户输入）
（不可中断，可能卡 100ms）              → 处理用户输入
                                        → B → C → D → 完成

Fiber 节点结构（简化）

每个 React 元素都对应一个 Fiber 节点：

{
  type: 'div',           // 元素类型
  stateNode: domNode,    // 对应的真实 DOM 节点
  
  // 树结构（链表）
  child: fiberChild,      // 第一个子节点
  sibling: fiberSibling,  // 下一个兄弟节点
  return: fiberParent,    // 父节点
  
  // 工作相关
  pendingProps: {},        // 新的 props
  memoizedState: {},       // 当前 state
  effectTag: 'UPDATE',     // 副作用标记（新增、更新、删除）
  
  // 双缓冲
  alternate: otherFiber,   // 指向另一棵树的对应节点
}

双缓冲（Double Buffering）

React 同时维护两棵 Fiber 树：

  • current 树：当前屏幕上显示的
  • workInProgress 树：正在构建的新树

构建完成后，React 将 workInProgress 树「提交」为新的 current 树（指针切换）。

current 树   ←  屏幕上显示的
workInProgress 树  ←  后台构建中

构建完成后：
workInProgress 变成新的 current（切换指针）
旧的 current 变成下次的 workInProgress

渲染的两个阶段

1. Render 阶段（可中断）

  • 遍历 Fiber 树
  • 对比新旧 props/state
  • 标记需要更新的节点（effectTag）
  • 不操作 DOM

2. Commit 阶段（不可中断）

  • 根据 effectTag 执行 DOM 操作
  • 执行生命周期/useEffect
  • 一次性完成，保证 DOM 一致性

优先级调度

React 19 中，不同的更新有不同的优先级：

优先级场景示例
最高同步flushSync
高用户交互按钮点击、输入
中默认更新setState
低TransitionstartTransition
最低空闲Suspense 回退
import { startTransition } from 'react';

function SearchResults() {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState([]);

  const handleChange = (e) => {
    // 高优先级：立即更新输入框
    setQuery(e.target.value);
    
    // 低优先级：搜索结果可以稍后更新
    startTransition(() => {
      setResults(search(e.target.value));
    });
  };
}

对实际开发的意义

  1. 理解为什么 state 更新是异步的：React 需要收集更新，合并后批量处理
  2. 理解 startTransition：利用优先级让紧急更新先执行
  3. 理解 useEffect 的执行时机：在 Commit 阶段之后异步执行
