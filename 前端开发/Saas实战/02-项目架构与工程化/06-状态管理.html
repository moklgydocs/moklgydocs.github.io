状态管理

状态管理

这一步解决什么问题？
路由和布局搭好了，但页面还没有"记忆"——用户登录状态怎么保存？菜单数据缓存在哪里？本文将实现两个核心 Zustand Store：auth-store（认证状态）和 menu-store（菜单状态），让应用具备"全局状态"的能力。

对于 ASP.NET Core 开发者来说，Store 就像 Scoped/Singleton Service + INotifyPropertyChanged——多个组件共享同一个状态，状态变化时自动通知订阅者。理解了这个类比，Zustand 的学习曲线几乎为零。

前置知识

Zustand vs Redux — .NET 开发者视角

对比项ZustandRedux
样板代码极少（一个函数）大量（action、reducer、saga）
学习曲线5 分钟2-3 天
异步处理直接在 action 中 async/await需要 redux-thunk 或 redux-saga
订阅模型精确选择器（只订阅需要的字段）全局选择器 + shallow compare
.NET 类比Scoped Service + INotifyPropertyChangedMediatR + 事件溯源

🤔 导师提问：回想一下你用 DI 容器时的体验——当注册代码超过几十行，找一个服务的注册位置是不是很头疼？Redux 的 action/reducer/saga 三件套和那种"注册地狱"有什么共通之处？Zustand 的"一个函数搞定"又让你想到 .NET 里什么简洁的模式？

为什么选 Zustand？ 因为 AdminWeb 的状态很简单——只有认证和菜单两个全局状态。用 Redux 就像用大炮打蚊子：你需要定义 action type、写 reducer、配置 middleware、用 connect() 或 useSelector 连接组件……为了管理 7 个字段的状态，写 200 行样板代码。Zustand 只需要 30 行。

Zustand 的精确订阅

// Redux: 组件订阅整个 store，任何字段变化都会触发重渲染
const isAuthenticated = useSelector(state => state.auth.isAuthenticated)

// Zustand: 组件只订阅 isAuthenticated，其他字段变化不触发重渲染
const isAuthenticated = useAuthStore(s => s.isAuthenticated)

.NET 类比：Redux 像事件总线（EventBus）——所有订阅者都会收到所有事件；Zustand 像 INotifyPropertyChanged——只有对应属性变化时才通知订阅者。

🤔 导师提问：如果有 10 个组件都用 useAuthStore(s => s.isAuthenticated) 订阅了认证状态，其中某个组件调用了 setTokens，会有几个组件重新渲染？提示：想想 INotifyPropertyChanged 的通知机制——改的是哪个属性？订阅的又是哪个属性？

persist 中间件 — .NET 类比

persist 中间件把 Store 状态自动保存到 localStorage，页面刷新后自动恢复。类似 .NET 中把配置保存到 appsettings.json，应用启动时自动读取。

// Zustand persist
persist(storeConfig, { name: "admin-auth" })
// → 写入 localStorage["admin-auth"] = JSON.stringify(state)

// .NET 等价
// File.WriteAllText("appsettings.json", JsonSerializer.Serialize(state));

代码实现

src/stores/auth-store.ts

import { create } from "zustand"
import { persist } from "zustand/middleware"
import type { CurrentUser, UserTenantInfo } from "@/types"

/**
 * 认证状态接口
 * 管理用户的 token、信息、租户等认证相关状态
 */
interface AuthState {
  /** 访问令牌（Bearer Token） */
  accessToken: string | null
  /** 刷新令牌 */
  refreshToken: string | null
  /** 当前登录用户信息 */
  user: CurrentUser | null
  /** 是否已认证 */
  isAuthenticated: boolean
  /** 当前选中的租户 ID */
  currentTenantId: string | null
  /** 当前选中的租户名称 */
  currentTenantName: string | null
  /** 用户可用的租户列表 */
  availableTenants: UserTenantInfo[] | null

  /** 设置 Token（登录成功或刷新 Token 时调用） */
  setTokens: (accessToken: string, refreshToken?: string) => void
  /** 设置当前用户信息 */
  setUser: (user: CurrentUser | null) => void
  /** 设置当前选中的租户 */
  setCurrentTenant: (tenantId: string, tenantName: string) => void
  /** 设置可用的租户列表 */
  setAvailableTenants: (tenants: UserTenantInfo[]) => void
  /** 登出（清除所有认证状态） */
  logout: () => void
}

/**
 * 认证状态管理 Store（Zustand + persist 持久化）
 * 使用 localStorage 持久化，key 为 "admin-auth"
 */
export const useAuthStore = create<AuthState>()(
  persist(
    (set) => ({
      accessToken: null,
      refreshToken: null,
      user: null,
      isAuthenticated: false,
      currentTenantId: null,
      currentTenantName: null,
      availableTenants: null,

      /** 设置 Token，同时将认证状态标记为 true */
      setTokens: (accessToken, refreshToken) =>
        set({ accessToken, refreshToken: refreshToken ?? null, isAuthenticated: true }),

      /** 设置当前用户信息 */
      setUser: (user) => set({ user }),

      /** 设置当前选中的租户 ID 和名称 */
      setCurrentTenant: (tenantId, tenantName) =>
        set({ currentTenantId: tenantId, currentTenantName: tenantName }),

      /** 设置可用的租户列表 */
      setAvailableTenants: (tenants) => set({ availableTenants: tenants }),

      /** 登出：清除所有认证相关状态 */
      logout: () => set({
        accessToken: null, refreshToken: null, user: null, isAuthenticated: false,
        currentTenantId: null, currentTenantName: null, availableTenants: null,
      }),
    }),
    // 持久化到 localStorage，key 为 "admin-auth"
    { name: "admin-auth" }
  )
)

src/stores/menu-store.ts

import { create } from "zustand"
import { persist } from "zustand/middleware"
import { menusApi } from "@/api/perm/menus"
import type { MenuDto } from "@/types"

interface MenuState {
  /** 当前用户的菜单树（已按权限过滤） */
  menus: MenuDto[]
  /** 是否已加载过 */
  loaded: boolean
  /** 加载中 */
  loading: boolean
  /** 错误信息 */
  error: string | null
  /** 上次成功获取的时间戳（用于缓存过期检查） */
  fetchedAt: number | null

  /** 获取当前用户菜单 */
  fetchMenus: (appCode: string) => Promise<void>
  /** 使缓存失效（强制下次重新获取） */
  invalidate: () => void
}

/** 缓存 TTL：5 分钟 */
const CACHE_TTL_MS = 5 * 60 * 1000

export const useMenuStore = create<MenuState>()(
  persist(
    (set, get) => ({
      menus: [],
      loaded: false,
      loading: false,
      error: null,
      fetchedAt: null,

      fetchMenus: async (appCode: string) => {
        const { loaded, fetchedAt, loading } = get()

        // 已在加载中，跳过
        if (loading) return

        // 缓存未过期，跳过
        if (loaded && fetchedAt && Date.now() - fetchedAt < CACHE_TTL_MS) return

        set({ loading: true, error: null })
        try {
          const res = await menusApi.getCurrentUserMenus(appCode)
          set({
            menus: res.data ?? [],
            loaded: true,
            fetchedAt: Date.now(),
          })
        } catch (err) {
          set({
            error: err instanceof Error ? err.message : "加载菜单失败",
            loaded: false,
          })
        } finally {
          set({ loading: false })
        }
      },

      invalidate: () => {
        set({ loaded: false, fetchedAt: null })
      },
    }),
    {
      name: "admin-menus",
      partialize: (state) => ({
        menus: state.menus,
        loaded: state.loaded,
        fetchedAt: state.fetchedAt,
      }),
    }
  )
)

代码讲解

auth-store 的 7 个状态字段

字段类型何时设置何时读取
accessTokenstring | null登录成功 / Token 刷新createHttp 请求拦截器
refreshTokenstring | null登录成功 / Token 刷新createHttp 401 拦截器
userCurrentUser | null登录成功后获取用户信息AppHeader 显示用户名/邮箱
isAuthenticatedbooleansetTokens 时自动设为 trueProtectedRoute 路由守卫
currentTenantIdstring | null用户选择租户createHttp 注入 X-Tenant-Id
currentTenantNamestring | null用户选择租户AppHeader 顶栏显示
availableTenantsUserTenantInfo[] | null登录成功后获取租户列表AppHeader 租户切换下拉框

.NET 类比：这就像 HttpContext 中的认证信息——accessToken = Bearer Token，currentTenantId = Tenant Context，isAuthenticated = User.Identity.IsAuthenticated。

setTokens 的隐式联动

setTokens: (accessToken, refreshToken) =>
  set({ accessToken, refreshToken: refreshToken ?? null, isAuthenticated: true }),

调用 setTokens 时自动将 isAuthenticated 设为 true。这保证了 token 和认证状态的一致性——不会出现"有 token 但未认证"或"已认证但无 token"的中间状态。

🤔 导师提问：为什么 setTokens 要同时设置 isAuthenticated: true，而不是让调用方自己分两步设置？想象一下：如果某处只写了 set({ accessToken }) 忘了设 isAuthenticated，路由守卫还能正确拦截吗？这跟后端里 SignInAsync 必须同时设 Cookie 和 Claims 是不是一个道理？

.NET 类比：就像 HttpContext.SignInAsync() 同时设置认证 Cookie 和 User.Identity。你不应该手动设置 IsAuthenticated = true 而不设置 Cookie。

logout 的全量清除

logout: () => set({
  accessToken: null, refreshToken: null, user: null, isAuthenticated: false,
  currentTenantId: null, currentTenantName: null, availableTenants: null,
}),

logout 清除了所有 7 个字段。这是因为登出意味着用户完全离开——不能保留租户信息、不能保留用户信息。如果漏掉 availableTenants，下次登录时可能会显示上一次的租户列表。

menu-store 的缓存 TTL 机制

const CACHE_TTL_MS = 5 * 60 * 1000 // 5 分钟

fetchMenus: async (appCode: string) => {
  const { loaded, fetchedAt, loading } = get()

  if (loading) return                              // 正在加载，跳过
  if (loaded && fetchedAt && Date.now() - fetchedAt < CACHE_TTL_MS) return  // 缓存有效，跳过

  // ... 发起 API 请求 ...
  set({ menus: res.data ?? [], loaded: true, fetchedAt: Date.now() })
}

这是客户端缓存的标准模式：

  1. 防重复请求：if (loading) return 防止组件多次挂载时触发多次 API 请求
  2. 缓存 TTL：5 分钟内不重复请求，减少后端压力
  3. 持久化 + 缓存：fetchedAt 保存到 localStorage，刷新页面后仍能判断缓存是否过期

.NET 类比：这就像 IMemoryCache + SetAbsoluteExpiration(TimeSpan.FromMinutes(5))。不同之处在于前端的缓存是主动拉取的（组件挂载时触发），后端的缓存是被动填充的（请求命中时触发）。

🤔 导师提问：为什么 fetchMenus 是 Store 的方法而不是一个独立的 Hook？提示：如果两个组件同时挂载并调用 fetchMenus，缓存数据需要在它们之间共享——useState 做不到这一点，但 Store 可以。想想后端里 IMemoryCache 为什么是 Singleton 而不是 Scoped。

partialize — 选择性持久化

partialize: (state) => ({
  menus: state.menus,
  loaded: state.loaded,
  fetchedAt: state.fetchedAt,
}),

partialize 控制哪些字段保存到 localStorage。menu-store 只持久化 3 个字段，排除了 loading、error 和方法（fetchMenus、invalidate）。

为什么排除 loading 和 error？

  • loading：页面刷新后不应该保留"正在加载"的状态，应该重新开始
  • error：上次加载失败的错误信息不应该在下次打开页面时还显示
  • 方法（fetchMenus、invalidate）：函数无法序列化到 JSON

.NET 类比：这就像 JsonIgnore 特性——某些属性不应该被序列化。

auth-store 为什么不用 partialize？

auth-store 持久化所有字段（没有 partialize），包括 isAuthenticated 和 user。这是因为：

  1. 用户刷新页面后应该保持登录状态（isAuthenticated: true）
  2. 用户信息（user）不需要重新请求
  3. Token 刷新时需要读取 refreshToken（如果它不在 localStorage 中，刷新页面后无法刷新 token）

Zustand 的精确订阅模型

// ✅ 只订阅 accessToken — 只有 accessToken 变化时才重渲染
const token = useAuthStore(s => s.accessToken)

// ❌ 订阅整个 store — 任何字段变化都触发重渲染
const store = useAuthStore()

// ✅ 订阅多个字段，用 shallow 比较
import { shallow } from "zustand/shallow"
const { accessToken, currentTenantId } = useAuthStore(
  s => ({ accessToken: s.accessToken, currentTenantId: s.currentTenantId }),
  shallow
)

这在 createHttp 的拦截器中体现为：

// 拦截器中使用 getState()，不触发组件重渲染
const { accessToken, currentTenantId } = useAuthStore.getState()

getState() 是同步读取当前状态的方法，不会建立订阅关系。这适合在 React 组件外（如拦截器、工具函数）使用。

.NET 类比：useAuthStore(s => s.accessToken) 像 Observable<string>（只监听特定属性），useAuthStore.getState() 像 ServiceProvider.GetRequiredService<AuthState>()（一次性获取）。

【易错点】 选择器返回引用类型时要格外小心。useAuthStore(s => s.user) 每次都返回同一个对象引用（因为 user 本身没变），所以不会触发多余的重渲染。但如果写成 useAuthStore(s => ({ name: s.user?.name }))，每次调用都创建一个新对象——即使 name 没变，引用也不同，组件会无限重渲染。解决方案：用 shallow 比较或直接订阅原始字段 s => s.user?.name。

🤔 导师提问：以下代码有什么问题？const info = useAuthStore(s => ({ name: s.user?.name, tenant: s.currentTenantName }))——看起来很合理，把需要的数据一次性取出来。但组件会怎样？如果你加了 shallow，问题解决了吗？为什么？

具体对比：

// ❌ 错误：每次都创建新对象，引用不同，导致每次都重渲染
const { name } = useAuthStore(s => ({ name: s.user?.name }))

// ✅ 正确方式一：直接订阅原始字段
const name = useAuthStore(s => s.user?.name)

// ✅ 正确方式二：用 shallow 比较多个字段
const { accessToken, currentTenantId } = useAuthStore(
  s => ({ accessToken: s.accessToken, currentTenantId: s.currentTenantId }),
  shallow
)

【性能陷阱】 persist 中间件在每次 set() 调用后都会执行一次 JSON.stringify() 将状态写入 localStorage。如果 Store 状态很大（比如 menu-store 的 menus 数组包含几百个节点），频繁 set() 会造成明显的序列化开销。AdminWeb 的 menu-store 通过 5 分钟 TTL 缓存避免频繁写入，而 auth-store 的状态很小（7 个字段），序列化成本可以忽略。如果未来某个 Store 状态体积变大，应该用 partialize 只持久化必要字段。

实测参考：在 Chrome DevTools → Performance 中录制一次 fetchMenus() 调用，可以看到 JSON.stringify() 的耗时通常在 1ms 以内（菜单数据量 < 100KB）。但如果某个 Store 管理的是大量列表数据（如文件目录树），单次序列化可能超过 10ms——此时应考虑只在关键时刻持久化，或使用 IndexedDB 替代 localStorage。

🤔 导师提问：假设你有一个文件管理 Store，存了 10000 条文件记录。每次 set() 都会触发 JSON.stringify 把整棵树序列化到 localStorage——用户拖拽排序时连续调用 10 次 set()，会发生什么？你会怎么优化？提示：想想后端里 EF Core 的批量更新为什么不是逐条 SaveChanges。

踩坑提醒

  1. persist 的 name 不能重复。如果两个 Store 使用相同的 name（如都叫 "admin-auth"），它们会互相覆盖 localStorage 数据。命名规范：admin-auth、admin-menus，用模块名做前缀。

  2. logout() 只清除了 Store 状态，没有清除 localStorage 中的旧 token。实际上 persist 中间件会在 set() 后自动同步 localStorage，所以 logout() 调用 set({accessToken: null, ...}) 后 localStorage 也被清空了。不需要手动 localStorage.removeItem()。

  3. fetchMenus 的 appCode 参数是硬编码的 "admin-web"。在 AppSidebar 中 fetchMenus("admin-web") 写死了应用编码。如果未来有多个前端应用（如移动端、小程序端），应该根据当前应用动态传入。

  4. invalidate() 只清除缓存标记，不清除菜单数据。调用 invalidate() 后 loaded 和 fetchedAt 被清除，但 menus 数组仍在内存中。下次 fetchMenus() 会重新请求 API 并覆盖 menus。这意味着在请求完成前，组件仍然渲染旧菜单——这是故意的，避免"清除菜单 → 白屏 → 重新加载"的闪烁。

组件思维：状态所有权与 Store 交互原则

什么时候用 Store，什么时候用 useState？

后端开发者刚接触 React 时，最常见的困惑就是：这个状态该放哪？ Zustand Store？组件的 useState？还是 URL 参数？

判断标准：

状态特征放哪里后端类比
多个组件需要读写Zustand StoreSingleton Service（全局共享）
只在一个组件内使用useState方法内的局部变量
需要页面刷新后保留Zustand Store + persistappsettings.json（持久化配置）
表单临时输入（不需要共享）useStateAction 参数（请求作用域）
控制对话框开关useState（除非父组件也要控制）Modal/Dialog 的 Show() 调用
当前选中的行/页码useState（除非需要跨页面保留）ViewState（页面作用域）

💡 核心原则：状态应该放在离它最近的、所有需要它的组件的公共祖先中。 如果只有组件自己用，就放 useState；如果兄弟组件也要用，就提升到父组件或 Store。

🤔 导师提问：如果一个搜索表单的筛选条件需要被表格组件读取，但只在 UserListPage 内部使用，应该放 Store 还是 useState？提示：考虑 UserListPage 是否是筛选条件和表格的"公共祖先"。

Store vs Props：组件如何获取数据？

Store 中的数据，组件有两种获取方式：

// 方式 1：直接从 Store 读取（组件与 Store 耦合）
function UserAvatar() {
  const userName = useAuthStore(s => s.user?.displayName)
  return <span>{userName}</span>
}

// 方式 2：通过 Props 传入（组件与 Store 解耦）
function UserAvatar({ userName }: { userName: string }) {
  return <span>{userName}</span>
}
// 父组件负责从 Store 获取数据并传入
<UserAvatar userName={user?.displayName} />

选择原则：

场景推荐方式原因
深层嵌套组件（3层以上）直接读 Store避免 Props Drilling（逐层传递）
可复用的通用组件通过 Props组件不依赖特定 Store，可在任何项目使用
页面级组件直接读 Store页面本身就是"知道一切"的编排者
UI 基础组件（Button、Dialog）通过 Props这些组件不应该知道业务逻辑

💡 后端类比：直接读 Store ≈ 在 Service 中注入 IMemoryCache；通过 Props ≈ 在方法参数中传入数据。前者方便但耦合，后者灵活但需要传递。

状态所有权：谁负责修改？

在 AdminWeb 中，auth-store 拥有认证状态的所有权：

auth-store 拥有：user, isAuthenticated, accessToken, currentTenantId, availableTenants
  ↓ 只有这些方法可以修改状态：
  setTokens()    → 设置 token + isAuthenticated
  setUser()      → 设置用户信息
  setCurrentTenant() → 设置当前租户
  setAvailableTenants() → 设置租户列表
  logout()       → 清除所有状态

任何组件都不应该直接修改 Store 的内部状态。组件只能：

  1. 读取状态（通过 selector）
  2. 调用 Store 暴露的方法来间接触发修改

类比后端：Store ≈ DbContext，Store 方法 ≈ Repository 方法，组件 ≈ Controller。Controller 不直接改 DbSet，而是调用 Repository 方法。

// ❌ 反模式：组件直接改 Store 内部状态
useAuthStore.setState({ isAuthenticated: true })  // 绕过了 setTokens 的原子性保证

// ✅ 正确：调用 Store 方法
setTokens(accessToken, refreshToken)  // setTokens 内部保证 isAuthenticated 同步更新

Zustand persist 的水合竞态

【易错点】使用 persist 中间件时，Store 在页面加载的极短瞬间内持有默认值（isAuthenticated: false），直到 localStorage 中的数据被水合（hydrate）完成。

这意味着：如果 ProtectedRoute 在水合完成前检查 isAuthenticated，会得到 false，导致已登录用户被重定向到登录页。

AdminWeb 通过 onRehydrateStorage 回调解决：

persist(
  (set) => ({ /* store definition */ }),
  {
    name: "admin-auth",
    onRehydrateStorage: () => {
      // 水合完成后的回调
      return (state, error) => {
        if (error) console.error("Auth store hydration failed:", error)
      }
    },
  }
)

如果遇到水合竞态问题（登录用户刷新后被短暂踢到登录页），可以：

  1. 在 ProtectedRoute 中添加一个 isHydrated 状态检查
  2. 水合完成前显示 Loading 而非直接重定向
  3. 使用 Zustand 的 skipHydration + 手动触发水合
