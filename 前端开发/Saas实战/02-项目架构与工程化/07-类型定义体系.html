类型定义体系

类型定义体系

本步目标

建立统一的 TypeScript 类型定义，理解前端类型系统和 .NET DTO 体系的对应关系，并验证 Vite 代理配置确保所有后端服务可达。

前置知识

TypeScript 类型 vs C# DTO

TypeScriptC#说明
interface ApiResult<T>class Result<T>统一响应包装
interface PagedResult<T>class PagedResult<T>分页查询结果
interface CurrentUserclass CurrentUser当前用户信息
interface MenuDtoclass MenuDto菜单传输对象
const MENU_TYPEenum MenuType枚举常量
type MenuType = typeof MENU_TYPE[keyof typeof MENU_TYPE]enum MenuType从常量对象派生联合类型

关键区别：TypeScript 类型在编译后被擦除

C# 的 DTO 类在运行时仍然存在——你可以用反射读取属性、序列化为 JSON、做数据验证。TypeScript 的接口只在编译时存在，编译为 JavaScript 后完全消失。这意味着：

  1. TypeScript 接口不能做运行时验证——需要用 Zod 等库做 schema 验证
  2. TypeScript 类型不需要考虑包体积——1000 个接口定义不会增加 JS 文件大小
  3. 所以我们把所有类型放在一个 types/index.ts 文件中，而不是按模块拆分

.NET 类比：就像 C# 的 record 类型——纯数据载体，没有行为。但 C# 的 record 在运行时仍然存在，TypeScript 的 interface 不存在。

代码讲解

ApiResult<T> — 统一响应格式

export interface ApiResult<T = unknown> {
  code: number       // 业务状态码，0 = 成功
  message: string    // 响应消息
  success: boolean   // 是否成功
  data?: T           // 响应数据
}

这是所有 API 请求的统一返回格式。createHttp 的 get/post/put/del 方法都返回 Promise<ApiResult<T>>，调用方通过 res.data 获取实际数据。

.NET 类比：这就像 .NET 的 Result<T> 模式——Success 对应 success: true，Data 对应 data，ErrorMessage 对应 message。区别在于 .NET 的 Result 通常用 OneOf/ discriminated union 实现，而前端用 { success, data } 扁平结构。

PagedResult<T> — 分页查询

export interface PagedResult<T> {
  items: T[]         // 当前页数据
  totalCount: number // 总记录数
  page: number       // 当前页码
  pageSize: number   // 每页条数
}

.NET 类比：完全对应 .NET 的 PagedResult<T> / PaginatedList<T>。page 对应 PageIndex，pageSize 对应 PageSize，totalCount 对应 TotalCount。

MENU_TYPE — 从常量对象派生联合类型

export const MENU_TYPE = {
  Directory: 0,
  Menu: 1,
  Button: 2,
  ExternalLink: 3,
} as const

export type MenuType = (typeof MENU_TYPE)[keyof typeof MENU_TYPE]
// 等价于: type MenuType = 0 | 1 | 2 | 3

为什么不直接用 TypeScript 的 enum？

  1. TypeScript enum 的坑：数字枚举会产生反向映射（MENU_TYPE[0] = "Directory"），增加运行时代码
  2. as const 常量对象：零运行时开销，TypeScript 自动推导字面量类型
  3. 与后端对齐：后端返回的是数字（0/1/2/3），常量对象的值也是数字，天然对应

.NET 类比：C# 的 enum MenuType { Directory = 0, Menu = 1, Button = 2, ExternalLink = 3 }。TypeScript 用 as const 对象 + 派生类型实现了相同的效果，但没有反向映射的运行时开销。

CurrentUser — JWT Claims 的前端映射

CurrentUser 接口中的组织上下文字段（primaryCompanyName、primaryOrgUnitName 等）来自 JWT Token 的 Claims。登录后前端解码 JWT，提取这些 Claims 填充到 CurrentUser 对象中。

.NET 类比：这就像 HttpContext.User.Claims 的映射——后端从 JWT 中读取 Claims，填充到 CurrentUser DTO 中返回给前端。

MenuDto 的树形嵌套

export interface MenuDto {
  id: string
  name: string
  children: MenuDto[]  // ← 递归引用自身
}

MenuDto 通过 children: MenuDto[] 实现无限层级的树形结构。后端返回的是扁平列表，前端需要自己构建树（或者后端直接返回树形结构）。

.NET 类比：这和 .NET 中 List<MenuDto> 的树形结构完全相同——Children 属性引用自身类型。

Vite Proxy — 请求路由映射

浏览器请求                   Vite Proxy              后端服务
───────────                 ─────────              ────────
/sso-api/users     ──→     :10001/users     (SSO 服务)
/perm-api/roles    ──→     :10002/roles     (权限中心)
/gw-api/routes    ──→     :10000/routes    (API 网关)
/file-api/files   ──→     :10011/files     (文件服务)
/print-api/jobs   ──→     :11010/jobs      (打印服务)
/notify-api/...   ──→     :10012/...       (通知中心)
/ops-api/...      ──→     :10013/...       (租户运营)
/connect/token    ──→     :10001/connect/token  (OIDC 端点，不 rewrite)
/hubs/notify      ──→     :10012/hubs/notify   (SignalR，ws: true)

rewrite 函数的作用是去掉 URL 中的前缀。例如 /sso-api/users → http://moklgy.me:10001/users（去掉了 /sso-api）。但 /connect/token 不需要 rewrite，因为后端的 OIDC 端点路径就是 /connect/token。

踩坑提醒

  1. as const 不能漏。如果写成 { Directory: 0, Menu: 1 }（不加 as const），TypeScript 会把类型推导为 { Directory: number, Menu: number }，MenuType 就变成了 number 而不是 0 | 1 | 2 | 3，失去类型安全。

  2. ApiResult<T> 的 data 是可选的（data?: T）。某些 API（如删除操作）不返回 data，只有 { success: true, code: 0, message: "ok" }。调用方需要处理 data 可能为 undefined 的情况。

  3. Vite Proxy 只在开发环境生效。生产环境中前端是静态文件，不经过 Vite Dev Server，需要 Nginx 或其他反向代理做相同的路由转发。部署时必须配置 Nginx 的 location 块，规则与 Vite proxy 完全一致。

  4. /connect 和 /.well-known 不做 rewrite。这两个路径是 OIDC 标准端点，后端 OpenIddict 直接监听 /connect/token、/.well-known/openid-configuration 等路径。如果做了 rewrite（如去掉前缀），后端会 404。

  5. SignalR 的 /hubs 需要 ws: true。默认情况下 Vite proxy 不代理 WebSocket 请求。SignalR 使用 WebSocket 传输，必须设置 ws: true。

自测题

入门题

  1. ApiResult<T> 中 code 和 success 有什么区别？既然 code === 0 就表示成功，为什么还需要 success 字段？

  2. MENU_TYPE 为什么用 as const 常量对象而不是 TypeScript 的 enum？

进阶题

  1. 请解释 type MenuType = (typeof MENU_TYPE)[keyof typeof MENU_TYPE] 这个类型推导的过程。如果 MENU_TYPE 的值是字符串而非数字（如 { Directory: "directory" }），类型推导的结果是什么？

  2. Vite proxy 配置中，/connect 和 /sso-api 都代理到同一个后端（10001 端口），但 /connect 不做 rewrite 而 /sso-api 要做 rewrite。请解释原因。

架构题

  1. 当前所有类型定义都在 types/index.ts 一个文件中（2300+ 行）。有人建议按模块拆分为 types/auth.ts、types/perm.ts、types/menu.ts 等。请分析两种方案的优缺点，并给出你的选择和理由。

  2. ApiResult<T> 是前端的统一响应格式，但并非所有后端 API 都遵守这个格式（如 OIDC 端点返回原生格式）。createHttp 的响应拦截器会自动包裹非标准响应。请评价这个设计的优缺点——如果让你重新设计，你会怎么处理响应格式不一致的问题？
