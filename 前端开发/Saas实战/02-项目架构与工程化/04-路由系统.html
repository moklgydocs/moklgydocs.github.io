路由系统

路由系统

这一步解决什么问题？
SPA 应用的页面跳转不是靠后端路由，而是靠前端路由。本文将实现 React Router v7 的路由配置，包含懒加载、嵌套路由、路由守卫和默认重定向——让应用知道"访问 /auth/users 时该渲染什么组件"。

对于 ASP.NET Core 开发者来说，前端路由就是 app.MapGet() 的客户端版本——<Route path="/users" /> 对应 MapGet("/users", ...)，<ProtectedRoute> 对应 [Authorize] 特性，<Outlet /> 对应 @RenderBody()。

前置知识

React Router vs ASP.NET Core Endpoint Routing

概念React RouterASP.NET Core
路由定义<Route path="/users" />app.MapGet("/users", ...)
路由守卫<ProtectedRoute> 包裹[Authorize] 特性
嵌套路由<Route> 嵌套 <Route>Area / RouteGroup
布局复用<Outlet /> 渲染子路由@RenderBody()
懒加载lazy(() => import(...))Assembly.Load() 按需加载
重定向<Navigate to="/xxx" replace />RedirectResult

懒加载的必要性

SPA 打包后所有页面代码都在一个 JS 文件中，首屏加载很慢。React.lazy() + import() 实现按需加载——用户访问 /auth/users 时才下载用户管理页面的代码。

.NET 类比：就像 ASP.NET Core 的 Assembly.Load() 按需加载插件程序集。用户访问某个功能时才加载对应的 DLL，而不是启动时加载所有 DLL。

代码实现

src/components/layout/protected-route.tsx

import { Navigate, useLocation } from "react-router-dom"
import { useAuthStore } from "@/stores/auth-store"

/**
 * 路由保护组件
 *
 * 包裹需要认证才能访问的路由，未登录用户会被重定向到登录页。
 * 对于多租户用户，若尚未选择租户，则引导至租户选择页。
 *
 * @param children - 受保护的子组件
 */
export function ProtectedRoute({ children }: { children: React.ReactNode }) {
  const isAuthenticated = useAuthStore((s) => s.isAuthenticated)
  const currentTenantId = useAuthStore((s) => s.currentTenantId)
  const availableTenants = useAuthStore((s) => s.availableTenants)
  const location = useLocation()

  // 未认证 → 跳转登录页，保留来源路径以便登录后回跳
  if (!isAuthenticated) {
    return <Navigate to="/login" state={{ from: location }} replace />
  }

  // 多租户用户尚未选择租户 → 引导到租户选择页
  if (availableTenants && availableTenants.length > 1 && !currentTenantId) {
    return <Navigate to="/select-tenant" replace />
  }

  return <>{children}</>
}

/** 包裹懒加载组件，统一 Suspense */
function Lazy({ children }: { children: React.ReactNode }) {
  return <Suspense fallback={<PageLoader />}>{children}</Suspense>

代码讲解

路由结构的四层嵌套

BrowserRouter（路由根容器）
  ├── /login           → 公开页面（无布局、无守卫）
  ├── /select-tenant   → 公开页面（无布局、无守卫）
  ├── 受保护路由        → ProtectedRoute + AppLayout
  │   ├── /            → DashboardPage（index 路由）
  │   ├── /auth/*      → 认证中心子路由
  │   ├── /perm/*      → 权限中心子路由
  │   └── ...          → 其他模块子路由
  └── /*               → 404 兜底，重定向到首页

.NET 类比：

  • BrowserRouter = app.MapControllers()
  • ProtectedRoute = [Authorize] 特性
  • AppLayout + <Outlet /> = _Layout.cshtml + @RenderBody()
  • <Route path="*" /> = app.UseStatusCodePagesWithReExecute("/")

为什么登录页和租户选择页是静态导入？

// 静态导入——这些页面是首屏必须的
import LoginPage from "@/pages/login"
import SelectTenantPage from "@/pages/select-tenant"

// 懒加载——其他页面按需加载
const DashboardPage = lazy(() => import("@/pages/dashboard"))

登录页是用户看到的第一个页面，如果懒加载它，用户会看到一个"加载中..."的白屏闪烁。租户选择页同理——用户登录后立即需要选择租户。其他页面可以懒加载，因为用户不会在页面加载的瞬间同时访问所有功能。

【性能陷阱】 React.lazy() 会在首次渲染时触发网络请求下载 chunk。如果 10 个懒加载组件在首屏同时渲染（如仪表盘页面加载了 10 个子模块），浏览器会同时发起 10 个请求。虽然 HTTP/2 支持多路复用，但过多的并发请求仍可能导致首屏卡顿。Vite 默认的代码分割策略是每个动态 import() 生成一个 chunk，你可以通过 vite.config.ts 的 build.rollupOptions.output.manualChunks 合并相关模块。

🤔 导师提问：假设你的 SPA 有 100 个页面，其中 90 个是管理后台页面，只有 10 个是用户常用的。如果把所有页面都懒加载，用户每次点新菜单都要等一次网络请求。你会如何平衡"首屏加载速度"和"页面切换速度"？

嵌套路由中的 <Outlet /> 是什么？

<Outlet /> 是 React Router 的"插槽"——它标记了子路由应该渲染的位置。当用户访问 /auth/users 时，渲染流程是：

AppLayout
  ├── AppSidebar（侧边栏，始终显示）
  ├── AppHeader（顶栏，始终显示）
  └── <main>
       └── <Outlet />  ← 这里渲染 AuthUsersPage
      </main>

.NET 类比：<Outlet /> = @RenderBody()。AppLayout = _Layout.cshtml，子页面 = 各个 View。

默认重定向的三种模式

模式 1：<Route index> 指向具体页面

<Route path="gateway">
  <Route index element={<Lazy><GatewayDashboardPage /></Lazy>} />

访问 /gateway 时直接显示仪表盘页面。

模式 2：<Navigate> 重定向到子路径

<Route path="auth">
  <Route index element={<Navigate to="/auth/users" replace />} />

访问 /auth 时自动跳转到 /auth/users。replace 表示替换浏览器历史记录，用户按"后退"不会回到 /auth。

模式 3：动态参数

<Route path="tenants/:id" element={<Lazy><OpsTenantDetailPage /></Lazy>} />

:id 是动态参数，在组件中用 useParams() 获取。

配置中心的路由传参

<Route path="perm-center" element={<Lazy><ConfigPage serviceBaseUrl="/perm-api" serviceLabel="权限中心" /></Lazy>} />

ConfigPage 是一个通用配置页面组件，通过 props 接收不同的服务 URL 和标签。这是一种"一个组件 + 多个路由"的设计——类似后端的一个 Controller 方法处理多个路由。

【设计取舍】 配置中心的 5 个路由都用 ConfigPage 组件 + props 区分服务。优点：只维护一个组件，减少重复代码。缺点：如果某个服务的配置页需要特殊字段或交互，props 传参会越来越复杂，最终变成"万能组件"。当差异超过 30% 时，应该拆分为独立组件。

【易错点】 <Navigate> 中的 replace 属性。不写 replace 时，重定向会在浏览器历史中留下两条记录（原路径 + 目标路径），用户按后退会触发无限重定向。加上 replace 后只保留一条记录——这一点在嵌套路由的默认重定向中尤其重要，因为用户不会想按"后退"回到 /auth 这个空路径。

🤔 导师提问：当前所有路由都在 App.tsx 一个文件中定义。如果项目扩展到 100 个路由，这个文件会变得难以维护。你会如何拆分？提示：想想 .NET 中 app.MapControllers() 是自动扫描程序集的——前端有没有类似的"约定大于配置"的方案？

Lazy 包装组件

function Lazy({ children }: { children: React.ReactNode }) {
  return <Suspense fallback={<PageLoader />}>{children}</Suspense>
}

每次使用懒加载组件都需要 <Suspense> 包裹，Lazy 组件避免重复写 <Suspense fallback={...}>。统一使用 PageLoader 作为加载中状态。

踩坑提醒

  1. lazy() 的回调必须返回 { default: Component } 格式。如果页面组件用 export default 导出，import() 会自动包装为这个格式。但如果用命名导出（export function XxxPage()），需要手动包装：lazy(() => import("@/pages/xxx").then(m => ({ default: m.XxxPage })))。

  2. <Navigate> 中的 replace 属性。不写 replace 时，重定向会在浏览器历史中留下两条记录（原路径 + 目标路径），用户按后退会触发无限重定向。加上 replace 后只保留一条记录。

  3. <Route element={...}> 和 <Route> 的区别。有 element 的 Route 会渲染组件，没有 element 的 Route 只做路径匹配。受保护路由的外层 <Route element={<ProtectedRoute><AppLayout /></ProtectedRoute>}> 只渲染布局和守卫，不渲染具体页面——页面由子 Route 的 <Outlet /> 承载。

  4. 路由参数 :id 和查询参数 ?key=value 是不同的。路由参数用 useParams() 获取，查询参数用 useSearchParams() 获取。不要混淆。
