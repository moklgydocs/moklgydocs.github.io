启动与验证

启动与验证

这一步解决什么问题？

项目搭好了，但还不能跑。我们需要启动开发服务器，验证一切工作正常，同时了解 React 19 的重要变化和 React Compiler 的作用。这就像 ASP.NET Core 项目中写好 Program.cs 后第一次 dotnet run——如果看到欢迎页，说明基础设施配好了。

前置知识

React 19 的变化

如果我们之前用过 React 18，注意以下变化：

1. 不再需要 import React

React 17 引入的新 JSX Transform（react-jsx）让我们不再需要在每个组件文件顶部写 import React from "react"。React 19 默认使用新 JSX Transform。

// React 16 及更早（旧 JSX Transform，必须手动导入）
import React from "react"           // ← 必须的，否则 JSX 编译报错
function App() {
  return <div>Hello</div>
}

// React 17+（新 JSX Transform，自动处理）
// import React from "react"        // ← 不需要了
function App() {
  return <div>Hello</div>
}

⚠️ 【易错点】：如果我们在代码中用了 React.useState、React.useEffect 等写法，仍然需要导入 React。只是 JSX 语法本身不再需要导入。

2. ref 作为 prop

React 19 中，函数组件可以直接接收 ref 作为 prop，不再需要 forwardRef：

// React 18：需要 forwardRef
const Input = React.forwardRef(function Input(props, ref) {
  return <input ref={ref} {...props} />
})

// React 19：ref 就是普通 prop
function Input({ ref, ...props }: InputProps) {
  return <input ref={ref} {...props} />
}

🤔 导师提问：forwardRef 在 React 19 中被废弃了，但 shadcn/ui 生成的组件代码中仍有 React.forwardRef——这些组件还能用吗？提示：React 19 仍然支持 forwardRef（向后兼容），只是不再需要了。shadcn/ui 后续版本会更新生成代码。

3. use() Hook

React 19 新增的 use() Hook，可以在渲染期间读取 Promise 和 Context：

// 以前：需要 useEffect + useState 来处理异步数据
// 现在：可以在渲染中直接 use() 一个 Promise
function UserProfile({ userPromise }: { userPromise: Promise<User> }) {
  const user = use(userPromise)  // React 会 suspend 直到 Promise resolve
  return <div>{user.displayName}</div>
}

⚠️ 【易错点】use() 必须在组件顶层调用，不能在条件语句或循环中使用（和所有 Hooks 一样）。另外，use(Promise) 必须有 <Suspense> 包裹，否则 Promise reject 时会抛出未捕获的错误。

💡 类比后端：use() 类似 C# 的 await——在异步操作完成前"暂停"当前函数。但 React 的"暂停"不会阻塞线程，而是挂起渲染，数据就绪后自动恢复。

🤔 导师提问：use() 和 async/await 都能处理异步数据，它们最大的区别是什么？提示：async/await 返回的是 Promise，而 use() 返回的是数据本身——在 React 的渲染函数里，能用 await 吗？React 组件的 render 函数不能是 async 的，这是 React 的设计约束。

4. React Compiler

React Compiler 自动优化重渲染，减少手动 useMemo/useCallback：

// 没有 React Compiler：需要手动优化
function SearchResults({ query, data }) {
  const filtered = useMemo(() => data.filter(item => item.name.includes(query)), [query, data])
  return <List items={filtered} />
}

// 有 React Compiler：不需要手动优化
function SearchResults({ query, data }) {
  const filtered = data.filter(item => item.name.includes(query))  // Compiler 自动 memoize
  return <List items={filtered} />
}

💡 类比后端：React Compiler 类似 .NET 的 Tiered Compilation——自动优化性能热点，不需要开发者手动标注。

⚠️ 【性能陷阱】：React Compiler 不是万能的。以下情况它无法自动优化：

  • 带副作用的计算（如修改外部变量、操作 DOM）
  • 依赖 this 的计算
  • 使用 arguments 对象的函数
  • 含 eval 或 new Function 的代码

AdminWeb 通过 babel-plugin-react-compiler 启用了 React Compiler，但我们仍需理解其局限性——就像 .NET 的 JIT 优化也不会覆盖所有场景。

🤔 导师提问：React Compiler 无法优化"带副作用的计算"——什么样的算作"副作用"？修改 DOM 算吗？发起网络请求算吗？console.log 算吗？类比后端：纯函数和副作用的概念，在 C# 的 LINQ 中也有体现——Where 是纯函数，ForEach 可能有副作用。

项目审视：AdminWeb 的环境搭建

做得好的地方

  1. React Compiler 已启用：通过 babel-plugin-react-compiler 自动优化重渲染
  2. Vite 8 + Rolldown：使用最新的构建引擎，构建速度极快
  3. 手动 chunk 分割：将 AG Grid、React 核心、UI 库、SignalR 分别打包，优化加载性能
  4. pnpm + corepack：规范的包管理

🤔 导师提问：AdminWeb 将依赖拆成多个 chunk（AG Grid、UI 库、SignalR 等），chunk 拆得越细越好吗？如果拆成 100 个小 chunk，和只拆 3 个大 chunk，各有什么问题？类比后端：微服务拆分的粒度权衡。

可以改进的地方

  1. 缺少 .env 环境变量管理：API 地址硬编码在 vite.config.ts 中，应使用环境变量
  2. 缺少 Prettier：ESLint 只做语法检查，没有统一格式化风格

改进建议：

# .env.development
VITE_SSO_API_URL=http://moklgy.me:10001
VITE_PERM_API_URL=http://moklgy.me:10002

💡 类比后端：VITE_ 前缀的环境变量类似 appsettings.Development.json 中的配置。Vite 只暴露以 VITE_ 开头的变量给客户端代码，避免敏感信息泄露——类似 ASP.NET Core 不会把 ConnectionStrings 暴露给前端。

踩坑提醒

  1. StrictMode 在开发模式下会让组件渲染两次：这是 React 的有意设计，用于检测副作用。不要因为看到"组件执行了两次"而困惑——这只在开发模式发生，生产模式不会。
  2. pnpm dev 必须在项目根目录执行：不在包含 package.json 的目录下执行会报错。类比 dotnet run 必须在 .csproj 所在目录。
  3. 修改 vite.config.ts 后需要重启开发服务器：Vite 不会热重载配置文件变更。按 Ctrl+C 停止再重新 pnpm dev。
  4. 停止开发服务器：按 Ctrl+C 停止。不要直接关闭终端窗口，否则端口可能不会立即释放。
  5. 构建生产版本：pnpm build 生成 dist/ 目录，这是部署到服务器的文件。pnpm preview 可以本地预览生产版本。

  1. cn() 函数中 clsx 和 twMerge 各自解决什么问题？为什么顺序不能反？
  2. React 19 中 ref 作为 prop 的变化，对我们写组件有什么实际影响？

推理级

  1. 如果两个组件使用 cn() 传入了矛盾的 Tailwind 类（如 text-red-500 和 text-blue-500），最终结果是什么？这与 CSS 的层叠规则有什么关系？
  2. React Compiler 能自动优化大部分重渲染场景，但哪些情况下它无法覆盖？如果我们依赖了 Compiler 但某个组件没有被优化，会有什么后果？

动手级

  1. 在 src/lib/utils.ts 中只保留 clsx 不用 twMerge，然后在组件中测试 cn("px-2", "px-4") 的输出，观察差异。
  2. 启动项目后，打开浏览器 DevTools 的 Network 面板，观察修改 App.tsx 后哪些网络请求被触发，验证 HMR 的"只更新变更模块"机制。

验证步骤

🔍 验证步骤

  1. 在项目根目录下执行 pnpm dev，确认启动成功（终端显示 Local: http://localhost:3000/）

  3. 打开 DevTools → Console，不应有红色错误
  4. 打开 DevTools → Network，刷新页面，确认 main.tsx 和 App.tsx 被加载为 ESM 模块（Type 为 module）
  5. 修改 App.tsx 中的文字，保存，确认页面自动更新（HMR 验证）
  6. 点击主题切换按钮（如果有），确认亮暗模式切换正常
