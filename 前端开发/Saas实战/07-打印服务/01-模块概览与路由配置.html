01 - 模块概览与路由配置

这一步解决什么问题？ 我们要搭建打印服务模块的骨架——路由和独立的 HTTP 客户端。打印服务与其他模块最大的不同是：报表渲染可能需要几十秒，默认的 15s 超时会直接中断请求。理解为什么需要独立的 HTTP 客户端，是这一步的核心。

前置知识

  • React Router 路由配置（<Route>、lazy、Navigate）
  • createHttp 工厂函数的用法（权限中心、文件服务已用过）
  • Vite 代理配置（vite.config.ts 中的 proxy）
  • 面包屑映射（breadcrumbs.ts）

代码实现

App.tsx 路由配置

以下代码来自 AdminWeb/src/App.tsx：

// 打印服务
const PrintTemplatesPage = lazy(() => import("@/pages/print/templates"))
const PrintJobsPage = lazy(() => import("@/pages/print/jobs"))
const PrintDatasourcesPage = lazy(() => import("@/pages/print/datasources"))

// ... 在路由树中：

          {/* 打印服务 /print/* */}
          <Route path="print">
            <Route index element={<Navigate to="/print/templates" replace />} />
            <Route path="templates" element={<Lazy><PrintTemplatesPage /></Lazy>} />
            <Route path="datasources" element={<Lazy><PrintDatasourcesPage /></Lazy>} />
            <Route path="jobs" element={<Lazy><PrintJobsPage /></Lazy>} />

【设计取舍】 三个子路由都用 Lazy 包裹实现代码分割，首屏不加载打印模块的 JS。这和权限中心、文件服务的做法一致——模块级懒加载是 AdminWeb 的统一策略。为什么不把整个 /print/* 做成一个嵌套 layout + Outlet？因为打印服务的三个页面共享同一套侧边栏布局（AppLayout），不需要额外的 layout 层。

HTTP 客户端

以下代码来自 AdminWeb/src/api/print/http.ts：

// PrintService 模块 HTTP 客户端
// 代理路径：/print-api/* → http://localhost:11010/*
import { createHttp } from "@/lib/create-http"

/** 打印服务 HTTP 客户端，基础路径为 /print-api，超时 120s（报表渲染耗时长） */
const printHttp = createHttp("/print-api")

/** 设置打印服务默认超时为 120s（FastReport 渲染可能超过 15s） */
printHttp.instance.defaults.timeout = 120000

/** 导出常用 HTTP 方法 */
export const { get, post, put, del } = printHttp
/** 导出 axios 实例，供需要自定义配置（如 responseType）的场景使用 */
export default printHttp.instance

模板 API（templates.ts）

以下代码来自 AdminWeb/src/api/print/templates.ts：

import { get, post, put, del, default as instance } from "./http"
import type {
  ReportTemplateListDto,
  ReportTemplateDetailDto,
  CreateTemplateInput,
  UpdateTemplateInput,
} from "@/types"

/** 报表模板 API，用于管理打印报表模板的完整生命周期 */
export const templatesApi = {
  /**
   * 查询报表模板列表（分页）
   * @param params 查询参数
   * @param params.keyword 搜索关键词
   * @param params.category 模板分类筛选
   * @param params.status 模板状态筛选
   * @param params.skipCount 跳过条数
   * @param params.maxResultCount 每页最大条数
   */
  list(params: {
    keyword?: string
    category?: string
    status?: number
    skipCount?: number
    maxResultCount?: number
  }) {
    return get<{ items: ReportTemplateListDto[]; totalCount: number }>(
      "/api/print/templates",
      params as Record<string, unknown>
    )
  },

  /**
   * 获取模板详情（含 FrxContent 模板文件内容）
   * @param id 模板 ID
   */
  detail(id: string) {
    return get<ReportTemplateDetailDto>(`/api/print/templates/${id}`)
  },

  /**
   * 创建报表模板
   * @param data 模板创建请求数据
   */
  create(data: CreateTemplateInput) {
    return post<ReportTemplateDetailDto>("/api/print/templates", data)
  },

  /**
   * 更新模板元数据（名称、描述、分类等）
   * @param id 模板 ID
   * @param data 模板更新请求数据
   */
  update(id: string, data: UpdateTemplateInput) {
    return put<ReportTemplateDetailDto>(`/api/print/templates/${id}`, data)
  },

  /**
   * 删除模板（软删除）
   * @param id 模板 ID
   */
  delete(id: string) {
    return del<void>(`/api/print/templates/${id}`)
  },

  /**
   * 发布模板，使其可用于生成报表
   * @param id 模板 ID
   */
  publish(id: string) {
    return post<void>(`/api/print/templates/${id}/publish`)
  },

  /**
   * 归档模板，归档后不可用于生成报表
   * @param id 模板 ID
   */
  archive(id: string) {
    return post<void>(`/api/print/templates/${id}/archive`)
  },

  /**
   * 导入 .frx 模板文件（multipart/form-data 上传）
   * @param file FastReport .frx 模板文件
   */
  import(file: File) {
    const formData = new FormData()
    formData.append("file", file) // 将 .frx 文件追加到 FormData
    // 用 axios instance 直接发，支持 responseType
    return instance.post<ReportTemplateDetailDto>(
      "/api/print/templates/import",
      formData,
      { headers: { "Content-Type": "multipart/form-data" } }
    )
  },

  /**
   * 导出模板为 .frx 文件（Blob 下载）
   * @param id 模板 ID
   */
  exportFrx(id: string) {
    return instance.get(`/api/print/templates/${id}/export`, {
      responseType: "blob", // 以 Blob 方式接收 .frx 文件
    })
  },
}

【易错点】 注意 templatesApi.import 和 exportFrx 使用的是 instance（axios 原始实例），而不是 post / get 封装方法。因为 import 需要自定义 Content-Type: multipart/form-data，exportFrx 需要 responseType: "blob"。封装的 post/get 方法会自动处理 ApiResult<T> 的解包，但文件上传和下载不走这个逻辑。这就是 http.ts 同时导出 instance 的原因。

任务 API（jobs.ts）

以下代码来自 AdminWeb/src/api/print/jobs.ts：

import { get, post, default as instance } from "./http"
import type { PrintJobDto, RenderReportInput } from "@/types"

/** 打印任务 API，用于创建和管理报表渲染任务 */
export const jobsApi = {
  /**
   * 查询打印任务列表（分页）
   * @param params 查询参数
   * @param params.templateId 模板 ID 筛选
   * @param params.status 任务状态筛选
   * @param params.skipCount 跳过条数
   * @param params.maxResultCount 每页最大条数
   */
  list(params: {
    templateId?: string
    status?: number
    skipCount?: number
    maxResultCount?: number
  }) {
    return get<{ items: PrintJobDto[]; totalCount: number }>(
      "/api/print/jobs",
      params as Record<string, unknown>
    )
  },

  /**
   * 查询打印任务详情（可用于轮询异步任务状态）
   * @param id 任务 ID
   */
  detail(id: string) {
    return get<PrintJobDto>(`/api/print/jobs/${id}`)
  },

  /**
   * 渲染报表
   * - 同步模式（async=false/undefined）：直接返回文件流（Blob）
   * - 异步模式（async=true）：返回 jobId，后续通过 detail 轮询或 download 下载
   * @param input 渲染请求参数
   */
  render(input: RenderReportInput) {
    if (input.async) {
      // 异步模式：返回 { jobId, status }
      return post<{ jobId: string; status: number }>("/api/print/jobs/render", {
        ...input,
        async: true,
      })
    }
    // 同步模式：返回 blob 文件流
    return instance.post("/api/print/jobs/render", input, {
      responseType: "blob",
    })
  },

  /**
   * 下载异步渲染任务的结果文件
   * @param id 任务 ID
   */
  download(id: string) {
    return instance.get(`/api/print/jobs/${id}/download`, {
      responseType: "blob",
    })
  },

  /**
   * 获取下载地址（presigned URL 或 API 降级路径）
   * @param id 任务 ID
   * @returns { url: string, fileId?: string }
   */
  getDownloadUrl(id: string) {
    return get<{ url: string; fileId?: string }>(`/api/print/jobs/${id}/download-url`)
  },
}

【易错点】 jobsApi.render 是整个打印服务最特殊的 API：同一个 URL，根据 async 参数走两种完全不同的返回类型。同步模式返回 Blob（二进制文件流），异步模式返回 { jobId, status }（JSON）。这在 TypeScript 中需要用条件分支来区分，不能用统一的泛型返回。如果前端在同步模式下用 ApiResult<T> 解包 Blob 响应，会直接报 JSON 解析错误。

【设计取舍】 客户端渲染 vs 服务端渲染：AdminWeb 选择了服务端渲染——FastReport 在后端完成模板+数据的合并，输出 PDF/Excel 文件，前端只负责下载。为什么不做成前端渲染？因为 FastReport 是 .NET 生态的报表引擎，只能在服务端运行；而且服务端渲染可以利用后端的计算资源，不会阻塞用户的浏览器。

代码讲解

我们在前面篇章中已经掌握了权限中心、API 网关、文件服务三大模块。这一章，我们进入一个业务特性更丰富的模块 —— 打印服务。

打印服务解决什么问题？在企业 SaaS 系统中，报表打印是刚需：采购订单、销售合同、财务报表……我们不可能为每种报表硬编码一个导出逻辑。打印服务将模板设计、数据获取、渲染输出三者解耦：

┌─────────────┐     ┌─────────────────┐     ┌──────────────┐
│  模板管理    │     │  数据源管理       │     │  任务管理     │
│  (.frx文件)  │────→│  (JSON/HTTP/DB/XML)│────→│  (渲染+下载)  │
└─────────────┘     └─────────────────┘     └──────────────┘
       ↓                      ↓                      ↓
  设计器编辑              连接测试/预览          同步/异步渲染
  导入导出                参数注入              轮询状态

ASP.NET Core 类比：

打印服务概念ASP.NET Core 对应说明
模板（Template）Razor 视图（.cshtml）定义报表的布局和样式
数据源（DataSource）DbContext / HttpClient提供渲染所需的数据
渲染任务（Job）后台任务（BackgroundService）执行模板+数据的合并输出
HTTP 客户端（printHttp）HttpClient 命名实例每个微服务独立的通信管道

核心差异：打印服务基于 FastReport 引擎（.frx 格式），不是 Razor。前端只负责管理模板元数据和触发渲染，模板设计器是独立的 Web 应用。

🤔 导师提问：在 ASP.NET Core 中，我们会用 IHttpClientFactory 创建命名客户端来隔离不同服务的配置（超时、基址等）。React 项目里没有工厂模式，我们用什么方式实现同样的隔离？先想一想，下文揭晓。

打印服务整体架构

打印服务是一个独立的微服务，不和网关共享入口。前端通过 Vite 代理将请求转发到打印服务后端，后端使用 FastReport 引擎渲染报表。整个请求链路如下：

┌──────────┐     ┌────────────┐     ┌─────────────┐     ┌──────────┐
│  React   │     │  Vite Dev  │     │  Print API  │     │ FastReport│
│  前端    │────→│  Server    │────→│  (端口11010) │────→│  渲染引擎 │
│          │     │  代理      │     │             │     │          │
└──────────┘     └────────────┘     └─────────────┘     └──────────┘
     │                  │                    │
     │  /print-api/*    │  去掉前缀转发      │  /api/print/*
     │─────────────────→│──────────────────→│
     │                  │                    │
     │  /prt/*          │  保留前缀转发      │  /prt/*
     │─────────────────→│──────────────────→│  (报表预览iframe)
     │                  │                    │
     │  /_fr/*          │  保留前缀转发      │  /_fr/*
     │─────────────────→│──────────────────→│  (FastReport设计器)

【易错点】 打印服务使用独立的 base URL /print-api，而不是统一的网关 /gw-api。这是因为打印服务端口是 11010，而网关端口是 10000，两者是完全独立的微服务。如果误把打印 API 写成 /gw-api/print/...，请求会被代理到网关，网关找不到对应路由会返回 404。

【易错点】 /prt 和 /_fr 两个代理路径不重写前缀（没有 rewrite），因为打印服务后端的 FastReport 设计器和预览页面内部引用了 /prt 和 /_fr 路径下的静态资源。如果重写前缀，这些内部引用会全部 404。

模块架构

打印服务前端模块分为三层：

src/
├── api/print/           ← API 层：封装与后端的所有通信
│   ├── http.ts          ← 独立 HTTP 客户端（baseURL=/print-api，超时120s）
│   ├── templates.ts     ← 模板 API
│   ├── datasources.ts   ← 数据源 API
│   └── jobs.ts          ← 任务 API
├── pages/print/         ← 页面层：三个管理页面
│   ├── templates/       ← 模板管理（CRUD + 导入导出 + 渲染预览）
│   ├── datasources/     ← 数据源管理（CRUD + 连接测试 + 数据预览）
│   └── jobs/            ← 任务管理（渲染 + 状态轮询 + 下载）
└── types/index.ts       ← 类型层：枚举 + DTO + Input

🤔 导师提问：为什么 api/print/ 目录下有四个文件而不是一个？回顾一下权限中心的 api/perm/ 目录，它是怎么组织的？把所有 API 写在一个文件里和按资源拆分，各有什么优缺点？

为什么打印服务需要独立的 HTTP 客户端？

其他模块（权限中心、文件服务）共享默认的 15s 超时。但报表渲染是个CPU 密集型操作 —— FastReport 渲染一个复杂报表可能需要 30s 甚至更久。如果使用默认超时，渲染请求会被提前中断。

普通 API 请求：  ──→ 200ms ←── 正常
报表渲染请求：   ──→ 15s ←── 超时！
报表渲染请求：   ──→ 45s ←── 120s 超时配置下正常完成

在 ASP.NET Core 中，我们会用 IHttpClientFactory.AddHttpClient("PrintApi", c => c.Timeout = TimeSpan.FromSeconds(120)) 来创建命名客户端。在 React 中，我们用 createHttp 工厂函数实现同样的效果——每个微服务创建独立的 axios 实例，各自配置超时和 base URL。

【性能陷阱】 报表渲染任务可能是长时间运行的。即使设置了 120s 超时，如果用户一次渲染 50 页以上的复杂报表，仍可能超时。对于这类场景，打印服务提供了异步渲染模式：前端先拿到 jobId，然后轮询任务状态，完成后再下载文件。我们在 jobs API 中会详细讲解。

路由设计

打印服务的路由采用前缀分组，和之前模块一样的模式：

/print              → 重定向到 /print/templates
/print/templates    → 模板管理页
/print/datasources  → 数据源管理页
/print/jobs         → 任务管理页

为什么默认跳转 templates 而不是 jobs？因为模板是起点 —— 没有模板就无法创建任务，模板管理是用户最常访问的入口。

踩坑提醒

  1. 打印 API 前缀不是 /gw-api：打印服务使用独立的 /print-api 前缀，不是统一的网关 /gw-api。如果误写成 /gw-api/print/...，请求会被代理到网关返回 404。
  2. HTTP 超时必须覆盖：createHttp 默认超时 15s，打印服务必须在 createHttp 之后手动设置 printHttp.instance.defaults.timeout = 120000，否则报表渲染会被提前中断。
  3. Vite 代理 rewrite 规则差异：/print-api 有 rewrite 去掉前缀，但 /prt 和 /_fr 不能加 rewrite，因为 FastReport 设计器和预览页内部引用了这些路径下的静态资源。
  4. Navigate 必须加 replace：/print 的 index 路由用 <Navigate to="/print/templates" replace />，不加 replace 用户按后退键会回到 /print 再跳转，形成循环。

自测题

  1. （概念级）：打印服务的 HTTP 客户端为什么要设置 120s 超时？如果不设置会怎样？

  2. （推理级）：createHttp 工厂内部已经包含了 Token 自动注入和 401 刷新逻辑。为什么打印服务不需要单独处理认证？如果打印服务后端部署在不同的域名下，withCredentials: true 还能正常工作吗？

  3. （推理级）：jobsApi.render 方法中，同步模式和异步模式返回的数据类型完全不同（Blob vs JSON）。这种"同一个 URL 根据参数返回不同类型"的设计，在 ASP.NET Core 中我们会怎么处理？提示：想想 IResult 和 Results<T1, T2> 。

  4. （动手级）：假设我们需要在浏览器中嵌入 FastReport 的报表预览页面（通过 iframe 加载 /prt/preview/{jobId}）。请尝试实现以下功能：

    • iframe 加载时显示 loading 状态，加载完成后隐藏
    • 考虑：iframe 加载的页面来自同一个 Vite 代理，是否存在跨域问题？如果打印服务部署到生产环境的独立域名下，需要怎么处理？
