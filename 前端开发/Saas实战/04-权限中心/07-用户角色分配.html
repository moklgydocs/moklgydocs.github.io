07 - 用户角色分配

07 - 用户角色分配

这一步解决什么问题？ 前面我们定义了权限、创建了角色、给角色分配了权限。但权限不会凭空生效——必须把角色分配给用户。就像 ASP.NET Core 里把用户加入 AspNetUserRoles 表一样，权限中心通过"用户角色分配"把用户和角色绑定起来。这一步要实现用户授权页面，包括 SSO 用户搜索、角色多选和全量覆盖保存。

前置知识

阅读本文档前，你需要了解：

  • 05-角色管理：角色的数据模型、按应用隔离、公开/私有属性
  • SSO 集成基础：AuthServer 的用户搜索 API、SsoUserPicker 组件的用法
  • 全量替换语义：PUT 的幂等性，与增量更新的区别
  • React 表单模式：受控组件、useEffect 初始化表单数据

一、ASP.NET Core 类比：用户角色分配 = AspNetUserRoles 表

在 ASP.NET Core Identity 里：

// ASP.NET Core: 把用户加入角色
await _userManager.AddToRoleAsync(user, "Manager");

// 查询用户的角色
var roles = await _userManager.GetRolesAsync(user);

// 数据库中的 AspNetUserRoles 表
// UserId | RoleId
// ------ | ------
// u-001  | r-manager
// u-001  | r-viewer
// u-002  | r-manager

权限中心的用户角色分配结构类似，但更复杂：

ASP.NET Core Identity             →    权限中心
─────────────────────            →    ──────────────
角色是全局的                       →    角色属于特定应用
一个用户可以属于多个角色            →    同上，但按应用分组
AddToRoleAsync（增量）             →    assign（全量覆盖）
GetRolesAsync 返回角色名列表       →    getByApp 返回用户+角色详情

🤔 导师提问：权限中心的 assign 是全量覆盖——每次保存发送用户应有的全部角色列表。而 ASP.NET Core 的 AddToRoleAsync 是增量操作——只添加一个角色。如果你用增量方式实现前端的角色分配，需要额外追踪"哪些角色是新增的、哪些是删除的"。全量覆盖为什么能避免这个问题？但全量覆盖有一个潜在风险——想想两个管理员同时修改同一用户的角色会怎样？

二、数据模型

2.1 用户及其角色

// src/types/index.ts

/** 用户及其角色信息（按应用分组） */
export interface UserWithRolesDto {
  userId: string
  userName: string | null
  displayName: string | null
  appCode: string         // 所属应用
  appName: string
  roles: RoleDto[]        // 已分配的角色列表
}

/** 分配用户角色请求 */
export interface AssignUserRolesRequest {
  userId: string
  appCode: string
  roleCodes: string[]     // 角色编码列表（全量覆盖）
}

2.2 API 层

// src/api/perm/user-roles.ts
export const userRolesApi = {
  /** 获取指定应用下所有用户及其角色分配情况 */
  getByApp(appCode: string) {
    return get<UserWithRolesDto[]>("/api/user-roles/by-app", { appCode })
  },

  /** 获取指定用户的角色分配详情 */
  getUserRoles(userId: string) {
    return get<UserRolesDto>(`/api/user-roles/${userId}`)
  },

  /** 为用户分配角色（全量覆盖） */
  assign(data: AssignUserRolesRequest) {
    return put<string>("/api/user-roles", data)
  },
}

// src/pages/perm/user-roles/index.tsx
export default function UserRolesPage() {
  const [apps, setApps] = useState<AppDto[]>([])
  const [selectedAppCode, setSelectedAppCode] = useState<string>("")
  const [data, setData] = useState<UserWithRolesDto[]>([])
  const [loading, setLoading] = useState(false)

  // 对话框状态
  const [assignOpen, setAssignOpen] = useState(false)
  const [editUser, setEditUser] = useState<UserWithRolesDto | null>(null)

  // 加载应用列表
  useEffect(() => {
    appsApi.getList().then((res) => {
      const list = res.data ?? []
      setApps(list)
      if (list[0]) setSelectedAppCode(list[0].code)
    }).catch(() => toast.error("获取应用列表失败"))
  }, [])

  /** 获取当前应用下的用户角色分配数据 */
  const fetchData = useCallback(async () => {
    if (!selectedAppCode) return
    setLoading(true)
    try {
      const res = await userRolesApi.getByApp(selectedAppCode)
      setData(res.data ?? [])
    } catch {
      toast.error("获取用户授权数据失败")
    } finally {
      setLoading(false)
    }
  }, [selectedAppCode])

  useEffect(() => { fetchData() }, [fetchData])

  const columns: AgColumn<UserWithRolesDto>[] = [
    {
      field: "userId",
      headerName: "用户",
      minWidth: 200,
      flex: 1,
      cellRenderer: ({ data }) => (
        <span className="text-sm">{data.displayName || data.userName || data.userId}</span>
      ),
    },
    {
      field: "roles",
      headerName: "已分配角色",
      minWidth: 200,
      flex: 2,
      cellRenderer: ({ data: item }) => (
        <div className="flex flex-wrap gap-1">
          {item.roles.length === 0 ? (
            <span className="text-sm text-muted-foreground">无角色</span>
          ) : (
            item.roles.map((role) => (
              <Badge key={role.code} variant="secondary">{role.name}</Badge>
            ))
          )}
        </div>
      ),
    },
    {
      field: "__actions__",
      headerName: "操作",
      width: 100,
      pinned: "right",
      cellRenderer: ({ data: item }) => (
        <Button variant="ghost" size="sm"
          onClick={() => { setEditUser(item); setAssignOpen(true) }}>
          <Pencil className="mr-1 h-3 w-3" />编辑
        </Button>
      ),
    },
  ]

  return (
    <div className="flex flex-col h-full">
      <PageToolbar
        title="用户授权"
        actions={
          <>
            <ToolbarButton icon={Plus} variant="primary"
              onClick={() => { setEditUser(null); setAssignOpen(true) }}
              disabled={!selectedAppCode}>
              授权用户
            </ToolbarButton>
            <ToolbarButton icon={RefreshCw} onClick={fetchData}>
              刷新
            </ToolbarButton>
          </>
        }
      />
      {/* 应用选择器 */}
      <div className="flex items-center gap-3">
        <span className="text-sm font-medium">选择应用：</span>
        <Select value={selectedAppCode} onValueChange={setSelectedAppCode}>
          <SelectTrigger className="w-64">
            <SelectValue placeholder="请选择应用" />
          </SelectTrigger>
          <SelectContent>
            {apps.map((app) => (
              <SelectItem key={app.code} value={app.code}>
                {app.name} ({app.code})
              </SelectItem>
            ))}
          </SelectContent>
        </Select>
      </div>
      <AgTable columns={columns} data={data} total={data.length}
        loading={loading} rowKey="userId" />
      <AssignRoleDialog
        open={assignOpen}
        onOpenChange={setAssignOpen}
        appCode={selectedAppCode}
        prefillUserId={editUser?.userId}
        prefillRoleCodes={editUser?.roles.map((r) => r.code)}
        onSuccess={fetchData}
      />
    </div>
  )
}

四、角色分配对话框

这是用户授权的核心——搜索 SSO 用户 + 角色多选。

4.1 SsoUserPicker 组件

新建模式下，需要从 AuthServer 搜索 SSO 用户。这是跨服务的搜索——权限中心代理调用 AuthServer 的用户搜索 API：

// src/pages/perm/user-roles/assign-role-dialog.tsx
export function AssignRoleDialog({
  open, onOpenChange, appCode,
  prefillUserId, prefillRoleCodes, prefillUserDisplay,
  onSuccess,
}: AssignRoleDialogProps) {
  const [roles, setRoles] = useState<RoleDto[]>([])
  const [userId, setUserId] = useState("")
  const [selectedUser, setSelectedUser] = useState<{
    userName: string; displayName?: string | null; email?: string | null
  } | null>(null)
  const [selected, setSelected] = useState<Set<string>>(new Set())
  const [loading, setLoading] = useState(false)
  const [saving, setSaving] = useState(false)

  // 打开时加载角色列表和预填充数据
  useEffect(() => {
    if (!open) return
    setUserId(prefillUserId ?? "")
    setSelectedUser(prefillUserDisplay ?? null)
    setSelected(new Set(prefillRoleCodes ?? []))
    setLoading(true)
    permRolesApi.getList(appCode)
      .then((res) => setRoles(res.data ?? []))
      .catch(() => toast.error("获取角色列表失败"))
      .finally(() => setLoading(false))
  }, [open, appCode])

  /** SSO 用户选择回调 */

> **🤔 导师提问**：对话框打开时，`useEffect` 会加载角色列表并回填已有角色。注意新建模式下 `selected` 初始为空集，编辑模式下从 `prefillRoleCodes` 填充。在 ASP.NET Core 中，打开编辑页面时你会在 `OnGet` 中从数据库查出角色列表并绑定到 ViewModel。React 的 `useEffect` + `useState` 和 Razor Page 的 `OnGet` + `ViewData`，在数据加载时机上有什么关键区别？提示：想想组件挂载前用户能看到什么。
  const handleUserSelect = (user: SsoUserSearchResult) => {
    setUserId(user.id)
    setSelectedUser({
      userName: user.userName,
      displayName: user.displayName,
      email: user.email,
    })
  }

  /** 清除已选用户 */
  const handleClearUser = () => {
    setUserId("")
    setSelectedUser(null)
  }

  /** 切换角色选中状态 */
  const toggle = (code: string) => {
    setSelected((prev) => {
      const next = new Set(prev)
      if (next.has(code)) next.delete(code)
      else next.add(code)
      return next
    })
  }

  /** 保存用户角色分配 */
  const handleSave = async () => {
    if (!userId.trim()) {
      toast.error("请选择用户")
      return
    }
    setSaving(true)
    try {
      await userRolesApi.assign({
        userId: userId.trim(),
        appCode,
        roleCodes: Array.from(selected),
      })
      toast.success("用户授权已保存")
      onSuccess()
      onOpenChange(false)
    } catch {
      toast.error("保存失败")
    } finally {
      setSaving(false)
    }
  }
  // ...
}

4.2 新建 vs 编辑模式

🤔 导师提问：编辑模式下用户不可更改（disabled），新建模式下可以搜索 SSO 用户。这和"应用管理"中 code 字段编辑时不可修改是同一个设计原则。在 ASP.NET Core 中，编辑 DTO 的主键字段通常也会被忽略（[ReadOnly(true)] 或不包含在 UpdateRequest 中）。为什么"实体的标识"在编辑时通常不可变？想想如果一个用户已经分配了角色，你把 userId 换成另一个人，原来那个人的角色会怎样？

功能新建模式编辑模式
用户选择可搜索 SSO 用户只读（用户不可更改）
角色选择多选（初始为空）多选（回填已有角色）
保存创建新授权覆盖已有授权
{/* 用户选择：编辑模式只读，新建模式可搜索 */}
<div className="space-y-2">
  <Label>选择用户 *</Label>
  {prefillUserId ? (
    // 编辑模式：只读显示
    <SsoUserPicker
      onSelect={handleUserSelect}
      selectedUserId={prefillUserId}
      selectedUserDisplay={selectedUser ?? { userName: prefillUserId }}
      disabled
    />
  ) : (
    // 新建模式：搜索选择
    <SsoUserPicker
      onSelect={handleUserSelect}
      selectedUserId={userId || undefined}
      selectedUserDisplay={selectedUser ?? undefined}
      onClear={handleClearUser}
    />
  )}
</div>

五、全量覆盖 vs 增量更新

用户角色分配使用全量覆盖策略：

// 保存时发送所有角色编码（而非只发送新增/删除的）
await userRolesApi.assign({
  userId: "u-001",
  appCode: "mok-erp-service",
  roleCodes: ["manager", "viewer"],  // 完整列表
})

后端处理逻辑：

  1. 查出该用户在当前应用下的所有旧角色
  2. 计算差集：需要新增的角色、需要删除的角色
  3. 执行新增和删除操作

💡 ASP.NET Core 类比：这就像 UserManager.AddToRolesAsync() + UserManager.RemoveFromRolesAsync() 的组合——前端只关心"最终状态"，后端负责计算增量。

为什么选择全量覆盖？

  • 前端逻辑简单——不需要追踪哪些角色是新增的、哪些是删除的
  • 避免并发冲突——如果两个管理员同时修改同一用户的角色，增量更新可能导致数据不一致
  • 幂等性——同样的请求执行多次，结果一样

🤔 导师提问：全量覆盖保证幂等性——同样的请求执行多次结果一样。在 ASP.NET Core 中，PUT 语义就是幂等的（全量替换），POST 语义是非幂等的（新增资源）。注意 userRolesApi.assign 用的是 put 方法而非 post。这和 HTTP 语义一致吗？如果用 POST /api/user-roles/incremental 做增量更新，POST 的非幂等性会带来什么问题？

六、数据流：从 SSO 到权限生效

1. 管理员在"用户授权"页面搜索 SSO 用户
       │
       ▼
2. SsoUserPicker → AuthServer API → 返回用户列表
       │
       ▼
3. 管理员选择用户 + 勾选角色 → 保存
       │
       ▼
4. userRolesApi.assign() → PermCenter 后端
       │
       ▼
5. PermCenter 写入 UserRoles 表
       │
       ▼
6. 用户下次请求 → JWT 包含新角色 → 菜单/权限生效

🤔 导师提问：第 6 步说"用户下次请求"时权限才生效。这意味着角色分配保存后，用户的当前会话不会立即拥有新权限——需要下次请求（通常是刷新页面或新请求）时才会生效。在 ASP.NET Core 中，如果你修改了用户的 Claims，当前的 ClaimsPrincipal 也不会立即更新——需要重新签发 Token 或刷新 Cookie。前端的"刷新即生效"和后端的"重新签发 Token"是同一个机制吗？

踩坑提醒

  1. 编辑模式下用户不可更改：如果用户已分配了角色，编辑时更换 userId 会导致原来那个用户的角色关联丢失，新用户的角色关联被错误创建。所以编辑模式下用户字段必须设为 disabled。
  2. 权限生效需要刷新会话：角色分配保存后，用户的当前 JWT Token 不包含新角色信息。需要用户重新登录或刷新页面，后端重新签发 Token 后权限才生效。前端无法强制刷新用户的 Token，只能提示用户"请刷新页面"。
  3. 全量覆盖的 PUT 语义：userRolesApi.assign 使用 PUT 方法（幂等），而非 POST（非幂等）。如果误用 POST 做增量更新，同样的请求执行两次可能创建重复的角色关联。
  4. SSO 用户搜索是代理调用：SsoUserPicker 搜索的不是权限中心本地用户，而是通过 PermCenter 代理调用 AuthServer。如果 AuthServer 不可用，搜索会超时失败，需要给用户明确的错误提示。

🔍 验证步骤

  1. 在用户授权页面，选择一个应用，确认用户列表正确加载，每行显示用户名和已分配角色（Badge 形式）
  2. 点击"授权用户"，在弹窗中搜索一个 SSO 用户，勾选若干角色，保存后确认列表中该用户行出现对应的角色 Badge
  3. 点击用户行的"编辑"按钮，确认弹窗中用户字段为只读，已分配角色已回填为选中状态
  4. 修改用户角色（增加或取消），保存后刷新页面，确认角色变更已生效
  5. 选择另一个应用，确认用户列表切换为该应用的用户角色数据
