06 - 动态菜单

06 - 动态菜单

这一步解决什么问题？ 菜单是用户看到权限的最直观方式——用户登录后看到的侧边栏菜单，是根据其角色和权限动态生成的。就像 ASP.NET Core 里 TagHelper 根据 [Authorize] 属性决定是否渲染某个链接，前端的动态菜单也是根据用户权限过滤菜单树。但比 TagHelper 更灵活：菜单的类型不仅限于页面链接，还有目录、按钮和外链。

前置知识

阅读本文档前，你需要了解：

  • 01-RBAC模型与权限树：权限与菜单的绑定关系（permissionName）
  • 02-权限API层：menusApi 的调用方式
  • Zustand 基础：create、persist 中间件、partialize 选项
  • React 条件渲染：{condition && <Element />} 模式

一、ASP.NET Core 类比：动态菜单 = 权限驱动的 TagHelper

在 ASP.NET Core Razor 里，你用 AuthorizationService 控制菜单项可见性：

@inject IAuthorizationService Auth

@if ((await Auth.AuthorizeAsync(User, "Purchase.View")).Succeeded)
{
    <a href="/purchase">采购管理</a>
}
@if ((await Auth.AuthorizeAsync(User, "Inventory.View")).Succeeded)
{
    <a href="/inventory">库存管理</a>
}

权限中心的动态菜单实现了同样的效果，但更完善：

Razor TagHelper 方式              →    权限中心动态菜单
─────────────────────            →    ────────────────
菜单项硬编码在 .cshtml 中         →    菜单项存储在数据库中
每个链接手动加权限判断             →    后端自动按角色过滤
只有页面链接                     →    支持4种类型：目录/菜单/按钮/外链
修改菜单需要改代码重新部署         →    修改菜单只需在管理页面操作

二、菜单数据模型

2.1 四种菜单类型

// src/types/index.ts
export const MENU_TYPE = {
  Directory: 0,      // 目录 — 仅分组用，不对应页面
  Menu: 1,           // 菜单 — 对应一个前端路由页面
  Button: 2,         // 按钮 — 对应页面内的操作按钮
  ExternalLink: 3,   // 外链 — 跳转到外部 URL
} as const

export type MenuType = (typeof MENU_TYPE)[keyof typeof MENU_TYPE]

export const MENU_TYPE_LABELS: Record<MenuType, string> = {
  [MENU_TYPE.Directory]: "目录",
  [MENU_TYPE.Menu]: "菜单",
  [MENU_TYPE.Button]: "按钮",
  [MENU_TYPE.ExternalLink]: "外链",
}

2.2 菜单 DTO

export interface MenuDto {
  id: string
  name: string           // 菜单名称，如 "采购管理"
  code: string           // 菜单编码（同一应用内唯一）
  path: string | null    // 前端路由路径，如 "/purchase"
  icon: string | null    // lucide 图标名，如 "ShoppingCart"
  type: MenuType         // 菜单类型
  permissionName: string | null  // 关联的权限名称
  parentId: string | null
  isVisible: boolean     // 是否在菜单栏显示
  isEnabled: boolean     // 是否启用
  sort: number
  children: MenuDto[]    // 子菜单（递归嵌套）
}

2.3 菜单树示例

目录: 采购管理 (Directory, icon=ShoppingCart)
├── 菜单: 采购列表 (Menu, path=/purchase/list, perm=Purchase.View)
│   ├── 按钮: 新建采购 (Button, perm=Purchase.Create)
│   └── 按钮: 审批 (Button, perm=Purchase.Approve)
└── 菜单: 采购报表 (Menu, path=/purchase/report, perm=Purchase.Report)

目录: 系统设置 (Directory, icon=Settings)
├── 菜单: 参数配置 (Menu, path=/settings/params)
└── 外链: 帮助文档 (ExternalLink, path=https://docs.example.com)

🤔 导师提问：菜单类型"按钮"（Button）不在侧边栏显示，那它为什么要存在于菜单树中？如果去掉"按钮"类型，用单独的"页面按钮权限表"来管理，会有什么问题？提示：想想菜单和权限的统一管理——菜单树已经是权限的载体，"按钮"天然挂在某个页面下。

三、两个菜单端点的区别

端点用途返回内容
GET /api/menus/current?appCode=xxx当前用户菜单按用户权限过滤后的菜单树
GET /api/menus/tree?appCode=xxx完整菜单树所有菜单（管理用）
// src/api/perm/menus.ts
export const menusApi = {
  /** 获取当前用户在某应用的菜单树（权限过滤） */
  getCurrentUserMenus(appCode: string) {
    return get<MenuDto[]>("/api/menus/current", { appCode })
  },

  /** 获取应用完整菜单树（管理用） */
  getTree(appCode: string) {
    return get<MenuDto[]>("/api/menus/tree", { appCode })
  },

  /** 创建菜单 */
  create(data: CreateMenuRequest) {
    return post<MenuDto>("/api/menus", data)
  },

  /** 更新菜单 */
  update(id: string, data: UpdateMenuRequest) {
    return put<MenuDto>(`/api/menus/${id}`, data)
  },

  /** 删除菜单 */
  delete(id: string) {
    return del<string>(`/api/menus/${id}`)
  },

  /** 移动菜单到新的父节点 */
  move(id: string, data: MoveMenuRequest) {
    return post<string>(`/api/menus/${id}/move`, data)
  },

  /** 批量排序 */
  sort(data: SortMenuRequest) {
    return post<string>("/api/menus/sort", data)
  },

  /** 切换可见/启用状态 */
  toggle(id: string, data: ToggleMenuRequest) {
    return post<string>(`/api/menus/${id}/toggle`, data)
  },
}

⚠️ 【易错点】菜单项没有绑定路由：Menu 类型的菜单必须有 path 字段，ExternalLink 类型的菜单 path 是外部 URL。如果创建菜单时忘记填写 path，用户点击后不会跳转到任何页面，也不会报错——这是一个"静默失败"。AdminWeb 在表单层面做了校验，但后端不会拒绝 path 为空的菜单创建请求。

四、菜单 Store：缓存 + 持久化

菜单数据需要在多个组件间共享（侧边栏、命令面板等），所以使用 Zustand store：

// src/stores/menu-store.ts
import { create } from "zustand"
import { persist } from "zustand/middleware"
import { menusApi } from "@/api/perm/menus"
import type { MenuDto } from "@/types"

interface MenuState {
  /** 当前用户的菜单树（已按权限过滤） */
  menus: MenuDto[]
  /** 是否已加载过 */
  loaded: boolean
  /** 加载中 */
  loading: boolean
  /** 错误信息 */
  error: string | null
  /** 上次成功获取的时间戳（用于缓存过期检查） */
  fetchedAt: number | null

  /** 获取当前用户菜单 */
  fetchMenus: (appCode: string) => Promise<void>
  /** 使缓存失效（强制下次重新获取） */
  invalidate: () => void
}

/** 缓存 TTL：5 分钟 */
const CACHE_TTL_MS = 5 * 60 * 1000

export const useMenuStore = create<MenuState>()(
  persist(
    (set, get) => ({
      menus: [],
      loaded: false,
      loading: false,
      error: null,
      fetchedAt: null,

      fetchMenus: async (appCode: string) => {
        const { loaded, fetchedAt, loading } = get()

        // 已在加载中，跳过
        if (loading) return

        // 缓存未过期，跳过
        if (loaded && fetchedAt && Date.now() - fetchedAt < CACHE_TTL_MS) return

        set({ loading: true, error: null })
        try {
          const res = await menusApi.getCurrentUserMenus(appCode)
          set({
            menus: res.data ?? [],
            loaded: true,
            fetchedAt: Date.now(),
          })
        } catch (err) {
          set({
            error: err instanceof Error ? err.message : "加载菜单失败",
            loaded: false,
          })
        } finally {
          set({ loading: false })
        }
      },

      invalidate: () => {
        set({ loaded: false, fetchedAt: null })
      },
    }),
    {
      name: "admin-menus",
      // 只持久化核心字段，不持久化 loading/error 等临时状态
      partialize: (state) => ({
        menus: state.menus,
        loaded: state.loaded,
        fetchedAt: state.fetchedAt,
      }),
    }
  )
)

4.1 缓存策略

首次访问侧边栏
    │
    ▼
  loaded=false → 发起 API 请求
    │
    ▼
  缓存菜单数据 + fetchedAt
    │
    ▼
5分钟内再次访问 → 命中缓存，跳过请求
    │
    ▼
5分钟后访问 → 缓存过期，重新请求
    │
    ▼
用户权限变更 → 调用 invalidate() 强制刷新

💡 ASP.NET Core 类比：这就像 IMemoryCache + 滑动过期时间。partialize 相当于只把 menus 序列化到 localStorage，不序列化临时状态。

4.2 persist 中间件

persist 中间件将 store 的部分状态持久化到 localStorage：

Zustand Store                    localStorage
─────────────                    ────────────
menus: [...]          →          "admin-menus": { menus: [...], loaded: true, fetchedAt: 1717843... }
loaded: true          →
fetchedAt: 1717843... →
loading: false        ✗ (不持久化)
error: null           ✗ (不持久化)

用户刷新页面后，菜单数据从 localStorage 恢复，不需要重新请求。只有在缓存过期或 invalidate() 后才会重新获取。

4.3 谁拥有菜单状态？为什么用 Store 而不是按页面获取？

🤔 导师提问：菜单数据只在一个侧边栏组件里渲染，为什么还要用全局 Store？直接在 AppSidebar 组件里 useState + useEffect 获取不行吗？

菜单状态必须在 Store 中的三个理由：

  1. 多消费者：菜单数据不只是侧边栏用。命令面板（Command Palette）、面包屑导航、Tab 标签页等都需要读取当前菜单树。如果用组件内 useState，每个消费者都要独立请求一次，造成重复 API 调用。
  2. 缓存一致性：Store 保证了全局只有一个菜单缓存实例。权限变更后调用一次 invalidate()，所有消费者下次访问都会重新获取。如果每个组件各自缓存，invalidate 时需要逐个通知，容易遗漏。
  3. 持久化需求：persist 中间件只作用于 Store。如果放在组件 useState 里，页面刷新就丢失了，每次打开应用都要等菜单加载完才能显示侧边栏，用户体验差。

⚠️ 【性能陷阱】每次导航都重新获取菜单：如果 fetchMenus 没有 loaded / fetchedAt 的缓存判断，每次侧边栏组件重新渲染都会触发 API 请求。在 SPA 中，路由切换会导致组件卸载再挂载，如果菜单数据不是持久化的，用户每次切换页面都会看到侧边栏闪烁。这就是为什么 persist + CACHE_TTL_MS 的组合如此重要。

五、侧边栏如何消费菜单

// src/components/layout/app-sidebar.tsx
import { useMenuStore } from "@/stores/menu-store"

export function AppSidebar() {
  const { menus, loading, error, fetchMenus } = useMenuStore()

  useEffect(() => {
    fetchMenus("admin-web")  // 加载 AdminWeb 自身的菜单
  }, [fetchMenus])

  // ...
}

5.1 递归菜单渲染组件

AdminWeb 的侧边栏使用递归组件模式渲染菜单树。核心是 DynamicMenuGroup 组件：

// src/components/layout/app-sidebar.tsx

/**
 * 动态菜单目录（Directory）渲染为可折叠分组
 */
function DynamicMenuGroup({ menu, isActive, navigate }: {
  menu: MenuDto
  isActive: (url: string) => boolean
  navigate: (url: string) => void
}) {
  // 过滤掉按钮类型（按钮不在侧边栏显示）
  const children = menu.children.filter(c => c.type !== MENU_TYPE.Button)

  // 权限过滤后可能所有子菜单都被移除，此时不渲染空目录
  if (children.length === 0) return null

  const hasActiveChild = children.some(c => isActive(c.path ?? ""))

  return (
    <Collapsible key={menu.id} defaultOpen={hasActiveChild} className="group/collapsible">
      <SidebarGroup>
        <CollapsibleTrigger asChild>
          <SidebarGroupLabel className="cursor-pointer hover:text-foreground transition-colors">
            {menu.icon && <DynamicIcon name={menu.icon} className="mr-1.5 h-3.5 w-3.5" />}
            {menu.name}
            <ChevronRight className="ml-auto h-3.5 w-3.5 transition-transform group-data-[state=open]/collapsible:rotate-90" />
          </SidebarGroupLabel>
        </CollapsibleTrigger>
        <CollapsibleContent>
          <SidebarGroupContent>
            <SidebarMenu>
              {children.map(child => (
                <SidebarMenuItem key={child.id}>
                  <SidebarMenuButton
                    isActive={isActive(child.path ?? "")}
                    onClick={() => {
                      if (child.type === MENU_TYPE.ExternalLink) {
                        window.open(child.path ?? "", "_blank")
                      } else {
                        navigate(child.path ?? "/")
                      }
                    }}
                    className="relative"
                  >
                    {isActive(child.path ?? "") && (
                      <motion.div
                        layoutId="sidebar-active"
                        className="absolute left-0 top-1/2 -translate-y-1/2 h-5 w-[3px] rounded-full bg-primary"
                        transition={{ type: "spring", stiffness: 350, damping: 30 }}
                      />
                    )}
                    {child.icon && <DynamicIcon name={child.icon} className="h-4 w-4" />}
                    <span>{child.name}</span>
                  </SidebarMenuButton>
                </SidebarMenuItem>
              ))}
            </SidebarMenu>
          </SidebarGroupContent>
        </CollapsibleContent>
      </SidebarGroup>
    </Collapsible>
  )
}

注意几个关键设计点：

  1. children.filter(c => c.type !== MENU_TYPE.Button)：过滤按钮类型，按钮只用于页面内权限控制，不在侧边栏显示
  2. children.length === 0 → return null：如果权限过滤后目录下没有可见子项，整个目录也不渲染（避免出现空的可折叠分组）
  3. defaultOpen={hasActiveChild}：如果当前路由命中了目录下的某个子菜单，目录默认展开——这是用户体验的关键细节
  4. ExternalLink 用 window.open 而不是 React Router 的 navigate：外链需要脱离 SPA 路由，在新的浏览器标签页打开

🤔 导师提问：DynamicMenuGroup 只处理了目录类型（Directory）的直接子项。如果菜单树有三层嵌套（目录 → 子目录 → 菜单），当前的渲染逻辑会出现什么问题？提示：看看 children.map 里 SidebarMenuButton 是怎么处理不同类型的——它没有再递归。

⚠️ 【易错点】菜单排序的竞态条件：menusApi.sort() 是一个批量排序接口，如果两个管理员同时对同一应用的菜单进行拖拽排序，后提交的会覆盖先提交的结果。这和角色权限的"全量替换"是同一个问题。AdminWeb 目前没有加锁机制，只依赖"后写入者赢"的语义。在并发量极低的管理后台场景下，这是可以接受的。

六、权限与菜单的绑定关系

菜单通过 permissionName 字段绑定权限：

菜单: 采购列表
  ├── code: "purchase-list"
  ├── path: "/purchase/list"
  ├── permissionName: "Purchase.View"    ← 关联的权限
  └── children:
      ├── 按钮: 新建采购
      │   └── permissionName: "Purchase.Create"
      └── 按钮: 审批
          └── permissionName: "Purchase.Approve"

过滤逻辑（后端执行）：

  1. 查询用户在当前应用下的所有角色
  2. 汇总角色关联的所有权限编码
  3. 遍历菜单树，保留 permissionName 为空或用户有对应权限的节点
  4. 如果父节点（目录）下所有子节点都被过滤掉了，父节点也不显示

💡 ASP.NET Core 类比：这就像 AuthorizationViewComponent，但逻辑在后端执行，前端只需要渲染后端返回的菜单树。

七、ToggleMenuRequest：两个独立的开关

菜单有两个独立的布尔状态：

字段含义Toggle 请求
isVisible是否在侧边栏显示{ field: "IsVisible", value: false }
isEnabled是否启用{ field: "IsEnabled", value: false }
export interface ToggleMenuRequest {
  field: "IsVisible" | "IsEnabled"
  value: boolean
}

为什么要两个开关？

  • isVisible=false, isEnabled=true：菜单存在且功能正常，但不在侧边栏显示（比如通过命令面板访问）
  • isVisible=true, isEnabled=false：菜单显示但灰掉，提示用户"此功能暂未开放"

八、【设计取舍】服务端驱动菜单 vs 客户端路由

🤔 导师提问：我们当前的方案是"服务端返回菜单树，前端动态渲染"。另一种常见方案是"前端定义所有路由，后端只返回权限列表，前端根据权限过滤路由"。两种方案各有什么优劣？

维度服务端驱动菜单（我们的方案）客户端路由 + 权限过滤
菜单变更后端修改即可，无需前端部署前端需要同步修改路由配置
多应用支持天然支持——每个应用有自己的菜单树每个应用需要独立的前端路由配置
离线可用首次加载后依赖 localStorage 缓存路由配置打包在前端代码里，天然可用
开发体验前端不需要硬编码菜单，但需要理解后端数据结构前端完全掌控，但每次新增页面要改两处（路由 + 后端菜单表）
权限一致性后端返回的菜单一定和权限一致前端过滤可能和后端权限判断不一致

为什么选服务端驱动？ SaaS 平台的核心需求是"多应用、多租户"。服务端驱动意味着运营人员可以通过管理后台自助配置菜单，而不需要开发人员介入。这在多应用场景下尤其重要——每新增一个应用，只需要在权限中心配置菜单，前端不需要改动。

踩坑提醒

  1. 菜单项没有绑定路由会"静默失败"：Menu 类型的菜单必须有 path 字段。如果创建菜单时忘记填写 path，用户点击后不会跳转到任何页面，也不会报错。AdminWeb 在表单层面做了校验，但后端不会拒绝 path 为空的菜单创建请求。
  2. 菜单排序的竞态条件：menusApi.sort() 是批量排序接口，如果两个管理员同时对同一应用的菜单进行拖拽排序，后提交的会覆盖先提交的结果。AdminWeb 目前没有加锁机制，只依赖"后写入者赢"的语义。
  3. 权限变更后菜单不会立即更新：菜单 Store 有 5 分钟的缓存 TTL。如果管理员修改了某个用户的权限，该用户的菜单不会立即更新。需要在权限变更后调用 invalidate() 强制刷新缓存，或等待 TTL 过期。
  4. DynamicMenuGroup 不支持三层以上嵌套：当前渲染逻辑只处理了目录类型（Directory）的直接子项，如果菜单树有三层嵌套（目录 → 子目录 → 菜单），子目录不会被渲染为可折叠分组，其下的菜单项也不会显示。

🤔 思考题

概念级（理解）

  1. 为什么"按钮"类型的菜单不在侧边栏显示？它的作用是什么？
  2. 菜单的 code 字段在同一应用内必须唯一。如果两个不同父目录下有同名的菜单项（如两个目录下都有"列表"），code 应该怎样命名？

推理级（分析）

  1. 菜单 Store 使用了 5 分钟的缓存 TTL。如果管理员修改了某个用户的权限，该用户的菜单不会立即更新。如何解决这个问题？
  2. persist 中间件把菜单数据存到了 localStorage。如果用户在另一个浏览器登录，菜单数据会怎样？这种持久化是否安全？

实操级（动手）

  1. 假设需要实现菜单的拖拽排序功能（拖动菜单项调整顺序），请设计前端交互方案和后端 API 调用流程。
  2. 如果要在侧边栏为每个菜单项显示一个 Badge（如"采购列表"旁显示待审批数量），应该怎样扩展菜单数据模型？

实战级（L3 动手）

  1. 打开 src/stores/menu-store.ts，当前 fetchMenus 只接受 appCode 参数。现在请修改 Store，使其支持多应用菜单缓存——即切换应用时不需要重新请求已有缓存的应用菜单。提示：将 menus: MenuDto[] 改为 menusMap: Record<string, MenuDto[]>，按 appCode 分别存储。修改后，验证在两个应用间切换时，菜单不会闪烁。思考：这种多应用缓存对 invalidate() 的影响是什么——应该清除单个应用的缓存还是全部？
