06 - 租户详情：6 Tab 数据加载与配额内联编辑

这一步解决什么问题？
租户详情页是运营中心信息密度最高的页面——6 个 Tab 覆盖概览、配额、模块、功能开关、健康检查和操作日志。核心难点是配额内联编辑的脏数据追踪——只提交修改过的行，而不是全量保存。

ASP.NET Core 开发者的直觉：脏数据追踪就像 EF Core 的 ChangeTracker——只提交 EntityState.Modified 的实体。前端用 Record<string, number> 代替 ChangeTracker，通过比较 editedQuotas[id] !== quota.quotaLimit 判断脏状态。

前置知识

  • 模块 10-01 中的平台级数据 vs 租户级数据区分
  • 模块 10-02 中的 tenantsApi 详情查询方法（getDashboard/getQuotas/getModules/...）
  • React Promise.all 并行请求模式
  • Record<string, T> 类型用于键值映射

export default function OpsTenantDetailPage() {
  const { id } = useParams<{ id: string }>()
  const navigate = useNavigate()

  const [dashboard, setDashboard] = useState<TenantDashboardDto | null>(null)
  const [quotas, setQuotas] = useState<TenantQuotaDto[]>([])
  const [modules, setModules] = useState<TenantModuleAccessDto[]>([])
  const [features, setFeatures] = useState<TenantFeatureFlagDto[]>([])
  const [health, setHealth] = useState<TenantHealthCheckDto | null>(null)
  const [logs, setLogs] = useState<TenantOperationLogDto[]>([])
  const [loading, setLoading] = useState(true)

  // 配额编辑状态：quotaId → 新的 quotaLimit
  const [editedQuotas, setEditedQuotas] = useState<Record<string, number>>({})

  const fetchAll = async () => {
    if (!id) return
    setLoading(true)
    try {
      const [dash, q, m, f, h, l] = await Promise.all([
        tenantsApi.getDashboard(id), tenantsApi.getQuotas(id), tenantsApi.getModules(id),
        tenantsApi.getFeatures(id), tenantsApi.getHealth(id), tenantsApi.getOperations(id),
      ])
      setDashboard(dash); setQuotas(q); setModules(m)
      setFeatures(f); setHealth(h); setLogs(l)
    } catch { toast.error("加载租户详情失败") }
    finally { setLoading(false) }
  }

  useEffect(() => { fetchAll() }, [id])

  // ... 6 个 Tab 的渲染，见完整源码
}

代码讲解

Promise.all 并行加载 6 个 Tab 的数据

const [dash, q, m, f, h, l] = await Promise.all([
  tenantsApi.getDashboard(id), tenantsApi.getQuotas(id), tenantsApi.getModules(id),
  tenantsApi.getFeatures(id), tenantsApi.getHealth(id), tenantsApi.getOperations(id),
])

⚠️ 【易错点】 Promise.all 的"快速失败"特性——如果 6 个请求中任意一个失败，整个 Promise.all 立即 reject，其他成功的结果也会丢失。如果希望"部分失败也能展示成功的数据"，应该用 Promise.allSettled 并单独处理每个结果的状态。

💡 ASP.NET Core 类比：这就像在 Controller 中并行发送多个 MediatR Query——但后端通常是串行的。前端选择并行加载是因为 6 个 Tab 的数据互不依赖，并行可以减少页面加载时间（6 次 RTT → 1 次 RTT，假设后端并行处理）。

🤔 导师提问：6 个 Tab 的数据源各不相同，页面初始化时用 Promise.all 并行加载。如果其中一个请求失败，Promise.all 会怎样？应该用 Promise.allSettled 吗？在后端，你习惯用 MediatR 发送多个 Query，但通常是串行的——前端为什么选择并行？

配额内联编辑的脏数据追踪

// 使用 Record<quotaId, newValue> 追踪修改
const [editedQuotas, setEditedQuotas] = useState<Record<string, number>>({})

// 判断某行是否有未保存的修改
const isDirty = (quota: TenantQuotaDto) =>
  editedQuotas[quota.id] !== undefined && editedQuotas[quota.id] !== quota.quotaLimit

// 保存后清除脏标记
const handleSave = async (quotaId: string) => {
  await tenantsApi.updateQuota(id, quotaId, editedQuotas[quotaId])
  setEditedQuotas(prev => { const next = { ...prev }; delete next[quotaId]; return next })
}

⚠️ 【易错点】 editedQuotas 只存储修改过的配额 ID 和新值。未修改的行不在 editedQuotas 中，editedQuotas[quota.id] 返回 undefined。isDirty 判断需要两个条件：editedQuotas[id] !== undefined（有修改）且 editedQuotas[id] !== quota.quotaLimit（值确实变了）。

⚠️ 【设计取舍】 为什么不用"全量保存"模式（一个"保存所有修改"按钮）？因为配额修改的影响范围不同——数据库连接串的配额修改和存储空间的配额修改，风险级别完全不同。逐行保存让用户更清楚地知道"我正在改什么"。

💡 ASP.NET Core 类比：editedQuotas 就像 EF Core 的 ChangeTracker——只提交 EntityState.Modified 的实体。Record<string, number> 是前端的"简易 ChangeTracker"，通过 delete next[quotaId] 模拟 Detach 操作。

🤔 导师提问：editedQuotas 是一个 Record<string, number>，只存储修改过的配额 ID 和新值。这和 EF Core ChangeTracker 的"快照式对比"有何异同？ChangeTracker 在首次追踪时保存原始值快照，而 editedQuotas 是通过比较 editedQuotas[id] !== quota.quotaLimit 来判断脏状态。哪种方式更可靠？

使用率可视化

配额使用率通过 Progress 进度条 + 颜色分级展示：

<Progress value={Math.min(q.usagePercentage, 100)}
  className={`h-2 ${q.usagePercentage > 90 ? "[&>div]:bg-red-500" : q.usagePercentage > 70 ? "[&>div]:bg-yellow-500" : ""}`} />
<span className="text-xs w-10 text-right">{q.usagePercentage.toFixed(0)}%</span>
  • 正常：默认蓝色
  • >70%：黄色 [&>div]:bg-yellow-500
  • >90%：红色 [&>div]:bg-red-500

⚠️ 【易错点】 Math.min(q.usagePercentage, 100) 确保进度条不会超过 100%——如果后端返回的使用率是 105%（超额使用），不加 Math.min 会导致进度条溢出。

🤔 导师提问：配额使用率用颜色分级（蓝/黄/红）提供视觉反馈。在后端，你可能用 Health Check 的 HealthStatus（Healthy/Degraded/Unhealthy）枚举来表达类似的概念。前端的颜色分级是硬编码的阈值（70%/90%），如果这些阈值需要按租户配置，前端应该如何改造？提示：考虑 CSS 变量或 Theme Token。

Switch 切换的防重复提交

const [togglingFeature, setTogglingFeature] = useState<string | null>(null)

<Switch
  disabled={togglingFeature === feat.featureKey}
  onCheckedChange={() => handleToggleFeature(feat)}
/>

⚠️ 【易错点】 如果不用 togglingFeature 而用一个全局 loading 状态，所有 Switch 都会被禁用——用户只能等一个操作完成才能切换下一个。用 featureKey 级别的 loading，只有正在操作的那个 Switch 被禁用。

🤔 导师提问：模块和功能开关都使用 Switch 切换，但它们调用的 API 不同——toggleModule vs setFeature。观察 handleToggleModule 和 handleToggleFeature 的实现，它们都遵循"切换 → 调 API → 刷新列表"的模式。在后端，这就像 Command → Handler → 返回结果。如果切换失败，Switch 应该回滚到原始状态——当前代码是怎么处理的？

踩坑提醒

  1. Promise.all 的快速失败：如果健康检查 API 超时，所有 6 个 Tab 的数据都会加载失败，页面只显示"加载租户详情失败"。应该改用 Promise.allSettled，让成功的 Tab 正常展示，失败的 Tab 显示"加载失败"的局部提示。

  2. Switch 切换失败没有回滚：当前 handleToggleModule 先调用 API，成功后刷新列表。但如果 API 失败，Switch 不会回滚——因为它用 onCheckedChange 触发，React 在 API 调用前已经更新了 Switch 状态。正确做法是：先保存原始状态，失败时手动回滚 Switch。

⚠️ 踩坑提醒

  1. Promise.all 的"快速失败"特性：如果 6 个并行请求中有任何一个失败，整个 fetchAll 会进入 catch 分支，所有数据都不会设置。改进方案是用 Promise.allSettled，让每个 Tab 独立处理成功/失败。
  2. Switch 切换失败无回滚：handleToggleModule 和 handleToggleFeature 在 API 失败时只显示 toast，但 Switch 的 UI 状态不会自动回滚——因为 catch 中没有重新 fetch 列表。
  3. 配额 Input 的 type="number" 陷阱：用户可能输入非数字字符（如 e、.），Number(e.target.value) 可能返回 NaN。应在保存前做 isNaN 校验。
  4. 操作日志用 key={i} 不安全：如果后端返回的日志列表有唯一 ID，应该用 key={log.id} 而非索引，避免列表更新时的 DOM 复用错误。

自测题

概念级（理解 Why）

  1. 配额内联编辑用 Record<string, number> 追踪脏数据，而不是维护一个完整的"修改后列表"。为什么只存增量更高效？
  2. 使用率的颜色分级（70%/90%）是硬编码的。如果需要按租户配置阈值，应该把阈值存在前端还是后端？

推理级（推导 What-if）

  1. 如果 6 个 Tab 中某个 API 响应特别慢（如操作日志有分页，需要 10 秒），Promise.all 会导致整个页面 10 秒后才渲染。怎么优化？
  2. Switch 切换失败时当前代码没有回滚 UI 状态。如果需要"乐观更新 + 失败回滚"模式，应该怎么改？

动手级（代码实践）

  1. 把 Promise.all 改为 Promise.allSettled，让每个 Tab 独立处理成功/失败状态。修改 fetchAll 函数和各 Tab 的渲染逻辑。
  2. 实现配额的"全量保存"模式：一个"保存所有修改"按钮，一次性提交所有脏数据。需要修改 handleSaveQuota 为批量提交。
