04 - 通知铃铛：实时推送的入口

04 - 通知铃铛：实时推送的入口

这一步解决什么问题？
用户在使用 SaaS 系统时，不可能一直盯着通知列表页。我们需要一个全局可见的入口——铃铛图标 + 未读徽标，让用户在任何页面都能感知到新通知，点击即可查看最近的通知并快速操作。

ASP.NET Core 类比：铃铛组件 ≈ _Layout.cshtml 里的通知 PartialView——每个页面都渲染它，它负责展示未读数和最近通知列表。

前置知识

  • 第 1-3 节的 SignalR 连接、通知 Store 和 API 层代码
  • React useEffect 的生命周期与 cleanup 机制
  • ASP.NET Core _Layout.cshtml 中的 Partial View 概念

  • mousedown / click 事件的触发时序差异

⚠️ 【组件思维】为什么 notification-bell.tsx 放在 components/ 根目录？

AdminWeb 的 src/components/ 目录结构：

components/
├── brand/              ← 品牌相关组件（Logo 等）
├── layout/             ← 布局组件（Header、Sidebar）
├── shared/             ← 通用共享组件（Button、Table 封装）
├── tree/               ← 树形组件
├── ui/                 ← shadcn/ui 基础组件
└── notification-bell.tsx  ← 为什么不在 shared/ 里？

notification-bell.tsx 放在 components/ 根目录而不是 components/shared/，原因是：

  1. 它不是"通用组件" —— shared/ 里的组件（如 Button、Dialog）是任何页面都能复用的，而铃铛只在顶栏 Header 中使用
  2. 它是"应用级入口组件" —— 它的地位类似于 layout 组件，是应用壳的一部分
  3. 它有自己的数据依赖 —— 直接依赖 notification-store 和 jobsApi，不像 shared/ 组件只接收 props

二、完整代码

/**
 * 通知铃铛组件
 *
 * 功能：
 * - 顶栏通知图标 + 未读徽标
 * - 点击展开下拉通知列表
 * - 支持标记已读 / 全部已读
 * - 首次挂载时初始化 SignalR 监听
 * - 打印任务通知点击可直接下载
 */
import { useEffect, useRef, useState } from "react"
import { Link } from "react-router-dom"
import { toast } from "sonner"
import { useNotificationStore } from "@/stores/notification-store"
import { jobsApi } from "@/api/print/jobs"
import { NotificationStatus } from "@/types/notification"

/**
 * 通知铃铛组件
 *
 * 在应用顶栏展示通知图标和未读数徽标，点击展开最近通知下拉列表。
 * 集成 SignalR 实时推送，并配合 60 秒轮询作为断线兜底。
 * 支持单条标记已读和一键全部已读。
 */
export function NotificationBell() {
  const { unreadCount, recentItems, loading, fetchUnreadCount, fetchRecent, markRead, markAllRead, initSignalR, disposeSignalR } =
    useNotificationStore()
  const [open, setOpen] = useState(false)
  const dropdownRef = useRef<HTMLDivElement>(null)

  // 初始化：拉取未读数 + 注册 SignalR 监听
  useEffect(() => {
    fetchUnreadCount()
    initSignalR()

    // 每 60 秒轮询未读数（SignalR 断线时兜底）
    const timer = setInterval(fetchUnreadCount, 60_000)

    return () => {
      clearInterval(timer)
      disposeSignalR()
    }
  }, [])

  // 展开下拉时加载最近通知
  useEffect(() => {
    if (open) {
      fetchRecent()
    }
  }, [open])

  // 点击外部关闭下拉
  useEffect(() => {
    function handleClickOutside(e: MouseEvent) {
      if (dropdownRef.current && !dropdownRef.current.contains(e.target as Node)) {
        setOpen(false)
      }
    }
    document.addEventListener("mousedown", handleClickOutside)
    return () => document.removeEventListener("mousedown", handleClickOutside)
  }, [])

  /** 点击通知项：如果是打印任务且有 jobId 则下载，否则标记已读 */
  const handleClickItem = (item: typeof recentItems[number]) => {
    if (item.status !== NotificationStatus.Read) {
      markRead(item.id)
    }
    // 解析 dataJson，打印完成通知可点击下载
    if (item.dataJson) {
      try {
        const data = JSON.parse(item.dataJson)
        if (data.jobId && data.status === "completed") {
          // 优先使用 presigned URL（无需 token），降级走 API
          const downloadUrl = data.downloadUrl
          if (downloadUrl && downloadUrl.startsWith("http")) {
            window.open(downloadUrl, "_blank")
          } else {
            jobsApi.download(data.jobId).then((res) => {
              const blob = new Blob([res.data as BlobPart])
              const url = URL.createObjectURL(blob)
              const a = document.createElement("a")
              a.href = url
              // 从 Content-Disposition 取文件名
              const cd = res.headers?.["content-disposition"] ?? ""
              const match = cd.match(/filename\*?=(?:UTF-8'')?([^;\n]+)/i)
              a.download = match ? decodeURIComponent(match[1].replace(/"/g, "")) : `report_${data.jobId.slice(0, 8)}`
              a.click()
              URL.revokeObjectURL(url)
            }).catch(() => toast.error("下载失败"))
          }
        }
      } catch {
        // 忽略
      }
    }
  }

  return (
    <div ref={dropdownRef} className="relative">
      {/* 铃铛按钮 */}
      <button
        onClick={() => setOpen(!open)}
        className="relative p-2 rounded-md hover:bg-gray-100 dark:hover:bg-gray-800 transition-colors"
        aria-label="通知"
      >
        <svg xmlns="http://www.w3.org/2000/svg" className="h-5 w-5" viewBox="0 0 20 20" fill="currentColor">
          <path d="M10 2a6 6 0 00-6 6v3.586l-.707.707A1 1 0 004 14h12a1 1 0 00.707-1.707L16 11.586V8a6 6 0 00-6-6zM10 18a3 3 0 01-3-3h6a3 3 0 01-3 3z" />
        </svg>
        {/* 未读徽标 - 超过 99 显示 "99+" */}
        {unreadCount > 0 && (
          <span className="absolute -top-1 -right-1 inline-flex items-center justify-center px-1.5 py-0.5 text-xs font-bold leading-none text-white bg-red-500 rounded-full animate-pulse">
            {unreadCount > 99 ? "99+" : unreadCount}
          </span>
        )}
      </button>

      {/* 下拉面板 */}
      {open && (
        <div className="absolute right-0 mt-2 w-80 bg-white dark:bg-gray-900 border border-gray-200 dark:border-gray-700 rounded-lg shadow-lg z-50">
          {/* 头部 */}
          <div className="flex items-center justify-between px-4 py-3 border-b border-gray-200 dark:border-gray-700">
            <span className="text-sm font-semibold">通知</span>
            {/* 有未读时显示"全部已读"按钮 */}
            {unreadCount > 0 && (
              <button
                onClick={() => markAllRead()}
                className="text-xs text-blue-600 hover:text-blue-800 dark:text-blue-400"
              >
                全部已读
              </button>
            )}
          </div>

          {/* 通知列表 */}
          <div className="max-h-96 overflow-y-auto">
            {loading ? (
              <div className="px-4 py-8 text-center text-sm text-gray-500">加载中...</div>
            ) : recentItems.length === 0 ? (
              <div className="px-4 py-8 text-center text-sm text-gray-500">暂无通知</div>
            ) : (
              recentItems.map((item) => (
                <div
                  key={item.id}
                  onClick={() => handleClickItem(item)}
                  className={`px-4 py-3 border-b border-gray-100 dark:border-gray-800 cursor-pointer hover:bg-gray-50 dark:hover:bg-gray-800 transition-colors ${
                    item.status !== NotificationStatus.Read ? "bg-blue-50/50 dark:bg-blue-900/10" : ""
                  }`}
                >
                  <div className="flex items-start gap-2">
                    {/* 未读指示点 */}
                    {item.status !== NotificationStatus.Read && (
                      <span className="mt-1.5 h-2 w-2 rounded-full bg-blue-500 flex-shrink-0" />
                    )}
                    <div className="flex-1 min-w-0">
                      <p className="text-sm font-medium truncate">{item.title ?? "通知"}</p>
                      <p className="text-xs text-gray-500 mt-1 line-clamp-2">{item.body}</p>
                      {/* 通知时间 */}
                      <p className="text-xs text-gray-400 mt-1">
                        {new Date(item.creationTime).toLocaleString("zh-CN")}
                      </p>
                    </div>
                  </div>
                </div>
              ))
            )}
          </div>

          {/* 底部链接 - 跳转通知列表页 */}
          <div className="px-4 py-2 border-t border-gray-200 dark:border-gray-700 text-center">
            <Link to="/notifications" onClick={() => setOpen(false)} className="text-xs text-blue-600 hover:text-blue-800 dark:text-blue-400">
              查看全部通知
            </Link>
          </div>
        </div>
      )}
    </div>
  )
}

三、三个 useEffect 的职责与时序

这是铃铛组件最精妙的设计——三个 useEffect 各司其职：

useEffect #1: 初始化（只运行一次）
├── fetchUnreadCount()   // 立即拉取未读数
├── initSignalR()        // 注册 SignalR 监听
├── setInterval(60s)     // 定时轮询兜底
└── cleanup: clearInterval + disposeSignalR

useEffect #2: 展开时加载
└── if (open) fetchRecent()  // 用户点击铃铛时才拉列表

useEffect #3: 点击外部关闭
└── document.addEventListener("mousedown", handleClickOutside)
时间线：
──────────────────────────────────────────────────────→
  │                     │            │
  组件挂载              用户点击铃铛    用户点击外部
  ├─ fetchUnreadCount   ├─ fetchRecent  ├─ setOpen(false)
  ├─ initSignalR        │  (拉最近10条)  │
  ├─ 启动60s轮询        │               │
  │                     │               │
  ...60s后...           │               │
  ├─ fetchUnreadCount   │               │
  │                     │               │
  ...SignalR推送...      │               │
  └─ onNewNotification  │               │
     (unreadCount+1)    │               │

逐行精讲：

标记代码解读
【设计取舍】useEffect(() => { ... }, [])空依赖数组 = 只在挂载时执行。fetchUnreadCount、initSignalR、setInterval 都是 Zustand store 的方法，引用稳定，不需要加到依赖数组
【易错点】const timer = setInterval(...)必须保存 timer 引用！cleanup 时需要 clearInterval(timer)。如果写成 setInterval(fetchUnreadCount, 60_000) 不保存引用，组件卸载时无法清除定时器
【性能陷阱】fetchRecent 只在 open 时调用不要在初始化时就 fetchRecent！用户可能永远不点铃铛，提前拉取浪费请求。懒加载是更好的策略
【易错点】handleClickOutside 用 mousedown 而非 clickclick = mousedown + mouseup。如果用 click，用户在面板内 mousedown、在面板外 mouseup 也会触发关闭，体验不好。mousedown 更早响应且更准确

⚠️ 【易错点】badge count 与 SignalR 的竞态条件

考虑这个场景：SignalR 推送了一条新通知（unreadCount + 1），同时 60 秒轮询也在请求最新的 unreadCount。如果轮询的响应在 SignalR 推送之前发出、但晚于推送到达浏览器，会发生什么？

时间线：
  t0: unreadCount = 5
  t1: SignalR 推送通知 → onNewNotification → unreadCount = 6
  t2: 60s 轮询响应到达（基于 t0 时刻的数据）→ unreadCount = 5 ❌

结果：SignalR 推送的 +1 被轮询的旧数据覆盖了！

AdminWeb 的 fetchUnreadCount 用的是服务端权威值覆盖（set({ unreadCount: res.data.unreadCount })），而不是增量更新。这意味着轮询响应会把 SignalR 的增量更新覆盖掉。

但这个问题在实践中影响有限，因为：

  1. 轮询间隔是 60 秒，竞态窗口很小
  2. 下一次轮询或 SignalR 推送会修正计数
  3. 用户点击铃铛时 fetchRecent 会重新拉取完整列表

⚠️ 【易错点】为什么不用 window.open(downloadUrl) 下载？
因为文件下载 API 需要认证！window.open 发出的请求不带 Authorization header，服务端会返回 401，然后重定向到登录页。

❌ window.open("/api/print/jobs/xxx/download")
   → 浏览器发 GET 请求（无 Bearer Token）
   → 后端返回 401
   → 重定向到登录页
   → 用户懵了：我只是想下载个文件！

✅ jobsApi.download(jobId)
   → axios 发请求（自动带 Bearer Token）
   → 后端返回 Blob
   → 前端用 URL.createObjectURL + <a> 触发下载

💡 但 AdminWeb 源码中有一个改进：presigned URL 优先
仔细看源码，如果 dataJson 中包含 downloadUrl（presigned URL），组件会用 window.open(downloadUrl, "_blank") 直接打开。因为 presigned URL 自带签名参数，不需要 Authorization header。只有没有 presigned URL 时，才降级走 API 下载。

presigned URL:
https://storage.example.com/reports/xxx.pdf?sig=abc123&se=2024-01-01T00:00:00Z
→ URL 自带访问签名，无需 Token
→ window.open() 直接打开即可

API 下载（降级）:
/api/print/jobs/xxx/download
→ 需要 Bearer Token
→ 必须用 axios + Blob 方式下载

💡 【设计取舍】typeof recentItems[number]
这是 TypeScript 从数组类型提取元素类型的技巧：

recentItems: NotificationDto[]
typeof recentItems[number]  // 等价于 NotificationDto

为什么不用直接写 NotificationDto？因为如果 recentItems 的类型变了，typeof 写法会自动跟着变，减少维护成本。

六、实时推送 + 轮询的双重保障

                    新通知到达
                       │
          ┌────────────┴────────────┐
          │                         │
    SignalR 推送 ✅              60s 轮询 ✅
    (实时，毫秒级)               (兜底，分钟级)
          │                         │
          ▼                         ▼
   onNewNotification()       fetchUnreadCount()
   ├─ unreadCount +1         ├─ 从服务端拿最新计数
   ├─ 插入 recentItems       └─ 覆盖本地 unreadCount
   └─ 显示 toast

⚠️ 【设计取舍】为什么需要双重保障？
SignalR 可能断线（网络波动、服务端重启）。如果只依赖 SignalR，断线期间的通知用户永远看不到。60 秒轮询是"安全网"——即使 SignalR 断了，最多延迟 60 秒也能拿到最新计数。

💡 但为什么轮询只拉计数，不拉列表？
因为列表数据量大（每条通知有标题、正文、时间等），60 秒拉一次列表太浪费。计数只有一个数字，轮询代价极低。用户真正看列表时（点击铃铛），才按需拉取。

⚠️ 【性能陷阱】通知轮询频率的选择

轮询间隔选择的影响：

间隔太短（如 5 秒）：
├── 优点：断线时发现快，通知延迟低
├── 缺点：100 个在线用户 = 每分钟 1200 次 HTTP 请求
└── 结论：对服务端压力太大，不可取

间隔太长（如 5 分钟）：
├── 优点：服务端压力小
├── 缺点：断线后用户可能 5 分钟看不到新通知
└── 结论：用户体验差

AdminWeb 选择 60 秒：
├── 断线后最多 1 分钟感知到新通知
├── 100 用户 = 每分钟 100 次请求，服务端轻松承受
└── 配合 SignalR 实时推送，正常情况下轮询只是"心跳确认"

🤔 导师提问：如果 SignalR 已连接且工作正常，60 秒轮询还在运行。这是不是浪费？怎么优化？

七、notification-store 中的 SignalR 集成

铃铛组件通过 useNotificationStore 使用 SignalR，但实际的 SignalR 注册逻辑在 store 中：

// notification-store.ts 核心片段

let _handlerRef: ((...args: unknown[]) => void) | null = null

initSignalR: () => {
  // 防止重复注册
  if (_handlerRef) return

  // 确保 WebSocket 连接已建立
  startConnection()

  const handler = (message: unknown) => {
    const msg = message as {
      type: string
      title?: string
      body?: string
      payload?: { recordId?: string; dataJson?: string }
    }
    // 仅处理 type 为 "notification" 的消息
    if (msg.type === "notification") {
      const notification: NotificationDto = {
        id: msg.payload?.recordId ?? crypto.randomUUID(),
        templateCode: "",
        channel: NotificationChannel.InApp,
        status: NotificationStatus.Sent,
        priority: NotificationPriority.Normal,
        title: msg.title,
        body: msg.body,
        dataJson: msg.payload?.dataJson,
        creationTime: new Date().toISOString(),
      }
      get().onNewNotification(notification)

      // 打印任务通知：解析 dataJson 显示可操作 toast
      if (notification.dataJson) {
        try {
          const data = JSON.parse(notification.dataJson)
          if (data.status === "completed" && data.jobId) {
            toast.success(notification.title ?? "渲染完成", {
              description: notification.body,
              action: {
                label: "下载",
                onClick: () => downloadJob(data.jobId, data.downloadUrl),
              },
              duration: 10000,
            })
          } else if (data.status === "failed") {
            toast.error(notification.title ?? "渲染失败", {
              description: notification.body,
              duration: 10000,
            })
          }
        } catch {
          // dataJson 不是合法 JSON，忽略
        }
      }
    }
  }

  _handlerRef = handler
  platformHub.on("ReceiveNotification", handler)
},

disposeSignalR: () => {
  if (_handlerRef) {
    platformHub.off("ReceiveNotification", _handlerRef)
    _handlerRef = null
  }
},

⚠️ 【易错点】_handlerRef 的防重复注册机制
initSignalR 开头检查 if (_handlerRef) return，这是防止重复注册的关键。如果铃铛组件被多次挂载/卸载（比如路由切换），每次挂载都会调用 initSignalR。没有这个守卫，同一个 handler 会被注册多次，导致同一条通知弹出多个 toast。

🤔 导师提问：initSignalR 在 if (_handlerRef) return 之后调用 startConnection()，但如果 startConnection() 失败了呢？handler 仍然被注册了，但连接没建立，消息永远不会到达。这有问题吗？

八、组件卸载时的资源清理

return () => {
  clearInterval(timer)    // 清除定时器
  disposeSignalR()        // 移除 SignalR 监听
}

如果不清理会怎样？

泄漏类型后果
setInterval 未清除组件卸载后仍然每 60 秒发 HTTP 请求，浪费流量 + 服务端压力
disposeSignalR 未调用SignalR handler 仍然在处理消息，_handlerRef 不为 null，下次挂载时 initSignalR 直接 return，新组件收不到通知
mousedown 监听器未移除组件卸载后点击事件处理器仍然绑定在 document 上，可能操作已卸载的组件状态

⚠️ 【设计取舍】徽标放在顶栏 Header 还是侧边栏 Sidebar？

方案对比：

┌─── 顶栏 Header ────────────────────────┐
│ Logo    搜索    🔔③  用户头像  ▼        │ ← 徽标在右上角
└────────────────────────────────────────┘

┌─── 侧边栏 Sidebar ────────────────────┐
│ 📊 仪表盘                              │
│ 📋 订单管理                            │
│ 🔔 通知中心  ③                         │ ← 徽标在菜单项旁边
│ ⚙️ 系统设置                            │
└────────────────────────────────────────┘
维度顶栏 Header侧边栏 Sidebar
可见性任何页面都可见侧边栏收起时不可见
视觉冲击角标醒目（红色+脉冲动画）菜单项旁数字，不够醒目
点击距离鼠标移动距离短需要先展开侧边栏
下拉面板空间有足够空间展开侧边栏宽度受限

AdminWeb 选择顶栏方案，原因是通知的全局性和紧急性——用户需要无论在哪个页面、无论侧边栏是否展开，都能第一时间感知到新通知。

验证步骤

在继续下一节之前，用以下步骤验证铃铛组件是否正确运行：

  1. 刷新页面，观察铃铛图标上的红色徽标数字。打开 Network 面板，应该看到请求 GET /notify-api/api/notifications/unread-count → 200
  2. 在另一个浏览器标签页中，用管理员账号发送一条通知，观察当前页面的铃铛徽标是否立即 +1，是否弹出了 toast 通知
  3. 点击铃铛图标，观察下拉面板是否出现，Network 面板应该有请求 GET /notify-api/api/notifications?page=1&pageSize=10
  4. 点击一条未读通知（蓝色背景），观察蓝点是否消失、背景是否变白、徽标数字是否 -1
  5. 点击"全部已读"按钮，所有通知背景变白、蓝点消失、徽标归零
  6. 导航到另一个路由（铃铛组件卸载），确认没有报错（如 Can't perform a React state update on an unmounted component），回到有铃铛的页面，确认 SignalR 重新初始化正常

踩坑提醒

  1. _handlerRef 必须防重复注册：铃铛组件被多次挂载/卸载时，每次挂载都会调用 initSignalR。没有守卫，同一个 handler 会被注册多次，导致同一条通知弹出多个 toast
  2. SignalR 推送和轮询存在竞态：轮询返回旧值可能覆盖 SignalR 推送的新值。AdminWeb 选择"容忍短时不一致 + 下次轮询自修正"的务实策略
  3. 下载文件用 axios 而非 window.open：因为需要注入 Token（Authorization header），window.open 无法携带自定义 header
  4. mousedown 而非 click 实现点击外部关闭：click 事件在 mouseup 时触发，如果用户在面板内按下鼠标拖到面板外松开，click 会关闭面板，但 mousedown 不会
  5. 组件卸载必须清理定时器和 SignalR 监听：否则会造成内存泄漏和"对已卸载组件执行 state 更新"的警告

  2. 点击外部关闭用 mousedown 而非 click，具体哪个场景会有差异？
