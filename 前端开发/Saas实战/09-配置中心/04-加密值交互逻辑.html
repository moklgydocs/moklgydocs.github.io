04 - 加密值交互逻辑：Dialog 表单与安全操作

这一步解决什么问题？
配置中心最复杂的交互在 Dialog 表单中——尤其是加密值的处理：新增时勾选加密、编辑时留空保留原值、删除时的二次确认、强制重载的即时生效。这节我们深入每一个 CRUD 操作的实现细节。

ASP.NET Core 开发者的直觉：加密值交互 ≈ 你在管理 ConnectionStrings 中的密码字段——展示时脱敏（***），修改时可选留空保留，新增时必须明文输入。

前置知识

  • 熟悉上一节（03-配置页面组件）中 ConfigPage 的 State 设计和渲染结构
  • 了解 AES-256 对称加密的基本概念（加密/解密使用同一密钥）
  • 理解 React 受控组件与 Dialog 开关控制模式

一、CRUD 操作总览

┌────────────────────────────────────────────────────────────────┐
│  操作      │ 触发方式        │ Dialog          │ API 方法     │
├────────────┼─────────────────┼─────────────────┼──────────────┤
│  新增      │ "新增配置"按钮   │ Upsert Dialog   │ POST /api/   │
│            │                 │ (editItem=null) │ runtime-config│
├────────────┼─────────────────┼─────────────────┼──────────────┤
│  编辑      │ 铅笔图标        │ Upsert Dialog   │ POST /api/   │
│            │                 │ (editItem=item) │ runtime-config│
├────────────┼─────────────────┼─────────────────┼──────────────┤
│  删除      │ 垃圾桶图标      │ Delete Dialog   │ DELETE /api/ │
│            │                 │ (deleteKey=key) │ runtime-     │
│            │                 │                 │ config/{key} │
├────────────┼─────────────────┼─────────────────┼──────────────┤
│  强制重载  │ "强制重载"按钮  │ 无（toast 确认）│ POST /api/   │
│            │                 │                 │ runtime-     │
│            │                 │                 │ config/reload│
└────────────┴─────────────────┴─────────────────┴──────────────┘

💡 【设计取舍】 新增和编辑共用一个 Dialog + 一个 API（POST Upsert）。通过 editItem 是否为 null 区分模式。这比两个 Dialog + 两个 API 更简洁。

二、新增流程

2.1 打开新增 Dialog

function openCreate() {
  setEditItem(null)         // null = 新增模式
  setForm(EMPTY_FORM)       // 清空表单
  setDialogOpen(true)       // 打开 Dialog
}

⚠️ 【易错点】 必须先 setEditItem(null) 再 setForm(EMPTY_FORM)！虽然 React 会批量更新 State，但语义上先切换模式再清空数据，代码意图更清晰。

⚠️ 【易错点】 浏览器密码自动填充！新增配置项的 Value 输入框可能被浏览器的"自动填充密码"功能干扰——浏览器检测到 type="password" 的输入框，会自动填入保存的密码。解决方案：给 Input 加 autoComplete="new-password" 或 autoComplete="off"，告诉浏览器这是新密码字段，不要自动填充。

2.2 新增 Dialog 表单

<Dialog open={dialogOpen} onOpenChange={open => { if (!open) closeDialog() }}>
  <DialogContent className="max-w-lg">
    <DialogHeader>
      <DialogTitle>{editItem ? "编辑配置项" : "新增配置项"}</DialogTitle>
      <DialogDescription>
        {editItem
          ? `修改配置项 "${editItem.key}"，保存后服务将在 5 秒内热重载。`
          : "填写配置键值，保存后服务将在 5 秒内热重载。"}
      </DialogDescription>
    </DialogHeader>

    <div className="space-y-4 py-2">
      {/* Key */}
      <div className="space-y-1.5">
        <Label htmlFor="cfg-key">Key <span className="text-destructive">*</span></Label>
        <Input
          id="cfg-key"
          placeholder="例如：Jwt:Secret、Storage:MinIO:AccessKey"
          value={form.key}
          onChange={e => setForm(f => ({ ...f, key: e.target.value }))}
          disabled={!!editItem}
          className="font-mono text-sm"
        />
        {editItem && (
          <p className="text-xs text-muted-foreground">编辑时 Key 不可修改。若需更换 Key，请删除后重新新增。</p>
        )}
      </div>
      {/* ... 其他字段 ... */}
    </div>
  </DialogContent>
</Dialog>

逐行精讲：

标记代码解读
【易错点】onOpenChange={open => { if (!open) closeDialog() }}只处理关闭事件！open=true 由按钮触发（openCreate/openEdit），不由 Dialog 的 onOpenChange 触发。避免点击背景关闭后又立即重新打开
【设计取舍】{editItem ? "编辑配置项" : "新增配置项"}标题根据模式变化！用户一看标题就知道当前是新增还是编辑
【易错点】disabled={!!editItem}编辑时 Key 禁用！双重否定 !! 把 `ConfigItemDto
【设计取舍】className="font-mono text-sm"Key 输入框用等宽字体！因为 Key 是代码标识符（Jwt:Secret），等宽字体更易辨认

三、编辑流程

3.1 打开编辑 Dialog

function openEdit(item: ConfigItemDto) {
  setEditItem(item)    // 非 null = 编辑模式
  setForm({
    key: item.key,
    value: item.isEncrypted ? "" : item.value,   // ← 加密项清空！
    environment: item.environment,
    isEncrypted: item.isEncrypted,
    description: item.description ?? "",
    groupName: item.groupName,
    groupSort: item.groupSort,
    sort: item.sort,
    impactScope: item.impactScope,
  })
  setDialogOpen(true)
}

逐行精讲：

标记代码解读
【易错点】value: item.isEncrypted ? "" : item.value加密项的 value 清空！后端返回的是密文，不能显示在输入框中。用户如果要修改加密值，需要重新输入明文

⚠️ 【易错点】 编辑加密项时，如果后端返回的 value 是密文（而非脱敏的 ******），而你忘记清空直接显示在 Input 中，用户会看到一串乱码。更危险的是，如果用户没注意直接点"保存"，密文会被当作新明文再次加密，导致原始值彻底丢失且无法恢复！

🤔 导师提问：编辑加密项时 value 清空而非填入密文，这是前端逻辑还是后端逻辑保证的？答案是前端——后端 API 返回的 value 可能是密文也可能是脱敏值，取决于后端实现。前端必须根据 isEncrypted 字段判断是否清空。如果前端不做判断，密文就可能被当作新值提交——这是一个前端必须防御的安全边界。
| 【设计取舍】 | description: item.description ?? "" | null 转 ""！表单 Input 的 value 不能是 null（受控组件），必须转为空字符串 |
| 【易错点】 | groupName: item.groupName | 直接赋值，不转换！groupName 在 DTO 中是 string \| null，在 Form 中也是 string \| null，类型一致 |

3.2 编辑模式下的 Value 输入

<Label htmlFor="cfg-value">
  Value
  {editItem?.isEncrypted && (
    <span className="ml-2 text-xs text-warning">留空 = 保留原加密值</span>
  )}
</Label>
<Input
  id="cfg-value"
  placeholder={editItem?.isEncrypted ? "留空保留原值，输入新值覆盖" : "配置值"}
  value={form.value}
  onChange={e => setForm(f => ({ ...f, value: e.target.value }))}
  type={form.isEncrypted ? "password" : "text"}
  className="font-mono text-sm"
/>

逐行精讲：

标记代码解读
【设计取舍】留空 = 保留原加密值黄色警告标签！只有编辑加密项时才显示，提示用户"不输入就是不改"
【易错点】type={form.isEncrypted ? "password" : "text"}动态切换输入类型！勾选加密时变成密码框（显示 ***），取消加密时变回普通文本框
【设计取舍】placeholder 根据模式变化新增时提示"配置值"，编辑加密项时提示"留空保留原值"。上下文感知的占位符

四、加密复选框交互

<div className="flex items-center gap-2.5">
  <Checkbox
    id="cfg-encrypted"
    checked={form.isEncrypted}
    onCheckedChange={checked => setForm(f => ({ ...f, isEncrypted: !!checked }))}
  />
  <Label htmlFor="cfg-encrypted" className="cursor-pointer text-sm">
    AES-256 加密存储（密码、AppSecret、Token 等敏感值请勾选）
  </Label>
</div>

加密复选框影响两个行为：

  1. Value 输入框类型：isEncrypted=true → type="password"，输入时显示 ***
  2. 保存时后端处理：勾选后后端会用 AES-256 加密明文再存储

⚠️ 【易错点】 onCheckedChange 的 checked 参数类型是 boolean | "indeterminate"！Radix UI 的 Checkbox 支持三态（未选中/选中/半选）。用 !!checked 转为布尔值，"indeterminate" → true。

🤔 导师提问：加密复选框勾选后 Value 输入框切换为 type="password"，显示 ***。但 type="password" 的输入框有个副作用——用户无法确认自己输入的内容是否正确。如果用户在加密项里输入了一个很长的密钥，怎么确认没打错字？ASP.NET Core 的 PasswordBox 有"显示密码"按钮，配置中心的 Dialog 应该加吗？

4.1 加密状态切换的边界情况

用户操作序列                    →  前端行为
──────────────────────────────────────────
新增时勾选加密 → 输入值         →  type="password"，提交时后端加密
新增时取消加密 → 输入值         →  type="text"，提交时后端明文存储
编辑加密项 → value 留空         →  后端保留原加密值（不覆盖）
编辑加密项 → value 有值         →  后端用新值覆盖（重新加密）
编辑加密项 → 取消加密勾选       →  ⚠️ 危险操作！明文存储原加密值

⚠️ 【易错点】 编辑加密项时取消加密勾选是危险操作！但当前代码没有阻止此操作。理想情况下，取消加密时应该弹出确认："此配置项当前加密存储，取消加密后将以明文保存。是否继续？"

⚠️ 【设计取舍】 客户端脱敏 vs 服务端脱敏——加密值的 ****** 显示由谁负责？

┌──────────────────┬────────────────────────────────┬───────────────────────────────┐
│ 方案              │ 实现方式                         │ 优劣                           │
├──────────────────┼────────────────────────────────┼───────────────────────────────┤
│ 服务端脱敏        │ 后端 API 返回 value="******"     │ 安全——明文永不离开服务端         │
│（当前方案）       │ 前端直接显示                     │ 但用户无法区分"真的 ****** "    │
│                  │                                 │ 和"脱敏后的 ******"             │
├──────────────────┼────────────────────────────────┼───────────────────────────────┤
│ 客户端脱敏        │ 后端 API 返回真实密文/明文        │ 灵活——前端可以提供"显示/隐藏"   │
│                  │ 前端根据 isEncrypted 遮盖显示     │ 但明文经过网络传输（HTTPS 保护）│
│                  │                                 │ DevTools 可见                   │
└──────────────────┴────────────────────────────────┴───────────────────────────────┘

当前方案选择服务端脱敏：后端返回 `******`，前端不接触明文。
这是更安全的方案——即使 HTTPS 被中间人攻击，攻击者也只能拿到脱敏后的值。
代价是用户无法"一键显示"加密值，必须重新输入才能修改。

⚠️ 【性能陷阱】 加密/解密的网络往返：每次保存加密配置项，请求链路是：

前端提交明文 → 后端 API → AES-256 加密 → 写入存储 → 返回结果
                                    ↑
                        每次保存都触发一次加密操作

对于普通配置项，保存只是简单的字符串写入。但加密项每次保存都要经过 AES-256 加密计算。在 100+ 并发编辑加密项的场景下，这可能成为性能瓶颈。不过实际场景中，配置项编辑是低频操作，这个性能陷阱基本不会触发。

🤔 导师提问：为什么不在前端做 AES-256 加密？如果前端加密，后端只接收密文并直接存储，好处是明文不经过网络传输。但坏处是什么？提示：1）前端加密密钥必须存在浏览器中——任何人打开 DevTools 都能看到密钥；2）不同用户可能用不同密钥加密，后端无法统一解密；3）前端 JavaScript 的加密性能远低于后端 C# 的 System.Security.Cryptography。

五、提交保存

async function handleSubmit() {
  if (!form.key.trim()) {
    toast.error("Key 不能为空")
    return
  }
  if (!form.value.trim() && !editItem?.isEncrypted) {
    toast.error("Value 不能为空")
    return
  }
  setSaving(true)
  try {
    await http.post("/api/runtime-config", form)
    toast.success(`"${form.key}" 已保存，热重载将在 5 秒内生效`)
    closeDialog()
    fetchItems()
  } catch (err) {
    toast.error("保存失败", { description: err instanceof Error ? err.message : String(err) })
  } finally {
    setSaving(false)
  }
}

逐行精讲：

标记代码解读
【易错点】!form.value.trim() && !editItem?.isEncrypted双重条件！非加密项 Value 不能为空；加密项编辑时 Value 可以为空（保留原值）。注意 editItem?.isEncrypted 的可选链——新增时 editItem 为 null，?. 安全返回 undefined（falsy）

🤔 导师提问：!form.value.trim() && !editItem?.isEncrypted 这个条件，如果用户在编辑一个非加密项时故意输入空格（" "），trim() 后为空字符串，验证能通过吗？答案是能——!"".trim() = !"" = true，会提示"Value 不能为空"。但如果用 !form.value 代替 !form.value.trim()，空格就能通过验证——这就是为什么要用 trim()。
| 【设计取舍】 | toast.success(...) 在 closeDialog() 之前 | 先提示成功再关闭弹窗！如果先关闭再提示，toast 可能被用户忽略。先提示让用户确认操作成功 |
| 【设计取舍】 | closeDialog() + fetchItems() | 关闭弹窗 + 刷新列表！先关闭弹窗（用户不用等刷新），再异步刷新列表 |
| 【易错点】 | finally { setSaving(false) } | 无论成功失败都关闭 saving 状态！如果不加 finally，失败时按钮永远 disabled |

5.1 新增 vs 编辑的 API 行为

新增：POST /api/runtime-config { key: "NewKey", value: "xxx", ... }
  → 后端检测 key 不存在 → 创建新配置项

编辑：POST /api/runtime-config { key: "ExistingKey", value: "yyy", ... }
  → 后端检测 key 已存在 → 更新该配置项

💡 两次操作走同一个 API，后端根据 Key 是否存在决定 Insert 还是 Update。这就是 Upsert（Update or Insert）语义。

六、删除流程

async function handleDelete() {
  if (!deleteKey) return
  setDeleting(true)
  try {
    await http.del(`/api/runtime-config/${encodeURIComponent(deleteKey)}`)
    toast.success(`配置项 "${deleteKey}" 已移除`)
    setDeleteKey(null)
    fetchItems()
  } catch (err) {
    toast.error("删除失败", { description: err instanceof Error ? err.message : String(err) })
    setDeleteKey(null)
  } finally {
    setDeleting(false)
  }
}

逐行精讲：

标记代码解读
【易错点】encodeURIComponent(deleteKey)URL 编码！配置 Key 可能含特殊字符（如 Jwt:Secret 中的冒号），不编码会导致 URL 解析错误
【设计取舍】setDeleteKey(null) 在成功和失败时都调用关闭删除确认 Dialog！无论删除成功或失败都关闭弹窗。成功时先 toast 提示再关闭；失败时先提示错误再关闭
【易错点】if (!deleteKey) return防御性检查！handleDelete 绑定在 Dialog 的确认按钮上，但 Dialog 可能因意外状态打开。检查 deleteKey 确保"确认删除"确实有目标

6.1 删除确认 Dialog

<Dialog open={!!deleteKey} onOpenChange={open => { if (!open) setDeleteKey(null) }}>
  <DialogContent className="max-w-sm">
    <DialogHeader>
      <DialogTitle>确认删除？</DialogTitle>
      <DialogDescription>
        将永久删除配置项 <span className="font-mono font-semibold">{deleteKey}</span>。
        服务在下次轮询（5 秒内）或强制重载后不再读取此配置。
        <br />此操作不可撤销。
      </DialogDescription>
    </DialogHeader>
    <DialogFooter>
      <Button variant="outline" onClick={() => setDeleteKey(null)} disabled={deleting}>取消</Button>
      <Button variant="destructive" onClick={handleDelete} disabled={deleting}>
        {deleting ? "删除中..." : "确认删除"}
      </Button>
    </DialogFooter>
  </DialogContent>
</Dialog>

⚠️ 【易错点】 open={!!deleteKey} — 用 deleteKey 是否存在来控制 Dialog 开关，而不是单独的 deleteDialogOpen State！这比多一个 State 更简洁，deleteKey 既有"是否打开"的语义又有"删除谁"的值。

💡 ASP.NET Core 类比：删除确认 ≈ MessageBox.Show("确认删除?", MessageBoxButtons.YesNo)。destructive 变体 ≈ 红色按钮，视觉警告用户"这是危险操作"。

七、强制重载

async function handleReload() {
  setReloading(true)
  try {
    await http.post("/api/runtime-config/reload")
    toast.success("IConfiguration 已强制刷新，新配置立即生效")
    fetchItems()
  } catch (err) {
    toast.error("热重载失败", { description: err instanceof Error ? err.message : String(err) })
  } finally {
    setReloading(false)
  }
}

💡 ASP.NET Core 类比：handleReload ≈ IConfiguration.Reload()。在 ASP.NET Core 中，IConfiguration 默认文件变更时自动重载（reloadOnChange: true），但数据库中的运行时配置需要手动触发刷新。

⚠️ 【设计取舍】 为什么需要强制重载？因为 5 秒轮询可能不够快——如果运维改完配置后急需验证，等 5 秒太久。强制重载 = 立即从数据库重新加载所有配置，跳过轮询间隔。

7.1 何时需要强制重载？

普通场景：保存配置 → 等 5 秒 → 自动热重载 → 生效
  ↓ 大多数情况够用

紧急场景：保存配置 → 点击"强制重载" → 立即生效
  ↓ 用于以下情况：
  1. 安全密钥泄露后紧急更换，1 秒都不能等
  2. 配置写错了导致服务异常，急需回滚
  3. 上线前验证配置是否正确

八、Dialog 通用逻辑

function closeDialog() {
  setDialogOpen(false)
  setEditItem(null)
  setForm(EMPTY_FORM)
}

⚠️ 【易错点】 必须按顺序清空三个 State！

State清空原因
dialogOpen=false关闭弹窗
editItem=null重置模式（下次新增时 !!editItem=false，Key 不禁用）
form=EMPTY_FORM清空表单（防止下次打开时显示上次数据）

如果忘记清空 editItem：关闭编辑 Dialog 后点"新增配置"，Key 输入框会被禁用（因为 editItem 还是非 null）。

如果忘记清空 form：下次打开 Dialog 时，表单会显示上一次的数据——这就是脏数据泄漏。

🔧 验证步骤

在继续思考题之前，我们用实际操作验证本节的核心知识点：

验证 1：新增 vs 编辑的 Dialog 模式切换

1. 打开配置中心页面，点击"新增配置"按钮
2. 确认 Dialog 标题为"新增配置项"，Key 输入框可编辑
3. 关闭 Dialog，点击某个配置项的编辑按钮
4. 确认 Dialog 标题为"编辑配置项"，Key 输入框被禁用
5. 关闭 Dialog 后再次点击"新增配置"，确认 Key 输入框恢复可编辑（验证 closeDialog 清空了 editItem）

验证 2：加密值的编辑行为

1. 找到一个 isEncrypted=true 的配置项，点击编辑

⚠️ 踩坑提醒

  1. 编辑加密项时密文被当作新明文提交：编辑加密项时如果不清空 value，后端返回的密文会显示在 Input 中。用户未注意直接点"保存"，密文会被当作新明文再次加密，导致原始值彻底丢失且无法恢复。前端必须根据 isEncrypted 清空 value。
  2. 浏览器密码自动填充干扰：type="password" 的输入框可能被浏览器自动填充已保存的密码。解决方案：加 autoComplete="new-password" 或 autoComplete="off"。
  3. 取消加密勾选是危险操作：编辑加密项时取消 isEncrypted 勾选，后端会以明文存储原加密值。当前代码没有阻止此操作，理想情况下应弹出二次确认。
  4. closeDialog 必须清空三个 State：dialogOpen、editItem、form 必须按顺序清空。忘记清空 editItem 会导致下次新增时 Key 被禁用；忘记清空 form 会导致脏数据泄漏。
  5. encodeURIComponent(deleteKey) 不可省略：配置 Key 含冒号（如 Jwt:Secret），不编码会导致 URL 解析错误。
