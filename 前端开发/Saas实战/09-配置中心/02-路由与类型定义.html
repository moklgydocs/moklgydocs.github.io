02 - 路由与类型定义：Props 驱动的组件复用

这一步解决什么问题？
配置中心是 AdminWeb 中最特殊的模块——一个 ConfigPage 组件服务 5 个后端微服务。这节我们深入理解路由如何通过 Props 驱动组件行为，以及配置项的类型定义如何体现前后端契约。

ASP.NET Core 开发者的直觉：路由配置 ≈ Program.cs 里的 app.MapController()，类型定义 ≈ 你的 DTO 类。但配置中心的特殊之处在于——路由不仅是"跳转到页面"，还负责"注入后端地址"。

前置知识

  • 了解 React Router v6 的嵌套路由与 <Route> 配置
  • 理解 TypeScript interface 与 C# class 的类型映射关系
  • 熟悉上一节（01-运行时配置概述）中配置中心的整体架构

一、路由配置精读

// src/App.tsx
const ConfigPage = lazy(() => import("@/pages/config"))

// 配置中心 /config/*：各微服务的运行时配置
<Route path="config">
  <Route index element={<Navigate to="/config/perm-center" replace />} />
  <Route path="perm-center"        element={<Lazy><ConfigPage serviceBaseUrl="/perm-api"    serviceLabel="权限中心" /></Lazy>} />
  <Route path="file-service"       element={<Lazy><ConfigPage serviceBaseUrl="/file-api"    serviceLabel="文件服务" /></Lazy>} />
  <Route path="print-service"      element={<Lazy><ConfigPage serviceBaseUrl="/print-api"   serviceLabel="打印服务" /></Lazy>} />
  <Route path="miniapp-platform"   element={<Lazy><ConfigPage serviceBaseUrl="/miniapp-api"  serviceLabel="小程序平台" /></Lazy>} />
  <Route path="notification-center" element={<Lazy><ConfigPage serviceBaseUrl="/notify-api" serviceLabel="通知中心" /></Lazy>} />
</Route>

逐行解析：

标记代码解读
【设计取舍】const ConfigPage = lazy(...)配置中心只懒加载一个组件！不像权限中心那样 PermAppsPage、PermRolesPage 各自独立懒加载
【易错点】<Navigate to="/config/perm-center" replace />replace 很重要！不加的话浏览器后退会回到 /config，又触发重定向，形成死循环
【设计取舍】serviceBaseUrl="/perm-api"前缀对应 Vite proxy 规则。每个微服务一个前缀，一个代理规则，一个后端地址
【设计取舍】serviceLabel="权限中心"纯展示用，出现在 PageHeader 标题中。和路由路径 perm-center 解耦——路径用英文（URL 安全），标签用中文（用户友好）

🤔 导师提问：如果你在浏览器地址栏直接输入 /config/（不指定具体服务），会发生什么？追踪一下代码——<Route index> 匹配 → <Navigate to="/config/perm-center" replace /> → 立即跳转到权限中心。如果不加 replace，浏览器历史栈会多一条 /config 记录，后退时又触发重定向——形成"回不去"的死循环。

1.1 Vite 代理映射

5 个 serviceBaseUrl 对应 5 个 Vite proxy 规则：

前端 serviceBaseUrl    →  Vite Proxy  →  后端地址
─────────────────────────────────────────────────────
/perm-api              →  rewrite      →  http://moklgy.me:10002
/file-api              →  rewrite      →  http://moklgy.me:10011
/print-api             →  rewrite      →  http://moklgy.me:11010
/miniapp-api           →  rewrite      →  http://moklgy.me:5020
/notify-api            →  rewrite      →  http://moklgy.me:10012

完整请求链路（以权限中心为例）：

浏览器 fetch("/perm-api/api/runtime-config")
         │
         ▼ Vite Dev Server
http://moklgy.me:10002/api/runtime-config
         │
         ▼ ASP.NET Core PermCenter
GET /api/runtime-config → ConfigController.GetAll()

💡 ASP.NET Core 类比：这和 IHttpClientFactory 的命名客户端如出一辙：

// 后端等价写法
builder.Services.AddHttpClient("PermCenter", c => c.BaseAddress = new Uri("http://moklgy.me:10002"));
builder.Services.AddHttpClient("FileService", c => c.BaseAddress = new Uri("http://moklgy.me:10011"));
// ...

二、ConfigPageProps 类型定义

// src/pages/config/index.tsx
interface ConfigPageProps {
  /** 目标服务的 Vite proxy 前缀，用于创建 HTTP 客户端 */
  serviceBaseUrl: string
  /** 目标服务的显示名称，用于 PageHeader 标题 */
  serviceLabel: string
}

逐行精讲：

字段类型为什么
serviceBaseUrlstring传入 createHttp() 创建绑定特定后端的 axios 实例。值必须是 Vite proxy 中已配置的前缀
serviceLabelstring纯 UI 展示，出现在 "${serviceLabel} — 运行时配置" 标题中

⚠️ 【易错点】 Props 是只读的！组件内部不能修改 serviceBaseUrl。如果需要切换后端，必须通过路由跳转（改变 URL），React Router 会重新渲染组件并传入新 Props。

🤔 导师提问：如果用户在权限中心的配置页面点了一个链接跳转到文件服务的配置页面，React 是复用同一个组件实例还是销毁重建？答案是——取决于 serviceBaseUrl 是否变化。如果 key（即 serviceBaseUrl）变了，React 会卸载旧组件、挂载新组件，useMemo 重新计算，fetchItems 重新请求。这和 ASP.NET Core 的 Scoped 服务生命周期类似——每个请求创建新实例。

2.1 Props 在组件内的使用

export default function ConfigPage({ serviceBaseUrl, serviceLabel }: ConfigPageProps) {
  // 1. 用 serviceBaseUrl 创建 HTTP 客户端
  const http = useMemo(() => createHttp(serviceBaseUrl), [serviceBaseUrl])

  // 2. 用 serviceLabel 展示页面标题
  <PageHeader
    title={`${serviceLabel} — 运行时配置`}
    description="配置写入后 5 秒内自动热重载。加密项以 AES-256 存储。"
  />

  // 3. 用 http 发请求
  const res = await http.get<ConfigItemDto[]>("/api/runtime-config")
}

逐行精讲：

标记代码解读
【易错点】useMemo(() => createHttp(serviceBaseUrl), [serviceBaseUrl])必须 useMemo！不加的话每次渲染都创建新的 axios 实例，导致请求拦截器重复注册、Token 刷新逻辑异常
【设计取舍】useMemo 依赖 [serviceBaseUrl]理论上同一个路由 serviceBaseUrl 不会变（Props 由路由决定），但加上依赖是防御性编程——如果未来路由参数可变，组件能正确响应
【易错点】http.get<ConfigItemDto[]>("/api/runtime-config")路径不含 serviceBaseUrl！createHttp 已经设置了 baseURL，这里只写后端路径

🤔 导师提问：如果 createHttp 返回的 axios 实例已经设置了 baseURL，那请求路径为什么不能写成 /perm-api/api/runtime-config？因为 baseURL + url 是直接拼接的，写成 /perm-api/api/runtime-config 会变成 /perm-api/api/runtime-config（baseURL 被忽略，因为 url 以 / 开头是绝对路径）。这是 axios 的 URL 解析规则——以 / 开头的路径会忽略 baseURL。

三、配置项 DTO：ConfigItemDto

// src/pages/config/index.tsx（类型定义在组件文件内）
interface ConfigItemDto {
  /** 配置键，如 "Jwt:Secret"、"Storage:MinIO:AccessKey" */
  key: string
  /** 配置值（加密项返回密文） */
  value: string
  /** 环境标识（空=全局，"Production"=仅生产环境） */
  environment: string
  /** 是否 AES-256 加密存储 */
  isEncrypted: boolean
  /** 配置说明（用途、取值范围） */
  description: string | null
  /** 分组名称（如 "SSO 认证"） */
  groupName: string | null
  /** 分组排序号 */
  groupSort: number
  /** 组内排序号 */
  sort: number
  /** 修改影响范围（风险提示文本） */
  impactScope: string | null
  /** 最后更新时间（ISO 8601） */
  updatedAt: string
}

逐行精讲：

字段类型为什么
keystring配置的业务主键。格式模仿 appsettings.json 的层级路径，用 : 分隔（ASP.NET Core 的 Configuration 约定）
valuestring统一为字符串！即使数字配置也存字符串，后端在 IConfiguration 中按需转换。这和 appsettings.json 的行为一致
environmentstring空字符串 = 全局配置，"Production" = 仅生产环境生效。类似 appsettings.Production.json 的覆盖机制
【易错点】 isEncryptedboolean查询时加密项的 value 字段返回密文（不可读），不是明文！前端需要用 ****** 遮盖
descriptionstring | null可空！老配置可能没有描述。前端用 ?? 安全访问
【设计取舍】 groupName + groupSort + sort三个排序字段groupSort 控制分组顺序，sort 控制组内顺序。双层排序确保配置列表稳定有序
【易错点】 impactScopestring | null这是风险提示！包含"危险"、"失败"等关键词时会变红显示。不是所有配置都需要风险提示
updatedAtstringISO 8601 字符串，前端用 new Date(item.updatedAt).toLocaleString("zh-CN") 格式化

💡 ASP.NET Core 类比：ConfigItemDto ≈ 你在 appsettings.json 中的一个键值对 + 元数据（描述、分组、排序、风险提示）。IConfiguration 只存 key-value，这里的 DTO 是增强版。

⚠️ 【易错点】 前后端类型不一致可能导致运行时错误！后端 C# 的 ConfigItemDto 中 Value 字段对加密项返回密文，但 TypeScript 的类型定义仍然是 value: string——TypeScript 无法区分"这是明文"还是"这是密文/脱敏值"。如果前端代码假设 value 始终是明文，对加密项做解析就会出错。这也是为什么编辑加密项时前端必须清空 value——类型系统帮不了我们，只能靠业务逻辑保证安全。

⚠️ 【设计取舍】 Union Type vs String Literal：value 应该用更精确的类型吗？

// 当前方案：所有值都是 string
value: string

// 替代方案：用 union type 区分明文和脱敏值
value: string  // 明文
maskedValue: string  // "******" 脱敏值

// 替代方案2：用 branded type 标记
type PlainValue = string & { __brand: "Plain" }
type MaskedValue = string & { __brand: "Masked" }
value: PlainValue | MaskedValue

当前方案选择 string 是因为：1）简单，前后端类型映射直接；2）前端已经通过 isEncrypted 字段区分了处理逻辑，不需要类型系统再约束。但如果团队经常因"误把密文当明文"而出 bug，可以考虑 branded type 方案。

🤔 导师提问：C# 的 record ConfigItemDto 有类型系统保护（string Value vs bool IsEncrypted 是两个独立字段），TypeScript 也有同样的结构。但为什么在 C# 中我们不太担心"误把密文当明文"，而在 TypeScript 中更容易犯这个错误？提示：想想 C# 的 IOptions<T> 模式——Value 通常在 OnConfigure 中处理，而不是直接展示在 UI 上。

四、Upsert 请求类型

// src/pages/config/index.tsx
interface UpsertRequest {
  /** 配置键 */
  key: string
  /** 配置值（加密项留空 = 保留原值） */
  value: string
  /** 环境标识 */
  environment: string
  /** 是否加密存储 */
  isEncrypted: boolean
  /** 配置说明 */
  description: string
  /** 分组名称 */
  groupName: string | null
  /** 分组排序号 */
  groupSort: number
  /** 组内排序号 */
  sort: number
  /** 修改影响范围 */
  impactScope: string | null
}

逐行精讲：

标记字段解读
【易错点】key新增时可编辑，编辑时禁用（disabled={!!editItem}）。因为 Key 是业务主键，修改 Key 等于删除旧配置再新增新配置
【易错点】value编辑加密项时，value 留空 = 保留原加密值，有值 = 覆盖。前端用 type="password" 输入
【设计取舍】description 是 stringConfigItemDto 中是 string | null（可空），但 UpsertRequest 中是 string（必填）。新增时要求必须填写描述——这是管理要求，不是技术要求
【设计取舍】groupName 是 string | nullnull 归入"未分组"。新建时提供 <datalist> 下拉建议已有分组名

4.1 空表单常量

const EMPTY_FORM: UpsertRequest = {
  key: "",
  value: "",
  environment: "",
  isEncrypted: false,
  description: "",
  groupName: null,
  groupSort: 0,
  sort: 0,
  impactScope: null,
}

💡 【设计取舍】 为什么定义 EMPTY_FORM 常量？

  1. 新增时：setForm(EMPTY_FORM) 清空表单
  2. 关闭 Dialog 时：setForm(EMPTY_FORM) 重置状态
  3. 保证所有字段都有初始值，避免 undefined 导致的受控组件警告

⚠️ 【易错点】 不能写成 setForm({} as UpsertRequest)！空对象会导致受控 Input 的 value 为 undefined，React 会报警告并切换到非受控模式。

五、分组类型：ConfigGroup

// src/pages/config/index.tsx
interface ConfigGroup {
  /** 分组名称 */
  groupName: string
  /** 分组排序号 */
  groupSort: number
  /** 该分组下的配置项 */
  items: ConfigItemDto[]
}

这是前端专用类型，后端不返回这个结构。后端返回的是扁平的 ConfigItemDto[]，前端通过 groupConfigs 函数将其转为分组结构。

数据流转：

后端返回：
  ConfigItemDto[]（扁平数组）
      │
      ▼ groupConfigs() 函数
  ConfigGroup[]（分组结构）
      │
      ▼ filteredGroups（搜索过滤后）
  渲染：每个 ConfigGroup → 一个 Collapsible Card

⚠️ 【易错点】 ConfigGroup 没有出现在后端 API 中——它是前端的视图模型，类似于 ASP.NET 中把 List<Order> 转成 Dictionary<Customer, List<Order>> 的中间处理。

🤔 导师提问：如果后端直接返回分组后的结构（ConfigGroup[]），前端代码会变简单，但有什么代价？提示：1）后端 API 耦合了前端的展示逻辑（分组规则变了要改后端）；2）其他客户端（CLI 工具、移动端）可能不需要分组；3）分组的排序逻辑变成后端职责——你更希望排序规则在后端还是前端控制？

六、前后端类型映射对照表

┌──────────────────────────┬────────────────────────────────────┐
│ 后端 C#                  │ 前端 TypeScript                    │
├──────────────────────────┼────────────────────────────────────┤
│ class ConfigItemDto      │ interface ConfigItemDto            │
│   string Key             │   key: string                     │
│   string Value           │   value: string                    │
│   string? Environment    │   environment: string              │
│   bool IsEncrypted       │   isEncrypted: boolean              │
│   string? Description    │   description: string | null       │
│   string? GroupName      │   groupName: string | null         │
│   int GroupSort          │   groupSort: number                 │
│   int Sort               │   sort: number                     │
│   string? ImpactScope    │   impactScope: string | null       │
│   DateTime UpdatedAt     │   updatedAt: string  (ISO 8601)   │
├──────────────────────────┼────────────────────────────────────┤
│ class UpsertRequest      │ interface UpsertRequest            │
│   string Key             │   key: string                      │
│   string Value           │   value: string                    │
│   string? Description    │   description: string (必填!)      │
│   ...                    │   ...                               │
├──────────────────────────┼────────────────────────────────────┤
│ (后端不返回分组)          │ interface ConfigGroup (前端专用)   │
│                          │   groupName + groupSort + items    │
└──────────────────────────┴────────────────────────────────────┘

⚠️ 【易错点】 description 在后端是 string?（可空），但在 UpsertRequest 中前端定义为 string（必填）。这是因为：1）新增时我们要求填写描述；2）编辑时如果原值是 null，表单会显示空字符串而非 null。提交时空字符串是合法值。

⚠️ 【易错点】 environment 在后端是 string?（可空），但前端定义为 string（非空）。空字符串表示"全局配置"，"Production" 表示"仅生产环境"。后端的 null 在前端映射为空字符串 ""——这里存在隐式转换，如果后端新增了一个环境值但前端不知道，前端仍然按 string 处理，不会报类型错误。

💡 类型映射的通用规则：

C# → TypeScript 映射规则：
  string       → string
  string?      → string | null（DTO 中）或 string（Request 中，null 转空字符串）
  bool         → boolean
  int          → number
  DateTime     → string（ISO 8601 格式，前端用 new Date() 解析）
  T[]          → T[]

关键差异：
  1. C# 的 DateTime → TS 的 string：JSON 序列化后日期变成字符串
  2. C# 的可空引用类型 string? → TS 的 string | null：需要显式处理 null
  3. C# 的 PascalCase → TS 的 camelCase：JSON 序列化器自动转换（System.Text.Json 需要配置 PropertyNamingPolicy）

⚠️ 踩坑提醒

  1. <Navigate> 不加 replace 导致重定向死循环：访问 /config/ 时，<Route index> 匹配后重定向到 /config/perm-center。如果不加 replace，浏览器历史栈会多一条 /config 记录，后退时又触发重定向，形成"回不去"的死循环。
  2. axios 绝对路径忽略 baseURL：createHttp 已设置 baseURL，请求路径应以相对路径（如 /api/runtime-config）书写。如果写成 /perm-api/api/runtime-config（以 / 开头），axios 会忽略 baseURL 直接使用该路径，导致 404。
  3. EMPTY_FORM 不能用 {} as UpsertRequest：空对象会导致受控 Input 的 value 为 undefined，React 报警告并切换到非受控模式。必须用包含所有字段初始值的 EMPTY_FORM 常量。
  4. 加密项的 value 是密文/脱敏值而非明文：TypeScript 类型定义是 value: string，无法区分明文与密文。前端必须根据 isEncrypted 字段判断处理逻辑，类型系统帮不了我们。
