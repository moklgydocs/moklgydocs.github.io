03 - 配置页面组件：分组展示与 CRUD 交互

这一步解决什么问题？
配置中心的核心是一个 610 行的 ConfigPage 组件——它同时处理数据加载、分组展示、搜索过滤、新增/编辑/删除操作。这节我们逐段解析它的完整实现，理解"一个组件如何服务五个后端"。

ASP.NET Core 开发者的直觉：这个组件 ≈ 一个完整的 Razor Page（Index.cshtml + Index.cshtml.cs），数据加载 = OnGetAsync()，表单提交 = OnPostAsync()，搜索过滤 = LINQ 查询。

前置知识

  • 理解 React useState、useEffect、useMemo、useCallback 的基本用法
  • 熟悉上一节（02-路由与类型定义）中 ConfigPageProps、ConfigItemDto 等类型定义
  • 了解 shadcn/ui 的 Dialog、Card、Collapsible 等组件 API

二、State 设计

// ── 数据 ──
const [items, setItems] = useState<ConfigItemDto[]>([])

const [error, setError] = useState<string | null>(null)

// ── UI 状态 ──

逐行精讲：

标记State解读
【设计取舍】items + loading + error三件套！数据列表、加载状态、错误信息分开管理，而不是用 status: "idle" | "loading" | "error" 联合类型。这和 ASP.NET 的 Try/Catch 异常处理思路一致——错误是独立状态，不是数据的一部分
【易错点】deleteKey: string | null只存 Key，不存整个对象！删除确认 Dialog 只需要显示 Key，没必要存完整 DTO。减少 State 体积
【易错点】editItem: ConfigItemDto | null存的是原始数据，不是表单数据！editItem 用于判断"是新增还是编辑"（!!editItem），表单数据在 form 中
【设计取舍】showValues 是全局开关不是每条配置单独控制！点击一次显示/隐藏所有加密值。因为加密值通常是少数，逐条切换反而增加操作步骤
【易错点】collapsedGroups: Set<string>用 Set 而不是数组！Set.has() 是 O(1)，Array.includes() 是 O(n)。虽然配置项不多，但这是好习惯
【性能陷阱】saving / deleting / reloading 三个独立 loading如果用 loadingType: "saving" | "deleting" | ...，一个状态就够了。但分开更直观，且不会互相干扰（比如保存中不会误触发删除的 loading）

🤔 导师提问：对比 ASP.NET Core Razor Page 的 PageModel，ConfigPage 把 14 个 State 变量全放在一个组件里。在 Razor Page 中，你会把加载状态、表单状态、UI 开关分别放在什么地方？React 没有类似 TempData 或 ViewData 的机制——如果 State 越来越多，你会如何重构？

💡 ASP.NET Core 类比：

  • items ≈ List<ConfigItemDto>（属性）
  • loading ≈ IsLoading（属性）
  • error ≈ Exception（异常）
  • form ≈ [BindProperty] UpsertRequest Form（模型绑定）

三、HTTP 客户端创建

const http = useMemo(() => createHttp(serviceBaseUrl), [serviceBaseUrl])

⚠️ 【易错点】 为什么用 useMemo 而不是 useRef？

// ❌ useRef 版本：serviceBaseUrl 变化时不会重新创建
const httpRef = useRef(createHttp(serviceBaseUrl))

// ✅ useMemo 版本：serviceBaseUrl 变化时自动重新创建
const http = useMemo(() => createHttp(serviceBaseUrl), [serviceBaseUrl])

useMemo 的依赖数组确保当路由切换（serviceBaseUrl 从 /perm-api 变为 /file-api）时，HTTP 客户端会重新创建，绑定新的后端地址。useRef 不会响应 Props 变化。

💡 但实际上，在当前路由设计中，serviceBaseUrl 不会在组件生命周期内变化（路由切换 = 组件卸载重建）。useMemo 是防御性编程。

四、数据加载

const fetchItems = useCallback(async () => {
  setLoading(true)
  setError(null)
  try {
    const res = await http.get<ConfigItemDto[]>("/api/runtime-config")
    setItems(res.data ?? [])
  } catch (err: unknown) {
    const msg = err instanceof Error ? err.message : String(err)
    setError(msg)
  } finally {
    setLoading(false)
  }
}, [http])

useEffect(() => { fetchItems() }, [fetchItems])

逐行精讲：

标记代码解读
【易错点】useCallback(..., [http])依赖 http！因为 fetchItems 内部调用了 http.get。http 由 useMemo 创建，依赖 serviceBaseUrl。整条依赖链：serviceBaseUrl → http → fetchItems → useEffect
【易错点】res.data ?? []用 ?? 不用 `
【易错点】err instanceof Error ? err.message : String(err)catch 中的 err 类型是 unknown，不能直接 .message。先检查是否是 Error 实例，再安全访问
【设计取舍】setLoading(true) + finally { setLoading(false) }无论成功或失败都关闭 loading。如果只在 try 末尾关闭，失败时 loading 永远为 true

4.1 为什么不用 React Query？

AdminWeb 的数据获取是手写 useState + useEffect + useCallback，而不是用 @tanstack/react-query。

维度手写React Query
代码量多（每个请求 ~15 行）少（useQuery 一行）
缓存无（每次 mount 重新请求）自动缓存 + 后台刷新
学习曲线低（原生 React）中（需理解 Query Key、Stale Time）
适合场景配置中心（数据变化少、无实时性要求）通知中心（需要实时刷新、乐观更新）

⚠️ 【设计取舍】 配置中心选择了手写，因为配置项变化频率低（几分钟才改一次），不需要 React Query 的缓存和自动刷新。通知中心等高频场景更适合 React Query。

五、分组 + 搜索过滤

const filteredGroups = useMemo(() => {
  const groups = groupConfigs(items)
  if (!searchQuery.trim()) return groups

  const q = searchQuery.toLowerCase()
  return groups
    .map(g => ({
      ...g,
      items: g.items.filter(item =>
        item.key.toLowerCase().includes(q) ||
        (item.description ?? "").toLowerCase().includes(q) ||
        (item.value ?? "").toLowerCase().includes(q)
      ),
    }))
    .filter(g => g.items.length > 0)
}, [items, searchQuery])

逐行精讲：

标记代码解读
【设计取舍】useMemo 依赖 [items, searchQuery]只有数据或搜索词变化时才重新计算分组。输入搜索词时不触发数据请求，纯前端过滤
【易错点】q = searchQuery.toLowerCase()大小写不敏感搜索！统一转小写比较。不能用 ===（精确匹配）——用户不会输入完整的 Jwt:Secret
【易错点】(item.description ?? "").toLowerCase()description 可能为 null！null.toLowerCase() 会报错，必须用 ?? 提供默认值
【设计取舍】.filter(g => g.items.length > 0)搜索后如果某分组没有匹配项，整个分组不显示。避免空分组卡片

逐行精讲：

逐行精讲：

标记代码解读
【易错点】item.isEncrypted && !showValues双重条件！加密 AND 未开启显示。两个条件缺一不可——非加密项不受 showValues 影响
【设计取舍】select-none on ******禁止选中！防止用户复制密文遮盖符。select-none 是 Tailwind 的 user-select: none
【设计取舍】max-w-full truncate长值截断！数据库连接串可能 200+ 字符，不截断会撑破布局。title={item.value} 让鼠标悬停可看完整值
【易错点】isDangerous(item.impactScope) ? "text-destructive" : "text-warning"两级风险颜色！包含"危险"/"失败"→红色，其他→橙色。不是简单的有/无风险，而是严重/一般

🤔 导师提问：加密值的显示控制是 item.isEncrypted && !showValues——用前端 State 控制遮盖，这意味着明文值已经在浏览器内存中了。在 ASP.NET Core 中，你会如何设计 API 返回值来避免敏感配置明文传到前端？如果后端只返回 isEncrypted: true 而不返回 value，前端的"显示值"功能还能实现吗？

7.1 isDangerous 风险判断

function isDangerous(text: string): boolean {
  return /危险|失败|所有.*失败|无需认证|全部失败|切勿/.test(text)
}

⚠️ 【易错点】 这是前端硬编码的关键词匹配，不是后端返回的风险等级！如果后端新增了 impactScope 包含"致命"但前端正则没覆盖，会显示橙色而非红色。

💡 改进方向：后端可以增加 riskLevel: "high" | "medium" | "low" 字段，前端根据等级着色，而非依赖关键词匹配。

🤔 导师提问：isDangerous 用正则匹配关键词来判断风险等级——这是纯前端逻辑，后端完全不知道前端做了这个判断。在 ASP.NET Core 中，如果你要给 impactScope 增加风险等级，你会选择：A）在 DTO 中加 riskLevel 字段（后端决定），还是 B）前端维护映射表？两种方案各有什么维护成本？

🤔 导师提问：组件结构总览中 CRUD 操作占 178-268 行（约 90 行），JSX 渲染占 270-609 行（约 340 行）。渲染代码是业务逻辑的近 4 倍。在 ASP.NET Core 中，Razor 模板和 PageModel 代码通常也是这个比例吗？React 的 JSX 把逻辑和渲染混在一个文件里，你觉得这和 Razor 的"代码分离"相比，是优势还是劣势？在什么情况下你会考虑拆分组件？

⚠️ 踩坑提醒

  1. useMemo vs useRef 创建 HTTP 客户端：useMemo 依赖 serviceBaseUrl，当路由切换时自动重新创建 HTTP 实例。useRef 不会响应 Props 变化，切换服务后仍请求旧后端地址。
  2. null.toLowerCase() 会报错：搜索过滤中 description 可能为 null，必须用 ?? 提供默认值：(item.description ?? "").toLowerCase()。直接调用 null.toLowerCase() 会抛出 TypeError。
  3. res.data ?? [] 而非 res.data || []：后端可能返回空数组 []（falsy 但合法），|| 会错误地替换。?? 只在 null/undefined 时替换，语义更准确。
  4. catch 中 err 类型是 unknown：不能直接 .message，必须先 instanceof Error 检查。这是 TypeScript 严格模式的要求，忽略会导致编译错误。

🤔 思考题
