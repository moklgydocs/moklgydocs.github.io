文件预览

文件预览

|

这一步解决什么问题？ 文件上传后，用户需要在浏览器中预览文件内容——图片要直接看、PDF 要内嵌翻页、文本要代码高亮。就像后端的 PhysicalFileProvider.GetFileInfo() 返回文件流供下载一样，前端需要根据文件类型选择不同的预览策略。⚠️ 核心挑战：认证。<img src="/api/files/xxx/thumbnail"> 不会携带 Bearer Token，私有图片会 401。这是前后端分离架构下的经典问题，类比后端 API 的 [Authorize] 保护。

前置知识

  • 02 篇文件 API 层：fetchImageBlobUrl 工具函数、filesApi.getPresignedDownloadUrl() 的用法
  • 04 篇文件上传：理解文件上传后的元数据（contentType、sizeBytes 等）
  • React useRef 的使用场景：存储不触发重渲染的引用值

三种预览策略

文件类型预览方式内存管理
图片fetchImageBlobUrl → Blob URL用完必须 revokeObjectURL
PDF预签名 URL → <iframe>无需手动释放（浏览器管理）
文本/JSON预签名 URL → <iframe>同上
其他仅显示下载按钮—

🤔 导师提问：为什么图片预览不直接用预签名 URL？两种方式（Blob URL 和预签名 URL）各自的认证模型有什么区别？（提示：Blob URL 是"前端代理认证"，预签名 URL 是"后端临时凭证"）

【易错点】不支持的格式预览：当 contentType 不在以上三种策略范围内时（如 .docx、.xlsx、.mp4），组件会进入 "download" 分支，仅显示文件名和下载按钮。用户可能会困惑"为什么有的文件能预览有的不能"。更好的做法是在文件列表中就标识哪些文件支持预览（如通过 contentType 判断），避免用户点击后才发现不支持。

【设计取舍】客户端 vs 服务端预览渲染：本系统的 PDF/文本预览使用 <iframe> 加载预签名 URL，实际渲染由浏览器内置引擎完成——这是客户端渲染。另一种方案是服务端渲染预览（如后端用 Puppeteer 将 PDF 转为图片再返回），好处是兼容性更可控（不受浏览器 PDF 插件影响），坏处是服务端资源消耗大、延迟高。本系统选择客户端渲染，因为主流浏览器都支持 PDF 内嵌显示，且无需额外部署服务端渲染服务。

完整代码

来源：src/pages/file/preview-dialog.tsx

import { useState, useEffect, useCallback, useRef } from "react"
import { toast } from "sonner"
import {
  Dialog, DialogContent, DialogHeader, DialogTitle,
} from "@/components/ui/dialog"
import { Button } from "@/components/ui/button"
import { Badge } from "@/components/ui/badge"
import { Skeleton } from "@/components/ui/skeleton"
import { Tooltip, TooltipContent, TooltipTrigger } from "@/components/ui/tooltip"
import {
  ChevronLeft, ChevronRight, Download, X, ZoomIn, ZoomOut, Maximize2, RotateCcw, AlertCircle,
} from "lucide-react"
import { filesApi } from "@/api/file/files"
import type { FileObjectDto } from "@/types"
import { formatBytes, fetchImageBlobUrl } from "@/lib/file-utils"

interface FilePreviewDialogProps {
  open: boolean
  onOpenChange: (open: boolean) => void
  files: FileObjectDto[]
  initialIndex: number
  onNavigate?: (index: number) => void
}

export default function FilePreviewDialog({
  open,
  onOpenChange,
  files,
  initialIndex,
  onNavigate,
}: FilePreviewDialogProps) {
  const [currentIndex, setCurrentIndex] = useState(initialIndex)
  const [previewData, setPreviewData] = useState<{
    type: "image" | "pdf" | "text" | "download"
    url?: string
    fileName?: string
    sizeBytes?: number
    contentType?: string
  } | null>(null)
  const [loading, setLoading] = useState(false)
  const [error, setError] = useState<string | null>(null)
  const [zoom, setZoom] = useState<number>(1)
  const blobUrlRef = useRef<string | null>(null)

  // 清理 Blob URL，防止内存泄漏
  useEffect(() => {
    return () => {
      if (blobUrlRef.current) {
        URL.revokeObjectURL(blobUrlRef.current)
        blobUrlRef.current = null
      }
    }
  }, [])

  const currentFile = files[currentIndex]
  const hasPrev = currentIndex > 0
  const hasNext = currentIndex < files.length - 1

  const loadPreview = useCallback(async (file: FileObjectDto) => {
    setLoading(true)
    setError(null)
    // 清理上一次的 Blob URL
    if (blobUrlRef.current) {
      URL.revokeObjectURL(blobUrlRef.current)
      blobUrlRef.current = null
    }
    setPreviewData(null)

    try {
      const contentType = file.contentType ?? "application/octet-stream"

      if (contentType.startsWith("image/")) {
        // 图片：通过 fetchImageBlobUrl 带认证获取图片
        const blobUrl = await fetchImageBlobUrl(file.id, 1024, 1024)
        blobUrlRef.current = blobUrl
        setPreviewData({
          type: "image",
          url: blobUrl,
          fileName: file.displayName ?? file.fileName,
        })
      } else if (contentType === "application/pdf") {
        // PDF：获取预签名 URL 用 iframe 嵌入
        const res = await filesApi.getPresignedDownloadUrl(file.id)
        const url = res.data?.url
        if (url) {
          setPreviewData({ type: "pdf", url, fileName: file.displayName ?? file.fileName })
        } else {
          setError("获取预览链接失败")
        }
      } else if (contentType.startsWith("text/") || contentType === "application/json") {
        // 文本：获取预签名 URL
        const res = await filesApi.getPresignedDownloadUrl(file.id)
        const url = res.data?.url
        if (url) {
          setPreviewData({ type: "text", url, fileName: file.displayName ?? file.fileName, contentType })
        } else {
          setError("获取预览链接失败")
        }
      } else {
        setPreviewData({
          type: "download",
          fileName: file.displayName ?? file.fileName,
          sizeBytes: file.sizeBytes,
          contentType,
        })
      }
    } catch {
      setError("加载预览失败")
    } finally {
      setLoading(false)
    }
  }, [])

  useEffect(() => {
    if (open && currentFile) {
      loadPreview(currentFile)
    }
  }, [open, currentFile, loadPreview])

  // 缩放控制
  const zoomSteps = [0.5, 1, 1.5, 2]
  const handleZoomIn = () => {
    setZoom((prev) => {
      const idx = zoomSteps.findIndex((s) => s > prev)
      return idx >= 0 ? zoomSteps[idx] : prev
    })
  }
  const handleZoomOut = () => {
    setZoom((prev) => {
      const idx = [...zoomSteps].reverse().findIndex((s) => s < prev)
      return idx >= 0 ? [...zoomSteps].reverse()[idx] : prev
    })
  }

  // 键盘左右切换
  useEffect(() => {
    if (!open) return
    const handler = (e: KeyboardEvent) => {
      if (e.key === "ArrowLeft" && hasPrev) handleNavigate("prev")
      if (e.key === "ArrowRight" && hasNext) handleNavigate("next")
    }
    window.addEventListener("keydown", handler)
    return () => window.removeEventListener("keydown", handler)
  })

  // ... 渲染部分省略，见完整源码
}

逐行讲解

blobUrlRef — Blob URL 生命周期管理

  • useRef 而非 useState：Blob URL 只是一个字符串引用，不需要触发重渲染。【易错点】如果用 useState，每次赋值都会触发组件重渲染，而这里只需要记住 URL 用于清理。
  • 组件卸载时清理：useEffect 返回的 cleanup 函数在组件卸载时执行，确保不会泄漏。

【易错点】MIME 类型检测的边界情况：file.contentType 可能为 null（后端未记录或上传时未提供）。代码中使用 file.contentType ?? "application/octet-stream" 做兜底。但更危险的是错误的 MIME 类型——比如一个 .exe 文件被标记为 image/png，前端会尝试按图片预览但必然失败。MIME 类型的权威来源应该是后端存储时检测的结果，而非前端根据文件扩展名猜测。

【易错点】PDF.js 加载失败：当浏览器未内置 PDF 阅读器（如某些移动端浏览器）时，<iframe src="预签名URL"> 会直接下载 PDF 而非内嵌显示。解决方案有二：1) 检测浏览器是否支持 PDF 内嵌，不支持则走下载；2) 引入 pdf.js 库做纯前端 PDF 渲染（体积较大，约 2MB）。本系统暂采用方案 1，因为主流桌面浏览器均支持 PDF 内嵌。

🤔 导师提问：previewData 的类型定义中 type 是联合字面量 "image" | "pdf" | "text" | "download"，而 url 是可选字段。如果 type 是 "image" 但 url 是 undefined，渲染时会怎样？你会怎么在类型层面防止这种非法状态？（提示：考虑使用判别联合类型）

  • 图片用 Blob URL：因为需要 Token 认证，<img src> 不带 Token，必须先 fetch + createObjectURL。

fetchImageBlobUrl 工具函数

来源：src/lib/file-utils.ts

export async function fetchImageBlobUrl(
  fileId: string,
  maxWidth = 1024,
  maxHeight = 1024
): Promise<string> {
  // 动态导入 auth-store 避免循环依赖
  const token = (await import("@/stores/auth-store")).useAuthStore.getState().accessToken
  const url = `/file-api/api/files/${fileId}/thumbnail?maxWidth=${maxWidth}&maxHeight=${maxHeight}`
  const res = await fetch(url, {
    headers: token ? { Authorization: `Bearer ${token}` } : {},
  })
  if (!res.ok) throw new Error(`图片加载失败: ${res.status}`)
  const blob = await res.blob()
  return URL.createObjectURL(blob)
}
  • dynamic import：await import("@/stores/auth-store") 在运行时才加载模块，避免 file-utils.ts → auth-store.ts 之间的循环依赖问题。如果用顶层 import，而 auth-store.ts 又间接引用了 file-utils.ts，就会报循环引用错误。
  • fetch 而非 axios：这里用原生 fetch 而非 fileHttp 实例，是因为需要手动控制 Authorization header 和 responseType: "blob" 的行为。fetch 的 .blob() 方法天然返回 Blob 对象。

切换文件时清理旧 Blob URL

if (blobUrlRef.current) {
  URL.revokeObjectURL(blobUrlRef.current)
  blobUrlRef.current = null
}
  • 每次加载新文件前先释放旧的：类比后端的 IDisposable.Dispose()。【性能陷阱】如果不释放，用户快速切换 100 张图片就会积累 100 个 Blob 引用，每个占几 MB 内存。

【性能陷阱】预览大文件的内存问题：当用户预览一个 50MB 的高清图片时，fetchImageBlobUrl 会将整个文件下载到内存中创建 Blob URL。如果图片分辨率远超屏幕显示尺寸（如 8000x6000 的照片），虽然前端指定了 maxWidth=1024&maxHeight=1024 让后端生成缩略图，但如果后端缩略图服务不可用或不支持该格式，就会返回原图——内存占用瞬间飙升。应该在 loadPreview 中加一个 sizeBytes 上限检查，超过阈值的文件直接走下载而非预览。

踩坑提醒

  1. <img> 标签不携带 Bearer Token：私有文件的缩略图/预览图直接用 <img src> 请求会 401。必须用 fetchImageBlobUrl 先 fetch 再创建 Blob URL，或使用预签名 URL 让后端生成临时访问凭证。
  2. MIME 类型可能为 null 或错误：file.contentType 可能为 null（后端未记录），代码用 ?? "application/octet-stream" 兜底。但更危险的是错误的 MIME 类型——如 .exe 文件被标记为 image/png，前端会尝试按图片预览但必然失败。MIME 类型的权威来源应该是后端存储时检测的结果。
  3. Blob URL 内存泄漏：每次 URL.createObjectURL 都会在内存中持有 Blob 引用。如果切换图片预览时不调用 URL.revokeObjectURL 释放旧引用，快速切换 100 张图片就会积累 100 个 Blob 引用，每个占几 MB 内存。
  4. PDF 内嵌显示兼容性：某些移动端浏览器未内置 PDF 阅读器，<iframe src="预签名URL"> 会直接下载 PDF 而非内嵌显示。应在 loadPreview 中检测浏览器是否支持 PDF 内嵌，不支持则走下载。
