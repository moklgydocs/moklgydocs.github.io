# 工具使用与函数调用

> Toolformer(Schick 等,2023)开创了自监督工具标注。Berkeley 函数调用排行榜 V4(Patil 等,2025)定下 2026 年的标杆:40% 智能体类、30% 多轮、10% live、10% 非 live、10% 幻觉。单轮调用已解决;记忆、动态决策和长程工具链还没有。

**类型:** 动手构建
**编程语言:** Python(标准库)
**前置要求:** 第 14 阶段 · 01(智能体循环)、第 13 阶段 · 01(函数调用深入)
**预计耗时:** 约 60 分钟

## 学习目标

- 解释 Toolformer 的自监督训练信号:只有当执行结果降低下一 token 损失时,才保留工具标注。
- 说出 BFCL V4 的五个评估类别及各自测量什么。
- 用纯标准库实现一个工具注册表:schema 校验、参数矫正、执行沙箱。
- 诊断 2026 年三个开放问题:长程工具链、动态决策、记忆。

## 问题

早期工具使用问的是:模型能不能预测出正确的函数调用?现代工具使用问的是:模型能不能跨 40 步串联工具——带记忆、带部分可观测、能从工具失败中恢复,而且不幻觉出不存在的工具?

Toolformer 建立了基线:模型可以用自监督学会何时调工具。BFCL V4 定义了 2026 年的评估目标。两者之间的地带,就是生产智能体生活的地方。

## 概念

### Toolformer(Schick 等,NeurIPS 2023)

思路:让模型给自己的预训练语料标注候选 API 调用。对每个候选执行一次,只有当包含工具结果能降低下一 token 的损失时才保留该标注。在过滤后的语料上微调。

覆盖的工具:计算器、问答系统、搜索引擎、翻译、日历。自监督信号只看"工具是否有助于预测文本"——不需要人工标注。

规模化的结果:工具使用随规模涌现。小模型加工具标注反而受害,大模型受益。这就是为什么 2026 年前沿模型自带强大的工具使用,而大多数 7B 模型需要显式的工具使用微调才可靠。

### Berkeley 函数调用排行榜 V4(Patil 等,ICML 2025)

BFCL 是 2026 年的事实评估标准。V4 构成:

- **智能体类(40%)** —— 完整智能体轨迹:记忆、多轮、动态决策。
- **多轮(30%)** —— 带工具链的交互对话。
- **Live(10%)** —— 用户提交的真实提示词(更难的分布)。
- **非 Live(10%)** —— 合成测试用例。
- **幻觉(10%)** —— 识别"不该调任何工具"的情形。

V3 引入了基于状态的评估:工具序列执行完后,检查 API 的真实状态(如"文件建好了吗?"),而不是比对工具调用的 AST。V4 增加了网页搜索、记忆和格式敏感性类别。

2026 年的关键发现:单轮函数调用接近解决。失败集中在:记忆(跨轮携带上下文)、动态决策(根据先前结果选工具)、长程链(20+ 步后漂移),以及幻觉检测(没有合适工具时拒绝调用)。

### 工具 schema

每个提供商都有自己的 schema,细节不同但形状相同:

```
name: string
description: string (what it does, when to use it)
input_schema: JSON Schema (properties, required, types, enums)
```

Anthropic 直接用 `input_schema`,OpenAI 用 `function.parameters`,都接受 JSON Schema。描述是承重的——模型靠读它来挑工具。糟糕的工具描述是"选错工具"失败的头号根因。

### 参数校验

不要信任任何工具调用。校验:

1. **类型矫正。** schema 要 int,模型可能返回字符串 "5"。无歧义就矫正,有歧义就拒绝。
2. **枚举校验。** schema 说 `status in {"open", "closed"}` 而模型吐出 `"in_progress"`,带描述性错误拒绝。
3. **必填字段。** 缺必填字段 → 立刻把错误观测返回给模型,而不是崩溃。
4. **格式校验。** 日期、邮箱、URL——用具体解析器校验,别用正则。

每次校验失败都应返回结构化观测,让模型能按正确形状重试。

### 并行工具调用

现代提供商支持一个助手轮内并行工具调用。循环:

1. 模型发出 3 个工具调用,各有不同的 `tool_use_id`。
2. 运行时执行它们(独立则并行)。
3. 每个结果以 `tool_result` 块返回,按 `tool_use_id` 关联。

工程规则:把关联 ID 当承重件。对错了,就是"工具甲的结果路由给工具乙"。

### 沙箱

工具执行就是沙箱边界,详见第 09 课。简版:每个工具都应声明读写面、网络访问、超时、内存上限。泛泛的 `run_shell(cmd)` 是危险信号;具体的 `git_status()` 更安全。

## 动手构建

`code/main.py` 实现一个生产形态的工具注册表:

- JSON Schema 子集校验器(纯标准库)。
- 工具注册:描述、输入 schema、超时、执行器。
- 参数矫正与枚举校验。
- 带关联 ID 的并行工具派发。
- 结构化字符串形式的错误观测。

运行:

```
python3 code/main.py
```

轨迹展示一个迷你智能体在一轮里调三个工具,其中一个故意写错的调用被带描述的错误拒绝——模型可以据此行动。

## 投入使用

每个提供商都有自己的工具 schema——Anthropic、OpenAI、Gemini、Bedrock。需要多提供商时用翻译层(OpenAI Agents SDK、Vercel AI SDK、LangChain 工具适配器)。BFCL 是参考基准——如果工具使用是产品核心,发布前先跑它。

## 交付

`outputs/skill-tool-registry.md`:给定任务领域,生成工具目录、schema 和注册表。含描述质量检查(每个工具的描述有没有告诉模型何时用它?)。

## 练习

1. 加一个"no-op"工具,让模型可以显式拒绝使用任何其他工具。在一个类 BFCL 的幻觉测试上测量。
2. 实现 int-as-string 和 float-as-string 的参数矫正。矫正从哪里开始掩盖真正的 bug?
3. 加逐工具超时和熔断器(连续失败 3 次后 60 秒内拒绝该工具)。这会如何改变模型的恢复行为?
4. 读 BFCL V4 描述。任选一个类别(如"多轮"),用你的智能体跑 10 个示例提示词,报告通过率。
5. 把标准库校验器移植到 Pydantic 或 Zod。Pydantic/Zod 抓到了什么玩具漏掉的东西?

## 关键术语

| 术语 | 人们常说的 | 实际含义 |
|------|----------------|------------------------|
| 函数调用 | "工具使用" | 带校验 schema 的结构化输出工具调用 |
| Toolformer | "自监督工具标注" | Schick 2023 —— 只保留其结果能降低下一 token 损失的工具调用 |
| BFCL | "Berkeley 函数调用排行榜" | 2026 基准:40% 智能体、30% 多轮、10% live、10% 非 live、10% 幻觉 |
| 工具 schema | "给模型看的函数签名" | name、description、参数的 JSON Schema |
| tool_use_id | "关联 ID" | 把工具调用与其结果绑定;并行派发的必需品 |
| 幻觉检测 | "知道何时不调" | V4 类别:没有合适工具时拒绝调用 |
| 参数矫正 | "字符串转 int 修复" | 对可预见的 schema 不匹配做窄修复;有歧义就拒绝 |
| 沙箱 | "工具执行边界" | 逐工具的读写面、网络、超时、内存上限 |
