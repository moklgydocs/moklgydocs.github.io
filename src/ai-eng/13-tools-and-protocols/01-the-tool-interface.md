# 工具接口 —— 智能体为什么需要结构化 I/O

> 语言模型产出 token，程序执行动作。两者之间的鸿沟就是工具接口：一份契约，让模型能请求一个动作、宿主程序来执行它。2026 年的每一套技术栈——OpenAI、Anthropic、Gemini 的函数调用，MCP 的 `tools/call`,A2A 的 task parts——都是同一个四步循环的不同编码。本课讲清这个循环，并展示让它跑起来的最小机制。

**类型：** Learn
**编程语言：** Python（标准库，不用 LLM)
**前置要求：** 第 11 阶段(LLM completion API)
**预计耗时：** 约 45 分钟

## 学习目标

- 解释为什么一个只会生成文本的 LLM，凭自己无法对真实世界采取行动
- 画出四步工具调用循环（describe → decide → execute → observe)，说清每一步归谁管
- 用三部分写出一个工具描述：名称、JSON Schema 输入、确定性的执行器函数
- 区分纯工具和有副作用的工具，说明这个区分对安全为什么重要

## 问题

LLM 的输出面只有一样东西：下一个 token 的概率分布。你问聊天模型"班加罗尔现在天气如何"，它能写出一句像模像样的话，但它没法拨通天气 API。那句话可能碰巧是对的，也可能是三天前的旧闻。

工具接口就是为了合上这个缺口。宿主程序——你的智能体运行时、Claude Desktop、ChatGPT、Cursor，或一个自定义脚本——向模型宣告一份可调用工具清单。模型在判断需要采取行动时，发出一个结构化载荷，指名某个工具及其参数。宿主解析载荷，真实地运行工具，把结果喂回去。循环继续，直到模型判断不再需要调用。

这份契约的第一个版本是 2023 年 6 月 OpenAI 的 "functions" 参数。Anthropic 随后在 Claude 2.1 里跟上 `tool_use` 块，Gemini 几个月后加了 `functionDeclarations`。如今每家厂商暴露的都是同一个形状：JSON Schema 类型化的工具清单进，JSON 载荷的工具调用出。Model Context Protocol(2024 年 11 月）把这份契约泛化，让一个工具注册表服务所有模型。A2A(2026 年 4 月，v1.0）把同一个原语叠到了智能体对智能体的委派上。

四步循环是这一切底下的不变量。第 13 阶段 的其他所有内容，都是它的展开。

## 概念

### 第一步：describe（描述）

宿主用三个字段声明每个工具。

- **名称。** 稳定、机器可读的标识符。`get_weather`，而不是 "weather thing"。
- **描述。** 一段自然语言简介："当用户询问某个城市的当前天气时使用。不要用于历史数据。"
- **输入 schema。** 一个描述工具参数的 JSON Schema 对象（2020-12 草案）。

模型收到这份清单。现代厂商用自家模板把这些声明序列化进系统提示词，所以你作为调用方只需要处理结构化的形式。

### 第二步：decide（决策）

给定用户消息和可用工具，模型三选一。

1. **直接回答**，纯文本，不调工具。
2. **调用一个或多个工具**，发出结构化的调用对象。在 `parallel_tool_calls: true` 下（OpenAI 和 Gemini 默认开，Anthropic 需显式开启），模型一轮可以发出多个调用。
3. **拒绝。** 严格模式的结构化输出可以产出一个类型化的 `refusal` 块，而不是调用。

一个工具调用载荷有三个固定字段：调用 `id`、工具 `name`、JSON 的 `arguments` 对象。id 的存在，是为了让宿主能把稍后返回的结果和具体调用对上号——并行调用乱序返回时，这一点很关键。

### 第三步：execute（执行）

宿主收到调用，按声明的 schema 校验参数，运行执行器。参数非法，说明模型幻觉出了一个字段或类型用错——弱模型上非常常见的故障模式。生产环境的宿主遇到非法参数时三选一：快速失败并把错误暴露给模型；用受约束的解析器修复 JSON；或者把校验错误放进提示词让模型重试。

执行器本身是普通代码：Python、TypeScript、一条 shell 命令、一次数据库查询。它产出一个结果——通常是字符串，但可以是任何 JSON 值或结构化内容块（MCP 里的文本、图像或资源引用）。结果必须可序列化。

### 第四步：observe（观察）

宿主把工具结果追加到对话里（作为一条 `tool` 角色消息，带匹配的 `id`)，再次调用模型。现在模型在上下文里有了工具输出，可以给出最终答案，或请求更多调用。循环继续，直到模型不再发出调用，或宿主撞到迭代次数的安全上限。

### 信任的划分

和安全相关的工具分两种。

- **纯工具（pure)。** 只读、确定性、无副作用。`get_weather`、`search_docs`、`get_current_time`。可以放心试探性地调。
- **后果性工具（consequential)。** 会改变状态、花钱、碰用户数据。`send_email`、`delete_file`、`execute_trade`。必须上闸门。

Meta 在 2026 年提出的智能体安全"二规则"(Rule of Two）说：单轮里最多只能同时出现三样中的两样——不可信输入、敏感数据、后果性动作。工具接口就是你执行这条规则的地方：拒绝调用、要求用户确认、或升级权限范围。完整安全章节见 第 13 阶段 · 15，智能体级权限政策见 第 14 阶段 · 09。

### 循环住在哪里

| 场景 | 谁 describe | 谁 decide | 谁 execute |
|---------|---------------|-------------|--------------|
| 单轮函数调用（OpenAI/Anthropic/Gemini) | 应用开发者 | LLM | 应用开发者 |
| MCP | MCP 服务器 | LLM（经 MCP 客户端） | MCP 服务器 |
| A2A | Agent Card 发布者 | 发起方智能体 | 被调用智能体 |
| 浏览器（函数调用智能体） | 浏览器扩展 / WebMCP | LLM | 浏览器运行时 |

哪里都是这四步。列名变了，结构没变。

### 为什么不直接让模型输出 JSON?

"让模型用 JSON 回复"是函数调用出现之前的做法。前沿模型上它有 5-15% 的失败率，小模型更惨。失败模式包括：缺括号、尾随逗号、幻觉字段、类型错误。然后你就需要 JSON 修复、重试，或约束解码器。

原生函数调用更好，有三个原因。第一，厂商在精确的调用形状上对模型做了端到端训练，严格模式下合法 JSON 率达到 98-99%。第二，调用载荷有自己独立的协议槽位，不混在自由文本里——工具调用永远不会泄漏进用户可见的回复。第三，厂商用约束解码强制 schema 合规（OpenAI 的严格模式、Anthropic 的 `tool_use`、Gemini 的 `responseSchema`)，输出保证能通过校验。

### 熔断器

循环在模型停止发出调用、或宿主撞到最大轮数时终止。生产宿主把这个上限设在 5 到 20 轮之间。超过这个范围，你几乎肯定陷入了一个模型自己出不来的循环。Claude Code 默认 20,OpenAI Assistants 默认 10,Cursor 的智能体模式默认 25。

反面——不设上限的循环——每半年就以"智能体一夜烧掉 $400 API 费"的事后复盘形式出现一次。没有上限，不要上线。

## 投入使用

`code/main.py` 不用 LLM 就能跑四步循环：一个假的 "decider" 函数通过模式匹配模拟模型的决策；执行器、schema 校验器和 observe 步骤的架子都是真的。跑一遍，看完整的请求/响应编舞和可打印的中间状态，然后在后面的课里把假 decider 换成任意真实厂商。

要看的地方：

- 工具注册表为每个工具存三个字段：名称、描述、schema，外加执行器引用。
- 校验器是一个只用标准库写的 JSON Schema 最小子集（类型、required、enum、min/max)。第 13 阶段 · 04 会交付一个更完整的。
- 循环把迭代次数限制在 5。生产级智能体需要的正是这样的熔断器。

## 交付

本课产出 `outputs/skill-tool-interface-reviewer.md`。给它一份工具定义草稿（名称 + 描述 + schema + 执行器大纲），这个 skill 会按循环适配性做审计：名称是否机器稳定，描述是否是完整的使用简报，schema 是否正确使用 JSON Schema 2020-12，纯工具 vs 后果性工具的分类是否显式标注。

## 练习

1. 给 `code/main.py` 加第四个工具 `get_stock_price(ticker)`，描述写为 "Use when the user asks for a current stock price by ticker. Do not use for historical prices or market summaries."。跑架子，确认假 decider 把提到股票代码的查询路由到了新工具。

2. 弄坏 schema 校验器：传一个 `arguments` 缺少必填字段的调用，确认宿主在执行前拒绝了它。再传一个带多余未知字段的调用。决策一下：宿主应该拒绝还是忽略？用安全论证说明你的选择。

3. 把架子里的每个工具分类为纯工具或后果性工具。给需要的注册项加 `consequential: true` 标记，并修改循环：每当选中一个后果性工具，打印一行 "would confirm with user"。这就是每个生产宿主都需要的确认闸门的形状。

4. 在纸上画出四步循环，并为你最喜欢的客户端（Claude Desktop、Cursor、ChatGPT 或自定义栈）填好上面的厂商列表格。与 第 13 阶段 · 06 的 MCP 变体交叉对照。

5. 把 OpenAI 的函数调用指南从头到尾读一遍。找出一个在请求里存在、但不属于本课四步循环的字段。解释它加了什么，以及为什么说它是便利而非必需。

## 关键术语

| 术语 | 大家嘴里的说法 | 实际含义 |
|------|----------------|------------------------|
| 工具（Tool) | "模型能调的东西" | 名称 + JSON Schema 类型化输入 + 执行器函数的三元组 |
| 函数调用 | "原生工具使用" | 厂商级 API 支持，让模型发出结构化工具调用而不是散文 |
| 工具调用 | "模型的行动请求" | 模型发出的带 `id`、`name`、`arguments` 的 JSON 载荷 |
| 工具结果 | "工具返回的东西" | 执行器的输出，包装成带匹配 id 的 `tool` 角色消息 |
| 并行工具调用 | "一次调多个" | 模型一轮内发出多个调用对象，相互独立，按 id 对号 |
| 严格模式 | "保证 JSON" | 约束解码，强制模型输出通过所声明 schema 的校验 |
| 纯工具 | "只读工具" | 无副作用，重复调用安全 |
| 后果性工具 | "动作工具" | 改变外部状态，需要闸门、审计或用户确认 |
| 四步循环 | "工具调用周期" | describe → decide → execute → observe |
| 宿主（Host) | "智能体运行时" | 持有工具注册表、调用模型、运行执行器的程序 |
