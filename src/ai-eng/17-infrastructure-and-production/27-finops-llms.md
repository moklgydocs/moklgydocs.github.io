# LLM 的 FinOps——单位经济模型与多租户成本归因

> 传统 FinOps 在 LLM 支出上失效了。成本按 token 交易计,不按资源在线时长计。标签对不上——一次 API 调用是一笔交易,不是一项资产。工程决策(提示词设计、上下文窗口、输出长度)就是财务决策。2026 年的打法要求第一天就埋好三个归因维度:按用户(`user_id`),支撑席位定价和增购;按任务(`task_id` + `route`),支撑产品功能成本核算和优先级排序;按租户(`tenant_id`),支撑单位经济模型和续约谈判。四层 token——prompt、tool、memory、response——混在一个桶里会掩盖支出。多租户产品的管控阶梯:按租户限流(预期峰值的 2-3 倍,返回明确的 429 + retry-after);每日支出上限(合同上限的 1.5-3 倍;触发后收紧限流 + 告警);支出 z 分数 > 4 时触发熔断开关(自动暂停 + 呼叫值班)。归因模式:打标后聚合、遥测关联(trace-ID → 账单;精度最高)、采样外推、基于模型的分摊、事件溯源、实时流式。单位指标:每次解决问题的成本、每份生成产物的成本——而不是 $/M token。事后补标永远有漏;必须在请求创建时埋点。

**类型:** 学习
**编程语言:** Python(标准库,带熔断开关的玩具版成本归因模拟器)
**前置要求:** 第 17 阶段 · 13(可观测性)、第 17 阶段 · 14(缓存)
**预计耗时:** 约 60 分钟

## 学习目标

- 解释为什么传统 FinOps(标签 + 分层)在 LLM 支出上失效,并说出三个新的归因维度。
- 列举四层 token(prompt、tool、memory、response),以及为什么单桶计费会掩盖成本。
- 为多租户产品设计管控阶梯(限流 → 支出上限 → 熔断开关)。
- 选择单位指标(每次解决问题 / 每份产物的成本),而不是 $/M token。

## 问题

账单写着 $40,000。你不知道:

- 是哪个租户花的。
- 是哪个产品功能烧掉的。
- 有没有某个用户在滥用。
- 元凶是提示词膨胀、工具调用,还是记忆放大。

云资源(EC2、S3)可以靠供应商侧打标再聚合,因为标签会传导到账单行项。LLM API 调用不会自动带标签——你得在调用点盖上 user/task/tenant 的戳并一路传下去。事后归因永远会漏掉边缘情况。

## 概念

### 三个归因维度

**按用户**(`user_id`):谁花了多少钱。驱动席位定价、增购沟通,识别重度用户。

**按任务**(`task_id` + `route`):哪个产品功能花了多少钱。驱动功能优先级排序、"砍掉烧钱功能"的决策。

**按租户**(`tenant_id`):哪个客户是赚钱的。驱动单位经济模型、续约定价、分层阈值。

第一天就在调用点对三个维度全部埋点。事后补永远更差。

### 四层 token

| 层 | 例子 | 典型占比 |
|-------|---------|---------------------|
| Prompt | 系统提示 + 用户输入 | 40-60% |
| Tool | 回灌的工具调用结果 | 20-40%(智能体负载) |
| Memory | 历史对话 / 检索到的文档 | 10-30% |
| Response | 模型输出 | 10-30% |

四层混在一个桶里,优化就是盲人摸象。在你的归因模型里把它们拆开。

### 管控阶梯

1. **按租户限流**。设为预期峰值的 2-3 倍。返回 429 并带 `Retry-After`。租户感到摩擦;账单不会爆惊喜。

2. **按租户每日支出上限**。设为合同上限的 1.5-3 倍。触发后:收紧限流 + 告警客户成功团队。

3. **熔断开关**:支出 z 分数相对租户基线 > 4 时触发。自动暂停租户;呼叫值班;升级到运维 + 客户成功。

### 归因模式

- **打标后聚合**:在元数据头上盖章;事后聚合。简单;粗糙。
- **遥测关联**:通过 trace ID 把链路和账单关联起来。精度最高。成熟团队的做法。
- **采样 + 外推**:采样 5-10%,再放大。粗略估算成本划算;抓不到长尾。
- **基于模型的分摊**:用回归推断成本驱动因素。用于没有标签的历史数据。
- **事件溯源**:成本作为事件流(Kafka / Kinesis)。实时。
- **实时流式**:仪表盘亚秒级更新。

### 每 X 成本才是单位指标

$/M token 是供应商的话术。产品指标应该是:

- 每张已解决工单的成本。
- 每篇生成文章的成本。
- 每个成功智能体任务的成本。
- 每用户会话分钟的成本。

把成本绑到产品结果上。否则优化没有锚点。

### 成本归因的 trace 形态

```
trace_id: abc123
  user_id: u_42
  tenant_id: t_7
  task_id: task_classify_doc
  route: model_haiku
  layers:
    prompt_tokens: 1800
    tool_tokens: 600
    memory_tokens: 400
    response_tokens: 150
  cost_usd: 0.0135
  cached_input: true
  batch: false
```

每次调用都发出。存进数据湖。按维度聚合。它就活在第 17 阶段 · 13 的可观测性体系里。

### 复利式省钱组合拳

组合:缓存 + 批处理 + 路由 + 网关。四个全上:
- L2 缓存(第 17 阶段 · 14):输入便宜约 10 倍。
- 批处理(第 17 阶段 · 15):半价。
- 路由到便宜模型(第 17 阶段 · 16):成本降 60%。
- 网关效率(第 17 阶段 · 19):冗余 + 重试。

理想情况下全部叠加:约为朴素基线的 5-10%。大多数团队只启用了 2-3 个杠杆;四个全叠的很少。

### 需要记住的数字

- 归因维度:按用户、按任务、按租户。
- 四层 token:prompt、tool、memory、response。
- 熔断开关:支出 z 分数 > 4。
- 单位指标:每次解决问题的成本,不是 $/M token。
- 叠加优化:可做到基线的 5-10%。

## 关键术语

| 术语 | 大家嘴里的说法 | 实际含义 |
|------|----------------|----------|
| 按用户归因 | "用户级成本" | 每次调用都盖上 `user_id` |
| 按任务归因 | "功能成本" | `task_id` + `route` 标识产品功能 |
| 按租户归因 | "客户成本" | `tenant_id`;驱动单位经济模型 |
| 四层 token | "成本分层" | prompt + tool + memory + response |
| 限流 | "429 防线" | 在网关强制执行的每租户上限 |
| 每日支出上限 | "每日天花板" | 租户级预算,带告警 |
| 熔断开关 | "自动暂停" | 支出 z 分数 > 4 触发自动停用 |
| 每解决一次的成本 | "产品单位指标" | 成本绑在产品结果上,而非 token |
| 遥测关联 | "链路到账单" | 精度最高的归因模式 |
| 叠加优化 | "缓存+批处理+路由+网关" | 复利式省钱,可达基线的 5-10% |
