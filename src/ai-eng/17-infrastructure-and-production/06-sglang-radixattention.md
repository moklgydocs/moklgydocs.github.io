# 前缀缓存推理 —— RadixAttention 与 KV 复用

> 把 KV 缓存当作一等、可复用的资源,存进一棵基数树(radix tree),调度方式也随之改变:vLLM 按 FCFS(先来先服务)调度,而缓存感知调度器会优先处理共享前缀更长的请求——本质上是对基数树做深度优先遍历,让热点分支常驻 HBM。SGLang 正是围绕这个想法构建的引擎。在 Llama 3.1 8B、ShareGPT 风格 1K 提示词上,SGLang 跑到约 16,200 tok/s,vLLM 约 12,500,领先约 29%。在前缀密集的 RAG 负载上,优势可达 6.4x。在语音克隆类负载上,缓存命中率超过 86%。2026 年已部署在 xAI、LinkedIn、Cursor、Oracle、GCP、Azure、AWS 的 40 万块以上 GPU 上。坑在于:一旦前缀顺序不一致,6.4x 的数字立刻蒸发——顺序才是工程师手里的杠杆。

## 学习目标

- 画出 RadixAttention:前缀如何存入基数树,同根分支的序列之间如何共享 KV 块。
- 解释缓存感知调度,以及为什么 FCFS 不适合前缀密集型流量。
- 给定前缀缓存命中率和提示词长度分布,算出负载的期望加速比。
- 说出让 6.4x 成为现实(而非白白流失)的提示词排序纪律。

## 问题

经典推理把每个请求的提示词当作不透明的整体。哪怕 5,000 个 RAG 请求都以同一段 2,000 token 的系统提示词加同一段检索前言开头,vLLM 也会把这 2,000 token 的前缀 prefill 5,000 次。GPU 一遍又一遍地重复同样的工作。

观察:智能体和 RAG 负载中的提示词几乎总是共享长前缀。系统提示词、工具 schema、few-shot 示例、检索头、对话历史——全都在请求间重复。如果把这段前缀的 KV 缓存存一次、反复复用,就不必再 prefill 它。

RadixAttention 做的正是这件事。token 被索引进一棵基数树;每个节点拥有从根到它路径上那段 token 序列的 KV 块。新请求进来时沿树下行:凡是 token 匹配的节点,直接复用其 KV 块。prefill 成本正比于"新"后缀,而非完整提示词。

难点在调度。如果两个请求共享 2,000 token 的前缀,第三个请求只共享同一前缀的 200 token,你会想把前两个长共享的请求放在一起服务,让长前缀留在 HBM 里。FCFS 恰好相反——它服务先到者,可能在下个长前缀请求到来之前就把热点分支挤出了缓存。

## 概念

### 基数树作为 KV 索引

基数树(压缩 trie)存储 token 序列。每个节点拥有一段 token 区间以及为该区间算好的 KV 块。子节点在序列上续接一个或多个 token。

```
root
 |- "You are a helpful assistant..."  (2,000 tokens, 124 KV blocks)
      |- "Context: <doc A>..."        (500 tokens, 31 blocks)
           |- "Question: Alice..."    (80 tokens, 5 blocks)
           |- "Question: Bob..."      (95 tokens, 6 blocks)
      |- "Context: <doc B>..."        (520 tokens, 33 blocks)
```

新请求进来:系统提示词 + "Context: <doc A>" + "Question: Carol"。调度器沿树走:系统前缀命中(复用 124 块),doc-A 分支命中(复用 31 块),只为 "Question: Carol" 分配新块(4 块)。prefill 成本:4 个新 token 块。没有这棵树:160 块。prefill 省了约 40 倍。

### 缓存感知调度

如果缓存反复颠簸,基数树复用就毫无意义。两条关键策略:

1. **深度优先派发**。从队列里挑下一个请求时,优先选与当前运行集合同根分支的请求,让热点分支钉在原地。
2. **分支级 LRU,而非块级 LRU**。整枝驱逐(从最少使用的叶子开始),而不是按单块驱逐,让缓存形状与基数树形状一致。

FCFS 两条都违反。一个共享 2,000 token 的请求排在一个共享 50 token 的请求后面,然后 2,000 token 的分支被驱逐,只为了给 50 token 的请求腾地方。

### 该背下来的基准数字

- Llama 3.1 8B、H100、ShareGPT 1K 提示词:SGLang 约 16,200 tok/s,vLLM 约 12,500(领先约 29%)。
- 前缀密集 RAG(同一系统提示词 + 同一文档,问题不同):SGLang 最高 6.4x。
- 语音克隆负载:前缀缓存命中率 86.4%。
- SGLang 客户生产环境命中率:50-99%,取决于提示词纪律。
- 2026 年已部署在 40 万块以上 GPU 上。

### 排序这个坑

6.4x 依赖一致的提示词模板顺序。如果你的客户端有些请求按 `[system, tools, context, history, question]` 拼,有些按 `[system, context, tools, history, question]` 拼,树就找不到共享前缀。在人眼里的共享前缀,在基数树眼里是两条不同的序列。

工程师的杠杆:提示词模板就是缓存键。固定顺序。不可变的内容(系统提示词、工具、schema)放最前,检索上下文其次,用户问题放最后。不要把动态内容插进前缀里。

研究中的真实案例:某次部署仅做了一次改动——把动态内容移出可缓存前缀——缓存命中率就从 7% 升到 74%。

### RadixAttention 在哪里赢、在哪里输

赢的场景:
- RAG(检索前言相同,问题不同)。
- 智能体(工具 schema 相同,查询不同)。
- 带长系统提示词的聊天。
- 前言重复的语音/视觉负载。

输的场景(退回 vLLM 水平吞吐):
- 提示词各不相同的单轮生成(代码补全、无系统提示词的开放聊天)。
- 每个请求都把独特内容插进前缀的动态提示词。

### 为什么这是调度问题,而不只是内核问题

KV 复用可以做成一个内核技巧。SGLang 的洞见是:只有调度器让热点分支常驻,复用才兑现收益。朴素的"有就复用"策略在混合负载下会让缓存颠簸。正是基数树索引的调度器,把内核技巧变成了 29% 的生产优势。

### 与 vLLM 的关系

两套系统并非纯粹的竞争关系。2026 年 vLLM 加了前缀缓存(`--enable-prefix-caching`)和缓存感知路由器(Rust 写的 vLLM Router)。差距缩小了,但没有完全消失——SGLang 全栈以基数树为先,vLLM 是后来嫁接的。前缀复用主导的负载,SGLang 仍是默认选择;没有明显前缀模式的通用推理,vLLM 持平或更好。

## 关键术语

| 术语 | 别人嘴里的说法 | 实际含义 |
|------|----------------|----------|
| RadixAttention | "SGLang 那套东西" | KV 缓存按基数树索引,共享前缀复用 KV 块 |
| 基数树 | "压缩 trie" | 每个节点拥有一段 token 区间及其 KV 块的树 |
| 缓存感知调度器 | "热点分支优先" | 优先调度与常驻分支同根的请求的调度器 |
| 前缀缓存命中率 | "提示词有多少是白捡的" | 提示词 token 中由复用 KV 块直接服务的比例 |
| FCFS | "先来先服务" | 破坏前缀局部性的默认调度 |
| 分支级 LRU | "逐叶子" | 与基数树形状对齐的驱逐策略 |
| 提示词模板顺序 | "缓存键" | 提示词各组成部分的顺序决定树能共享什么 |
| 系统提示词钉住 | "常驻前缀" | 让不可变的系统部分保持钉住,避免驱逐颠簸 |
