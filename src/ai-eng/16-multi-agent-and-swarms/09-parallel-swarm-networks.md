# 并行 / 蜂群 / 网络化架构

> 与监督者对照:没有中央决策者。智能体读一条共享事件总线,异步领活,把结果写回去。LangGraph 明确支持面向去中心化、动态环境的"蜂群架构"。Matrix(arXiv:2511.21686)把控制流和数据流都表示为经分布式队列传递的序列化消息,消除编排者瓶颈。取舍是明摆着的:拿确定性和可追踪性,换可扩展性。蜂群适合有大量独立子问题的任务;不适合需要单一连贯计划的任务。

**类型:** 学习 + 动手构建
**编程语言:** Python(标准库,`threading`、`queue`)
**前置要求:** 第 16 阶段 · 05(监督者模式)、第 16 阶段 · 04(原语模型)
**预计耗时:** 约 75 分钟

## 问题

监督者能扩到几个工人。几百个呢?监督者自己成了瓶颈:"谁做什么"的每个决定都要过这一个智能体。计划里一步慢,整个系统都停。

蜂群架构把设计翻了过来。不再是中央规划者派活,而是工人从共享队列里领活。"协调"被烙进了事件总线的语义里。没有编排者;系统能扩到队列的极限。

## 概念

### 形状

```
                ┌──── shared queue ────┐
                │                      │
       ┌────────┼────────┐  ◄──────┬───┘
       ▼        ▼        ▼         │
     Worker  Worker  Worker   Worker
      A       B       C        D
       │        │        │         │
       └────────┴────────┴─────────┘
                 │
                 ▼
            results pool
```

没有编排者。每个工人循环:领一个任务、处理、写结果(可选地把后续任务再入队)。

### 蜂群何时合适

- **大量独立任务。** 抓取、转换、分类。任务互不依赖。
- **时长不均的工作。** 如果有的任务 100ms、有的 10s,蜂群自动平衡负载——快的工人领下一个活。监督者则必须预判时长。
- **吞吐优先于确定性。** 你在乎总完成时间,不在乎严格顺序。

### 蜂群何时失败

- **有序工作流。** 如果第 3 步需要第 2 步的输出,蜂群可能让第 3 步在第 2 步完成前就开跑。
- **全局计划任务。** 复杂研究问题受益于规划者。一蜂群研究员产出的是一堆独立事实,不是一份连贯的报告。
- **调试。** 没有中央日志、工作异步,复现一个 bug 代价高昂。

### Matrix(arXiv:2511.21686)

Matrix 是 2025 年把蜂群推到自然终点的论文:控制流和数据流都是分布式队列上的序列化消息。没有中央协调者。容错来自消息持久化。可扩展性是消息代理的问题,不是系统的问题。

贡献在于:它提出一种编程模型,多智能体协调的问题是"这个智能体订阅哪个消息主题?",而不是"监督者下一个挑哪个智能体?"。这让系统看起来像一张 pub/sub 事件网。

### 图框架里的蜂群

LangGraph 2025 年文档明确把"蜂群架构"列为多智能体模式之一:智能体是节点,但边构成一个有环的有向图,任何节点都能从池中被激活。工人按条件从可用工作中挑选,而不是等监督者指派。

### 失败模式:饥饿与热点

如果所有工人都挑最快能拿到的任务,长任务永远轮不到,直到只剩它们。经典的队列饥饿。

缓解:
- 带显式老化(aging)的优先级队列(等待越久,优先级越高)。
- 工人专门化:一些工人只接"长"任务。
- 背压:限制进入队列的快任务数量。

### 与内容路由的联系

蜂群与基于内容的路由(第 22 课)天然搭配。不用一个通用队列,而是每种消息类型一个队列。专门的工人只订阅自己的类型。这是能扩到几千个智能体的消息总线架构的基础。

## 动手构建

`code/main.py` 实现一个 4 工人线程的蜂群,从共享 `queue.Queue` 领活。任务时长不一(有快有慢)。演示对比:

- **串行基线:** 一个工人串行处理所有任务。
- **固定分配:** 每个任务预先指派给特定工人(监督者风格)。
- **蜂群:** 工人从共享队列领活。

蜂群自动平衡负载;固定分配则让快工人在自己被指派的慢任务前干等。

运行:

```
python3 code/main.py
```

输出展示每工人的任务数(蜂群分配不均但是最优)和墙钟时间。

## 投入使用

`outputs/skill-swarm-fit.md` 评估一个任务该用蜂群还是监督者。输入:任务独立性、时长方差、顺序要求、可调试性需求。

## 交付

检查清单:

- **带老化的优先级队列。** 防止长任务饥饿。
- **工人幂等。** 工人中途崩溃,任务可能被重复领取。工人必须幂等。
- **持久化队列。** 生产用 Kafka、Redis Streams 或数据库-backed 队列。`queue.Queue` 只在内存里。
- **每任务可观测。** 每个任务有 trace ID;每个工人用它记录起止。
- **背压。** 如果队列增长快过工人消费,让生产者慢下来。

## 练习

1. 运行 `code/main.py`。在时长不均的负载上,蜂群比串行快多少?比固定分配快多少?
2. 加一个优先级队列变体(用 `queue.PriorityQueue`)。按任务的 "importance" 字段定优先级。观察持续负载下,低优先级任务会不会饿死。
3. 实现热点检测器:当任何工人处理的任务数是最慢工人的 3 倍时记日志。这说明了任务时长分布的什么?
4. 读 Matrix 论文(arXiv:2511.21686)摘要和第 3 节。指出 Matrix 接受的一个具体取舍(可扩展性收益)和它放弃的一个东西(可追踪性、确定性)。
5. 把蜂群 demo 改成用 `(task_type, payload)` 元组的 `queue.Queue`,工人只订阅特定类型。任务异质时,什么路由规则合理?

## 关键术语

| 术语 | 大家口头的说法 | 实际含义 |
|------|----------------|------------------------|
| 蜂群架构 | "去中心化智能体" | 工人从共享队列领活;没有中央编排者。 |
| 事件总线 | "智能体订阅主题" | 按类型或内容把任务路由给工人的消息代理。 |
| 饥饿(Starvation) | "任务永远轮不到" | 低优先级任务永远不被选中,因为高优先级的活源源不断。 |
| 热点(Hot-spotting) | "一个工人被淹" | 负载失衡,一个工人拿到大部分任务。 |
| 背压(Back-pressure) | "让生产者慢点" | 队列填满时,向上游发停止生产的信号的机制。 |
| 幂等工人 | "重跑也安全" | 一个任务处理两次,产出相同结果。必须满足,因为工人可能中途崩溃。 |
| 持久化队列 | "崩了也不丢" | 由磁盘或复制存储支撑的队列;工人崩溃,任务不丢。 |
| Matrix 框架 | "全消息传递蜂群" | 数据流和控制流都是分布式队列上的序列化消息。 |
