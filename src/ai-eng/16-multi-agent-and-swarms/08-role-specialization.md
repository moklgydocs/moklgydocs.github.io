# 角色专门化 —— 规划者、批评者、执行者、验证者

> 2026 年最常见的多智能体分解:一个规划,一个执行,一个批评或验证。MetaGPT(arXiv:2308.00352)把这形式化为编码进角色提示词的 SOP——产品经理、架构师、项目经理、工程师、QA 工程师——遵循 `Code = SOP(Team)`。ChatDev(arXiv:2307.07924)把设计师、程序员、评审、测试串成一条"聊天链",带"通信式去幻觉"(智能体显式索要缺失的细节)。验证者是承重墙:Cemri 等人(MAST,arXiv:2503.13657)证明,每一个多智能体失败都能追溯到缺失或坏掉的验证。PwC 报告,在 CrewAI 中加入结构化验证循环,准确率提升 7 倍(10% → 70%)。

**类型:** 学习 + 动手构建
**编程语言:** Python(标准库)
**前置要求:** 第 16 阶段 · 04(原语模型)、第 16 阶段 · 05(监督者模式)
**预计耗时:** 约 60 分钟

## 问题

泛泛的多智能体系统产出泛泛的结果。群聊里的三个程序员写出三种风味的同样的平庸代码。你加更多智能体、加更多轮次,依然跨不过质量门槛。

解法不是更多智能体,而是*不同*的智能体。分配不同的角色。给批评者一些规划者没有的工具,给验证者一套客观的测试套件。这样,系统内部的分歧才有落地的纠正,而不只是并行瞎猜。

## 概念

### 四个经典角色

**规划者(Planner)。** 读目标,产出步骤清单或规格。工具:知识检索、文档。输出:结构化计划。

**执行者(Executor)。** 一次读一个计划步骤,产出工件。工具:干活的真工具(代码编译器、shell、API 客户端)。输出:工件。

**批评者(Critic)。** 对照规划者的意图,审读执行者的产出。工具:对工件的只读访问、静态分析。输出:接受/拒绝,附理由。

**验证者(Verifier)。** 读工件,跑确定性检查。工具:测试运行器、类型检查器、schema 校验器。输出:通过/失败,附证据。

批评者是主观的、有观点的,常常基于 LLM;验证者是客观的、确定性的,常常基于代码。它们不是同一个角色。

### MetaGPT 的 SOP 模式

MetaGPT(arXiv:2308.00352)把软件工程 SOP 编码为角色提示词:

- **产品经理**写 PRD。
- **架构师**产出系统设计。
- **项目经理**拆分任务。
- **工程师**实现。
- **QA 工程师**跑测试。

每个角色有严格的输入/输出 schema。角色提示词说明这个角色*是什么*、*必须产出什么*。`Code = SOP(Team)` 这个提法——确定性的 SOP 把一队 LLM 变成一条可预测的流水线。

### ChatDev 的通信式去幻觉

ChatDev 加了一个关键动作:当执行者需要计划里没有的具体细节时,它在继续之前显式地向设计师索要。这防止了 LLM 的经典失败——像模像样地编造细节。

实现:角色提示词里包含"当你需要未被提供的具体信息时,先按名字向相关角色询问,再产出。"

### 为什么验证者最承重

Cemri 等人(MAST)追查了 1642 个多智能体执行失败。21.3% 是验证缺口——系统交付了一个没人检查过的答案。剩下 79% 也常常能追溯到"有一个检查,但它静默失败了,或根本没跑"。验证是承重的角色。

PwC 报告(CrewAI 部署,2025):加入结构化验证循环,把准确率从 10% 提到 70%。一个角色,7 倍收益。

### 批评者 vs 验证者

- 批评者是一个评审工件质量的 LLM。主观。会被貌似通顺的文字骗过。
- 验证者是一个在工件上运行的确定性程序。客观。给出通过/失败,附证据。

两个都用。批评者抓验证者说不出的品味问题;验证者抓批评者看不见的 bug——因为它们只在运行时才现形。

### 反模式

系统里每个角色都是 LLM,每个角色的输出都是"我觉得没问题"。经典的 MAST 失败模式。至少要有一个验证者,它的通过/失败由代码决定,不由 LLM 决定。

### 框架映射

- **CrewAI** —— `Agent(role, goal, backstory)` 是教科书级的专门化表面。
- **LangGraph** —— 节点可以有专门的提示词;边强制执行流水线。
- **AutoGen** —— GroupChat 里角色专门的 ConversableAgent,名字一个词。
- **OpenAI Agents SDK** —— 角色专门的 Agent 之间的移交工具。

## 动手构建

`code/main.py` 实现一条构建简单 Python 函数的 4 角色流水线:

- **规划者**产出规格。
- **执行者**生成代码字符串。
- **批评者**(LLM 模拟)标记明显问题。
- **验证者**在沙箱(`exec`)里对着测试用例跑生成的代码。

演示跑两次:一次执行者产出正确代码(批评者 + 验证者都过),一次执行者产出不合规格的代码(批评者漏掉 bug,因为它看起来挺合理;验证者抓住它,因为测试挂了)。

运行:

```
python3 code/main.py
```

## 投入使用

`outputs/skill-role-designer.md` 接收一个任务,产出角色名册(3-5 个角色)、每角色的输入/输出 schema,以及验证者检查项。把智能体接进框架之前,先用它。

## 交付

检查清单:

- **至少一个确定性验证者。** 永远不要全 LLM。
- **每角色显式 I/O schema。** 规划者返回规格,不是散文;执行者读那个 schema。
- **通信式去幻觉。** 信息缺失时,执行者必须问规划者;永远不要编造。
- **批评者/验证者顺序。** 先跑批评者(便宜,抓设计问题),再跑验证者(慢,抓 bug)。
- **循环预算。** 批评者-执行者修订最多 2 轮,之后升级给人。

## 练习

1. 运行 `code/main.py`,观察验证者如何抓住批评者漏掉的 bug。加一个静态分析检查(数 `return` 出现次数)作为额外验证者。它能抓到运行时测试抓不到的什么?
2. 加第 5 个角色:"需求分析师",把用户愿望翻译成规划者可用的规格。哪些通信式去幻觉的请求应该流向它?
3. 读 MetaGPT 第 3 节("Agents")。列出 MetaGPT 五个角色各自的输入/输出 schema。
4. 读 ChatDev 的聊天链图(arXiv:2307.07924 图 3)。指出通信式去幻觉在哪里打断了一个否则无限循环的回路。
5. PwC 的 7 倍准确率提升来自验证循环。假设三个加验证者也没有用的任务——即确定性检查正确性不可能或代价过高的场景。

## 关键术语

| 术语 | 大家口头的说法 | 实际含义 |
|------|----------------|------------------------|
| 角色专门化 | "不同智能体,不同差事" | 为规划者/执行者/批评者/验证者角色调优的不同系统提示词。 |
| SOP 模式 | "编码的标准作业程序" | MetaGPT 的提法:每角色严格的 I/O schema,把团队变成流水线。 |
| 通信式去幻觉 | "先问再编" | ChatDev 模式:细节缺失时,执行者问规划者,而不是自己造一个。 |
| 批评者(Critic) | "LLM 评审" | 主观、有观点的评审。抓品味问题。会被貌似通顺的文字骗过。 |
| 验证者(Verifier) | "确定性检查" | 基于代码的通过/失败。测试运行器、类型检查器、schema 校验器。骗不过。 |
| 验证缺口 | "没人检查" | MAST 失败的 21.3%。交付的答案,没有跑过那个本可以抓住 bug 的检查。 |
| 修订循环 | "批评者打回" | 批评者拒绝,触发执行者带反馈重跑。需要预算。 |
| 全 LLM 反模式 | "我觉得没问题" | 每个角色都是 LLM,没有确定性检查。经典 MAST 失败。 |
