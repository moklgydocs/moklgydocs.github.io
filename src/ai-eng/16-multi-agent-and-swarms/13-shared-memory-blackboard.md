# 共享记忆与黑板模式

> 2026 年的多智能体系统里共存着两条路线：**消息池**（每个人看到所有人的消息，如 AutoGen GroupChat、MetaGPT）和**带订阅的黑板**（智能体订阅相关事件，如 Context-Aware MCP 或 Matrix 框架）。两者都是多智能体系统中唯一有状态的部分——这意味着有趣的 bug 都住在这里。参考级故障模式是**记忆投毒**（memory poisoning)：一个智能体幻觉出一条"事实"，其他智能体把它当作已验证的真相，准确率以渐进的方式腐坏——这比当场崩溃难调试得多。本课用标准库把两种结构都搭出来，注入一次投毒攻击，并展示在生产中真正有效的三种缓解措施。

**类型：** Learn + Build
**编程语言：** Python（标准库，`threading`)
**前置要求：** 第 16 阶段 · 04（原语模型）、第 16 阶段 · 09（并行蜂群网络）
**预计耗时：** 约 75 分钟

## 问题

多智能体系统需要一个让智能体共享事实的地方。一个直白的选项是"一切都走消息传递"——但那只是多拷几份地重造了共享状态。另一个是"给所有人一个全局日志"——但全局日志无界增长，而且容易被投毒。第三个是"按智能体投影视图"——可扩展，但要背 schema 的重担。

当其中一个智能体产生幻觉并把幻觉写进共享状态，每一个读到该状态的下游智能体都会把幻觉当作事实。等人发现时，推理链已经叠了五层，而根因是最早写下的第三条消息。调试多智能体的准确率腐坏，比调试崩溃难得多。

这就是记忆投毒。它是 MAST 分类法（Cemri et al.,arXiv:2503.13657）中文献记录第二多的故障家族，而且它是结构性的：任何没有出处、没有不可写入验证者的共享记忆设计，迟早会表现出它。

## 概念

### 两种主流拓扑

**全量消息池。** 每个智能体读每一条消息。AutoGen GroupChat 和 MetaGPT 用这个。简单、透明、可检查，但过不了约 10 个智能体这道坎——因为每个智能体的上下文会被其他智能体的工作塞满。

```
agent-A ──write──▶ ┌────────────────┐ ◀──read── agent-D
                   │ message pool   │
agent-B ──write──▶ │                │ ◀──read── agent-E
                   │ (global log)   │
agent-C ──write──▶ └────────────────┘ ◀──read── agent-F
```

**带订阅的黑板。** 智能体声明对话题的兴趣；底层只路由相关消息。CA-MCP(arXiv:2601.11595）和 Matrix 去中心化框架（arXiv:2511.21686）用这个。能扩得更远，但需要 upfront 的 schema 设计，订阅才有意义。

```
                   ┌─ topic: prices ──┐
agent-A ──pub────▶ │                  │ ──▶ agent-D (subscribed)
                   ├─ topic: orders ──┤
agent-B ──pub────▶ │                  │ ──▶ agent-E (subscribed)
                   ├─ topic: alerts ──┤
agent-C ──pub────▶ │                  │ ──▶ agent-F (subscribed)
                   └──────────────────┘
```

### 各自赢在哪

- **全量池**赢在智能体少（< 10)、异构、对话短平快的时候。当每个人看到一切，推"谁说了什么"是 trivial 的。
- **黑板**赢在智能体多、角色同质但实例众多（蜂群）、对话长时运行的时候。路由节省了 token 成本和上下文污染。

生产系统经常混用：顶层一个小全量池（规划层），下面若干黑板（工人层）。

### 记忆投毒，一个场景

三个智能体做一个研究任务。A 是检索智能体，B 是摘要员，C 是分析师。

1. A 抓了一个页面，往共享状态写："该研究报告了 42% 的准确率提升。"
2. 那个页面实际写的是 "4.2% 提升"。A 幻觉了一个小数点。
3. B 读共享状态，写："报告了高达 42% 的准确率提升（来源：A)。"
4. C 读共享状态，写："建议采用——42% 的提升是变革性的。"
5. 最终报告引用了一个从未存在过的 42%。

没有智能体崩溃，没有测试失败，系统"正常工作了"。幻觉通过一个智能体的上下文，经共享状态流进了每个下游智能体的推理。

### 为什么这是结构性的

没有共享状态，A 的幻觉只留在 A 的上下文里。下游智能体会重新抓取或重新推导，可能当场抓住错误。有了朴素的共享状态，A 的上下文变成了所有人的上下文，幻觉被洗白成了事实。

问题不在共享状态本身，而在**没有出处、没有独立验证者**的共享状态。三种缓解措施对症：

1. **每次写入都记录出处。** 共享状态里的每条记录都写明：谁写的、什么时候、在什么提示词下、（如适用）引了什么来源。下游智能体按出处带着相应的怀疑去读。
2. **版本化写入，视为只追加。** 更正是取代旧条目的新条目，不是原地更新。审计轨迹得以保留。
3. **至少保留一个不能写共享状态的智能体。** 一个只读验证者智能体：抽查条目、重新抓取来源、标记不一致。因为它不能往池里写，所以它不会被池投毒。

### 黑板的先例（Hayes-Roth,1985)

黑板模式比 LLM 智能体早了四十年。Hayes-Roth(1985,"A Blackboard Architecture for Control")描述了专家知识源（Knowledge Source)：观察全局黑板、贡献部分解、触发其他知识源。2026 年的黑板（CA-MCP、Matrix）是同一个模式，只是知识源换成了 LLM 智能体、部分解换成了 JSON blob。老文献里记载着写竞争、机会主义控制和一致性的解决方案，现代系统正在重新发现它们。

### 投影 vs 全量视图

纯黑板给每个订阅者相同的投影（按话题圈定）。更激进的设计是**按智能体投影**：每个智能体拿到按它角色定制的视图。LangGraph 的 state reducer 是 2026 年的 经典 实现——reducer 函数把全局状态折叠成角色专属的一片。

按智能体投影扩得更远，但需要 schema。没有它，你等于在每个智能体的提示词里重建临时投影。

### 写竞争模式

多个智能体同时写，是并发问题，不只是 LLM 问题。三种模式有效：

- **顺序写入者（单生产者）。** 所有写都过一个串行化的协调智能体。简单，但是瓶颈。
- **带版本号的乐观并发。** 每条记录带版本；版本不匹配则写入失败并重试。经典的数据库技术。
- **话题分区。** 不同智能体拥有不同话题。没有跨话题竞争。需要设计好的分区边界。

大多数 2026 框架默认顺序写入者，因为 LLM 调用足够慢，竞争罕见，瓶颈不痛。

### 不可写入的验证者

最能承重的缓解措施是只读验证者。实现规则：

- 验证者与团队共享状态（读黑板或池）。
- 验证者对共享状态没有写句柄——只有一条独立的验证通道。
- 验证者独立抓取写入中引用的来源，标记分歧。
- 验证者自己的输出路由给人类或单独的决策智能体，永远不回灌进池。

没有这个隔离，验证者的输出会变成池里的新条目——被投毒的池投毒验证者，被投毒的验证者再投毒它的验证结论。

## 动手构建

`code/main.py` 用标准库 Python 实现了两种拓扑，外加一个玩具投毒攻击和三种缓解措施。

- `MessagePool` —— 线程安全的只追加日志，全量读出。
- `Blackboard` —— 按话题键控的发布/订阅，按智能体订阅。
- `ProvenanceEntry` —— 每次写入记录（writer, timestamp, prompt_hash, source_uri)。
- `PoisoningScenario` —— 跑一个三智能体研究任务，A 幻觉了一个小数点。打印最终报告。
- `Verifier` —— 一个只读智能体，重新抓取来源并标记不一致。在有验证者的情况下重跑同一场景。

运行：

```
python3 code/main.py
```

预期输出：
- 第 1 次运行（无验证者）：幻觉的 42% 一路传进最终报告。
- 第 2 次运行（有验证者）：验证者标记不一致，池被标为 "flagged"，最终报告包含撤回声明。

## 投入使用

`outputs/skill-memory-auditor.md` 是一个 skill，审计任意多智能体系统的共享记忆设计：出处、版本化和验证者隔离。在新的多智能体架构上生产前跑一遍。

## 交付

任何共享记忆设计：

- 每次写入记录出处：`(writer, timestamp, prompt_hash, tool_calls_cited, source_uri)`。
- 日志只追加。更正是引用被取代者的新条目。
- 至少部署一个带独立来源访问的只读验证者智能体。
- 验证者输出走单独通道，不回灌共享池。
- 记录"取代式写入"的占比——占比上升是幻觉模式的早期证据。

## 关键术语

| 术语 | 大家嘴里的说法 | 实际含义 |
|------|----------------|------------------------|
| 消息池 | "共享聊天记录" | 每个智能体都读的只追加日志。完全透明，扩展性差 |
| 黑板 | "共享工作区" | 按话题键控的发布/订阅。智能体订阅相关话题。扩得更远 |
| 出处（Provenance) | "谁写的什么" | 每次写入的元数据：写者、时间戳、提示词、来源 |
| 记忆投毒 | "幻觉扩散" | 一个智能体的错误进入共享状态，下游智能体当作事实 |
| 只追加 | "不原地更新" | 更正是取代旧条目的新条目。保住审计轨迹 |
| 不可写入的验证者 | "独立审计员" | 重新抓取来源、标记不一致的只读智能体 |
| 投影 | "有范围的视图" | 从全局状态算出的按智能体视图。LangGraph reducer 是 经典 案例 |
| 知识源 | "专家智能体" | Hayes-Roth 1985 年对黑板参与者的称呼 |
