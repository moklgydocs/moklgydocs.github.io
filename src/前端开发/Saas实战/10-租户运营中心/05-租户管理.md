# 05 - 租户管理：生命周期操作与版本变更

> **这一步解决什么问题？**
> 租户管理聚焦于租户生命周期：开通（Provision）、激活（Activate）、暂停（Suspend）、终止（Terminate）。本节实现租户查询页面、开通对话框和版本变更对话框。核心设计是**危险操作需确认 + 审计原因**——暂停和终止需要二次确认和 reason 参数，激活不需要。
>
> **ASP.NET Core 开发者的直觉**：租户的四个生命周期操作就像数据库的 `CREATE / ONLINE / OFFLINE / DROP`。Provision = `CREATE DATABASE`，Activate = `ALTER DATABASE SET ONLINE`，Suspend = `ALTER DATABASE SET OFFLINE`，Terminate = `DROP DATABASE`（不可逆）。

      await fetchDashboard()

💡 **ASP.NET Core 类比**：确认对话框就像 `Are you sure?` 的 CLI 提示——危险操作需要二次确认。`confirmAction` 的 `type` 字段就像 `Command` 模式中的命令类型，`handleConfirmAction` 就是 `CommandDispatcher`。

## 代码讲解

### 确认对话框的 Command 分发模式

暂停和终止共用一个 `ConfirmDialog`，通过 `confirmAction.type` 区分操作类型：

```typescript
const [confirmAction, setConfirmAction] = useState<{ type: string; reason?: string } | null>(null)

// 设置确认动作
<Button onClick={() => { setConfirmAction({ type: "suspend" }); setConfirmOpen(true) }}>暂停</Button>
<Button onClick={() => { setConfirmAction({ type: "terminate" }); setConfirmOpen(true) }}>终止</Button>

// 确认后分发
const handleConfirmAction = () => {
  if (confirmAction.type === "suspend") handleSuspend()
  else if (confirmAction.type === "terminate") handleTerminate()
}
```

⚠️ **【易错点】** `confirmAction` 同时承担了"是否打开 Dialog"和"执行什么操作"两个职责。如果 `confirmAction` 为 `null`，Dialog 不会打开（`open={confirmOpen}` 单独控制）。如果用户关闭了 Dialog，`setConfirmAction(null)` 清空操作，防止下次打开时执行残留的操作。

⚠️ **【设计取舍】** 为什么不用两个独立的 ConfirmDialog（一个暂停、一个终止）？因为两个 Dialog 的 UI 几乎相同，只有标题和描述不同。合并为一个 Dialog + 状态分发，减少了重复代码。这和后端用一个 Action 处理多种操作的思路类似。

> 🤔 **导师提问**：暂停和终止都需要 `reason` 参数（审计日志），激活不需要。这和后端的审计日志设计一致——破坏性操作需要记录原因。但前端的 `ConfirmDialog` 目前没有 reason 输入框，`confirmAction.reason` 从何而来？如果需要添加 reason 输入，`ConfirmDialog` 应该如何改造？

### 枚举作为下拉选项

计费周期使用枚举值作为 Select 的 value：

```typescript
const cycleOptions = [
  { value: String(BC.Monthly), label: "月付" },   // value: "1"
  { value: String(BC.Yearly), label: "年付" },   // value: "2"
]

// 提交时转换回数字枚举
cycle: Number(form.cycle) as BillingCycle
```

⚠️ **【易错点】** Select 组件的 `value` 必须是 string 类型，但后端枚举是 int。所以用 `String(BC.Monthly)` 转为 `"1"`，提交时 `Number("1")` 转回 `1`。如果忘记转换，后端会收到字符串 `"1"` 而非数字 `1`，导致 Model Binding 失败。

💡 **ASP.NET Core 类比**：这就像 `JsonConverter<StringEnumConverter>`——默认枚举序列化为 int，但前端下拉框需要字符串。`String(BC.Monthly)` 就是 `"1"`，提交时 `Number("1")` 转回 `1`。

> 🤔 **导师提问**：计费周期用数字枚举（0/1/2）而非字符串（"Monthly"/"Yearly"），前端需要 `String()` → `Number()` 双向转换。在后端，你更倾向于用 `enum BillingCycle { Monthly = 1, Yearly = 2 }` 还是用字符串常量？两种方案在 API 版本兼容性上各有什么优劣？

### form id + Button form 的提交模式

开通和版本变更对话框都使用 `form id` + `Button form` 模式：

```tsx
<form id="provision-form" onSubmit={handleSubmit}>...</form>
<DialogFooter>
  <Button type="submit" form="provision-form">开通</Button>
</DialogFooter>
```

⚠️ **【易错点】** `Button` 不在 `<form>` 内部，但通过 `form="provision-form"` 关联到表单。这样 DialogFooter 可以独立于表单内容布局。如果不加 `form` 属性，点击 Button 不会触发表单的 `onSubmit`，而是需要手动绑定 `onClick`。

💡 **ASP.NET Core 类比**：`form id` 关联就像 ASP.NET Core 的 `asp-handler`——按钮的 `form` 属性指定提交到哪个表单，相当于指定 `asp-handler="Create"` 或 `asp-handler="Edit"`。

### 版本变更对现有租户的影响

三种级联方案：

| 方案 | 行为 | 优缺点 |
|------|------|--------|
| **A（级联更新）** | 所有该版本租户配额自动变更 | 风险：商业合同冲突 |
| **B（快照模式）** | 租户创建时拷贝配额，后续不受影响 | 安全但升级需手动 |
| **C（默认+覆盖）** | 无覆盖时跟随版本变更，有覆盖则保留 | 灵活但复杂 |

当前项目采用**方案 C**，在租户详情页的配额管理 Tab 中体现。

> 🤔 **导师提问**：版本变更的三种级联方案中，当前项目选择了方案 C。这三种方案本质上对应了配置继承的三种策略——覆盖（Override）、隔离（Isolate）、继承（Inherit）。在后端，你设计过类似的默认配置 + 租户级覆盖模型吗？EF Core 的 TPH/TPT 继承策略和这里的方案 C 有什么思想上的共通之处？

## 踩坑提醒

1. **`confirmAction.reason` 目前没有输入源**：暂停和终止需要 reason 参数（审计日志），但 `ConfirmDialog` 没有 reason 输入框。当前 `confirmAction.reason` 是 `undefined`，后端会收到空值。如果审计要求 reason 必填，需要给 ConfirmDialog 增加一个 Textarea 输入框。

2. **开通对话框的版本列表加载时机**：`editionsApi.getList()` 在 `useEffect([open])` 中调用，每次打开 Dialog 都会请求。如果版本列表很大且变化不频繁，可以考虑缓存版本列表到父组件，通过 Props 传入，避免重复请求。
