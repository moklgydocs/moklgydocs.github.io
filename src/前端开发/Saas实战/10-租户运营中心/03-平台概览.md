# 03 - 平台概览：5 个 StatCard 的仪表盘

> **这一步解决什么问题？**
> 就像 ASP.NET 的 Health Check Dashboard 一样，平台概览是运营中心的"仪表盘"。运营人员打开后台，第一眼需要看到什么？租户总数、活跃租户、暂停租户、版本数量、月度收入——5 个关键指标一目了然。
>
> **ASP.NET Core 开发者的直觉**：`PlatformOverviewDto` 就像 ASP.NET 的 `/health` 端点返回的 `HealthCheckResult`——一个聚合的统计对象，背后可能关联了多张表、多个查询。

## 一、PlatformOverviewDto 的字段解读

### 1.1 类型定义

```typescript
// src/types/index.ts
export interface PlatformOverviewDto {
  totalTenants: number              // 租户总数
  activeTenants: number             // 活跃租户
  suspendedTenants: number          // 暂停租户
  totalEditions: number             // 版本总数
  monthlyRecurringRevenue: number   // 月度经常性收入(MRR)
}
```

### 1.2 为什么是 5 个字段？

| 字段 | 业务含义 | 运营价值 |
|------|---------|---------|
| `totalTenants` | 系统中有多少租户 | 平台规模 |
| `activeTenants` | 多少租户在正常使用 | 活跃度 |
| `suspendedTenants` | 多少租户被暂停 | 风险信号 |
| `totalEditions` | 定义了多少版本套餐 | 产品丰富度 |
| `monthlyRecurringRevenue` | 每月可预期的收入 | 财务健康 |

【设计取舍】 为什么没有 `terminatedTenants`（已终止租户数）？因为终止是终态，已终止的租户不再产生收入，也不需要关注。如果运营需要查看历史终止数据，应该在操作日志中查询，而不是放在概览页。

**MRR（Monthly Recurring Revenue）** 是 SaaS 最核心的财务指标，就像后端的 QPS 之于性能监控。MRR 突然下降 30% 比任何告警都严重。

🤔 **导师提问**：如果我们想加一个"今日新开通租户数"的 StatCard，后端的 `PlatformOverviewDto` 要加字段，前端要加组件。但这个指标的查询频率（每次打开概览页）远高于它的变化频率（一天最多几次）。你会怎么优化？

## 二、完整源码

### 2.1 OpsOverviewPage 组件

```tsx
// src/pages/ops/overview/index.tsx
import { useEffect, useState, useCallback } from "react"
import { AnimatedPage } from "@/components/shared/animated-page"
import { PageHeader } from "@/components/shared/page-header"
import { StatCard } from "@/components/shared/stat-card"
import { overviewApi } from "@/api/ops/overview"
import { toast } from "sonner"
import type { PlatformOverviewDto } from "@/types"
import { Building2, ShieldCheck, AlertTriangle, Box, DollarSign } from "lucide-react"

/**
 * 平台概览页面
 * 展示租户运营中心整体运行状况，包括租户数量、版本数量和月度收入等关键指标。
 */
export default function OpsOverviewPage() {
  const [data, setData] = useState<PlatformOverviewDto | null>(null)
  const [loading, setLoading] = useState(false)

  const fetchData = useCallback(async () => {
    setLoading(true)
    try {
      const res = await overviewApi.get()
      setData(res.data ?? null)
    } catch {
      toast.error("获取平台概览失败")
    } finally {
      setLoading(false)
    }
  }, [])

  useEffect(() => { fetchData() }, [fetchData])

  return (
    <AnimatedPage>
      <div className="space-y-6">
        <PageHeader title="平台概览" description="租户运营中心整体运行状况" />
        <div className="grid grid-cols-1 sm:grid-cols-2 lg:grid-cols-5 gap-4">
          <StatCard icon={Building2} label="租户总数" value={data?.totalTenants ?? 0} loading={loading} color="primary" />
          <StatCard icon={ShieldCheck} label="活跃租户" value={data?.activeTenants ?? 0} loading={loading} color="success" />
          <StatCard icon={AlertTriangle} label="暂停租户" value={data?.suspendedTenants ?? 0} loading={loading} color="warning" />
          <StatCard icon={Box} label="版本总数" value={data?.totalEditions ?? 0} loading={loading} color="info" />
          <StatCard icon={DollarSign} label="月度经常性收入" value={`¥${(data?.monthlyRecurringRevenue ?? 0).toLocaleString()}`} loading={loading} color="primary" />
        </div>
      </div>
    </AnimatedPage>
  )
}
```

## 三、逐行讲解

### 3.1 状态管理

```typescript
const [data, setData] = useState<PlatformOverviewDto | null>(null)
const [loading, setLoading] = useState(false)
```

- `data`：初始值为 `null`，表示"还没加载过"。与 `undefined` 的区别：`null` 是"明确没有数据"，`undefined` 是"未定义"
- `loading`：初始值为 `false`，而不是 `true`。为什么？因为组件首次渲染时还没有发起请求，`loading` 应该为 false。请求发起后设为 true

【易错点】 如果 `loading` 初始值为 `true`，页面首次渲染时会显示 Skeleton 一闪而过（因为 `useEffect` 同步调度 `fetchData`，但 React 批处理了状态更新）。`false` 初始值避免了这种闪烁。

### 3.2 fetchData 的 useCallback

```typescript
const fetchData = useCallback(async () => {
  setLoading(true)
  try {
    const res = await overviewApi.get()
    setData(res.data ?? null)
  } catch {
    toast.error("获取平台概览失败")
  } finally {
    setLoading(false)
  }
}, [])
```

【性能陷阱】 `useCallback` 的依赖数组是 `[]`（空），意味着 `fetchData` 的引用在组件整个生命周期中保持不变。这是故意的：

- `overviewApi.get()` 是模块级常量，不会变
- `setData`、`setLoading` 是 React 保证的稳定引用
- 如果不传 `[]`，每次渲染都创建新的 `fetchData`，导致 `useEffect` 无限循环

**ASP.NET Core 类比**：`useCallback` 就像 `IHttpClientFactory` 缓存实例——避免重复创建，保证引用稳定。

【易错点】 **平台级数据 vs 租户级数据的混淆**：`overviewApi.get()` 没有传任何参数，因为它获取的是平台级的聚合数据。如果错误地传了 `tenantId`，后端可能返回单个租户的概览，而不是整个平台的。运营中心的概览 API 天然不需要租户过滤——它就是"全局"的。

### 3.3 setData 中的空值合并

```typescript
setData(res.data ?? null)
```

【易错点】 用 `?? null` 而非 `|| null`。因为 `res.data` 可能是 `0` 或空字符串——这些是 falsy 但合法的值：

- `??`（空值合并）：只有 `null`/`undefined` 时才用右侧。`0 ?? null` → `0`
- `||`（逻辑或）：任何 falsy 值都用右侧。`0 || null` → `null`（错误！丢失了 0）

🤔 **导师提问**：如果后端返回的 `monthlyRecurringRevenue` 是 `0`，用 `|| null` 会导致什么？MRR 显示为 `¥0` 还是空白？注意 StatCard 的 value 是 `data?.monthlyRecurringRevenue ?? 0`——这里 `??` 保证了 `0` 不会丢失。

### 3.4 useEffect 的触发

```typescript
useEffect(() => { fetchData() }, [fetchData])
```

依赖数组是 `[fetchData]`。由于 `fetchData` 被 `useCallback(() => {...}, [])` 包裹，引用不变，所以 `useEffect` 只在组件挂载时执行一次。

### 3.5 StatCard 的 5 个实例

```tsx
<StatCard icon={Building2} label="租户总数" value={data?.totalTenants ?? 0} loading={loading} color="primary" />
```

每个 StatCard 接收 5 个 props：

| prop | 说明 | 示例 |
|------|------|------|
| `icon` | lucide-react 图标组件 | `Building2` |
| `label` | 标题文本 | "租户总数" |
| `value` | 数值或格式化字符串 | `0` 或 `"¥12,345"` |
| `loading` | 加载状态 | `true` 时显示 Skeleton |
| `color` | 主题色 | `"primary"` / `"success"` / `"warning"` / `"destructive"` |

图标的语义选择：

| StatCard | 图标 | 选择理由 |
|----------|------|---------|
| 租户总数 | `Building2` | 建筑=组织=租户 |
| 活跃租户 | `ShieldCheck` | 盾牌+勾=安全=正常 |
| 暂停租户 | `AlertTriangle` | 三角警告=需要关注 |
| 版本总数 | `Box` | 盒子=产品=版本 |
| 月度收入 | `DollarSign` | 美元=收入 |

### 3.6 MRR 的格式化

```tsx
value={`¥${(data?.monthlyRecurringRevenue ?? 0).toLocaleString()}`}
```

`toLocaleString()` 添加千分位分隔符：

```
0       → "0"
12345   → "12,345"
1234567 → "1,234,567"
```

最终显示为 `¥12,345`。

【易错点】 `toLocaleString()` 的行为依赖浏览器语言设置。在中文环境下可能显示 `12,345` 或 `1万2345`。如果需要一致格式，应该用 `Intl.NumberFormat` 并指定 `locale`：

```typescript
new Intl.NumberFormat("zh-CN").format(12345)  // "12,345"
```

### 3.7 响应式网格布局

```tsx
<div className="grid grid-cols-1 sm:grid-cols-2 lg:grid-cols-5 gap-4">
```

| 屏幕宽度 | 列数 | 效果 |
|---------|------|------|
| < 640px (手机) | 1 | 每行 1 个卡片 |
| 640-1024px (平板) | 2 | 每行 2 个卡片 |
| > 1024px (桌面) | 5 | 每行 5 个卡片 |

5 列布局匹配 5 个统计卡片，桌面端一行展示所有指标，无需滚动。

🤔 **导师提问**：如果有 6 个 StatCard，桌面端应该用 `lg:grid-cols-6` 还是 `lg:grid-cols-3`（分两行）？6 列可能太窄，3x2 布局更合理。但这也取决于每个卡片的信息密度。

### 3.8 AnimatedPage 和 PageHeader

```tsx
<AnimatedPage>
  <div className="space-y-6">
    <PageHeader title="平台概览" description="租户运营中心整体运行状况" />
    {/* ... */}
  </div>
</AnimatedPage>
```

- `AnimatedPage`：页面切换动画容器（framer-motion），提供统一的淡入效果
- `PageHeader`：页面标题栏，包含标题和描述文本。其他页面还会在右侧放操作按钮

## 四、概览页的局限与改进方向

### 4.1 当前局限

1. **没有时间趋势**：只展示当前快照，看不到 MRR 是涨还是跌
2. **没有下钻能力**：看到暂停租户数增加，但无法从这里跳转到暂停租户列表
3. **没有自动刷新**：数据只在页面加载时获取一次，不会自动更新

### 4.2 改进方向

**趋势图**：增加 MRR 7 天趋势线图，用 Recharts 或 ECharts 实现：

```tsx
// 伪代码：MRR 趋势图
<LineChart data={mrrTrend}>
  <XAxis dataKey="date" />
  <YAxis />
  <Line dataKey="mrr" stroke="#2563eb" />
</LineChart>
```

**下钻链接**：暂停租户的 StatCard 点击后跳转到租户管理页，筛选 `status=Suspended`：

```tsx
<StatCard
  icon={AlertTriangle}
  label="暂停租户"
  value={data?.suspendedTenants ?? 0}
  color="warning"
  onClick={() => navigate("/ops/tenants?status=suspended")}
/>
```

**自动刷新**：用 `useEffect` + `setInterval` 每 30 秒刷新一次：

```typescript
useEffect(() => {
  const timer = setInterval(fetchData, 30000)
  return () => clearInterval(timer)
}, [fetchData])
```

【性能陷阱】 自动刷新间隔不能太短。30 秒是合理值——太快会增加服务器压力，太慢则数据不及时。如果运营中心同时有 10 个管理员在线，30 秒间隔意味着每秒约 0.33 次请求，完全可以接受。

【性能陷阱】 **概览页的多个 API 调用**：当前概览页只调用一个 API（`overviewApi.get()`），后端在单次查询中聚合所有 5 个指标。如果未来改为 5 个独立 API，页面加载时间将从 1 次 RTT 变成 5 次 RTT，甚至可能出现数据不一致（比如在两次请求之间有租户被暂停）。**聚合 API 是概览页的最佳实践**——就像后端的 CQRS 模式，为读场景设计专门的查询接口。

### 4.3 概览页的数据流图

理解概览页如何从后端获取数据，有助于我们把握整个数据流：

```
┌──────────────────────────────────────────────────────────────────┐
│                        概览页数据流                                │
│                                                                  │
│  后端                                                            │
│  ┌─────────────────┐     ┌──────────────────────────┐           │
│  │ Tenants 表       │     │ Editions 表               │           │
│  │ COUNT(*) → total │     │ COUNT(*) → totalEditions  │           │
│  │ WHERE Status=1   │     └────────────┬─────────────┘           │
│  │   → activeTenants│                  │                         │
│  │ WHERE Status=2   │     ┌────────────┴─────────────┐           │
│  │   → suspended    │     │ TenantEditions 表          │           │
│  └────────┬────────┘     │ SUM(MonthlyPrice)          │           │
│           │              │   → monthlyRecurringRevenue│           │
│           ▼              └────────────┬─────────────┘           │
│  ┌─────────────────┐                  │                         │
│  │ GET /overview    │ ◄───────────────┘                         │
│  │ → PlatformOverviewDto                                         │
│  └────────┬────────┘                                             │
│           │                                                      │
│  前端     ▼                                                      │
│  ┌─────────────────┐                                             │
│  │ overviewApi.get()│                                             │
│  │ → setData(res)   │                                             │
│  └────────┬────────┘                                             │
│           ▼                                                      │
│  ┌─────────────────────────────────────────┐                    │
│  │ 5 × StatCard ← data?.xxx ?? 0           │                    │
│  └─────────────────────────────────────────┘                    │
└──────────────────────────────────────────────────────────────────┘
```

后端的一次 `GET /overview` 聚合了 3 张表的查询结果，前端一次请求拿到全部数据。这就是聚合 API 的威力——如果拆成 3 个 API，前端需要 `Promise.all` 并行请求，还要处理部分失败的情况。

## 五、StatCard 组件的接口设计

虽然 StatCard 是共享组件，不在运营中心目录下，但理解它的接口有助于用好它：

```typescript
interface StatCardProps {
  icon?: LucideIcon       // 图标组件
  label: string           // 标题
  value: string | number  // 数值
  sub?: string            // 副标题（如"共 5 个"）
  loading?: boolean       // 加载状态
  color?: "primary" | "success" | "warning" | "destructive" | "info"  // 主题色
}
```

`color` 的语义映射：

| color | 含义 | 运营场景 |
|-------|------|---------|
| `primary` | 默认/中性 | 总数、MRR |
| `success` | 正面/健康 | 活跃租户 |
| `warning` | 需要关注 | 暂停租户 |
| `destructive` | 危险/异常 | 终止租户（未使用） |
| `info` | 信息/辅助 | 版本数 |

暂停租户用 `warning`（橙色）而非 `destructive`（红色），因为暂停≠终止——暂停是可以恢复的，只是需要关注。

🤔 **导师提问**：如果暂停租户数从 2 增长到 20，我们应该动态改变 StatCard 的 color（从 warning 变 destructive）吗？这种"根据数据变化改变 UI 语义"的做法在运营看板中很常见，但也可能引起误判——20 个暂停租户在 1000 个总租户中可能不是大问题。

## 六、overview API 的实现

```typescript
// src/api/ops/overview.ts
import { get } from "./http"
import type { PlatformOverviewDto } from "@/types"

export const overviewApi = {
  get: () => get<PlatformOverviewDto>("/api/tenant-ops/overview"),
}
```

只有一个方法——运营中心概览只需要一个聚合查询。注意它返回的是 `PlatformOverviewDto`，不是分页结果，因为没有"列表"的概念。

**ASP.NET Core 类比**：这就像一个只读的 `DashboardController`，没有 CRUD 操作，只有一个 `GetOverview()` 方法。后端可能用一条复杂的 SQL 聚合查询，或者从缓存中读取预计算结果。

## ⚠️ 踩坑提醒

1. **`loading` 初始值为 `false` 而非 `true`**：如果初始值为 `true`，页面首次渲染时会显示 Skeleton 一闪而过。`false` 初始值避免了这种闪烁。
2. **`?? null` 而非 `|| null`**：`res.data` 可能是 `0` 或空字符串（falsy 但合法），`||` 会错误替换。`??` 只在 `null`/`undefined` 时替换。
3. **MRR 为 0 时的显示**：如果后端返回的 `monthlyRecurringRevenue` 是 `0`，用 `|| null` 会导致显示空白。`data?.monthlyRecurringRevenue ?? 0` 保证了 `0` 不会丢失。
4. **概览页只调用一个聚合 API**：当前设计是最佳实践——如果拆成多个 API，可能出现数据不一致和加载时间增加。

## ⚠️ 踩坑提醒

1. **`loading` 初始值必须是 `false`**：如果初始值为 `true`，页面首次渲染会显示 Skeleton 一闪而过（因为 `useEffect` 同步调度 `fetchData`，React 批处理了状态更新）。`false` 初始值避免了这种闪烁。

2. **`?? null` 而非 `|| null`**：`res.data` 可能是 `0` 或空字符串——falsy 但合法的值。`||` 会错误地把 `0` 替换为 `null`，`??` 只在 `null`/`undefined` 时替换。特别是 MRR 为 0 时，`|| null` 会导致显示空白。
