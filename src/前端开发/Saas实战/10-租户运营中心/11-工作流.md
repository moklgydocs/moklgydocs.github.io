# 11 - 工作流：审批状态机与操作日志

> **这一步解决什么问题？**
> 复杂的租户操作（开通、升级）可能需要审批流程——不是所有人都能直接开通租户，高级操作需要上级确认后才能执行。工作流引入了"审批"环节，让开通和升级操作不再是即时生效的。本节实现工作流的发起和审批操作，以及操作日志搜索页。
>
> **ASP.NET Core 开发者的直觉**：工作流就像 `IWorkflowExecutor` + 状态机——先创建待审批记录（Pending），审批通过后执行实际操作（Provision/Upgrade），审批拒绝则标记为 Rejected。这和 MediatR 的 `INotificationHandler` 类似，但增加了"等待审批"这个中间状态。

## 代码实现

### 工作流审批页

```tsx
// src/pages/ops/workflow/index.tsx
import { useState, useEffect } from "react"
import { Play, ArrowUpCircle, CheckCircle, XCircle } from "lucide-react"
import { Button } from "@/components/ui/button"
import { Input } from "@/components/ui/input"
import { Label } from "@/components/ui/label"
import { Textarea } from "@/components/ui/textarea"
import { Card, CardContent, CardHeader, CardTitle } from "@/components/ui/card"
import { Select, SelectContent, SelectItem, SelectTrigger, SelectValue } from "@/components/ui/select"
import { toast } from "sonner"
import { workflowApi } from "@/api/ops/workflow"
import { editionsApi } from "@/api/ops/editions"
import type { EditionDto, StartProvisionWorkflowRequest, StartUpgradeWorkflowRequest, ApprovalRequest } from "@/types"

export default function OpsWorkflowPage() {
  const [editions, setEditions] = useState<EditionDto[]>([])
  const [provisionForm, setProvisionForm] = useState<StartProvisionWorkflowRequest>({
    tenantName: "", tenantIdentifier: "", editionId: "",
  })
  const [upgradeForm, setUpgradeForm] = useState<StartUpgradeWorkflowRequest>({
    tenantId: "", targetEditionId: "",
  })
  const [approvalForm, setApprovalForm] = useState<ApprovalRequest>({
    workflowId: "", approved: true, reason: "",
  })
  const [submitting, setSubmitting] = useState<string | null>(null)

  useEffect(() => {
    editionsApi.getList().then((res) => setEditions((res.data ?? []).filter((e) => e.isActive)))
  }, [])

  const handleStartProvision = async () => {
    if (!provisionForm.tenantName || !provisionForm.tenantIdentifier || !provisionForm.editionId) {
      toast.error("请填写完整的开通信息"); return
    }
    setSubmitting("provision")
    try { await workflowApi.startProvision(provisionForm); toast.success("开通工作流已发起") }
    catch { toast.error("发起失败") } finally { setSubmitting(null) }
  }

  const handleStartUpgrade = async () => {
    if (!upgradeForm.tenantId || !upgradeForm.targetEditionId) {
      toast.error("请填写完整的升级信息"); return
    }
    setSubmitting("upgrade")
    try { await workflowApi.startUpgrade(upgradeForm); toast.success("升级工作流已发起") }
    catch { toast.error("发起失败") } finally { setSubmitting(null) }
  }

  const handleApproval = async (approved: boolean) => {
    if (!approvalForm.workflowId) { toast.error("请输入工作流 ID"); return }
    setSubmitting("approval")
    try {
      const fn = approved ? workflowApi.approve : workflowApi.reject
      await fn(approvalForm.workflowId, { ...approvalForm, approved })
      toast.success(approved ? "已审批通过" : "已审批拒绝")
    } catch { toast.error("审批操作失败") } finally { setSubmitting(null) }
  }

  return (
    <div className="p-6 space-y-6">
      <h1 className="text-2xl font-bold">工作流审批</h1>
      <div className="grid grid-cols-1 lg:grid-cols-3 gap-6">
        {/* 发起开通工作流 Card */}
        {/* 发起升级工作流 Card */}
        {/* 审批操作 Card */}
        {/* ... 完整渲染见源码 */}
      </div>
    </div>
  )
}
```

### 操作日志搜索页

```tsx
// src/pages/ops/search/index.tsx
import { useState } from "react"
import { Search } from "lucide-react"
import { Button } from "@/components/ui/button"
import { Input } from "@/components/ui/input"
import { Table, TableBody, TableCell, TableHead, TableHeader, TableRow } from "@/components/ui/table"
import { Badge } from "@/components/ui/badge"
import { toast } from "sonner"
import opsHttp from "@/api/ops/http"
import type { TenantOperationLogDto } from "@/api/ops/tenants"

export default function OpsSearchPage() {
  const [keyword, setKeyword] = useState("")
  const [results, setResults] = useState<TenantOperationLogDto[]>([])
  const [loading, setLoading] = useState(false)

  const handleSearch = async () => {
    if (!keyword.trim()) { toast.error("请输入搜索关键词"); return }
    setLoading(true)
    try { setResults(await opsHttp.get<TenantOperationLogDto[]>("/search", { params: { keyword } })) }
    catch { toast.error("搜索失败") } finally { setLoading(false) }
  }

  return (
    <div className="p-6 space-y-6">
      <h1 className="text-2xl font-bold">操作日志搜索</h1>
      <div className="flex gap-2">
        <Input value={keyword} onChange={(e) => setKeyword(e.target.value)}
          placeholder="输入关键词搜索操作日志..." className="max-w-md"
          onKeyDown={(e) => e.key === "Enter" && handleSearch()} />
        <Button onClick={handleSearch} disabled={loading}>
          <Search className="mr-2 h-4 w-4" /> 搜索</Button>
      </div>
      {/* 搜索结果 Table */}
    </div>
  )
}
```

## 代码讲解

### 工作流的状态流转

```
发起开通/升级 → 创建工作流记录 → 等待审批
                                       ↓
                              审批通过 → 执行操作
                              审批拒绝 → 工作流终止
```

💡 **ASP.NET Core 类比**：工作流就像 `IWorkflowExecutor` + 状态机——先创建待审批记录（Pending），审批通过后执行实际操作（Provision/Upgrade）。审批拒绝则标记为 Rejected。

### 全局互斥 loading

```typescript
const [submitting, setSubmitting] = useState<string | null>(null)

// 任一操作进行中，所有按钮禁用
<Button disabled={submitting !== null} onClick={handleStartProvision}>发起开通</Button>
<Button disabled={submitting !== null} onClick={handleStartUpgrade}>发起升级</Button>
<Button disabled={submitting !== null} onClick={() => handleApproval(true)}>通过</Button>
```

⚠️ **【设计取舍】** 三个 Card 共用一个 `submitting` 状态来防止重复提交。这和功能开关页面的独立 loading 策略不同——三个按钮共用一个 `string | null`。选择全局互斥的原因是：工作流的三个操作是**互斥**的——你不应该同时发起开通和审批，它们操作的是不同的业务流程，但共享页面级的提交状态。

⚠️ **【易错点】** 全局互斥的代价：如果审批操作需要 5 秒，期间用户无法发起开通或升级。如果需要允许并行操作，应该改为三个独立的 `useState<boolean>`。

> 🤔 **导师提问**：工作流的三个 Card（开通/升级/审批）都共用一个 `submitting` 状态来防止重复提交。这和功能开关页面的独立 loading 策略不同。为什么工作流页面选择全局互斥，而不是三个独立 loading？如果两个运营员同时审批不同的工作流，后端如何处理并发审批？

### 审批操作的模式

```typescript
const handleApproval = async (approved: boolean) => {
  const fn = approved ? workflowApi.approve : workflowApi.reject
  await fn(approvalForm.workflowId, { ...approvalForm, approved })
  toast.success(approved ? "已审批通过" : "已审批拒绝")
}
```

⚠️ **【易错点】** `handleApproval` 同时处理通过和拒绝——`const fn = approved ? approveWorkflow : rejectWorkflow`。这和后端用一个 Action 处理多种操作（如 `[HttpPatch] process`）的取舍一样。合并处理的简洁性 vs 分离处理的清晰性，取决于业务复杂度——如果通过和拒绝的逻辑差异很大（如通过需要额外审批步骤），应该拆成两个独立函数。

> 🤔 **导师提问**：工作流的状态流转（Pending → Approved → Executed / Rejected）是经典的有限状态机。在后端，你通常用数据库事务保证状态转换的原子性。但前端没有事务概念——如果 `approveWorkflow` 请求发出后网络超时，前端无法知道后端是否已处理。这种情况在前端应该如何处理？提示：考虑轮询工作流状态或乐观更新 + 回滚。

### 操作日志搜索直接使用 opsHttp

```typescript
setResults(await opsHttp.get<TenantOperationLogDto[]>("/search", { params: { keyword } }))
```

⚠️ **【易错点】** 搜索页直接使用 `opsHttp.get`（原始 axios 实例），而不是通过 API 模块封装。这和 `data-exchange.ts` 的做法类似——当 API 调用是临时性的、不需要复用的，可以直接在组件中使用 `opsHttp`。但如果搜索功能在其他页面也需要用到，应该封装到 `api/ops/search.ts` 模块中。

> 🤔 **导师提问**：操作日志搜索页直接使用了 `opsHttp.get`（原始 axios 实例），而不是通过 API 模块封装。这和 02 节中 `data-exchange.ts` 的做法类似。什么情况下应该把 API 调用封装到独立模块，什么情况下可以直接在组件中使用 `opsHttp`？两种方式的优缺点是什么？

## 踩坑提醒

1. **网络超时后前端状态不一致**：如果 `approveWorkflow` 请求超时，前端不知道后端是否已经处理。用户可能再次点击"通过"，导致重复审批。后端应该做幂等处理——同一个 `instanceId` 只能审批一次，重复请求返回"已处理"。

2. **版本列表未缓存**：`editionsApi.getList()` 在页面加载时请求，但如果版本列表很大（100+），Select 渲染可能卡顿。应该考虑虚拟滚动或只请求活跃版本的精简列表。
