# 04 - 权限定义

> **这一步解决什么问题？** 权限定义是 RBAC 模型的"原子单位"。就像 ASP.NET Core 里 `[Authorize(Policy = "Purchase.Approve")]` 中的策略名，每个权限定义对应一个具体的操作或数据范围。但权限不是平铺的列表——它按组分类，组内定义可以嵌套，形成一棵权限树。我们要实现权限组的 CRUD 和权限定义的管理，并理解树形数据的扁平化展示技巧。

## 一、ASP.NET Core 类比：权限定义 = Policy 名称

在 ASP.NET Core 里，你定义 Policy 的方式：

```csharp
// ASP.NET Core: 定义 Policy
services.AddAuthorization(options =>
{
    options.AddPolicy("Purchase.View", policy => policy.RequireClaim("permission", "Purchase.View"));
    options.AddPolicy("Purchase.Approve", policy => policy.RequireClaim("permission", "Purchase.Approve"));
    options.AddPolicy("Inventory.View", policy => policy.RequireClaim("permission", "Inventory.View"));
});
```

在权限中心里，这些 Policy 名称变成了数据库中的权限定义记录：

```
权限组: Purchase (采购管理)
├── Purchase.View      [操作权限, 启用]  → 对应 Policy "Purchase.View"
├── Purchase.Create    [操作权限, 启用]  → 对应 Policy "Purchase.Create"
├── Purchase.Approve   [操作权限, 启用]  → 对应 Policy "Purchase.Approve"
└── Purchase.DataScope [数据权限, 启用]  → 无 Policy 对应，用于后端数据过滤

权限组: Inventory (库存管理)
├── Inventory.View     [操作权限, 启用]
└── Inventory.Adjust   [操作权限, 禁用]  → 策略存在但不生效
```

## 二、数据模型：两层树形结构

### 2.1 权限组 + 权限定义

```
权限组 (PermissionGroup)
├── code: "Purchase"            ← 组代码，创建后不可改
├── displayName: "采购管理"      ← 显示名称
├── sort: 1
└── permissions: [               ← 组下的权限定义列表
      PermissionDefinition,
      PermissionDefinition,
      ...
    ]

权限定义 (PermissionDefinition)   ← 支持嵌套子定义
├── name: "Purchase.Approve"     ← 权限名称，创建后不可改
├── displayName: "审批采购单"
├── type: 0 (操作权限) | 1 (数据权限)
├── isEnabled: true
├── sort: 3
└── children: [                  ← 子权限定义（更深的树）
      PermissionDefinition,
      ...
    ]
```

### 2.2 类型定义

> **🤔 导师提问**：`PermissionDefinitionDto` 有一个 `children: PermissionDefinitionDto[]` 字段——类型引用了自身，形成递归结构。在 C# 中你也会遇到类似的递归类型（如 `List<Category> Children`）。递归类型在序列化为 JSON 时很自然，但扁平化到表格中需要手动处理。如果不扁平化，直接把树形 JSON 丢给 `AgTable`，会发生什么？

```typescript
// src/types/index.ts
export interface PermissionGroupDto {
  id: string
  code: string           // 如 "Purchase"
  displayName: string    // 如 "采购管理"
  sort: number
  permissions: PermissionDefinitionDto[]  // 组下的权限定义列表
}

export interface PermissionDefinitionDto {
  id: string
  name: string           // 如 "Purchase.Approve"
  displayName: string    // 如 "审批采购单"
  parentId: string | null
  type: number           // 0=操作权限, 1=数据权限
  isEnabled: boolean
  sort: number
  children: PermissionDefinitionDto[]   // 子权限定义（递归嵌套）
}
```

## 三、两个 API 端点的区别

权限定义有两个获取端点：

| 端点 | 用途 | 返回内容 |
|------|------|---------|
| `GET /api/permissions/admin/definitions?appCode=xxx` | **管理视图** | 包含所有分组（含禁用的） |
| `GET /api/permissions/definitions?appCode=xxx` | **普通视图** | 仅可见分组（用于角色分配权限时） |

```typescript
// src/api/perm/permissions.ts
export const permissionsApi = {
  /** 管理员视图（包含全部分组） */
  getAllDefinitions(appCode: string) {
    return get<PermissionGroupDto[]>("/api/permissions/admin/definitions", { appCode })
  },

  /** 普通视图（仅可见分组） */
  getDefinitions(appCode: string) {
    return get<PermissionGroupDto[]>("/api/permissions/definitions", { appCode })
  },

  /** 创建权限分组 */
  createGroup(data: CreatePermissionGroupRequest) { /* ... */ },

  /** 更新权限分组 */
  updateGroup(id: string, data: UpdatePermissionGroupRequest) { /* ... */ },

  /** 删除权限分组 */
  deleteGroup(id: string) { /* ... */ },

  /** 创建权限定义 */
  createDefinition(data: CreatePermissionDefinitionRequest) { /* ... */ },

  /** 更新权限定义 */
  updateDefinition(id: string, data: UpdatePermissionDefinitionRequest) { /* ... */ },

  /** 删除权限定义 */
  deleteDefinition(id: string) { /* ... */ },
}
```

💡 **ASP.NET Core 类比**：管理视图 ≈ `IncludeDisabled = true` 的查询参数，普通视图 ≈ 默认只查启用的记录。

> **🤔 导师提问**：为什么"角色分配权限"时用普通视图（不含禁用的），而"权限管理页面"用管理视图（包含禁用的）？如果一个禁用的权限出现在角色分配的勾选列表中，管理员给它打勾了，后端应该接受还是拒绝？这种"看不到就不会选错"的设计，在 ASP.NET Core 中有类似的做法吗？

## 四、树形数据的扁平化展示

权限定义是树形结构，但 `AgTable` 需要扁平的行数据。我们需要一个**扁平化函数**，将树转换为表格行，同时记录每行的深度和展开状态。

### 4.1 扁平行类型

```typescript
// src/pages/perm/permissions/index.tsx
interface FlatPermRow {
  id: string
  rowType: "group" | "permission"    // 行类型：权限组或权限定义
  depth: number                      // 缩进层级
  displayName: string
  code: string
  groupCode: string
  type?: number                      // 权限类型：0=操作权限，1=数据权限
  isEnabled?: boolean
  sort: number
  hasChildren: boolean
  childCount?: number                // 子权限总数
  enabledCount?: number              // 已启用的子权限数
  _groupDto?: PermissionGroupDto     // 关联的权限组 DTO
  _permDto?: PermissionDefinitionDto // 关联的权限定义 DTO
}
```

### 4.2 递归扁平化

```typescript
/** 递归统计权限定义总数 */
function countAll(perms: PermissionDefinitionDto[]): number {
  return perms.reduce((sum, p) => sum + 1 + countAll(p.children), 0)
}

/** 递归统计已启用的权限定义数 */
function countEnabled(perms: PermissionDefinitionDto[]): number {
  return perms.reduce(
    (sum, p) => sum + (p.isEnabled ? 1 : 0) + countEnabled(p.children),
    0,
  )
}

/** 递归将权限定义树扁平化为行数据 */
function flattenPermissions(
  perms: PermissionDefinitionDto[],
  depth: number,
  groupCode: string,
  expandedIds: Set<string>,
  rows: FlatPermRow[],
) {
  for (const perm of perms) {
    rows.push({
      id: perm.id,
      rowType: "permission",
      depth,
      displayName: perm.displayName,
      code: perm.name,
      groupCode,
      type: perm.type,
      isEnabled: perm.isEnabled,
      sort: perm.sort,
      hasChildren: perm.children.length > 0,
      _permDto: perm,
    })
    // 仅展开的节点才递归处理子级
    if (perm.children.length > 0 && expandedIds.has(perm.id)) {
      flattenPermissions(perm.children, depth + 1, groupCode, expandedIds, rows)
    }
  }
}

/** 将权限组树扁平化为表格行数据 */
function flattenTree(
  groups: PermissionGroupDto[],
  expandedIds: Set<string>,
): FlatPermRow[] {
  const rows: FlatPermRow[] = []
  for (const group of groups) {
    rows.push({
      id: group.id,
      rowType: "group",
      depth: 0,
      displayName: group.displayName,
      code: group.code,
      groupCode: group.code,
      sort: group.sort,
      hasChildren: group.permissions.length > 0,
      childCount: countAll(group.permissions),
      enabledCount: countEnabled(group.permissions),
      _groupDto: group,
    })
    if (expandedIds.has(group.id)) {
      flattenPermissions(group.permissions, 1, group.code, expandedIds, rows)
    }
  }
  return rows
}
```

> **🤔 导师提问**：`flattenPermissions` 函数是递归的，用 `expandedIds` 控制是否展开子节点。在 ASP.NET Core 中，如果你用 EF Core 的 `.Include()` 加载树形数据，数据库会一次查出所有层级。而前端这里的"懒展开"——只展开用户点击的节点——有什么好处？如果权限树有 5 层、每层 20 个节点，一次性全部扁平化 vs 按需展开，性能差距在哪里？

## 五、权限管理页面实现

### 5.1 应用选择器 + 权限树表格

页面顶部有应用选择器（Select），切换应用后重新加载权限数据。权限树用 AgTable 展示，行按 `depth` 缩进：

```typescript
export default function PermissionsPage() {
  const [apps, setApps] = useState<AppDto[]>([])
  const [selectedAppCode, setSelectedAppCode] = useState<string>("")
  const [groups, setGroups] = useState<PermissionGroupDto[]>([])
  const [loadingGroups, setLoadingGroups] = useState(false)
  const [expandedIds, setExpandedIds] = useState<Set<string>>(new Set())
  const [togglingId, setTogglingId] = useState<string | null>(null)

  // 对话框状态
  const [groupDialog, setGroupDialog] = useState<{
    open: boolean; editing: PermissionGroupDto | null
  }>({ open: false, editing: null })
  const [defDialog, setDefDialog] = useState<{
    open: boolean; editing: PermissionDefinitionDto | null; defaultGroupCode?: string
  }>({ open: false, editing: null })
  const [deleteGroupTarget, setDeleteGroupTarget] = useState<PermissionGroupDto | null>(null)
  const [deleteDefTarget, setDeleteDefTarget] = useState<PermissionDefinitionDto | null>(null)

  // 加载应用列表
  useEffect(() => {
    appsApi.getList().then((res) => {
      const list = res.data ?? []
      setApps(list)
      if (list[0]) setSelectedAppCode(list[0].code)
    }).catch(() => toast.error("获取应用列表失败"))
  }, [])

  // 加载当前应用下的权限定义
  const fetchGroups = useCallback(async () => {
    if (!selectedAppCode) return
    setLoadingGroups(true)
    try {
      const res = await permissionsApi.getAllDefinitions(selectedAppCode)
      const data = res.data ?? []
      setGroups(data)
      setExpandedIds(new Set(data.map((g) => g.id)))  // 默认展开所有权限组
    } catch {
      toast.error("获取权限定义失败")
    } finally {
      setLoadingGroups(false)
    }
  }, [selectedAppCode])

  useEffect(() => { fetchGroups() }, [fetchGroups])
  // ...
}
```

### 5.2 名称列的树形渲染

> **🤔 导师提问**：名称列的 `cellRenderer` 中用 `style={{ paddingLeft: `${8 + row.depth * 20}px` }}` 来实现缩进。这种"动态计算 padding"的方案，和 ASP.NET Core Razor 中的 `@for` 循环输出 `<span style="margin-left:@(depth*20)px">` 本质一样。但前端的树形渲染更复杂——还需要展开/折叠按钮、类型图标、统计 Badge。如果让你用 C# 写一个递归方法生成这种 HTML，你会怎么组织代码？对比 React 组件的写法，哪个更容易维护？

名称列是权限树的核心展示——带缩进、展开按钮、类型图标和代码标签：


## 六、权限定义表单对话框

### 6.1 创建权限定义

```typescript
// src/pages/perm/permissions/definition-form-dialog.tsx
export function DefinitionFormDialog({
  open, onOpenChange, appCode, groups, defaultGroupCode, editing, onSuccess,
}: DefinitionFormDialogProps) {
  const isEdit = !!editing
  const [form, setForm] = useState({
    groupCode: "",
    name: "",
    displayName: "",
    type: "0",         // 默认操作权限
    isEnabled: true,
    sort: 1,
  })

  useEffect(() => {
    if (!open) return
    if (editing) {
      // 编辑模式：从 groups 中找到包含该权限的组
      const ownerGroup = groups.find((g) =>
        g.permissions.some((p) => p.id === editing.id)
      )
      setForm({
        groupCode: ownerGroup?.code ?? "",
        name: editing.name,
        displayName: editing.displayName,
        type: String(editing.type),
        isEnabled: editing.isEnabled,
        sort: editing.sort,
      })
    } else {
      setForm({
        groupCode: defaultGroupCode ?? groups[0]?.code ?? "",
        name: "",
        displayName: "",
        type: "0",
        isEnabled: true,
        sort: 1,
      })
    }
  }, [open])

  const handleSubmit = async (e: React.FormEvent) => {
    e.preventDefault()
    // ... 验证逻辑
    if (isEdit) {
      await permissionsApi.updateDefinition(editing!.id, {
        displayName: form.displayName,
        type: parseInt(form.type),
        isEnabled: form.isEnabled,
        sort: form.sort,
      })
    } else {
      await permissionsApi.createDefinition({
        groupCode: form.groupCode,
        appCode,
        name: form.name,
        displayName: form.displayName,
        type: parseInt(form.type),
        sort: form.sort,
      })
    }
    onSuccess()
    onOpenChange(false)
  }
  // ... 渲染
}
```

### 6.2 创建 vs 编辑的关键差异

| 字段 | 创建模式 | 编辑模式 |
|------|---------|---------|
| groupCode | 可选择（Select） | 只读（不可移动到其他组） |
| name | 必填，可输入 | 只读（名称创建后不可改） |
| displayName | 必填，可输入 | 可修改 |
| type | 可选择 | 可修改 |
| isEnabled | 不显示（默认启用） | 显示 Switch |
| sort | 默认 1 | 可修改 |

## 七、删除的约束条件

### 7.1 删除权限组

权限组下如果还有权限定义，**不能删除**：

> "确定删除权限组「采购管理」？若组内仍有权限点则无法删除。"

### 7.2 删除权限定义

权限定义如果已被授予给用户或角色，**不能删除**：

> "确定删除权限「审批采购单」（Purchase.Approve）？已被授予给用户/角色的权限无法删除。"

💡 **ASP.NET Core 类比**：这就像你不能删除一个正在被 `[Authorize]` 引用的 Policy。删除前必须先移除所有引用。

> **🤔 导师提问**：权限组下有权限定义时不能删除，权限定义被角色引用时也不能删除。这和数据库的外键约束（`ON DELETE RESTRICT`）逻辑一致。但在前端，删除前你并不知道后端会不会拒绝——你是先调 API 看结果，还是先在前端检查？两种策略各有什么利弊？提示：想想"先检查再删除"是否存在 TOCTOU（Time of Check to Time of Use）问题。

---

## 踩坑提醒

1. **权限组下有定义时不能删除**：后端会拒绝删除包含权限定义的权限组。前端删除确认对话框的描述文案要提示"若组内仍有权限点则无法删除"，但最终以 API 返回结果为准，不能仅依赖前端判断。
2. **权限定义被角色引用时不能删除**：已被授予给用户或角色的权限定义同样无法删除。这是后端的外键约束逻辑，前端只能捕获错误并展示提示。
3. **树形数据不能直接传给 AgTable**：`AgTable` 需要扁平行数据，如果把嵌套的树形 JSON 直接传给 `AgTable`，只有顶层节点会被渲染，子节点全部丢失。必须先通过 `flattenTree` 函数扁平化。
4. **启用/禁用切换后必须刷新**：`handleTogglePerm` 调用 API 成功后会 `await fetchGroups()` 重新从后端拉取数据。不能直接在本地反转 `isEnabled` 状态，因为后端可能有额外的业务校验逻辑。
