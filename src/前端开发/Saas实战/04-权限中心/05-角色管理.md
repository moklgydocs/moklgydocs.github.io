# 05 - 角色管理

> **这一步解决什么问题？** 角色是 RBAC 模型中连接"用户"和"权限"的桥梁。就像 ASP.NET Core 里 `[Authorize(Roles = "Manager")]` 中的角色名，权限中心的角色也是一个命名的权限集合。但权限中心的角色比 ASP.NET Core 内置角色更灵活——每个角色属于一个应用，可以设为公开或私有，还能按权限组勾选权限。我们要实现角色的创建和权限分配功能。

---

## 一、ASP.NET Core 类比：角色 = 权限集合

在 ASP.NET Core 内置角色系统里：

```csharp
// ASP.NET Core: 简单的角色检查
[Authorize(Roles = "Manager")]
public class PurchaseController { ... }
```

这种方式把角色硬编码在代码里，而且角色是全局的。权限中心的角色则更灵活：

```
ASP.NET Core 内置角色系统         →    权限中心角色系统
─────────────────────────        →    ──────────────────
角色是全局的（跨所有 Controller）  →    角色属于特定应用（按 appCode 隔离）
角色 = 字符串名称                →    角色 = 有 code + name + 属性的实体
角色只有名称                     →    角色有公开/私有、启用/禁用属性
角色在代码中硬编码               →    角色在数据库中动态管理
角色直接用于 [Authorize]         →    角色关联权限列表，鉴权基于权限而非角色
```

## 二、角色数据模型

```typescript
// src/types/index.ts
export interface RoleDto {
  id: string
  appId: string          // 所属应用 ID
  code: string           // 角色代码，如 "manager"
  name: string           // 显示名称，如 "采购经理"
  description: string | null
  isDefault: boolean     // 是否默认角色（新用户自动分配）
  isStatic: boolean      // 是否静态角色（系统内置，不可删除）
  isPublic: boolean      // 是否公开角色（可分配给任意用户）
  isEnabled: boolean     // 是否启用
  sort: number
}

export interface CreateRoleRequest {
  appCode: string        // 所属应用代码
  code: string           // 角色代码
  name: string
  description?: string
  isPublic: boolean
  sort: number
}

export interface SetRolePermissionsRequest {
  permissions: string[]  // 权限名称列表（全量覆盖）
}
```

### 2.1 角色的四个布尔属性

| 属性 | 含义 | 示例 |
|------|------|------|
| `isDefault` | 新用户自动获得此角色 | "普通员工"角色 |
| `isStatic` | 系统内置，不可删除 | "admin"超级管理员 |
| `isPublic` | 可分配给任意用户 | "查看者"角色 |
| `isEnabled` | 当前是否生效 | 临时停用的角色 |

💡 **ASP.NET Core 类比**：`isStatic` 类似 `SeedingData` 里的初始角色——部署时创建，运行时不可删除。`isDefault` 类似注册时自动添加到 `AspNetUserRoles` 表。

> **🤔 导师提问**：角色有四个布尔属性（`isDefault`、`isStatic`、`isPublic`、`isEnabled`）。在 ASP.NET Core Identity 的 `IdentityRole` 中，你见过这么多属性吗？Identity 的角色本质上只是一个 `Name` 字符串。为什么权限中心需要这么多属性？试着说出 `isPublic: false` 的角色在什么场景下有意义——提示：想想"部门经理"这种只应在本部门用户间分配的角色。

```typescript
// src/pages/perm/roles/role-form-dialog.tsx
export function RoleFormDialog({ open, onOpenChange, appCode, onSuccess }: RoleFormDialogProps) {
  const [loading, setLoading] = useState(false)
  const [form, setForm] = useState({
    code: "", name: "", description: "", isPublic: true, sort: 1,
  })

  useEffect(() => {
    if (open) setForm({ code: "", name: "", description: "", isPublic: true, sort: 1 })
  }, [open])

  const handleSubmit = async (e: React.FormEvent) => {
    e.preventDefault()
    if (!form.code || !form.name) {
      toast.error("角色代码和名称不能为空")
      return
    }
    setLoading(true)
    try {
      await permRolesApi.create({
        appCode,
        code: form.code,
        name: form.name,
        description: form.description,
        isPublic: form.isPublic,
        sort: form.sort,
      })
      toast.success("角色已创建")
      onSuccess()
      onOpenChange(false)
    } catch {
      toast.error("创建失败")
    } finally {
      setLoading(false)
    }
  }

  return (
    <Dialog open={open} onOpenChange={onOpenChange}>
      <DialogContent className="sm:max-w-md">
        <DialogHeader>
          <DialogTitle>新建角色</DialogTitle>
        </DialogHeader>
        <form onSubmit={handleSubmit} className="space-y-4 py-2">
          <div className="space-y-2">
            <Label>应用</Label>
            <Input value={appCode} disabled />
          </div>
          <div className="space-y-2">
            <Label htmlFor="roleCode">角色代码 *</Label>
            <Input id="roleCode" placeholder="如: manager"

              onChange={(e) => setForm({ ...form, code: e.target.value })} />
```

## 五、角色权限分配对话框

这是角色管理的核心功能——给角色勾选权限。

### 5.1 数据加载：两个并行请求

对话框打开时，需要同时获取：
1. 当前应用的权限定义（用于展示勾选列表）
2. 当前角色已有的权限列表（用于回填勾选状态）

```typescript
// src/pages/perm/roles/role-permission-dialog.tsx
useEffect(() => {
  if (!open || !role) return
  setLoading(true)

  Promise.all([
    permissionsApi.getDefinitions(appCode),  // 权限定义（不含禁用的）
    permRolesApi.getPermissions(role.id),     // 角色已有权限
  ])
    .then(([defsRes, permsRes]) => {
      setGroups(defsRes.data ?? [])
      setSelected(new Set(permsRes.data ?? []))
    })
    .catch(() => toast.error("加载权限数据失败"))
    .finally(() => setLoading(false))
}, [open, role, appCode])
```

💡 **ASP.NET Core 类比**：这就像你打开一个角色编辑页面，先查出所有可用的 Policy 列表，再查出该角色已关联的 Policy，最后把已关联的打勾。

> **🤔 导师提问**：权限分配对话框打开时，用 `Promise.all` 同时发起两个请求——获取权限定义和获取角色已有权限。在 ASP.NET Core 中，你会用 `Task.WhenAll` 做同样的事。为什么用并行而不是串行？如果两个请求都耗时 500ms，串行需要 1000ms，并行只需要 500ms。但并行有一个潜在问题：如果其中一个请求失败，`Promise.all` 会怎样？应该用 `Promise.allSettled` 吗？

### 5.3 全选/取消全选逻辑

> **🤔 导师提问**：`toggleGroup` 的逻辑是：如果当前组全部选中则取消全选，否则全选。这意味着"部分选中"时点击组标题，行为是"全选"而非"取消全选"。在 ASP.NET Core 的 CheckBox 列表中，`indeterminate`（半选）状态通常只影响视觉，不影响点击行为。你觉得"部分选中时点击=全选"这个交互合理吗？如果改为"部分选中时点击=取消全选"，哪个更不容易误操作？

```typescript
/** 切换整个权限组的全选/取消全选 */
const toggleGroup = (group: PermissionGroupDto) => {
  const groupPerms = group.permissions.map((p) => p.name)
  const allChecked = groupPerms.every((p) => selected.has(p))
  setSelected((prev) => {
    const next = new Set(prev)
    if (allChecked) {
      // 全部取消
      groupPerms.forEach((p) => next.delete(p))
    } else {
      // 全部勾选
      groupPerms.forEach((p) => next.add(p))
    }
    return next
  })
}
```

### 5.4 保存权限（全量覆盖）

```typescript
const handleSave = async () => {
  if (!role) return
  setSaving(true)
  try {
    await permRolesApi.setPermissions(role.id, {
      permissions: Array.from(selected),  // Set → Array
    })
    toast.success("权限已保存")
    onOpenChange(false)
  } catch {
    toast.error("保存失败")
  } finally {
    setSaving(false)
  }
}
```

⚠️ **注意：这是"全量覆盖"而非"增量更新"**。每次保存时，把角色当前应有的所有权限编码发送给后端，后端先清除旧权限，再写入新权限。

💡 **ASP.NET Core 类比**：这就像 `RoleManager.UpdateAsync()` 时替换了角色的 Claim 列表，而不是逐个添加/删除。

> **🤔 导师提问**：`handleSave` 中 `Array.from(selected)` 把 `Set` 转为数组传给后端。这是"全量覆盖"策略——每次保存，发送角色应有的全部权限列表。在 ASP.NET Core 中，你更习惯用 `AddClaim` / `RemoveClaim` 做增量更新。全量覆盖的一个关键优势是"幂等性"——同样请求执行多次结果一样。增量更新有这个特性吗？两个管理员同时操作同一角色的权限时，哪种策略更安全？
