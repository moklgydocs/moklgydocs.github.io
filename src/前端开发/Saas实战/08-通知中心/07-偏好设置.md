# 07 - 通知偏好设置：卡片式开关管理

> **这一步解决什么问题？**
> 用户可能不想接收短信通知（省钱），或者不想接收邮件通知（太吵）。偏好设置页面让用户自己控制每个渠道的开关。紧急通知不受偏好影响——服务端会强制发送。
>
> **ASP.NET Core 类比**：偏好设置 ≈ `UserNotificationPreferences` 表的 CRUD。后端有 `GetPreferences` 和 `UpdatePreferences` 接口，前端只是把数据库里的开关用卡片展示出来。

## 二、完整代码

```typescript
import { useState, useEffect } from "react"
import { toast } from "sonner"
import { Save, RefreshCw } from "lucide-react"
import { AnimatedPage } from "@/components/shared/animated-page"
import { PageHeader } from "@/components/shared/page-header"
import { PageToolbar, ToolbarButton } from "@/components/shared/page-toolbar"
import { Switch } from "@/components/ui/switch"
import { Card, CardContent, CardDescription, CardHeader, CardTitle } from "@/components/ui/card"
import { getPreferences, updatePreferences } from "@/api/notify/preferences"
import { NotificationChannel } from "@/types/notification"
import type { PreferenceDto, UpdatePreferenceRequest } from "@/types/notification"

// ── 渠道配置 ──
const channelConfig = [
  {
    channel: NotificationChannel.InApp,
    label: "站内信",
    description: "通过 SignalR 实时推送到浏览器，并在通知铃铛中显示",
    icon: "🔔",
  },
  {
    channel: NotificationChannel.Email,
    label: "邮件通知",
    description: "发送邮件到您的注册邮箱",
    icon: "📧",
  },
  {
    channel: NotificationChannel.Sms,
    label: "短信通知",
    description: "发送短信到您的手机号（可能产生费用）",
    icon: "📱",
  },
  {
    channel: NotificationChannel.WeChatTemplate,
    label: "微信消息",
    description: "通过微信公众号/小程序推送消息（即将上线）",
    icon: "💬",
    disabled: true,
  },
  {
    channel: NotificationChannel.MobilePush,
    label: "移动推送",
    description: "通过 APP 推送通知到手机（即将上线）",
    icon: "📲",
    disabled: true,
  },
]

/**
 * 通知偏好设置页面
 * 管理各通知渠道（站内信、邮件、短信、微信、移动推送）的接收开关。
 * 紧急通知会忽略偏好设置强制发送。
 */
export default function NotificationPreferencesPage() {
  const [preferences, setPreferences] = useState<Map<string, boolean>>(new Map())
  const [loading, setLoading] = useState(false)
  const [saving, setSaving] = useState(false)

  const fetchPreferences = async () => {
    setLoading(true)
    try {
      const res = await getPreferences()
      const prefs = res.data ?? []
      // 只取全局偏好（templateCode 为空）
      const map = new Map<string, boolean>()
      prefs
        .filter((p: PreferenceDto) => !p.templateCode)
        .forEach((p: PreferenceDto) => map.set(p.channel, p.isEnabled))
      setPreferences(map)
    } catch {
      toast.error("获取偏好设置失败")
    } finally {
      setLoading(false)
    }
  }

  useEffect(() => { fetchPreferences() }, [])

  const toggleChannel = (channel: string) => {
    setPreferences((prev) => {
      const next = new Map(prev)
      const current = next.get(channel) ?? true // 默认开启
      next.set(channel, !current)
      return next
    })
  }

  const handleSave = async () => {
    setSaving(true)
    try {
      const updates: UpdatePreferenceRequest[] = channelConfig
        .filter((c) => !c.disabled)
        .map((c) => ({
          channel: c.channel,
          isEnabled: preferences.get(c.channel) ?? true,
        }))
      await updatePreferences(updates)
      toast.success("偏好设置已保存")
    } catch {
      toast.error("保存失败")
    } finally {
      setSaving(false)
    }
  }

  return (
    <AnimatedPage className="flex flex-col h-full">
      <div className="p-4 pb-0 space-y-4">
        <PageHeader title="通知偏好" description="管理各通知渠道的接收设置，紧急通知会忽略此设置强制发送" />
      </div>

      <PageToolbar
        actions={
          <>
            <ToolbarButton icon={Save} variant="primary" onClick={handleSave} disabled={saving}>
              {saving ? "保存中..." : "保存设置"}
            </ToolbarButton>
            <ToolbarButton icon={RefreshCw} onClick={fetchPreferences}>刷新</ToolbarButton>
          </>
        }
      />

      <div className="p-4 space-y-4 overflow-auto flex-1">
        {loading ? (
          <div className="text-center text-muted-foreground py-12">加载中...</div>
        ) : (
          <div className="grid gap-4 md:grid-cols-2 lg:grid-cols-3">
            {channelConfig.map((cfg) => {
              const isEnabled = preferences.get(cfg.channel) ?? true
              return (
                <Card key={cfg.channel} className={cfg.disabled ? "opacity-50" : ""}>
                  <CardHeader className="pb-3">
                    <div className="flex items-center justify-between">
                      <div className="flex items-center gap-2">
                        <span className="text-xl">{cfg.icon}</span>
                        <CardTitle className="text-base">{cfg.label}</CardTitle>
                      </div>
                      <Switch
                        checked={isEnabled}
                        onCheckedChange={() => toggleChannel(cfg.channel)}
                        disabled={cfg.disabled}
                      />
                    </div>
                  </CardHeader>
                  <CardContent>
                    <CardDescription>{cfg.description}</CardDescription>
                    {cfg.disabled && (
                      <p className="text-xs text-amber-600 mt-2">此渠道尚未实现，将在后续版本中上线</p>
                    )}
                  </CardContent>
                </Card>
              )
            })}
          </div>
        )}
      </div>
    </AnimatedPage>
  )
}
```

💡 **数据驱动的 UI 渲染模式**：

```
channelConfig (数据)
     │
     │ .map(cfg => <Card .../>)
     ▼
┌──────────────────────────────────────────────────┐
│ 配置项 → UI 组件的映射                             │
│                                                   │
│ channel     → key (React 列表渲染)                │
│ icon        → <span>{cfg.icon}</span>            │
│ label       → <CardTitle>{cfg.label}</CardTitle> │
│ description → <CardDescription>{cfg.description}</CardDescription>│
│ disabled    → className="opacity-50" + Switch disabled│
└──────────────────────────────────────────────────┘
```

⚠️ **【设计取舍】为什么不用后端返回渠道列表？**
因为 UI 展示的 `icon`、`label`、`description` 是前端展示逻辑，后端不关心用铃铛还是信封图标。`channelConfig` 是前端专属的展示配置。

⚠️ **【易错点】`disabled: true` 的渠道**
微信和移动推送标注了 `disabled: true`，表示"尚未实现"。UI 效果是：
1. 卡片半透明（`opacity-50`）
2. Switch 不可点击（`disabled={cfg.disabled}`）
3. 显示"此渠道尚未实现"的黄色提示

这是**功能预告**的常见 UI 模式——让用户知道未来会有这个功能，但当前不可用。

## 四、偏好状态：Map<channel, isEnabled>

```typescript
const [preferences, setPreferences] = useState<Map<string, boolean>>(new Map())
```

> **🤔 导师提问**：偏好状态用 `Map<string, boolean>` 存储，key 是渠道名（如 `"inApp"`），value 是开关状态。在 ASP.NET Core 后端，`PreferenceDto` 有 `id`、`channel`、`isEnabled`、`templateCode` 四个字段，但前端只用了 `channel` 和 `isEnabled`。为什么前端不需要 `id`？想想提交更新时后端怎么识别要更新哪条记录——是靠 `id` 还是靠 `channel`？

### 4.1 数据加载

```typescript
const fetchPreferences = async () => {
  setLoading(true)
  try {
    const res = await getPreferences()
    const prefs = res.data ?? []
    // 只取全局偏好（templateCode 为空）
    const map = new Map<string, boolean>()
    prefs
      .filter((p: PreferenceDto) => !p.templateCode)
      .forEach((p: PreferenceDto) => map.set(p.channel, p.isEnabled))
    setPreferences(map)
  } catch {
    toast.error("获取偏好设置失败")
  } finally {
    setLoading(false)
  }
}
```

逐行精讲：

| 标记 | 代码 | 解读 |
|------|------|------|
| **【设计取舍】** | `.filter((p) => !p.templateCode)` | 只取**全局偏好**（`templateCode` 为空的），忽略模板级偏好。当前 UI 只管理全局开关，不支持"某个模板单独关通知" |
| **【易错点】** | `map.set(p.channel, p.isEnabled)` | Map 的 key 是渠道字符串（如 `"inApp"`），value 是布尔开关。如果后端没返回某个渠道的偏好，Map 里就没有这个 key |

> **🤔 导师提问**：`fetchPreferences` 中 `.filter(!p.templateCode)` 只取全局偏好。这意味着如果后端有模板级偏好（`templateCode` 不为空），它们会被完全忽略。当前 UI 不支持"某个模板单独关通知"，但如果产品要求加上这个功能，你需要改哪些地方？对比 ASP.NET Core 中从"全局配置"扩展到"按实体配置"的经验。

### 4.2 切换开关

```typescript
const toggleChannel = (channel: string) => {
  setPreferences((prev) => {
    const next = new Map(prev)
    const current = next.get(channel) ?? true // 默认开启
    next.set(channel, !current)
    return next
  })
}
```

⚠️ **【易错点】`?? true` 默认值**
如果 Map 中没有某个渠道的 key（比如新用户后端还没创建偏好记录），`next.get(channel)` 返回 `undefined`。`?? true` 表示默认开启——新用户应该默认收到所有通知。

⚠️ **【易错点】`new Map(prev)` 创建新 Map**
和数组一样，React 状态更新要求不可变数据。直接修改 `prev` 的 Map 不会触发重渲染：

```typescript
// ❌ 错误：直接修改 Map
prev.set(channel, !current)
return prev  // React 检测不到变化！

// ✅ 正确：创建新 Map
const next = new Map(prev)
next.set(channel, !current)
return next  // 新引用 → React 检测到变化 → 重渲染
```

### 4.3 保存偏好

```typescript
const handleSave = async () => {

  try {

    toast.success("偏好设置已保存")
  } catch {
    toast.error("保存失败")

```

逐行精讲：

| 标记 | 代码 | 解读 |
|------|------|------|
| **【设计取舍】** | `.filter((c) => !c.disabled)` | 不保存 disabled 渠道的偏好！因为微信和移动推送尚未实现，传给后端也没意义 |
| **【易错点】** | `preferences.get(c.channel) ?? true` | 和 toggleChannel 一样的默认值逻辑。用户没改过某个渠道 → Map 里没值 → 默认 true |
| **【设计取舍】** | 一次性批量保存 vs 逐个保存 | 当前是**一次性保存所有渠道**，一个 PUT 请求搞定。比每个 Switch 变化都发一次请求更高效 |

> **🤔 导师提问**：批量保存时 `channelConfig.filter(!c.disabled)` 排除了微信和移动推送。如果用户在页面上看到 5 张卡片，但保存时只提交了 3 个渠道的偏好——这合理吗？对比 ASP.NET Core 中"未实现的功能不应该出现在 UI 上"vs"显示但置灰让用户知道未来会有"两种设计哲学，你倾向哪种？

> **🤔 导师提问**：当前 `toggleChannel` 只修改本地 Map，不调 API，等到用户点"保存设置"才批量提交。如果用户切换了开关但没保存就关闭页面，修改就丢了。在 ASP.NET Core 中，表单的"未保存提示"通常怎么实现？前端的 `beforeunload` 事件你能用起来吗？

## 六、Map vs Object：状态存储的选择

```
┌────────────────┬─────────────────────────┬─────────────────────────┐
│ 维度            │ Map<string, boolean>     │ Record<string, boolean> │
├────────────────┼─────────────────────────┼─────────────────────────┤
│ 创建新实例      │ new Map(prev) ✅         │ { ...prev } ✅          │
│ 获取值          │ map.get(key) ?? default  │ obj[key] ?? default     │
│ 设置值          │ map.set(key, value)      │ { ...obj, [key]: val }  │
│ 判断存在        │ map.has(key)             │ key in obj              │
│ 遍历           │ map.forEach()            │ Object.entries()        │
│ 序列化(JSON)   │ ❌ 不支持直接序列化       │ ✅ 天然支持              │
│ 性能(大量key)   │ ✅ O(1) 查找             │ ✅ O(1) 查找             │
│ key类型         │ 任意类型                 │ 只能 string/Symbol       │
└────────────────┴─────────────────────────┴─────────────────────────┘
```

⚠️ **【设计取舍】为什么用 Map？**
5 个渠道的数量级下，Map 和 Object 性能差异可以忽略。但 Map 的语义更清晰——"从渠道名到开关状态的映射"。`new Map(prev)` 创建副本比 `{...prev}` 更明确表达"创建新引用"的意图。

如果用 Object，toggle 代码是：
```typescript
setPreferences(prev => ({ ...prev, [channel]: !(prev[channel] ?? true) }))
```
Map 版本：
```typescript
setPreferences(prev => { const next = new Map(prev); next.set(channel, !(next.get(channel) ?? true)); return next })
```
Object 版本更简洁，但 Map 版本更具可读性（显式的 get/set 操作）。

## 七、数据流：加载 → 展示 → 修改 → 保存

```
┌──────────────────────────────────────────────────────────────┐
│  偏好设置数据流                                               │
│                                                              │
│  ① 加载                                                      │
│  getPreferences() ──→ PreferenceDto[]                        │
│    │                                                          │
│    ├─ .filter(!templateCode) ──→ 只保留全局偏好               │
│    └─ .forEach → Map.set(channel, isEnabled)                 │
│                                                              │
│  ② 展示                                                      │
│  channelConfig.map(cfg => {                                  │
│    isEnabled = preferences.get(cfg.channel) ?? true           │
│    return <Card><Switch checked={isEnabled} .../></Card>     │
│  })                                                          │
│                                                              │
│  ③ 修改（纯本地）                                             │
│  toggleChannel(channel) ──→ Map.set(channel, !current)       │
│  ⚠️ 不发 API！等用户点"保存设置"                              │
│                                                              │
│  ④ 保存                                                      │
│  handleSave() ──→ channelConfig.filter(!disabled)            │
│    │  .map(c => ({ channel, isEnabled: preferences.get() })) │
│    └─ updatePreferences(updates) ──→ PUT /api/notification-preferences │
└──────────────────────────────────────────────────────────────┘
```

⚠️ **【设计取舍】批量保存 vs 即时保存**
当前是批量保存：用户可以同时切换多个开关，最后一次性提交。

另一种方案是**即时保存**：每次 Switch 变化都调 API。

```
批量保存：                          即时保存：
切换开关 → 本地状态更新             切换开关 → 调 API → 成功 → 本地状态更新
切换开关 → 本地状态更新             切换开关 → 调 API → 成功 → 本地状态更新
...                                 ...
点击保存 → 一次 API 请求            (无需保存按钮)
```

AdminWeb 选择批量保存的原因：
1. 减少 API 请求次数（5 个渠道只需 1 次 vs 最多 5 次）
2. 用户可以"改了又改回来"而不触发无意义的 API 调用
3. 提供明确的"保存"操作，用户有掌控感
