# 01 - 实时通信基础：从 HTTP 到 WebSocket 的进化

> **这一步解决什么问题？**
> 用户在 SaaS 系统里提交了一个报表渲染任务，怎么让 Ta 知道任务完成了？用 HTTP 轮询？太浪费。发邮件？太慢。我们需要一种**服务端主动推消息到浏览器**的机制——这就是实时通信。
>
> **ASP.NET Core 开发者的直觉**：你在后端用过 SignalR Hub，写过 `Clients.All.SendAsync("ReceiveNotification", ...)`。但前端怎么接收这个推送？这就是我们今天要搞清楚的事。

---

## 一、三种实时通信方案对比

在浏览器里实现"服务端推消息"，我们有三种主流方案：

```
┌──────────────────────────────────────────────────────────────────────┐
│                    实时通信方案对比                                    │
├──────────┬──────────────────┬──────────────────┬─────────────────────┤
│ 维度      │ 短轮询 Polling    │ SSE              │ WebSocket           │
├──────────┼──────────────────┼──────────────────┼─────────────────────┤
│ 方向      │ 客户端 → 服务端    │ 服务端 → 客户端   │ 双向                │
│ 连接      │ 每次请求新建       │ 长连接 HTTP/1.1   │ 长连接 TCP 升级      │
│ 延迟      │ 高（取决于间隔）    │ 低                │ 极低                │
│ 开销      │ 每次带 HTTP 头     │ 一次 HTTP 头      │ 握手后无 HTTP 头     │
│ 断线恢复  │ 天然支持           │ 内置 Last-Event-ID│ 需自行实现重连        │
│ 二进制    │ 支持              │ 仅文本            │ 支持                │
│ 典型场景  │ 兼容性兜底         │ 单向推送(股票行情) │ 聊天/协作/通知       │
└──────────┴──────────────────┴──────────────────┴─────────────────────┘
```

⚠️ **为什么 AdminWeb 选 SignalR（WebSocket）而不是 SSE？**
因为通知中心不只是"收消息"，还需要**客户端→服务端**的调用（比如 Ping 心跳）。WebSocket 天然双向，而 SSE 只能单向推送。

> **讲师提问**：如果我们的通知中心只需要"服务端推消息给浏览器"，不需要浏览器主动调用服务端方法，选 SSE 还是 WebSocket？为什么？
>
> <details><summary>参考答案</summary>如果只需要单向推送，SSE 更简单：原生浏览器支持（EventSource API）、自动重连、自带 Last-Event-ID 断线续传。WebSocket 的优势在于双向通信，单向场景下是"杀鸡用牛刀"。但 AdminWeb 选 SignalR 是因为 SignalR 自动协商传输方式（优先 WebSocket，降级 SSE，再降级 Long Polling），比原生 SSE 更健壮。</details>

## 二、SignalR 是什么？ASP.NET Core 开发者的理解捷径

SignalR 是微软推出的实时通信库，你大概率在后端已经用过它。关键映射：

```
ASP.NET Core 后端                          React 前端
──────────────────                         ──────────────────
[Hub] PlatformHub : Hub                    platformHub 对象
  ├─ OnAsync("ReceiveNotification")  ←──→   platformHub.on("ReceiveNotification", cb)
  └─ SendAsync("Ping")               ←──→   platformHub.invoke("Ping")

services.AddSignalR()                      @microsoft/signalr NPM 包
app.MapHub<PlatformHub>("/hubs/platform")  HubConnectionBuilder.withUrl("/hubs/platform")

IHubContext<Clients>                       connection 对象
```

**核心区别**：后端的 Hub 是一个**类**，前端的 HubConnection 是一个**客户端实例**。后端你用 `[HubMethodName]` 标注方法，前端你用字符串 `"ReceiveNotification"` 匹配方法名。

⚠️ **【易错点】SignalR 的 negotiate 请求**
SignalR 在建立 WebSocket 连接之前，会先发一个 HTTP POST 请求到 `/hubs/platform/negotiate`。这个请求用来协商传输方式（WebSocket / SSE / Long Polling）。如果 negotiate 请求失败（比如 401、CORS 错误），WebSocket 连接根本不会建立。新手经常只盯着 WebSocket 报错，忽略了 negotiate 请求才是真正的失败原因。

> **讲师提问**：在浏览器开发者工具的 Network 面板中，你应该先检查哪个请求来判断 SignalR 连接问题？
>
> <details><summary>参考答案</summary>先找 `negotiate` 请求。如果它返回 401，说明 Token 有问题；如果返回 404，说明 Hub 端点路径不对或代理没配好；如果返回 CORS 错误，说明后端没配置 SignalR 的跨域策略。只有 negotiate 成功后，才会出现 WebSocket 连接请求。</details>

## 三、AdminWeb 的 SignalR 配置全貌

让我们看 `signalr.ts` 的核心配置，这是整个通知中心的基石。

### 3.1 Hub URL 与 Vite 代理

```typescript
/** Hub 端点路径（通过 Vite proxy 转发到 NotificationCenter 服务） */
const HUB_URL = "/hubs/platform"
```

💡 **为什么是 `/hubs/platform` 而不是 `ws://localhost:10012/hubs/platform`？**
因为在开发环境中，前端跑在 `localhost:5173`，后端跑在 `localhost:10012`。跨域的 WebSocket 连接需要 Vite 代理。

Vite 配置中需要开启 `ws: true`（WebSocket 代理）：

```
vite.config.ts 中的代理配置（关键片段）：

┌──────────────────────────────────────────────┐
│  '/hubs/platform': {                         │
│    target: 'http://localhost:10012',          │
│    ws: true  ← 这个是关键！开启 WebSocket 代理 │
│  }                                           │
└──────────────────────────────────────────────┘

请求流：
浏览器 ──ws://localhost:5173/hubs/platform──→ Vite Proxy ──ws://localhost:10012/hubs/platform──→ 后端 Hub
```

⚠️ **【易错点】** 如果你忘记配 `ws: true`，Vite 只会代理 HTTP 请求，WebSocket 握手会直接 404。症状是浏览器控制台报 `WebSocket connection to 'ws://localhost:5173/hubs/platform' failed`。

### 3.2 断线重连策略

```typescript
/** 断线重连延迟策略（毫秒）。重试 5 次后放弃，需手动重连。 */
const RECONNECT_DELAYS = [0, 2000, 5000, 10000, 30000]
```

这是一个**递增延迟**策略：

```
断线时刻
  │
  ├─ 0ms    → 第1次重连（立即尝试，可能只是网络抖动）
  ├─ 2s     → 第2次重连
  ├─ 5s     → 第3次重连
  ├─ 10s    → 第4次重连
  └─ 30s    → 第5次重连（仍失败则放弃，需用户手动刷新）
```

💡 **为什么不是固定间隔？**
固定间隔（比如每 5 秒）的问题：如果服务端刚重启，大量客户端同时重连会造成**重连风暴**。递增延迟让客户端错开重连时间。

⚠️ **【设计取舍】** 5 次后放弃 vs 永远重试？
AdminWeb 选择 5 次后放弃，因为：1）持续重连浪费资源；2）用户可能主动断网；3）60 秒轮询兜底机制会接管。这是一个务实的工程决策。

⚠️ **【易错点】WebSocket 重连后的状态同步**
重连成功后，SignalR 会触发 `onreconnected` 回调，但**重连期间丢失的消息不会自动补发**。也就是说，如果断线 10 秒期间有 3 条通知推送，重连后你不会收到这 3 条。这就是为什么 AdminWeb 需要 60 秒轮询兜底——轮询会补齐断线期间的遗漏。

> **讲师提问**：SignalR 重连成功后 `onreconnected` 回调会传入一个新的 `connectionId`，这个 ID 和之前的一样吗？如果不一样，后端需要注意什么？
>
> <details><summary>参考答案</summary>可能不一样。如果 WebSocket 是"快速重连"（底层 TCP 连接没断），connectionId 不变；如果连接完全断开后重建，connectionId 会变。后端如果用 `connectionId` 做用户→连接的映射（比如在线用户列表），必须在 `OnReconnected` 回调中更新映射关系，否则映射过期会导致消息推送到错误的（或已失效的）连接。</details>

### 3.3 Token 认证

```typescript
connection = new signalR.HubConnectionBuilder()
  .withUrl(HUB_URL, {
    // 每次建立/重建 WebSocket 时，从 Zustand AuthStore 获取最新的 access_token
    accessTokenFactory: () => {
      const { accessToken } = useAuthStore.getState()
      return accessToken ?? ""
    },
  })
  .withAutomaticReconnect(RECONNECT_DELAYS)
  .configureLogging(signalR.LogLevel.Warning)
  .build()
```

逐行解析关键代码：

| 行 | 代码 | 为什么 |
|---|---|---|
| `accessTokenFactory` | `() => useAuthStore.getState().accessToken` | 【易错点】不用 `useAuthStore(state => state.accessToken)`，因为那是个 React Hook 写法，这里在非组件上下文中。`getState()` 是 Zustand 的**非 React**用法 |
| `withAutomaticReconnect` | `RECONNECT_DELAYS` | 传入延迟数组，SignalR 自动处理重连逻辑 |
| `configureLogging` | `LogLevel.Warning` | 【性能陷阱】开发时用 `LogLevel.Information` 便于调试，但生产环境应设 Warning，否则每个心跳都会打印日志 |

⚠️ **【易错点】accessTokenFactory 为什么是函数而不是固定值？**
Token 会过期刷新！如果写成 `accessToken: "xxx"`，刷新后的新 Token 不会被使用。写成 `factory` 函数，SignalR 每次建立/重建连接时都会调用它获取最新 Token。

## 四、连接状态生命周期

SignalR 连接有三种状态，我们用回调来追踪：

```typescript
// 断线后开始重连
connection.onreconnecting((_error) => {
  console.warn("[SignalR] 正在重连...")
  notifyStateListeners("reconnecting")
})

// 重连成功
connection.onreconnected((_connectionId) => {
  console.info("[SignalR] 重连成功")
  notifyStateListeners("connected")
})

// 连接关闭
connection.onclose((_error) => {
  console.info("[SignalR] 连接已关闭")
  notifyStateListeners("disconnected")
})
```

状态流转图：

```
                    startConnection()
  Disconnected ─────────────────────→ Connected
       ↑                                 │  │
       │                          onclose()  onreconnecting()
       │                                 │  │
       │                                 ↓  ↓
       └────────────────────────── Disconnected  Reconnecting
                                         ↑          │
                                         │   onreconnected()
                                         │          │
                                         └──────────↓
                                               Connected
```

💡 **ASP.NET Core 类比**：这和后端的 `IHubContext` 生命周期类似，但后端由 DI 容器管理，前端需要我们手动管理连接的启动和停止。

⚠️ **【易错点】并发消息处理**
SignalR 保证消息**按序到达**，但不保证 `on` 回调的执行是异步安全的。如果你的 `on` 回调里做了 `set((state) => ({ unreadCount: state.unreadCount + 1 }))`，这是安全的，因为 Zustand 的 `set` 用函数写法能保证基于最新 state 计算。但如果用 `set({ unreadCount: unreadCount + 1 })`（直接读闭包变量），多条消息快速到达时可能丢失计数。

```typescript
// ❌ 错误：快速收到多条通知时，unreadCount 可能只 +1（闭包捕获了旧值）
onNewNotification: (notification) => {
  set({ unreadCount: get().unreadCount + 1 })  // get() 是安全的
}

// ❌ 更危险：直接读 state 变量
onNewNotification: (notification) => {
  set({ unreadCount: unreadCount + 1 })  // 闭包捕获，多条消息只 +1
}

// ✅ 正确：函数式 set，基于最新 state
onNewNotification: (notification) => {
  set((state) => ({ unreadCount: state.unreadCount + 1 }))
}
```

## 五、启动与停止连接

```typescript
export async function startConnection(): Promise<void> {
  const conn = getOrCreateConnection()

  if (conn.state === signalR.HubConnectionState.Connected) {
    return // 已连接，无需重复启动
  }

  // 仅在断开状态下尝试启动（正在连接/重连中不干预）
  if (conn.state === signalR.HubConnectionState.Disconnected) {
    try {
      await conn.start()
      console.info("[SignalR] 连接成功")
      notifyStateListeners("connected")
    } catch (err) {
      console.error("[SignalR] 连接失败:", err)
      notifyStateListeners("disconnected")
    }
  }
}

export async function stopConnection(): Promise<void> {
  if (connection) {
    try {
      await connection.stop()
    } catch (err) {
      console.error("[SignalR] 断开失败:", err)
    }
    connection = null  // 清空实例，下次 startConnection 会重建
  }
}
```

逐行精讲：

| 标记 | 代码 | 解读 |
|------|------|------|
| **【易错点】** | `if (conn.state === Connected) return` | 必须检查状态！重复调用 `start()` 会抛异常 `Cannot start a connection that is not in the Disconnected state` |
| **【设计取舍】** | `if (conn.state === Disconnected)` | 不在 Connecting/Reconnecting 状态下调用 start()，因为这两种状态 SignalR 内部正在处理，强行介入会冲突 |
| **【易错点】** | `connection = null` | stop 后必须清空！否则下次 `getOrCreateConnection()` 会复用已停止的连接，导致 `start()` 抛异常 |

💡 **ASP.NET Core 类比**：
- `startConnection()` ≈ `app.MapHub<PlatformHub>("/hubs/platform")` —— 注册 Hub 端点
- `stopConnection()` ≈ 应用关闭时断开所有连接

> **讲师提问**：`startConnection()` 在 `conn.state` 为 `Connecting` 时直接跳过了，不做任何处理。如果用户在这个状态下连续点击"重连"按钮，会有什么问题？应该怎么改进？
>
> <details><summary>参考答案</summary>用户连续点击"重连"不会有副作用（因为 Connecting 状态被跳过），但也得不到任何反馈——看起来按钮没反应。改进方案：1）在 UI 层禁用按钮（connecting 状态时 disabled）；2）在 startConnection 中对 Connecting 状态返回一个特殊值或 Promise，让调用方知道"正在连接中"；3）用防抖（debounce）避免连续点击。</details>

## 六、组件思维：谁拥有连接状态？

在 AdminWeb 中，SignalR 的连接管理分为两层：

```
┌─────────────────────────────────────────────────────────────────┐
│  层级          文件                     职责                      │
├─────────────────────────────────────────────────────────────────┤
│  基础设施层    lib/signalr.ts          连接生命周期管理            │
│               ┌─────────────────┐     ├─ 创建/销毁 HubConnection │
│               │ startConnection │     ├─ 重连策略                 │
│               │ stopConnection  │     ├─ Token 获取               │
│               │ platformHub     │     └─ 状态通知机制             │
│               └─────────────────┘                                  │
│                                                                   │
│  业务逻辑层    stores/               通知业务逻辑                  │
│               notification-store.ts  ├─ 注册/注销 ReceiveNotif.   │
│               ┌─────────────────┐     ├─ 消息→NotificationDto    │
│               │ initSignalR     │     ├─ 未读数维护               │
│               │ disposeSignalR  │     └─ toast 弹出              │
│               │ onNewNotification│                                    │
│               └─────────────────┘                                  │
└─────────────────────────────────────────────────────────────────┘
```

**关键设计决策**：`signalr.ts` 不知道"通知"是什么，它只知道"连接"和"消息"。`notification-store.ts` 不知道"WebSocket"是什么，它只知道"有新通知来了"。这种**关注点分离**让两个模块可以独立变化——以后如果加一个"在线协作"功能，只需要在另一个 store 里注册新的 handler，不需要改动 `signalr.ts`。

⚠️ **【设计取舍】WebSocket vs SSE vs Long Polling —— SignalR 的自动协商**

SignalR 内置了**传输协商**机制，不需要我们手动选择：

```
SignalR negotiate 流程：

客户端发 POST /hubs/platform/negotiate
         │
         ▼
服务端返回支持的传输方式列表
         │
         ▼
客户端按优先级选择：
  1. WebSocket  ✅ 最优（双向、低延迟、无 HTTP 头开销）
  2. Server-Sent Events  ↓ 降级（单向、HTTP/1.1 长连接）
  3. Long Polling  ↓ 兜底（每次请求-响应，兼容性最好）
```

| 传输方式 | 延迟 | 开销 | 双向 | 兼容性 | SignalR 何时降级 |
|---------|------|------|------|--------|-----------------|
| WebSocket | 极低 | 极低 | 是 | 现代浏览器 | — |
| SSE | 低 | 低 | 否 | HTTP/1.1 | WebSocket 不可用（如代理不支持） |
| Long Polling | 高 | 高 | 是 | 所有 | SSE 不可用（如 HTTP/2 限制） |

💡 **为什么我们不手动选 WebSocket？** 因为在某些企业网络环境下，代理服务器可能不支持 WebSocket。SignalR 的自动协商让我们不用写 `if/else` 判断环境，它会自动降级到可用的传输方式。

## 七、platformHub 操作对象

```typescript
export const platformHub = {
  on: (method: string, callback: (...args: unknown[]) => void) => {
    getOrCreateConnection().on(method, callback)
  },

  off: (method: string, callback: (...args: unknown[]) => void) => {
    getOrCreateConnection().off(method, callback)
  },

  invoke: async (method: string, ...args: unknown[]): Promise<void> => {
    const conn = getOrCreateConnection()
    if (conn.state === signalR.HubConnectionState.Connected) {
      await conn.invoke(method, ...args)
    } else {
      console.warn(`[SignalR] 未连接，跳过调用 ${method}`)
    }
  },

  get state(): signalR.HubConnectionState {
    return connection?.state ?? signalR.HubConnectionState.Disconnected
  },
}
```

⚠️ **【易错点】`on` 和 `off` 必须传入同一个回调引用！**

```typescript
// ❌ 错误：off 无法移除 on 注册的回调（两个箭头函数是不同的引用）
platformHub.on("ReceiveNotification", (data) => { /* ... */ })
platformHub.off("ReceiveNotification", (data) => { /* ... */ })

// ✅ 正确：保存引用，用同一个引用 on 和 off
const handler = (data: unknown) => { /* ... */ }
platformHub.on("ReceiveNotification", handler)
platformHub.off("ReceiveNotification", handler)
```

AdminWeb 在 `notification-store.ts` 中就是这样做的：

```typescript
// notification-store.ts 中的 _handlerRef 模式
let _handlerRef: ((...args: unknown[]) => void) | null = null

initSignalR: () => {
  if (_handlerRef) return  // 防止重复注册

  const handler = (message: unknown) => { /* ... */ }
  _handlerRef = handler
  platformHub.on("ReceiveNotification", handler)
},

disposeSignalR: () => {
  if (_handlerRef) {
    platformHub.off("ReceiveNotification", _handlerRef)  // 用同一个引用 off
    _handlerRef = null
  }
},
```

⚠️ **【设计取舍】invoke 为什么在未连接时静默跳过？**
因为通知推送的语义是"通知你来拿消息"，而不是"你必须回复"。如果断线时 invoke 抛异常，会导致 UI 闪红色错误。静默跳过 + 轮询兜底是更稳健的策略。

> **讲师提问**：`platformHub.on()` 调用的是 `getOrCreateConnection().on()`，这意味着即使还没调用 `startConnection()`，`on` 也能注册成功。那消息什么时候才能被收到？
>
> <details><summary>参考答案</summary>`on` 只是注册回调，不会触发连接。回调被存在 HubConnection 实例的内部映射表中。只有当 `startConnection()` 被调用并成功建立连接后，服务端推送的消息才会被接收并触发已注册的回调。所以调用顺序应该是：先 `on` 注册回调，再 `startConnection` 建立连接。AdminWeb 的 `initSignalR` 正是这样做的：先调用 `startConnection()`，再 `platformHub.on("ReceiveNotification", handler)`。</details>

## 八、连接状态订阅机制

```typescript
type ConnectionStateListener = (state: "connected" | "disconnected" | "reconnecting") => void
const stateListeners: ConnectionStateListener[] = []

export function onConnectionStateChange(listener: ConnectionStateListener): () => void {
  stateListeners.push(listener)
  return () => {
    const index = stateListeners.indexOf(listener)
    if (index >= 0) stateListeners.splice(index, 1)
  }
}

function notifyStateListeners(state: "connected" | "disconnected" | "reconnecting") {
  stateListeners.forEach((listener) => listener(state))
}
```

💡 **这个设计模式和 ASP.NET Core 的 `IObserver<T>` 异曲同工**：
- `onConnectionStateChange` ≈ `Subscribe(observer)`
- 返回的函数 ≈ `IDisposable.Dispose()`（取消订阅）
- `notifyStateListeners` ≈ `OnNext(state)`

⚠️ **【性能陷阱】** 返回的取消订阅函数**必须在组件 unmount 时调用**，否则监听器会泄漏！

```typescript
useEffect(() => {
  const unsubscribe = onConnectionStateChange((state) => {
    // 更新 UI 连接状态指示器
  })
  return () => unsubscribe()  // 必须！
}, [])
```

⚠️ **【性能陷阱】消息队列无限增长的风险**
SignalR 的 `on` 回调是同步执行的。如果回调中做了耗时操作（比如复杂的 DOM 更新或大量计算），会阻塞后续消息的处理。极端情况下，如果消息到达速度超过处理速度，浏览器内存会持续增长。

AdminWeb 的做法是：
1. `onNewNotification` 只做轻量操作（`set` 更新 Zustand state + `toast` 通知）
2. 不在回调中发起新的 HTTP 请求（避免级联延迟）
3. 下载等重操作由用户主动触发（点击通知项），不在回调中自动执行

```typescript
// ✅ 回调中只做轻量操作
const handler = (message: unknown) => {
  // 轻量：更新 state + 显示 toast
  get().onNewNotification(notification)
  toast.success(...)  // sonner 的 toast 是异步渲染，不阻塞
}

// ❌ 危险：回调中发起 HTTP 请求
const handler = async (message: unknown) => {
  await fetch("/api/notifications/sync")  // 阻塞！多条消息会排队等待
  get().onNewNotification(notification)
}
```

## 十、验证步骤

在继续下一节之前，我们用以下步骤验证今天的代码是否正确运行：

### 步骤 1：检查 SignalR 连接是否建立

打开浏览器开发者工具 → Network → 筛选 `WS`（WebSocket），刷新页面后应该看到：

```
名称              状态    类型
/hubs/platform   101     websocket
```

如果看不到这个请求，检查：
- `negotiate` 请求是否成功（状态码 200）
- Vite 代理配置是否包含 `ws: true`
- 后端 Hub 端点是否注册

### 步骤 2：检查 Token 是否传递

在 Network 面板中找到 `negotiate` 请求，查看 Request Headers：

```
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

如果没有 `Authorization` header，检查 `accessTokenFactory` 是否正确读取了 `useAuthStore`。

### 步骤 3：模拟断线重连

在 Network 面板中右键 WebSocket 连接 → 关闭连接，观察控制台：

```
[SignalR] 正在重连...     ← onreconnecting 触发
... 2秒后 ...
[SignalR] 重连成功         ← onreconnected 触发
```

### 步骤 4：检查连接状态监听

在控制台执行：

```javascript
import { onConnectionStateChange } from "@/lib/signalr"
const unsub = onConnectionStateChange((state) => console.log("状态:", state))
// 触发断线/重连，应该看到 "状态: reconnecting" / "状态: connected"
unsub()  // 验证取消订阅
```
