# 目录结构设计

> **这一步解决什么问题？**
> 当我们打开一个陌生的前端项目时，最常问的问题是"这个文件该放哪里？"——目录结构就是团队的约定地图。本文将带我们理解 AdminWeb 的目录布局，建立"每个文件该放哪里"的心智模型，并用一条命令创建所有目录。
>
> 对于 ASP.NET Core 开发者来说，这相当于理解 `Controllers/`、`Services/`、`Models/` 的职责划分——只是前端的"文件夹"换成了一套不同的命名约定。

## 本步目标

理解 AdminWeb 项目的完整目录结构，建立"每个文件该放哪里"的心智模型，并用一条命令创建所有目录。

## 前置知识

如果你是从 ASP.NET Core 过来的，前端项目的目录划分和后端的分层思路是一致的：

| 前端目录 | .NET 对应 | 说明 |
|---------|----------|------|
| `api/` | Controllers + HttpClient | 每个 API 子目录 = 一个微服务的 HttpClient 工厂 |
| `components/` | Views + ViewComponents | UI 组件 = Razor 视图，shared = ViewComponent |
| `stores/` | Scoped Services + INotifyPropertyChanged | 全局状态 = 带属性变更通知的服务 |
| `hooks/` | Extension Methods / Filter | 可复用的逻辑片段 |
| `types/` | DTOs + record types | TypeScript 接口 = C# 的 record / DTO 类 |
| `lib/` | Utils / Helper 静态类 | 纯函数，无状态，无副作用 |

> **关键区别**：后端是请求-响应模型，一个请求对应一个 Controller 方法；前端是持续渲染模型，页面组件持续响应状态变化。理解这个区别，就能理解为什么前端需要 `stores/`——因为页面需要持续"监听"数据变化并更新 UI。

## 代码讲解

### 按服务拆分 vs 按功能拆分：api/ 的组织策略

这是一个关键的设计决策。常见的前端项目会按功能组织 API（如 `api/users.ts`、`api/roles.ts`），但 AdminWeb 选择按后端微服务拆分（`api/auth/`、`api/perm/`）。

两种方案的对比：

| 维度 | 按服务拆分（AdminWeb 选用） | 按功能拆分 |
|------|--------------------------|-----------|
| 目录结构 | `api/auth/users.ts`、`api/perm/roles.ts` | `api/users.ts`、`api/roles.ts` |
| HTTP 实例 | 每个服务一个 `http.ts`，配置隔离 | 通常共享一个 HTTP 实例 |
| 代理映射 | 目录名 → Vite proxy 前缀，一对一 | 需要额外映射文件 |
| 跨服务实体 | 同名实体在不同目录（如 `auth/roles.ts` vs `perm/roles.ts`） | 同名实体需加前缀（如 `auth-roles.ts` vs `perm-roles.ts`） |
| 适用场景 | 微服务架构，各服务独立部署 | 单体后端，或 API 网关统一入口 |
| 找文件速度 | 知道服务就能定位 | 知道实体名就能定位 |

> **🤔 导师提问**：回头看看你自己的微服务项目——你觉得哪种组织方式更合适？如果你的后端有 5 个服务，但其中 3 个共享同一个数据库，这会影响你的选择吗？

AdminWeb 选择按服务拆分的原因有三：

1. **微服务边界对齐**：后端是独立的微服务，每个服务有独立的端口、数据库和部署周期。API 层按服务拆分，与后端一一对应，修改某个服务时只需关注一个目录。

2. **HTTP 实例隔离**：每个服务需要不同的 HTTP 配置。SSO 服务不需要发 `X-Tenant-Id` 头（`sendTenantId: false`），打印服务需要 120 秒超时，文件服务需要处理 Blob 响应。按服务拆分后，每个 `http.ts` 只管自己的配置。

3. **代理路由明确**：Vite 的 proxy 配置按前缀分发请求（`/sso-api` → 10001 端口，`/perm-api` → 10002 端口）。API 目录结构直接映射到 proxy 规则，调试时一目了然。

> **.NET 类比**：就像你不会把所有 HttpClient 放在一个文件里，而是按服务注册不同的 Typed HttpClient——每个服务有独立的 BaseAddress 和 DelegatingHandler 管道。

> **【易错点】** `api/` 下的子目录名必须和 Vite proxy 前缀一一对应。例如 `api/auth/http.ts` 的 baseURL 是 `/sso-api`，Vite 配置中有 `"/sso-api": { target: "http://xxx:10001" }`。如果目录名和 proxy 前缀不对应，请求会 404——这个问题在开发环境才暴露，因为生产环境走 Nginx 反向代理。

### 为什么 components/ 分五层？

| 子目录 | 职责 | 修改频率 | .NET 类比 |
|--------|------|---------|----------|
| `ui/` | shadcn/ui 基础组件，CLI 生成 | 极低（只升级） | Tag Helper |
| `shared/` | 业务通用组件（数据表格、搜索表单） | 中等 | ViewComponent |
| `tree/` | 通用树形组件（含 Hook 和工具函数） | 低 | 自定义 HtmlHelper |
| `layout/` | 布局组件（侧边栏、顶栏） | 低 | `_Layout.cshtml` |
| `brand/` | Logo、品牌标识 | 极低 | `_BrandPartial.cshtml` |

这个分层的核心原则是**修改频率隔离**。`ui/` 由 shadcn CLI 管理，我们永远不应该手动修改它——需要定制就包一层 `shared/` 组件。这和后端不修改第三方 NuGet 包的源码是同一个道理。

> **🤔 导师提问**：如果你把 UI 组件（Button、Dialog）和业务组件（DataTable 带权限列、SearchForm 绑 API）混在同一个目录下，会出现什么痛点？想想后端项目里把 TagHelper 和 ViewComponent 混放时的体会。

> **【设计取舍】** `notification-bell.tsx` 为什么放在 `components/` 根目录而不是 `shared/` 或 `layout/`？因为它既不是纯业务通用组件（它绑定了 `notification-store`），也不是纯布局组件（它有交互逻辑），但又需要被 `app-header.tsx`（layout 组件）引用。放在根目录是一个折中——如果未来通知铃铛变得复杂（比如拆成多个子组件），应该提升为 `components/notification/` 子目录。

> **【设计取舍】** `tree/` 组件放在 `components/` 下而不是 `shared/` 下，因为它自带 Hook 和工具函数——如果放在 `shared/tree/` 下会导致 `shared/` 职责膨胀。当组件的复杂度超过"单个文件"级别，就应该独立为顶层目录。

### 为什么 pages/ 和 api/ 的子目录不是一一对应的？

`pages/` 和 `api/` 的子目录粒度不同。`api/auth/` 下有 6 个 API 文件，但 `pages/auth/` 下有 4 个页面子目录。这是因为：

- **API 按接口粒度拆分**：每个实体一个文件（users.ts、clients.ts、scopes.ts、roles.ts）
- **页面按用户操作粒度拆分**：每个管理界面一个目录，页面内部组合多个 API 调用

> **.NET 类比**：就像 Controller 按 URL 路由分组，但 Service 按业务实体分组。一个 UserController 可能调用 UserService、RoleService、TenantService 多个服务。

### hooks/ 和 lib/ 有什么区别？

| | `lib/` | `hooks/` |
|---|--------|----------|
| 性质 | 纯函数，无状态 | React Hook，有状态 |
| 能否在组件外调用 | 可以 | 不行（Hook 只能在组件内使用） |
| .NET 类比 | `static class Utils` | Extension Method + Filter |
| 示例 | `cn()`、`createHttp()`、`signalr.ts` | `useAuth()`、`useMobile()` |

`createHttp()` 放在 `lib/` 而不是 `hooks/`，因为它不是 Hook——它不调用 `useState` 或 `useEffect`，只是一个返回对象的工厂函数。同理 `signalr.ts` 放在 `lib/`——它管理 WebSocket 连接，不依赖 React 生命周期。

> **🤔 导师提问**：`signalr.ts` 明明管理着连接状态（是否已连接、重连次数），为什么它不是 Hook？提示：想想它的状态是"React 组件的状态"还是"模块级别的变量"——后者的生命周期跟谁走？

### stores/ 的三个 Store 各管什么？

| Store | 持久化 | 缓存策略 | .NET 类比 |
|-------|--------|---------|----------|
| `auth-store` | 全量持久化（localStorage key: `admin-auth`） | 无缓存，实时读写 | IHttpContextAccessor |
| `menu-store` | 选择性持久化（只存 menus/loaded/fetchedAt） | 5 分钟 TTL | IMemoryCache + 绝对过期 |
| `notification-store` | 无持久化 | 无缓存，轮询 + SignalR 实时推送 | IRealTimeNotifier |

> **🤔 导师提问**：什么时候应该新建一个 Store，什么时候用 `useState` 就够了？判断标准是什么——想想后端里什么时候用 Scoped Service，什么时候用一个局部变量。

> **.NET 类比**：三个 Store 就像后端三种不同作用域的服务——auth 是请求级别的上下文，menu 是带缓存的查询服务，notification 是实时推送服务。

### types/ 为什么不全放一个文件？

`types/` 目录目前有两个文件：`index.ts`（通用类型）和 `notification.ts`（通知专属类型）。通用类型合并在一起方便跨服务引用（如 `ApiResult<T>`），但通知类型有独立的枚举（`NotificationStatus`、`NotificationChannel`、`NotificationPriority`）——如果全放 `index.ts` 会让文件膨胀到难以维护。

> **.NET 类比**：就像你不会把所有 DTO 放在一个 `Dtos.cs` 文件里——通用的放 `Common/`，业务的按模块拆分。

## 踩坑提醒

1. **不要手动修改 `ui/` 下的组件**。shadcn CLI 重新生成时会覆盖你的修改。需要定制时，在 `shared/` 下创建包装组件。

2. **`api/` 下的 `http.ts` 是每个服务的入口**，导入 API 方法时必须从对应子目录导入，不要从根目录统一导出。这样 Vite 的 tree-shaking 才能正确移除未使用的服务模块。

3. **`types/index.ts` 是主文件**，但不是唯一文件。独立模块（如 `notification.ts`）可以有自己的类型文件。TypeScript 的类型在编译后会被擦除，不会增加包体积。

4. **`stores/` 只有全局状态才放这里**，页面内部的状态（如表单输入、弹窗开关）直接用 `useState`。Store 滥用会让代码难以追踪——就像后端不应该把所有数据都塞进 Redis 一样。

5. > **【易错点】** `api/` 子目录和 Vite proxy 前缀必须一一对应。`auth/http.ts` → baseURL `/sso-api` → proxy 规则 `"/sso-api": { target: "http://xxx:10001" }`。如果忘了配 proxy 或前缀对不上，请求会 404。

> **🤔 导师提问**：如果 `api/auth/` 目录下的 `http.ts` 把 baseURL 写成了 `/perm-api` 而不是 `/sso-api`，会发生什么？请求能发出去吗？会到哪个后端服务？这跟后端的 HttpClient BaseAddress 配错有多像？

>
> 1. 在 `src/` 目录下执行 `ls`，确认 `api/`、`components/`、`hooks/`、`lib/`、`pages/`、`stores/`、`types/` 目录都已创建
> 2. 打开 `vite.config.ts`，确认 `proxy` 配置中的前缀（`/sso-api`、`/perm-api`、`/gw-api`）与 `api/` 下子目录名一致
