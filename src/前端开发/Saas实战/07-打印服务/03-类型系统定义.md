# 03 - 类型系统定义

> **这一步解决什么问题？** 我们要定义打印服务涉及的所有 TypeScript 类型——4 组枚举、6 个 DTO/Input。类型系统是前后端的契约：ASP.NET Core 用 C# `enum` 和 `class`，React 用 `as const` 对象和 `interface`。理解两者的映射关系，是正确编写前端代码的基础。

## 代码讲解

在 ASP.NET Core 中，我们用 C# 的 `enum` 和 `class` 定义 DTO。在 React/TypeScript 中，类型系统同样重要 —— 但实现方式不同：

```
C# 世界:                         TypeScript 世界:
enum TemplateStatus {            const TEMPLATE_STATUS = {
  Draft = 0,                       Draft: 0,
  Published = 1,                   Published: 1,
  Archived = 2,                    Archived: 2,
}                                } as const
                                 type TemplateStatus = (typeof TEMPLATE_STATUS)[keyof typeof TEMPLATE_STATUS]

class ReportTemplateListDto {    interface ReportTemplateListDto {
  public string Id { get; set; }    id: string
  public string Name { get; set; }  name: string
}                                }
```

**核心差异**：

| 特性 | C# enum | TypeScript `as const` 对象 |
|---|---|---|
| 运行时存在 | 是（编译为整数） | 是（普通对象） |
| 反向映射 | 支持（`Enum.Name`） | 通过 `LABELS` 映射实现 |
| 遍历 | `Enum.GetValues()` | `Object.entries()` |
| 类型安全 | 编译时 | 编译时 |

> **为什么不用 TypeScript `enum`？** 因为 TypeScript `enum` 编译后的代码冗余，且数字枚举存在反向映射陷阱。`as const` 对象 + 类型推导是 React 社区的主流方案。

> **🤔 导师提问**：C# 的 `enum` 是值类型，编译后就是整数；TypeScript 的 `enum` 编译后是双向映射对象（数字→名称 + 名称→数字）。想想看：为什么 TypeScript 数字枚举的双向映射反而是一个"陷阱"？如果你在代码中写了 `Object.values(TemplateStatus)` 遍历枚举，C# 和 TypeScript 的输出分别是什么？

### 打印服务的四组枚举

打印服务涉及四组枚举，分别对应模板状态、导出格式、数据源类型、任务状态：

### DTO 设计：ListDto vs DetailDto

模板有两个 DTO：`ReportTemplateListDto`（列表）和 `ReportTemplateDetailDto`（详情）。区别在于：

```
ListDto:  { id, name, code, status, ... }          ← 列表页展示，不含 frxContent
DetailDto extends ListDto: { ... frxContent }      ← 详情/编辑时才加载模板文件内容
```

> **ASP.NET Core 类比**：这就像 OData 查询中的 `$select`，列表页只返回必要字段，避免传输大字段（frxContent 可能几十 KB）。类似 EF Core 的 `ProjectTo<T>()` 而非 `ToList<T>()`。

> **🤔 导师提问**：`ReportTemplateDetailDto extends ReportTemplateListDto` 只新增了 `frxContent` 一个字段。在 C# 中，这种继承很常见；但在 TypeScript 中，另一种做法是交叉类型 `ReportTemplateListDto & { frxContent: string }`。两种方式有什么区别？如果 `ListDto` 的字段将来会变，哪种方式维护成本更低？

### Input 类型：Create vs Update

```
CreateTemplateInput:     UpdateTemplateInput:
  name: string  ← 必填    name: string  ← 必填
  code?: string           code?: string
  ...                     ...
                          defaultDataSourceConfigId?: string | null ← Update 独有
```

> **注意**：`UpdateTemplateInput` 多了一个 `defaultDataSourceConfigId` 字段（可为 null），用于清除模板关联的数据源。`CreateTemplateInput` 没有这个字段，因为创建时不自动关联数据源。

> **🤔 导师提问**：`DataSourceConfigDto` 中有大量 `string | null` 字段（如 `httpUrl: string | null`），而 `CreateDataSourceInput` 中对应字段是 `string | undefined`（如 `httpUrl?: string`）。后端返回的 DTO 用 `null` 表示"未设置"，前端提交的 Input 用 `undefined` 表示"不传这个字段"。为什么后端和前端的"空"表示方式不同？如果把 Input 中的 `httpUrl?: string` 改成 `httpUrl?: string | null`，序列化时会有什么问题？

### 枚举模式关键行

| 行 | 代码 | 解析 |
|---|---|---|
| `as const` | `export const TEMPLATE_STATUS = { ... } as const` | **【易错点】** `as const` 让 TypeScript 将对象属性标记为字面量类型（`0` 而非 `number`）。没有 `as const`，`TEMPLATE_STATUS.Draft` 的类型是 `number` 而非 `0`，后续 `Record<TemplateStatus, string>` 无法正确约束 key |
| 类型推导 | `type TemplateStatus = (typeof TEMPLATE_STATUS)[keyof typeof TEMPLATE_STATUS]` | 这行的拆解：`typeof TEMPLATE_STATUS` 得到对象的类型 → `keyof` 提取所有 key → 索引访问得到值类型的联合 → 最终 `TemplateStatus = 0 \| 1 \| 2` |
| LABELS 映射 | `Record<TemplateStatus, string>` | **【设计取舍】** 用 `Record` 而非普通对象确保标签覆盖所有枚举值。如果新增了枚举值但忘记加标签，TypeScript 编译时会报错 |

### DTO 关键行

| 行 | 代码 | 解析 |
|---|---|---|
| `code: string \| null` | `ReportTemplateListDto.code` | **【易错点】** 后端 DTO 的 `string?`（C# 可空）映射为 `string \| null`，不是 `string \| undefined`。后端返回 JSON 时，未设置的引用类型字段为 `null` 而非缺失 |
| `extends` | `ReportTemplateDetailDto extends ReportTemplateListDto` | 继承复用，只新增 `frxContent` 字段。类似 C# 的继承，TypeScript interface 同样支持 extends |
| `unknown` | `RenderReportInput.directData?: unknown` | **【设计取舍】** `directData` 可以是任意结构（数组、对象、字符串），用 `unknown` 比用 `any` 更安全 —— 使用前必须类型断言，不会隐式逃逸类型检查 |

> **🤔 导师提问**：`unknown` 和 `any` 都能表示"任意类型"，但 `unknown` 要求使用前必须做类型检查（类型收窄）。如果把 `directData` 的类型改成 `any`，代码可以编译但运行时可能出错。这和 C# 的 `dynamic` vs `object` 有什么相似之处？你能举一个 `unknown` 在编译时帮你发现错误的例子吗？

| `type = interface` | `UpdateDataSourceInput = CreateDataSourceInput` | TypeScript 类型别名，两个类型完全相同。后端 Update 和 Create 共用同一个 DTO 结构 |

## 踩坑提醒

1. **`as const` 不能省略**：没有 `as const`，`TEMPLATE_STATUS.Draft` 的类型是 `number` 而非 `0`，后续 `Record<TemplateStatus, string>` 无法正确约束 key。所有枚举定义必须加 `as const`。
2. **DTO 中可空字段用 `| null` 不是 `| undefined`**：后端返回的 JSON 中未设置字段为 `null` 而非缺失，所以 `code: string | null` 才是正确的 DTO 写法。Input 中用 `?` 表示"不传这个字段"即可。
3. **`UpdateDataSourceInput = CreateDataSourceInput` 是类型别名**：两者完全相同，修改其中一个不会影响另一个——因为它们是同一个类型的不同名字。
