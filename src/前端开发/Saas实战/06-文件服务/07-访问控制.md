# 访问控制

[← 上一篇：配额管理](06-配额管理.md) | [下一篇：文件分享 →](08-文件分享.md)

---

> **这一步解决什么问题？** 文件的 `accessLevel` 只解决了粗粒度的"谁能看"问题——私有、租户内公开、全平台公开。但在实际业务中，我们需要**细粒度**的权限控制：比如"这份报表只给张三看 3 天"、"这个设计稿让李四可以编辑但不能删除"、"项目文档允许团队成员读取但外包人员 7 天后失效"。这就是文件级 ACL（Access Control List），类比 Windows NTFS 的文件权限设置，或 ASP.NET Core 中自定义的 `[Authorize(Policy = "FileRead")]` 策略。

## 前置知识

- 01 篇文件服务架构：`ACCESS_LEVEL`（0/1/2）三级访问控制、`FILE_PERMISSION`（Read/Write/Delete）权限类型

## ACL 模型 vs RBAC

| 特性 | RBAC（角色权限） | ACL（访问控制列表） |
|------|------------------|---------------------|
| 粒度 | 资源类型级 | 资源实例级 |
| 类比 | `[Authorize(Roles = "Admin")]` | NTFS 文件权限 |
| 适用 | 菜单、按钮、API 端点 | 单个文件的读/写/删 |
| 时效 | 永久（直到角色变更） | 可设过期时间 |

本系统的权限中心用 RBAC 管功能权限，文件服务用 ACL 管文件权限，两者互补。

> **🤔 导师提问**：假设一个用户拥有"管理员"角色（RBAC），同时某个文件给他单独授权了 ACL Read 权限。如果该文件的 `accessLevel` 是 Private，这个用户能访问吗？三种权限机制（RBAC 角色、accessLevel、ACL）的优先级关系是怎样的？

【设计取舍】权限继承模型：本系统的 ACL 是**显式授权**，不继承。即：文件夹的权限不会自动传递给子文件，每个文件的 ACL 是独立的。这种设计简化了权限判断逻辑——不需要递归查找父级权限，但代价是用户需要逐个文件授权。如果业务需要"整个文件夹共享"的场景，应该通过**文件分享**（ShareLink）而非 ACL 来实现。

## ACL API 层

访问控制的后端交互封装在 `src/api/file/file-access.ts` 中：

```typescript
import { get, post, del } from "./http"
import type { FileAccessGrantDto, GrantAccessRequest } from "@/types"

/** 文件级 ACL（访问控制列表）API，用于管理文件的用户级权限 */
export const fileAccessApi = {
  grant(data: GrantAccessRequest) {
    return post<FileAccessGrantDto>("/api/file-access/grant", data)
  },

  revoke(grantId: string) {
    return del<void>(`/api/file-access/${grantId}`)
  },

  listByFile(fileId: string) {
    return get<FileAccessGrantDto[]>(`/api/file-access/file/${fileId}`)
  },

  listMyGrants() {
    return get<FileAccessGrantDto[]>("/api/file-access/my-grants")
  },

  checkPermission(fileId: string, userId: string, permission: string) {
    return get<{ hasPermission: boolean }>("/api/file-access/check", {
      fileId,
      userId,
      permission,
    })
  },
}
```

### 关键类型

```typescript
/** 文件访问授权记录 DTO */
export interface FileAccessGrantDto {
  id: string
  fileId: string
  grantedToUserId: string
  permission: string
  expiresAt: string | null
  isExpired: boolean
  createdAt: string
  grantedBy: string | null
}

/** 授权文件访问请求 */
export interface GrantAccessRequest {
  fileId: string
  grantedToUserId: string
  permission: string
  expiresAt?: string
}
```

> **🤔 导师提问**：`FileAccessGrantDto.permission` 的类型是 `string` 而非 `FilePermission`。这是因为后端返回的 permission 字段可能不在前端 `FILE_PERMISSION` 的枚举范围内（比如后端新增了 `Admin` 权限，但前端还没更新）。这种宽松类型设计有什么好处和风险？

【易错点】`checkPermission` API 看起来可以用来做前端权限判断，但它是一个**网络请求**，不能用于 UI 渲染的条件判断（如 `if (hasPermission) showEditButton()`）。因为网络请求是异步的，页面渲染时还没拿到结果。前端应该根据 ACL 列表自行判断，`checkPermission` 主要用于操作前的二次确认。

## 逐行讲解

### `presetFileId` — 双入口设计

```typescript
interface FileAccessPanelProps {
  presetFileId?: string
}
```

- **双入口**：1) 从文件管理页右键菜单 → 弹窗中嵌入面板（传 `presetFileId`）；2) 从侧边栏导航 → 独立页面（不传 `presetFileId`，需要搜索文件）。【设计取舍】一个组件同时服务弹窗和页面两种场景，避免代码重复。
- **条件渲染**：`{!presetFileId && <Card>...</Card>}` —— 当预设文件 ID 存在时，跳过文件搜索卡片，直接显示已选文件信息。这样弹窗场景下用户不需要重复选择文件。

### 过期时间计算

```typescript
const expiresAt = grantExpiryDays && grantExpiryDays !== "0"
  ? new Date(Date.now() + parseInt(grantExpiryDays) * 86400000).toISOString()
  : undefined
```

- **86400000 = 24 * 60 * 60 * 1000**：一天的毫秒数。【易错点】`parseInt(grantExpiryDays)` 如果 `grantExpiryDays` 为空字符串会返回 `NaN`，但前面已用 `grantExpiryDays &&` 短路保护。
- **`"0"` 表示永久**：前端的约定，0 天 = 不过期。传 `undefined` 给后端，后端不设过期时间。

【易错点】`ACCESS_LEVEL` 与 `FILE_PERMISSION` 是两套不同的概念，容易混淆：
- `ACCESS_LEVEL`（0/1/2）：文件的**可见范围**，决定谁能看到文件存在
- `FILE_PERMISSION`（Read/Write/Delete）：ACL 的**操作权限**，决定授权用户能做什么

一个常见的错误是在前端用 `accessLevel === 2` 来判断用户能否编辑文件——实际上 `accessLevel` 只控制可见性，编辑权限由 ACL 的 `Write` 权限控制。

### 用户名称映射

```typescript
const uniqueUserIds = [...new Set(grantList.map((g) => g.grantedToUserId).filter(Boolean))]
if (uniqueUserIds.length > 0) {
  const nameMap: Record<string, string> = { ...userNames }
  await Promise.all(
    uniqueUserIds.map(async (uid) => {
      if (!nameMap[uid]) {
        try {
          const uRes = await usersApi.getById(uid)
          if (uRes.success && uRes.data) {
            nameMap[uid] = uRes.data.displayName || uRes.data.userName
          } else {
            nameMap[uid] = uid.substring(0, 8) + "..."
          }
        } catch {
          nameMap[uid] = uid.substring(0, 8) + "..."
        }
      }
    })
  )
  setUserNames({ ...nameMap })
}
```

- **去重 + 缓存**：先 `new Set()` 去重，再检查 `nameMap[uid]` 是否已缓存，避免重复请求。【性能陷阱】如果授权列表有 50 个不同用户，会并发发 50 个 HTTP 请求。生产环境应考虑批量查询接口。
- **降级策略**：请求失败时用 `uid.substring(0, 8) + "..."` 显示，确保表格不会因为用户名获取失败而空白。

> **🤔 导师提问**：`userNames` 状态是在 `loadGrants` 中更新的，但如果用户切换了文件（选中另一个文件），旧文件的用户名缓存会丢失吗？为什么这里的缓存设计是"组件级"而非"全局级"的？

### `filterTab` 筛选

```typescript
const filteredGrants =
  filterTab === "all"
    ? grants
    : filterTab === "active"
      ? grants.filter((g) => !g.isExpired)
      : grants.filter((g) => g.isExpired)
```

- **前端过滤**：数据量小（通常几十条授权记录），无需后端分页。如果未来授权记录增长到上千条，应改为后端过滤。

### 组件思维：谁拥有访问控制状态？

`FileAccessPanel` 组件内部的 `grants` 状态是**组件私有**的，不会同步到全局 store。这意味着：

1. 用户在面板 A 授权后，面板 B 不会自动更新（如果同时存在两个面板实例）
2. 授权操作后调用 `loadGrants()` 刷新本组件数据，但不影响其他组件

这种设计是合理的——访问控制是低频操作，不太可能同时操作。但如果未来需要在文件列表页实时显示"已授权 N 人"之类的统计信息，就需要把 ACL 状态提升到 store 或使用 React Query 的缓存失效机制。

## 踩坑提醒

1. **`ACCESS_LEVEL` 与 `FILE_PERMISSION` 容易混淆**：`ACCESS_LEVEL`（0/1/2）控制文件的**可见范围**（谁能看到文件存在），`FILE_PERMISSION`（Read/Write/Delete）控制 ACL 的**操作权限**（授权用户能做什么）。常见错误是用 `accessLevel === 2` 判断用户能否编辑文件——实际上编辑权限由 ACL 的 `Write` 权限控制。
2. **`checkPermission` 不能用于 UI 渲染**：`checkPermission` 是异步网络请求，不能用在 `if (hasPermission) showEditButton()` 这种同步渲染中。页面渲染时结果还没返回。前端应根据 ACL 列表自行判断权限，`checkPermission` 主要用于操作前的二次确认。
3. **用户名称映射的并发请求问题**：如果授权列表有 50 个不同用户，`loadGrants` 中会并发发 50 个 `usersApi.getById` 请求。生产环境应考虑批量查询接口或请求合并。
