> **这一步解决什么问题？** 我们刚刚搭好了 API 网关，请求已经能正确路由到后端服务。现在要把目光投向 SaaS 平台的基础设施之一——**文件服务**。在后端开发中，你可能习惯用 `IFormFile` 接收上传、用 `System.IO.File` 写磁盘、用 SQL 存文件元数据。但 SaaS 多租户场景下，这种方式会面临几个硬伤：存储隔离、配额控制、访问控制、大文件处理。文件服务就是解决这些问题的统一入口，类比 ASP.NET Core 的 `IFileProvider` + `PhysicalFileProvider`，只不过它面向的是多租户、云原生的场景。

## 核心概念

### 存储后端

| 后端 | 类比 ASP.NET Core | 特点 |
|------|-------------------|------|
| MinIO | `PhysicalFileProvider` | 自建 S3 兼容对象存储，私有部署首选 |
| AWS S3 | — | 公有云标准，无需运维存储集群 |
| Azure Blob | `AzureBlobStorage` | Azure 生态集成 |

本系统使用 **MinIO** 作为存储后端，通过 S3 兼容协议交互。后端服务对前端透明——前端只跟 FileService API 通信。

> **🤔 导师提问**：后端选择了 MinIO 作为存储，但前端代码中完全看不到 MinIO 的影子。这说明前端和存储后端之间是怎样一种耦合关系？如果将来从 MinIO 迁移到 AWS S3，前端需要改代码吗？

### 配额体系

```
租户 (Tenant)
  └── 配额 (Quota)
        ├── quotaBytes: 配额总量（字节）
        ├── usedBytes:  已使用量
        └── fileCount:  文件数量
```

类比 SQL Server 的 `MAX_STORAGE_SIZE_MB` 设置，但粒度精确到字节，而且支持**动态调整**。管理员可以在运行时扩容或缩容，无需重启服务。

### 访问控制模型

```
文件 (File)
  ├── accessLevel: 0=私有, 1=租户内公开, 2=全平台公开
  └── ACL 授权记录 (FileAccessGrant)
        ├── grantedToUserId: 被授权用户
        ├── permission: Read | Write | Delete
        └── expiresAt: 过期时间
```

这不是简单的"公开/私有"二元划分，而是 **两层模型**：

1. **文件级访问级别（accessLevel）**：粗粒度，类似 ASP.NET Core 的 `[AllowAnonymous]` vs `[Authorize]`
2. **用户级 ACL 授权**：细粒度，类似 Windows NTFS 的 ACL，可以给特定用户授予 Read/Write/Delete 权限，并设过期时间

### 整体架构图

```
┌──────────────┐     ┌───────────────────┐     ┌───────────┐
│  前端 React  │────▶│  FileService API  │────▶│   MinIO   │
│  AdminWeb    │     │  (ASP.NET Core)   │     │  (S3 API) │
└──────────────┘     └────────┬──────────┘     └───────────┘
                              │
                     ┌────────┴────────┐
                     │   PostgreSQL    │
                     │  (元数据+配额)  │
                     └─────────────────┘
```

前端通过网关（`/file-api/*`）访问 FileService，FileService 负责鉴权、配额检查、元数据记录，然后与 MinIO 交互存储实际文件。

### 请求链路详解

上面的架构图只展示了服务间关系。让我们放大"前端 → 后端"这条链路，看看一个文件请求到底经过了哪些环节：

```
浏览器 (React)
  │
  │  axios.get("/file-api/api/files")
  │  headers: { Authorization: "Bearer xxx", X-Tenant-Id: "tenant-1" }
  ▼
Vite Dev Server (proxy)
  │  /file-api/* → http://moklgy.me:10011/*
  │  rewrite: /file-api/api/files → /api/files
  │
  │  ⚠️ 文件上传有 body size 限制
  ▼
FileService API (ASP.NET Core, port 10011)
  │  1. 验证 Token + 租户归属
  │  2. 检查配额（上传时）
  │  3. 检查 accessLevel + ACL（读取时）
  ▼
MinIO (S3 API)
  │  putObject / getObject
  ▼
PostgreSQL (元数据)
```

> **🤔 导师提问**：Vite proxy 在 rewrite 时把 `/file-api` 前缀去掉了。如果后端同时部署了多个服务（如权限服务、文件服务），Nginx 的 rewrite 规则要怎么写才能正确路由？

【易错点】Vite proxy 的 `bodyParser` 默认限制请求体大小为 **30MB**（不同版本可能不同）。上传大文件时，如果超过此限制会收到 `413 Payload Too Large`，但错误来自 Vite 而非后端。生产环境用 Nginx 不受此限制，但开发时需要在 `vite.config.ts` 中配置 `proxy` 的 `configure` 选项来调整。

【设计取舍】BLOB 存储 vs 文件系统：MinIO 等对象存储将文件作为 BLOB（Binary Large Object）管理，不提供目录遍历、符号链接等文件系统语义。好处是天然适合云原生（水平扩展、分片冗余），坏处是某些场景（如需要文件锁、追加写入）不如文件系统灵活。本系统选择 BLOB 存储，因为 SaaS 文件服务以"上传-下载"为主，不需要文件系统的复杂语义。

## 文件 API 的 HTTP 客户端

所有文件 API 都基于同一个 `fileHttp` 实例，定义在 `src/api/file/http.ts`：

```typescript
// FileService 模块 HTTP 客户端
// 代理路径：/file-api/* → http://moklgy.me:10011/*
import { createHttp } from "@/lib/create-http"

/** 文件服务 HTTP 客户端，基础路径为 /file-api */
const fileHttp = createHttp("/file-api")

/** 导出常用 HTTP 方法 */
export const { get, post, put, del } = fileHttp
/** 导出 axios 实例，供需要自定义配置（如 responseType、onUploadProgress）的场景使用 */
export default fileHttp.instance
```

### 逐行解读

- **`createHttp("/file-api")`**：调用公共工厂函数创建 axios 实例，`baseURL` 设为 `/file-api`。这个前缀对应 Vite proxy 的路由规则。
- **`export const { get, post, put, del } = fileHttp`**：解构出封装好的 REST 方法，子模块直接 `import { get } from "./http"` 即可使用，无需关心 axios 实例细节。
- **`export default fileHttp.instance`**：导出底层 axios 实例。为什么需要它？因为 `filesApi.upload()` 需要用 `onUploadProgress` 追踪上传进度，以及设置 `headers: { "Content-Type": "multipart/form-data" }`，这些是封装方法不支持的。

【易错点】文件下载场景（`filesApi.download()`、`filesApi.packageDownload()`）需要 `responseType: "blob"`，也只能通过 `fileHttpInstance.get()` / `fileHttpInstance.post()` 直接调用，封装的 `get()` / `post()` 方法不支持传 axios config。

> **🤔 导师提问**：`createHttp` 工厂函数内部做了请求拦截（自动挂 Bearer Token 和 X-Tenant-Id）和响应拦截（401 自动刷新 Token）。如果我们有两个 API 模块（如 `ssoHttp` 和 `fileHttp`），它们的 Token 刷新逻辑是共享的还是各自独立的？如果其中一个模块刷新失败，另一个模块的请求会怎样？

## 文件上传流程

文件上传是文件服务最复杂的交互，涉及认证、分片、进度追踪。核心流程如下：

```
浏览器
  │
  │  1. 用户选择文件 → 计算 SHA-256 哈希
  │
  │  2. 秒传检测 POST /file-api/api/files/instant-upload
  │     body: { hash, fileName, contentType, sizeBytes }
  │
  ├─── 命中 → 返回文件元数据，上传结束（0 字节传输）
  │
  └─── 未命中 (404) → 3. 正常上传 POST /file-api/api/files/upload
        Content-Type: multipart/form-data
        body: FormData { file: File }
        query: ?accessLevel=0&folderId=xxx
        onUploadProgress: (evt) → 更新进度条
        │
        ▼
     Vite Proxy → FileService → MinIO
```

> **🤔 导师提问**：秒传检测时，前端需要计算文件的 SHA-256 哈希。对于一个 1GB 的文件，这个计算在主线程上执行会有什么问题？你会怎么优化？

【性能陷阱】大文件上传：当前系统的小文件走单个 `POST /api/files/upload` 请求，大文件（超过约 100MB）应走分片上传（`/api/multipart/*`）。分片上传的流程是：前端先请求后端创建分片任务 → 逐片上传 → 后端合并。单请求上传大文件时，如果网络中断，整个文件需要重新上传；分片上传则只需重传失败的分片。但分片上传的实现复杂度远高于单请求，需要在进度追踪、断点续传、错误重试等方面额外处理。

/** 访问级别 - 运行时常量 */
export const ACCESS_LEVEL = {

  TenantPublic: 1,

export type AccessLevel = (typeof ACCESS_LEVEL)[keyof typeof ACCESS_LEVEL]

## 逐行讲解

### `ACCESS_LEVEL` 常量定义

```typescript
export const ACCESS_LEVEL = {
  Private: 0,
  TenantPublic: 1,
  Public: 2,
} as const
```

- **`as const`**：将对象变为字面量类型，使 `ACCESS_LEVEL.Private` 的类型是 `0` 而非 `number`。【易错点】如果漏掉 `as const`，`AccessLevel` 类型会变成 `number`，丧失类型约束力。
- 数字递增对应权限范围递增：0 最严格，2 最开放。【设计取舍】用数字而非字符串是因为后端 enum 序列化为整数，前端保持一致减少映射。

### `FILE_STATUS` 常量定义

```typescript
export const FILE_STATUS = {
  Active: 0,
  Deleted: 1,
} as const
```

- 删除不是物理删除，而是**软删除**（`status` 从 `0` 变为 `1`），类比后端的 `IsDeleted` 字段配合 EF Core 的全局查询过滤器。
- 文件进入回收站后仍可恢复（`restore` API），永久删除使用 `purge` API。

> **🤔 导师提问**：`FileObjectDto` 中 `folderId: string | null` 表示文件可以不在任何文件夹下（根目录文件）。那如果用户删除了一个非空文件夹，后端应该怎么处理？先删子文件再删文件夹，还是级联软删除？

### `FolderTreeNode` 递归结构

```typescript
export interface FolderTreeNode {
  id: string
  name: string
  fullPath: string
  level: number
  children: FolderTreeNode[]  // ← 递归引用自身
}
```

- **`children: FolderTreeNode[]`**：递归定义，类比后端的树形结构序列化。【性能陷阱】深层嵌套时前端递归渲染要注意虚拟化，否则万级节点会卡顿。
- **`fullPath`**：服务端预计算完整路径（如 `/项目文档/2024/报告`），避免前端递归拼接。

【易错点】文件夹名称中的特殊字符（如 `/`、`\`、`..`）可能导致路径遍历问题。后端必须校验文件夹名不包含路径分隔符和 `..`，否则用户创建名为 `../../etc` 的文件夹可能导致安全隐患。前端也应做基本校验，但**安全防线在后端**。

### `QuotaDto` 配额模型

```typescript
export interface QuotaDto {
  tenantId: string
  quotaBytes: number        // 字节级精度
  usedBytes: number
  fileCount: number
  usagePercentage: number   // 服务端计算，前端直接使用
}
```

- **`quotaBytes` 用 number**：JS number 最大安全整数 `2^53 - 1` ≈ 9 PB，远超实际需求。【易错点】不要用 `string` 存字节数再手动 `parseInt`，`JSON.parse` 对 64 位整数可能丢精度，但本系统配额不会超过 PB 级。
- **`usagePercentage` 由服务端计算**：避免前端因 `quotaBytes` 和 `usedBytes` 精度问题算出 99.999% 或 100.001% 这种尴尬值。

## 踩坑提醒

1. **Vite proxy 的 body size 限制**：Vite proxy 默认限制请求体大小约 30MB。上传大文件超过此限制会收到 `413 Payload Too Large`，但错误来自 Vite 而非后端。开发时需在 `vite.config.ts` 中配置 proxy 的 `configure` 选项来调整，生产环境用 Nginx 不受此限制。
2. **`as const` 不能漏掉**：如果漏掉 `as const`，`ACCESS_LEVEL.Private` 的类型会变成 `number` 而非字面量 `0`，`AccessLevel` 类型会变成 `number`，丧失类型约束力——`const level: AccessLevel = 3` 不会报错。
3. **文件夹名中的特殊字符**：名称中如 `/`、`\`、`..` 可能导致路径遍历问题。后端必须校验不包含路径分隔符和 `..`，前端也应做基本校验，但**安全防线在后端**。
