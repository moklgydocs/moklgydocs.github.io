# 01 - 运行时配置概述：从 appsettings.json 到前端配置中心

> **这一步解决什么问题？**
> 在 ASP.NET Core 后端，我们习惯用 `appsettings.json` 管理配置，配合 `IOptionsMonitor<T>` 实现热重载。但 SaaS 平台有多个微服务（权限中心、文件服务、打印服务……），每修改一个配置项就要重启服务？不可接受。我们需要一个**前端配置管理界面**，让运维人员在浏览器里增删改配置，配置项自动热重载到后端——这就是 AdminWeb 的配置中心。
>
> **ASP.NET Core 开发者的直觉**：你在后端用过 `appsettings.json` + `IOptionsSnapshot<T>`，知道修改配置后需要等文件变更通知或手动 reload。AdminWeb 的配置中心就是把这个流程搬到了 Web 界面，底层仍然是后端的 `IConfiguration` + 文件轮询机制。

---

## 一、构建时配置 vs 运行时配置

前端项目本身也有"配置"——Vite 的环境变量 `.env`、TypeScript 的编译选项等。这些是**构建时配置**，打包后无法修改。而配置中心管理的是**运行时配置**，服务运行期间可随时修改并生效。

```
┌─────────────────────────────────────────────────────────────────────┐
│                     配置的分类与生命周期                               │
├──────────────────┬────────────────────┬─────────────────────────────┤
│ 维度              │ 构建时配置           │ 运行时配置                   │
├──────────────────┼────────────────────┼─────────────────────────────┤
│ 存储位置          │ .env / vite.config  │ 后端 JSON 文件 + Consul     │
│ 修改时机          │ 构建前              │ 运行中（通过配置中心界面）      │
│ 生效方式          │ 重新构建 & 部署      │ 后端轮询 / 强制重载（5 秒内）  │
│ 前端可修改？      │ 否                  │ 是（通过 API）               │
│ 典型例子          │ VITE_API_BASE_URL   │ Jwt:Secret、Storage:MinIO   │
│ ASP.NET 类比      │ csproj 编译常量      │ appsettings.json + Reload   │
└──────────────────┴────────────────────┴─────────────────────────────┘
```

⚠️ **【易错点】** 不要把 Vite 的 `import.meta.env.VITE_*` 和配置中心的运行时配置混淆。前者是 Webpack/Vite 构建时注入的静态值，后者是后端服务运行时从 API 拉取的动态值。

⚠️ **【易错点】** 构建时配置一旦打包就无法修改——即使你修改了 `.env` 文件，已经部署的静态文件里的值也不会变。这意味着像 API 地址这种可能随环境变化的值，不应该只放在 `.env` 里，而应该通过运行时配置中心管理，或者使用 Docker/K8s 的环境变量在容器启动时注入。

> 🎯 **组件思维**：在 React 中，构建时配置 ≈ 组件的 defaultProps（编译时确定），运行时配置 ≈ 组件的 state（运行时可变）。我们不会把运行时变化的数据放在 defaultProps 里，同理也不应该把需要动态修改的值放在 `.env` 里。

💡 **ASP.NET Core 类比**：

```
构建时配置（前端 .env）    ≈  编译时常量 #define / [Conditional]
运行时配置（配置中心）      ≈  appsettings.json + IOptionsMonitor<T>
```

## 二、AdminWeb 配置中心的架构

AdminWeb 的配置中心不是一个独立的微服务，而是一个**统一的前端页面**，通过路由参数指向不同的后端服务。每个微服务都暴露 `/api/runtime-config` 端点，前端通过 Vite 代理转发请求。

```
┌──────────────────────────────────────────────────────────────────────┐
│                         AdminWeb 前端                                 │
│                                                                      │
│  ┌─────────────────────────────────────────────────────────────────┐ │
│  │  /config/* 路由（共用同一个 ConfigPage 组件）                     │ │
│  │  ┌────────────────┬────────────────┬──────────────────────┐    │ │
│  │  │ /config/       │ /config/       │ /config/             │    │ │
│  │  │ perm-center    │ file-service   │ print-service  ...   │    │ │
│  │  │                │                │                      │    │ │
│  │  │ serviceBaseUrl │ serviceBaseUrl │ serviceBaseUrl       │    │ │
│  │  │ = "/perm-api"  │ = "/file-api"  │ = "/print-api"      │    │ │
│  │  │ serviceLabel   │ serviceLabel   │ serviceLabel         │    │ │
│  │  │ = "权限中心"    │ = "文件服务"    │ = "打印服务"          │    │ │
│  │  └───────┬────────┴───────┬────────┴──────────┬───────────┘    │ │
│  └──────────┼────────────────┼───────────────────┼────────────────┘ │
│             │                │                   │                  │
│  ┌──────────▼────────────────▼───────────────────▼────────────────┐ │
│  │                  Vite Dev Server Proxy                         │ │
│  │  /perm-api  →  http://moklgy.me:10002                         │ │
│  │  /file-api  →  http://moklgy.me:10011                         │ │
│  │  /print-api →  http://moklgy.me:11010                         │ │
│  │  /miniapp-api → http://moklgy.me:5020                         │ │
│  │  /notify-api → http://moklgy.me:10012                         │ │
│  └────────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────┘
                              │
              ┌───────────────▼───────────────┐
              │    各微服务后端                  │
              │    /api/runtime-config         │
              │    /api/runtime-config/reload   │
              │                                │
              │    内部：IConfiguration 轮询    │
              │    AES-256 加密存储             │
              └────────────────────────────────┘
```

💡 **核心设计思想**：一个 ConfigPage 组件，通过 props 区分服务。这避免了 5 个服务写 5 个几乎一样的页面。

> 🎯 **教练提问**：如果我们为每个微服务写一个独立的配置页面（PermConfigPage、FileConfigPage……），会有多少重复代码？5 个页面 × 4 个 API 调用 = 20 段几乎一样的代码。Props 驱动的复用策略在这里省了多少工作量？

⚠️ **【设计取舍】** 为什么不把配置中心做成独立微服务？
因为每个微服务的配置项结构和 API 接口完全一致（`/api/runtime-config`），只需要一个前端组件 + 路由分发。如果做成独立微服务，反而增加了部署复杂度和网络跳数。

⚠️ **【设计取舍】** 前端配置 vs 后端配置 vs 环境变量：如何选择？

```
┌────────────────┬──────────────────────────────┬────────────────────────────┐
│ 方式            │ 适用场景                       │ 优劣                        │
├────────────────┼──────────────────────────────┼────────────────────────────┤
│ 前端配置中心     │ 运维人员需要动态修改的配置        │ 可视化操作、热重载、有审计     │
│                │ （JWT 密钥、数据库连接串）       │ 但需要后端 API 支持           │
├────────────────┼──────────────────────────────┼────────────────────────────┤
│ appsettings    │ 只在启动时读取、运行中不变的配置  │ 简单、无额外依赖              │
│ （后端配置）     │ （日志级别、Kestrel 端口）      │ 但修改需重启服务              │
├────────────────┼──────────────────────────────┼────────────────────────────┤
│ 环境变量        │ 容器部署时注入的配置              │ 12-Factor 标准、CI/CD 友好   │
│                │ （数据库地址、Redis 连接串）      │ 但没有可视化界面、难以审计     │
└────────────────┴──────────────────────────────┴────────────────────────────┘

优先级：环境变量 > 配置中心 > appsettings.json（和 ASP.NET Core 的配置优先级一致）
```

## 三、API 接口设计

配置中心的后端 API 非常简洁，4 个端点覆盖所有操作：

```
┌──────────────────────────────────────────────────────────────────┐
│                     Runtime Config API                            │
├─────────┬───────────────────────────────┬───────────────────────┤
│ 方法     │ 路径                           │ 说明                   │
├─────────┼───────────────────────────────┼───────────────────────┤
│ GET     │ /api/runtime-config           │ 获取所有配置项列表       │
│ POST    │ /api/runtime-config           │ 新增/更新配置项(Upsert) │
│ DELETE  │ /api/runtime-config/:key      │ 删除指定配置项          │
│ POST    │ /api/runtime-config/reload    │ 强制重载（立即生效）     │
└─────────┴───────────────────────────────┴───────────────────────┘
```

💡 **为什么是 Upsert 而不是分开 Create/Update？**
因为配置的 Key 是唯一标识。如果 Key 已存在就更新，不存在就新建——这和 ASP.NET Core 的 `IConfiguration` 里"后注册的覆盖先注册的"逻辑一致。前端只需要一个 `handleSubmit` 函数，不用判断"是新增还是编辑"来调不同 API。

⚠️ **【易错点】** Upsert 的 Key 不可修改！编辑时 `disabled={!!editItem}`，用户只能修改 value、description 等字段。如果需要换 Key，只能删除后重建。

> 🎯 **教练提问**：为什么后端选择 Upsert 而不是分开 Create 和 Update 两个 API？想想 ASP.NET Core 的 `IConfiguration` 里"后注册的覆盖先注册的"这个设计原则——配置的本质是"同一个 Key 对应一个值"，不存在"创建"和"更新"的概念区别，只有"写入"。

## 四、AES-256 加密存储

敏感配置（密码、AppSecret、Token）不能明文存储在后端文件中。AdminWeb 配置中心使用 AES-256 对称加密：

```
存储流程：

  前端提交 isEncrypted=true 的配置项
       │
       ▼
  后端接收 → AES-256 加密 → 写入 JSON 文件（密文）
       │
       │  读取时：
       ▼
  后端读取 JSON → AES-256 解密 → 返回给前端（脱敏后）
```

⚠️ **【易错点】** AES-256 是**对称加密**，加密和解密用同一把密钥。这和 ASP.NET Core 的 Data Protection API（DPAPI）不同——DPAPI 使用非对称方式保护密钥环。在 AdminWeb 场景中，对称加密足够，因为密钥只存储在服务端。

⚠️ **【易错点】** 加密值在浏览器 DevTools 中也是密文！如果你在 Network 面板查看 `/api/runtime-config` 的响应，加密项的 `value` 字段返回的是脱敏后的 `******`，而不是明文。这是后端在返回数据时就做了脱敏处理，前端只是照着显示。千万不要以为"HTTPS 已经加密了传输，所以不需要 AES-256"——HTTPS 保护的是传输过程，AES-256 保护的是存储安全。

💡 **ASP.NET Core 类比**：

```
配置中心 AES-256 加密    ≈  Data Protection API (Protect/Unprotect)
配置中心的 isEncrypted   ≈  [ProtectedPersonalData] 特性
配置项的 ****** 显示     ≈  日志脱敏 [REDACTED]
```

⚠️ **【设计取舍】** 为什么不直接用 DPAPI？
因为 DPAPI 绑定 Windows 机器密钥，在 Linux 容器部署时不可用。AES-256 跨平台兼容，密钥通过环境变量注入，适合容器化部署。

## 五、热重载轮询机制

配置写入后，后端如何感知变更？有两种机制：

### 5.1 自动轮询（5 秒间隔）

后端每隔 5 秒轮询配置文件变更：

```
时间线：
  t=0s   运维在前端修改 Jwt:Secret
  t=0s   后端 API 接收 → AES-256 加密 → 写入 JSON
  t=0~5s 后端轮询检测到文件变更 → 重新加载 IConfiguration
  t=5s   新配置生效，所有 IOptionsMonitor<T>.OnChange 回调触发
```

⚠️ **【性能陷阱】** 轮询 vs 推送——配置热重载的两种策略：

```
┌──────────────────┬───────────────────────────┬───────────────────────────────┐
│ 策略              │ 当前方案（5 秒轮询）         │ 替代方案（WebSocket/SSE 推送）  │
├──────────────────┼───────────────────────────┼───────────────────────────────┤
│ 实时性            │ 最长 5 秒延迟               │ 毫秒级                         │
│ 实现复杂度        │ 极低（File.GetLastWriteTime）│ 需要维护 WebSocket 连接         │
│ 服务端资源消耗     │ 低（5 秒一次文件检查）       │ 每个客户端一个长连接             │
│ 适用场景          │ 配置变更不频繁（分钟/小时级） │ 配置变更频繁（秒级）             │
└──────────────────┴───────────────────────────┴───────────────────────────────┘

当前 5 秒轮询是合理的：配置变更属于低频操作，5 秒延迟在运维场景中完全可以接受。
如果未来配置变更频率变高（如 A/B 测试动态调整），再考虑升级为推送方案。
```

💡 **ASP.NET Core 类比**：
- 后端轮询 ≈ `builder.Configuration.AddJsonFile("appsettings.json", reloadOnChange: true)` 中的文件监听
- `IOptionsMonitor<T>.OnChange` ≈ 前端的 `useEffect` 依赖变更触发重渲染

> 🎯 **教练提问**：ASP.NET Core 的 `reloadOnChange: true` 底层用的是 `FileSystemWatcher`，这其实是一种推送机制（操作系统通知文件变更），而不是轮询。那 AdminWeb 为什么不用 `FileSystemWatcher` 而用轮询？提示：想一想容器化部署中的文件系统行为。

### 5.2 强制重载（手动触发）

前端提供"强制重载"按钮，调用 `/api/runtime-config/reload` 端点：

```typescript
// 源码位置：pages/config/index.tsx
async function handleReload() {
  setReloading(true)
  try {
    await http.post("/api/runtime-config/reload")
    toast.success("IConfiguration 已强制刷新，新配置立即生效")
    fetchItems()
  } catch (err) {
    toast.error("热重载失败", { description: err instanceof Error ? err.message : String(err) })
  } finally {
    setReloading(false)
  }
}
```

💡 注意 toast 提示里直接写了 `IConfiguration`，这是后端概念。运维人员看到这个提示就知道后端确实执行了 `IConfiguration` 的刷新。

⚠️ **【性能陷阱】** 强制重载是**全量刷新**，不是只刷新单个配置项。在高并发场景下频繁点击"强制重载"可能导致短暂的服务抖动。建议只在紧急配置变更时使用。

## 六、配置影响范围分析

每个配置项都有一个 `impactScope` 字段，描述修改此项后可能带来的影响：

```
┌──────────────────────────────────────────────────────────────────────┐
│                    impactScope 风险等级                                │
├────────────┬─────────────────────────────────────────────────────────┤
│ 低风险      │ "仅影响新会话，已有会话不受影响"                           │
│ 中风险      │ "修改后所有用户 5 秒内生效，可能导致短暂服务中断"            │
│ 高风险      │ "危险：修改后所有已登录用户会话失效，需重新登录"             │
│ 极高风险    │ "全部失败：错误的数据库连接串会导致所有数据操作失败"          │
└────────────┴─────────────────────────────────────────────────────────┘
```

前端用 `isDangerous()` 函数识别高风险配置项，以红色警告样式展示：

```typescript
// 源码位置：pages/config/index.tsx
function isDangerous(text: string): boolean {
  return /危险|失败|所有.*失败|无需认证|全部失败|切勿/.test(text)
}
```

⚠️ **【设计取舍】** 用正则匹配关键词而非结构化等级字段？
因为 `impactScope` 是运维人员手写的自由文本，不是枚举。正则匹配是在"结构化等级"和"自由文本灵活性"之间的折中——大多数情况下够用，极端情况可能漏判。

## 七、配置项数据模型详解

每个配置项包含 10 个字段，与后端概念一一对应：

| 字段 | 类型 | 后端类比 | 说明 |
|------|------|---------|------|
| `key` | `string` | `IConfiguration["Jwt:Secret"]` | 用冒号分隔层级，和 appsettings.json 的 key 一致 |
| `value` | `string` | 配置值明文 | 加密项返回脱敏值，前端显示 `******` |
| `environment` | `string` | `IHostEnvironment.EnvironmentName` | 空=全局，否则按环境隔离 |
| `isEncrypted` | `boolean` | `[ProtectedPersonalData]` 特性 | 标记此值是否加密存储 |
| `description` | `string \| null` | XML 文档注释 | 给运维看的说明，类似代码注释 |
| `groupName` | `string \| null` | appsettings.json 的 JSON 层级 | 前端分组展示用，后端不关心 |
| `groupSort` | `number` | — | 控制分组在 UI 中的显示顺序 |
| `sort` | `number` | — | 控制组内配置项的显示顺序 |
| `impactScope` | `string \| null` | 运维变更评估文档 | 描述修改此项的风险 |
| `updatedAt` | `string` | `LastWriteTime` | 文件最后修改时间 |

⚠️ **【易错点】** `key` 使用冒号 `:` 分隔层级（如 `Jwt:Secret`），而不是点号 `.` 或斜杠 `/`。这是 ASP.NET Core `IConfiguration` 的约定——冒号是配置键的层级分隔符。

⚠️ **【易错点】** 配置值的优先级可能导致意外行为！如果同一个 Key 在多个层级存在（如全局 `Jwt:Secret` 和环境特定 `Jwt:Secret` with `environment=Production`），后端的 `IConfiguration` 会按照"更具体的覆盖更通用的"原则合并。这和 `appsettings.json` + `appsettings.Production.json` 的覆盖逻辑完全一致，但在配置中心界面上可能不明显——用户可能修改了全局配置，却发现生产环境的行为没变，因为环境特定的配置优先级更高。

> 🎯 **教练提问**：如果一个配置项的 `environment` 为空（全局）和 `environment=Production` 同时存在同一个 Key，后端应该用哪个值？这和 ASP.NET Core 中 `appsettings.json` 与 `appsettings.Production.json` 的关系是什么？

## 八、从零到一：配置中心的工作流程

让我们用一次完整的配置变更操作，把前面学的内容串起来：

```
场景：运维发现 JWT 密钥可能泄露，需要紧急更换

步骤 1：打开配置中心
  → 浏览器访问 /config/perm-center
  → React Router 匹配路由，渲染 <ConfigPage serviceBaseUrl="/perm-api" serviceLabel="权限中心" />
  → 组件 mount → fetchItems() → GET /perm-api/api/runtime-config → Vite 代理转发到权限中心后端
  → 返回配置列表，分组展示

步骤 2：定位目标配置
  → 搜索框输入 "Jwt" → filteredGroups 过滤只显示包含 "Jwt" 的配置项
  → 找到 Jwt:Secret，看到 impactScope: "危险：修改后所有已登录用户会话失效，需重新登录"
  → 红色警告文案让运维三思

步骤 3：修改配置
  → 点击编辑按钮 → openEdit() → form.value = ""（加密项清空）
  → 输入新密钥 → 勾选 AES-256 加密 → 点击保存
  → POST /perm-api/api/runtime-config → Vite 代理转发
  → 后端接收新密钥 → AES-256 加密 → 写入 JSON 文件
  → toast 提示"已保存，热重载将在 5 秒内生效"

步骤 4：确认生效
  → 等待 5 秒（后端轮询检测到文件变更 → 重新加载 IConfiguration）
  → 或点击"强制重载" → POST /perm-api/api/runtime-config/reload → 立即生效
  → 新 JWT 密钥已生效，所有旧 Token 失效，用户需重新登录
```

💡 **ASP.NET Core 全链路**：

```
前端 POST → 后端 API 接收 → AES-256.Encrypt(value) → File.WriteAllText(jsonPath)
    → 后端轮询线程 (5s interval) → File.GetLastWriteTime() 变化？
    → IConfigurationRoot.Reload() → IOptionsMonitor<JwtOptions>.OnChange 触发
    → 新密钥注入 JwtBearerOptions → 新签发的 Token 使用新密钥
```

## 九、配置中心与 ASP.NET Core 的全景映射

把本节知识点串成一张全景对照表：

```
┌──────────────────────────────┬──────────────────────────────────────────┐
```

## 🔧 验证步骤

在继续思考题之前，我们用实际操作验证本节的核心知识点：

### 验证 1：构建时配置 vs 运行时配置

```
1. 打开 AdminWeb 项目，找到 .env 或 .env.development 文件
2. 找到 VITE_API_BASE_URL（或类似变量），确认它是构建时注入的
3. 在浏览器 DevTools 控制台输入 import.meta.env，观察输出——这些值在运行时不可修改
4. 对比：打开配置中心页面，修改一个配置项的值，观察 5 秒后后端自动热重载
```

### 验证 2：加密值的传输与显示

```
1. 打开配置中心，找到一个 isEncrypted=true 的配置项
2. 打开浏览器 DevTools → Network 面板
3. 刷新页面，查看 /api/runtime-config 的响应
4. 确认加密项的 value 字段返回的是 "******" 或密文，而非明文
5. 在配置列表中确认加密值显示为遮盖状态
```

### 验证 3：热重载机制

```
1. 修改一个非敏感配置项的值（如 description）
2. 保存后不点击"强制重载"，等待 5 秒
3. 观察后端日志，确认 IConfiguration 已自动刷新
4. 再修改一个配置项，这次立即点击"强制重载"
5. 对比两种方式的生效时间差异
```

### 验证 4：配置值优先级

```
1. 找到一个同时有全局版本和 environment=Production 版本的配置项
2. 分别修改两个版本的值
3. 切换到生产环境后端，确认生效的是环境特定的值
4. 删除环境特定的配置项，确认回退到全局值
```

## 🤔 思考题

### L1 入门（理解 What）
1. 构建时配置和运行时配置的核心区别是什么？各举一个例子。
2. 为什么配置中心用 AES-256 而不是 HTTPS 就够了？
3. 配置中心的 4 个 API 端点分别对应什么操作？

### L2 进阶（推导 What-if）
4. 如果后端的配置文件轮询间隔从 5 秒改为 30 秒，对运维体验有什么影响？如果改为 0.5 秒呢？

### L3 架构（设计 Why）

9. 配置中心的 `impactScope` 是自由文本而非结构化枚举。如果让你重新设计，你会选择哪种方式？权衡是什么？
