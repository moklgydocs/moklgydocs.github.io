## 四种限流算法详解

### FixedWindow（固定窗口）

```
时间轴: |--- 窗口1 ---|--- 窗口2 ---|
请求:   ✓✓✓✓✓ ✗✗✗     ✓✓✓✓✓ ✗✗✗
         ↑ 100个/1s    ↑ 100个/1s
```

每个固定窗口允许 `permitLimit` 个请求。窗口到期后计数器归零。

**边界突发问题**：在窗口 1 的最后 100ms 和窗口 2 的开头 100ms 内，理论上可以涌入 200 个请求（窗口 1 的 100 + 窗口 2 的 100），是限额的 2 倍。

> **🤔 导师提问**：你能想到一个真实场景，窗口边界 2 倍突发会造成实际问题的吗？你会怎么缓解？

**关键参数**：
- `permitLimit`：窗口内允许的最大请求数
- `windowSeconds`：窗口长度（秒）
- `queueLimit`：超限后排队等待的数量，0 = 直接拒绝

**后端类比**：`services.AddRateLimiter(opt => opt.AddFixedWindowLimiter("policy", opt => { opt.PermitLimit = 100; opt.Window = TimeSpan.FromSeconds(1); }))`

### SlidingWindow（滑动窗口）

```
时间轴:    |--- 当前段 ---|
之前段:  ████████░░░░░░░░ (按比例衰减)
当前段:  ████████████████
总和:    ≤ permitLimit
```

窗口不是固定的边界，而是随时间平滑滑动。过期的段按比例衰减（如已过 60% 则只计 40% 的权重），避免了边界突发。

**关键参数**：与 FixedWindow 相同（`permitLimit` + `windowSeconds` + `queueLimit`）。

**vs FixedWindow**：SlidingWindow 更精确但内存占用略高（需要维护多个子窗口的计数器）。

【易错点】SlidingWindow 的 `windowSeconds` 不是"子窗口大小"，而是整个滑动窗口的长度。YARP 内部会将窗口分为若干段来计算。

### TokenBucket（令牌桶）

```
令牌池: ┌─────────────────────┐
        │ ○○○○○○○○○○ (满10个) │  ← 每秒补充 permitLimit/windowSeconds 个
        │ ○○○○○○            │  ← 请求消耗令牌
        └─────────────────────┘
请求:   拿到令牌 → 放行
        没令牌  → 排队(queueLimit) 或拒绝(429)
```

令牌桶的核心思想：
1. 桶的容量 = `permitLimit`，最多存这么多令牌
2. 令牌按 `permitLimit / windowSeconds` 的速率持续补充
3. 每个请求消耗一个令牌
4. 桶空时：排队等待（`queueLimit > 0`）或直接拒绝（`queueLimit = 0`）

**允许短时突发**：如果桶是满的，可以瞬间处理 `permitLimit` 个请求，但之后的补充速率受 `windowSeconds` 限制。

**适用场景**：上传/下载接口——平时流量不大，但偶尔需要突发传输一批数据。

> **🤔 导师提问**：为什么令牌桶比固定窗口更适合上传接口？想想上传的流量模式是什么样的。

### Concurrency（并发限制）

```
请求槽: ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐
        │█│ │█│ │█│ │░│ │░│   permitLimit = 5
        └─┘ └─┘ └─┘ └─┘ └─┘
        活跃   活跃  活跃  空闲  空闲

新请求: 空闲槽 → 放行
        全满  → 排队(queueLimit) 或拒绝(429)
```

限制同时处理的请求数，不看时间窗口。只要当前活跃请求数 < `permitLimit`，新请求就可以进来。

**关键参数**：
- `permitLimit`：最大并发数（等价于信号量大小）
- `windowSeconds`：**忽略**——并发限制不关心时间
- `queueLimit`：等待队列大小

**后端类比**：本质上就是 `SemaphoreSlim(permitLimit, queueLimit)`。第一个参数是最大并发，第二个是等待队列容量。

**适用场景**：耗时接口（报表导出、AI 推理），这些接口的瓶颈不是请求速率，而是同时占用的计算资源。

> **🤔 导师提问**：对于一个 AI 推理端点，什么时候该选 Concurrency 而不是 TokenBucket？它们限制的本质有什么不同？

### 四种算法对比总结

| 维度 | FixedWindow | SlidingWindow | TokenBucket | Concurrency |
|------|------------|--------------|-------------|-------------|
| 限制维度 | 请求速率 | 请求速率 | 请求速率 | 并发数 |
| 突发处理 | 边界可能 2 倍 | 平滑无突发 | 允许短时突发 | 不适用 |
| `windowSeconds` | 有效 | 有效 | 有效（补充速率） | **忽略** |
| `permitLimit` 含义 | 窗口内最大请求数 | 窗口内最大请求数 | 令牌桶容量 | 最大并发数 |
| 内存开销 | 低（1 个计数器） | 中（多段计数器） | 中（令牌计数） | 低（信号量） |
| 典型场景 | 简单 API 限流 | 精确限流 | 上传/下载 | 耗时操作 |

> **后端类比**：限流 ≈ ASP.NET Core 的 `RateLimiterMiddleware`。.NET 7+ 用 `app.UseRateLimiter()` + `AddRateLimiter()` 配置。本系统中限流策略存数据库、前端管理、YARP 运行时执行。

## 限流策略 API 层完整源码

### `src/api/gateway/rate-limit-policies.ts`

```typescript
import { get, post, put, del } from "./http"
import type { RateLimitPolicyDto, CreateRateLimitPolicyRequest, UpdateRateLimitPolicyRequest } from "@/types"

/** 限流策略管理 API，用于管理 API 网关的请求速率限制策略 */
export const rateLimitPoliciesApi = {
  /** 获取所有限流策略列表 */
  getAll: () => get<RateLimitPolicyDto[]>("/api/gateway/rate-limit-policies"),

  /**
   * 根据 ID 获取限流策略详情
   * @param id 策略 ID
   */
  getById: (id: string) => get<RateLimitPolicyDto>(`/api/gateway/rate-limit-policies/${id}`),

  /**
   * 创建新限流策略
   * @param data 限流策略创建请求数据
   */
  create: (data: CreateRateLimitPolicyRequest) => post<RateLimitPolicyDto>("/api/gateway/rate-limit-policies", data),

  /**
   * 更新限流策略
   * @param id 策略 ID
   * @param data 限流策略更新请求数据
   */
  update: (id: string, data: UpdateRateLimitPolicyRequest) => put<RateLimitPolicyDto>(`/api/gateway/rate-limit-policies/${id}`, data),

  /**
   * 删除限流策略
   * @param id 策略 ID
   */
  delete: (id: string) => del<object>(`/api/gateway/rate-limit-policies/${id}`),
}
```

### API 方法汇总

| 方法 | HTTP | 路径 | 返回类型 | 说明 |
|------|------|------|----------|------|
| `getAll()` | GET | `/api/gateway/rate-limit-policies` | `ApiResult<RateLimitPolicyDto[]>` | 获取所有策略 |
| `getById(id)` | GET | `/api/gateway/rate-limit-policies/${id}` | `ApiResult<RateLimitPolicyDto>` | 获取单个策略 |
| `create(data)` | POST | `/api/gateway/rate-limit-policies` | `ApiResult<RateLimitPolicyDto>` | 创建策略 |
| `update(id, data)` | PUT | `/api/gateway/rate-limit-policies/${id}` | `ApiResult<RateLimitPolicyDto>` | 更新策略 |
| `delete(id)` | DELETE | `/api/gateway/rate-limit-policies/${id}` | `ApiResult<object>` | 删除策略 |

### 重点列讲解

**请求上限列**：非 Concurrency 显示 `100 / 1s`，Concurrency 只显示数字 `5`。`tabular-nums` CSS 类让数字等宽对齐，避免表格列宽跳动。

**排队上限列**：`queueLimit === 0` 显示"直接拒绝"——超限立即返回 HTTP 429。**后端类比**：`SemaphoreSlim(5, 0)` 满员直接拒绝。

【易错点】`tabular-nums` 是 CSS `font-variant-numeric: tabular-nums` 的 Tailwind 快捷方式，只对数字生效。如果字体不支持这个特性（如某些中文字体），数字可能仍然不等宽。

### 保存回调

```typescript
if (editingPolicy) {
  const res = await rateLimitPoliciesApi.update(editingPolicy.id, {
    ...data,
    isEnabled: data.isEnabled ?? editingPolicy.isEnabled,
  })
  if (res.success) toast.success("更新成功，重启 Gateway 后参数生效")
} else {
  const res = await rateLimitPoliciesApi.create(data)
  if (res.success) toast.success("创建成功，重启 Gateway 后策略生效")
}
```

- `isEnabled ?? editingPolicy.isEnabled`：空值合并运算符兜底，确保更新时不会意外清除启用状态。
- **"重启 Gateway 后策略生效"**：ASP.NET Core 限流器不支持热更新，需重启。路由/集群通过"发布配置"热重载即可。

【性能陷阱】限流策略的变更需要重启 Gateway 服务才能生效，这意味着在重启窗口期内，新策略不会被应用。对于高频变更的限流配置，应该考虑灰度发布策略，避免影响线上流量。

> **后端类比**：`AddRateLimiter()` 注册的限流器在 `IOptions<RateLimiterOptions>` 中是只读快照。而 YARP 路由配置支持 `IProxyConfigProvider` 变更通知，可以热重载。这是两者的本质区别。

## 限流策略表单完整源码

### `src/pages/gateway/rate-limit-policies/rate-limit-policy-form-dialog.tsx`

```typescript
import { useEffect, useState } from "react"
import type { RateLimitPolicyDto, CreateRateLimitPolicyRequest } from "@/types"

/**
 * 限流策略表单对话框的 Props 接口
 * @property open - 对话框是否打开
 * @property onOpenChange - 对话框打开状态变更回调
 * @property policy - 正在编辑的策略数据，为 null 时表示新建模式
 * @property onSave - 保存回调，接收策略表单数据
 */
interface Props {
    open: boolean
    onOpenChange: (open: boolean) => void
    policy: RateLimitPolicyDto | null
    onSave: (data: CreateRateLimitPolicyRequest) => void
}

/** 限流策略类型选项，包含类型值、显示标签和描述说明 */
const TYPE_OPTIONS = [
    { value: "FixedWindow", label: "FixedWindow — 固定窗口", desc: "在固定时间窗口内限制请求数，窗口边界可能有突发" },
    { value: "SlidingWindow", label: "SlidingWindow — 滑动窗口", desc: "平滑限流，无边界突发问题，内存占用略高" },
    { value: "TokenBucket", label: "TokenBucket — 令牌桶", desc: "允许短时突发，适合上传/下载等接口" },
    { value: "Concurrency", label: "Concurrency — 并发数", desc: "限制同时处理的请求数，适合耗时接口（导出、AI推理）" },
]

/**
 * 限流策略表单对话框组件
 * 用于新建或编辑限流策略，支持配置策略名称、类型、请求上限、时间窗口和排队上限等参数。
 */
export function RateLimitPolicyFormDialog({ open, onOpenChange, policy, onSave }: Props) {
    const [name, setName] = useState("")
    const [type, setType] = useState("FixedWindow")
    const [permitLimit, setPermitLimit] = useState(100)
    const [windowSeconds, setWindowSeconds] = useState(1)
    const [queueLimit, setQueueLimit] = useState(0)
    const [description, setDescription] = useState("")
    const [isEnabled, setIsEnabled] = useState(true)

    // 对话框打开时，根据是否为编辑模式初始化表单数据
    useEffect(() => {
        if (policy) {
            setName(policy.name)
            setType(policy.type)
            setPermitLimit(policy.permitLimit)
            setWindowSeconds(policy.windowSeconds)
            setQueueLimit(policy.queueLimit)
            setDescription(policy.description || "")
            setIsEnabled(policy.isEnabled)
        } else {
            setName("")
            setType("FixedWindow")
            setPermitLimit(100)
            setWindowSeconds(1)
            setQueueLimit(0)
            setDescription("")
            setIsEnabled(true)
        }
    }, [policy, open])

    const handleSubmit = (e: React.FormEvent) => {
        e.preventDefault()
        onSave({
            name,
            type,
            permitLimit,
            windowSeconds,
            queueLimit,
            description: description || undefined,
            isEnabled: isEnabled,
        })
    }

    /** 是否为并发限制类型，并发类型不需要时间窗口 */
    const isConcurrency = type === "Concurrency"
    /** 当前选中的策略类型描述 */
    const selectedType = TYPE_OPTIONS.find(t => t.value === type)

    if (!open) return null

    return (
        <div className="fixed inset-0 z-50 flex items-center justify-center bg-black/50" onClick={() => onOpenChange(false)}>
            <div className="w-full max-w-lg max-h-[90vh] overflow-y-auto rounded-lg bg-background p-6 shadow-lg" onClick={e => e.stopPropagation()}>
                <h2 className="text-lg font-semibold mb-4">{policy ? "编辑限流策略" : "新建限流策略"}</h2>
                <form onSubmit={handleSubmit} className="space-y-4">
                    <div>
                        <label className="text-sm font-medium">策略名称</label>
                        <input
                            value={name}
                            onChange={e => setName(e.target.value)}
                            required
                            placeholder="如：global、upload、auth-strict"
                            className="mt-1 w-full rounded-md border px-3 py-2 text-sm font-mono"
                            disabled={!!policy} // 策略名称创建后不可修改
                        />
                        {policy && <p className="mt-0.5 text-xs text-muted-foreground">策略名称不可修改（路由已引用此名称）</p>}
                        {!policy && <p className="mt-0.5 text-xs text-muted-foreground">路由通过此名称引用限流策略，创建后不可更改</p>}
                    </div>

                    <div>
                        <label className="text-sm font-medium">策略类型</label>
                        <select value={type} onChange={e => setType(e.target.value)} className="mt-1 w-full rounded-md border px-3 py-2 text-sm">
                            {TYPE_OPTIONS.map(t => (
                                <option key={t.value} value={t.value}>{t.label}</option>
                            ))}
                        </select>
                        {/* 显示当前策略类型的说明 */}
                        {selectedType && (
                            <p className="mt-1 text-xs text-muted-foreground">{selectedType.desc}</p>
                        )}
                    </div>

                    <div className="grid grid-cols-3 gap-3">
                        <div>
                            <label className="text-sm font-medium">
                                {isConcurrency ? "最大并发数" : "请求上限"}
                            </label>
                            <input
                                type="number"
                                min={1}
                                value={permitLimit}
                                onChange={e => setPermitLimit(Number(e.target.value))}
                                className="mt-1 w-full rounded-md border px-3 py-2 text-sm"
                            />
                        </div>
                        <div>
                            <label className="text-sm font-medium">
                                {isConcurrency ? "时间窗口（忽略）" : "时间窗口（秒）"}
                            </label>
                            <input
                                type="number"
                                min={1}
                                value={windowSeconds}
                                onChange={e => setWindowSeconds(Number(e.target.value))}
                                disabled={isConcurrency} // 并发限制类型不需要时间窗口
                                className="mt-1 w-full rounded-md border px-3 py-2 text-sm disabled:opacity-40"
                            />
                        </div>
                        <div>
                            <label className="text-sm font-medium">排队上限</label>
                            <input
                                type="number"
                                min={0}
                                value={queueLimit}
                                onChange={e => setQueueLimit(Number(e.target.value))}
                                className="mt-1 w-full rounded-md border px-3 py-2 text-sm"
                            />
                            <p className="mt-0.5 text-xs text-muted-foreground">0 = 超出直接 429</p>
                        </div>
                    </div>

                    <div>
                        <label className="text-sm font-medium">描述</label>
                        <input
                            value={description}
                            onChange={e => setDescription(e.target.value)}
                            placeholder="可选"
                            className="mt-1 w-full rounded-md border px-3 py-2 text-sm"
                        />
                    </div>

                    <label className="flex items-center gap-2 text-sm cursor-pointer">
                        <input type="checkbox" checked={isEnabled} onChange={e => setIsEnabled(e.target.checked)} />
                        启用此策略
                    </label>

                    {/* 提示：策略参数修改后需重启 Gateway 才能生效 */}
                    <div className="rounded-md bg-warning/10 border border-warning/30 px-3 py-2 text-xs text-warning">
                        注意：修改策略参数需重启 Gateway 服务后才能生效（ASP.NET Core 限流器不支持热更新）
                    </div>

                    <div className="flex justify-end gap-2 pt-4">
                        <button type="button" onClick={() => onOpenChange(false)} className="rounded-md border px-4 py-2 text-sm">取消</button>
                        <button type="submit" className="rounded-md bg-primary px-4 py-2 text-sm text-primary-foreground hover:bg-primary/90">保存</button>
                    </div>
                </form>
            </div>
        </div>
    )
}
```

### 策略名称不可修改

```typescript
<input value={name} onChange={e => setName(e.target.value)} required
  placeholder="如：global、upload、auth-strict"
  disabled={!!policy}  // 编辑模式下禁用
/>
```

- `disabled={!!policy}`：编辑模式下名称不可修改。
- **为什么？**：路由通过策略**名称**（非 ID）引用限流策略。改名会让所有引用失效。
- **后端类比**：类似数据库外键引用——被引用的字段不应该 UPDATE。

> **🤔 导师提问**：为什么策略名称创建后不可修改？如果允许改名，什么会出问题？提示：想想 YARP 运行时如何引用限流策略。

```typescript
{policy && <p className="mt-0.5 text-xs text-muted-foreground">策略名称不可修改（路由已引用此名称）</p>}
{!policy && <p className="mt-0.5 text-xs text-muted-foreground">路由通过此名称引用限流策略，创建后不可更改</p>}
```

新建和编辑模式下显示不同的提示文案，让用户理解为什么名称不可改。

### 条件渲染

```typescript
const isConcurrency = type === "Concurrency"

<label>{isConcurrency ? "最大并发数" : "请求上限"}</label>
<input type="number" min={1} value={permitLimit} onChange={...} />

<label>{isConcurrency ? "时间窗口（忽略）" : "时间窗口（秒）"}</label>
<input type="number" min={1} value={windowSeconds} onChange={...}
  disabled={isConcurrency} className="... disabled:opacity-40" />
```

- 标签动态变化：Concurrency 类型下 `permitLimit` 的含义是"最大并发数"而非"请求上限"。
- 时间窗口 disabled 而非隐藏：让用户知道字段存在但不适用，而不是以为漏了配置项。

【易错点】不要把时间窗口字段完全隐藏（`display: none`）。如果隐藏了，用户编辑 Concurrency 策略时不知道 `windowSeconds` 的存在，切换回其他类型时会困惑为什么值是空的。`disabled + opacity` 是更好的 UX 选择。

> **🤔 导师提问**：表单用 `disabled` + 降低透明度来隐藏不适用的字段，而不是 `display:none`。这背后的 UX 理由是什么？什么情况下 `display:none` 反而是更好的选择？

### 排队上限说明

```typescript
<input type="number" min={0} value={queueLimit} onChange={...} />
<p className="...text-muted-foreground">0 = 超出直接 429</p>
```

`queueLimit = 0` 表示不排队，超限直接返回 HTTP 429 Too Many Requests。如果 `queueLimit > 0`，超限请求会排队等待，但排队也可能超时。

### 重启提示

```typescript
<div className="rounded-md bg-warning/10 border border-warning/30 px-3 py-2 text-xs text-warning">
  注意：修改策略参数需重启 Gateway 服务后才能生效（ASP.NET Core 限流器不支持热更新）
```

【设计取舍】为什么重启而不是热重载？ASP.NET Core 的 `RateLimiterOptions` 在服务注册时被读取为只读快照，后续修改不会被运行时感知。要使新策略生效，必须重启整个进程。这是框架层面的限制，不是我们系统的设计问题。

这个提示用 `bg-warning/10 + border-warning/30 + text-warning` 的黄色配色，视觉上醒目但不刺眼，适合"警告但不紧急"的场景。

## 限流策略列表页完整源码

### `src/pages/gateway/rate-limit-policies/index.tsx`

```typescript
import { useEffect, useState, useCallback } from "react"
import { PageToolbar, ToolbarButton } from "@/components/shared/page-toolbar"
import { AgTable, type AgColumn } from "@/components/shared/ag-table"
import { ConfirmDialog } from "@/components/shared/confirm-dialog"
import { Button } from "@/components/ui/button"
import { rateLimitPoliciesApi } from "@/api/gateway/rate-limit-policies"
import { toast } from "sonner"
import { Plus, RefreshCw } from "lucide-react"
import type { RateLimitPolicyDto, CreateRateLimitPolicyRequest } from "@/types"
import { RateLimitPolicyFormDialog } from "./rate-limit-policy-form-dialog"

/** 限流策略类型对应的徽章样式映射 */
const TYPE_BADGE: Record<string, { label: string; color: string }> = {
  FixedWindow:  { label: "固定窗口", color: "bg-info/10 text-info" },
  SlidingWindow:{ label: "滑动窗口", color: "bg-primary/10 text-primary" },
  TokenBucket:  { label: "令牌桶",   color: "bg-orange-100 text-orange-700" },
  Concurrency:  { label: "并发限制", color: "bg-pink-100 text-pink-700" },
}

/**
 * 限流策略管理页面
 * 展示限流策略列表，支持新建、编辑和删除策略。
 * 策略类型包括固定窗口、滑动窗口、令牌桶和并发限制。
 */
export default function RateLimitPoliciesPage() {
  /** 限流策略列表数据 */
  const [policies, setPolicies] = useState<RateLimitPolicyDto[]>([])
  /** 表格加载状态 */
  const [loading, setLoading] = useState(false)
  /** 新建/编辑对话框是否打开 */
  const [dialogOpen, setDialogOpen] = useState(false)
  /** 当前正在编辑的策略，为 null 时表示新建模式 */
  const [editingPolicy, setEditingPolicy] = useState<RateLimitPolicyDto | null>(null)
  /** 待删除的策略，非 null 时显示删除确认框 */
  const [deleteTarget, setDeleteTarget] = useState<RateLimitPolicyDto | null>(null)
  /** 删除操作进行中 */
  const [deleting, setDeleting] = useState(false)

  /** 获取限流策略列表 */
  const fetchPolicies = useCallback(async () => {
    setLoading(true)
    try {
      const res = await rateLimitPoliciesApi.getAll()
      if (res.success) setPolicies(res.data ?? [])
    } catch {
      toast.error("获取限流策略失败")
    } finally {
      setLoading(false)
    }
  }, [])

  useEffect(() => { fetchPolicies() }, [fetchPolicies])

  /** 打开新建策略对话框 */
  const handleCreate = () => {
    setEditingPolicy(null)
    setDialogOpen(true)
  }

  /** 打开编辑策略对话框 */
  const handleEdit = (policy: RateLimitPolicyDto) => {
    setEditingPolicy(policy)
    setDialogOpen(true)
  }

  /** 确认删除策略 */
  const handleDeleteConfirm = async () => {
    if (!deleteTarget) return
    setDeleting(true)
    try {
      const res = await rateLimitPoliciesApi.delete(deleteTarget.id)
      if (res.success) {
        toast.success("删除成功")
        setDeleteTarget(null)
        await fetchPolicies()
      } else {
        toast.error(res.message)
      }
    } catch {
      toast.error("删除失败")
    } finally {
      setDeleting(false)
    }
  }

  /** 保存策略（新建或更新） */
  const handleSave = async (data: CreateRateLimitPolicyRequest) => {
    try {
      if (editingPolicy) {
        const res = await rateLimitPoliciesApi.update(editingPolicy.id, {
          ...data,
          isEnabled: data.isEnabled ?? editingPolicy.isEnabled,
        })
        if (res.success) {
          toast.success("更新成功，重启 Gateway 后参数生效")
          setDialogOpen(false)
          await fetchPolicies()
        } else {
          toast.error(res.message)
        }
      } else {
        const res = await rateLimitPoliciesApi.create(data)
        if (res.success) {
          toast.success("创建成功，重启 Gateway 后策略生效")
          setDialogOpen(false)
          await fetchPolicies()
        } else {
          toast.error(res.message)
        }
      }
    } catch {
      toast.error("保存失败")
    }
  }

  // ... columns 定义（见上文） ...

  return (
    <div className="flex flex-col h-full">
      <PageToolbar
        title="限流策略"
        actions={
          <>
            <ToolbarButton icon={Plus} variant="primary" onClick={handleCreate}>
              新建策略
            </ToolbarButton>
            <ToolbarButton icon={RefreshCw} onClick={fetchPolicies}>
              刷新
            </ToolbarButton>
          </>
        }
      />

      <AgTable
        columns={columns}
        data={policies}
        total={policies.length}
        loading={loading}
        rowKey="id"
      />

      <RateLimitPolicyFormDialog
        open={dialogOpen}
        onOpenChange={setDialogOpen}
        policy={editingPolicy}
        onSave={handleSave}
      />

      <ConfirmDialog
        open={!!deleteTarget}
        onOpenChange={(open) => { if (!open) setDeleteTarget(null) }}
        title="删除限流策略"
        description={`确定删除策略 "${deleteTarget?.name}" 吗？注意：如果有路由引用此策略，删除将被拒绝。`}
        onConfirm={handleDeleteConfirm}
        loading={deleting}
        variant="destructive"
        type="warning"
        confirmLabel="删除"
      />
    </div>
  )
}
```

### 页面组件结构与集群页面对比

限流策略页面和集群页面的结构几乎一致——相同的 6 个 useState、相同的 CRUD 处理器模式、相同的 ConfirmDialog。**这不是巧合，而是 React CRUD 页面的标准模板**。

**与集群页面的关键差异**：

| 差异点 | 集群页面 | 限流策略页面 |
|--------|---------|-------------|
| 删除确认框 `type` | `"danger"` | `"warning"` — 因为有外键检查 |
| 删除确认文案 | 简单确认 | 额外提示"有路由引用则拒绝" |
| 保存成功提示 | "创建/更新成功" | 额外提醒"重启 Gateway 后生效" |
| `handleSave` | 直接传 `data` | `isEnabled: data.isEnabled ?? editingPolicy.isEnabled` 空值合并兜底 |
| TYPE_BADGE | 无 | 4 种类型各有配色徽章 |

💡 **后端类比**：这就像 EF Core 的 `Repository<T>` 模式——每个实体的 CRUD 逻辑 90% 相同，只有 10% 是业务差异。理解了这个模板，以后写任何 CRUD 页面只需要关注那 10% 的差异。

## 踩坑提醒

1. **限流策略修改后需重启 Gateway 才能生效**：ASP.NET Core 的 `RateLimiterOptions` 在注册后是只读快照，不支持热更新。运维人员可能以为点"发布配置"就够了，但限流策略的变更必须重启整个进程。
2. **策略名称创建后不可修改**：路由通过策略**名称**（非 ID）引用限流策略。改名会让所有引用失效，类似数据库外键引用的字段不应该 UPDATE。
3. **时间窗口字段不要用 `display:none` 隐藏**：Concurrency 类型下时间窗口不适用，但用 `disabled + opacity` 而非完全隐藏。如果隐藏了，用户切换回其他类型时会困惑为什么值是空的。
