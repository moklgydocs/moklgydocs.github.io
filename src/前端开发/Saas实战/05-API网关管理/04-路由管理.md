# 路由管理

[← 上一篇：集群管理](03-集群管理.md) | [下一篇：限流策略 →](05-限流策略.md)

---

> **这一步解决什么问题？** 上一步我们搭好了集群管理——定义了"请求发到哪"。现在要实现**路由管理**——定义"哪些请求走哪条路"。在 YARP 中，Route 是入口：请求先匹配路由规则（路径、方法、主机），再转发到对应集群。没有路由，网关不知道怎么分发请求。

## 前置知识

- 01 篇 YARP 网关基础：Route → Cluster → Destination 三层结构
- 03 篇集群管理：`ClusterDto` 类型定义、集群 CRUD API 的使用方式
- ASP.NET Core 路由基础：`[Route]`、`app.MapWhen()`、`app.UseProxy()` 的概念

> **后端类比**：Route ≈ ASP.NET Core 的 `app.MapWhen()` + `app.UseProxy()`，定义匹配条件 + 转发目标。Nginx 中对应 `location /api/auth { proxy_pass http://authserver; }`。

## 路由 API 层

### `src/api/gateway/routes.ts`

```typescript
import { get, post, put, del } from "./http"
import type { RouteDto, CreateRouteRequest, UpdateRouteRequest } from "@/types"

export const routesApi = {
  getAll: () => get<RouteDto[]>("/api/gateway/routes"),
  getById: (id: string) => get<RouteDto>(`/api/gateway/routes/${id}`),
  create: (data: CreateRouteRequest) => post<RouteDto>("/api/gateway/routes", data),
  update: (id: string, data: UpdateRouteRequest) => put<RouteDto>(`/api/gateway/routes/${id}`, data),
  delete: (id: string) => del<object>(`/api/gateway/routes/${id}`),
}
```

标准 CRUD 五件套，和 `clustersApi` 结构一致。

> **🤔 导师提问**：`routesApi` 和 `clustersApi` 结构几乎一样——都是 `getAll / getById / create / update / delete` 五件套。类比后端，这就像 EF Core 的 `Repository<T>` 泛型模式。既然如此，为什么不写一个通用的 `createCrudApi(baseUrl)` 工厂函数来生成这些 API？什么情况下差异化比通用化更重要？

## 路由列表页

### `src/pages/gateway/routes/index.tsx`

### 并行加载路由 + 集群

```typescript
const fetchData = useCallback(async () => {
  setLoading(true)
  try {
    const [routesRes, clustersRes] = await Promise.all([
      routesApi.getAll(),
      clustersApi.getAll(),
    ])
    if (routesRes.success) setRoutes(routesRes.data ?? [])
    if (clustersRes.success) setClusters(clustersRes.data ?? [])
  } catch {
    toast.error("获取数据失败")
  } finally {
    setLoading(false)
  }
}, [])
```

- **`Promise.all`**：并行发两个请求。后端类比：`await Task.WhenAll(routingTask, clusterTask)`。
- **为什么需要集群列表？**：路由表单的"目标集群"下拉框需要数据源，通过 Props 传给 `RouteFormDialog`。

## 路由表单对话框

### `src/pages/gateway/routes/route-form-dialog.tsx`

这是整个网关模块最复杂的表单，需配置：匹配路径、目标集群、限流策略、优先级、路径转换规则。

### 动态加载限流策略

```typescript
useEffect(() => {
  if (!open) return
  rateLimitPoliciesApi.getAll().then(res => {
    if (res.success) setAvailablePolicies((res.data ?? []).filter(p => p.isEnabled))
  }).catch(() => {
    // 加载失败时保持空列表，不影响主流程
  })
}, [open])
```

- 对话框打开时加载限流策略，只展示已启用的。
- **后端类比**：`OnInitializedAsync` 中加载下拉数据源，失败只影响下拉选项，不阻止页面渲染。

### 限流策略选择

```typescript
<select value={rateLimiterPolicy} onChange={e => setRateLimiterPolicy(e.target.value)}>
  <option value="">无限流</option>
  {availablePolicies.map(p => (
    <option key={p.id} value={p.name}>
      {p.name}
      {p.type !== "Concurrency"
        ? ` (${p.permitLimit}/${p.windowSeconds}s)`
        : ` (并发 ${p.permitLimit})`}
    </option>
  ))}
  {rateLimiterPolicy && !availablePolicies.find(p => p.name === rateLimiterPolicy) && (
    <option value={rateLimiterPolicy}>{rateLimiterPolicy} (已禁用)</option>
  )}
</select>
```

- **`p.name` 作为 value**：路由通过策略名称（非 ID）引用限流策略，这是 YARP 的设计。类比 ASP.NET Core 的 `[EnableRateLimiting("policy-name")]`。
- **已禁用策略的占位项**：编辑时关联策略已被禁用，仍显示占位项标记"(已禁用)"，避免下拉值为空。

### 路径转换规则

```typescript
const addTransform = () => {
  setTransforms(prev => [...prev, { ...emptyTransform, order: prev.length }])
}

const updateTransform = (index: number, field: keyof RouteTransformDto, value: string | number) => {
  setTransforms(prev => prev.map((t, i) => i === index ? { ...t, [field]: value } : t))
}

const removeTransform = (index: number) => {
  setTransforms(prev => prev.filter((_, i) => i !== index))
}
```

和集群管理中的 Destination 列表一样，Transforms 是动态增删的子表单：

```typescript
{transforms.map((t, i) => (
  <div key={i} className="flex gap-2 items-center">
    <select value={t.type} onChange={e => updateTransform(i, "type", e.target.value)}>
      <option value="">选择类型</option>
      <option value="PathRemovePrefix">PathRemovePrefix</option>
      <option value="PathPrefix">PathPrefix</option>
      <option value="PathPattern">PathPattern</option>
      <option value="RequestHeaderOriginalHost">RequestHeaderOriginalHost</option>
    </select>
    <input value={t.value} onChange={e => updateTransform(i, "value", e.target.value)}
      placeholder="值，如 /api/auth" />
    <button type="button" onClick={() => removeTransform(i)}>删除</button>
  </div>
))}
```

**四种转换类型**：

| 类型 | 作用 | 类比 |
|------|------|------|
| `PathRemovePrefix` | 转发前去掉路径前缀 | `app.UsePathBase()` 的反向操作 |
| `PathPrefix` | 转发前添加路径前缀 | `app.UseRewriter()` 添加前缀 |
| `PathPattern` | 用模板重写路径 | `[Route("{controller}/{action}")]` |
| `RequestHeaderOriginalHost` | 保留原始 Host 头 | `ForwardedHeaders` 中间件 |

【易错点】`PathRemovePrefix` 是最常用的转换类型，因为它可以去掉匹配路径的前缀再转发。比如路由匹配 `/api/auth/{**catch}`，转发前去掉 `/api/auth` 前缀，后端收到的请求路径就是 `/{**catch}` 部分。如果忘记配置转换，后端会收到完整的前缀路径，可能导致 404。

### 提交表单

```typescript
const handleSubmit = (e: React.FormEvent) => {
  e.preventDefault()
  onSave({
    routeId,
    clusterId,
    matchPath,
    matchMethods: matchMethods || undefined,
    rateLimiterPolicy: rateLimiterPolicy || undefined,
    order,
    isEnabled,
    description: description || undefined,
    transforms: transforms.filter(t => t.type && t.value),
  })
}
```

- `|| undefined`：空字符串转 `undefined`，不会把 `""` 发给后端。
- `.filter(t => t.type && t.value)`：只提交完整的转换规则。

> **🤔 导师提问**：路由表单中限流策略用 `p.name` 而非 `p.id` 作为下拉值，而 `clusterId` 也是用逻辑标识而非数据库 ID。YARP 运行时通过名称/标识做关联，而不是通过数据库自增主键——这种设计选择的好处是什么？如果用 ID 关联会怎样？

## 踩坑提醒

1. **`Promise.all` 并行加载失败处理**：路由列表页用 `Promise.all` 并行加载路由和集群数据。如果其中一个请求失败，整个 `catch` 分支会触发，两个数据源都会丢失。如果需要更健壮的错误处理，应该改用 `Promise.allSettled`，让成功的请求仍然展示数据。
2. **已禁用限流策略的占位项**：编辑路由时，如果关联的限流策略已被禁用，下拉框中仍需显示该策略（标记"已禁用"），否则下拉框值为空，用户会以为没有选择过策略。缺少这个占位项会导致保存时 `rateLimiterPolicy` 被清空，路由丢失限流配置。
3. **路径转换规则过滤**：提交表单时 `.filter(t => t.type && t.value)` 会丢弃不完整的转换规则。如果用户选了类型但没填值，这条规则会被静默丢弃——不会报错，但用户可能困惑"为什么我加的转换规则没生效"。可以考虑在前端做校验，要求类型和值都填写后才允许提交。

## 验证步骤

1. 访问 `http://localhost:3000/gateway/routes`，确认路由列表正常显示，每条路由显示匹配路径、目标集群、优先级和状态
2. 点击"新建路由"，填写路由标识（如 `auth-route`）、匹配路径（如 `/api/auth/{**catch-all}`）、选择目标集群，点击保存
3. 确认列表新行显示路由标识、匹配路径用 `<code>` 等宽标签渲染、目标集群名称正确
4. 编辑该路由，添加一条 `PathRemovePrefix` 转换规则，值为 `/api/auth`，保存后确认转换列显示 `PathRemovePrefix: /api/auth`
5. 测试限流策略选择：选择一个已启用的策略，保存后再编辑，确认下拉框回显正确的策略名称
6. 测试已禁用策略：禁用一个被路由引用的限流策略，编辑该路由，确认下拉框显示策略名 + "(已禁用)"
