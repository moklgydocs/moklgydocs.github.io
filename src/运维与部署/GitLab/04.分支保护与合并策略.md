# 分支保护与合并策略

不保护分支，任何人都能往 main 推代码，哪天手滑就炸了。MR 审核 + 分支保护 = 代码质量的最后防线。

---

## 分支保护

### 配置入口

```
项目 → Settings → Repository → Protected branches
```

### 推荐配置

| 分支 | 谁能 Push | 谁能 Merge | 允许 Force Push |
|------|----------|-----------|----------------|
| `main` | No one | Maintainers | ❌ |
| `develop` | Maintainers | Developers + Maintainers | ❌ |

```
main 分支：
  Allowed to merge: Maintainers
  Allowed to push and merge: No one
  → 只能通过 MR 合并，不能直接 push

develop 分支：
  Allowed to merge: Developers + Maintainers
  Allowed to push and merge: Maintainers
  → 开发者通过 MR 合并，负责人可以直接 push
```

## Merge Request（MR）流程

### 完整流程

```
1. 开发者在 feature 分支写代码
2. push 到远程
3. 创建 MR（feature → develop）
4. 自动触发 CI 流水线
5. 指定审查人 Review 代码
6. 审查通过 + CI 通过 → 合并
7. 自动删除 feature 分支
```

### 创建 MR

```
GitLab → 项目 → Merge Requests → New merge request

Source branch: feature/user-management
Target branch: develop

Title: feat: 用户管理模块
Description:
  ## 改了什么
  - 添加用户 CRUD 接口
  - 添加角色关联

  ## 测试了什么
  - 单元测试通过
  - Swagger 手动测试通过

Assignee: 自己
Reviewer: 技术负责人
Labels: feature

☑ Delete source branch when merge request is accepted
☑ Squash commits when merge request is accepted
```

## 合并策略

### 三种合并方式

```
1. Merge commit（默认）
   保留所有提交历史，创建一个合并提交
   → 历史完整但可能杂乱

2. Squash and merge（推荐功能分支）
   把 feature 分支的多次提交压成一个
   → develop 历史干净

3. Fast-forward merge
   不创建合并提交，要求分支是最新的
   → 最干净但要求严格
```

### 推荐配置

```
项目 → Settings → Merge requests

Merge method:
  → ✅ Merge commit with semi-linear history
     （要求分支 rebase 到最新，再合并）

Squash commits when merging:
  → Encourage（鼓励但不强制）

Merge checks:
  → ✅ Pipelines must succeed（CI 必须通过）
  → ✅ All discussions must be resolved（讨论必须解决）
```

## 审查规则

### Approval Rules

```
项目 → Settings → Merge requests → Approval rules

Rule: 至少 1 人审批
  Approvals required: 1
  Eligible approvers: 项目 Maintainers

# 也可以设置多条规则
Rule: 后端审批
  Approvals required: 1
  Eligible approvers: 后端组成员
```

### Code Review 要点

```
审查关注点：
  ✅ 逻辑正确性 —— 业务逻辑对不对
  ✅ 异常处理 —— 边界情况考虑了吗
  ✅ 安全性 —— SQL注入、XSS、密码硬编码
  ✅ 性能 —— N+1查询、大量内存分配
  ✅ 可维护性 —— 命名、注释、函数长度
  ❌ 不纠结代码风格 —— 交给 linter 自动化
```

### Review 操作

```
在 MR 页面的 Changes tab：
  → 选中代码行 → 添加评论
  → 建议修改 → 用 suggestion 代码块
  → 审查完毕 → Approve（通过）或 Request changes（打回）
```

## CI 通过才能合并

```
Settings → Merge requests → Merge checks
→ ✅ Pipelines must succeed

效果：MR 的 CI 流水线没跑过，合并按钮是灰色的
```

配合 `.gitlab-ci.yml`（如果使用 GitLab CI）或 Jenkins Webhook 回写状态。

---

## 推荐的项目设置总结

```
分支保护：
  main     → 只能通过 MR 合并
  develop  → Maintainer 可直接 push，Developer 走 MR

合并策略：
  → Semi-linear history
  → 鼓励 Squash
  → CI 必须通过
  → 讨论必须解决

审批规则：
  → 至少 1 人 Approve

自动化：
  → 合并后自动删除源分支
  → 合并后自动触发部署

命名规范：
  → feature/* → develop → main
  → bugfix/* → develop
  → hotfix/* → main + develop
```

## 速查

| 目标 | 配置位置 |
|------|---------|
| 禁止直接 push main | Settings → Repository → Protected branches |
| CI 必须通过才能合并 | Settings → Merge requests → Merge checks |
| 需要审批才能合并 | Settings → Merge requests → Approval rules |
| 合并后自动删源分支 | MR 创建时勾选 / Settings → Merge requests |
| Squash 提交 | Settings → Merge requests → Squash commits |
