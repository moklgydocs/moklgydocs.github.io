# Git 工作流

团队协作不定规矩，代码仓库就是灾难。选对分支策略，少踩 90% 的坑。

---

## 三种主流工作流

```
工作流          复杂度   适合           核心思路
──────────────────────────────────────────────
GitFlow         高      版本发布制      多长期分支，严格流程
GitHub Flow     低      持续部署        只有 main + feature
Trunk-Based     中      大团队/CI强     主干开发，短命分支
```

---

## GitFlow（适合版本发布）

```
main ──────●──────────────●──────────── 生产版本
           ↑              ↑
release ── ├── v1.0 ──────┤── v2.0 ──  发布分支
           ↑              ↑
develop ───●──●──●──●──●──●──●──●───── 开发主线
              ↑     ↑        ↑
feature   feat/A  feat/B  feat/C       功能分支
```

### 分支说明

| 分支 | 生命周期 | 说明 |
|------|---------|------|
| `main` | 永久 | 生产代码，每个提交都是一个发布版本 |
| `develop` | 永久 | 开发主线，功能在这里集成 |
| `feature/*` | 临时 | 功能开发，完成后合并到 develop |
| `release/*` | 临时 | 发布准备，测试修bug，完成后合并到 main + develop |
| `hotfix/*` | 临时 | 紧急修复，从 main 拉出，修完合并到 main + develop |

### 完整流程

```bash
# 1. 开发新功能
git checkout develop
git checkout -b feature/user-management
# ... 开发 ...
git add . && git commit -m "feat: 用户管理模块"

# 2. 功能完成，合并到 develop
git checkout develop
git merge --no-ff feature/user-management
git branch -d feature/user-management

# 3. 准备发布
git checkout develop
git checkout -b release/v1.0
# ... 测试、修bug ...
git commit -m "fix: 修复登录验证问题"

# 4. 发布
git checkout main
git merge --no-ff release/v1.0
git tag -a v1.0 -m "Release v1.0"

# 把 release 的修复同步回 develop
git checkout develop
git merge --no-ff release/v1.0
git branch -d release/v1.0

# 5. 紧急修复
git checkout main
git checkout -b hotfix/login-crash
# ... 修复 ...
git checkout main
git merge --no-ff hotfix/login-crash
git tag -a v1.0.1 -m "Hotfix: login crash"
git checkout develop
git merge --no-ff hotfix/login-crash
git branch -d hotfix/login-crash
```

**适合**：有明确版本号的产品（v1.0、v2.0）、客户端应用、需要同时维护多个版本。

## GitHub Flow（适合持续部署）

```
main ──────●──────●──────●──────●──── 始终可部署
           ↑      ↑      ↑      ↑
feature  feat/A feat/B feat/C feat/D  短命分支
```

### 规则

1. `main` 始终可部署
2. 新功能从 `main` 拉分支
3. 频繁提交，推到远程
4. 创建 Merge Request（MR）
5. 代码审查通过后合并到 `main`
6. 合并后立即部署

```bash
# 1. 拉功能分支
git checkout main
git checkout -b feature/add-export

# 2. 开发并推送
git add . && git commit -m "feat: 添加导出功能"
git push origin feature/add-export

# 3. 在 GitLab 创建 MR → 代码审查 → 合并
# 4. CI/CD 自动部署
```

**适合**：Web 应用、SaaS、能做持续部署的团队。

## 我们的推荐：简化 GitFlow

大多数中小团队不需要完整 GitFlow，简化版就够用：

```
main ──────●──────────────●──────── 生产
           ↑              ↑
develop ───●──●──●──●──●──●──●──── 开发（日常在这里）
              ↑     ↑        ↑
feature    feat/A feat/B  feat/C   功能分支
```

```
只用 3 种分支：
  main      → 生产环境代码
  develop   → 开发环境代码
  feature/* → 个人功能分支

流程：
  feature → MR → develop → 测试通过 → MR → main → 部署
```

## 分支命名规范

```bash
# 功能
feature/user-management
feature/export-excel
feature/JIRA-123-add-login

# 修复
bugfix/login-validation
bugfix/JIRA-456-fix-timeout

# 紧急修复
hotfix/critical-data-loss

# 发布
release/v1.0
release/v2.0-rc1
```

---

## 提交信息规范

```bash
# 格式: <type>: <description>
feat: 添加用户导出功能
fix: 修复登录超时问题
docs: 更新 API 文档
style: 格式化代码
refactor: 重构订单服务
test: 添加用户服务单元测试
chore: 更新依赖包版本

# 带作用域
feat(user): 添加角色管理功能
fix(order): 修复金额计算精度问题
```

## 速查

| 团队规模 | 部署频率 | 推荐工作流 |
|---------|---------|-----------|
| 1-3人 | 随时部署 | GitHub Flow |
| 3-10人 | 按版本发布 | 简化 GitFlow |
| 10人+ | 需要多环境 | 完整 GitFlow |
| 大厂 | 天级部署 | Trunk-Based |
