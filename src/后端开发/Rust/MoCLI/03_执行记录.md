### 遇到的借用检查器错误 #1：`AggKey` 不能 derive `Copy`

**问题**：最初想让 `AggKey` 实现 `Copy`，这样 HashMap 操作更方便：

```rust
#[derive(Copy, Clone, Hash, Eq, PartialEq)]
pub struct AggKey {
    level: LogLevel,
    message_prefix: String,   // ← 问题在这
}
```

**编译错误**：

```
error[E0204]: the trait `Copy` cannot be implemented for this type
  --> src/types.rs:XX:XX
   |
XX |     message_prefix: String,
   |     ---------------------- this field does not implement `Copy`
```

**根因**：`String` 拥有堆内存，实现了 `Drop`，因此无法实现 `Copy`（`Copy` 要求复制操作是按位复制且无析构）。C# 中没有这个限制，因为 `string` 是引用类型，复制只是复制引用（不复制堆数据），由 GC 管理生命周期。

**解法**：去掉 `Copy`，改用 `Clone`：

```rust
#[derive(Debug, Clone, Hash, Eq, PartialEq)]  // 没有 Copy
pub struct AggKey {
    pub level: LogLevel,
    pub message_prefix: String,
}
```

HashMap `entry()` API 接受 `&AggKey`（引用），不需要 `Copy`。

**C# 类比**：

```csharp
// C# — 引用类型作 Dictionary Key 是正常的
record AggKey(LogLevel Level, string Message);
var map = new Dictionary<AggKey, int>();
```

```rust
// Rust — 需要 Clone，但 HashMap.entry() 用引用，很少需要真正克隆
let key = AggKey::from_entry(&entry);
map.entry(key)  // key 被 move 进 entry()，不需要 Clone
   .or_insert(0);
```

### 遇到的借用检查器错误 #2：`LogLevel` serde 反序列化

**问题**：JSON 日志中 `level` 字段值是 `"ERROR"`（全大写），而 serde 默认按 Rust 枚举变体名匹配（`Error`、`Warn`…）。

```rust
#[derive(Deserialize)]
pub enum LogLevel {
    Error,  // serde 期望 JSON 中是 "Error"，但实际是 "ERROR"
    Warn,
    Info,
    Debug,
}
```

**运行现象**：解析时 `"ERROR"` 会 -> `ParseError::InvalidJson`，所有日志都解析失败。

**解法**：加 `#[serde(rename_all = "UPPERCASE")]`：

```rust
#[derive(Deserialize, Serialize)]
#[serde(rename_all = "UPPERCASE")]  // "ERROR" ↔ Error, "WARN" ↔ Warn
pub enum LogLevel {
    Error,
    Warn,
    Info,
    Debug,
}
```

**额外问题**：部分日志用 `"warn"`（小写）或 `"Warning"`（混合大小写）。serde 的 `rename_all` 不做 case-insensitive 匹配，因此在 CLI 层（`parse_level` 函数）用 `to_ascii_uppercase()` 统一转换，再传给 filter。

## M2：解析器 + 过滤器

### ADR-01：解析失败策略——跳过 vs 终止

**背景**：生产日志文件中可能含有非 JSON 行（如应用崩溃时写入的 stacktrace、或 syslog 格式混入）。

**决策**：解析失败**跳过**该行并计数，不终止程序。

**理由**：
- AC 明确要求"解析失败时跳过并计数，最后报告解析失败行数"
- 对应 `01_立项.md` 风险矩阵中的"日志格式非标准 JSON"风险缓解措施
- 实际场景：1GB 文件中有 100 行非 JSON，如果终止程序则损失全部分析结果

**实现**：`runner.rs` 中用 `match parse_log_line(...)` 处理 `Err`：

```rust
let entry = match parse_log_line(&line, line_num) {
    Ok(e) => e,
    Err(_) => {
        parse_errors += 1;  // 计入错误计数
        continue;           // 跳过这行，继续下一行
    }
};
```

### 遇到的借用检查器错误 #3：`filter.rs` 中的引用生命周期

**问题**：第一版 `passes_filter` 尝试返回引用：

```rust
// ❌ 错误写法：试图从函数参数中返回引用
fn passes_filter<'a>(entry: &'a LogEntry, filter: &FilterArgs) -> Option<&'a LogEntry> {
    if condition { Some(entry) } else { None }
}
```

编译通过，但调用方难以使用：需要维持对原 `entries` 的不可变借用，而后续代码需要消费 `entries`。

**解法**：改为返回 `bool`，调用方自己决定是否保留：

```rust
// ✅ 正确写法：纯判断函数，返回 bool
pub fn passes_filter(entry: &LogEntry, filter: &FilterArgs) -> bool {
    ...
}

// 调用方：filter 成立后 push 到 Vec（获得所有权）
if passes_filter(&entry, &config.filter) {
    matched.push(entry);  // entry 被 move 进 Vec
}
```

**C# 类比**：C# 的 LINQ `.Where(e => condition(e))` 返回 `IEnumerable`（惰性），底层类似返回 `bool` 的判断函数。Rust 也可以用 Iterator 链（`.filter(|e| passes_filter(e, &filter))`），但流式读取场景中我们需要手动控制内存（只 push 通过过滤的 entry），所以选择显式 `push`。

### 遇到的借用检查器错误 #4：rayon `fold` + `reduce` 模式

**问题**：第一版尝试用 `Mutex<HashMap>` 实现并行聚合：

```rust
// ❌ 性能陷阱写法
let map = Mutex::new(HashMap::new());
entries.par_iter().for_each(|entry| {
    let mut m = map.lock().unwrap();  // 每条日志都争锁 → 实际是串行
    m.entry(key).and_modify(...);
});
```

`cargo clippy` 会报 `await_holding_lock` 警告（workspace lint 配置了 deny），提示全局锁是性能反模式。

**【Arch】指导**：正确做法是 `fold`（各线程局部 HashMap）+ `reduce`（合并），零锁竞争：

```rust
// ✅ rayon fold + reduce：无锁并行
entries
    .into_par_iter()
    .fold(
        HashMap::new,               // 工厂函数：每线程独立 HashMap
        |mut local, entry| {        // local 是本线程私有的，无需锁
            local.entry(key).or_insert_with(...);
            local
        }
    )
    .reduce(
        HashMap::new,               // 初始空 HashMap
        |mut a, b| {                // 合并两个线程的结果
            for (k, v) in b { a.entry(k).or_insert_with(...); }
            a
        }
    )
```

**性能原理**：

```
rayon 线程池（8核）:
    Thread 1: 处理 1/8 数据 → local_map_1
    Thread 2: 处理 1/8 数据 → local_map_2
    ...
    Thread 8: 处理 1/8 数据 → local_map_8
    reduce: local_map_1 + local_map_2 → merge_12
            local_map_3 + local_map_4 → merge_34
            ...
            merge_12 + merge_34 + ... → final_map
```

这是 MapReduce 模型在单机多核上的实现，benchmark 验证在 8 核机器上达到 5-6x 加速（I/O 是瓶颈，纯 CPU 计算部分达到 7-8x）。

### ADR-02：并行策略切换阈值——100MB

**背景**：rayon 并行有固定开销（线程池初始化、数据分片、结果合并），对小文件可能反而比单线程慢。

**决策**：文件大小 ≥ 100MB 时启用 rayon 并行，< 100MB 用单线程。

**测量依据**（本地 8 核 MacBook）：

| 文件大小 | 单线程 | 8线程并行 | 选择 |
|----------|--------|-----------|------|
| 10MB     | 0.8s   | 1.2s      | 单线程 |
| 50MB     | 4.1s   | 2.8s      | 接近，取 50MB 以上并行 |
| 100MB    | 8.3s   | 2.1s      | 并行 4x |
| 1GB      | 83s    | 18s       | 并行 4.6x |

**注意**：阈值写在 `runner.rs` 的常量中，未来可改为 CLI 参数 `--parallel-threshold`。

### 遇到的借用检查器错误 #5：`BufReader::lines()` 与所有权

**问题**：尝试在迭代 `reader.lines()` 的同时，把 `reader` 传给另一个函数：

```rust
// ❌ 不可编译
let reader = BufReader::new(file);
some_function(&reader);          // 不可变借用
for line in reader.lines() { ... }  // lines() 消费 reader（move）
```

**编译错误**：`error[E0505]: cannot move out of 'reader' because it is borrowed`

**解法**：要么不在 `lines()` 循环外借用 `reader`，要么把 `some_function` 移到 `lines()` 循环之前且不再持有借用：

```rust
let file   = File::open(&config.input)?;
let meta   = file.metadata()?;   // 在 BufReader 创建前读取 metadata
let reader = BufReader::new(file);

// 此后 reader 仅在 .lines() 中使用，不再传给其他函数
for line in reader.lines() { ... }
```

这个错误非常经典：C# 中你可以任意传 `StreamReader` 的引用，GC 保证安全；Rust 的借用检查器要求引用生命周期不能跨越所有权转移点。

### ADR-03：clap derive 模式 vs builder 模式

**决策**：选 derive 模式（`#[derive(Parser)]`）。

**理由**：
- 参数定义即文档，`///` 注释直接变成 `--help` 的帮助文字
- 自动生成参数校验，不需要手写 `if args.level.is_none() { error!(...) }`
- `value_parser` 支持自定义解析函数（`parse_level`、`parse_datetime`）

**`--help` 实际输出**（derive 自动生成）：


### 遇到的借用检查器错误 #6：`args.input` 在 `with_context` 中 move 后再用

**问题**：

```rust
// ❌ 问题代码
let summary = run_analysis(config)
    .with_context(|| format!("分析文件 `{}` 失败", args.input.display()))?;
//                                                   ^^^^^^^^^ 这里借用 args.input

// config 已经包含 args.input（被 move 进去了）
```

**编译错误**：`error[E0382]: borrow of moved value: 'args.input'`

**解法**：在 `RunConfig` 构建时克隆路径（`PathBuf` 实现了 `Clone`），保留一份用于错误消息：

```rust
let input_path = args.input.clone();  // 先 clone，保留用于错误消息
let config = RunConfig {
    input: args.input,  // 原始值 move 进 config
    ...
};
let summary = run_analysis(config)
    .with_context(|| format!("分析文件 `{}` 失败", input_path.display()))?;
//                                                    ^^^^^^^^^^^ 使用 clone
```

**为什么这里 clone 是合理的**：`PathBuf` clone 只复制路径字符串（通常 < 256 bytes），且只做一次，不在循环中，性能开销可忽略。这是"知道为什么 clone" vs "逃避借用检查器随便 clone" 的区别。

## M5：rayon 并行 + Benchmark

### 任务

优化并行路径，用 criterion 验证 AC6（并行速度 > 单线程 2x）。

### ADR-04：`aggregate_parallel` 接受 `Vec<LogEntry>` 而非迭代器

**背景**：最初设计 `aggregate_parallel` 也接受 `impl Iterator<Item=LogEntry>`，与 `aggregate_serial` 接口统一。

**问题**：`rayon::ParallelIterator` 和 `std::iter::Iterator` 是不同 trait，无法统一为同一个函数参数类型。且 `BufReader::lines()` 是顺序迭代器，把它转换为并行迭代器（`par_bridge()`）实际上是**把 IO 操作并行化**——但 IO 是顺序的（HDD/SSD 顺序读比随机跳跃快），并行反而更慢。

**决策**：流水线拆为两阶段：
1. **IO 阶段**（顺序）：`BufReader::lines()` → 过滤 → `Vec<LogEntry>`
2. **CPU 阶段**（并行）：`Vec<LogEntry>.into_par_iter()` → 聚合

**接口**：
- `aggregate_serial(impl Iterator<Item=LogEntry>)`：顺序消费迭代器
- `aggregate_parallel(Vec<LogEntry>)`：接收已收集的 Vec，纯 CPU 并行

这样 rayon 只并行化 CPU 密集的**统计聚合**，IO 保持顺序，两全其美。

### Benchmark 结果分析

criterion 在 benchmark 机器（8 核 Intel i7-12700H）上的输出：

```
aggregation/serial/500000    time:   [2.3521 s 2.3784 s 2.4012 s]
aggregation/parallel/500000  time:   [418.24 ms 421.87 ms 425.11 ms]

// 加速比：2378ms / 421ms ≈ 5.6x（> AC6 要求的 2x）
```

**为什么比预期高**：500K 行数据的聚合是 CPU 密集操作（HashMap hash + 比较），rayon 在 8 核上接近线性加速。真实 1GB 文件场景中，IO 成为瓶颈，加速比降至约 3-4x，仍高于 2x 要求。

## M6：测试 + CI + Dockerfile

### ADR-05：不用 `mock` 文件系统，用 `tempfile` 创建真实临时文件

**背景**：测试 `run_analysis` 需要提供文件路径。有两种方案：
- 方案 A：mock 文件系统（实现 `trait FileSystem`，测试注入 mock）
- 方案 B：用 `tempfile` 创建真实临时文件

**决策**：方案 B。

**理由**：
- CLI 工具的核心测试目标就是"文件输入 → 文件输出"，mock 文件系统测的是 mock，不是真实行为
- `tempfile::NamedTempFile` 自动在测试结束后删除，无清理负担
- 代码更简单，无需引入 trait 抽象
- 类比 testcontainers 哲学：测试应尽可能用真实组件

### Dockerfile 多阶段构建踩坑

**问题**：distroless 镜像没有 `libc`（只有 `libgcc`），而 `csv` crate 链接了 `libc` 中的内存分配器。

**表现**：`docker run` 时立刻报 `exec format error` 或 `not found`。

**解法**：使用 `gcr.io/distroless/cc-debian12`（包含 `libgcc`，不包含 shell），而不是 `gcr.io/distroless/static`（完全静态，需要 `RUSTFLAGS="-C target-feature=+crt-static"` 才行）。

```dockerfile
# ✅ cc-debian12：包含 libgcc，适合大多数 Rust 二进制
FROM gcr.io/distroless/cc-debian12

# ❌ static：只适合完全静态链接的二进制
# FROM gcr.io/distroless/static
```

如果未来需要完全静态（不依赖 glibc），要改用 `musl` target：

```bash
rustup target add x86_64-unknown-linux-musl
cargo build --release --target x86_64-unknown-linux-musl
# 然后可用 FROM scratch 或 distroless/static
```

## 关键 Rust 语法要点总结

| 遇到的问题 | 根因 | 解法 | C# 中不存在此问题的原因 |
|-----------|------|------|------------------------|
| `String` 不能 `Copy` | `String` 拥有堆内存，实现了 `Drop` | 用 `Clone` 或引用 | GC 管理内存，所有 class 赋值只复制引用 |
| `reader.lines()` move 后无法再用 | `lines()` 消费 `reader` 的所有权 | 提前读取需要的数据再 `lines()` | `StreamReader` 可任意传递（引用语义） |
| 并行 HashMap 不能直接用 `&mut` | 多线程 `&mut` 违反借用规则 | `rayon fold+reduce`（局部 HashMap） | `lock()` 语义，运行时保证，编译器不检查 |
| `args.input` 在 move 后再借用 | 所有权转移后原变量失效 | move 前 `clone()` | 引用类型赋值只是复制引用，两者都有效 |
| `serde(rename_all)` 不做 case-insensitive | serde 按精确字符串匹配 | CLI 层统一 `to_ascii_uppercase()` | 通常用库处理（如 `JsonStringEnumConverter`） |
