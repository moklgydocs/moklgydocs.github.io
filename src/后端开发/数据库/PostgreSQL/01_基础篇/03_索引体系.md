# 索引体系

::: tip 核心观点
PostgreSQL 提供了 6 种索引类型，覆盖了从等值查询到全文搜索、地理空间到向量检索的全场景。理解每种索引的适用场景，比盲目加索引重要一百倍。
:::

## B-Tree 索引

B-Tree 是 PG 的默认索引类型，适用于等值查询、范围查询和排序：

```sql
-- 创建 B-Tree 索引（默认）
CREATE INDEX idx_users_email ON users (email);

-- 等值查询
SELECT * FROM users WHERE email = 'alice@example.com';

-- 范围查询
SELECT * FROM orders WHERE created_at BETWEEN '2025-01-01' AND '2025-06-30';

-- 排序（索引可避免 sort）
SELECT * FROM orders ORDER BY created_at DESC LIMIT 100;

-- 前缀 LIKE（仅前缀匹配可以用 B-Tree）
SELECT * FROM users WHERE name LIKE '张%';    -- ✅ 可用索引
SELECT * FROM users WHERE name LIKE '%明';    -- ✗ 无法用索引
```

```sql
-- 多列 B-Tree 索引（最左前缀原则）
CREATE INDEX idx_orders_user_date ON orders (user_id, created_at);

-- ✅ 可以使用索引
SELECT * FROM orders WHERE user_id = 1;
SELECT * FROM orders WHERE user_id = 1 AND created_at > '2025-01-01';

-- ✗ 无法使用索引（跳过了 user_id）
SELECT * FROM orders WHERE created_at > '2025-01-01';
```

## Hash 索引

```sql
-- Hash 索引：仅支持等值查询，不存储顺序
CREATE INDEX idx_session_token ON sessions USING hash (token);

SELECT * FROM sessions WHERE token = 'abc123def456';
```

::: warning 慎用 Hash 索引
- 只支持 `=` 查询，不支持范围、排序
- PG 10 前的 Hash 索引不写 WAL，崩溃后需重建
- PG 10+ 已修复 WAL 问题，但 B-Tree 在等值场景性能接近，没理由优先用 Hash
- 参考文档：[Hash Indexes](https://www.postgresql.org/docs/16/indexes-types.html)
:::

## GIN 索引

GIN（Generalized Inverted Index，广义倒排索引）是 PG 最强大的索引类型之一，专为多值元素设计：

```mermaid

    end

```

### GIN 用于数组

```sql
-- 数组列 + GIN 索引
CREATE TABLE articles (
    id    integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title text NOT NULL,
    tags  text[] NOT NULL DEFAULT '{}'
);

CREATE INDEX idx_articles_tags ON articles USING GIN (tags);

-- 包含查询
SELECT * FROM articles WHERE tags @> ARRAY['PostgreSQL'];     -- 包含指定元素
SELECT * FROM articles WHERE tags && ARRAY['PostgreSQL', 'MySQL']; -- 有交集
SELECT * FROM articles WHERE tags <@ ARRAY['PostgreSQL', 'MySQL', 'Redis']; -- 子集
```

### GIN 用于 JSONB

```sql
-- JSONB 列 + GIN 索引
CREATE TABLE products (
    id     integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name   text NOT NULL,
    attrs  jsonb NOT NULL DEFAULT '{}'
);

-- 默认 GIN 索引（支持所有 JSONB 操作符）
CREATE INDEX idx_products_attrs ON products USING GIN (attrs);

-- jsonb_path_ops（更小更快，但仅支持 @> 操作符）
CREATE INDEX idx_products_attrs_path ON products USING GIN (attrs jsonb_path_ops);

-- 对比
-- 默认 GIN：支持 @>, ?, ?|, ?&  （索引更大）
-- jsonb_path_ops：仅支持 @>      （索引更小，查询更快）
```

```sql
-- @> 包含查询（两种 GIN 索引都支持）
SELECT * FROM products WHERE attrs @> '{"cpu": "M3 Pro"}';
-- 等价于 attrs->>'cpu' = 'M3 Pro'，但 @> 可以用索引

-- ? 键存在查询（仅默认 GIN 支持）
SELECT * FROM products WHERE attrs ? 'cpu';

-- 嵌套包含
SELECT * FROM products WHERE attrs @> '{"specs": {"screen": 14}}';
```

### GIN 用于全文搜索

```sql
-- 中文全文搜索（需 zhparser 或 pg_jieba 扩展）
-- 这里用英文 tsvector 演示
CREATE TABLE documents (
    id       integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title    text NOT NULL,
    content  text NOT NULL,
    tsv      tsvector GENERATED ALWAYS AS (
        setweight(to_tsvector('english', coalesce(title, '')), 'A') ||
        setweight(to_tsvector('english', coalesce(content, '')), 'B')
    ) STORED
);

CREATE INDEX idx_documents_tsv ON documents USING GIN (tsv);

-- 全文搜索
SELECT title, ts_rank(tsv, query) AS rank
FROM documents, plainto_tsquery('english', 'PostgreSQL index optimization') query
WHERE tsv @@ query
ORDER BY rank DESC;
```

## GiST 索引

GiST（Generalized Search Tree，通用搜索树）是一个框架，支持自定义数据类型的索引：

```sql
-- GiST 用于范围类型
CREATE TABLE schedules (
    id         integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_id    integer NOT NULL,
    time_slot  tstzrange NOT NULL
);

CREATE INDEX idx_schedules_time ON schedules USING GiST (time_slot);

-- 重叠查询
SELECT * FROM schedules WHERE time_slot && '[2025-06-04 09:00, 2025-06-04 11:00)'::tstzrange;

-- 排除约束（防止重叠预订）
ALTER TABLE schedules
    ADD CONSTRAINT no_overlap
    EXCLUDE USING GiST (room_id WITH =, time_slot WITH &&);
```

```sql
-- GiST 用于 PostGIS 几何类型
CREATE EXTENSION IF NOT EXISTS postgis;

CREATE TABLE locations (
    id   integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL,
    geo  geometry(Point, 4326) NOT NULL
);

CREATE INDEX idx_locations_geo ON locations USING GiST (geo);

-- 附近搜索
SELECT name, ST_Distance(geo::geography, ST_MakePoint(116.4, 39.9)::geography) AS dist
FROM locations
WHERE ST_DWithin(geo::geography, ST_MakePoint(116.4, 39.9)::geography, 5000)  -- 5km 内
ORDER BY dist;
```

## BRIN 索引

BRIN（Block Range Index，块范围索引）适用于物理有序的大表，索引极小：

```sql
-- BRIN 索引：记录每个数据块的值范围
CREATE TABLE access_logs (
    id         bigint GENERATED ALWAYS AS IDENTITY,
    path       text NOT NULL,
    method     text NOT NULL,
    status     integer NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
) PARTITION BY RANGE (created_at);

-- 时间序列数据天然有序，BRIN 索引效果极好
CREATE INDEX idx_logs_created_at ON access_logs USING BRIN (created_at)
    WITH (pages_per_range = 32);  -- 每 32 个数据块记录一次范围

-- 索引大小对比
-- 1 亿行数据：
-- B-Tree 索引：约 2-3 GB
-- BRIN 索引：约 2-5 MB   ← 小 1000 倍！
```

```sql
-- 查看索引大小
SELECT indexrelname,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE schemaname = 'public';

--  indexrelname          | size
-- -----------------------+-------
--  idx_logs_created_at   | 56 kB    (BRIN)
--  idx_logs_path         | 2146 MB  (B-Tree)
```

::: tip BRIN 的适用场景
- **时间序列数据**：日志、监控、IoT 数据（按时间自然有序）
- **自增 ID**：插入顺序与 ID 顺序一致
- **不适合**：随机写入、值分布无序的列

参考：[BRIN Indexes](https://www.postgresql.org/docs/16/brin.html)
:::

## SP-GiST 索引

```sql
-- SP-GiST：支持非平衡数据结构（如前缀树、四叉树）
CREATE TABLE phone_numbers (
    id    integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    phone text NOT NULL
);

-- 前缀匹配（电话区号、IP 路由等）
CREATE INDEX idx_phone_prefix ON phone_numbers USING SP-GiST (phone text_pattern_ops);

SELECT * FROM phone_numbers WHERE phone LIKE '010%';
```

## 高级索引特性

### 部分索引（Partial Index）

```sql
-- 只索引活跃用户，减少索引大小
CREATE INDEX idx_users_active_email ON users (email)
    WHERE status = 'active';

-- 只索引未完成的订单
CREATE INDEX idx_orders_pending ON orders (created_at)
    WHERE status = 'pending';

-- 查询必须满足 WHERE 条件才能使用部分索引
SELECT * FROM users WHERE email = 'alice@example.com' AND status = 'active';
-- ✅ 可以使用 idx_users_active_email

SELECT * FROM users WHERE email = 'alice@example.com';
-- ✗ 无法使用部分索引（不保证覆盖所有行）
```

### 表达式索引

```sql
-- 对计算结果建索引
CREATE INDEX idx_users_lower_email ON users (lower(email));

-- 查询时使用相同的表达式才能命中
SELECT * FROM users WHERE lower(email) = 'alice@example.com';  -- ✅ 命中索引
SELECT * FROM users WHERE email = 'Alice@Example.com';          -- ✗ 无法命中

-- 日期截断索引
CREATE INDEX idx_orders_month ON orders (date_trunc('month', created_at));

SELECT * FROM orders WHERE date_trunc('month', created_at) = '2025-06-01'::timestamptz;
```

### 覆盖索引（Covering Index，PG 11+）

```sql
-- INCLUDE 列存在索引中但不参与排序，用于 Index Only Scan
CREATE INDEX idx_orders_user_covering ON orders (user_id)
    INCLUDE (amount, status, created_at);

-- 查询只需访问索引，不需要回表
EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id, amount, status, created_at
FROM orders
WHERE user_id = 1;
-- Index Only Scan using idx_orders_user_covering
```

### 唯一索引

```sql
-- 唯一索引保证列值唯一
CREATE UNIQUE INDEX idx_users_email ON users (email);

-- 部分唯一索引：允许 null 重复，非 null 唯一
CREATE UNIQUE INDEX idx_users_phone ON users (phone) WHERE phone IS NOT NULL;

-- 多列唯一
CREATE UNIQUE INDEX idx_user_roles ON user_roles (user_id, role_id);
```

### 并发创建索引

```sql
-- 普通创建索引会锁表（阻塞写入）
CREATE INDEX idx_orders_status ON orders (status);  -- ⚠️ 阻塞写入

-- 并发创建：不锁表，但耗时更长
CREATE INDEX CONCURRENTLY idx_orders_status ON orders (status);
-- ✅ 不阻塞读写，但创建过程中需要两次扫描表

-- 唯一索引也可以并发创建
CREATE UNIQUE INDEX CONCURRENTLY idx_users_phone ON users (phone);
```

::: important CREATE INDEX CONCURRENTLY 注意事项
- **不能在事务中执行**：`CONCURRENTLY` 不支持事务回滚
- **可能失败**：如果创建过程中有冲突的写入，索引会标记为 INVALID
- **修复失败索引**：`DROP INDEX idx_name;` 然后重新创建
- 参考文档：[Concurrent Index Builds](https://www.postgresql.org/docs/16/sql-createindex.html#SQL-CREATEINDEX-CONCURRENTLY)
:::

## EXPLAIN 验证索引使用

```sql
-- 创建测试数据
CREATE TABLE orders (
    id         integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id    integer NOT NULL,
    status     text NOT NULL DEFAULT 'pending',
    amount     numeric(10, 2) NOT NULL,
    created_at timestamptz DEFAULT now()
);

-- 不加索引：Seq Scan
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 1;
-- Seq Scan on orders  (cost=0.00..1542.00 rows=1 width=40)

-- 加索引后：Index Scan
CREATE INDEX idx_orders_user_id ON orders (user_id);
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 1;
-- Index Scan using idx_orders_user_id on orders  (cost=0.29..8.31 rows=1 width=40)

-- 覆盖索引：Index Only Scan
CREATE INDEX idx_orders_user_covering ON orders (user_id) INCLUDE (amount, status);
EXPLAIN ANALYZE SELECT user_id, amount, status FROM orders WHERE user_id = 1;
-- Index Only Scan using idx_orders_user_covering on orders

-- 多行匹配：Bitmap Scan
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id < 100;
-- Bitmap Heap Scan on orders
--   ->  Bitmap Index Scan using idx_orders_user_id
```

## PostgREST 查询与索引

[PostgREST](https://github.com/PostgREST/postgrest) 将 HTTP 请求映射为 SQL 查询，索引直接决定 API 性能：

```
# PostgREST API 请求
GET /orders?user_id=eq.1&select=id,amount,status&order=created_at.desc&limit=10
```

```sql
-- 等价 SQL
SELECT id, amount, status
FROM orders
WHERE user_id = 1
ORDER BY created_at DESC
LIMIT 10;

-- 为 PostgREST 查询优化的索引
CREATE INDEX idx_orders_user_date_desc ON orders (user_id, created_at DESC)
    INCLUDE (amount, status);
-- Index Only Scan，覆盖查询全部列
```

## 面试技巧

::: tip 面试高频问题
1. **B-Tree 和 GIN 索引的区别？**
   - B-Tree：一个 key 对应一行，适合标量值（=, <, >, BETWEEN）
   - GIN：一个 key 对应多行（倒排），适合多值元素（数组、JSONB、全文搜索）

2. **什么时候用 BRIN？**
   - 数据量大（亿级）、物理有序（时间序列/自增 ID）、需要极小索引
   - BRIN 不存储具体值，只存数据块的范围摘要

3. **部分索引有什么用？**
   - 减少索引大小（只索引需要的行）
   - 索引条件越精确，索引越小，维护成本越低

4. **CREATE INDEX CONCURRENTLY 的原理和风险？**
   - 分两阶段扫描，不持有排他锁
   - 风险：创建失败会留下 INVALID 索引，需要手动清理

5. **覆盖索引（INCLUDE）解决了什么问题？**
   - Index Only Scan 避免回表
   - 适合"查少量列"的高频查询
:::
