# 索引设计完全手册

索引是 SQL 性能的基石。没索引的查询就像没目录的字典——想查一个字只能从第一页翻到最后一页。但索引不是越多越好，乱建索引反而拖慢写入。这篇把常用的索引类型、设计原则、命中规则讲清楚。

## 索引的本质

SQL Server 的索引是 **B+ 树** 结构。想象一本书的目录：

- **根节点**：总目录（第 1 章在哪页、第 2 章在哪页）
- **中间节点**：章节目录
- **叶子节点**：具体的数据行（聚集索引）或指向数据行的指针（非聚集索引）

查找时从根节点往下走，每层缩小范围，通常 3-4 层就能定位到任何一行。100 万行的表，索引查找只需要读 3-4 个数据页。全表扫描可能要读几千个页。

## 索引类型

### 聚集索引（Clustered Index）

- 每张表只能有一个
- 决定了数据的物理存储顺序
- 叶子节点就是数据行本身
- 默认主键就是聚集索引

```sql
-- 建表时自动创建聚集索引
CREATE TABLE Orders (
    OrderId INT PRIMARY KEY,  -- 这就是聚集索引
    ...
);

-- 或者显式指定
CREATE CLUSTERED INDEX IX_Orders_OrderId ON Orders(OrderId);
```

**聚集索引选谁**：
- 窄（字节少）、唯一、递增、不常变的列
- INT IDENTITY 是最佳选择
- 不要用 GUID 做聚集索引——随机插入导致页分裂，性能很差

### 非聚集索引（Nonclustered Index）

- 每张表最多 999 个（但别真建这么多）
- 独立的 B+ 树，叶子节点存的是索引列的值 + 聚集索引键（指回数据行）
- 可以有多个

```sql
CREATE NONCLUSTERED INDEX IX_Orders_CustomerId
ON Orders(CustomerId);
```

### 覆盖索引（Covering Index）

不是一种新索引，是一种设计技巧——**让索引包含查询需要的所有列**，这样查索引就够了，不用回表。

```sql
-- 查询
SELECT OrderDate, Amount FROM Orders WHERE CustomerId = 100;

-- 如果只有 CustomerId 的索引，需要 Key Lookup 取 OrderDate 和 Amount
-- 加 INCLUDE 变成覆盖索引：
CREATE INDEX IX_Orders_CustomerId
ON Orders(CustomerId)
INCLUDE (OrderDate, Amount);
-- 现在 Index Seek 直接拿到所有需要的列，不用回表了
```

**INCLUDE 和索引键的区别**：
- 索引键（KEY）：参与 B+ 树排序，WHERE、ORDER BY、JOIN 条件用到的列放这里
- INCLUDE 列：只存在叶子节点，不参与排序，只是为了覆盖 SELECT 的列

### 筛选索引（Filtered Index）

只对符合条件的行建索引，索引更小更快：

```sql
-- 只对未完成的订单建索引（假设 99% 的订单都已完成）
CREATE INDEX IX_Orders_Pending
ON Orders(OrderDate, CustomerId)
WHERE Status = 0;
```

100 万订单里只有 1 万个未完成的，这个索引只有 1 万行，比全量索引小太多了。

**限制**：WHERE 条件里不能用变量，只能用常量。存储过程里的参数不能直接匹配筛选索引，需要加 `OPTION(RECOMPILE)` 或写成常量。

### 唯一索引

```sql
CREATE UNIQUE INDEX IX_Customers_Phone ON Customers(Phone);
```

既是约束又是索引。如果业务上某列不该重复，加唯一索引比在代码里检查可靠得多。

## 索引设计原则

### 1. 先看查询，再建索引

不要凭空建索引。看你的查询 WHERE、JOIN、ORDER BY 用了什么列，针对性地建。

```sql
-- 如果最常见的查询是这个
SELECT * FROM Orders WHERE CustomerId = @cid ORDER BY OrderDate DESC;

-- 那么最优索引是
CREATE INDEX IX ON Orders(CustomerId, OrderDate DESC) INCLUDE (...);
```

### 2. 最左前缀原则

复合索引 `(A, B, C)` 能支持的查询：
- WHERE A = 1 ✅
- WHERE A = 1 AND B = 2 ✅
- WHERE A = 1 AND B = 2 AND C = 3 ✅
- WHERE B = 2 ❌（不走索引，A 没用上）
- WHERE A = 1 AND C = 3 ⚠️（只用到 A，C 不能跳过 B）

把**选择性高的列放前面**。选择性 = 不同值的数量 / 总行数。比如 Status 只有 3 个值（选择性低），CustomerId 有 1 万个值（选择性高），应该 CustomerId 在前。

### 3. 等值条件在前，范围条件在后

```sql
WHERE CustomerId = 100 AND OrderDate > '2024-01-01'
```

索引应该是 `(CustomerId, OrderDate)`，不是 `(OrderDate, CustomerId)`。因为范围条件之后的列不能用于 Seek。

### 4. 不要建太多索引

每个索引都是一棵 B+ 树，INSERT/UPDATE/DELETE 时要维护所有相关索引。索引越多，写入越慢。

一般一张表 **5-8 个非聚集索引**以内。超过了就要审视一下有没有重复的、没人用的。

### 5. 定期清理无用索引

```sql
-- 查看索引使用情况
SELECT
    OBJECT_NAME(s.object_id) AS TableName,
    i.name AS IndexName,
    s.user_seeks, s.user_scans, s.user_lookups, s.user_updates
FROM sys.dm_db_index_usage_stats s
JOIN sys.indexes i ON s.object_id = i.object_id AND s.index_id = i.index_id
WHERE s.database_id = DB_ID()
ORDER BY s.user_seeks + s.user_scans + s.user_lookups;
```

`user_seeks + user_scans = 0` 但 `user_updates` 很高的索引，就是白白维护没人用的废索引。

## 索引命名规范

别用默认的 `IX_Orders_CustomerId` 之后再加个 `IX_Orders_CustomerId1`。建议命名格式：

```
IX_{表名}_{列1}_{列2}
UIX_{表名}_{列}          -- 唯一索引前缀 UIX
FIX_{表名}_{描述}         -- 筛选索引前缀 FIX
```

## 索引维护

### 碎片整理

随着数据的插入删除修改，索引会产生碎片（页分裂）。碎片多了扫描效率下降。

```sql
-- 查看碎片率
SELECT
    OBJECT_NAME(ips.object_id) AS TableName,
    i.name AS IndexName,
    ips.avg_fragmentation_in_percent
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') ips
JOIN sys.indexes i ON ips.object_id = i.object_id AND ips.index_id = i.index_id
WHERE ips.avg_fragmentation_in_percent > 10
ORDER BY ips.avg_fragmentation_in_percent DESC;
```

| 碎片率 | 处理方式 |
|--------|----------|
| < 10% | 不用管 |
| 10% - 30% | REORGANIZE（在线整理，轻量） |
| > 30% | REBUILD（重建，更彻底，会锁表 —— ONLINE 选项可避免） |

```sql
-- 重组
ALTER INDEX IX_Orders_CustomerId ON Orders REORGANIZE;

-- 重建
ALTER INDEX IX_Orders_CustomerId ON Orders REBUILD;

-- 在线重建（Enterprise 版）
ALTER INDEX IX_Orders_CustomerId ON Orders REBUILD WITH (ONLINE = ON);

-- 重建所有索引
ALTER INDEX ALL ON Orders REBUILD;
```

### 统计信息更新

索引的统计信息过期会导致优化器选错执行计划。通常自动更新就够了，但有时候需要手动更新：

```sql
UPDATE STATISTICS Orders;

-- 或者带全扫描（更准确）
UPDATE STATISTICS Orders WITH FULLSCAN;
```

## 快速决策表

| 我的查询 | 建什么索引 |
|----------|-----------|
| WHERE A = @a | `(A)` |
| WHERE A = @a ORDER BY B | `(A, B)` |
| WHERE A = @a AND B > @b | `(A, B)` |
| WHERE A = @a，SELECT 有 C、D | `(A) INCLUDE (C, D)` |
| WHERE A IN (1,2,3) AND B = @b | `(B, A)` —— 等值在前 |
| JOIN ON A = B.A | 两边都要有 A 的索引 |
| 99% 的查询只关心 Status=0 的行 | 筛选索引 `WHERE Status = 0` |
