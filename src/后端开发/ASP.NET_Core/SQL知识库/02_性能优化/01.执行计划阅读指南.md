# 执行计划阅读指南

SQL 慢不慢，不是靠猜的。打开执行计划，SQL Server 会告诉你它到底怎么执行你的查询——走了什么索引、做了多少次扫描、哪一步最耗时。看懂执行计划，是 SQL 优化的第一步。

## 怎么打开执行计划

### SSMS 图形化

```
-- 方法 1：预估执行计划（不真正执行）
Ctrl + L

-- 方法 2：实际执行计划（真正执行，看实际行数）
Ctrl + M，然后执行查询
```

预估和实际的区别：预估是 SQL Server "猜" 的行数，实际是真跑出来的行数。两者差很多的话，说明统计信息过期了。

### 文本格式

```sql
SET SHOWPLAN_TEXT ON;   -- 预估，文本格式
GO
SELECT * FROM Orders WHERE CustomerId = 100;
GO
SET SHOWPLAN_TEXT OFF;

-- 或者更详细的
SET SHOWPLAN_ALL ON;
SET STATISTICS PROFILE ON;  -- 实际执行计划，文本
```

### 最实用：IO 和时间统计

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT * FROM Orders WHERE CustomerId = 100;

-- 输出：
-- Table 'Orders'. Scan count 1, logical reads 3, physical reads 0
-- SQL Server Execution Times: CPU time = 0 ms, elapsed time = 1 ms
```

**logical reads（逻辑读）** 是最关键的数字。它代表从内存（缓冲区）读了多少个 8KB 的数据页。逻辑读越少，查询越快。优化的目标就是让这个数字变小。

## 执行计划看什么

### 阅读方向

图形化执行计划**从右往左看**。最右边是数据源（表/索引），数据从右边流向左边，最左边是最终输出。

箭头越粗，表示数据量越大。

### 三个关键数字

把鼠标悬停在操作符上，重点看：

1. **Estimated Number of Rows**（预估行数） vs **Actual Number of Rows**（实际行数）。差距大 = 统计信息不准
2. **Estimated Subtree Cost**（子树成本）。数字越大花费越高。看哪个操作符成本最大
3. **Number of Executions**（执行次数）。嵌套循环里的操作可能执行几万次

## 常见操作符

### 表/索引访问

| 操作符 | 图标含义 | 好坏 |
|--------|----------|------|
| **Clustered Index Seek** | 聚集索引查找 | ✅ 最优，直接定位 |
| **Index Seek** | 非聚集索引查找 | ✅ 很好 |
| **Clustered Index Scan** | 聚集索引扫描（全表扫描） | ⚠️ 小表没事，大表要警惕 |
| **Index Scan** | 非聚集索引扫描 | ⚠️ 扫了整个索引 |
| **Table Scan** | 堆表扫描（没聚集索引的表） | ❌ 全表扫描 |
| **Key Lookup** | 回表查找 | ⚠️ 索引里没有需要的列，回聚集索引取 |
| **RID Lookup** | 堆表回表 | ⚠️ 同上，但表没聚集索引 |

**Seek vs Scan**：Seek 是精确查找，像用目录翻书直接翻到那页；Scan 是一页一页翻完整本书。

**Key Lookup（书签查找）** 是常见的性能问题。就是说非聚集索引找到了行，但你 SELECT 的字段不在索引里，要回去聚集索引再查一次。解决办法：把需要的列加到索引的 INCLUDE 里。

### 连接方式

| 操作符 | 特点 | 适用场景 |
|--------|------|----------|
| **Nested Loops** | 外表每行去内表找一次 | 外表小、内表有索引 |
| **Hash Match** | 先建哈希表，再探测 | 两个大表、无合适索引 |
| **Merge Join** | 两个已排序的数据集合并 | 两边都有序（有索引） |

Nested Loops 不一定差，Hash Match 不一定好，取决于数据量。但如果你看到 Hash Match 出现在本该走索引查找的地方，说明缺索引了。

### 其他常见操作

| 操作符 | 含义 |
|--------|------|
| **Sort** | 排序。如果有合适索引，这步可以省掉 |
| **Filter** | 过滤。WHERE 条件过滤 |
| **Compute Scalar** | 计算表达式（比如 CASE WHEN、函数调用） |
| **Stream Aggregate** | 已排序数据的聚合（GROUP BY） |
| **Hash Aggregate** | 大量数据的聚合 |
| **Parallelism** | 并行操作。SQL Server 用多个线程跑 |
| **Spool (Eager/Lazy)** | 缓存中间结果，后面重复使用 |

## 红色警告

执行计划里有些操作会标黄色感叹号 ⚠️，叫 Warning：

- **Missing Index**：SQL Server 建议你建个索引，会直接告诉你建什么索引。准确率大约 70%，别无脑照建
- **No Join Predicate**：笛卡尔积！忘写 JOIN 条件了，赶紧检查
- **Implicit Conversion**：隐式类型转换，可能导致索引失效（后面会细说）
- **Excessive Memory Grant**：申请了太多内存，实际没用那么多

## 实战：读一个真实的执行计划

```sql
SET STATISTICS IO ON;

-- 查某个客户的订单，按日期倒序取前 10 条
SELECT TOP 10 o.OrderId, o.OrderDate, o.Amount, c.CustomerName
FROM Orders o
INNER JOIN Customers c ON o.CustomerId = c.CustomerId
WHERE o.CustomerId = 12345
ORDER BY o.OrderDate DESC;
```

好的执行计划应该是：
1. Orders 表 → **Index Seek**（走 CustomerId 索引定位）
2. 如果索引包含了 OrderDate、Amount → 不需要 Key Lookup
3. Customers 表 → **Clustered Index Seek**（主键查找）
4. **Nested Loops** 连接（因为 Orders 结果集小）
5. **Top** 操作符取前 10

糟糕的执行计划：
1. Orders 表 → **Clustered Index Scan**（全表扫描 100 万行）
2. **Sort**（扫完了再排序）
3. Customers 表 → **Hash Match**（大量数据连接）

## 对比优化前后

养成习惯：优化之前先拿到 baseline，优化之后再跑一次对比。

```sql
-- 优化前
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT ... -- 你的查询

-- 记录：logical reads = 15234, CPU time = 312 ms

-- 优化后（加了索引 / 改写了SQL）
SELECT ... -- 优化后的查询

-- 记录：logical reads = 45, CPU time = 0 ms
```

**逻辑读从 15234 降到 45，就是实打实的优化效果。**

## 几个实用技巧

1. **看实际执行计划，不要只看预估的**。预估行数可能差 100 倍
2. **找成本最高的操作符**。SSMS 里每个操作符会标百分比，从最大的开始优化
3. **关注箭头粗细变化**。如果某一步进去 100 万行出来还是 100 万行，说明过滤条件没用上
4. **点击 SELECT 操作符看整体信息**。里面有 Missing Index 建议和总成本
5. **用 `SET STATISTICS IO ON`**。相比图形化执行计划，logical reads 数字最客观，不受显示方式影响
