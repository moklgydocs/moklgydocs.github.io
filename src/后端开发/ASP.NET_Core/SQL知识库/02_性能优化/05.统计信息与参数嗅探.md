# 统计信息与参数嗅探

同一个存储过程，有时候跑得飞快有时候慢得要死——八成是参数嗅探的锅。要搞清楚这个问题，先得理解 SQL Server 的统计信息是怎么回事。

## 统计信息是什么

SQL Server 的查询优化器在生成执行计划时，需要**估算每一步操作会返回多少行**。估算行数用的就是统计信息——一组描述列中数据分布的直方图。

打个比方：你问"北京有多少订单"，SQL Server 不会真去数，它看统计信息里记录的北京大概有多少不同值、分布在什么范围，然后估一个数。估得准，执行计划就对；估得不准，执行计划就可能选错索引、选错连接方式。

### 查看统计信息

```sql
-- 查看某个索引/统计信息的直方图
DBCC SHOW_STATISTICS('Orders', 'IX_Orders_CustomerId');
```

输出三个部分：
1. **Header**：最后更新时间、采样行数
2. **Density**：列组合的唯一性
3. **Histogram**：直方图，200 个区间，描述数据分布

### 自动更新机制

SQL Server 默认开启统计信息自动更新。触发条件：

- 表从 0 行变成有数据
- 表行数 < 500 时，修改了 500 行
- 表行数 >= 500 时，修改了 `500 + 表行数 * 20%` 行（2016 之前）
- SQL Server 2016+ 开启了 Trace Flag 2371 或数据库兼容级别 130+，阈值改为 `SQRT(1000 * 表行数)`，大表更新更频繁

**问题**：100 万行的表，旧版本要改 20 万行才触发自动更新。这期间统计信息可能严重过时。

### 手动更新

```sql
-- 更新某张表所有统计信息
UPDATE STATISTICS Orders;

-- 全表扫描更新（最准，但最慢）
UPDATE STATISTICS Orders WITH FULLSCAN;

-- 指定采样比例
UPDATE STATISTICS Orders WITH SAMPLE 30 PERCENT;

-- 更新整个数据库
EXEC sp_updatestats;
```

**建议**：重要表在业务低峰期定期跑 `UPDATE STATISTICS ... WITH FULLSCAN`。

## 统计信息不准会怎样

执行计划里预估行数偏差大 → 选错执行策略：

| 预估 vs 实际 | 后果 |
|---|---|
| 预估 1 行，实际 10 万行 | 选了 Nested Loops，实际应该用 Hash Join。循环 10 万次，慢死 |
| 预估 100 万行，实际 1 行 | 选了 Hash Join + 并行，白白浪费资源 |
| 预估少 → 内存分配不足 | 排序/哈希操作溢出到磁盘（TempDB），看到 Sort Warnings |

在执行计划里，鼠标悬停在操作符上，对比 **Estimated Rows** 和 **Actual Rows**。两者差 10 倍以上就有问题了。

## 参数嗅探

### 什么是参数嗅探

存储过程第一次执行时，SQL Server 会"嗅探"传入的参数值，根据这个值生成并缓存执行计划。后续调用不管传什么值，都复用这个缓存的计划。

```sql
CREATE PROCEDURE sp_GetOrders
    @CustomerId INT
AS
    SELECT * FROM Orders WHERE CustomerId = @CustomerId;
```

如果第一次调用传的是 VIP 客户（只有 5 笔订单）→ 计划选了 Index Seek + Nested Loops。

第二次传了个普通客户（有 50000 笔订单）→ 还是用这个 Nested Loops 计划 → 慢得要死。

反之也会出问题：第一次传大客户 → 计划选了全表扫描。后来传小客户 → 也全表扫描 → 本该很快的查询也变慢了。

### 确认是不是参数嗅探

1. 同一个存储过程，某些参数快某些慢
2. 清了计划缓存后又正常了（但过一阵又慢了）
3. 把存储过程的 SQL 复制出来直接跑很快，但调存储过程就慢

### 怎么解决

#### 方法 1：OPTION (RECOMPILE)

```sql
CREATE PROCEDURE sp_GetOrders
    @CustomerId INT
AS
    SELECT * FROM Orders WHERE CustomerId = @CustomerId
    OPTION (RECOMPILE);
```

每次执行都重新编译执行计划。**最简单粗暴**。代价是每次多花一点编译时间（通常几毫秒），对于执行频率不高但执行时间长的查询很划算。

#### 方法 2：OPTIMIZE FOR

```sql
-- 告诉优化器按"典型值"来优化
SELECT * FROM Orders WHERE CustomerId = @CustomerId
OPTION (OPTIMIZE FOR (@CustomerId = 1000));

-- 或者用 UNKNOWN，让优化器用统计信息的平均值
SELECT * FROM Orders WHERE CustomerId = @CustomerId
OPTION (OPTIMIZE FOR UNKNOWN);
```

`OPTIMIZE FOR UNKNOWN` 等于让优化器不嗅探，用统计信息的密度信息来估。适合参数分布比较均匀的情况。

#### 方法 3：本地变量（有用但不推荐）

```sql
CREATE PROCEDURE sp_GetOrders
    @CustomerId INT
AS
    DECLARE @cid INT = @CustomerId;  -- 赋给本地变量
    SELECT * FROM Orders WHERE CustomerId = @cid;
```

本地变量不会被嗅探，优化器用 UNKNOWN 估算。等于打了 `OPTIMIZE FOR UNKNOWN`。但这种写法很隐蔽，别人看你的代码会纳闷"为什么多此一举"。

#### 方法 4：清除计划缓存

```sql
-- 清除某个存储过程的缓存计划
DECLARE @planHandle VARBINARY(64);
SELECT @planHandle = plan_handle
FROM sys.dm_exec_procedure_stats
WHERE object_id = OBJECT_ID('sp_GetOrders');

IF @planHandle IS NOT NULL
    DBCC FREEPROCCACHE(@planHandle);
```

治标不治本——下次编译又可能踩到坏参数。

#### 方法 5：计划指南（Plan Guide）

在不修改代码的情况下强制某个查询使用特定的执行计划提示。适合改不了代码的场景（第三方应用），但维护成本高。

---

## 实际决策

| 场景 | 推荐方案 |
|------|---------|
| 存储过程偶尔慢，参数分布不均 | OPTION (RECOMPILE) |
| 参数分布均匀，只是偶尔碰到异常值 | OPTIMIZE FOR UNKNOWN |
| 执行频率极高（每秒几千次） | 避免 RECOMPILE，考虑 OPTIMIZE FOR |
| 紧急修复，不能改代码 | 清缓存，临时解决 |
| 第三方应用 | Plan Guide |

**我的建议**：90% 的场景加个 `OPTION (RECOMPILE)` 就解决了。编译开销相对于一次查询执行几百毫秒不算什么。只有高频调用（每秒几千次的 OLTP）才需要考虑其他方案。

## 配套：定期维护脚本

```sql
-- 放到 SQL Agent Job 里，每天凌晨跑一次
-- 更新所有用户表的统计信息
EXEC sp_updatestats;

-- 或者只更新那些过期了的
DECLARE @sql NVARCHAR(MAX) = '';
SELECT @sql = @sql + 'UPDATE STATISTICS ' + QUOTENAME(SCHEMA_NAME(t.schema_id))
    + '.' + QUOTENAME(t.name) + ' WITH SAMPLE 50 PERCENT;' + CHAR(13)
FROM sys.tables t
WHERE EXISTS (
    SELECT 1 FROM sys.stats s
    WHERE s.object_id = t.object_id
    AND STATS_DATE(s.object_id, s.stats_id) < DATEADD(DAY, -1, GETDATE())
);
EXEC sp_executesql @sql;
```
