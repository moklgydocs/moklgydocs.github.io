# 慢 SQL 诊断流程

线上报了个接口慢，查到数据库这层，怎么快速定位是哪条 SQL 的问题，然后修好它？这篇给一个标准的排查流程，按步骤走就行。

## 第一步：定位慢 SQL

### 方法1：查当前正在跑的慢查询

```sql
-- 找当前执行时间超过 5 秒的查询
SELECT
    r.session_id,
    r.status,
    r.command,
    r.wait_type,
    r.total_elapsed_time / 1000 AS elapsed_sec,
    r.cpu_time / 1000 AS cpu_sec,
    r.logical_reads,
    SUBSTRING(t.text, (r.statement_start_offset/2)+1,
        ((CASE r.statement_end_offset WHEN -1 THEN DATALENGTH(t.text)
          ELSE r.statement_end_offset END - r.statement_start_offset)/2)+1
    ) AS current_sql,
    p.query_plan
FROM sys.dm_exec_requests r
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) t
OUTER APPLY sys.dm_exec_query_plan(r.plan_handle) p
WHERE r.total_elapsed_time > 5000  -- 超过 5 秒
  AND r.session_id <> @@SPID
ORDER BY r.total_elapsed_time DESC;
```

### 方法2：从缓存里找历史慢查询

```sql
-- 找历史上平均执行时间最长的 Top 20 SQL
SELECT TOP 20
    qs.total_elapsed_time / qs.execution_count / 1000 AS avg_ms,
    qs.execution_count,
    qs.total_logical_reads / qs.execution_count AS avg_reads,
    SUBSTRING(t.text, (qs.statement_start_offset/2)+1,
        ((CASE qs.statement_end_offset WHEN -1 THEN DATALENGTH(t.text)
          ELSE qs.statement_end_offset END - qs.statement_start_offset)/2)+1
    ) AS sql_text
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) t
ORDER BY avg_ms DESC;
```

### 方法3：找逻辑读最高的

```sql
-- 按总逻辑读排序（IO 消耗最大的查询）
SELECT TOP 20
    qs.total_logical_reads,
    qs.execution_count,
    qs.total_logical_reads / qs.execution_count AS avg_reads,
    SUBSTRING(t.text, (qs.statement_start_offset/2)+1,
        ((CASE qs.statement_end_offset WHEN -1 THEN DATALENGTH(t.text)
          ELSE qs.statement_end_offset END - qs.statement_start_offset)/2)+1
    ) AS sql_text
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) t
ORDER BY qs.total_logical_reads DESC;
```

## 第二步：量化问题

找到嫌疑 SQL 后，在 SSMS 里单独跑一下，先拿到 baseline 数据：

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

-- 你的慢 SQL
SELECT ...

-- 记录三个数字：
-- 1. logical reads = ?
-- 2. CPU time = ?
-- 3. elapsed time = ?
```

这三个数字就是你的优化前基线，改完之后对比着看。

## 第三步：看执行计划

```sql
-- 打开实际执行计划
-- SSMS: Ctrl+M 然后执行
```

重点关注：

1. **有没有 Table Scan / Clustered Index Scan**？大表全扫就是问题
2. **有没有 Key Lookup**？回表次数太多性能差
3. **箭头粗细**：哪一步数据量暴涨
4. **预估行数 vs 实际行数**：差距大说明统计信息有问题
5. **Warning 标记**：Missing Index、Implicit Conversion、No Join Predicate

---

## 第四步：分析原因

根据执行计划，问题通常落在这几类：

### 缺索引

执行计划里出现了 Missing Index 建议，或者看到大表 Scan。

**解法**：按照查询的 WHERE、JOIN、ORDER BY 建合适的索引。

```sql
-- 执行计划建议的索引（右键点 Missing Index Details）
CREATE INDEX IX_Orders_CustomerId_OrderDate
ON Orders(CustomerId, OrderDate DESC)
INCLUDE (Amount, Status);
```

### 索引失效

有索引但没走。检查：函数包裹、隐式转换、最左前缀不匹配。

### 回表（Key Lookup）太多

非聚集索引找到了行，但 SELECT 的列不在索引里，要一行行回聚集索引取。

**解法**：INCLUDE 需要的列，或者减少 SELECT 的列（别 `SELECT *`）。

### 统计信息过期

预估行数和实际行数差很多（比如预估 1 行实际 10 万行）。

```sql
UPDATE STATISTICS 表名 WITH FULLSCAN;
```

### SQL 写法问题

- 子查询套子查询，逻辑重复计算
- OR 条件没拆分
- 不必要的 DISTINCT
- 关联子查询在 SELECT 里逐行执行

## 第五步：优化

### 加索引

最常见的优化手段。对照执行计划加索引，加完之后重新跑，对比 logical reads。

### 改写 SQL

```sql
-- 优化前：关联子查询
SELECT c.CustomerName,
    (SELECT COUNT(*) FROM Orders o WHERE o.CustomerId = c.CustomerId) AS OrderCount
FROM Customers c;

-- 优化后：改成 JOIN
SELECT c.CustomerName, ISNULL(t.OrderCount, 0) AS OrderCount
FROM Customers c
LEFT JOIN (
    SELECT CustomerId, COUNT(*) AS OrderCount
    FROM Orders GROUP BY CustomerId
) t ON c.CustomerId = t.CustomerId;
```

### 分步执行

如果一条 SQL 又长又复杂又慢，拆成几步，中间结果存临时表：

```sql
-- 把复杂的 CTE 或子查询拆出来
SELECT ...
INTO #Step1
FROM ... WHERE ...;

CREATE INDEX IX ON #Step1(KeyColumn);

SELECT ...
FROM #Step1
JOIN OtherTable ON ...;
```

这样每一步都可以独立看执行计划，定位瓶颈更准。

## 第六步：验证

优化之后必须验证效果：

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

-- 跑优化后的 SQL

-- 对比：
-- logical reads: 15234 → 45  ✅ 降了 300 倍
-- CPU time: 312ms → 0ms      ✅
-- elapsed time: 850ms → 5ms  ✅
```

确认效果 OK 再上线。

## 常见等待类型速查

如果查询慢不是因为执行计划差，而是在等资源，看 `wait_type`：

| 等待类型 | 含义 | 排查方向 |
|----------|------|----------|
| CXPACKET | 并行等待 | 可能不是问题，也可能 MAXDOP 设置不合理 |
| LCK_M_X / LCK_M_S | 等锁 | 有别的事务锁住了表，查阻塞链 |
| PAGEIOLATCH_SH | 等磁盘 IO | 内存不够或磁盘慢 |
| SOS_SCHEDULER_YIELD | CPU 繁忙 | CPU 瓶颈，优化查询减少 CPU 消耗 |
| ASYNC_NETWORK_IO | 等客户端取数据 | 客户端处理太慢（前端拿了太多数据没消费） |
| WRITELOG | 等日志写入 | 日志磁盘慢、事务太频繁 |

### 查当前阻塞

```sql
-- 谁阻塞了谁
SELECT
    blocking.session_id AS blocker_sid,
    blocked.session_id AS blocked_sid,
    blocked.wait_type,
    blocked.wait_time / 1000 AS wait_sec,
    bt.text AS blocker_sql,
    t.text AS blocked_sql
FROM sys.dm_exec_requests blocked
JOIN sys.dm_exec_sessions blocking ON blocked.blocking_session_id = blocking.session_id
CROSS APPLY sys.dm_exec_sql_text(blocked.sql_handle) t
OUTER APPLY sys.dm_exec_sql_text(blocking.most_recent_sql_handle) bt
WHERE blocked.blocking_session_id > 0;
```

## 诊断流程一张图

```
接口报慢
  │
  ├─ 定位慢 SQL（dm_exec_requests / dm_exec_query_stats）
  │
  ├─ 量化 baseline（STATISTICS IO / TIME）
  │
  ├─ 看执行计划
  │   ├─ Scan？      → 加索引
  │   ├─ Key Lookup？ → INCLUDE 列
  │   ├─ Sort？      → 索引覆盖排序
  │   ├─ 预估偏差？  → 更新统计信息
  │   └─ Warning？   → 处理隐式转换/笛卡尔积
  │
  ├─ 优化（加索引 / 改写 SQL / 拆步骤）
  │
  └─ 验证效果（对比 logical reads / CPU / elapsed）
```
