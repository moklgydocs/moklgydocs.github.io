# 大表查询优化实战

百万级、千万级的表怎么查才不卡？这篇整理几个真实场景的优化套路，不讲理论直接上手。

## 场景一：ID 查询很快，但条件查询慢

**现象**：`WHERE OrderId = xxx` 秒出，但 `WHERE CustomerId = xxx AND Status = 1` 要 5 秒。

**原因**：OrderId 是主键有聚集索引，CustomerId + Status 没合适的索引。

**优化**：

```sql
-- 看查询
SELECT OrderId, OrderDate, Amount
FROM Orders
WHERE CustomerId = 100 AND Status = 1
ORDER BY OrderDate DESC;

-- 建覆盖索引
CREATE INDEX IX_Orders_Cust_Status
ON Orders(CustomerId, Status, OrderDate DESC)
INCLUDE (Amount);
```

这个索引精确匹配 WHERE 条件，ORDER BY 也不需要额外排序，SELECT 的列都在 INCLUDE 里不用回表。一个索引搞定三件事。

## 场景二：报表查询跑 30 秒

**现象**：月度汇总报表，JOIN 了 5 张表，GROUP BY 了 3 个字段，跑 30 秒。

**套路**：拆步骤 + 临时表 + 局部索引。

```sql
-- 原来是一条巨长的 SQL，优化器自己都晕了
-- 拆成几步

-- 第 1 步：先在大表上做最强过滤，结果存临时表
SELECT OrderId, CustomerId, Amount, OrderDate
INTO #MonthOrders
FROM Orders
WHERE OrderDate >= '2024-01-01' AND OrderDate < '2024-02-01'
  AND Status = 1;
-- 100 万行 → 过滤后可能只剩 5 万行

-- 第 2 步：给临时表建索引
CREATE INDEX IX ON #MonthOrders(CustomerId);

-- 第 3 步：临时表和其他表 JOIN
SELECT c.CustomerName, c.City,
    COUNT(*) AS OrderCount,
    SUM(o.Amount) AS TotalAmount
FROM #MonthOrders o
JOIN Customers c ON o.CustomerId = c.CustomerId
JOIN CustomerGroups cg ON c.GroupId = cg.GroupId
GROUP BY c.CustomerName, c.City;

DROP TABLE #MonthOrders;
```

为什么这样快？因为复杂查询让优化器在一步里考虑太多选择，经常选错；拆开后每一步都简单，执行计划基本不会错。

## 场景三：分页到后面越来越慢

**现象**：第 1 页 20ms，第 100 页 200ms，第 5000 页 15 秒。

**原因**：OFFSET 5000 * 20 要先扫描和跳过 10 万行。

**优化**：键集分页。

```sql
-- 前端传上一页最后一条的 OrderId
DECLARE @LastOrderId INT = 100000;

SELECT TOP 20 OrderId, CustomerId, OrderDate, Amount
FROM Orders
WHERE OrderId > @LastOrderId
ORDER BY OrderId;
-- 走主键 Seek，不管第几页都是一样快
```

如果必须支持跳页，限制最大页码（比如 100 页），或者用 ElasticSearch 做搜索层。

## 场景四：COUNT(*) 慢

**现象**：`SELECT COUNT(*) FROM Orders WHERE Status = 1` 要 3 秒。

**原因**：100 万行表做了全表扫描/全索引扫描。

**优化思路**：

```sql
-- 方案 1：建窄索引
CREATE INDEX IX_Orders_Status ON Orders(Status);
-- COUNT(*) 只需要扫这个窄索引（比聚集索引小很多）

-- 方案 2：如果精确到个位数不重要，用近似值
SELECT SUM(p.rows) AS ApproxCount
FROM sys.partitions p
WHERE p.object_id = OBJECT_ID('Orders')
  AND p.index_id IN (0, 1);
-- 这个数不是实时精确的，但查询瞬间完成

-- 方案 3：维护一个计数表
-- 每次 INSERT/DELETE 时同步更新计数
-- 查的时候直接读计数表
```

## 场景五：大表 JOIN 大表

**现象**：100 万订单 JOIN 100 万物流记录，跑 20 秒。

**优化套路**：

1. **确保 JOIN 列都有索引**

```sql
-- 两边都要有
CREATE INDEX IX_Orders_OrderNo ON Orders(OrderNo);
CREATE INDEX IX_Shipping_OrderNo ON ShippingRecords(OrderNo);
```

2. **先过滤再 JOIN**

```sql
-- ❌ 先 JOIN 再过滤
SELECT o.*, s.ShippingDate
FROM Orders o
JOIN ShippingRecords s ON o.OrderNo = s.OrderNo
WHERE o.OrderDate >= '2024-01-01';

-- ✅ 先过滤到临时表再 JOIN
SELECT OrderNo, OrderDate, Amount
INTO #filtered
FROM Orders
WHERE OrderDate >= '2024-01-01';

CREATE INDEX IX ON #filtered(OrderNo);

SELECT f.*, s.ShippingDate
FROM #filtered f
JOIN ShippingRecords s ON f.OrderNo = s.OrderNo;
```

3. **避免 SELECT ***

只查需要的列，减少数据传输量和内存占用。

## 场景六：批量 INSERT 慢

**现象**：往 1000 万行的表里 INSERT 10 万行，要 30 秒。

**优化**：

```sql
-- 1. 关掉索引，插完再重建（适合大批量导入）
ALTER INDEX ALL ON TargetTable DISABLE;

-- 批量插入
INSERT INTO TargetTable ...

-- 重建索引
ALTER INDEX ALL ON TargetTable REBUILD;

-- 2. 如果不能关索引，分批插入
DECLARE @BatchSize INT = 5000;
WHILE 1 = 1
BEGIN
    INSERT INTO TargetTable (...)
    SELECT TOP (@BatchSize) ...
    FROM SourceTable s
    WHERE NOT EXISTS (SELECT 1 FROM TargetTable t WHERE t.Id = s.Id);

    IF @@ROWCOUNT < @BatchSize BREAK;
END

-- 3. 用 BULK INSERT 或 SqlBulkCopy（.NET）
-- 比逐行 INSERT 快 10-100 倍
```

## 场景七：DELETE 大量数据慢

**现象**：删除 50 万行，DELETE 跑了 2 分钟还锁着表。

**原因**：一次 DELETE 50 万行 = 一个巨大事务，锁升级到表锁，日志暴涨。

**优化**：分批删。

```sql
DECLARE @BatchSize INT = 5000;
DECLARE @Deleted INT = 1;

WHILE @Deleted > 0
BEGIN
    DELETE TOP (@BatchSize)
    FROM Orders
    WHERE OrderDate < '2020-01-01';

    SET @Deleted = @@ROWCOUNT;

    -- 可选：每批之间等一下，给其他查询留空间
    -- WAITFOR DELAY '00:00:01';
END
```

每次删 5000 行，事务小、锁快速释放。总时间可能差不多，但不会锁住整张表。

## 场景八：EXISTS vs COUNT 判断是否存在

**现象**：代码里用 `COUNT(*) > 0` 判断有没有数据。

```sql
-- ❌ 数了所有匹配行
IF (SELECT COUNT(*) FROM Orders WHERE CustomerId = 100) > 0 ...

-- ✅ 找到第一行就停
IF EXISTS (SELECT 1 FROM Orders WHERE CustomerId = 100) ...
```

COUNT 要数完所有行才能告诉你数量，EXISTS 找到一行就返回 true。百万行表差距明显。

## 通用优化清单

遇到大表慢查询，挨个过一遍：

| 检查项 | 怎么做 |
|--------|--------|
| WHERE 条件有索引吗？ | 看执行计划有没有 Scan |
| 索引覆盖了 SELECT 的列吗？ | 有没有 Key Lookup |
| JOIN 两边都有索引吗？ | 看 JOIN 操作符是不是 Nested Loops + Seek |
| 有没有隐式转换？ | 看 Warning |
| 能不能先过滤减少数据量？ | 临时表 + 索引 |
| 需要 SELECT * 吗？ | 只选需要的列 |
| 分页是不是太深了？ | 键集分页 |
| 统计信息是否最新？ | UPDATE STATISTICS |
| 有没有参数嗅探？ | OPTION (RECOMPILE) |
| 能不能换个思路？ | 缓存/预计算/物化视图 |
