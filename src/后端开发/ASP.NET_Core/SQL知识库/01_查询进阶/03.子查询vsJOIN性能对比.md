# 子查询 vs JOIN 性能对比

"用子查询还是 JOIN？""IN 和 EXISTS 哪个快？"这是被问烂了的问题，但很多回答都是错的。不是说 EXISTS 一定比 IN 快，也不是说 JOIN 一定比子查询快——**要看数据量和执行计划**。

## 先搭个测试环境

```sql
-- 订单表：100 万行
CREATE TABLE Orders (
    OrderId INT PRIMARY KEY IDENTITY,
    CustomerId INT,
    Amount DECIMAL(10,2),
    OrderDate DATE
);

-- 客户表：1 万行
CREATE TABLE Customers (
    CustomerId INT PRIMARY KEY,
    CustomerName NVARCHAR(50),
    City NVARCHAR(50)
);

-- 建索引
CREATE INDEX IX_Orders_CustomerId ON Orders(CustomerId);
```

---

## 场景一：查"有订单的客户"

### 写法对比

```sql
-- 写法1：IN + 子查询
SELECT * FROM Customers
WHERE CustomerId IN (SELECT CustomerId FROM Orders);

-- 写法2：EXISTS
SELECT * FROM Customers c
WHERE EXISTS (SELECT 1 FROM Orders o WHERE o.CustomerId = c.CustomerId);

-- 写法3：INNER JOIN（注意去重）
SELECT DISTINCT c.*
FROM Customers c
INNER JOIN Orders o ON c.CustomerId = o.CustomerId;

-- 写法4：INNER JOIN + GROUP BY
SELECT c.*
FROM Customers c
INNER JOIN (SELECT DISTINCT CustomerId FROM Orders) o
ON c.CustomerId = o.CustomerId;
```

### 性能分析

这个场景下，**IN 和 EXISTS 的执行计划几乎一样**。SQL Server 的优化器足够聪明，会把 IN 子查询自动改写成半连接（Semi Join），和 EXISTS 的执行方式一样。

JOIN 的写法反而可能更慢，因为它要先做完整连接再去重。一个客户有 100 笔订单，JOIN 出来 100 行再 DISTINCT 回 1 行，白算了 99 行。

**结论**：查"存在性"（有没有）用 **EXISTS** 最语义清晰，性能也好。

---

## 场景二：查"没有订单的客户"

```sql
-- 写法1：NOT IN
SELECT * FROM Customers
WHERE CustomerId NOT IN (SELECT CustomerId FROM Orders);

-- 写法2：NOT EXISTS
SELECT * FROM Customers c
WHERE NOT EXISTS (SELECT 1 FROM Orders o WHERE o.CustomerId = c.CustomerId);

-- 写法3：LEFT JOIN + IS NULL
SELECT c.*
FROM Customers c
LEFT JOIN Orders o ON c.CustomerId = o.CustomerId
WHERE o.OrderId IS NULL;
```

### NOT IN 的大坑

::: danger NOT IN 遇到 NULL 会整个查询返回空
如果 Orders 表里有一行 `CustomerId = NULL`，那么 NOT IN 的结果是**空集**。因为 `任何值 NOT IN (..., NULL, ...)` 的结果是 UNKNOWN，WHERE 条件不成立。

```sql
-- 假设 Orders 有一行 CustomerId = NULL
SELECT * FROM Customers WHERE CustomerId NOT IN (1, 2, NULL);
-- 返回 0 行！不是你想要的结果
```
:::

所以**永远不要用 NOT IN**，用 NOT EXISTS 或 LEFT JOIN + IS NULL。这不是性能问题，是正确性问题。

### 性能对比

NOT EXISTS 和 LEFT JOIN + IS NULL 的执行计划通常一样，都是 Anti Semi Join。选哪个看个人习惯。我更偏好 NOT EXISTS，语义更直接。

## 场景三：关联子查询 vs JOIN

```sql
-- 关联子查询：查每个客户的订单总额
SELECT c.CustomerName,
    (SELECT SUM(Amount) FROM Orders o WHERE o.CustomerId = c.CustomerId) AS TotalAmount
FROM Customers c;

-- JOIN 写法
SELECT c.CustomerName, ISNULL(t.TotalAmount, 0) AS TotalAmount
FROM Customers c
LEFT JOIN (
    SELECT CustomerId, SUM(Amount) AS TotalAmount
    FROM Orders GROUP BY CustomerId
) t ON c.CustomerId = t.CustomerId;
```

### 性能差异

**关联子查询**看起来像是"对每个客户执行一次子查询"（N+1 问题），但 SQL Server 的优化器通常会把它改写成 JOIN。所以在执行计划层面，两种写法经常是一样的。

但有些情况优化器改写不了（子查询太复杂、涉及多表），这时候关联子查询真的会变成逐行执行，性能就崩了。

**经验法则**：
- 简单的关联子查询：优化器会搞定，写哪种都行
- 复杂的关联子查询：手动改成 JOIN，别赌优化器的智商

## 场景四：IN vs JOIN 取交集

```sql
-- 查北京客户的订单
-- 写法1：IN
SELECT * FROM Orders
WHERE CustomerId IN (SELECT CustomerId FROM Customers WHERE City = '北京');

-- 写法2：EXISTS
SELECT * FROM Orders o
WHERE EXISTS (
    SELECT 1 FROM Customers c
    WHERE c.CustomerId = o.CustomerId AND c.City = '北京'
);

-- 写法3：JOIN
SELECT o.*
FROM Orders o
INNER JOIN Customers c ON o.CustomerId = c.CustomerId
WHERE c.City = '北京';
```

这三种在有索引的情况下，**执行计划基本一样**。优化器都会选择最优的连接方式。

但如果子查询返回的数据量很大（比如几十万个 ID），IN 写法可能会有问题——它要把这些 ID 全部放内存里做比较。这种情况 JOIN 更稳。

---

## 真正影响性能的因素

与其纠结 IN 还是 EXISTS，不如关注这些：

### 1. 有没有索引

```sql
-- 没索引：不管用什么写法，Orders 表都要全表扫描
-- 有索引：IN/EXISTS/JOIN 执行计划都差不多

-- 关键索引
CREATE INDEX IX_Orders_CustomerId ON Orders(CustomerId);
CREATE INDEX IX_Customers_City ON Customers(City) INCLUDE (CustomerId);
```

### 2. 数据量的比例

| 外表（驱动表） | 内表（被查表） | 推荐写法 |
|---|---|---|
| 小（千级） | 大（百万级） | EXISTS / IN 都行 |
| 大 | 小 | JOIN / IN（子查询结果集小） |
| 大 | 大 | 看索引，看执行计划 |

### 3. 是否需要去重

- 只判断"有没有" → EXISTS（不会多产生行）
- 需要取对方表的字段 → JOIN
- JOIN 会导致一对多膨胀，如果只要左表结果要 DISTINCT

### 4. NULL 值

- IN 遇到 NULL → 大坑（前面说了）
- EXISTS 遇到 NULL → 没问题
- JOIN 遇到 NULL → ON 条件里 NULL = NULL 不成立，不会匹配

---

## 速查结论

| 场景 | 推荐写法 | 理由 |
|------|---------|------|
| 判断"存在" | EXISTS | 语义清晰，不受 NULL 影响 |
| 判断"不存在" | NOT EXISTS | NOT IN 有 NULL 陷阱 |
| 取对方表字段 | JOIN | 必须 JOIN 才能取到 |
| 子查询结果集小且固定 | IN | 简洁 |
| SELECT 里的关联子查询 | 简单的就写，复杂的改 JOIN | 简单的优化器会改写 |

**最终原则**：别猜，打开执行计划看。`SET STATISTICS IO ON` 看逻辑读次数，哪个少用哪个。

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

-- 跑你的两种写法，对比 logical reads 和 CPU time
SELECT ...
```
