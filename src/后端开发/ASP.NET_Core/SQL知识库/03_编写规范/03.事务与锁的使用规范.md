# 事务与锁的使用规范

事务用不好要么数据不一致，要么死锁满天飞。这篇讲在 SQL Server 里怎么正确使用事务，以及锁相关的注意事项。

## 事务基础

### 显式事务模板

```sql
BEGIN TRY
    BEGIN TRANSACTION;

    -- 业务操作 1
    UPDATE Accounts SET Balance = Balance - 100 WHERE AccountId = 1;

    -- 业务操作 2
    UPDATE Accounts SET Balance = Balance + 100 WHERE AccountId = 2;

    -- 记录日志
    INSERT INTO TransferLog (FromId, ToId, Amount, CreateTime)
    VALUES (1, 2, 100, GETDATE());

    COMMIT TRANSACTION;
END TRY
BEGIN CATCH
    IF @@TRANCOUNT > 0
        ROLLBACK TRANSACTION;

    -- 记录错误信息
    DECLARE @ErrMsg NVARCHAR(4000) = ERROR_MESSAGE();
    DECLARE @ErrSev INT = ERROR_SEVERITY();
    RAISERROR(@ErrMsg, @ErrSev, 1);
END CATCH;
```

**关键点**：
- `BEGIN TRY ... END TRY` + `BEGIN CATCH ... END CATCH` 是标准结构
- CATCH 块里先判断 `@@TRANCOUNT > 0` 再 ROLLBACK，防止重复回滚
- 不要吞掉错误——至少 RAISERROR 或 THROW 出去

### SET XACT_ABORT ON

```sql
SET XACT_ABORT ON;  -- 推荐在存储过程开头加这行

BEGIN TRANSACTION;
-- 如果任何语句出错，自动回滚整个事务
UPDATE ...;
INSERT ...;
COMMIT TRANSACTION;
```

没有 `SET XACT_ABORT ON` 的话，某些错误（比如约束冲突）会终止当前语句但不回滚事务，你的事务处于半提交状态很危险。

**建议**：所有存储过程开头都加 `SET XACT_ABORT ON; SET NOCOUNT ON;`。

## 事务规范

### 1. 事务要尽量短

```sql
-- ❌ 事务里做了太多事
BEGIN TRANSACTION;
-- 查数据
SELECT ... INTO #temp FROM BigTable WHERE ...;
-- 复杂计算
-- 调外部接口（通过 CLR 或 xp_cmdshell）
-- 更新数据
UPDATE ...;
COMMIT;

-- ✅ 只把必须原子的操作放事务里
-- 先在事务外准备好数据
SELECT ... INTO #temp FROM BigTable WHERE ...;
-- 做完计算

-- 事务里只做写操作
BEGIN TRANSACTION;
UPDATE ...;
INSERT ...;
COMMIT;
```

事务持续时间越长 → 持有锁的时间越长 → 阻塞其他查询的概率越大。

### 2. 不要在事务里等用户输入

这在前端直连数据库的老架构里常见（好在现在基本不会了）。事务打开后等用户点"确认"，锁一直拿着。

### 3. 按固定顺序访问表

```sql
-- ❌ 两个事务以不同顺序访问表 → 死锁
-- 事务 A: 先锁 Orders 再锁 Inventory
-- 事务 B: 先锁 Inventory 再锁 Orders

-- ✅ 所有事务按同一顺序：先 Inventory 后 Orders
```

死锁的根本原因是交叉等待。如果团队约定所有事务按固定顺序访问表（比如按表名字母序），死锁概率大大降低。

### 4. 避免大事务

一个事务涉及几万行数据 → 锁升级到表锁 → 阻塞所有人。

```sql
-- ❌ 一次更新 10 万行
BEGIN TRANSACTION;
UPDATE Orders SET Status = 2 WHERE Status = 1 AND CreateDate < '2023-01-01';
-- 可能影响 10 万行，锁升级
COMMIT;

-- ✅ 分批更新
DECLARE @batch INT = 5000;
WHILE 1 = 1
BEGIN
    BEGIN TRANSACTION;
    UPDATE TOP (@batch) Orders SET Status = 2
    WHERE Status = 1 AND CreateDate < '2023-01-01';
    IF @@ROWCOUNT = 0 BEGIN COMMIT; BREAK; END
    COMMIT;
END
```

## 隔离级别

SQL Server 默认是 **READ COMMITTED**（读已提交），大多数场景够用。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 性能 |
|----------|------|-----------|------|------|
| READ UNCOMMITTED | ✅ 有 | ✅ 有 | ✅ 有 | 最快 |
| READ COMMITTED | ❌ 无 | ✅ 有 | ✅ 有 | 默认 |
| REPEATABLE READ | ❌ 无 | ❌ 无 | ✅ 有 | 较慢 |
| SERIALIZABLE | ❌ 无 | ❌ 无 | ❌ 无 | 最慢 |
| SNAPSHOT | ❌ 无 | ❌ 无 | ❌ 无 | 好（用版本控制） |

### NOLOCK 到底能不能用

```sql
SELECT * FROM Orders WITH (NOLOCK);
-- 等于 READ UNCOMMITTED，可以读到其他事务还没提交的数据（脏读）
```

**能用的场景**：报表统计、数据展示、对精确度要求不高的查询。多读一行少读一行无所谓。

**不能用的场景**：涉及金额、库存、状态判断的关键业务逻辑。读到脏数据可能导致业务错误。

**更好的选择**：开启 READ COMMITTED SNAPSHOT ISOLATION (RCSI)。

```sql
-- 数据库级别开启（只需执行一次）
ALTER DATABASE YourDB SET READ_COMMITTED_SNAPSHOT ON;
```

开启后，SELECT 默认读的是行的"快照版本"，不加锁也不读脏数据。写操作还是正常加锁。这是大多数场景的最优选择。

## 死锁处理

### 排查死锁

```sql
-- 开启 1222 跟踪标志，死锁信息写到错误日志
DBCC TRACEON(1222, -1);

-- 或用扩展事件
CREATE EVENT SESSION [DeadlockCapture] ON SERVER
ADD EVENT sqlserver.xml_deadlock_report
ADD TARGET package0.event_file(SET filename=N'DeadlockCapture')
WITH (STARTUP_STATE=ON);
```

### 死锁重试

在应用层加重试逻辑：

```csharp
// C# 示例
int retryCount = 3;
while (retryCount > 0)
{
    try
    {
        await ExecuteTransactionAsync();
        break;
    }
    catch (SqlException ex) when (ex.Number == 1205) // 死锁
    {
        retryCount--;
        if (retryCount == 0) throw;
        await Task.Delay(100); // 等一下再重试
    }
}
```

### 减少死锁的手段

1. 所有事务按固定顺序访问表
2. 事务尽量短
3. 给 WHERE 条件加索引（减少锁的范围，行锁而不是表锁）
4. 开启 RCSI
5. 避免锁升级（分批操作）

## 常用锁提示

| 提示 | 含义 | 场景 |
|------|------|------|
| NOLOCK | 不加共享锁 | 非关键查询 |
| ROWLOCK | 强制行锁 | 防止锁升级 |
| UPDLOCK | 加更新锁（先读后改） | 防止死锁的 SELECT + UPDATE 模式 |
| HOLDLOCK | 持有共享锁到事务结束 | 可重复读语义 |
| TABLOCK | 表锁 | 大批量导入 |

### 经典模式：SELECT + UPDATE 防死锁

```sql
-- 先读后改一行，两个事务都这样做容易死锁
-- 用 UPDLOCK 解决

BEGIN TRANSACTION;

SELECT @balance = Balance
FROM Accounts WITH (UPDLOCK)
WHERE AccountId = 1;

-- 计算新余额
SET @newBalance = @balance - 100;

UPDATE Accounts SET Balance = @newBalance WHERE AccountId = 1;

COMMIT;
```

UPDLOCK 在 SELECT 时就加了更新锁，其他事务不能同时 UPDLOCK 同一行，避免了两个事务互相等待的死锁。
