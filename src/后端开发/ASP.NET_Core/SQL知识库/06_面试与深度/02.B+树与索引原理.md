# B+ 树与索引原理

面试被问"索引为什么快"，不能只说"加了索引就快"。要理解底层的 B+ 树结构。

## 为什么用 B+ 树

数据库的数据存在磁盘上，磁盘 IO 是最大的性能瓶颈。B+ 树的设计目标就是**用最少的磁盘 IO 找到数据**。

- **二叉树**：高度 log₂(N)。100 万行 → 高度 20 → 最多 20 次 IO。太多了。
- **B+ 树**：每个节点存几百个 key。100 万行 → 高度只有 3-4 → 最多 3-4 次 IO。

## B+ 树结构

```
                    [Root: 50, 100]
                   /       |        \
    [Leaf: 10,20,30,40] [Leaf: 50,60,70,80] [Leaf: 100,110,120]
         ↓↓↓↓              ↓↓↓↓                ↓↓↓↓
       数据行            数据行              数据行
```

**特点**：
1. **非叶子节点只存 key + 指针**，不存数据 → 一个页能放更多 key → 树更矮
2. **数据全在叶子节点**
3. **叶子节点之间有双向链表** → 范围查询可以顺着链表扫，不用回根节点

## SQL Server 的页和区

- **页（Page）**：8KB，是最小的 IO 单位。读一条记录也要读整个 8KB 页
- **区（Extent）**：8 个连续页 = 64KB
- 一个 B+ 树节点 = 一个 8KB 页

假设索引 key 是 INT（4 字节），加上指针（6 字节），一个页能装约 800 个 key。

- 高度 1（根）：800 个 key
- 高度 2：800 × 800 = 64 万
- 高度 3：800 × 800 × 800 = 5.12 亿

所以大多数表的索引只有 **3 层**，找任何一条记录最多 3 次磁盘 IO。

## 聚集索引

- 每张表只能有**一个**聚集索引
- 叶子节点就是**数据行本身**
- 数据按聚集索引的顺序物理排列
- 默认是主键

```
[Root: 50, 100]
    ↓
[Leaf: 数据行1, 数据行2, ..., 数据行N]  ← 叶子节点 = 实际数据
```

## 非聚集索引

- 每张表可以有多个
- 叶子节点存的是 **索引 key + 聚集索引 key（书签）**
- 查到索引后如果需要其他列，还要**回表（Key Lookup）**

```
非聚集索引：
[Root: 北京, 上海]
    ↓
[Leaf: 北京→主键5, 北京→主键12, 上海→主键3, ...]
                ↓
          根据主键 5 去聚集索引找完整数据行（回表）
```

## 覆盖索引

如果非聚集索引的叶子节点**包含了查询需要的所有列**，就不用回表了：

```sql
-- 查询
SELECT OrderDate, Amount FROM Orders WHERE CustomerId = 100;

-- 覆盖索引（INCLUDE 了 SELECT 需要的列）
CREATE INDEX IX ON Orders(CustomerId) INCLUDE (OrderDate, Amount);
-- 叶子节点：CustomerId + OrderDate + Amount → 不用回表
```

## 索引 Seek vs Scan

| 操作 | 含义 | 性能 |
|------|------|------|
| Index Seek | 从根到叶，精确定位 | O(log N)，快 |
| Index Scan | 扫描整个索引的叶子层 | O(N)，慢 |
| Table Scan | 扫描整个堆（没聚集索引的表） | O(N)，最慢 |

目标是让查询走 **Seek 而不是 Scan**。

## 索引的代价

索引不是越多越好：

1. **写入变慢**：每次 INSERT/UPDATE/DELETE 都要维护所有索引
2. **占用空间**：每个索引都是一棵独立的 B+ 树
3. **索引碎片**：频繁更新导致页分裂，需要定期重建

## 面试回答模板

> 问：索引为什么能加速查询？

回答：SQL Server 的索引基于 B+ 树结构。非叶子节点只存 key 和指针，一个 8KB 页能存几百个 key。100 万行的表索引高度只有 3 层，找任何一条记录最多 3 次磁盘 IO。相比全表扫描要读几千个页，索引 Seek 的 IO 少了几个数量级。
