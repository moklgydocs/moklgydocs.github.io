# ASP.NET Core 请求管道（Middleware Pipeline）：源码级深入

---

## 一、先建立一个核心认知

> **中间件管道的本质就是"函数套函数"。整条管道最终就是一个 `RequestDelegate`，也就是一个 `Func<HttpContext, Task>`。**

```csharp
// 这就是整个管道的类型签名，简单到不能再简单
public delegate Task RequestDelegate(HttpContext context);

// 整条管道 = 一个函数
// 传入 HttpContext，返回 Task
// 就这么简单
```

---

## 二、从最底层开始：三种注册中间件的方式

### 方式1：`app.Use()` —— 最原始的方式

```csharp
// 📁 源码位置: src/Http/Http/src/Builder/ApplicationBuilder.cs

// Use 方法签名
public IApplicationBuilder Use(Func<RequestDelegate, RequestDelegate> middleware);
```

理解这个签名：

```
Func<RequestDelegate, RequestDelegate>
     ───────────────  ───────────────
          输入              输出
      "下一个中间件"    "包裹后的新中间件"
```

实际使用：

```csharp
app.Use(next =>          // next = 下一个中间件(RequestDelegate)
{
    return async context =>   // 返回一个新的 RequestDelegate
    {
        Console.WriteLine("Before");   // 前处理
        await next(context);            // 调用下一个
        Console.WriteLine("After");    // 后处理
    };
});
```

### 方式2：`app.Use(async (context, next) => ...)` —— 语法糖

```csharp
// 📁 源码位置: src/Http/Http/src/Builder/UseExtensions.cs

public static IApplicationBuilder Use(
    this IApplicationBuilder app,
    Func<HttpContext, RequestDelegate, Task> middleware)  // 👈 语法糖
{
    // 内部转换成方式1的形式
    return app.Use(next =>
    {
        return context => middleware(context, next);  // 包装一下而已
    });
}
```

使用起来更直观：

```csharp
app.Use(async (context, next) =>
{
    Console.WriteLine("Before");
    await next(context);
    Console.WriteLine("After");
});
```

### 方式3：`app.UseMiddleware<T>()` —— 基于类的中间件

```csharp
// 📁 源码位置: src/Http/Http/src/Builder/UseMiddlewareExtensions.cs

public static IApplicationBuilder UseMiddleware<TMiddleware>(
    this IApplicationBuilder app, params object[] args)
{
    return app.UseMiddleware(typeof(TMiddleware), args);
}
```

你写一个中间件类：

```csharp
public class MyMiddleware
{
    private readonly RequestDelegate _next;

    // 构造函数注入 next（管道中的下一个）
    public MyMiddleware(RequestDelegate next)
    {
        _next = next;
    }

    // 约定方法名：Invoke 或 InvokeAsync
    public async Task InvokeAsync(HttpContext context, ILogger<MyMiddleware> logger)
    //                                                  ^^^^^^^^^^^^^^^^^^^^^^
    //                                            支持从DI注入额外参数！
    {
        logger.LogInformation("Before");
        await _next(context);
        logger.LogInformation("After");
    }
}
```

**`UseMiddleware<T>()` 的源码核心逻辑：**

```csharp
// 📁 源码位置: src/Http/Http/src/Builder/UseMiddlewareExtensions.cs
// 简化后的核心逻辑

public static IApplicationBuilder UseMiddleware(
    this IApplicationBuilder app, Type middleware, params object[] args)
{
    // 检查是否实现了 IMiddleware 接口
    if (typeof(IMiddleware).IsAssignableFrom(middleware))
    {
        // 工厂模式（后面讲）
        return UseMiddlewareInterface(app, middleware);
    }

    return app.Use(next =>
    {
        // 🔥 通过反射找到 Invoke 或 InvokeAsync 方法
        var methods = middleware.GetMethods(BindingFlags.Instance | BindingFlags.Public);
        var invokeMethods = methods.Where(m =>
            string.Equals(m.Name, "Invoke", StringComparison.Ordinal) ||
            string.Equals(m.Name, "InvokeAsync", StringComparison.Ordinal)
        ).ToArray();

        // 必须恰好有一个 Invoke/InvokeAsync 方法
        if (invokeMethods.Length != 1)
            throw new InvalidOperationException("...");

        var methodInfo = invokeMethods[0];

        // 第一个参数必须是 HttpContext
        if (!typeof(HttpContext).IsAssignableFrom(methodInfo.GetParameters()[0].ParameterType))
            throw new InvalidOperationException("...");

        // 🔥 创建中间件实例（构造函数中注入 next 和其他参数）
        var instance = ActivatorUtilities.CreateInstance(app.ApplicationServices, 
            middleware, 
            new object[] { next }.Concat(args).ToArray());

        // 🔥 如果 Invoke 方法只有一个 HttpContext 参数，直接创建委托
        if (methodInfo.GetParameters().Length == 1)
        {
            return (RequestDelegate)methodInfo.CreateDelegate(
                typeof(RequestDelegate), instance);
        }

        // 🔥 如果有额外参数（DI注入的），用表达式树编译一个委托
        // 运行时从 HttpContext.RequestServices 中解析额外参数
        var factory = Compile<object>(methodInfo, parameters);
        return context =>
        {
            var serviceProvider = context.RequestServices;  // 👈 请求级别的DI
            // ... 解析参数并调用
            return factory(instance, context, serviceProvider);
        };
    });
}
```

**关键发现：**

```
┌──────────────────────────────────────────────────────────────────┐
│ 基于约定的中间件（不实现IMiddleware）                               │
│                                                                  │
│ 1. 构造函数中的参数 → 从根 DI 容器解析 (Singleton 级别)            │
│ 2. Invoke方法中的参数 → 从请求 DI Scope 解析 (Scoped 级别)        │
│ 3. 中间件实例本身 → Singleton（只创建一次！）                       │
│                                                                  │
│ ⚠️  所以：不要在中间件的构造函数中注入 Scoped 服务！               │
│     应该在 InvokeAsync 的参数中注入                                │
└──────────────────────────────────────────────────────────────────┘
```

### IMiddleware 接口 —— 另一种方式

```csharp
// 📁 源码位置: src/Http/Http.Abstractions/src/IMiddleware.cs
public interface IMiddleware
{
    Task InvokeAsync(HttpContext context, RequestDelegate next);
}

// 使用这种方式的中间件：
// 1. 从DI容器解析（可以是Scoped/Transient）
// 2. 但 Invoke 方法签名固定，不支持额外DI参数
```

## 三、管道构建的核心：`ApplicationBuilder.Build()`

这是整个管道系统最核心的代码，我们逐行分析：

```csharp
// 📁 源码位置: src/Http/Http/src/Builder/ApplicationBuilder.cs

public class ApplicationBuilder : IApplicationBuilder
{
    // 存储所有中间件的列表
    private readonly List<Func<RequestDelegate, RequestDelegate>> _components = new();
    
    public IApplicationBuilder Use(Func<RequestDelegate, RequestDelegate> middleware)
    {
        _components.Add(middleware);
        return this;  // 返回自身，支持链式调用
    }

    public RequestDelegate Build()
    {
        // ======================================
        // 第1步：管道末端 —— 404处理
        // ======================================
        RequestDelegate app = context =>
        {
            // 如果没有任何中间件处理这个请求
            // 检查是否已经设置了状态码
            if (!context.Response.HasStarted)
            {
                context.Response.StatusCode = StatusCodes.Status404NotFound;
            }
            return Task.CompletedTask;
        };

        // ======================================
        // 第2步：从后往前遍历，构建套娃
        // ======================================
        for (var c = _components.Count - 1; c >= 0; c--)
        {
            app = _components[c](app);  
            // 把当前的 app（下一个中间件）传给当前中间件
            // 返回新的 app（包裹了当前中间件的 RequestDelegate）
        }

        return app;
    }
}
```

### 用一个完整例子演示构建过程

```csharp
// 你写的代码：
app.Use(async (context, next) =>    // 中间件A：日志
{
    Console.WriteLine("[A] 请求进入");
    await next(context);
    Console.WriteLine("[A] 响应返回");
});

app.Use(async (context, next) =>    // 中间件B：计时
{
    var sw = Stopwatch.StartNew();
    await next(context);
    sw.Stop();
    Console.WriteLine($"[B] 耗时: {sw.ElapsedMilliseconds}ms");
});

app.Use(async (context, next) =>    // 中间件C：处理请求
{
    Console.WriteLine("[C] 处理请求");
    context.Response.StatusCode = 200;
    await context.Response.WriteAsync("Hello!");
    // 注意：没有调用 next()，管道到此终止（短路）
});
```

**Build() 的执行过程：**

```
_components 列表：[ A, B, C ]   （按注册顺序）

初始状态：
  app = context => { context.Response.StatusCode = 404; }   // 404兜底

─── 第1轮：c = 2（中间件C，最后注册的）───
  app = C(404兜底)
  
  展开就是：
  app = async context => {
      Console.WriteLine("[C] 处理请求");
      context.Response.StatusCode = 200;
      await context.Response.WriteAsync("Hello!");
      // C没有调用next，所以404兜底永远不会执行
  }

─── 第2轮：c = 1（中间件B）───
  app = B(C(404兜底))
  
  展开就是：
  app = async context => {
      var sw = Stopwatch.StartNew();
      
      await [C的逻辑](context);  // next指向C
      
      sw.Stop();
      Console.WriteLine($"[B] 耗时: ...");
  }

─── 第3轮：c = 0（中间件A）───
  app = A(B(C(404兜底)))
  
  展开就是：
  app = async context => {
      Console.WriteLine("[A] 请求进入");
      
      await [B的逻辑](context);  // next指向B
      
      Console.WriteLine("[A] 响应返回");
  }

最终结果：一个 RequestDelegate，就是 A(B(C(404)))
```

**执行时的输出：**

```
[A] 请求进入
[B] (开始计时)
[C] 处理请求
[B] 耗时: 5ms
[A] 响应返回
```

## 四、短路（Short-Circuiting）—— 中间件的关键行为

```csharp
// 短路 = 不调用 next()
app.Use(async (context, next) =>
{
    if (context.Request.Path == "/health")
    {
        // 直接返回，不调用 next()
        // 后续中间件（认证、授权、路由等）全部被跳过
        context.Response.StatusCode = 200;
        await context.Response.WriteAsync("OK");
        return;  // ⛔ 短路！
    }
    
    await next(context);  // 其他请求正常传递
});
```

**哪些内置中间件会短路？**

```
┌─────────────────────────┬───────────────────────────────────────────┐
│ 中间件                   │ 短路条件                                   │
├─────────────────────────┼───────────────────────────────────────────┤
│ StaticFiles             │ 请求匹配到静态文件 → 直接返回文件内容        │
│ ResponseCaching         │ 缓存命中 → 直接返回缓存                     │
│ CORS                    │ OPTIONS预检请求 → 直接返回CORS头            │
│ Authorization           │ 授权失败 → 返回401/403，不继续              │
│ ExceptionHandler        │ 不短路，但捕获后续异常后替换响应             │
└─────────────────────────┴───────────────────────────────────────────┘
```

## 五、`app.Map()` 和 `app.UseWhen()` —— 管道分支

### `app.Map()` —— 按路径分叉

```csharp
// 📁 源码位置: src/Http/Http/src/Builder/MapExtensions.cs

public static IApplicationBuilder Map(
    this IApplicationBuilder app, 
    PathString pathMatch,
    Action<IApplicationBuilder> configuration)
{
    // 🔥 创建一个新的分支管道
    var branchBuilder = app.New();  // 新的 ApplicationBuilder
    configuration(branchBuilder);    // 在分支上配置中间件
    var branch = branchBuilder.Build();  // 构建分支管道

    // 在主管道中添加一个"路由中间件"
    return app.Use(next => async context =>
    {
        if (context.Request.Path.StartsWithSegments(pathMatch, out var remaining))
        {
            // 匹配成功 → 走分支管道
            var previousPath = context.Request.Path;
            var previousPathBase = context.Request.PathBase;
            
            context.Request.PathBase += pathMatch;
            context.Request.Path = remaining;
            
            await branch(context);  // 👈 执行分支管道
            
            // 恢复路径
            context.Request.Path = previousPath;
            context.Request.PathBase = previousPathBase;
        }
        else
        {
            // 不匹配 → 走主管道的下一个中间件
            await next(context);
        }
    });
}
```

**管道分支示意图：**

```
                    请求进入
                       │
                       ▼
                ┌──────────────┐
                │ Middleware A  │
                └──────┬───────┘
                       │
                       ▼
              路径是 /api/* ?
              ┌────┴────┐
              │ Yes     │ No
              ▼         ▼
        ┌──────────┐  ┌──────────┐
        │ API分支   │  │ 主管道    │
        │ 管道      │  │ 继续      │
        │ ┌──────┐ │  │ ┌──────┐ │
        │ │Auth  │ │  │ │Static│ │
        │ │JSON  │ │  │ │Files │ │
        │ │Route │ │  │ │MVC   │ │
        │ └──────┘ │  │ └──────┘ │
        └──────────┘  └──────────┘
```

### `app.UseWhen()` —— 条件性插入（不分叉）

```csharp
// 📁 源码位置: src/Http/Http/src/Builder/UseWhenExtensions.cs

public static IApplicationBuilder UseWhen(
    this IApplicationBuilder app,
    Func<HttpContext, bool> predicate,
    Action<IApplicationBuilder> configuration)
{
    var branchBuilder = app.New();
    configuration(branchBuilder);

    return app.Use(main =>
    {
        // 🔥 分支管道的末端连接回主管道
        branchBuilder.Run(main);  // 👈 区别在这里！
        var branch = branchBuilder.Build();

        return async context =>
        {
            if (predicate(context))
            {
                await branch(context);   // 走分支，分支末端会回到主管道
            }
            else
            {
                await main(context);     // 直接走主管道
            }
        };
    });
}
```

**Map vs UseWhen 的区别：**

```
Map (分叉，不回来)：
    主管道: A → B → [Map判断] → C → D
                        │
                        └──► 分支: X → Y → Z (结束，不回主管道)

UseWhen (条件执行，然后回来)：
    主管道: A → B → [UseWhen判断] → C → D
                        │                ▲
                        └──► 分支: X → Y ─┘  (回到主管道的C)
```

## 六、`app.Run()` 中间件 vs `app.Use()` 中间件

```csharp
// 📁 源码位置: src/Http/Http/src/Builder/RunExtensions.cs

public static void Run(this IApplicationBuilder app, RequestDelegate handler)
{
    app.Use(_ => handler);  // 忽略next，直接执行handler
    //         ▲
    //     不使用 next！所以后面的中间件永远不会执行
}
```

```csharp
// Run = 终端中间件，管道到此为止
app.Use(async (context, next) =>
{
    // 可以选择是否调用 next
    await next(context);
});

app.Run(async context =>
{
    // 没有 next 参数，无法传递
    // 这是管道的终点
    await context.Response.WriteAsync("End of pipeline");
});

app.Use(async (context, next) =>
{
    // ⚠️ 这个永远不会执行！因为上面的 Run 不会调用 next
    await next(context);
});
```

## 七、真实的 ASP.NET Core 管道长什么样

当你写一个典型的Web应用时，管道的实际结构：

```csharp
var app = builder.Build();

app.UseExceptionHandler("/Error");    // 1
app.UseHsts();                        // 2
app.UseHttpsRedirection();            // 3
app.UseStaticFiles();                 // 4
app.UseRouting();                     // 5  ⭐
app.UseCors();                        // 6
app.UseAuthentication();              // 7  ⭐⭐⭐
app.UseAuthorization();               // 8  ⭐⭐⭐
app.MapControllers();                 // 9  (在UseEndpoints内部)
```

**完整的请求流转：**

```
HTTP请求: GET /api/users (带JWT Token)
│
▼
┌──────────────────────────────────────────────────────────────────────┐
│ ① ExceptionHandler                                                  │
│    try {                                                             │
│        await next(context);  // 包裹后续所有中间件                      │
│    } catch (Exception ex) {                                          │
│        // 如果后续任何中间件抛异常，在这里捕获                            │
│        // 重定向到 /Error                                             │
│    }                                                                 │
├──────────────────────────────────────────────────────────────────────┤
│ ② HSTS                                                              │
│    添加 Strict-Transport-Security 响应头                              │
│    await next(context);                                              │
├──────────────────────────────────────────────────────────────────────┤
│ ③ HTTPS Redirection                                                 │
│    if (不是HTTPS) { 重定向到HTTPS; return; }  // 可能短路              │
│    await next(context);                                              │
├──────────────────────────────────────────────────────────────────────┤
│ ④ Static Files                                                      │
│    if (请求匹配静态文件) { 返回文件; return; }  // 可能短路             │
│    await next(context);  // /api/users 不是静态文件，继续               │
├──────────────────────────────────────────────────────────────────────┤
│ ⑤ Routing (UseRouting)                                              │
│    从所有注册的Endpoint中，找到匹配的那个                               │
│    context.SetEndpoint(matchedEndpoint);  // 👈 设置到HttpContext上    │
│    // 注意：这里只是"匹配"，不执行！                                    │
│    await next(context);                                              │
├──────────────────────────────────────────────────────────────────────┤
│ ⑥ CORS                                                              │
│    根据Endpoint的CORS策略，处理跨域                                    │
│    await next(context);                                              │
├──────────────────────────────────────────────────────────────────────┤
│ ⑦ Authentication  ⭐                                                │
│    var endpoint = context.GetEndpoint();                              │
│    // 获取默认的认证方案（如JWT Bearer）                                │
│    var result = await context.AuthenticateAsync(defaultScheme);       │
│    if (result.Succeeded)                                             │
│    {                                                                 │
│        context.User = result.Principal;  // 👈 设置用户身份!           │
│        // ClaimsPrincipal，包含了JWT中的所有Claims                     │
│    }                                                                 │
│    await next(context);                                              │
├──────────────────────────────────────────────────────────────────────┤
│ ⑧ Authorization  ⭐                                                 │
│    var endpoint = context.GetEndpoint();                              │
│    var authorizeData = endpoint.Metadata.GetOrderedMetadata           │
│                            <IAuthorizeData>();                        │
│    // 获取 [Authorize] 特性中的策略                                    │
│    var policy = await policyProvider.GetPolicyAsync(authorizeData);   │
│    var authResult = await authorizationService                        │
│                        .AuthorizeAsync(context.User, policy);        │
│    if (!authResult.Succeeded)                                        │
│    {                                                                 │
│        // 授权失败 → Challenge(401) 或 Forbid(403)                    │
│        return;  // ⛔ 短路！                                         │
│    }                                                                 │
│    await next(context);                                              │
├──────────────────────────────────────────────────────────────────────┤
│ ⑨ Endpoint Execution (UseEndpoints / MapControllers)                │
│    var endpoint = context.GetEndpoint();                              │
│    await endpoint.RequestDelegate(context);                          │
│    // 执行你的 Controller Action                                     │
│    // UsersController.GetUsers()                                     │
│    // 写入 Response Body: [{"id":1,"name":"张三"}, ...]               │
└──────────────────────────────────────────────────────────────────────┘
│
│  然后响应原路返回：⑨ → ⑧ → ⑦ → ⑥ → ⑤ → ④ → ③ → ② → ①
│  每个中间件的"await next(context)"之后的代码依次执行
│
▼
HTTP响应: 200 OK
```

## 八、深入 Routing 中间件 —— UseRouting() 和 UseEndpoints() 的协作

这是ASP.NET Core 3.0+ 引入的**Endpoint Routing**，理解它对理解OpenIddict至关重要。

### 为什么分成两步？

```csharp
app.UseRouting();       // 步骤1：匹配Endpoint（但不执行）
// ... 中间这些中间件可以访问匹配结果 ...
app.UseAuthentication();  // 可以知道匹配到了哪个Endpoint
app.UseAuthorization();   // 可以读取Endpoint上的[Authorize]元数据
app.UseEndpoints(...);  // 步骤2：执行匹配到的Endpoint
```

**如果不分开，会怎样？**

```
如果路由和执行在一起（旧版）：
  请求 → 路由匹配+执行 → 认证 → 授权
                                    ▲
                                    │
                              已经执行完了！
                              授权检查太晚了！

分开后（新版Endpoint Routing）：
  请求 → 路由匹配（只匹配，不执行）→ 认证 → 授权 → 路由执行
                                                        ▲
                                              授权通过才执行！✅
```

internal sealed class EndpointRoutingMiddleware

    private readonly RequestDelegate _next;

    public async Task Invoke(HttpContext httpContext)

## 九、Authentication 中间件源码（对SSO最关键）

```csharp
// 📁 源码位置: src/Security/Authentication/Core/src/AuthenticationMiddleware.cs

public class AuthenticationMiddleware
{
    private readonly RequestDelegate _next;

    public async Task Invoke(HttpContext context)
    {
        // 🔥 第1步：设置当前请求的认证方案处理器
        context.Features.Set<IAuthenticationFeature>(new AuthenticationFeature
        {
            OriginalPath = context.Request.Path,
            OriginalPathBase = context.Request.PathBase
        });

        // 🔥 第2步：获取认证方案提供者
        var handlers = context.RequestServices
            .GetRequiredService<IAuthenticationHandlerProvider>();

        // 🔥 第3步：遍历所有方案，找"请求处理器"
        foreach (var scheme in await Schemes.GetRequestHandlerSchemesAsync())
        {
            var handler = await handlers.GetHandlerAsync(context, scheme.Name)
                as IAuthenticationRequestHandler;
                
            if (handler != null && await handler.HandleRequestAsync())
            {
                // ⛔ 如果某个Handler处理了请求（比如OAuth回调），直接返回
                // OpenIddict 的 /connect/token 端点就是在这里被处理的！！！ ⭐⭐⭐
                return;
            }
        }

        // 🔥 第4步：执行默认认证方案
        var defaultAuthenticate = await Schemes.GetDefaultAuthenticateSchemeAsync();
        if (defaultAuthenticate != null)
        {
            var result = await context.AuthenticateAsync(defaultAuthenticate.Name);
            if (result?.Principal != null)
            {
                context.User = result.Principal;  // 👈 设置用户身份
            }
            if (result?.Succeeded ?? false)
            {
                // 认证成功的日志
                var authFeatures = new AuthenticationFeatures(result);
                context.Features.Set<IHttpAuthenticationFeature>(authFeatures);
            }
        }

        // 🔥 第5步：继续管道
        await _next(context);
    }
}
```

**关键发现：**

```
┌──────────────────────────────────────────────────────────────────────┐
│                                                                      │
│  🔥 认证中间件的两大职责：                                             │
│                                                                      │
│  1. IAuthenticationRequestHandler.HandleRequestAsync()               │
│     → 处理特殊的认证请求（如 OAuth 回调、Token 端点）                   │
│     → OpenIddict 的服务器端点就是通过这个机制嵌入管道的！                │
│     → 如果返回 true，整个管道短路，后续中间件不执行                      │
│                                                                      │
│  2. context.AuthenticateAsync(defaultScheme)                         │
│     → 解析普通请求中的身份信息（Cookie、JWT Token等）                   │
│     → 设置 context.User                                              │
│     → 不管成功失败都继续管道（不短路）                                  │
│                                                                      │
│  ⚠️ 注意：认证中间件不负责"拒绝请求"！                                │
│     认证失败也会继续执行。拒绝是 Authorization 中间件的事。             │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

## 十、自己从零实现一个极简中间件管道

为了彻底理解本质，我们用50行代码实现核心机制：

```csharp
using System;
using System.Collections.Generic;
using System.Threading.Tasks;

// ========== 极简实现 ==========

// 模拟 HttpContext
class MyHttpContext
{
    public string RequestPath { get; set; } = "/";
    public int StatusCode { get; set; } = 200;
    public string ResponseBody { get; set; } = "";
}

// 模拟 RequestDelegate
delegate Task MyRequestDelegate(MyHttpContext context);

// 模拟 ApplicationBuilder
class MyAppBuilder
{
    private readonly List<Func<MyRequestDelegate, MyRequestDelegate>> _middlewares = new();

    public void Use(Func<MyRequestDelegate, MyRequestDelegate> middleware)
        => _middlewares.Add(middleware);

    public MyRequestDelegate Build()
    {
        // 管道末端：404
        MyRequestDelegate app = ctx =>
        {
            ctx.StatusCode = 404;
            ctx.ResponseBody = "Not Found";
            return Task.CompletedTask;
        };

        // 从后往前套娃
        for (int i = _middlewares.Count - 1; i >= 0; i--)
        {
            app = _middlewares[i](app);
        }
        return app;
    }
}

// ========== 使用它 ==========

var builder = new MyAppBuilder();

// 中间件1：日志
builder.Use(next => async ctx =>
{
    Console.WriteLine($">>> 请求进入: {ctx.RequestPath}");
    await next(ctx);
    Console.WriteLine($"<<< 响应返回: {ctx.StatusCode}");
});

// 中间件2：认证
builder.Use(next => async ctx =>
{
    if (ctx.RequestPath.StartsWith("/admin"))
    {
        Console.WriteLine("⛔ 未认证，拒绝访问");
        ctx.StatusCode = 401;
        ctx.ResponseBody = "Unauthorized";
        return; // 短路！
    }
    await next(ctx);
});

// 中间件3：处理请求
builder.Use(next => async ctx =>
{
    Console.WriteLine("✅ 处理业务逻辑");
    ctx.StatusCode = 200;
    ctx.ResponseBody = "Hello World!";
    // 不调用next，终端中间件
});

// 构建管道
var pipeline = builder.Build();

// 测试1：普通请求
Console.WriteLine("=== 测试1: GET / ===");
var ctx1 = new MyHttpContext { RequestPath = "/" };
await pipeline(ctx1);
Console.WriteLine($"结果: {ctx1.StatusCode} {ctx1.ResponseBody}\n");

// 测试2：管理员页面（未认证）
Console.WriteLine("=== 测试2: GET /admin ===");
var ctx2 = new MyHttpContext { RequestPath = "/admin" };
await pipeline(ctx2);
Console.WriteLine($"结果: {ctx2.StatusCode} {ctx2.ResponseBody}\n");
```

**输出：**

```
=== 测试1: GET / ===
>>> 请求进入: /
✅ 处理业务逻辑
<<< 响应返回: 200
结果: 200 Hello World!

=== 测试2: GET /admin ===
>>> 请求进入: /admin
⛔ 未认证，拒绝访问
<<< 响应返回: 401
结果: 401 Unauthorized
```

> **运行这段代码**，你就真正理解了 ASP.NET Core 管道的全部精髓。剩下的只是规模和细节的差异。

## 十三、检验你的理解

1. **`ApplicationBuilder.Build()` 为什么要从后往前遍历？**
   （答案：因为每个中间件需要"包裹"它后面的中间件。最先注册的中间件在最外层，最先执行。从后往前构建才能让第一个注册的中间件拿到"包含了所有后续中间件"的next。）

2. **如果把 `UseAuthentication()` 写在 `UseRouting()` 前面会怎样？**
   （答案：认证中间件无法知道请求匹配到了哪个Endpoint，也就无法读取Endpoint的认证元数据。虽然默认认证仍会执行，但一些依赖Endpoint元数据的认证行为会失效。）

3. **为什么认证失败了，认证中间件不直接返回401？**
   （答案：认证和授权是分离的。有些Endpoint可能允许匿名访问[AllowAnonymous]，认证中间件不知道当前请求是否需要认证。判断"是否需要认证"是授权中间件的职责。）

4. **OpenIddict 处理 `/connect/token` 请求时，走的是中间件管道的哪个环节？**
   （答案：走的是 `AuthenticationMiddleware` 中的 `IAuthenticationRequestHandler.HandleRequestAsync()` 环节。如果没有开启Passthrough，请求在认证中间件层就被处理了，不会到达Controller。）

5. **中间件实例是Singleton（只创建一次），但InvokeAsync方法的额外参数是Scoped的，这是怎么实现的？**
   （答案：中间件实例在Build时创建一次。每次请求调用InvokeAsync时，额外参数通过 `httpContext.RequestServices`（请求级Scope）动态解析。框架用表达式树编译了一个委托来完成这个操作。）
