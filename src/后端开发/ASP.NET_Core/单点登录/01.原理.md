# OpenIddict 实现SSO原理

OpenIddict 并不是自己发明了一套登录机制，它仅仅是 **OIDC 协议在 .NET Core 中的一个完美实现库** 。只要你懂了 OIDC，你就懂了 OpenIddict。 [blog.csdn](https://blog.csdn.net/weixin_48916144/article/details/147078039)

对于你这样一个 .NET 后端老兵，我们可以用一个**“去游乐场买通票”**的生动类比，结合 HTTP 请求的底层流程来拆解它的实现原理：

### 核心角色定义
在 OpenIddict 的 SSO 架构中，只有三个核心角色 ： [cloud.tencent](https://cloud.tencent.com/developer/article/2124238)
1. **User（用户）**：想去游乐场玩的游客（也就是浏览器前的用户）。
2. **SSO Server（OpenIddict 认证中心）**：游乐场大门口的“售票与实名认证中心”（即 Identity Provider, IdP）。 [support.zendesk](https://support.zendesk.com/hc/zh-cn/articles/7957465432474-%E8%AE%BE%E7%BD%AE-OpenID-Connect-OIDC-%E5%8D%95%E7%82%B9%E7%99%BB%E5%BD%95)
3. **Client App（你的各个业务系统，如 App A、App B）**：游乐场里的“过山车”、“碰碰车”等独立游乐项目（即 Relying Party, RP）。 [cloud.tencent](https://cloud.tencent.com/developer/article/2124238)

### 原理拆解：一次完整的 SSO 登录全流程

假设用户第一次访问你的业务系统 A（App A），以下是底层发生的 HTTP 交互原理：

#### 第一步：拦截与重定向（你没票，去大门口验明正身）
1. 用户在浏览器输入 `https://appA.com`。
2. App A 发现用户没有携带任何登录凭证（Cookie/Token）。
3. App A 返回一个 **HTTP 302 重定向** ，把用户踢到 SSO Server： [reddit](https://www.reddit.com/r/dotnet/comments/1d29mih/sso_server_with_aspnet_core_identity_openiddict/)
   `Location: https://sso.com/connect/authorize?client_id=AppA&response_type=code&redirect_uri=https://appA.com/callback` [comate.baidu](https://comate.baidu.com/zh/page/dircyn0ek14)
   *(潜台词：这个游客想玩过山车，但我不知道他是谁，请大门口的 SSO Server 验证一下，验证完了让他带着证明从 callback 这扇门回来。)*

#### 第二步：SSO 认证与发票（在认证中心登录并获取“授权码”）
1. 用户的浏览器来到了 SSO Server（这就是 OpenIddict 发挥作用的地方）。
2. SSO Server 发现这个用户在自己的域名下也没有 Cookie，于是弹出一个漂亮的登录页面。
3. 用户输入账号密码，点击登录。你的 .NET 代码校验密码成功后，OpenIddict 登场。
4. **OpenIddict 的原理运作**：它在数据库（或内存）中生成一串随机字符串，称为 **Auth Code（授权码）** 。然后再次触发 **HTTP 302**，把用户踢回 App A： [comate.baidu](https://comate.baidu.com/zh/page/dircyn0ek14)
   `Location: https://appA.com/callback?code=XyZ123`

#### 第三步：拿码换证（App A 后台去校验这票是不是伪造的）
1. 浏览器带着 `code=XyZ123` 回到了 App A 的后端（注意，这个 Code 不能直接用来登录，它只是一把钥匙）。
2. App A 的后端拿到 Code 后，**在服务器内部（不经过浏览器，防止被黑客窃听）**，带上自己的 ClientSecret，向 SSO Server 发起一个 POST 请求：
   `POST https://sso.com/connect/token` [comate.baidu](https://comate.baidu.com/zh/page/dircyn0ek14)
3. **OpenIddict 再次运作**：它核对这个 Code 没过期，且 Secret 正确，于是使用 **RSA 非对称加密算法**（用私钥签名）生成一串包含用户身份信息（如 UserID、Name、Role）的 **ID Token（一个 JWT 字符串）**，以及一个 Access Token，返回给 App A 后端 。 [houbb.github](https://houbb.github.io/2024/08/04/privilege-access-control-23-authing-openid-connect)

#### 第四步：App A 登录成功（游客成功坐上过山车）
1. App A 拿到 JWT，用 SSO 的公钥验证签名无误。
2. App A 把 JWT 里的用户信息解析出来，在自己 `appA.com` 的域名下写入一个普通的 Session Cookie。
3. 用户在 App A 登录成功。

### 为什么能实现“单点”登录？（去玩碰碰车不用再买票了）

SSO（Single Sign-On）最神奇的魔法发生在用户接着访问 **App B** 的时候：

1. 用户在浏览器输入 `https://appB.com`。
2. App B 发现没登录，走第一步的老路，用 302 把用户踢到了 SSO Server：
   `Location: https://sso.com/connect/authorize?client_id=AppB...`
3. **关键点来了**：当浏览器来到 `sso.com` 时，浏览器会自动带上之前在 SSO 登录成功时种下的 **SSO Cookie** ！ [support.zendesk](https://support.zendesk.com/hc/zh-cn/articles/7957465432474-%E8%AE%BE%E7%BD%AE-OpenID-Connect-OIDC-%E5%8D%95%E7%82%B9%E7%99%BB%E5%BD%95)
4. OpenIddict 读取到这个 Cookie，知道“哦，这个游客刚才已经实名认证过了”。
5. OpenIddict **直接静默跳过登录页面（无感验证）**，瞬间生成一个新的 Auth Code，用 302 把用户踢回 App B 的 callback。
6. App B 后台拿 Code 换 Token，验证通过。

**用户体验到的就是：我打开 App B，页面闪了一下（经历了两次极快的 302 跳转），然后就自动登录进去了！** [fortinet](https://www.fortinet.com/cn/resources/cyberglossary/oidc)

### 总结
OpenIddict 实现 SSO 的核心原理就是：
1. **浏览器重定向（302 跳转）**：用于在各个子系统和中心之间传递用户 。 [reddit](https://www.reddit.com/r/dotnet/comments/1d29mih/sso_server_with_aspnet_core_identity_openiddict/)
2. **中心化 Cookie 信任**：用户的认证状态（Cookie）只保存在 SSO 中心这一个域名下 。 [fortinet](https://www.fortinet.com/cn/resources/cyberglossary/oidc)
3. **非对称加密的 JWT (ID Token)**：用于安全地把用户的身份从 SSO 中心“分发”给各个子系统，且不怕被篡改 。 [support.zendesk](https://support.zendesk.com/hc/zh-cn/articles/7957465432474-%E8%AE%BE%E7%BD%AE-OpenID-Connect-OIDC-%E5%8D%95%E7%82%B9%E7%99%BB%E5%BD%95)

作为后端老兵，这套标准的 OAuth2/OIDC 授权码流程你一定能迅速消化。如果在你们公司落地，你是比较头疼**如何在 EF Core 里配置 OpenIddict 的这些 Client 和 Scope 表**，还是比较头疼**用户注销（SSO Logout）时怎么同时通知所有系统踢人**？
