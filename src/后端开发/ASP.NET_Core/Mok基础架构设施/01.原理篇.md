# 原理篇：突破 IConfiguration 生命周期

## 为什么要把配置存到数据库

对于绝大多数普通项目，把配置存进数据库纯属多此一举。但对于核心业务系统（比如 SSO 认证中心），把"特定部分"的配置存进数据库是绝对必要的。

关键在于区分系统里的 **两类完全不同的配置**。

### 基础设施配置（坚决不要放进数据库）

比如：数据库连接字符串、Redis 节点地址、RabbitMQ 密码、日志输出级别。

- **为什么不放？** 经典的"鸡生蛋"问题——连数据库的密码都存在数据库里，系统启动时怎么连数据库？
- **最佳归宿**：放在 `appsettings.json`，或者在 Docker/K8s 部署时通过环境变量注入。这类配置一旦改变，系统必须重启才能重新建立连接池，不需要热更新。

### 业务与运营配置（有必要放进数据库）

比如：SSO Token 过期时间、CORS 白名单、系统维护模式开关、密码重试锁定次数、注册是否需要邮箱验证。

如果把这些配置死钉在 `appsettings.json` 里，团队会面临三个问题：

**问题一：小需求打断开发节奏**

运营说"今天搞活动，把 JWT 过期时间从 2 小时改成 24 小时"。如果用配置文件，就得拉代码、改 JSON、提交 Git、走一遍 CI/CD 流水线。如果有数据库配置表，运营自己在后台管理界面改一下就完事了。

**问题二：集群部署的数据不一致**

SSO 用 Docker 跑了 3 个实例做负载均衡，改配置得改 3 份 `appsettings.json`，漏改一个就出幽灵 Bug。数据库是唯一的"单点真相（Single Source of Truth）"，所有节点轮询数据库，天然保持一致。不想引入 Apollo / Nacos 这类中间件的话，数据库就是"穷人版配置中心"的唯一解。

**问题三：没有操作审计**

配置写错导致系统崩溃是常有的事。改物理文件很难追查谁在什么时候改了什么。数据库配置表天然支持 `LastModifiedBy`、`UpdatedAt` 字段和历史记录表。

### 混合模式架构

最终方案是混合双打：

1. **程序启动层**：保留 `appsettings.json`，只写 `ConnectionStrings` 和基础不可变配置。
2. **业务逻辑层**：手写 `EFConfigurationProvider`，把需要灵活控制的规则放进数据库。
3. **配置覆盖机制**：ASP.NET Core 的配置系统是后注册覆盖先注册。数据库里的 `JwtSettings:ExpireDays` 会自动覆盖 `appsettings.json` 里的同名配置。

## ASP.NET Core 配置系统的底层机制

ASP.NET Core 的配置系统不在乎数据从 JSON、环境变量还是内存来，一切配置最终都会被拍扁成一个 **键值对字典** (`Dictionary<string, string>`)。

要实现数据库配置读取并支持动态刷新，需要做三件事：

1. **实现自定义 `ConfigurationProvider`** —— 查数据库，把数据塞进字典。
2. **实现自定义 `IConfigurationSource`** —— 把 Provider 注册到配置管道中。
3. **实现动态刷新机制** —— 调用 Provider 底层的 `OnReload()` 通知全网配置已更新。

## 为什么不能用中间件读配置

ASP.NET Core 的生命周期是严格分层的：

1. **第一阶段：构建配置（IConfiguration）** —— 读取文件、数据库。
2. **第二阶段：构建容器（DI Container）** —— 注册所有 Service，构造函数里可能注入 `IOptions<T>`。
3. **第三阶段：构建管道（Middleware Pipeline）** —— 处理 HTTP 请求。

如果用中间件去读数据库配置，意味着配置在第三阶段才产生。而第二阶段注册的 Singleton 服务、DbContext、后台任务，它们的构造函数里根本拿不到配置（因为 HTTP 请求还没进来）。这会直接摧毁 `IOptions<T>` 的整个生态。

中间件的真正用武之地是 **多租户场景**——根据请求域名动态加载不同租户的配置，但这属于 Scoped 级别的上下文，不是全局配置。

## 配置的"洋葱模型"

`IConfiguration` 是一个"大杂烩"。多个配置源按注册顺序叠加，相同 Key 后注册的覆盖先注册的。

`WebApplication.CreateBuilder(args)` 默认已经加载了：

1. `appsettings.json`
2. `appsettings.{Environment}.json`
3. 系统环境变量
4. 命令行参数

把数据库配置源加在最后面，它就具有最高优先级。

```csharp
var builder = WebApplication.CreateBuilder(args);
var connectionString = builder.Configuration.GetConnectionString("DefaultConnection");

// 数据库源排在默认文件源之后，优先级最高
builder.Configuration.AddEFConfiguration(options => 
    options.UseSqlServer(connectionString), out var efConfigSource);
```

这种"双源融合"带来三个好处：

1. **缺省回退**：数据库里没有的 Key，自动回退到 `appsettings.json`。系统刚部署时配置表是空的也能正常运行。
2. **环境隔离**：开发环境可以选择不加载数据库配置，用 `appsettings.Development.json` 隔离。
3. **物理隔离**：不可变的基础设施配置留在文件里，可变的业务配置交给数据库，在内存里通过 `IConfiguration` 合并。

## IOptions 三兄弟的选择

配置支持动态刷新后，在 Controller 或 Service 中读取配置时，注入的类型至关重要：

| 类型 | 生命周期 | 热更新 | 说明 |
| :-- | :-- | :-- | :-- |
| `IOptions<T>` | Singleton | ❌ | 启动后值永远不变 |
| `IOptionsSnapshot<T>` | Scoped | ✅ | 每次 HTTP 请求拿最新值，同一请求内不变 |
| `IOptionsMonitor<T>` | Singleton | ✅ | 带 `OnChange` 事件，能实时监听 `OnReload()` |

想享受热更新，必须注入 `IOptionsMonitor<T>` 或 `IOptionsSnapshot<T>`。

```csharp
public class AuthService
{
    private readonly IOptionsMonitor<JwtOptions> _jwtOptionsMonitor;

    public AuthService(IOptionsMonitor<JwtOptions> jwtOptionsMonitor)
    {
        _jwtOptionsMonitor = jwtOptionsMonitor;

        // 监听配置变更事件
        _jwtOptionsMonitor.OnChange(newOptions => 
        {
            Console.WriteLine($"配置变了，新的过期天数：{newOptions.ExpireDays}");
        });
    }

    public string GenerateToken()
    {
        // 每次调用拿到的都是最新值
        var currentConfig = _jwtOptionsMonitor.CurrentValue;
        var key = currentConfig.SecretKey;
        // ...
    }
}
```

## Program.cs 的黄金铁律

写 `Program.cs` 时，永远遵循这个生命周期顺序：

1. **`builder.Configuration.AddXXX()`** 最前面 —— 收集所有配置。
2. **`builder.Services.AddXXX()`** 中间 —— 把配置喂给各种 Service、DbContext、Options。
3. **`var app = builder.Build();`** 楚河汉界 —— 容器锁定，配置锁定。
4. **`app.UseXXX()` / `app.MapXXX()`** 最后 —— 注册 HTTP 管道、中间件、路由。

```csharp
var builder = WebApplication.CreateBuilder(args);

// 第一步：配置（必须最先）
builder.Configuration.AddMokDatabaseConfiguration<SSODbContext>(out var dbConfigSource);

// 第二步：服务注册（必须在配置之后）
builder.Services.AddDefaultDbContext<SSODbContext>(builder.Configuration, dbConfigSource);
builder.Services.AddDefaultOptions(builder.Configuration);

var app = builder.Build();
app.Run();
```

配置注册必须在最前面，因为后面的服务注册依赖它查出来的数据。如果颠倒顺序，Options 绑定的永远只是本地文件的默认值。
