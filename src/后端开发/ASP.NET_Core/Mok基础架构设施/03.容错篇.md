# 容错篇：防止数据库连不上导致启动崩溃

## 问题描述

在真实环境（尤其是 CI/CD 自动化部署）中，程序第一次启动时，数据库可能已经建好了，但 EF Core 的迁移还没来得及跑，`app_settings` 表还不存在。

如果在 `Load()` 里直接执行 `dbContext.Set<AppSettings>().ToList()`，表不存在时会抛出 `NpgsqlException`（`relation does not exist`）或 `SqlException`（`对象名无效`），导致整个 ASP.NET Core 应用直接崩溃，连跑后续代码建表的机会都没有。

---

## 解决方案：拦截异常，优雅降级

在配置系统层，发现表不存在或连不上数据库时不让系统崩溃，改为记录警告并返回空字典。系统退而求其次用 `appsettings.json` 里的默认配置先启动，等数据库建好后通过后台任务热更新拉取配置。

```csharp
using System;
using System.Collections.Generic;
using System.Linq;
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.Configuration;
using Mok.SqlFactory.Models;

namespace Mok.SqlFactory.DbAppsettings
{
    public class EFConfigurationProvider<TContext> : ConfigurationProvider 
        where TContext : DbContext
    {
        private readonly Action<DbContextOptionsBuilder> _optionsAction;

        public EFConfigurationProvider(Action<DbContextOptionsBuilder> optionsAction)
        {
            _optionsAction = optionsAction;
        }

        public override void Load()
        {
            var builder = new DbContextOptionsBuilder<TContext>();
            _optionsAction(builder);

            var dataDictionary = new Dictionary<string, string>(
                StringComparer.OrdinalIgnoreCase);

            try
            {
                using var dbContext = (TContext)Activator.CreateInstance(
                    typeof(TContext), builder.Options);

                var allConfigs = dbContext.Set<AppSettings>().ToList();
                var leafNodes = allConfigs.Where(c => c.Value != null);

                foreach (var leaf in leafNodes)
                {
                    string fullKey = BuildKeyPath(leaf, allConfigs);
                    dataDictionary[fullKey] = leaf.Value;
                }
            }
            catch (Exception ex)
            {
                // 两种常见情况会走到这里：
                // 1. 数据库连不上（网络不通 / 密码错误）
                // 2. 数据库连上了，但 app_settings 表不存在（尚未跑 Migration）
                //
                // 此时 DI 容器还未建立，无法注入 ILogger，用 Console 输出
                Console.WriteLine(
                    $"[警告] 无法从 {typeof(TContext).Name} 加载配置，" +
                    $"回退使用 appsettings.json。原因: {ex.Message}");
            }

            // 无论成功还是失败，都赋值给 Data，保证配置不中断
            Data = dataDictionary;
        }

        private string BuildKeyPath(AppSettings current, List<AppSettings> allNodes)
        {
            if (current.ParentId == null)
                return current.NodeName;

            var parent = allNodes.FirstOrDefault(n => n.Id == current.ParentId);
            if (parent != null)
                return $"{BuildKeyPath(parent, allNodes)}:{current.NodeName}";

            return current.NodeName;
        }

        public void ReloadFromDatabase()
        {
            Load();
            OnReload();
        }
    }
}
```

## 为什么不用 `TableExists` 提前判断

有些开发者喜欢在查询前调用底层 SQL 判断表存不存在：

```csharp
var exists = dbContext.Database.ExecuteSqlRaw(
    "SELECT 1 FROM pg_tables WHERE tablename = 'app_settings'");
```

这在本项目中不可取，原因有二：

1. **多数据库兼容性被破坏**。`Mok.SqlFactory` 支持 PostgreSQL、SQL Server、MySQL，查系统表的 SQL 每种数据库都不一样，写三套方言会非常难维护。
2. **连接超时照样挂**。如果不是表不存在而是网络断了，`ExecuteSqlRaw` 一样会抛异常，最终还是得包 `try-catch`。

`try-catch` 是综合成本最低、覆盖面最广的方案。

## 完整的自愈闭环

加上容错处理后，配合后台定时热重载服务（第四章），系统具备了自我愈合能力：

| 时间线 | 发生了什么 |
| :-- | :-- |
| **启动** | 数据库表还没建好。`Load()` 走进 `catch`，返回空字典。系统用 `appsettings.json` 正常启动。 |
| **稍后** | 运维执行了 Migration 或手动建表，插入了配置数据。 |
| **下一个轮询周期** | 后台任务触发 `ReloadFromDatabase()`，`Load()` 这次成功查到数据。所有 `IOptionsMonitor` 自动切换到数据库配置。 |

全程不需要人工重启，系统自己从"降级状态"平滑切换到"完整状态"。

## Checklist

保存代码后确认以下三点：

- [ ] `SSODbContext` 有 `public DbSet<AppSettings> AppSettings { get; set; }`
- [ ] `SSODbContext` 有接收 `DbContextOptions<SSODbContext>` 的公共构造函数（为了 `Activator.CreateInstance` 能成功调用）
- [ ] `AppSettings` 实体正确声明了 `Id`、`ParentId`、`NodeName`、`Value` 属性
