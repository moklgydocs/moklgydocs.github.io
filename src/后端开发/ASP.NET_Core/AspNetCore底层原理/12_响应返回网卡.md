## 二、SenderTask 详解

### 2.1 SenderTask 主循环

```csharp
// src/Servers/Kestrel/Transport.Sockets/src/SocketConnection.cs 简化版

private async Task ProcessSendsAsync()
{
    var output = _outputPipe.Reader; // 从 OutputPipe 读取待发送数据

    while (true)
    {
        // ── 等待数据 ──
        // ApplicationTask（序列化层）往 OutputPipe.Writer 写数据后唤醒此处
        var result = await output.ReadAsync();
        var buffer = result.Buffer;

        if (buffer.IsEmpty && result.IsCompleted)
            break; // OutputPipe 已完成，没有更多数据了

        // ── 发送数据 ──
        // 数据可能跨越多个 Segment（非连续内存）
        // SocketSender 负责处理跨 Segment 的 gather-send（scatter-gather IO）
        await _sender.SendAsync(buffer);

        // ── 通知 Pipe 数据已消费 ──
        output.AdvanceTo(buffer.End);

        if (result.IsCompleted)
            break; // 没有更多数据，退出循环
    }

    output.Complete();
}
```

### 2.2 `SocketSender.SendAsync()`——Scatter-Gather 发送

```mermaid
sequenceDiagram
    participant ST as SenderTask
    participant SS as SocketSender
    participant OS as OS 内核

    ST->>SS: SendAsync(buffer)
    Note over SS: buffer = ReadOnlySequence<byte>\n可能由多个 Segment 组成\n[JSON头部 Segment A][JSON体 Segment B]

    SS->>SS: 构建 SocketAsyncEventArgs.BufferList\n每个 Segment → 一个 ArraySegment<byte>\n无需合并！直接 gather send

    SS->>OS: socket.SendAsync(socketArgs)\n底层：sendmsg() with msghdr.msg_iov[]\n多个内存块 → 单次系统调用

    OS->>OS: 把多个缓冲区数据合并发送\n（内核处理，无用户空间复制）
    OS-->>SS: 发送完成（bytes_transferred）

    SS-->>ST: 发送成功

    Note over ST: OutputPipe.AdvanceTo(buffer.End)\n释放 Segment 回内存池
```

## 三、HTTP 响应头的发送时机

响应头不是和 Body 一起写的，而是在第一次写 Body 之前由 Kestrel 自动插入：

```mermaid
flowchart TD
    FIRST_WRITE["OutputFormatter 第一次调用\nBodyWriter.Advance()"]
    CHECK{"Response.HasStarted?"}
    COMPOSE["组装响应行 + 头部：\nHTTP/1.1 200 OK\\r\\n\nContent-Type: application/json; charset=utf-8\\r\\n\nContent-Length: 1234\\r\\n（若已知）\nor Transfer-Encoding: chunked\\r\\n（流式）\nDate: Mon, 01 Jan 2024 00:00:00 GMT\\r\\n\n\\r\\n"]
    MARK["Response.HasStarted = true"]
    BODY["写入 Body 字节（JSON 内容）"]
    SEND["SenderTask 统一发送头部 + Body"]

    FIRST_WRITE --> CHECK
    CHECK -->|"=false（还未发送）"| COMPOSE
    CHECK -->|"=true（已发送）"| BODY
    COMPOSE --> MARK --> BODY --> SEND

    style COMPOSE fill:#1e3a5f,color:#fff
    style SEND fill:#1a4731,color:#fff
```

**关键点：一旦 `Response.HasStarted = true`，就不能再修改响应头！**

```csharp
// ❌ 危险代码：在某些情况下会抛出 InvalidOperationException
app.Use(async (context, next) =>
{
    await next(context); // 执行后续中间件（可能已写入响应头）

    // 如果响应已开始，这里修改头部会抛异常
    if (context.Response.HasStarted)
        return; // 必须检查！

    context.Response.Headers["X-Custom"] = "value"; // 太晚了！
});

// ✅ 正确：使用 Response.OnStarting 在发送前注册回调
app.Use(async (context, next) =>
{
    context.Response.OnStarting(() =>
    {
        // 此回调在响应头即将发送时执行（HasStarted 变为 true 之前）
        context.Response.Headers["X-Custom"] = "value";
        return Task.CompletedTask;
    });

    await next(context);
});
```

## 四、HTTP/1.1 Keep-Alive——连接复用

```mermaid
sequenceDiagram
    participant C as 客户端
    participant K as Kestrel

    Note over C,K: ── 第一个请求 ──
    C->>K: GET /api/users HTTP/1.1\nHost: example.com\nConnection: keep-alive\n\n
    K->>K: 处理请求...
    K-->>C: HTTP/1.1 200 OK\nContent-Length: 234\nConnection: keep-alive\nKeep-Alive: timeout=15, max=1000\n\n{...响应体234字节...}

    Note over C,K: ── 连接保持，无需三次握手 ──

    Note over C,K: ── 第二个请求（复用同一 TCP 连接）──
    C->>K: POST /api/orders HTTP/1.1\nHost: example.com\nContent-Length: 89\n\n{...请求体89字节...}
    K->>K: 处理请求...
    K-->>C: HTTP/1.1 201 Created\n...

    Note over C,K: ── 超过 15 秒无请求 ──
    K->>K: Keep-Alive 超时
    K-->>C: Connection: close （下次响应时通知）
    K->>K: 关闭 TCP 连接
```

**Kestrel Keep-Alive 配置**：

```csharp
builder.WebHost.ConfigureKestrel(options =>
{
    options.Limits.KeepAliveTimeout = TimeSpan.FromSeconds(120); // 默认 120s
    options.Limits.RequestHeadersTimeout = TimeSpan.FromSeconds(30); // 请求头超时
    options.Limits.MaxConcurrentConnections = 10000; // 最大并发连接数
    options.Limits.MaxConcurrentUpgradedConnections = 1000; // WebSocket 等升级连接
});
```

## 五、HTTP/2 多路复用——彻底解决队头阻塞

```mermaid
sequenceDiagram

    Note over C,K: 单个 TCP 连接，多个并发 Stream

    C->>K: HEADERS frame (Stream 1: GET /api/users)
    C->>K: HEADERS frame (Stream 3: GET /api/orders)
    C->>K: HEADERS frame (Stream 5: POST /api/events)

    Note over K: 三个 Stream 并发处理！
    Note over K: Stream 1: DB 查询（慢）
    Note over K: Stream 3: 内存缓存（快）
    Note over K: Stream 5: 写操作（中）

    K-->>C: HEADERS + DATA frame (Stream 3: 200 OK + orders)
    K-->>C: HEADERS + DATA frame (Stream 5: 201 Created)
    K-->>C: HEADERS + DATA frame (Stream 1: 200 OK + users)

    Note over C,K: Stream 3 先完成就先返回\n不需要等 Stream 1！
```

**优雅关闭实现**：

```csharp
// Program.cs
builder.Host.ConfigureHostOptions(opts =>
{
    opts.ShutdownTimeout = TimeSpan.FromSeconds(15); // 给 15 秒处理进行中的请求
});

// 监听 SIGTERM（Kubernetes 滚动更新时发送）
app.Lifetime.ApplicationStopping.Register(() =>
{
    // 立即停止接受新请求（但当前请求继续）
    // Kestrel 自动处理，通常不需要手动注册
});

// 自定义优雅停机：等待后台队列清空
app.Lifetime.ApplicationStopping.Register(async () =>
{
    var backgroundQueue = app.Services.GetRequiredService<IBackgroundTaskQueue>();
    await backgroundQueue.WaitForEmptyAsync(TimeSpan.FromSeconds(10));
});
```

**零拷贝 / 零分配 / 零阻塞的协同效果**：

```
传统阻塞模型（一连接一线程）:
  10,000 并发 → 10,000 线程 → 10GB 线程栈内存 → 大量上下文切换

Kestrel 异步模型:
  10,000 并发 → ~100 线程 → 100MB 内存 → 几乎零上下文切换

内存分配对比（每个请求）:
  传统 NetworkStream: ~50KB 分配（byte[], string, List, 等）
  Kestrel Pipelines:  ~1KB 分配（对象池 + 栈分配，接近零）
```

## 九、`HttpContext` 对象池的完整生命周期


## 十、本模块总结

| 知识点 | 核心结论 |
|--------|---------|
| SenderTask | 从 OutputPipe.Reader 读取，用 Socket.SendAsync() 发送，支持 Scatter-Gather IO |
| 响应头发送时机 | 第一次写 Body 之前自动插入，`HasStarted=true` 后不可修改 |
| HTTP/1.1 Keep-Alive | 复用 TCP 连接，免三次握手开销，但仍有队头阻塞 |
| HTTP/2 多路复用 | 单 TCP 连接多 Stream，互不阻塞，先完成先返回 |
| 优雅关闭 | Stop → 停止接受新连接 → 等待现有请求完成 → ShutdownTimeout 后强制关闭 |
| 对象池生命周期 | 从池取出 → Initialize → 请求处理 → Uninitialize → 归还池，进程期间持续复用 |
