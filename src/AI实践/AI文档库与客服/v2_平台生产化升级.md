# v2 · 平台生产化升级全解

> **写在前面**：L1–L10 带你把系统从零跑起来，v2 要解决的是另一个问题——**跑起来的系统能不能放心地给真人用**。这两件事的距离，远比你想象的大。

完成 L1–L10 那一刻，你的 ZuruAI 平台可以对话、可以检索、可以调工具、可以管多租户。但如果真的上线，大概率会遇到：

- 第一周：有人用默认密码把管理员账号跑进来了
- 第一个月：DeepSeek 抽风宕机，所有用户同时报错
- 第三个月：日志里全是 key=sk-xxxx，安全团队找上门
- 半年后：老板问"这个月 AI 费用多少"，你只能说"大概"

v2 的全部工作，就是把这些"大概率会发生"的问题提前堵死。

---

## 一、为什么 v1 是半成品

v1 的问题不在功能，在假设。整个 L1–L10 的开发过程中，有几个隐含的假设从来没被挑战过：

**假设一：开发环境的代码就是生产代码**

`jwt_secret = "change-me"` 这种配置在教程里看起来无害，因为"反正等下要改嘛"。但真实项目里，这行代码有 40% 的概率原封不动地进了 prod。

**假设二：外部服务一直可用**

调用 DeepSeek 的代码没有熔断，调用 Qdrant 的代码没有超时，Celery 任务没有队列深度限制。单机测试环境里这些都没问题，多人同时使用时任何一个外部服务抖动都可能把你的服务拖垮。

**假设三：LLM 调用一定会成功**

`raw_output = await llm.complete(...)` 然后直接解析结果。真实情况是：LLM 有时候返回 Markdown 包裹的 JSON，有时候返回不完整 JSON，有时候给你一段道歉声明说"我无法完成这个请求"。

**假设四：只有自己人用**

Prompt 输入没有长度限制，没有注入检测，API 没有 IP 级别的限速，日志里明文打印了 API Key。

v2 就是把这四个假设全部消除掉。

## 二、安全加固：从"能用"到"敢用"

### 2.1 凭据强制校验：第一道防线

**核心思路**：不是靠人的自觉，而是靠启动时的代码校验。系统带着危险默认值根本起不来。

```python
# app/core/config.py — v2 版本
class Settings(BaseSettings):
    env: str = "development"
    jwt_secret: str                    # 无默认值，不填启动时直接报错
    admin_password: str
    llm_api_key: str

    @model_validator(mode="after")
    def forbid_defaults_in_production(self):
        """生产环境拒绝一切看起来像默认值的配置"""
        if self.env != "production":
            return self

        DANGEROUS_PATTERNS = [
            "change-me", "changeme", "secret", "test",
            "dev", "zuru@2024", "sk-test", "password"
        ]
        for field_name in ["jwt_secret", "admin_password", "llm_api_key"]:
            val = str(getattr(self, field_name, "")).lower()
            for pattern in DANGEROUS_PATTERNS:
                if pattern in val:
                    raise ValueError(
                        f"[安全] 生产环境 {field_name} 包含危险默认值 '{pattern}'，"
                        f"请在 .env 中设置真实值后重启"
                    )
        return self
```

返回的 `raise ValueError` 会让 FastAPI 的 lifespan 在启动时崩溃，服务根本起不来。这比上线后被人发现默认密码还在强。

**配套：日志脱敏**

```python
# structlog 配置：过滤敏感字段，防止 API Key 进日志
def filter_sensitive_fields(logger, method, event_dict):
    SENSITIVE_KEYS = {"api_key", "token", "password", "secret", "authorization"}
    for key in list(event_dict.keys()):
        if any(s in key.lower() for s in SENSITIVE_KEYS):
            event_dict[key] = "***REDACTED***"
    return event_dict

structlog.configure(
    processors=[
        filter_sensitive_fields,      # 必须放在第一位
        structlog.processors.JSONRenderer(),
    ]
)
```

### 2.2 JWT 吊销：让登出真正有效

JWT 的本质是自包含凭证，服务端不存状态。这导致一个反直觉的问题：**用户点了"退出登录"，Token 还是有效的，直到过期为止**。

v2 的解法是黑名单机制：登出时把 `jti`（JWT 唯一标识）写入 Redis，鉴权中间件每次验签后查一次黑名单。

```python
# 登出接口：把 jti 写入 Redis 黑名单
async def logout(token: str, redis: Redis) -> None:
    try:
        claims = decode_jwt(token)
        ttl = claims["exp"] - int(time.time())
        if ttl > 0:
            # TTL 设置为 Token 剩余有效期，到期自动清理，不占用无限空间
            await redis.setex(f"jwt_blacklist:{claims['jti']}", ttl, "1")
    except JWTError:
        pass  # 无效 Token 登出，直接忽略

# 鉴权中间件：验签 + 查黑名单
async def auth_middleware(request: Request, call_next):
    raw_token = request.headers.get("Authorization", "").removeprefix("Bearer ")
    if not raw_token:
        if request.url.path in PUBLIC_PATHS:
            return await call_next(request)
        return JSONResponse(status_code=401, content={"detail": "未提供认证信息"})

    claims = verify_jwt(raw_token)  # 签名无效直接 raise

    # 黑名单检查——这是 v2 新增的关键步骤
    if await redis.exists(f"jwt_blacklist:{claims.get('jti')}"):
        return JSONResponse(status_code=401, content={"detail": "Token 已吊销，请重新登录"})

    request.state.claims = claims
    return await call_next(request)
```

**Key 设计细节**：

| 问题 | 解法 |
|------|------|
| 黑名单无限增长 | TTL = Token 剩余有效期，过期自动删除 |
| 多实例部署 | 黑名单在 Redis 共享，任意实例的登出对所有实例生效 |
| 性能影响 | Redis GET 耗时约 0.1ms，每次鉴权增加不到 1ms |

### 2.3 Prompt 注入防护

企业客服系统的最大安全漏洞之一：**用户输入的内容会拼入 Prompt**。恶意用户通过特定输入，可能绕过系统提示词的约束，让 AI 说出不该说的话。

```python
import re
import hashlib

# 已知注入模式（持续更新）
INJECTION_PATTERNS = [
    r"忽略(之前|前面|上面|所有).{0,10}指令",
    r"ignore\s+(previous|all|above|prior)\s+instructions",
    r"你现在是.{0,20}(无限制|黑客|攻击者|越狱)",
    r"<\|im_start\|>|<\|system\|>|<system>|\[INST\]|\[/INST\]",
    r"\bDAN\b|jailbreak|越狱模式|开发者模式",
    r"pretend\s+you\s+are|act\s+as\s+if\s+you\s+have\s+no",
]

def sanitize_input(text: str, max_length: int = 2000) -> str:
    """
    用户输入的第一道门——所有进入对话的文本必须过这里。
    
    截断 + 注入检测，命中则替换，不抛异常（用户体验），但记录日志。
    """
    # 1. 长度截断（防止超长输入把 context window 打爆）
    if len(text) > max_length:
        text = text[:max_length]

    # 2. 注入模式检测
    for pattern in INJECTION_PATTERNS:
        if re.search(pattern, text, re.IGNORECASE | re.DOTALL):
            # 记录日志但不暴露原始内容（取 MD5 指纹）
            logger.warning(
                "prompt_injection_detected",
                pattern=pattern[:30],
                input_hash=hashlib.md5(text.encode()).hexdigest()[:8],
            )
            return "[输入包含不安全内容，已过滤]"

    return text
```

**一个容易忽略的点**：系统 Prompt 和用户 Prompt 必须严格分离，用户输入只出现在 `role=user` 的消息里，绝不能字符串拼接到 `system` 里。

```python
# ❌ v1 容易写出的危险代码
system = f"你是客服助手。用户说：{user_input}"  # 注入直接生效

# ✅ v2 正确写法
messages = [
    {"role": "system", "content": "你是 Zuru 企业客服助手，只回答产品相关问题。"},
    {"role": "user",   "content": sanitize_input(user_input)},  # 严格隔离
]
```

### 2.4 PII 脱敏：云端调用前的最后防线

用户在聊天框里发手机号、订单号、身份证号是常有的事。这些数据在发往 DeepSeek/OpenAI 云端之前，必须先脱敏。

```python
import re

PII_PATTERNS = {
    # 中国手机号（13x/14x/15x/16x/17x/18x/19x）
    "phone":    (r"1[3-9]\d{9}", lambda m: m[:3] + "****" + m[-4:]),
    # 中国居民身份证（18位）
    "id_card":  (r"\d{17}[\dXx]", lambda m: m[:6] + "********" + m[-4:]),
    # 邮箱
    "email":    (r"[\w.+-]+@[\w-]+\.[\w.-]+", lambda m: m.split("@")[0][:2] + "***@" + m.split("@")[1]),
    # 银行卡（16-19位数字）
    "bank_card":(r"\b\d{16,19}\b", lambda m: m[:4] + " **** **** " + m[-4:]),
}

def mask_pii(text: str) -> str:
    """
    发往云端 LLM 前调用。本地部署的模型不需要脱敏。
    
    注意：脱敏只是在 Prompt 层面保护隐私，原始数据存储层的保护是另外的事。
    """
    for pii_type, (pattern, replacer) in PII_PATTERNS.items():
        def replace_match(m):
            original = m.group()
            masked = replacer(original)
            logger.debug("pii_masked", type=pii_type, length=len(original))
            return masked

        text = re.sub(pattern, replace_match, text)
    return text

# 在 LLM 调用的最后一环使用
async def call_cloud_llm(messages: list, provider: str) -> str:
    if provider in ("openai", "deepseek", "anthropic"):
        # 云端调用前脱敏
        messages = [
            {**m, "content": mask_pii(m["content"]) if m["role"] == "user" else m["content"]}
            for m in messages
        ]
    return await llm_client._call(provider, messages)
```

### 2.5 CORS 白名单化

一行 `allow_origins=["*"]` 是开发期间的快捷键，但它让任何网站都能向你的 API 发请求。v2 要求生产环境必须显式配置白名单。

```python
# app/main.py
cors_raw = settings.cors_origins  # 从环境变量读取，格式："https://app.zuru.com,https://admin.zuru.com"

if settings.env == "production":
    if not cors_raw or cors_raw.strip() == "*":
        raise ValueError(
            "[安全] 生产环境必须设置 CORS_ORIGINS 环境变量（逗号分隔多个域名），"
            "禁止使用通配符 *"
        )

cors_origins = [o.strip() for o in cors_raw.split(",") if o.strip()]

app.add_middleware(
    CORSMiddleware,
    allow_origins=cors_origins,
    allow_credentials=True,
    allow_methods=["GET", "POST", "PUT", "DELETE", "PATCH"],
    allow_headers=["Authorization", "Content-Type", "X-Request-ID"],
)
```

## 三、可靠性工程：从"有时坏"到"优雅降级"

### 3.1 多 Provider LLM Fallback

单一 LLM Provider 是最危险的单点。DeepSeek 每季度都有几次抖动，OpenAI 也不例外。v2 要求 LLM 客户端内置 Fallback 逻辑。

**设计原则**：
- 主用 DeepSeek（性价比高）
- 备用 OpenAI GPT-4o-mini（稳定性好）
- 兜底 Claude Haiku（Anthropic 历史可用性最高）
- 每个 Provider 独立熔断，不因主 Provider 宕机导致备用也慢响应

```python
class LLMClientWithFallback:
    """
    统一 LLM 客户端，内置多 Provider 自动切换。
    
    每个 Provider 独立维护熔断状态（存 Redis），全局共享。
    切换时记录告警，让运维知道当前在用哪个 Provider。
    """

    PROVIDERS = [
        {
            "name": "deepseek",
            "model": "deepseek-chat",
            "base_url": "https://api.deepseek.com/v1",
            "api_key_env": "DEEPSEEK_API_KEY",
        },
        {
            "name": "openai",
            "model": "gpt-4o-mini",
            "base_url": "https://api.openai.com/v1",
            "api_key_env": "OPENAI_API_KEY",
        },
        {
            "name": "anthropic",
            "model": "claude-haiku-4-5-20251001",
            "base_url": "https://api.anthropic.com/v1",
            "api_key_env": "ANTHROPIC_API_KEY",
        },
    ]

    def __init__(self, redis: Redis):
        self.redis = redis
        self._breakers = {
            p["name"]: RedisCircuitBreaker(
                service=f"llm:{p['name']}",
                redis=redis,
                failure_threshold=3,  # 连续 3 次失败就熔断（LLM 超时成本高）
                recovery_timeout=60,  # 60s 后半开探测
            )
            for p in self.PROVIDERS
        }

    async def complete(self, messages: list, **kwargs) -> tuple[str, str]:
        """返回 (content, provider_name)，调用方可知道用了哪个 Provider"""
        last_err = None
        for provider in self.PROVIDERS:
            breaker = self._breakers[provider["name"]]
            try:
                content = await breaker.call(
                    self._http_call(provider, messages, **kwargs)
                )
                if provider["name"] != "deepseek":
                    logger.warning(
                        "llm_fallback_active",
                        provider=provider["name"],
                        reason=str(last_err)[:100],
                    )
                return content, provider["name"]
            except (CircuitBreakerOpen, asyncio.TimeoutError, httpx.HTTPStatusError) as e:
                last_err = e
                continue

        raise LLMAllProvidersFailedError("所有 LLM 供应商均不可用") from last_err
```

**关于「首 token 超时」和「流式停滞超时」的区别**：

这是两个完全不同的超时场景，必须分别处理：

```python
# v1 常见写法：只有一个总超时（错误）
timeout = httpx.Timeout(30.0)  # 30s? LLM 慢时用户要等 30s 才知道失败

# v2 正确写法：首 token 超时 + 流式停滞超时分开
timeout = httpx.Timeout(
    connect=5.0,    # 建立连接：5s
    read=10.0,      # 首个 token 到达：10s（首 token 超过 10s 基本是 LLM 死了）
    write=5.0,
    pool=1.0,
)
# 流式过程中，单个 token 间隔超过 10s 用 asyncio.wait_for 包裹 yield
```

### 3.2 Redis 分布式熔断器

v1 如果用了 `pybreaker` 这类库，熔断状态只存在单个进程内存里。多实例部署时，每个实例独立计数，出现诡异现象：实例 A 已经触发熔断了，实例 B 完全不知道还在继续打 LLM API。

v2 要求熔断状态必须存 Redis，所有实例共享同一个视图。

```python
class RedisCircuitBreaker:
    """
    熔断器三个状态：
    - CLOSED（关闭）：正常通行，计数失败次数
    - OPEN（打开）：全部拒绝，等待恢复超时
    - HALF_OPEN（半开）：允许一个请求试探，成功则关闭，失败则重新打开
    
    状态存 Redis Hash，格式：cb:{service_name} → {state, failure_count, opened_at}
    """
    KEY_PREFIX = "cb:"

    def __init__(self, service: str, redis: Redis,
                 failure_threshold: int = 5,
                 recovery_timeout: int = 30):
        self.key = f"{self.KEY_PREFIX}{service}"
        self.redis = redis
        self.failure_threshold = failure_threshold
        self.recovery_timeout = recovery_timeout

    async def call(self, coro: Coroutine):
        state = (await self.redis.hget(self.key, "state") or b"closed").decode()

        if state == "open":
            opened_at = float(await self.redis.hget(self.key, "opened_at") or 0)
            if time.time() - opened_at < self.recovery_timeout:
                # 还在冷却期，直接拒绝（快速失败，不等待）
                raise CircuitBreakerOpen(f"服务 {self.key} 熔断中，请稍后重试")
            # 超过冷却期，进 half_open 试探
            await self.redis.hset(self.key, "state", "half_open")

        try:
            result = await coro
            # 成功：重置熔断器
            await self.redis.hset(self.key, mapping={
                "state": "closed",
                "failure_count": 0,
            })
            return result

        except Exception as exc:
            # 失败：增加计数，考虑是否打开熔断器
            count = await self.redis.hincrby(self.key, "failure_count", 1)
            if count >= self.failure_threshold or state == "half_open":
                await self.redis.hset(self.key, mapping={
                    "state": "open",
                    "opened_at": str(time.time()),
                })
                logger.error("circuit_breaker_opened",
                             service=self.key, failure_count=count)
            raise
```

**状态机流转图**：

```
         失败 >= threshold
CLOSED ──────────────────→ OPEN
  ↑                          │
  │ 探测成功                  │ recovery_timeout 到期
  │                          ↓
  └──────────────────── HALF_OPEN
          探测失败 → OPEN
```

### 3.3 上下文窗口裁剪

多轮对话最终会碰到一个不可避免的问题：历史消息太多，超过模型的 context window。v1 的处理方式大多是"直接传进去，让 LLM API 报错"——这样用户看到的是一个莫名其妙的 500 错误。

v2 的解法是主动裁剪，超限时把旧消息压缩成摘要：

```python
async def trim_context(
    messages: list[dict],
    system_prompt: str,
    max_tokens: int = 8000,
    keep_recent_turns: int = 4,
) -> list[dict]:
    """
    上下文裁剪策略：保留「system + 摘要 + 最近 N 轮」
    
    之所以不是简单截断最老的消息，是因为旧消息里可能有关键信息
    （用户一开始说了自己的订单号，中间聊了很多，不能直接丢掉）。
    用 LLM 压缩摘要比截断更智能。
    """
    # 计算当前总 token 数
    total = count_tokens(system_prompt)
    total += sum(count_tokens(m.get("content", "")) for m in messages)

    if total <= max_tokens:
        return messages  # 还没超，直接返回

    # 保留最近 N 轮（N 轮 = N*2 条消息，每轮 user+assistant）
    cutoff = keep_recent_turns * 2
    recent = messages[-cutoff:]
    older = messages[:-cutoff]

    if not older:
        # 连最近几轮都超了，只能截断，没有更好办法
        logger.warning("context_overflow_unavoidable",
                       total_tokens=total, max_tokens=max_tokens)
        return recent

    # 把旧消息压缩成摘要（用便宜的小模型，不用浪费大模型）
    dialog_text = "\n".join(
        f"{m['role'].upper()}: {m.get('content', '')[:200]}"  # 截断单条超长消息
        for m in older
    )
    summary_prompt = f"请用不超过 150 字总结以下对话的关键信息，保留：用户身份、提到的订单号/问题类型、已确认的结论：\n\n{dialog_text}"

    summary = await llm_client.complete(
        [{"role": "user", "content": summary_prompt}],
        model=settings.llm.cheap_model,  # 用便宜模型做摘要
        max_tokens=300,
    )

    logger.info("context_trimmed",
                original_turns=len(messages) // 2,
                kept_turns=keep_recent_turns,
                summary_length=len(summary))

    return [{"role": "system", "content": f"[对话历史摘要] {summary}"}] + recent
```

### 3.4 Celery 队列背压保护

Celery 默认无限接受任务。如果 Embedding API 变慢，任务积压速度超过消费速度，内存会无限增长，直到 OOM。

```python
# app/tasks/doc_pipeline.py
MAX_PENDING_PER_TENANT = 20  # 每个租户最多 20 个等待中的任务

async def submit_doc_task(doc_id: str, tenant_id: str) -> dict:
    """提交文档处理任务前，先检查队列深度"""
    # 用 Redis 计数器维护每个租户的 pending 任务数
    counter_key = f"celery:pending:{tenant_id}"
    pending = int(await redis.get(counter_key) or 0)

    if pending >= MAX_PENDING_PER_TENANT:
        raise HTTPException(
            status_code=429,
            detail={
                "error": "queue_full",
                "message": f"队列已满（{pending}/{MAX_PENDING_PER_TENANT}），请等待当前任务完成后再上传",
                "pending_count": pending,
            }
        )

    # 提交任务
    task = process_document.apply_async(
        args=[doc_id, tenant_id],
        queue=_get_priority_queue(doc_id),  # 按文档大小分优先级队列
    )

    # 计数 +1，任务完成时在 task callback 里 -1
    await redis.incr(counter_key)
    await redis.expire(counter_key, 3600)  # 1小时兜底过期，防止计数器泄漏

    return {"task_id": task.id, "status": "queued", "queue_position": pending + 1}


def _get_priority_queue(doc_id: str) -> str:
    """根据文档元数据判断优先级队列"""
    # 实际可根据文件大小、文件类型等判断
    # 这里简化为按 doc_id 后缀
    meta = get_doc_meta(doc_id)
    if meta.size_bytes < 1 * 1024 * 1024:    # < 1MB
        return "high_priority"
    elif meta.size_bytes < 50 * 1024 * 1024:  # 1-50MB
        return "low_priority"
    else:
        return "batch"
```

## 四、可扩展性：从单机到多实例

### 4.1 无状态服务的核心原则

多实例部署（Kubernetes、ECS 等）的前提是：**任何请求可以打到任意实例，结果一致**。这意味着：

```
❌ 不能放在进程内存中（多实例会不一致）：
  - 用户 Session 和对话历史
  - Circuit Breaker 熔断状态
  - Token 配额计数
  - 文档处理锁

✅ 必须放在外部存储中：
  - 对话历史 → Redis（TTL 2h）
  - LangGraph State → PostgreSQL
  - 熔断器状态 → Redis Hash
  - 配额计数 → Redis 原子操作
  - 分布式锁 → Redis SETNX
```

### 4.2 成本追踪持久化

v1 的成本追踪大多是打日志，没有结构化存储，老板问"上个月花了多少"只能去翻日志做统计。

v2 要求实时写入 Redis，支持按日/租户查询：

```python
class CostTracker:
    """
    成本追踪器，按租户+日期存 Redis Hash。
    
    Key: cost:{tenant_id}:{YYYY-MM-DD}
    Field: tokens_used, cost_rmb, request_count
    TTL: 90 天（保留三个月用于账单对账）
    """

    PRICE_PER_1K = {
        "deepseek-chat": {"prompt": 0.001, "completion": 0.002},
        "gpt-4o-mini":   {"prompt": 0.0015, "completion": 0.006},
        "claude-haiku-4-5": {"prompt": 0.00025, "completion": 0.00125},
    }

    async def record(
        self, tenant_id: str, model: str,
        prompt_tokens: int, completion_tokens: int
    ) -> None:
        date_str = datetime.utcnow().strftime("%Y-%m-%d")
        key = f"cost:{tenant_id}:{date_str}"

        price = self.PRICE_PER_1K.get(model, {"prompt": 0.001, "completion": 0.002})
        cost_rmb = (
            prompt_tokens / 1000 * price["prompt"] +
            completion_tokens / 1000 * price["completion"]
        )

        pipe = redis.pipeline()
        pipe.hincrbyfloat(key, "cost_rmb", cost_rmb)
        pipe.hincrby(key, "tokens_used", prompt_tokens + completion_tokens)
        pipe.hincrby(key, "request_count", 1)
        pipe.expire(key, 90 * 24 * 3600)
        await pipe.execute()

    async def get_daily_summary(self, tenant_id: str, date: str) -> dict:
        key = f"cost:{tenant_id}:{date}"
        data = await redis.hgetall(key)
        return {
            "date": date,
            "tenant_id": tenant_id,
            "cost_rmb": float(data.get(b"cost_rmb", 0)),
            "tokens_used": int(data.get(b"tokens_used", 0)),
            "request_count": int(data.get(b"request_count", 0)),
        }
```

### 4.3 RAG 查询结果缓存

企业客服系统里，70% 的问题是近似重复的。每次都走完整的 RAG 流水线（检索 + Rerank + LLM 生成）平均耗时 5 秒、成本约 ¥0.02。加上语义缓存后，重复问题 10ms 返回、成本 ¥0。

```python
async def rag_with_cache(query: str, tenant_id: str) -> dict:
    # 1. 生成缓存 Key（以 query 的 SHA-256 为 Key，精确字符串匹配）
    cache_key = f"rag_cache:{tenant_id}:{hashlib.sha256(query.encode()).hexdigest()}"
    cached = await redis.get(cache_key)
    if cached:
        RAG_CACHE_HIT.labels(tenant=tenant_id).inc()
        return json.loads(cached)

    RAG_CACHE_MISS.labels(tenant=tenant_id).inc()

    # 2. 缓存未命中，走完整 RAG 流水线
    result = await full_rag_pipeline(query, tenant_id)

    # 3. 写入缓存，TTL 1 小时
    await redis.setex(cache_key, 3600, json.dumps(result, ensure_ascii=False))

    return result

# 知识库更新时，主动失效该租户的所有 RAG 缓存
async def invalidate_rag_cache(tenant_id: str) -> int:
    pattern = f"rag_cache:{tenant_id}:*"
    keys = await redis.keys(pattern)
    if keys:
        await redis.delete(*keys)
    logger.info("rag_cache_invalidated", tenant_id=tenant_id, count=len(keys))
    return len(keys)
```

## 五、可观测性：从"看日志猜"到"指标说话"

### 5.1 全链路 Request ID

没有 Request ID 的系统，排查一个 bug 的过程大概是这样的：
1. 用户说"刚才查询出错了"
2. 你去翻日志，看到一堆错误，不知道哪条是他的
3. 靠时间戳和用户 ID 过滤，发现同一秒有 50 个请求
4. 放弃，告诉用户"你再试试"

有 Request ID 之后：

```
用户 → 你 → 你 grep "X-Request-ID: abc-123" → 完整链路串起来 → 5分钟定位问题
```

```python
# gateway/middleware.py
import uuid
import contextvars

request_id_var: contextvars.ContextVar[str] = contextvars.ContextVar("request_id", default="")

@app.middleware("http")
async def request_id_middleware(request: Request, call_next):
    # 优先使用客户端传入的 ID（方便前端 debug 时自己带 ID）
    req_id = request.headers.get("X-Request-ID") or str(uuid.uuid4())

    # 写入 contextvar，此后所有 async 任务自动继承这个值
    request_id_var.set(req_id)

    # structlog 全局绑定——此后所有 logger.xxx() 调用自动带 request_id
    structlog.contextvars.bind_contextvars(request_id=req_id)

    response = await call_next(request)

    # 回显给前端，方便前端上报 "这个 request_id 的请求出错了"
    response.headers["X-Request-ID"] = req_id
    return response

# 下游服务调用时透传（关键！否则链路断了）
async def call_downstream(url: str, payload: dict) -> dict:
    headers = {
        "X-Request-ID": request_id_var.get(),  # 透传
        "Authorization": f"Bearer {get_service_token()}",
    }
    resp = await http_client.post(url, json=payload, headers=headers)
    return resp.json()
```

### 6.1 Prompt 版本管理

Prompt 改了一行，RAG 回答质量可能大幅变化。没有版本管理的 Prompt 工程，等于在没有 git 的情况下改代码——出了问题不知道是哪次改动造成的。

**YAML 文件格式**：

```yaml

  - v2.0.0: 要求引用时注明「来源文档名 + 页码」
  - v2.0.0: 不确定时明确说明，而不是用模糊表达

  4. 回答简洁，不重复问题，不客套话
```

**PromptManager 加载器**：

```python
from pathlib import Path
import yaml

class PromptManager:
    """
    Prompt 版本管理器。
    - 支持按名称 + 版本号加载
    - "stable" 版本由软链接或配置文件指定（不硬编码在代码里）
    - 支持热加载，改 YAML 不需要重启服务
    """
    _cache: dict[str, dict] = {}
    _stable_map: dict[str, str] = {}

    def __init__(self, prompts_dir: str = "prompts"):
        self.base = Path(prompts_dir)
        self._load_stable_map()

    def _load_stable_map(self):
        """stable.yaml 记录每个 Prompt 的稳定版本"""
        stable_file = self.base / "stable.yaml"
        if stable_file.exists():
            self._stable_map = yaml.safe_load(stable_file.read_text())

    async def get(self, name: str, version: str = "stable") -> dict:
        if version == "stable":
            version = self._stable_map.get(name, "latest")

        cache_key = f"{name}:{version}"
        if cache_key not in self._cache:
            self._cache[cache_key] = self._load(name, version)
        return self._cache[cache_key]

    def _load(self, name: str, version: str) -> dict:
        if version == "latest":
            # 按版本号排序，取最新的
            files = sorted(self.base.glob(f"{name}/v*.yaml"))
            if not files:
                raise FileNotFoundError(f"Prompt '{name}' 不存在")
            path = files[-1]
        else:
            path = self.base / name / f"{version}.yaml"
            if not path.exists():
                raise FileNotFoundError(f"Prompt '{name}' 版本 {version} 不存在")

        return yaml.safe_load(path.read_text())

    async def set_stable(self, name: str, version: str) -> None:
        """回滚：将某个 Prompt 的稳定版本切换到指定版本"""
        self._stable_map[name] = version
        stable_file = self.base / "stable.yaml"
        stable_file.write_text(yaml.dump(self._stable_map))
        # 清空缓存，强制重新加载
        self._cache = {k: v for k, v in self._cache.items() if not k.startswith(name)}
```

### 6.2 RAG 自动化评估流水线

**核心思路**：不能等用户投诉才知道 RAG 质量变差，必须有自动化的预警机制。

触发时机有三个：
1. 有新文档入库（知识库变了）
2. Prompt 版本更新（回答策略变了）
3. 每周定时（防止模型行为漂移）

```python
# evaluation/runners/run_ragas.py

from datasets import Dataset
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_recall, context_precision

async def run_evaluation(
    rag_pipeline,
    dataset_path: str = "evaluation/datasets/golden_set.json",
    report_dir: str = "evaluation/reports",
) -> dict:
    """
    golden_set.json 格式：
    [
      {
        "question": "T3000 型号的额定电压是多少？",
        "ground_truth": "額定電壓 220V，±10% 范围内稳定工作",
        "source_doc": "T3000技术手册.pdf",
        "source_page": 23
      },
      ...
    ]
    """
    with open(dataset_path) as f:
        cases = json.load(f)

    rows = []
    for case in cases:
        answer, contexts = await rag_pipeline(case["question"])
        rows.append({
            "question": case["question"],
            "answer": answer,
            "contexts": contexts,           # list[str]，检索到的文本片段
            "ground_truth": case["ground_truth"],
        })

    scores = evaluate(
        Dataset.from_list(rows),
        metrics=[faithfulness, answer_relevancy, context_recall, context_precision],
    )

    # 保存报告快照
    report = {
        "timestamp": datetime.utcnow().isoformat(),
        "dataset_size": len(cases),
        "scores": {
            "faithfulness":         round(scores["faithfulness"], 4),
            "answer_relevancy":     round(scores["answer_relevancy"], 4),
            "context_recall":       round(scores["context_recall"], 4),
            "context_precision":    round(scores["context_precision"], 4),
        }
    }
    report_path = Path(report_dir) / f"{datetime.utcnow().strftime('%Y-%m-%d')}.json"
    report_path.write_text(json.dumps(report, ensure_ascii=False, indent=2))

    # 未达标时发钉钉告警
    THRESHOLDS = {"faithfulness": 0.75, "answer_relevancy": 0.80}
    failed = {k: v for k, v in report["scores"].items()
              if k in THRESHOLDS and v < THRESHOLDS[k]}

    if failed:
        body = "\n".join(f"- {k}: {v} (阈值: {THRESHOLDS[k]})" for k, v in failed.items())
        await send_dingtalk_alert(
            level="P2",
            title="RAG 评估指标未达标",
            body=body,
            runbook_url="https://wiki.zuru.com/runbooks/rag-quality-degraded",
        )

    return report
```

**RAGAS 四大指标的白话解释**：

| 指标 | 说明 | 常见失分原因 |
|------|------|------------|
| Faithfulness（忠诚度） | LLM 的回答是否基于检索到的文档 | LLM 使用了自己的训练知识，没用文档内容 |
| Answer Relevancy（相关性） | 回答是否切合问题 | 检索噪声太多，LLM 答非所问 |
| Context Recall（召回率） | 正确答案所需的信息是否被检索到 | 分块策略差，关键信息被切碎 |
| Context Precision（精确率） | 检索到的内容有多少是有用的 | Rerank 阈值太低，噪声太多进了 Context |

### 6.3 工具输出 Schema 验证

```typescript
 * 带指数退避的 SSE 重连 Hook
 *
 * 重试策略：100ms → 500ms（带随机抖动）→ 2s → 放弃
 * 放弃后展示"连接失败，请刷新页面"
 */
function useSSEWithRetry(
  url: string,
  onMessage: (data: string) => void,
  onError?: (err: string) => void,
) {
  const retryRef = useRef(0);
  const esRef = useRef<EventSource | null>(null);
  const MAX_RETRIES = 3;

  const connect = useCallback(() => {
    esRef.current?.close();

    const es = new EventSource(url);

    es.onmessage = (event) => {
      retryRef.current = 0;  // 收到数据，重置重试计数
      onMessage(event.data);
    };

    es.onerror = () => {
      es.close();

      const attempt = retryRef.current++;
      if (attempt >= MAX_RETRIES) {
        const errMsg = "网络连接中断，请刷新页面后重试";
        onError?.(errMsg);
        onMessage(JSON.stringify({ type: "error", content: errMsg }));
        return;
      }

      // 指数退避：100ms, 500ms, 2000ms（加随机抖动防止惊群）
      const baseDelays = [100, 500, 2000];
      const jitter = Math.random() * 100;
      const delay = baseDelays[attempt] + jitter;

      console.log(`SSE 连接中断，${delay.toFixed(0)}ms 后重连（第 ${attempt + 1}/${MAX_RETRIES} 次）`);
      setTimeout(connect, delay);
    };

    esRef.current = es;
  }, [url, onMessage, onError]);

  useEffect(() => {
    connect();
    return () => esRef.current?.close();
  }, [connect]);
}
```

### 8.1 启动强制校验

每个服务的 lifespan 里加环境变量检查，缺了哪个立刻崩溃，不要等到第一次请求才发现。

```python
# 每个服务的 app/main.py lifespan
from contextlib import asynccontextmanager

REQUIRED_ENV = {
    "L3/L4 文档服务": ["EMBED_API_KEY", "QDRANT_URL", "CELERY_BROKER_URL", "REDIS_URL"],
    "L9 Agent 服务": ["LLM_API_KEY", "REDIS_URL", "PG_DSN", "DINGTALK_ALERT_WEBHOOK"],
    "L10 Gateway":   ["JWT_SECRET", "CORS_ORIGINS", "ADMIN_PASSWORD"],
}

@asynccontextmanager
async def lifespan(app: FastAPI):
    # ── 启动阶段 ──
    # 1. 环境变量检查
    service_name = settings.service_name
    required = REQUIRED_ENV.get(service_name, [])
    missing = [k for k in required if not os.getenv(k)]
    if missing:
        raise RuntimeError(
            f"[启动失败] 服务 {service_name} 缺少必要环境变量：{missing}\n"
            f"请检查 .env 文件或 docker-compose.yml 的 environment 配置"
        )

    # 2. 外部依赖连通性检查（快速发现基础设施问题）
    await check_redis_connection()
    await check_qdrant_connection()
    if settings.pg_dsn:
        await check_postgres_connection()

    logger.info("startup_checks_passed", service=service_name)

    yield  # 服务正常运行

    # ── 关闭阶段 ──
    await graceful_shutdown()  # 等待正在进行的 LLM 流式响应完成
```

### 8.2 优雅关闭

不做优雅关闭，每次部署会截断所有正在进行的 SSE 流式响应，用户看到输出中途消失。

```python
import asyncio
from contextlib import asynccontextmanager

# 全局追踪进行中的 SSE 响应
active_streams: set[asyncio.Task] = set()

async def graceful_shutdown(timeout: float = 30.0):
    """等待正在进行的流式响应完成，最多等 30 秒"""
    if not active_streams:
        return

    logger.info("graceful_shutdown_started", active_streams=len(active_streams))
    _, pending = await asyncio.wait(active_streams, timeout=timeout)

    if pending:
        logger.warning("graceful_shutdown_timeout",
                       cancelled_streams=len(pending),
                       timeout=timeout)
        for task in pending:
            task.cancel()
    else:
        logger.info("graceful_shutdown_completed")

# 在 StreamingResponse 里注册任务
def stream_with_tracking(generator):
    async def tracked_generator():
        task = asyncio.current_task()
        active_streams.add(task)
        try:
            async for chunk in generator:
                yield chunk
        finally:
            active_streams.discard(task)
    return tracked_generator()
```

## 九、v2 升级路线图（优先级排序）

看到这里你可能觉得改动量很大，但并不是所有改动都要立刻做。按照影响面划分优先级：

### P0 — 一周内（影响安全/可用性）

这些不做，系统随时可能出重大事故：

```
□ 生产环境启动强制校验（去除默认凭据）
□ CORS 改为白名单（非 *）
□ JWT 吊销机制（登出写 Redis 黑名单）
□ LLM 客户端多 Provider Fallback
□ 上下文窗口裁剪（防 context overflow 崩溃）
```

### P1 — 两周内（影响稳定性）

这些不做，系统在高并发或外部抖动时会出问题：

```
□ Redis 分布式熔断器（LLM + Qdrant）
□ Celery 队列深度保护（每租户 20 任务上限）
□ Prometheus 指标规范化 + 钉钉告警
□ 工具写操作 requires_confirm 防重放
□ SSE 断线指数退避重连
```

### P2 — 一个月内（提升质量）

这些不做，系统能用但质量不可量化：

```
□ Prompt 版本管理（YAML versioning）
□ RAG 评估流水线（50 条 golden set + 自动触发）
□ RAG 查询结果 Redis 缓存（1h TTL）
□ 成本追踪持久化（Redis Hash + 管理面板看板）
□ 答案反馈组件（👍/👎 + 差评率告警）
□ 引用来源侧边栏预览
```

### P3 — 两个月内（完善生产）

```
□ LangGraph Checkpoint 定期清理（30 天前 PG 记录）
□ 文档增量更新（knowledge_v2 版本化，不停服）
□ 全链路 OTel 追踪（Jaeger 可视化）
□ 对话历史导出（Markdown 格式）
□ API Key 过期时间 + 最后使用记录
□ 操作审计日志（Redis Stream，90 天保留）
```
