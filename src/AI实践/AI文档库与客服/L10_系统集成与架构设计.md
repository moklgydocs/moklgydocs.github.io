## Gateway：统一路由层

Gateway 是 L10 新增的核心。它不包含任何 AI 逻辑，只做三件事：

1. **路由分发**：按路径前缀反向代理到对应的后端服务
2. **鉴权统一**：JWT/API-Key 校验在 Gateway 做，后端服务信任 Gateway 转发的请求
3. **聚合健康检查**：并发 ping 所有后端，返回统一的 `/health` 响应

```python
# zuruai/app/main.py (Gateway)
@app.get("/health")
async def health():
    services = {
        "rag":    "http://localhost:8003/health",
        "agent":  "http://localhost:8005/health",
        "multi":  "http://localhost:8006/health",
        "prod":   "http://localhost:8007/health",
    }
    results = await asyncio.gather(*[
        check_service(name, url) for name, url in services.items()
    ], return_exceptions=True)
    statuses = {name: result for name, result in zip(services, results)}
    overall = "ok" if all(s.get("status") == "ok" for s in statuses.values()) else "degraded"
    return {"status": overall, "services": statuses}
```

## 钉钉 Bot 接入

钉钉机器人通过 Webhook 接收消息，格式固定：

```python
@app.post("/webhook/dingtalk")
async def dingtalk_webhook(request: Request):
    body = await request.json()

    # 1. 签名验证（防止第三方伪造）
    timestamp = request.headers.get("timestamp")
    sign = request.headers.get("sign")
    verify_dingtalk_sign(timestamp, sign, settings.dingtalk_secret)

    # 2. 解析消息
    sender_id = body["senderStaffId"]
    text = body["text"]["content"].strip()
    session_id = f"dd-{sender_id}"

    # 3. 路由到 L9 生产 Agent
    response = await call_agent(session_id, text, user_id=sender_id)

    # 4. 回复钉钉
    await dingtalk_reply(body["sessionWebhook"], response)
    return {"errcode": 0}
```

钉钉消息限制：单次回复 < 2000 字，超长内容自动分段。Markdown 格式在钉钉群里不渲染，回复时转换为纯文本。

```yaml
# docker-compose.yml（L10 完整版）
services:
  # 基础设施
  postgres:
    image: postgres:16
    environment: { POSTGRES_DB: zuruai, ... }
    ports: ["5432:5432"]
    healthcheck: { test: ["CMD", "pg_isready", "-U", "postgres"] }

  redis:
    image: redis:7-alpine
    ports: ["6379:6379"]

    image: qdrant/qdrant:v1.9.0
    ports: ["6333:6333"]
    volumes: ["qdrant_data:/qdrant/storage"]

  # 后端服务
  gateway:
    build: { context: ./zuruai, dockerfile: Dockerfile }
    ports: ["8009:8009"]
    depends_on: { postgres: {condition: service_healthy}, redis: {condition: service_started} }

  rag-service:
    build: { context: ./L4_rag_core }
    ports: ["8003:8003"]
    environment: { QDRANT_URL: "http://qdrant:6333", REDIS_URL: "redis://redis:6379" }

  agent-service:
    build: { context: ./L6_tools }

  multi-agent:
    build: { context: ./L8_multiagent }

    build: { context: ./L9_agent_production }

    build: { context: ./L3_doc_pipeline }

    volumes: ["./monitoring/dashboards:/etc/grafana/provisioning/dashboards"]

  # 前端
  web:
    build: { context: ./web }
    ports: ["80:80"]

volumes:
  qdrant_data:
  postgres_data:
```

## 从 L1 到 L10：核心教训

### 1. 接口稳定性 >> 实现优雅

`OpenAICompatibleClient` 的接口在 L1 就定好了，L9 的 `ProductionLLMClient` 和它签名完全一致，所以 7 个关卡的节点代码一行不改。**接口比实现更难改，先把接口设计好**。

### 2. 向量存储的多租户从第一天开始

L3 就加了 `tenant_id` 过滤，否则到 L10 加钉钉接入时（多个用户共用一个 Qdrant），会发现数据隔离无法补救。

### 3. LangGraph 不是银弹

L6 的 while 循环对简单工具调用已经够用，L7 才引入 LangGraph。过早引入状态机会增加复杂度，等到"流程透明度"和"断点续传"真正成为需求时再用。

### 4. 成本监控和功能开发同等重要

L9 的 `CostTracker` 不是锦上添花，是上线必须项。没有成本监控的 AI 系统，老板看到账单的那一天就是系统下线的那一天。

### 5. 前端 UI 质量直接影响业务落地

两个功能完全相同的系统，UI 对比度不达标、缺少动效反馈、消息刷新丢失的那个，实际使用率会低 50% 以上。WCAG AA 对比度、framer-motion 动效、LocalStorage 持久化，这些"小事"决定用户是否愿意每天打开系统。
