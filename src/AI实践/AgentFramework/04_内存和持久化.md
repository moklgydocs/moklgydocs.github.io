# 内存和持久化

上一篇的 Session 让 Agent 在多轮对话里记事，但默认存内存，进程一重启就全丢。这一篇解决怎么让记忆持久化。

---

## 4.1 先想清楚问题

第 3 篇那个 `InMemoryChatHistoryProvider` 看起来很好用，但放到生产环境立刻会出问题：

- 服务重启，所有用户的对话历史没了
- 部署两个实例做负载均衡，用户这次连 A、下次连 B，B 看不到 A 上的历史
- 想做对话审计、回溯、合规留档，内存里根本没法查
- 多个 Agent 想共享同一段历史（比如客服转人工），做不到

所以生产环境一定要把历史挪到外部存储。框架的设计就是让你能换存储后端，而不动业务代码。

## 4.2 两种存储模式

框架把存储分成两类，先想清楚你用的是哪类，因为后面的 API 不一样。

**本地会话状态**——历史消息存在你自己的进程里或外部存储里，框架自己管。`AgentSession.state` 就是这个状态的入口。OpenAI Chat Completion 这种 API 本身不存历史，必须走这条路。

**服务托管存储**——历史存在模型服务那边，比如 Azure AI Foundry、OpenAI Responses API。你的 session 只保存一个 `service_session_id` 指向远端的会话。下次调用把这个 ID 带上，服务端自动把历史拼好。

判断标准很简单：看你用的 Provider 本身支不支持服务端会话。支持就走托管模式，省心；不支持就必须走本地模式，自己存。

## 4.3 内存存储的真实样子

先看默认的内存模式，理解清楚再去换持久化。

```csharp
AIAgent agent = new OpenAIClient("<your_api_key>")
    .GetChatClient(modelName)
    .AsAIAgent(instructions: "You are a helpful assistant.", name: "Assistant");

AgentSession session = await agent.CreateSessionAsync();
Console.WriteLine(await agent.RunAsync("Tell me a joke about a pirate.", session));

// 可以直接读到 session 里存的历史
var provider = agent.GetService<InMemoryChatHistoryProvider>();
List<ChatMessage>? messages = provider?.GetMessages(session);
```

注意最后两行——`agent.GetService<InMemoryChatHistoryProvider>()` 能拿到默认的 provider 实例，再 `GetMessages(session)` 就能读到这个 session 的历史。调试时很有用，看看到底存了什么进去。

## 4.4 历史太长怎么办：上 Reducer

对话一长，历史消息越积越多，每次调用都要全发给 LLM。token 越烧越多，最后撞上模型的上下文窗口直接报错。

框架给的解法是 `ChatReducer`，挂在 provider 的 options 上：

```csharp
AIAgent agent = new OpenAIClient("<your_api_key>")
    .GetChatClient(modelName)
    .AsAIAgent(new ChatClientAgentOptions
    {
        Name = "Assistant",
        ChatOptions = new() { Instructions = "You are a helpful assistant." },
        ChatHistoryProvider = new InMemoryChatHistoryProvider(new InMemoryChatHistoryProviderOptions
        {
            ChatReducer = new MessageCountingChatReducer(20)  // 只保留最近 20 条
        })
    });
```

`MessageCountingChatReducer(20)` 的意思就是每次发请求前，从历史里截最近 20 条消息。再多的就丢了。

这是个简单粗暴的方案，但够用。如果你想做更聪明的——比如把老消息让 LLM 总结成一段摘要再保留——可以自己实现 `ChatReducer` 接口。

> 注意：Reducer 只对本地历史 provider 生效。服务托管存储的简化策略由服务端自己定，框架管不着。

## 4.5 服务托管存储长什么样

走这条路的典型是 OpenAI Responses API 或 Azure AI Foundry。session 里只存一个远端会话 ID：

```csharp
AIAgent agent = new OpenAIClient("<your_api_key>")
    .GetOpenAIResponseClient(modelName)
    .AsAIAgent(instructions: "You are a helpful assistant.", name: "Assistant");

AgentSession session = await agent.CreateSessionAsync();
Console.WriteLine(await agent.RunAsync("Tell me a joke about a pirate.", session));

// 强转成具体类型，能拿到远端的会话 ID
ChatClientAgentSession typedSession = (ChatClientAgentSession)session;
Console.WriteLine(typedSession.ConversationId);
```

这个 `ConversationId` 就是远端的会话标识。下次用户回来，把这个 ID 传给 `CreateSessionAsync` 就能续上：

```csharp
AgentSession session = await chatClientAgent.CreateSessionAsync(conversationId);
```

服务托管模式的好处是省事——你不用管历史存哪、怎么取、怎么裁剪，全是服务端的事。坏处是绑定了服务商，迁移成本高，审计也得依赖服务端给的能力。

## 4.6 自己实现持久化：`ChatHistoryProvider`

这是生产环境最常用的路子。Redis、Cosmos DB、Postgres、Blob——你想存哪都行，自己实现 `ChatHistoryProvider`。

基类是 `Microsoft.Agents.AI.ChatHistoryProvider`。最简单的实现只重写两个方法：

- `ProvideChatHistoryAsync` — 调用 LLM 前触发，返回要拼进请求的历史消息
- `StoreChatHistoryAsync` — 调用 LLM 后触发，把这次的新消息存起来

下面是官方给的极简版示例，历史直接存在 session state 里：

```csharp
public sealed class SimpleInMemoryChatHistoryProvider : ChatHistoryProvider
{
    private readonly ProviderSessionState<State> _sessionState;

    public SimpleInMemoryChatHistoryProvider(
        Func<AgentSession?, State>? stateInitializer = null,
        string? stateKey = null)
    {
        this._sessionState = new ProviderSessionState<State>(
            stateInitializer ?? (_ => new State()),
            stateKey ?? this.GetType().Name);
    }

    public override string StateKey => this._sessionState.StateKey;

    protected override ValueTask<IEnumerable<ChatMessage>> ProvideChatHistoryAsync(
        InvokingContext context, CancellationToken cancellationToken = default) =>
        new(this._sessionState.GetOrInitializeState(context.Session).Messages);

    protected override ValueTask StoreChatHistoryAsync(
        InvokedContext context, CancellationToken cancellationToken = default)
    {
        var state = this._sessionState.GetOrInitializeState(context.Session);
        var allNewMessages = context.RequestMessages.Concat(context.ResponseMessages ?? []);
        state.Messages.AddRange(allNewMessages);
        this._sessionState.SaveState(context.Session, state);
        return default;
    }

    public sealed class State
    {
        [JsonPropertyName("messages")]
        public List<ChatMessage> Messages { get; set; } = [];
    }
}
```

把这个例子里的存储后端换成 Redis/DB，就是生产可用的版本。`State.Messages` 换成 `redis.StringSet(sessionKey, ...)`，`ProvideChatHistoryAsync` 里改成从 Redis 读，就这么简单。

## 4.7 一个关键设计：`ChatHistoryProvider` 是 Agent 级单例

这点很容易出问题，必须讲清楚。

`ChatHistoryProvider` 实例**挂在 Agent 上，所有 session 共用一个实例**。所以你不能把 session 相关的状态存在 provider 的字段里——会串。

错误写法（会串数据）：

```csharp
public class BadProvider : ChatHistoryProvider
{
    private List<ChatMessage> _messages = new();  // 所有 session 共用！灾难
    private string? _currentSessionId;             // 同上
}
```

正确写法——session 相关的状态存到 `AgentSession` 里。框架给了 `ProviderSessionState<T>` 这个工具类专门干这个：

```csharp
internal class MyCustomState
{
    public string? DbKey { get; set; }  // 比如 Redis 的 key
}

var sessionStateHelper = new ProviderSessionState<MyCustomState>(
    stateInitializer: currentSession => new MyCustomState { DbKey = Guid.NewGuid().ToString() },
    stateKey: this.GetType().Name,
    jsonSerializerOptions: myJsonSerializerOptions);

// 读
MyCustomState state = sessionStateHelper.GetOrInitializeState(session);

// 写
sessionStateHelper.SaveState(session, state);
```

数据库客户端（连接、Redis 多路复用器这种）可以存 provider 字段里——它们本来就是共享的。但 session 相关的 key、消息列表，必须走 session state。

## 4.8 高级实现：自己接管整个流程

简单版只重写 `ProvideChatHistoryAsync` 和 `StoreChatHistoryAsync`，基类帮你处理消息合并、过滤等流程。

如果你想完全接管（比如要做特殊的消息变换、审计、双重存储），可以重写 `InvokingCoreAsync` 和 `InvokedCoreAsync`。这两个方法分别在 LLM 调用前后触发。

`InvokingCoreAsync` 基类的默认行为：

1. 调 `ProvideChatHistoryAsync` 拿历史消息
2. 跑一个可选的 `provideOutputMessageFilter` 过滤
3. 把历史和本次输入合并成完整请求
4. 给历史消息打标记，标明它来自历史（后面存的时候要排除）

`InvokedCoreAsync` 基类的默认行为：

1. 如果调用失败，直接返回
2. 过滤掉来自历史的消息（不能重复存）
3. 把新消息传给 `StoreChatHistoryAsync`

你要重写这俩，就得自己把这些逻辑实现出来。除非有特殊需求，别这么干，用简单版就够了。

## 4.9 跨进程恢复 Session

光把历史存到 DB 还不够——用户回来时怎么续上？两种做法。

**做法一：自己存消息，新建 session 时加载**

你的 provider 在 `ProvideChatHistoryAsync` 里根据 `userId` 去 DB 把历史读出来返回。新 session 不用恢复，每次现读现拼。

**做法二：序列化整个 session**

框架支持把 `AgentSession` 整个序列化保存，下次反序列化恢复：

```csharp
JsonElement serialized = agent.SerializeSession(session);
// 把 serialized 存到 Redis/DB

// 下次取出恢复
AgentSession resumed = await agent.DeserializeSessionAsync(serialized);
```

这种做法保留了 session 的完整状态（不止消息，还有 StateBag 里的自定义数据）。

但有个硬约束——**必须用创建它的同一个 Agent/Provider 配置来恢复**。换了 Agent 实例、改了 instructions、换了模型，旧 session 不能用，上下文会失效。把 session 当成不透明对象，别手动改它的内容。

## 4.10 一个生产架构示意

把上面这些拼起来，一个能上生产的对话持久化方案大概长这样：

```
用户请求带 userId
    │
    ├─ 用 userId 去Redis查 ConversationId
    │       │
    │       └─ 查不到 → 新建 session，把 ConversationId 写回 Redis
    │       └─ 查到   → 用 ConversationId 恢复 session
    │
    ├─ 调 agent.RunAsync(message, session)
    │       │
    │       └─ 自定义 ChatHistoryProvider：
    │           - 调用前从 Postgres 读历史消息
    │           - 调用后把新消息写回 Postgres
    │
    └─ 返回响应
```

Redis 做 userId → ConversationId 的快速映射，Postgres 存完整历史。这样既能快速恢复，又能做长期审计。

## 4.11 几个注意事项

**Reducer 只管本地历史**。服务托管存储的简化是服务端的事，你挂的 Reducer 不生效。

**同一个 session 不要在多 Agent 间共用**。每个 Agent 的 instructions、模型都不一样，历史上下文不能跨 Agent 复用，否则行为不可预测。

**`AgentSession` 不透明**。不要手动改 session 内部状态，只用框架给的方法读写。版本升级时内部结构可能变。

**多线程下 session 不安全**。同一个 session 并发 `RunAsync` 会乱，要么加锁，要么用 channel 串行化。

**Python 侧只有一个 history provider 能开 `load_messages=True`**。多个 provider 都加载历史，会重复回放。C# 侧虽然没这个开关，但同理——别让多个 provider 都返回完整历史。
