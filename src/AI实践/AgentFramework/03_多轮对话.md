# 多轮对话（Session）

前两篇的 Agent 都是无状态的——每次 `RunAsync` 都是独立调用，记不住上一句。这一篇给它加上 Session，让它能在多轮对话中保持上下文。

---

## 3.1 为什么需要 Session

LLM 本身是无状态的。看下面这个例子：

```
调用1: RunAsync("我叫Alice")
       → LLM 回答："你好 Alice"
调用2: RunAsync("我叫什么名字？")
       → LLM 回答："我不知道你的名字"  ← 无状态
```

为什么？因为每次 `RunAsync` 都是一个独立的 HTTP 请求，LLM 看不到之前的对话。

要让 LLM"记住"上一轮，唯一办法是每次调用时把之前的对话历史也一起打包发给它：

```
调用2 实际发给 LLM 的内容：
  [系统指令] You are a friendly assistant.
  [用户] 我叫Alice
  [助手] 你好 Alice
  [用户] 我叫什么名字？  ← 当前问题
       → LLM 回答："你叫 Alice"  ← 因为它看到了历史
```

LLM 的"记忆"本质上是每次调用都把历史重发一遍。Session 就是帮你管理这些历史的容器。

打个比方，没 Session 像每次见客户都从头自我介绍，有 Session 像有个客户档案夹，每次见面翻出之前的记录接着聊。
## 3.2 核心抽象：`AgentSession`

`AgentSession` 是跨多次 `RunAsync` 调用共享的会话状态容器。

它包含一个核心字段 `StateBag`——任意状态容器（可变字典），存自定义数据。C# 的 `AgentSession` 是抽象基类，具体实现（通过 `CreateSessionAsync()` 创建）可能会加额外字段，比如远程聊天历史存储的 ID。

默认情况下，Agent 会自动用 `InMemoryChatHistoryProvider` 存对话历史。你只要把 `session` 传给 `RunAsync`，框架自动帮你把每轮对话存进 session，下次调用时框架自动把历史取出来、拼到请求里发给 LLM。你不需要手动维护消息列表。

但默认是内存存储，进程一退出就没了。生产环境要换成持久化存储（第 4 篇讲）。

## 3.3 最小可运行示例

```csharp
using System;
using Azure.AI.Projects;
using Azure.Identity;
using Microsoft.Agents.AI;

var endpoint = Environment.GetEnvironmentVariable("AZURE_OPENAI_ENDPOINT")
    ?? throw new InvalidOperationException("Set AZURE_OPENAI_ENDPOINT");
var deploymentName = Environment.GetEnvironmentVariable("AZURE_OPENAI_DEPLOYMENT_NAME")
    ?? "gpt-4o-mini";

AIAgent agent = new AIProjectClient(new Uri(endpoint), new DefaultAzureCredential())
    .AsAIAgent(
        model: deploymentName,
        instructions: "You are a friendly assistant. Keep your answers brief.",
        name: "ConversationAgent");

// ============ 关键：创建 Session ============
AgentSession session = await agent.CreateSessionAsync();

// 第一轮
Console.WriteLine(await agent.RunAsync("My name is Alice and I love hiking.", session));
// Agent 回答："Nice to meet you Alice! Hiking is wonderful."

// 第二轮 —— Agent 记得用户名字和爱好
Console.WriteLine(await agent.RunAsync("What do you remember about me?", session));
// Agent 回答："You're Alice and you enjoy hiking."
```

和第 1 篇的代码对比，唯一区别就是多了一个 `session` 参数：第 1 篇是 `agent.RunAsync("问题")`，这里是 `agent.RunAsync("问题", session)`。这是框架设计优雅的地方——加记忆几乎零成本。

两个关键 API：`agent.CreateSessionAsync()` 创建新会话返回 `AgentSession`，`agent.RunAsync(用户输入, session)` 带 session 调用，自动读写历史。

## 3.4 多用户场景：每个用户一个 Session

这是实战中最重要的模式——一个 Agent 服务多个用户，每个用户的对话历史要隔离。

```csharp
// 每个用户一个独立 session
AgentSession aliceSession = await agent.CreateSessionAsync();
AgentSession bobSession = await agent.CreateSessionAsync();

// Alice 的对话
await agent.RunAsync("My name is Alice.", aliceSession);
await agent.RunAsync("What's my name?", aliceSession);  // 记得是 Alice

// Bob 的对话 —— 和 Alice 完全隔离
await agent.RunAsync("My name is Bob.", bobSession);
await agent.RunAsync("What's my name?", bobSession);    // 记得是 Bob
```

Session 就是"对话作用域"，不同 Session 之间的历史互不干扰。

在 ASP.NET Core 里，通常这样组织（简化示意，省略 DI、错误处理）：

```csharp
app.MapPost("/chat/{userId}", async (string userId, string message) =>
{
    // 从缓存/数据库取出该用户的 session
    AgentSession session = await GetOrCreateSessionAsync(userId);

    // 调用 Agent
    string reply = await agent.RunAsync(message, session);

    // 持久化 session（第 4 篇细讲）
    await SaveSessionAsync(userId, session);

    return reply;
});
```

`userId` → `Session` 的映射要你自己管理。框架不管哪个用户对应哪个 session。

## 3.5 从已有 Session ID 恢复会话

场景：用户聊到一半关掉浏览器，第二天回来要继续昨天的对话。这时需要从已有 Session ID 恢复。

**方式一：从服务端会话 ID 恢复**（基础服务管理历史时）

```csharp
// 假设 conversationId 是之前保存的会话 ID
AgentSession session = await chatClientAgent.CreateSessionAsync(conversationId);
```

适用于 Azure AI Foundry 这类服务端存储历史的情况，会话 ID 由服务端分配。

**方式二：序列化/反序列化**（自定义存储时）

```csharp
// 把 session 序列化成可存储的形式（比如存到 Redis/数据库）
var serialized = agent.SerializeSession(session);

// 之后从存储取出，反序列化恢复
AgentSession resumed = await agent.DeserializeSessionAsync(serialized);
```

这里有个硬约束：**会话专用于特定的代理或服务**。使用其他代理配置或提供程序重用会话可能会导致上下文无效。Session 和 Agent 是绑定的，换了一个 Agent 实例（比如改了 instructions、换了模型），旧 Session 不能直接用——里面的历史上下文可能对新 Agent 不适用。

## 3.6 流式多轮对话

把第 1 篇的流式调用和第 3 篇的 Session 结合：

```csharp
AgentSession session = await agent.CreateSessionAsync();

// 第一轮流式
await foreach (var update in agent.RunStreamingAsync("My name is Alice.", session))
{
    Console.Write(update);
}
Console.WriteLine();

// 第二轮流式 —— 记得第一轮
await foreach (var update in agent.RunStreamingAsync("What's my name?", session))
{
    Console.Write(update);
}
```

`RunStreamingAsync` 同样接受 `session` 参数，流式和记忆可以同时用。

## 3.7 自定义 ChatHistoryProvider

默认的 `InMemoryChatHistoryProvider` 在进程内多轮对话正常，但进程重启就丢，多台服务器不共享。

通过 `ChatClientAgentOptions` 传入自定义 `ChatHistoryProvider`：

```csharp
AIAgent agent = new AIProjectClient(new Uri(endpoint), new DefaultAzureCredential())
    .AsAIAgent(
        model: deploymentName,
        options: new ChatClientAgentOptions()
        {
            ChatOptions = new() { Instructions = "You are a helpful assistant." },
            ChatHistoryProvider = new CustomChatHistoryProvider()  // ← 自定义
        });
```

`CustomChatHistoryProvider` 是你自己实现的，可以把历史存到 Redis、SQL Server / Cosmos DB、Azure Blob Storage 等任何地方。第 4 篇会详细讲怎么实现。

生产环境必须换成持久化 Provider，否则服务重启用户对话全丢、横向扩展时对话不连续、无法做对话审计。

## 3.8 三个概念别混：Session / ChatHistoryProvider / ContextProvider

这三个概念新手容易混，专门讲清楚：

- **`AgentSession`** 是单次会话容器，一次连续对话的上下文（含 StateBag）
- **`ChatHistoryProvider`** 是历史存储策略，对话历史存哪、怎么取（内存/Redis/DB）
- **`ContextProvider`** 是上下文注入器，给 Agent 注入额外上下文（如 RAG 检索结果、用户画像）

三者关系：

```
Agent.RunAsync(message, session)
        │
        ├── session 维护当前会话状态
        │
        ├── ChatHistoryProvider（通过 session 工作）
        │       ↓
        │   从存储取出历史消息 → 拼进请求
        │       ↓
        │   调用完成后把新消息写回存储
        │
        └── ContextProvider（可选）
                ↓
            注入额外上下文（如"这个用户是VIP"）
                ↓
            改写指令、附加知识
```

一句话总结：Session 是"对话实例"，ChatHistoryProvider 是 Session 背后存历史的"仓库"，ContextProvider 是往请求里塞额外东西的"插件"。

## 3.9 常见坑

**别忘了传 session**。

错误的写法：

```csharp
await agent.RunAsync("My name is Alice.");              // 没传 session
await agent.RunAsync("What's my name?");                // 不记得
```

正确的写法：

```csharp
var session = await agent.CreateSessionAsync();
await agent.RunAsync("My name is Alice.", session);     // 传 session
await agent.RunAsync("What's my name?", session);       // 记得
```

**历史会越积越长，注意 token 成本**。每次调用都把全部历史发给 LLM，意味着对话越长、请求 token 越多，成本线性上升，超过模型上下文窗口会报错。长对话要做历史裁剪（只保留最近 N 轮），或用摘要（让 LLM 总结前面的对话）。第 4 篇会涉及这块。

**Session 和 Agent 绑定**。同一个 Session 不要在多个 Agent 实例间共用。换了一个 Agent（改了 instructions、换了模型），新建 Session。

**多线程要注意**。`AgentSession` 不是线程安全的。同一个 session 不要并发调用 `RunAsync`，要么加锁，要么用 channel 串行化。

**生产环境的 Session ID 要持久化**。用户下次回来要能恢复对话。把 `session_id` 或序列化后的 session 存到 Redis/DB，用 `userId` 关联。
