# 深入核心 — Agent 架构、Provider、Middleware、Skills

入门篇讲的是"怎么用"，这一篇讲"为什么这么设计、边界在哪、怎么选"。把前面 6 篇里一带而过的几个概念展开——Agent 类型体系、中间件、技能、上下文提供程序。理解了这些，才能在面对具体需求时知道选哪个、避开哪个。

---

## 7.1 Agent 的类型体系

前面 6 篇写的所有 Agent 都是通过 `AsAIAgent()` 创建的，看起来只有一种。但框架其实有一个类型体系，不同场景要用不同的 Agent 类型。

### 7.1.1 共同的根：`AIAgent`

所有 Agent 都派生自 `AIAgent` 基类。这个基类定义了所有 Agent 类型共有的接口——主要是 `RunAsync` 和 `RunStreamingAsync`。正是因为有统一接口，才能实现"代理无关"的高级功能：工作流里能装任何 Agent，A2A 协议能暴露任何 Agent，多代理编排能组合任何 Agent。

### 7.1.2 三大类 Agent

**简单代理**——基于推理服务。给任何实现了 `IChatClient` 的客户端包一层，就是简单代理。对应的类是 `ChatClientAgent`。它原生支持函数调用、多轮对话、本地或服务端聊天历史、自定义服务端工具（MCP、代码执行）、结构化输出、流式响应。前面 6 篇用的 `AsAIAgent()` 创建的就是这种。

```csharp
var agent = new ChatClientAgent(chatClient, instructions: "You are a helpful assistant");
```

**复杂自定义代理**——直接继承 `AIAgent` 基类自己实现。完全控制代理行为和功能。适合确定性代理（不调 LLM、纯逻辑）、API 支持的代理（包装外部 API 当代理用）这种非标准场景。

**远程代理的代理**——`A2AAgent` 之类，把远程 A2A 端点包装成本地 Agent。第 6 篇讲过，调用方式跟本地 Agent 一样。

### 7.1.3 Provider 体系：`IChatClient` 是关键

简单代理背后的核心是 `IChatClient` 接口。任何推理服务只要实现了 `IChatClient`，就能被包装成 `ChatClientAgent`。这是整个 Provider 体系的基石。

框架为常见服务提供了帮助方法，让你不用手动 new `ChatClientAgent`：

| 底层服务 | 是否支持服务端历史存储 | 备注 |
|---------|-------------------|------|
| Microsoft Foundry Agent | 是 | 用代理服务做后端 |
| Foundry Models ChatCompletion | 否 | 用 Foundry 部署的任意模型 |
| Foundry Models Responses | 是 | 通过 Responses API |
| Azure OpenAI ChatCompletion | 否 | |
| Azure OpenAI Responses | 是 | |
| OpenAI ChatCompletion | 否 | |
| OpenAI Responses | 是 | |
| Anthropic | 否 | Claude 模型 |
| Ollama | 否 | 本地模型，OpenAI 兼容 API |
| 任意 `IChatClient` | 取决于实现 | 自定义服务 |

这张表里"是否支持服务端历史存储"那列很关键——它决定了你的会话历史是存在 LLM 服务那边（省心但绑定服务商），还是必须走本地 `InMemoryChatHistoryProvider` 或自定义持久化（第 4 篇讲过）。

### 7.1.4 怎么选 SDK

连同一个服务也可能有多个 SDK 能连。比如连 Azure OpenAI 可以用 Azure OpenAI SDK、OpenAI SDK、Azure AI Inference SDK。官方建议用 OpenAI SDK，因为它同时能连 OpenAI、Azure OpenAI、Foundry 模型，迁移成本低。

连 Foundry 服务用 Azure AI Projects SDK：

```csharp
AIAgent agent = new AIProjectClient(
    new Uri(serviceUrl),
    new DefaultAzureCredential())
 .AsAIAgent(
     model: deploymentName,
     instructions: "You are good at telling jokes.",
     name: "Joker");
```

连 Anthropic 用 Anthropic SDK 或 Foundry Anthropic SDK（通过 Foundry 用 Claude）：

```csharp
var client = new AnthropicClient() { ApiKey = apiKey };
AIAgent agent = client.AsAIAgent(
    model: deploymentName,
    instructions: "You are good at telling jokes.",
    name: "Joker");
```

选型时记住一个原则：**SDK 是适配层，Agent 代码不动**。你换 SDK 只影响 `IChatClient` 怎么创建，Agent 的 instructions、tools、session 代码完全不用改。

## 7.2 中间件（Middleware）— 切面逻辑的归宿

### 7.2.1 解决什么问题

写 Agent 时经常遇到这种需求：每次调用都记日志、每次调用前检查权限、每次调用后做敏感词过滤、把工具调用的结果统一格式化。这些需求有个共同点——和业务逻辑无关，是"切面"性质的关注点。

如果直接写在 Agent 调用前后，代码会越来越乱，而且没法复用。中间件就是把这些切面逻辑抽出来，按管道组织，类似 ASP.NET Core 的中间件管道。

### 7.2.2 三种中间件

框架提供三种中间件，截获的位置不同：

**代理运行中间件（Agent Run Middleware）**——截获所有 Agent 运行。能拿到进入 Agent 的消息和 Agent 返回的响应，可以在前后做处理或修改。适合日志、计时、权限检查。

**函数调用中间件（Function Calling Middleware）**——截获 Agent 执行的所有函数调用。能拿到函数名、参数、返回值。适合工具调用审计、结果转换、参数预处理。注意只对用 `FunctionInvokingChatClient` 的 Agent（比如 `ChatClientAgent`）生效。

**IChatClient 中间件**——截获对 `IChatClient` 的调用。最底层，能拿到发给推理服务的原始请求和返回。适合 token 计数、请求重试、内容过滤。

### 7.2.3 洋葱模型

多个中间件组成链，每个中间件通过 `call_next`（Python）或调用 `innerAgent`（C#）调下一个。执行顺序是洋葱模型——进去时按顺序，出来时反向：

```
代理级中间件 [A1, A2] + 运行级中间件 [R1, R2]:

A1 → A2 → R1 → R2 → Agent → R2 → R1 → A2 → A1
```

也就是说，最外层的中间件最先进入、最后退出，能"包"住整个执行过程。

### 7.2.4 C# 怎么写

C# 用函数回调 + Builder 模式注册中间件。代理运行中间件长这样：

```csharp
async Task<AgentResponse> CustomAgentRunMiddleware(
    IEnumerable<ChatMessage> messages,
    AgentSession? session,
    AgentRunOptions? options,
    AIAgent innerAgent,
    CancellationToken cancellationToken)
{
    Console.WriteLine($"输入消息数: {messages.Count()}");
    var response = await innerAgent.RunAsync(messages, session, options, cancellationToken);
    Console.WriteLine($"输出消息数: {response.Messages.Count}");
    return response;
}
```

注册到 Agent：

```csharp
var middlewareEnabledAgent = originalAgent
    .AsBuilder()
        .Use(runFunc: CustomAgentRunMiddleware, runStreamingFunc: CustomAgentRunStreamingMiddleware)
        .Use(CustomFunctionCallingMiddleware)
    .Build();
```

注意要同时提供 `runFunc` 和 `runStreamingFunc`。只提供非流式的，流式调用会降级到非流式模式跑，影响体验。

函数调用中间件的签名不一样，多一个 `next` 回调和 `FunctionInvocationContext`：

```csharp
async ValueTask<object?> CustomFunctionCallingMiddleware(
    AIAgent agent,
    FunctionInvocationContext context,
    Func<FunctionInvocationContext, CancellationToken, ValueTask<object?>> next,
    CancellationToken cancellationToken)
{
    Console.WriteLine($"调用函数: {context.Function.Name}");
    var result = await next(context, cancellationToken);
    Console.WriteLine($"函数返回: {result}");
    return result;
}
```

函数调用中间件有个特殊能力——设置 `context.Terminate = true` 能终止整个函数调用循环，阻止 LLM 进一步发请求。但要小心：终止可能导致聊天历史不一致（有函数调用但没函数结果），后续运行可能出错。除非真有强需求，别用。

### 7.2.5 注册范围：Agent 级 vs Run 级

中间件能在两个范围注册：

**Agent 级**——创建 Agent 时配置，对 Agent 的所有运行生效。适合全局都要的日志、安全。

**Run 级**——单次 `RunAsync` 调用时传，只对这次运行生效。适合按请求定制的逻辑，比如不同用户用不同的过滤策略。

执行顺序是 Agent 级中间件包在外面，Run 级中间件在里层，最里面是 Agent 本身。

### 7.2.6 中间件能终止执行

中间件可以提前终止整个执行链——设置 `context.Result` 后抛 `MiddlewareTermination` 异常（Python）或类似机制（C#）。终止后剩下的中间件和 Agent 本身都不执行，直接返回你设置的结果。

这种模式适合做拦截器：检测到敏感词直接返回拒绝消息，不让 Agent 处理；检测到无权限直接返回 403，不调 LLM 省钱。

### 7.2.7 聊天中间件和函数调用循环的关系

一个容易忽略的点：聊天中间件在**函数调用循环里**运行。意思是 Agent 一次 `RunAsync` 可能调多次 LLM（用户问题 → LLM 说要调工具 → 调完工具把结果发回 LLM → LLM 给最终答案），每次调 LLM 都会跑一遍聊天中间件。

所以聊天中间件里别做重逻辑，否则多轮工具调用时性能爆炸。

## 7.3 技能（Skills）— 可移植的能力包

### 7.3.1 技能是什么

技能是"指令 + 脚本 + 资源"的可移植包，给 Agent 提供专门功能和领域知识。一个技能就是一个目录，里面有 `SKILL.md` 描述这个技能是什么、怎么用，可选还有 `scripts/`（可执行脚本）、`references/`（参考文档）、`assets/`（模板等静态资源）。

```
expense-report/
├── SKILL.md                          # 必需 - frontmatter + 指令
├── scripts/
│   └── validate.py                   # 可执行代码
├── references/
│   └── POLICY_FAQ.md                 # 参考文档
└── assets/
    └── expense-report-template.md    # 模板等静态资源
```

### 7.3.2 技能和工具、工作流的区别

这三个概念容易混。一句话区分：**工具是单个函数，技能是一套领域知识+指令+脚本，工作流是显式流程图。**

更细的对比：

| 维度 | 技能 | 工作流 |
|------|------|--------|
| 控制权 | AI 决定怎么执行指令 | 开发者写死执行路径 |
| 复原能力 | 单个代理轮次内，失败要重试整个 | 支持检查点，失败能从上一步续 |
| 副作用 | 适合幂等或低风险操作 | 适合有副作用的操作（发邮件、收费） |
| 复杂性 | 集中的单域任务 | 多步骤业务流程、多代理协调 |

经验法则：想让 AI 自己判断"怎么做"用技能，要保证"执行哪些步骤、按什么顺序"用工作流。

### 7.3.3 渐进式披露

技能的设计哲学是"渐进式披露"——不是一开始就把所有内容塞给 LLM，而是分四个阶段按需加载：

1. **宣告**（约 100 tokens）——每次运行开始时，技能的名字和描述注入系统提示。LLM 知道有这个技能存在。
2. **加载**（小于 5000 tokens）——任务匹配时，LLM 调 `load_skill` 拉取完整 `SKILL.md` 正文。
3. **读取资源**（按需）——LLM 调 `read_skill_resource` 读补充文件。
4. **运行脚本**（按需）——LLM 调 `run_skill_script` 执行技能里的脚本。

这种设计是为了省 token——100 个技能的宣告只占 1 万 token，但实际只用一个时，只加载那一个的完整内容。

### 7.3.4 三种定义技能的方式

**基于文件**——`SKILL.md` 放在目录里，框架自动发现：

```csharp
var skillsProvider = new AgentSkillsProvider(
    Path.Combine(AppContext.BaseDirectory, "skills"));
```

可以指定多个根目录，子目录自动识别为技能。

**代码内联定义**——`AgentInlineSkill`，在代码里写：

```csharp
var codeStyleSkill = new AgentInlineSkill(
    name: "code-style",
    description: "Coding style guidelines and conventions for the team",
    instructions: """
        Use this skill when answering questions about coding style.
        1. Read the style-guide resource for the full set of rules.
        2. Answer based on those rules.
        """)
    .AddResource("style-guide", """
        # Team Coding Style Guide
        - Use 4-space indentation
        - Maximum line length: 120 characters
        """);

var skillsProvider = new AgentSkillsProvider(codeStyleSkill);
```

资源还能用 lambda 动态生成：

```csharp
.AddResource("environment", () =>
{
    string env = Environment.GetEnvironmentVariable("APP_ENV") ?? "development";
    return $"Environment: {env}";
})
```

**基于类**——继承 `AgentClassSkill<T>`，把技能封装成类，支持依赖注入：

```csharp
internal sealed class UnitConverterSkill : AgentClassSkill<UnitConverterSkill>
{
    public override AgentSkillFrontmatter Frontmatter { get; } = new(
        "unit-converter",
        "Convert between common units using a multiplication factor.");

    protected override string Instructions => """
        1. Review the conversion-table resource to find the correct factor.
        2. Use the convert script, passing the value and factor.
        """;

    [AgentSkillResource("conversion-table")]
    public string ConversionTable => """
        | From | To | Factor |
        | miles | kilometers | 1.60934 |
        """;

    [AgentSkillScript("convert")]
    private static string ConvertUnits(double value, double factor)
    {
        double result = Math.Round(value * factor, 4);
        return JsonSerializer.Serialize(new { value, factor, result });
    }
}
```

基于类的好处是能用 DI 注入依赖（数据库服务、配置等），还能打包成 NuGet 包分发。

### 7.3.5 脚本执行的安全警告

`SubprocessScriptRunner` 默认就是个简单的子进程执行器——直接 `Process.Start("python3", ...)`，没有沙盒、没有资源限制、没有审计。

官方明确警告：**仅用于演示，生产环境要自己加沙盒、资源限制、输入验证、审计追踪**。

技能里的脚本是第三方代码，要按引入第三方代码的标准对待：用前审查、只装可信来源、隔离运行、记录日志。

生产环境建议开启脚本审批：

```csharp
var skillsProvider = new AgentSkillsProvider(
    skillPath: Path.Combine(AppContext.BaseDirectory, "skills"),
    options: new AgentSkillsProviderOptions
    {
        ScriptApproval = true,  // 脚本执行前要审批
    });
```

## 7.4 上下文提供程序（Context Provider）— 动态注入上下文

### 7.4.1 和 ChatHistoryProvider 的区别

第 4 篇讲过 `ChatHistoryProvider`，专门管"对话历史存哪、怎么取"。`AIContextProvider` 是更通用的扩展点——不光能注入历史，还能注入指令、消息、工具。

两者的关系是：`ChatHistoryProvider` 本质上是 `AIContextProvider` 的特化版本，只处理消息的加载和存储。需要更灵活的上下文注入时，就用 `AIContextProvider`。

### 7.4.2 解决什么问题

典型场景：

- **RAG**——根据用户问题检索知识库，把检索到的内容作为上下文注入
- **用户画像**——从数据库读用户偏好，作为指令注入（"这个用户是 VIP，回答要更礼貌"）
- **动态工具选择**——根据对话内容每轮动态增减可用工具
- **长期记忆**——把跨会话的记忆提取出来注入

这些都是"每次调用前要往请求里塞东西"的需求，用上下文提供程序最合适。

### 7.4.3 简单实现

最简单的 `AIContextProvider` 重写两个方法：

- `ProvideAIContextAsync`——调用 LLM 前触发，返回要注入的指令、消息或工具
- `StoreAIContextAsync`——调用 LLM 后触发，从新消息里提取信息存储

看个和外部记忆服务集成的例子：

```csharp
internal sealed class SimpleServiceMemoryProvider : AIContextProvider
{
    private readonly ProviderSessionState<State> _sessionState;
    private readonly ServiceClient _client;

    public SimpleServiceMemoryProvider(ServiceClient client)
        : base(null, null)
    {
        _sessionState = new ProviderSessionState<State>(
            _ => new State(),
            this.GetType().Name);
        _client = client;
    }

    public override string StateKey => _sessionState.StateKey;

    protected override ValueTask<AIContext> ProvideAIContextAsync(InvokingContext context, CancellationToken ct = default)
    {
        var state = _sessionState.GetOrInitializeState(context.Session);
        if (state.MemoriesId == null)
            return new(new AIContext());

        var memories = _client.LoadMemories(state.MemoriesId,
            string.Join("\n", context.AIContext.Messages?.Select(x => x.Text) ?? []));

        return new(new AIContext
        {
            Messages = [new ChatMessage(ChatRole.User,
                "Here are some memories: " + string.Join("\n", memories.Select(x => x.Text)))]
        });
    }

    protected override async ValueTask StoreAIContextAsync(InvokedContext context, CancellationToken ct = default)
    {
        var state = _sessionState.GetOrInitializeState(context.Session);
        state.MemoriesId ??= _client.CreateMemoryContainer();
        _sessionState.SaveState(context.Session, state);

        await _client.StoreMemoriesAsync(state.MemoriesId,
            context.RequestMessages.Concat(context.ResponseMessages ?? []), ct);
    }

    public class State { public string? MemoriesId { get; set; } }
}
```

注册到 Agent：

```csharp
AIAgent agent = new OpenAIClient("<key>")
    .GetChatClient(modelName)
    .AsAIAgent(new ChatClientAgentOptions()
    {
        ChatOptions = new() { Instructions = "You are a helpful assistant." },
        AIContextProviders = [new SimpleServiceMemoryProvider(client)],
    });
```

### 7.4.4 和 ChatHistoryProvider 一样的设计约束

`AIContextProvider` 实例**挂在 Agent 上，所有 session 共用一个实例**。session 相关的状态（比如记忆 ID、用户画像）必须存到 `AgentSession` 里，用 `ProviderSessionState<T>` 工具类管理，不能存到 provider 的字段里——会串。

这条规则和第 4 篇讲 `ChatHistoryProvider` 时一模一样。框架里所有"Agent 级单例 + session 级状态"的扩展点都遵循同一套模式，理解了一次就贯通了。

### 7.4.5 高级实现：完全接管

简单版只重写 `ProvideAIContextAsync` 和 `StoreAIContextAsync`，基类帮你处理消息合并、过滤、打标记。

如果要完全控制，可以重写 `InvokingCoreAsync` 和 `InvokedCoreAsync`。基类的默认实现会做这些事：

`InvokingCoreAsync` 的默认行为：

1. 把输入消息列表过滤成只包含调用者传给代理的消息（排除历史和其他 provider 注入的）
2. 用过滤后的消息、现有工具和指令调 `ProvideAIContextAsync`
3. 给返回的消息打标记，标明来自这个 provider（后面存储时要排除）
4. 把返回的消息、工具、指令和现有内容合并

`InvokedCoreAsync` 的默认行为：

1. 检查运行是否失败，失败直接返回
2. 过滤掉来自历史的消息（不能重复存）
3. 把新消息传给 `StoreAIContextAsync`

重写这两个方法要自己实现这些逻辑。除非有特殊需求（比如要做自定义的消息变换、双重存储、复杂的过滤规则），别这么干，用简单版就够。

### 7.4.6 动态工具选择

上下文提供程序不只能注入消息和指令，还能**每轮动态增减工具**。配合 Foundry 工具箱能做到：根据用户问题内容，每轮选择不同的工具子集给 LLM。

这对工具数量多的场景很有用——一次性把 100 个工具都发给 LLM，token 爆炸且 LLM 容易选错。每轮只给相关的几个，准确率和成本都更好。

## 7.5 几个概念边界再梳理

到这里你可能会觉得概念有点多。把它们的关系理一下：

```
AIAgent (根类型)
  │
  ├── ChatClientAgent (基于 IChatClient 的简单代理)
  │       │
  │       ├── ChatHistoryProvider (存取对话历史)
  │       ├── AIContextProvider (注入指令/消息/工具/记忆)
  │       └── Middleware (切面逻辑：日志/安全/过滤)
  │
  ├── 自定义 Agent (继承 AIAgent)
  │
  └── A2AAgent (远程代理的本地代理)

Skill (独立概念，给 Agent 加能力包)
  └── 通过 AgentSkillsProvider 注册到 Agent
```

**记忆相关**有两层：`ChatHistoryProvider` 管对话历史，`AIContextProvider` 管更广的上下文注入（含 RAG、用户画像、长期记忆）。两者都是 Agent 级单例 + session 级状态的模式。

**能力相关**也有两层：工具（Function Tool）是单个函数，技能（Skill）是"指令+资源+脚本"的完整能力包。技能内部可以包含脚本，脚本本质也是工具，但技能多了一层"什么时候用、怎么用"的指令封装。

**切面逻辑**全靠中间件，三种中间件分别截获不同层级：Agent 运行、函数调用、IChatClient 调用。

理解了这个分类，碰到新需求时就能快速定位用哪个机制：要持久化历史 → ChatHistoryProvider；要注入 RAG 上下文 → AIContextProvider；要日志审计 → 中间件；要给 Agent 加领域知识 → 技能；要单个工具 → 函数工具；要跨服务调 Agent → A2AAgent。

## 7.6 几个注意事项

**`AIContextProvider` 和 `ChatHistoryProvider` 都是 Agent 级单例**。session 状态必须走 `ProviderSessionState<T>`，不能存 provider 字段里。这条规则前面第 4 篇讲过，这里再强调一次——所有这类扩展点都遵循同一约束。

**中间件要同时提供流式和非流式版本**。只提供非流式的，流式调用会降级，用户体验变差。`Use(sharedFunc: ...)` 那个重载只能用于"只看输入不改输出"的场景，因为它不能截获或替换输出。

**函数调用中间件只对 `ChatClientAgent` 生效**。其他 Agent 类型（自定义继承 `AIAgent` 的）不走 `FunctionInvokingChatClient`，函数调用中间件不会触发。

**`SubprocessScriptRunner` 不能上生产**。技能脚本默认执行器没有沙盒，跑第三方脚本等于让陌生代码在你进程里执行。生产环境必须自己实现带沙盒的脚本执行器，或开启脚本审批。

**终止函数调用循环会破坏历史一致性**。`context.Terminate = true` 看起来好用，但会导致聊天历史里有函数调用但没有对应结果，后续 LLM 调用可能出错。除非确定这次调用后不再继续，否则别用。

**技能的 `SKILL.md` 要控制在 500 行以内**。超出的内容拆到 `references/` 子目录，按需加载。一次性塞太多内容既费 token 又让 LLM 难以聚焦。

**聊天中间件在函数调用循环里多次执行**。一次 `RunAsync` 可能调多次 LLM（工具调用循环），每次都跑一遍聊天中间件。重逻辑放这里会严重影响性能。
