# 工作流高级模式 — 状态、检查点、事件、人机循环

第 5 篇讲了工作流的基本骨架——执行器、边缘、超级步骤、运行。那篇够你跑通简单流程，但生产环境真正用得上的是这一篇的内容：状态怎么在执行器间共享、长任务崩了怎么恢复、怎么观察工作流内部在发生什么、怎么让人介入决策。这些机制是工作流区别于"一串函数调用"的根本所在。

---

## 8.1 工作流状态 — 跨执行器共享数据

### 8.1.1 为什么需要状态

第 5 篇的工作流里，执行器之间靠消息传递数据。但有些场景消息传递不灵光：

- 多个执行器需要读同一份数据（比如一份文件内容，下游好几个执行器都要用）
- 中间结果要保留到后面很远的一个执行器用，一路透传消息太累赘
- 执行器要存自己的内部状态，让检查点能捕获

状态就是为这些场景设计的——一个工作流范围内的共享存储，执行器可以往里写、从里读，不用靠消息层层传递。

### 8.1.2 读写状态的两个 API

写状态用 `QueueStateUpdateAsync`，读状态用 `ReadStateAsync`：

```csharp
internal sealed partial class FileReadExecutor() : Executor<string, string>("FileReadExecutor")
{
    public override async ValueTask<string> HandleAsync(
        string message, IWorkflowContext context, CancellationToken ct = default)
    {
        string fileContent = File.ReadAllText(message);
        string fileId = Guid.NewGuid().ToString("N");
        await context.QueueStateUpdateAsync(fileId, fileContent, scopeName: "FileContent", ct);
        return fileId;
    }
}

internal sealed partial class WordCountingExecutor() : Executor<string, int>("WordCountingExecutor")
{
    public override async ValueTask<int> HandleAsync(
        string message, IWorkflowContext context, CancellationToken ct = default)
    {
        var fileContent = await context.ReadStateAsync<string>(message, scopeName: "FileContent", ct)
            ?? throw new InvalidOperationException("File content state not found");
        return fileContent.Split([' ', '\n', '\r'], StringSplitOptions.RemoveEmptyEntries).Length;
    }
}
```

`FileReadExecutor` 把文件内容写到状态里，返回一个 fileId 给下游。`WordCountingExecutor` 拿到 fileId 后从状态里读出内容。这样文件内容不用塞在消息里一路传下去。

### 8.1.3 作用域（Scope）

状态读写有个 `scopeName` 参数，这是状态的"命名空间"：

- `scopeName` 是 `null`——用执行器的私有默认作用域，别的执行器看不到
- `scopeName` 设成具体值（比如 `"FileContent"`）——共享作用域，所有用相同 scopeName 的执行器都能读写

要跨执行器共享状态，读写两边的 `scopeName` 必须一致。这是个常见的坑——忘了设 scopeName 或者两边写错，状态就读不到。

### 8.1.4 可见性时序——遵循超级步骤规则

这是状态机制最微妙的一点。状态的可见性遵循第 5 篇讲的超级步骤规则：

- 写状态的执行器自己，在同一个 handler 里能立即读到更新的值
- **其他执行器要等下一个超级步骤才能看到这个更新**

为什么这么设计？因为超级步骤是同步屏障，一个超级步骤里所有执行器并发执行，如果状态能即时可见，就会引入竞争条件——你写我读、我写你读，结果不可预测。延迟到下一个超级步骤才可见，保证了每个超级步骤看到的状态是一致的。

这条规则在实际写工作流时会影响设计。如果你想让执行器 A 的状态立刻被 B 看到，要么把它们放进同一个执行器（同一个 handler 内立即可见），要么接受延迟一个超级步骤。

### 8.1.5 状态隔离 — 一个容易踩的大坑

工作流是 `WorkflowBuilder` 创建的，构建后不可变。但执行器实例是普通的 .NET 对象——如果你把同一个执行器实例用在多个工作流里，它的可变状态会跨工作流共享，导致数据串台。

错误的写法：

```csharp
var executorA = new CustomExecutorA();
var executorB = new CustomExecutorB();

var builder = new WorkflowBuilder(startExecutor: executorA).AddEdge(executorA, executorB);

var workflowA = builder.Build();
var workflowB = builder.Build();
// workflowA 和 workflowB 共用同一批执行器实例，状态会串
```

正确的写法——每次构建都创建新实例：

```csharp
Workflow CreateWorkflow()
{
    var executorA = new CustomExecutorA();
    var executorB = new CustomExecutorB();
    return new WorkflowBuilder(startExecutor: executorA)
        .AddEdge(executorA, executorB)
        .Build();
}

var workflowA = CreateWorkflow();
var workflowB = CreateWorkflow();  // 独立实例，状态隔离
```

Agent 也一样——工作流里包装的 Agent 有自己的线程（会话历史），跨工作流共享会导致对话历史串。同样的解法：把 Agent 创建也包进工厂方法里。

如果执行器实例化成本高、必须共享（比如工作流作为 Agent 暴露时），有状态执行器要实现 `IResettableExecutor` 接口。框架在工作流运行之间会自动调 `ResetAsync()` 清理状态。这个机制在第 5 篇提过，这里补全它的用途——就是为状态隔离服务的。

## 8.2 检查点 — 长任务的救命稻草

### 8.2.1 解决什么问题

工作流跑到一半崩了怎么办？没有检查点，只能从头重来。长任务跑几小时甚至几天，崩一次重来是不可接受的。

检查点让你在工作流执行的特定点保存完整状态，崩了能从最近的检查点恢复，不用从头跑。适用场景：

- 长时间运行的工作流，避免故障丢失进度
- 需要暂停和恢复的工作流
- 出于审计或合规需要定期保存状态
- 跨环境或跨实例迁移工作流

### 8.2.2 检查点在超级步骤边界创建

检查点不是随便什么时候创建的——**在每个超级步骤结束时创建**，那个超级步骤里所有执行器都跑完之后。

这个设计很巧妙。超级步骤是同步屏障，超级步骤边界是工作流的"稳定点"——所有并发执行都完成了，没有中间状态。在这个点保存状态是一致的、可恢复的。如果在超级步骤中间保存，状态可能不一致，恢复后会出错。

检查点捕获的完整状态包括：

- 所有执行器的当前状态
- 下一个超级步骤的所有挂起消息
- 待处理的请求和响应（人机循环的待处理请求也算）
- 共享状态

### 8.2.3 启用检查点

要启用检查点，运行工作流时传一个 `CheckpointManager`：

```csharp
CheckpointManager checkpointManager = CheckpointManager.CreateInMemory();

StreamingRun run = await InProcessExecution
    .RunStreamingAsync(workflow, input, checkpointManager);

await foreach (WorkflowEvent evt in run.WatchStreamAsync())
{
    if (evt is SuperStepCompletedEvent superStepCompletedEvt)
    {
        CheckpointInfo? checkpoint = superStepCompletedEvt.CompletionInfo?.Checkpoint;
        // 每个超级步骤完成都会有一个检查点
    }
}

// 也能直接从 run 拿所有检查点
IReadOnlyList<CheckpointInfo> checkpoints = run.Checkpoints;
```

框架提供三种内置存储后端，都实现同一个 `CheckpointStorage` 接口，换后端不用改工作流代码：

| Provider | 持久性 | 适用场景 |
|----------|-------|---------|
| `InMemoryCheckpointStorage` | 进程内 | 测试、演示、短期工作流 |
| `FileCheckpointStorage` | 本地磁盘 | 单机工作流、本地开发 |
| `CosmosCheckpointStorage` | Azure Cosmos DB | 生产、分布式、跨进程工作流 |

### 8.2.4 从检查点恢复

两种恢复方式。

**方式一：在同一个 run 实例上恢复**

```csharp
CheckpointInfo savedCheckpoint = run.Checkpoints[5];
await run.RestoreCheckpointAsync(savedCheckpoint);

await foreach (WorkflowEvent evt in run.WatchStreamAsync())
{
    if (evt is WorkflowOutputEvent outputEvt)
        Console.WriteLine($"完成: {outputEvt.Data}");
}
```

适合工作流还没结束、要从中间某个点重跑的情况（比如某步失败了，回退重试）。

**方式二：解冻到新的 run 实例**

```csharp
CheckpointInfo savedCheckpoint = run.Checkpoints[5];
StreamingRun newRun = await InProcessExecution
    .ResumeStreamingAsync(newWorkflow, savedCheckpoint, checkpointManager);

await foreach (WorkflowEvent evt in newRun.WatchStreamAsync())
{
    if (evt is WorkflowOutputEvent outputEvt)
        Console.WriteLine($"完成: {outputEvt.Data}");
}
```

适合跨进程恢复——把检查点存到 Cosmos，新进程读出来在新 run 上续跑。这是长任务跨重启恢复的标准模式。

### 8.2.5 让执行器状态被检查点捕获

默认情况下，检查点只捕获共享状态和挂起消息，不捕获执行器的私有字段。如果你的执行器有需要被检查点保留的内部状态，要重写两个方法：

```csharp
internal sealed partial class CustomExecutor() : Executor("CustomExecutor")
{
    private const string StateKey = "CustomExecutorState";
    private List<string> _messages = new();

    [MessageHandler]
    private async ValueTask HandleAsync(string message, IWorkflowContext context)
    {
        _messages.Add(message);
        // 业务逻辑...
    }

    // 检查点保存时触发——把私有状态写到共享状态里
    protected override ValueTask OnCheckpointingAsync(IWorkflowContext context, CancellationToken ct = default)
        => context.QueueStateUpdateAsync(StateKey, _messages, ct);

    // 从检查点恢复时触发——从共享状态读回私有状态
    protected override async ValueTask OnCheckpointRestoredAsync(IWorkflowContext context, CancellationToken ct = default)
        => _messages = await context.ReadStateAsync<List<string>>(StateKey, ct) ?? new();
}
```

模式很固定：保存时把私有字段写到状态，恢复时从状态读回私有字段。如果不重写这两个方法，执行器的私有字段在跨检查点恢复时会丢失——这是常见的"怎么恢复后状态不对了"的原因。

### 8.2.6 安全注意事项

检查点存储是信任边界。官方明确警告：**切勿从不受信任或可能被篡改的源加载检查点**。

具体到不同存储：

- `FileCheckpointStorage` 需要显式 `storage_path`，没有默认目录。保护存储目录（文件权限、加密、访问控制）是开发者的责任
- `CosmosCheckpointStorage` 尽量用托管标识/RBAC，不要用账号密钥；必须用时定期轮换

Python 侧的 `FileCheckpointStorage` 和 `CosmosCheckpointStorage` 默认用受限的 unpickler，只允许内置安全类型和框架内部类型。要支持自定义类型，用 `allowed_checkpoint_types` 参数显式声明：

```python
storage = FileCheckpointStorage(
    "/tmp/checkpoints",
    allowed_checkpoint_types=["my_app.models:SafeState"],
)
```

如果威胁模型完全不允许 pickle 序列化，用 `InMemoryCheckpointStorage` 或自己实现 `CheckpointStorage`。

## 8.3 事件系统 — 工作流的可观测性

### 8.3.1 事件是什么

工作流执行过程中，框架在关键点会发出事件。这些事件是观察工作流内部的窗口——你能知道哪个执行器在跑、哪个超级步骤完成了、什么时候产出结果、哪里出错了。所有事件都通过流式方式实时推送，订阅 `WatchStreamAsync()` 就能收到。

### 8.3.2 内置事件类型

按类别分：

**工作流生命周期事件**：

- `WorkflowStartedEvent`——工作流开始
- `WorkflowOutputEvent`——工作流产出最终输出
- `WorkflowErrorEvent`——工作流出错
- `WorkflowWarningEvent`——工作流遇到警告

**执行器事件**：

- `ExecutorInvokedEvent`——执行器开始处理
- `ExecutorCompletedEvent`——执行器完成处理
- `ExecutorFailedEvent`——执行器出错
- `AgentResponseEvent`——Agent 运行产出输出
- `AgentResponseUpdateEvent`——Agent 流式更新

**超级步骤事件**：

- `SuperStepStartedEvent`——超级步骤开始
- `SuperStepCompletedEvent`——超级步骤完成

**请求事件**：

- `RequestInfoEvent`——发出请求（人机循环用）

### 8.3.3 订阅事件

```csharp
await foreach (WorkflowEvent evt in run.WatchStreamAsync())
{
    switch (evt)
    {
        case ExecutorInvokedEvent invoke:
            Console.WriteLine($"开始 {invoke.ExecutorId}");
            break;

        case ExecutorCompletedEvent complete:
            Console.WriteLine($"完成 {complete.ExecutorId}: {complete.Data}");
            break;

        case WorkflowOutputEvent output:
            Console.WriteLine($"工作流输出: {output.Data}");
            return;

        case WorkflowErrorEvent error:
            Console.WriteLine($"工作流出错: {error.Exception}");
            return;
    }
}
```

用 C# 的模式匹配 switch 处理不同事件类型是最自然的写法。每个事件类型带的数据不同，比如 `ExecutorCompletedEvent` 有 `ExecutorId` 和 `Data`，`SuperStepCompletedEvent` 带检查点信息（这就是 8.2 节里拿检查点的地方）。

### 8.3.4 自定义事件

内置事件不够用时，执行器能发自定义事件。场景比如：报告进度、发出诊断指标、中继领域数据。

定义自定义事件——继承 `WorkflowEvent`：

```csharp
internal sealed class ProgressEvent(string step) : WorkflowEvent(step) { }
internal sealed class MetricsEvent(MetricsData metrics) : WorkflowEvent(metrics) { }
```

在执行器里发事件：

```csharp
internal sealed partial class CustomExecutor() : Executor("CustomExecutor")
{
    [MessageHandler]
    private async ValueTask HandleAsync(string message, IWorkflowContext context)
    {
        await context.AddEventAsync(new ProgressEvent("验证输入"));

        // 业务逻辑...

        await context.AddEventAsync(new ProgressEvent("处理完成"));
    }
}
```

订阅时用模式匹配筛出来：

```csharp
await foreach (WorkflowEvent evt in run.WatchStreamAsync())
{
    switch (evt)
    {
        case ProgressEvent progress:
            Console.WriteLine($"进度: {progress.Data}");
            break;
        case WorkflowOutputEvent output:
            Console.WriteLine($"完成: {output.Data}");
            return;
    }
}
```

自定义事件别用 `"started"`、`"status"`、`"failed"` 这几个保留类型——框架生命周期通知用的，执行器发会被忽略并记录警告。

### 8.3.5 事件和中间件的区别

事件和第 7 篇的中间件都涉及"观察"工作流，但定位不同：

- **事件**是单向通知——执行器告诉外界"我干了什么"，外界只能听不能改
- **中间件**是双向拦截——能修改请求和响应，能终止执行

需要观察和记录用事件，需要修改和控制用中间件。

## 8.4 人机循环（Human-in-the-Loop）— 让人介入决策

### 8.4.1 解决什么问题

有些工作流步骤不能让 LLM 或代码自动决策，必须人来拍板：

- 工具调用要审批——发邮件、转账、删数据这种敏感操作
- 关键节点要人确认——生成的报告要人审过后再发
- 需要人提供 LLM 拿不到的信息——比如让用户选一个方案

人机循环（HITL）就是为这些场景设计的。框架通过"请求/响应"机制实现——执行器把请求发到工作流外部，等待响应，收到响应后继续执行。

### 8.4.2 RequestPort — 请求/响应的通道

`RequestPort` 是个特殊的通信通道，挂在工作流入口。执行器通过它发请求，外部系统监听请求、处理、把响应发回来，框架自动路由给原执行器。

看个猜数字游戏的例子。工作流让执行器判断人猜的数字对不对，不对就提示"大了"或"小了"，让人再猜。

先创建 RequestPort：

```csharp
var numberRequestPort = RequestPort.Create<NumberSignal, int>("GuessNumber");
```

`NumberSignal` 是请求类型（提示信号），`int` 是响应类型（人的猜测）。

构建工作流——RequestPort 作为起始节点，连到 JudgeExecutor，JudgeExecutor 又连回 RequestPort：

```csharp
JudgeExecutor judgeExecutor = new(42);
var workflow = new WorkflowBuilder(numberRequestPort)
    .AddEdge(numberRequestPort, judgeExecutor)
    .AddEdge(judgeExecutor, numberRequestPort)
    .WithOutputFrom(judgeExecutor)
    .Build();
```

JudgeExecutor 的逻辑：

```csharp
internal enum NumberSignal { Init, Above, Below }

internal sealed class JudgeExecutor() : Executor<int>("Judge")
{
    private readonly int _targetNumber;
    private int _tries;

    public JudgeExecutor(int targetNumber) : this() => _targetNumber = targetNumber;

    public override async ValueTask HandleAsync(int message, IWorkflowContext context, CancellationToken ct = default)
    {
        _tries++;
        if (message == _targetNumber)
        {
            await context.YieldOutputAsync($"{_targetNumber} 在 {_tries} 次尝试后找到！", ct);
        }
        else if (message < _targetNumber)
        {
            await context.SendMessageAsync(NumberSignal.Below, cancellationToken: ct);
        }
        else
        {
            await context.SendMessageAsync(NumberSignal.Above, cancellationToken: ct);
        }
    }
}
```

执行器判断完后把信号发回 RequestPort，RequestPort 会发出 `RequestInfoEvent`，外部监听这个事件、获取人的输入、把响应发回来。

### 8.4.3 外部怎么处理请求

工作流跑起来后，监听事件流里的 `RequestInfoEvent`：

```csharp
await using StreamingRun handle = await InProcessExecution.RunStreamingAsync(workflow, NumberSignal.Init);

await foreach (WorkflowEvent evt in handle.WatchStreamAsync())
{
    switch (evt)
    {
        case RequestInfoEvent requestInputEvt:
            // 从人那里拿到猜测
            int guess = GetGuessFromHuman();
            // 把响应发回工作流
            await handle.SendResponseAsync(requestInputEvt.Request.CreateResponse(guess));
            break;

        case WorkflowOutputEvent outputEvt:
            Console.WriteLine($"工作流完成: {outputEvt.Data}");
            return;
    }
}
```

关键流程：监听 `RequestInfoEvent` → 处理请求（这里是问人）→ 用 `SendResponseAsync` 把响应发回。框架自动把响应路由到发请求的那个执行器，执行器继续处理。

`GetGuessFromHuman()` 这一步是你的代码——可以是从控制台读、从 Web UI 拿、从消息队列收，框架不管。这就是"请求/响应"模式的灵活性——把"谁来响应"完全解耦。

### 8.4.4 工具审批 — HITL 的特化场景

上面是用 `RequestPort` 自定义请求/响应。更常见的场景是工具审批——Agent 要调用某个敏感工具（比如发邮件、转账），必须等人批准。

这种场景不需要你自己搭 RequestPort，框架在代理编排（顺序、并发、群组聊天工作流）里内置了工具审批机制。Agent 调用需要审批的工具时，工作流自动暂停，发出 `RequestInfoEvent`，事件负载是 `ToolApprovalRequestContent`（包含工具名、参数等）。外部批准或拒绝后，工作流继续或终止。

和处理普通 `RequestInfoEvent` 的代码一样——监听事件、处理、发响应。区别只是事件负载的类型不同。

### 8.4.5 检查点和请求的关系

人机循环的请求是异步的——发出去要等人响应，可能等几小时甚至几天。这期间工作流是暂停的。如果这时候进程崩了，待处理的请求会丢失吗？

不会。**检查点会保存待处理的请求**。从检查点恢复时，待处理的请求会重新作为 `RequestInfoEvent` 发出，让你重新捕获和响应。

注意一个限制：**恢复时不能直接提供响应**，必须监听重新发出的事件，用标准响应机制响应。这是为了保持恢复流程的一致性——不管是不是从检查点恢复，处理请求的代码都一样。

## 8.5 几个注意事项

**状态可见性的超级步骤延迟**。执行器 A 写了状态，执行器 B 在同一个超级步骤里读不到——要等下一个超级步骤。如果 B 急着用，要么把 A 和 B 放进同一个执行器，要么调整工作流拓扑让它们分属不同超级步骤。

**忘了设 `scopeName` 导致状态读不到**。跨执行器共享状态时，读写两边的 `scopeName` 必须一致。一边写了 `scopeName: "FileContent"`，另一边读时 `scopeName: null` 或写错名字，就读到 null。

**执行器实例跨工作流共享导致状态串台**。这是状态隔离的核心问题。要么每次 `Build()` 前重新 new 执行器，要么实现 `IResettableExecutor`。Agent 同理——工作流里的 Agent 有自己的会话线程，跨工作流共享会串历史。

**执行器私有状态没被检查点捕获**。执行器有私有字段，没重写 `OnCheckpointingAsync` 和 `OnCheckpointRestoredAsync`，跨检查点恢复后字段丢失。这是"恢复后状态不对"的最常见原因。

**从不可信源加载检查点**。检查点存储是信任边界。生产环境必须保护存储位置（Cosmos 用 RBAC、文件存储设权限），不要让不受信任的代码或用户能写入。Python 侧尤其注意 pickle 反序列化的风险。

**人机循环的响应不能在恢复时直接提供**。从检查点恢复有待处理请求时，必须监听重新发出的 `RequestInfoEvent`，用 `SendResponseAsync` 响应。不能在 `ResumeStreamingAsync` 调用时直接传响应。

**事件类型用了保留名**。自定义事件不要用 `"started"`、`"status"`、`"failed"` 这几个框架保留类型，会被忽略。
